# 安全

谁会来攻击、攻击什么，以及所有模块共同遵守的安全规则。各模块自己的安全设计写在各自的文档里，这里只写跨模块的部分，并链接过去。

## 要求

- 不能被人查到漏洞：鉴权、计费、出站请求这些高风险路径都有明确的规则和测试。
- 影响用户体验的安全措施（限流、自动暂停、自动吊销、过滤等）一律做成配置项，不写死；默认值由负责人决定。

## 威胁模型

| 来源 | 典型手法 | 主要防护 |
|---|---|---|
| 外部攻击者 | 盗 key、撞库、SSRF、注入、计费溢出、DDoS | 下文「安全基线」「防攻击」「账户安全」 |
| 恶意用户 | 跨租户访问、刷注册赠送的额度、用盗来的信用卡充值、通过我们滥用上游导致供应商账号被封 | 下文「租户隔离」「防滥用」「内容安全」；计费的[风控状态](domains/billing.md#风控状态) |
| 不可信的上游 | 篡改输出、偷换模型、虚报用量、偷看提示词 | [端点评估](domains/quality.md)的篡改与真伪检测；计费的[成本对账](domains/billing.md#供应商成本) |
| 内部风险 | 运营 agent 被操纵、节点被攻破、密钥泄露 | [运营](domains/operations.md)的控制面、审批、模型代理和审计；下文「密钥管理」 |
| 供应链 | 依赖投毒、CI 被篡改 | 下文「安全基线」；只部署 CI 签名的版本（见[运营的「部署与节点管理」](domains/operations.md#部署与节点管理)） |

## 安全基线

new-api 的 15 条安全公告和 sub2api 的 2 条高危公告（GitHub，2026-10）几乎都属于下面几类，逐条堵住：

| 规则 | 防的是 |
|---|---|
| 所有出站请求走同一个客户端：先由我们解析目标地址并校验 IP，拒绝内网、回环、`0.0.0.0`、IPv6 映射地址和云元数据地址，再连接校验过的 IP；经外部代理时只用隧道方式连到校验过的 IP；不跟随重定向；上游路径只按白名单拼接，不拼接用户传来的路径 | SSRF：new-api 同类问题出了 4 次；sub2api 把客户端路径拼进上游地址 |
| 用户的 API key 只存带密钥的哈希；上游凭证和号池令牌用信封加密（每份数据用单独的密钥加密，这些密钥再用主密钥加密）存储，主密钥不在数据库里；任何密钥都不进日志 | new-api 的 API key 和渠道密钥明文存库；sub2api 的账号凭证看起来也是明文 |
| 访问租户数据的查询只能通过带站点和账户范围的句柄调用，在类型层面强制；对外响应使用独立的结构，不直接序列化数据库行 | 越权访问；new-api 的用户列表接口返回了管理员令牌 |
| 对话内容按账户加密存储，对象存储不对公网开放；任何人都不能通过产品查看，只能受控导出 | 内容泄露 |
| 数量和金额在入口校验范围，运算检查溢出 | new-api 曾被在野利用的漏洞：数量溢出成负数，扣费变充值 |
| 余额不在缓存里留副本 | new-api 用旧快照整体覆盖 Redis 里的用户额度，抹掉了并发扣减，可绕过额度（GHSA-j6gc-4893-qwmp） |
| 支付回调必须验签，密钥缺失时一律拒绝，并限制请求体大小 | new-api 的 Stripe 回调验签可被绕过 |
| 生成链接和做安全判断时，不信任 Host 和转发头 | sub2api 用 Host 头拼密码重置链接 |
| 管理员和持有敏感权限的人必须开启两步验证；运营 agent 使用带权限范围的令牌，每次操作都记审计；修改供应商网址和凭证绑定的出口一律记审计 | sub2api 的管理接口只有一把共享密钥；改网址可以把上游 key 发到别处 |
| 从供应商页面、上游响应读到的内容，对运营 agent 一律视为不可信输入 | 提示注入 |
| 依赖尽量少；govulncheck 和 Dependabot 持续检查；前端包管理器默认禁止依赖的安装脚本，并延迟采用刚发布的版本 | 供应链攻击 |

## 租户隔离

两层保护：

- **代码层面**：访问租户数据的查询只能通过带站点和账户范围的句柄调用（见上文「安全基线」）。
- **数据库层面**：租户数据表启用 PostgreSQL 的行级安全。每个事务开始时设定当前的站点和账户，数据库只返回属于它们的行；即使某处代码漏了条件，也拿不到别的租户的数据。后台任务和计费这类系统流程使用单独的数据库角色，权限按需授予。

## 防滥用

以下措施全部是配置项，具体数值和开关在后台设置：

| 措施 | 做什么 | 默认 |
|---|---|---|
| 限流 | 按 key、账户、IP 分别限制请求频率和并发，不同等级可以不同 | 由平台设定，可以不限 |
| 注册防刷 | 人机验证、邮箱域名规则、邀请码 | 由站点设定（见[账户与租户的「登录与会话」](domains/accounts.md#登录与会话)） |
| 赠送额度的条件 | 要求先验证邮箱，并设总量上限 | 由站点设定 |
| key 盗用检测 | 某个 key 突然花费暴涨、出现陌生地区的 IP、调用平时不用的模型时告警；可选自动暂停该 key 并通知用户 | 告警开启，自动暂停关闭 |
| 泄露的 key | key 带醒目的前缀，以后接入 GitHub 的密钥扫描；发现泄露时通知用户，可选自动吊销 | 通知开启，自动吊销关闭 |

## 防攻击

- 入口节点放在带 DDoS 防护的服务商或 CDN 后面。
- 入口限制每个 IP 的连接数和请求大小，阈值是后台配置。

## 账户安全

- **防暴力破解**：多次登录失败后加延迟并要求人机验证。可配置，默认开启。
- **异地登录**：提醒用户。可配置，默认开启。
- **敏感修改**：改邮箱、改密码、关闭两步验证都要重新验证身份，并通知原邮箱。

## 内容安全

- **记录信号**：上游的拒绝和违规信号总是按账户记录。
- **按信号暂停账户**：某个账户频繁触发上游拒绝时自动暂停它，用来保护我们在上游的账号。可配置，默认关闭。
- **内容过滤**：关键词或分类过滤。可配置，默认关闭。更完整的敏感信息过滤和提示注入检测列在以后的范围（见[产品需求的「范围」](product.md#范围)）。

## 密钥管理

- 主密钥放在专门的密钥管理服务，或核心节点上受严格保护的文件中，另有备份。
- 所有密钥都可以轮换：
  - API key 的哈希密钥带版本号，轮换后旧 key 不会全部失效；
  - 上游凭证可以用新密钥重新加密；
  - 节点证书自动轮换（见[总体架构的「部署拓扑」](architecture.md#部署拓扑)）。

## 安全开发流程

- **授权测试矩阵**：每个接口 × 每种角色 × 每个租户的组合都有测试，越权访问必须失败。
- **模糊测试**：协议解析和格式转换做模糊测试。
- **CI 扫描**：依赖漏洞、密钥、静态安全检查（见[总体架构的「技术选型」](architecture.md#技术选型)）。
- **专项评审**：改动涉及鉴权、计费、出站请求的 PR，评审时必须专门检查安全。
- **上线前**：做一次完整的安全审查；预算允许时，请外部团队做渗透测试。
- **报告与应急**：公开安全问题的报告渠道；准备应急预案，例如批量吊销 key、轮换供应商凭证。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 影响用户体验的安全措施都是配置项 | 负责人要求。限流、自动暂停、过滤这类措施会误伤正常用户，取舍因站点和客户而异 |
| key 盗用自动暂停、按信号暂停账户、内容过滤默认关闭 | 负责人决定。告警和信号记录照常进行，需要时再开启 |
| 租户隔离在代码之外再加数据库行级安全 | 负责人要求不能被查到漏洞；只靠代码的话，漏一处条件就会越权 |
| 安全规则集中在本文 | 安全横跨所有模块，集中写才不会散落和互相矛盾；各模块的细节链接到各自文档 |

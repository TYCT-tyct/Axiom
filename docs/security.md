# 安全

谁会来攻击、攻击什么，以及所有模块共同遵守的安全规则。各模块自己的安全设计写在各自的文档里，这里只写跨模块的部分，并链接过去。

## 要求

- 高风险路径（鉴权、计费、出站请求）都有明确的规则和对应的测试，不留可被利用的漏洞。
- 影响用户体验的安全措施（限流、自动暂停、自动吊销、过滤等）一律做成配置项，不写死。默认值由负责人决定；负责人尚未表态的，由开发者先定，负责人可以随时修改。

## 威胁模型

| 来源 | 典型手法 | 主要防护 |
|---|---|---|
| 外部攻击者 | 盗 key、撞库、SSRF、注入、计费溢出、DDoS | 下文「安全基线」「防攻击」「账户安全」 |
| 恶意用户 | 跨租户访问、刷注册赠送的额度、用盗来的信用卡充值和事后拒付、通过我们滥用上游导致供应商账号被封 | 下文「租户隔离」「防滥用」「内容安全」；拒付和欺诈见计费的[风控状态](domains/billing.md#风控状态)，支付侧的防护见[支付的「防欺诈」](domains/payments.md#防欺诈) |
| 不可信的上游 | 篡改输出、偷换模型、虚报用量、偷看提示词 | [端点评估](domains/quality.md)的篡改与真伪检测；计费的[成本对账](domains/billing.md#供应商成本) |
| 内部风险 | 运营 agent 被操纵、节点被攻破、密钥泄露 | [运营](domains/operations.md)的控制面、审批、模型代理和审计；下文「密钥管理」 |
| 供应链 | 依赖投毒、CI 被篡改 | 下文「安全基线」；只部署 CI 签名的版本（见[运营的「部署与节点管理」](domains/operations.md#部署与节点管理)） |

## 安全基线

new-api 的 15 条安全公告和 sub2api 的 2 条高危公告（GitHub，2026-10）几乎都属于下面几类，逐条堵住：

| 规则 | 防的是 |
|---|---|
| 所有出站请求走同一个客户端：先由我们解析目标地址并校验 IP，拒绝内网、回环、`0.0.0.0`、IPv6 映射地址和云元数据地址，再连接校验过的 IP；经外部代理时只用隧道方式连到校验过的 IP；不跟随重定向；上游路径只按白名单拼接，不拼接用户传来的路径 | SSRF：new-api 同类问题出了 4 次；sub2api 把客户端路径拼进上游地址 |
| 用户的 API key 只存带密钥的哈希；上游凭证、号池令牌和 Webhook 签名密钥用信封加密（每份数据用单独的密钥加密，这些密钥再用主密钥加密）存储，主密钥不在数据库里；任何密钥都不进日志 | new-api 的 API key 和渠道密钥明文存库；sub2api 的账号凭证看起来也是明文 |
| 访问租户数据的查询只能通过带站点和账户范围的事务执行：模块拿不到连接池和连接，平台之外不能引用数据库驱动，设定范围的 SQL 只允许出现在平台的 `pg` 包里，由 CI 检查（见[平台](../internal/platform/README.md#不变量)）；对外响应使用独立的结构，不直接序列化数据库行 | 越权访问；new-api 的用户列表接口返回了管理员令牌 |
| 对话内容按账户加密存储，对象存储不对公网开放；任何人都不能通过产品查看，只能受控导出 | 内容泄露 |
| 数量和金额在入口校验范围，运算检查溢出 | new-api 曾被在野利用的漏洞：数量溢出成负数，扣费变充值 |
| 余额不在缓存里留副本 | new-api 用旧快照整体覆盖 Redis 里的用户额度，抹掉了并发扣减，可绕过额度（GHSA-j6gc-4893-qwmp） |
| 支付回调必须验签，密钥缺失时一律拒绝，并限制请求体大小 | new-api 的 Stripe 回调验签可被绕过 |
| 生成链接和做安全判断时，不信任 Host 和转发头 | sub2api 用 Host 头拼密码重置链接 |
| 持有敏感权限的人必须开启两步验证（见[账户与租户的「登录与会话」](domains/accounts.md#登录与会话)）；运营 agent 使用带权限范围的令牌，每次操作都记审计；修改供应商网址和凭证绑定的出口一律记审计 | sub2api 的管理接口只有一把共享密钥；改网址可以把上游 key 发到别处 |
| 从供应商页面、上游响应读到的内容，对运营 agent 一律视为不可信输入 | 提示注入 |
| 依赖尽量少；govulncheck 和 Dependabot 持续检查；前端包管理器默认禁止依赖的安装脚本，并延迟采用刚发布的版本 | 供应链攻击 |

## 租户隔离

两层保护：

- **代码层面**：访问租户数据的查询只能通过带站点和账户范围的事务执行（见上文「安全基线」）。
- **数据库层面**：租户数据表启用 PostgreSQL 的行级安全，数据库只返回本次操作被授权范围内的行。即使某处代码漏了条件，也拿不到别的租户的数据。

行级安全必须守住以下几条，否则形同虚设：

- **租户范围只在本事务内有效**：每个事务开始时设定本次操作被授权的范围，事务结束即失效。连接池复用连接时，不会把上一个请求的范围带给下一个。
- **没有设定租户范围就什么都查不到**：漏设范围时，查询返回空，而不是返回全部。
- **应用使用的数据库角色受行级安全约束**：它不是表的所有者，不是超级用户，也没有"绕过行级安全"的权限；表上强制启用行级安全，所有者也不例外。
- **范围随查询执行读取**：缓存查询计划不缓存上次事务的范围值；策略级 InitPlan 在本次语句内复用解析结果，写法与验证见 [pg](../internal/platform/pg/README.md)。
- **租户范围是一个集合**：可以包含多个站点和账户。代码先按授权规则算出操作者能访问的范围（例如站长的员工可以访问其开设的站点，见[账户与租户的「授权」](domains/accounts.md#授权)），再写入事务；数据库按集合判断。

每张表的数据属于下面一类，类别决定它的行级安全策略：

| 类别 | 例子 | 能读的范围 | 能写的范围 |
|---|---|---|---|
| 账户数据 | 工作区、API key | 包含该账户、它的站点或平台 | 同读 |
| 站点数据 | 站点配置、等级 | 包含该站点或平台 | 同读 |
| 公开数据 | 已上架的模型、名字、参考价 | 任意非空范围 | 只有平台 |
| 站点的公开配置 | 付款方式、手续费、充值限额（[支付的「收款渠道」](domains/payments.md#收款渠道)）：账户范围的充值页要读，又不是秘密 | 范围的站点等于该行的站点（账户范围的站点是授权时认出的所属站点，见[平台的「范围」](../internal/platform/README.md#范围)） | 包含该站点或平台 |
| 共享计数 | 商户账户当天的充值用量：账户范围的下单要锁住并加上它，却读不到别的账户的订单 | 范围的站点等于该行的站点 | 同读；INSERT 的 `WITH CHECK` 与 UPDATE 都按行的站点，列权限只有 SELECT、INSERT 和 `UPDATE (used)`；行里是该站点某商户当天的收款额（不含订单和用户内容），所以不跨站读写；改错最多让本站限额失准，每日对账按订单复算核对 |
| 平台数据 | 目录的改动历史、页面快照、审核项 | 只有平台 | 只有平台 |
| 审计日志 | 所有模块的审计条目（见[平台的「审计日志」](../internal/platform/README.md#审计日志)） | 条目属于账户或站点的，同账户或站点数据；不属于租户的只有平台。条目的站点和账户必须是平台登记表里登记过的组合 | 同读，只追加：应用不能改、删 |
| 队列里的待发邮件 | 出站邮件的收件人、主题和正文：等待发送期间要按任务里的 id 读回来（见[mail 的「队列与重试」](../internal/platform/mail/README.md#队列与重试)） | 同账户或站点数据 | 同读，可删；不能改。写入的 `WITH CHECK` 挡住替别的租户入队。任务行不属于任何租户，所以它的参数只有 id，worker 返回给 River 的错误也只有分类：收件人和正文不进 `river.river_job` 的参数和 `errors` 列 |

公开数据也守"没有设定范围就什么都查不到"；它不放操作者、理由、证据这类内部信息，这些是平台数据。

不同流程使用不同的数据库角色：

| 角色 | 谁用 | 能访问什么 |
|---|---|---|
| 应用角色 | 控制台、管理后台、运营接口、调用路径 | 租户数据表，受行级安全约束；审计日志只能追加和读 |
| 登录前查找 | 认 key、认会话、登录和注册在知道租户之前；后台任务按 id 找回租户（`pg.TenantTx`，第一个用的是出站邮件） | 不能登录，应用角色不能切换成它；只拥有几个专用函数，应用调用它们，把 key 的哈希、会话令牌、邮箱、邀请码或队列行的 id 换成所属的标识；只能读这些函数要用的列（见 [accounts 的「登录前的查找」](../internal/accounts/README.md#登录前的查找)） |
| 后台任务角色 | 对账、清理、同步等，每类任务一个 | 只授予该任务需要的表和字段；到期删除审计条目也由这样一个角色执行，应用角色不能删 |
| 迁移角色 | 数据库迁移 | 不能登录的所有者拥有表，迁移管理员只在迁移时切换成它，见[平台的「角色」](../internal/platform/README.md#角色)；应用运行时不使用 |

调用路径在查到 key 所属的租户后，预留和结算都在该租户的范围内执行，同样受行级安全约束。

## 防滥用

以下措施全部是配置项，具体数值和开关在后台设置：

| 措施 | 做什么 | 默认 |
|---|---|---|
| 限流 | 按 key、账户、IP 分别限制请求频率和并发，不同等级可以不同 | 由平台设定，可以不限 |
| 注册防刷 | 开放注册先验证邮箱；可开启自托管工作量证明，配置邮箱域名黑白名单，并按 IP 和邮箱域名限流；邀请码站点沿用邀请码 | 开放默认关闭；数值由站点设定（见[账户与租户的「登录与会话」](domains/accounts.md#登录与会话)） |
| 赠送额度的条件 | 要求先验证邮箱，并设总量上限 | 由站点设定 |
| key 盗用检测 | 由 `observability` 按调用记录离线检测（按 key 的指标会让标签基数失控，记录里有 IP、模型和花费的完整组合）：某个 key 突然花费暴涨、出现陌生地区的 IP、调用平时不用的模型时，告警给用户和平台运维；可选自动暂停该 key | 告警开启，自动暂停关闭 |
| 泄露的 key | 主站的 key 前缀固定，以后接入 GitHub 的密钥扫描；发现泄露时通知用户，可选自动吊销。二级站点的前缀各不相同，需要各自登记后才能扫描 | 通知开启，自动吊销关闭 |
| 平台消耗告警 | 按供应商和全平台统计上游消耗的速度，异常升高时告警给平台运维；只告警，不影响任何用户 | 开启 |

上表里发给用户的提醒，收件人、模板和站点品牌由[账户与租户的「给用户的邮件」](domains/accounts.md#给用户的邮件)负责。

## 防攻击

- 入口节点放在带 DDoS 防护的服务商或 CDN 后面。
- 按 IP 的连接数由前置的 CDN 或反向代理限制：节点只绑本机，accept 时看到的是代理的地址，节点自己按 IP 限连接只会变成限整个节点的连接数。节点自己限在途请求（总量、按 IP、按 key）和请求体大小，阈值是后台配置；按 IP 的在途上限和控制台的按 IP 计数都经 `platform/clientip` 读地址，代理写进 `AXIOM_TRUSTED_PROXIES` 后才信 `X-Forwarded-For`，所以代理后面按的是客户端自己的地址。

## 账户安全

- **防暴力破解**：登录失败按 IP 和邮箱各自计数，超限返回 429 和 `Retry-After`，不硬性锁定账户，以免别人故意输错密码把用户锁在门外。多个核心节点共用 Valkey 里的计数；Valkey 不可用时各节点按份额在进程内计数，不拒绝登录（[accounts 的「决策与理由」](../internal/accounts/README.md#决策与理由)）。可经站点 `/login-limits` 管理接口配置，默认 IP 突发 20、每分钟 10 次，邮箱 15 分钟失败 10 次、用户一小时错误码 10 次、单挑战 5 次。开放注册的人机校验是自托管工作量证明，站点可调 12 到 24 位；它只增加批量注册的成本，不替代登录限流（[账户与租户](domains/accounts.md#登录与会话)）。
- **安全事件**：登录、注册及 MFA/恢复码的猜凭证失败记结构化审计；正常会话过期、表单错误及限流拒绝不计攻击，伪造 Cookie 在 IP 预算内只计数；只存 ID 和固定分类，不存原始个人信息或凭证。每站点完整 UTC 分钟失败次数原子汇总，由后台按站点每分钟至多一次通过平台 `accounts.authentication_failures` 信号按配置阈值告警，停止失败后自动恢复，机制见 [accounts](../internal/accounts/README.md#注册登录与会话)。
- **异地登录**：提醒用户。可配置，默认开启。邮件见[账户与租户的「给用户的邮件」](domains/accounts.md#给用户的邮件)。
- **敏感修改**：改邮箱、改密码、关闭两步验证、绑定或解绑第三方身份、增删通行密钥都要重新验证身份，改密码还要通知原邮箱；通行密钥的增删要求当前密码，第三方身份的绑定和解绑要求已登录，已开启第二因素时还要求本次会话做过两步验证，变更都记审计并提升 factor_version。
- **第三方登录**：state 一次性且只存哈希，并绑定发起浏览器的 `__Host-` nonce Cookie，GitHub/Google/LinuxDO 都用 PKCE；回调只回到站点固定的登录域名，只按 provider 的 subject 匹配已绑定身份，未绑定不注册、不按邮箱合并；签发的会话也重新确认身份仍属于该用户，避免与解绑并发。client secret 用信封加密存储，不进日志。
- **通行密钥**：RP ID 与 origin 来自站点的登录域名，注册、登录和第二因素都要求 user verification；注册要求 resident key，签名计数器只增不减，回退视为凭证可能被克隆并拒绝，零只在库中也为零时接受。登录域名上的密码登录会等待通行密钥；其他控制台域名对只有通行密钥的用户把密码登录引导到登录域名，同时有 TOTP 的用户仍可用 TOTP；管理后台只认 TOTP，不会把通行密钥算作已开启的两步验证。添加或删除通行密钥与绑定/解绑第三方身份一样，提升 factor_version、吊销其他会话并记审计；增删都按用户的失败桶限制密码猜测。数据库触发器拒绝为持有通行密钥的用户写入控制台 `password` 会话，滚动发布中尚未认识通行密钥的旧节点也无法用密码绕过它。
- 会话、CSRF 防护、第三方登录的身份合并规则见[账户与租户的「登录与会话」](domains/accounts.md#登录与会话)。
- **停用边界**：账户暂停调用与用户禁用登录分开控制；用户恢复不恢复旧会话，平台授予恢复新建记录并检查权限子集。账户暂停在准入同一条 SQL 中识别，其他条件有效的 key 返回 403，调用不增加数据库往返。
- **防枚举**：key 不存在、属于别的站点、已停用、过期、删除、IP 不允许，返回完全相同的错误，别站的 key 与不存在的 key 走同一条路径；登录时邮箱不存在也算一次密码哈希。剩余的时间差（本站真实存在的 key 多一次数据库查询）只有持有这把 key 的人能利用（见[账户与租户的「API key」](domains/accounts.md#api-key)、[accounts 的「认出与准入」](../internal/accounts/README.md#认出与准入)）。

## 内容安全

- **记录信号**：上游的拒绝和违规信号总是按账户记录。
- **按信号暂停账户**：某个账户频繁触发上游拒绝时自动暂停它，用来保护我们在上游的账号。可配置，默认关闭。
- **内容过滤**：关键词或分类过滤。可配置，默认关闭。更完整的敏感信息过滤和提示注入检测列在以后的范围（见[产品需求的「范围」](product.md#范围)）。

## 网页与域名

- **控制台**：站点的品牌和主题只接受颜色、图片、文字等受限的配置项，不允许插入任意 HTML 或脚本；页面启用严格的内容安全策略（CSP），防止跨站脚本攻击。
- **管理后台**：管理监听上已经有管理后台和管理接口（`/api/admin/v1`，含资金和定价操作）；守卫只放行管理域名并要求两步验证，默认只听本机地址，现在每个节点都开。只在核心上开、只对受限来源开放尚未实现（[Issue #171](https://github.com/TYCT-tyct/Axiom/issues/171)，见[总体架构的「技术选型」](architecture.md#技术选型)）。
- **自定义域名**：站长添加域名时，通过 DNS 记录证明域名归自己所有，再自动签发证书。验证请求走统一的出站客户端。定期重新验证，域名失效时立即停用，防止被他人接管。

## 日志

- 日志只用结构化格式，用户可控的字段一律转义，防止伪造日志行。

## 密钥管理


- 主密钥放在专门的密钥管理服务，或核心节点上受严格保护的文件中，另有备份；只有负责人能接触。主密钥本身也可以轮换：用新主密钥重新加密所有数据密钥即可，数据不用重新加密。
- 当前实现使用受保护文件，不引入 Vault。主密钥的「可读版本」与「当前写版本」分开：先新增独立随机密钥、人工分发给全部节点并逐节点检查，再停写、激活、分批重包裹、确认零引用后退役，最后重启全部写入进程。M2 不支持在线切换旧进程；自动多节点分发归 M3 #322。数据库只存版本状态与用于一致性检查的摘要；命令和启动错误只报告版本号。每批重包裹与审计同事务，中断可重跑。步骤和备份保留要求见[主密钥轮换](ops/backup-restore.md#主密钥轮换)，加密与 AAD 约定见 [platform](../internal/platform/README.md#凭证加密)。
- 数据库的账号密码以密钥的方式保管，不写进代码和配置文件；数据库备份加密存放。CI 中的密钥放在 GitHub Secrets（见 [AGENTS.md 的「安全」](../AGENTS.md#安全)）。
- 所有密钥都可以轮换：
  - API key 的哈希密钥带版本号，轮换后旧 key 不会全部失效；
  - 上游凭证可以用新密钥重新加密；
  - 节点证书自动轮换（见[总体架构的「部署拓扑」](architecture.md#部署拓扑)）。

## 安全开发流程

- **授权测试矩阵**：每个接口 × 每种角色 × 每个租户的组合都有测试，越权访问必须失败。
- **模糊测试**：协议解析和格式转换做模糊测试。
- **CI 扫描**：依赖漏洞、密钥、静态安全检查（见[总体架构的「技术选型」](architecture.md#技术选型)）。
- **专项评审**：改动涉及鉴权、计费、出站请求的 PR，评审时必须专门检查安全。
- **上线前**：做一次完整的安全审查；预算允许时，请外部团队做渗透测试。
- **报告与应急**：公开安全问题的报告渠道；准备应急预案，例如批量吊销 key、轮换供应商凭证。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 影响用户体验的安全措施都是配置项 | 负责人要求。限流、自动暂停、过滤这类措施会误伤正常用户，取舍因站点和客户而异 |
| key 盗用自动暂停、按信号暂停账户、内容过滤默认关闭 | 负责人决定。告警和信号记录照常进行，需要时再开启 |
| key 盗用检测归 observability，按调用记录离线算 | 指标不能按 key 区分，一个站点几千把 key 会让指标序列爆炸；调用记录里本来就有这个 key 的 IP、模型、花费和时间，检测在后台跑、不进调用路径，同一份记录还能给出证据。否决的做法：加按 key 的指标和告警：基数失控，还会把用户行为带进监控系统 |
| 防暴力破解、异地登录提醒、盗用告警、泄露通知默认开启；泄露 key 自动吊销默认关闭 | 开发者先定，负责人可以随时修改。前四项只影响登录环节或只是通知，几乎不打扰正常使用；自动吊销会直接中断用户的调用，与负责人对自动暂停的选择保持一致 |
| 平台消耗告警默认开启 | 限流可以不限、自动暂停默认关闭时，被盗的 key 能快速耗尽我们在上游的余额；这项告警只通知运维，不影响用户 |
| 租户范围只在本事务内有效，应用角色不能绕过 | 否则连接池会串租户，或者最需要保护的计费路径反而不受约束 |
| 租户隔离在代码之外再加数据库行级安全 | 负责人要求不能被查到漏洞；只靠代码的话，漏一处条件就会越权 |
| 开放注册默认关闭，邮箱验证后才建用户，人机校验自托管，IP 与域名双限流 | 默认关闭让升级不改变任何站点；未验证的地址不占用账户；自托管校验不把访客数据交给第三方；双限流同时挡住单 IP 刷量和单一域名集中注册，复用共享计数并在 Valkey 故障时按节点分摊，不因缓存故障拒绝全部注册 |
| 安全规则集中在本文 | 安全横跨所有模块，集中写才不会散落和互相矛盾；各模块的细节链接到各自文档 |

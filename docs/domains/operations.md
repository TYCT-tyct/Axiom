# 运营

由 AI agent 执行日常运营：谁做什么、agent 怎么运行、权限和审批怎么控制、怎么通知负责人、怎么发现 bug。对应代码模块 `operations`，接口和不变量见[模块 README](../../internal/operations/README.md)；运维节点在部署拓扑中的位置见[总体架构](../architecture.md#部署拓扑)。告警和通知渠道属于记录与告警（`observability`），本文只写运营如何使用它们。

AI 运营域已冻结：代码保留，不再追加设计；本文只写现在的行为和规则。

## 要求

- 运营由 AI agent 执行，尽量减少负责人投入的时间（见[产品需求的「运营」](../product.md#运营)）。
- agent 能力上权限全面；资金和高风险操作按风险受控，高风险操作除人工审批外也可由第二个 AI 分析后审批。
- 不绑定某一家模型；不因中转站或 Axiom 自身出问题而瘫痪。
- 通知负责人用记录与告警的通知渠道（[「通知渠道」](observability.md#通知渠道)）；agent 能发现 bug 并提交 Issue。

## 设计

### 三层分工

- **固定流程（代码）**：规则明确、要求快和稳定的事：同步、检测、熔断、按规则调价、端点自动下线、故障切换。
- **运营 agent**：需要判断的事：处理异常、认领待映射的模型、协助接入供应商、裁决数据来源冲突、提出定价建议、排查故障、提 Issue。
- **负责人**：超出 agent 权限的事：审批、定策略、处理上报。

### agent 的组成

运行框架 Hermes Agent（可替换）；工具是运营接口的 MCP 工具；模型代理是运维节点上的小服务，保管模型 key、按顺序尝试模型来源、执行花费预算；规则（权限、风险分级、审批、上限、审计）在核心服务端执行；运行手册作为技能放仓库里。

- **控制全在服务端**：换框架不用改规则；负责人临时用 Claude Code 或 Codex 执行运维，也经同样的 MCP 工具、受同样约束。
- **agent 手里没有密钥**：模型 key 在模型代理；中转站由服务端浏览器工具代为登录；运营令牌在运维节点的 MCP 桥，不交给模型。
- **Hermes 加固**（部署尚未落地）：固定镜像摘要与依赖哈希；Docker 沙箱，出站只允许 MCP 桥、模型代理和浏览器工具；只开放 MCP 工具和浏览器工具，命令行、读写文件、执行代码的工具启动时检查关闭，不符拒绝启动；运行手册只读挂载，agent 的记忆只当不可信参考；对话入口只接受负责人账号的私聊。
- **模型来源**：模型代理登记多个来源按顺序尝试，至少一个不经过中转站也不经过 Axiom；每个来源用运维专用 key 并在厂商处设花费上限；每天花费、单任务工具调用次数和 token 有上限；全部不可用时 agent 停止，固定流程和告警照常，告警永远不依赖 agent。
- **定时巡检**：按站点和供应商周期只读巡检余额、模型和分组变化、端点健康、价格与成本、待映射模型，异常经 `alert_raise` 发出。固定规则先判断，判断不了的才交 agent；阈值和周期在控制面，agent 不能改；每轮有调用预算和页面读取上限，失败不无限重试。

### 运营接口
运营接口是 agent 改动 Axiom 的唯一入口；读供应商页面走浏览器工具。

- **契约与监听**：契约 `api/operations.yaml`，前缀 `/api/operations/v1`，只挂在核心的运营监听（`AXIOM_OPERATIONS_ADDR`）。默认关闭；打开时只接受出示 `ops` 用途客户端证书的双向 TLS（URI 备用名 `urn:axiom:node-purpose:ops`；入口节点证书没有），来源按 `AXIOM_OPERATIONS_SOURCES` 限制（只看连接地址；非回环又没配来源拒绝启动）。唯一客户端是运维节点的 MCP 桥，同时出示 `ops` 证书和运营凭证。处理器在 `cmd/axiom`，只经各模块公开接口组合；读复用管理接口的处理器。
- **不是管理接口的副本**：只暴露 agent 需要的操作；控制面、用户与平台授权、商户与收款配置、数据删除、部署与升级、服务器增减只在管理后台。一次调用只作用于一个对象，不提供批量资金写或批量高风险写。
- **统一约定**：JSON；失败体 `{"error": {"code", "message", "fields"}}`，`code` 是稳定封闭枚举；每个请求带 `X-Request-ID`，响应 `Cache-Control: no-store`；列表用键集游标（默认 50、最大 200）；金额是十进制文本，单位是站点记账货币的十亿分之一。每个调用带 `reason`（1–1000 字），可用 `X-Axiom-Run-ID` 标运行。写必须带 `Idempotency-Key`（重发返回第一次的运营操作并带 `Idempotency-Replayed: true`），可选 `dry_run`（回滚的事务里跑完全部检查，只写操作记录，不构成执行许可）；对象带 `rev` 的写要送回 `rev`，已变化答 409 `stale_revision`。请求体上限 1 MiB，写期限 30 秒、读 15 秒；外部调用不在数据库事务里做。
- **能读什么**：读不到明文密钥、供应商登录凭证和对话内容，调用记录只回元数据、费用和尝试。站点范围之外的资源和不存在的一样答 404；供应商只列平台自己的。

**读工具**（权限）：`whoami`、`operation_log_list`、`operations_list`、`operation_get`、`approvals_list`、`approval_get`、`approval_wait`、`caps_get`（`operations.read`）；`suppliers_list`、`suppliers_get`、`pending_mappings_list`（`suppliers.view`）；`models_list`、`model_get`、`prices_list`、`pricing_rules_list`（`catalog.view`、`pricing.view`）；`calls_list`、`call_get`、`alerts_list`（`calls.search`、`calls.inspect`）；`audit_list`、`audit_get`、`audit_digests`（`audit.view` 加平台范围）。

**写**：每个写带 `reason` 和 `Idempotency-Key`，回答是运营操作对象（`operation_id`、`state`、`risk`、`approval`、`result` 或 `error`）。本地完成答 200；等审批或外部调用未完成答 202；硬上限或校验拒绝答 422；状态冲突、幂等键复用答 409。

| 操作 | 风险类别 | 权限 | 默认审批 |
|---|---|---|---|
| 端点启用/停用、选用分组、映射待映射模型、上架模型 | 日常 | `suppliers.manage` / `catalog.manage` | 直接执行 |
| 下架模型 | 下架 | `catalog.manage` | 人工 |
| 发布售价、改定价规则 | 售价 | `pricing.manage`、`operations.money` | 包络内直接执行，超出人工 |
| 提出、确认供应商充值 | 充值 | `suppliers.manage`、`operations.money` | 上限内直接提出，超出人工；确认必须附付款凭证 |
| 退款 | 退款 | `refunds.manage`、`operations.money` | 人工；支付的第二人规则同时适用 |
| 赠额 | 赠额 | `credits.grant`、`operations.money` | 人工；计费的规则同时适用 |
| 发告警、恢复自己的告警；撤回自己的待审批提案 | 日常 | `operations.write` | 直接执行，告警限频 |
| 升级、增减服务器、删除数据、发布路由预设 | — | — | 不在运营接口里 |

动钱的写在契约上标 `x-axiom-money: true`，守卫另查 `operations.money`。除告警和撤回外的写都要平台范围；售价和规则只作用于主站，凭证够不着主站答 404；赠额和退款的账户或订单站点不在凭证站点里答 404。

各写的规则：

- **上下架模型**：提案时按 `rev` 和模型状态先拒绝目标一定会拒绝的。**端点开关**：审计 `supplier.endpoint.enabled`；启用不重置熔断（见[端点评估](quality.md#三条摘除通道各归各的主人)）。
- **选用分组**：第一次选用起代号、之后不变，下次同步建 key、把已映射模型变成端点；取消选用退出路由、保留代号。
- **映射待映射模型**：把分组列为待映射的名字映射到目录模型，只对该分组有效，结果是别名，下次同步后成为端点，真伪检测通过前不是 `verified`。只能映射正在等的名字到分组里还没有名字的模型（否则 409），目录没有或已下架的模型 422；供应商移除中或已移除时，端点、分组和映射的写都答 409。
- **赠额**、**退款**：按管理接口赠额/管理员退款的同一套规则校验，永远等负责人（202）；不提供线下退款。
- **告警**：`alert_raise` 发种类 `operations.agent_alert` 的信号，合并键 `<凭证 UUID>/<key>`，带严重度和摘要（最多 512 字节，按不可信文字对待）；同一个键恢复前再发只累加次数、不再通知；`alert_resolve` 只能恢复自己凭证发的；负责人给这个种类配规则和渠道才会收到。
- **撤回**：`approval_withdraw` 撤回自己的待审批提案，不建运营操作。

**状态机**：`pending_approval` → `approved`/`rejected`/`expired`/`canceled`；`approved` → `executing`/`rejected`/`expired`/`canceled`；`executing` → `succeeded`/`failed`/`unknown`；`unknown` 经对账到 `succeeded` 或 `failed`。`rejected`、`expired`、`canceled`、`failed`、`reverted` 是终态；重做就新建操作。批准的操作都在批准的事务里执行完（退款停在 `executing`）。

**权限**：运营凭证用 `accounts` 已有的权限名，另加 `operations.read`、`operations.write`、`operations.money`（敏感）、`operations.approve`（敏感）、`operations.manage`（敏感）、`refunds.manage`（敏感）。运营凭证不能持有 `operations.manage`、`operations.approve` 和 `platform_grants.manage`（代码和表的 CHECK 两处拒绝），所以 agent 不能审批自己、改策略或授予平台角色。

尚未实现：一键令牌、审批 AI、MCP 桥按任务预算、连续认证失败告警，以及计划中的工具（检测重跑、重启节点、提 Issue、取消与回滚、余额与路由预览等读）。

#### 运营凭证

- **是什么**：`accounts` 的第三种操作者：256 位随机令牌，前缀 `op-ax-v1-` 带校验位，只在创建或轮换的那次响应里出现；`accounts.agent_credentials` 只存带密钥哈希、前缀和末四位。只在运营监听有效，不能登录、调模型或调公网接口。
- **权限与范围**：有自己的权限集合、站点范围（默认所有站点，可缩小）、是否带平台范围（默认不带）和提出方厂商列表；总带 `operations.read`。授权不经账户或平台成员关系，也不套用人的会话级别和两步验证；平台级资源要平台范围。
- **生命周期**：只在管理后台创建、轮换和吊销，要 `operations.manage`、两步验证和 CSRF；不能改范围，要改就新建再吊销旧的。到期时间创建时必填且在未来。轮换时新旧令牌最多重叠 24 小时（默认 24，可设 0），再轮换时上次的旧令牌立即失效。每个请求都查数据库不缓存，到期、吊销后下一次请求即失败。
- **请求认证**：`Authorization: Bearer <token>` 加 `ops` 客户端证书；不读 Cookie，不要 CSRF 和 `Origin`，不开 CORS。缺、错、过期、吊销答 401，权限不足 403，范围外 404。
- **限频**（每张凭证、按核心节点在进程内计）：请求每分钟 600；资金写每分钟 30、每小时 300（试运行和重放也算）；发告警每小时 60。超过答 429 和 `Retry-After`。负责人可在控制面 `/operations/agent-limits` 调低四项（`requests_per_minute` 1–600、`money_writes_per_minute` 1–30、`money_writes_per_hour` 1–300、`alerts_per_hour` 1–60），按读到的版本改，审计 `agent_limits.set`，从下一个请求起生效。
- 吊销一张凭证也作废它的待审批提案。

#### MCP 映射

- **位置**：运维节点的 `axiom serve`（角色 `ops`）在回环地址 `AXIOM_MCP_ADDR` 开 MCP 监听，只服务本机 Hermes。运营凭证在 `AXIOM_OPERATIONS_TOKEN_FILE`（只能属主可读），每次工具调用重读，令牌只在桥进程里；Hermes 到桥用每次启动随机生成的本地令牌（`AXIOM_MCP_TOKEN_FILE`，0600，与运营凭证或节点证书同一文件则拒绝启动）。桥到核心用 `ops` 证书加运营凭证（`AXIOM_OPERATIONS_URL`），从不跟随重定向。
- **协议**：官方 Go SDK 的 Streamable HTTP，无会话，不开 SSE；拒绝 `Host` 非本机的请求和浏览器跨源请求；请求体上限 1 MiB。
- **工具生成**：启动时从嵌入的契约生成，一个操作一个工具（名字是 `x-mcp-name`，`x-mcp: false` 不生成）；桥只拒绝多余参数、会改变路径的路径参数和对象或数组参数，其余由核心校验；按 `GET /me` 的权限决定提供哪些工具，核心拒绝这张凭证时拒绝启动。没有任意 HTTP、shell、文件、批准、策略、凭证或部署工具；`TestBridgeToolsFollowTheContract` 守着工具名单。
- **工具语义**：核心的回答原样作为文本返回，3xx、4xx、5xx 和发不出的调用标 `isError`。每个写都要 `idempotency_key`；回答在桥这边丢了时，用同一个键再调。需要审批时返回 202 和 `approval_id`，不阻塞模型；`approval_wait` 每秒读一次，审批被决定、撤回、作废或到期就答，最迟 `wait_seconds`（1–10，默认 10）。
- **审批在带外**：批准和驳回只在管理后台，对话里说"同意"不算批准。

### 资金操作上限

上限约束 **agent 发起** 的运营操作。负责人在管理后台自己做的充值、退款、赠额按管理接口的两步验证和第二人规则执行，不占 agent 额度，同样写审计。两类上限分开计，都要 `operations.money`：**转账**（充值、退款、赠额）按站点记账货币的整数金额累计，单位 10⁻⁹ 个币种单位；**售价**（发布售价、改定价规则）按单价变动和笔数累计，不折算成金额。

#### 转账的累计金额上限
- **策略**：每个 `(类别, 站点)` 一行（站点为空是平台），类别 `money.top_up`、`money.refund`、`money.credit`。策略有币种（建了不变）、五个自主上限（单笔、日、周、按对象每日、日笔数）和三个硬上限（单笔、日、周，不低于对应自主上限）。没有策略就不动钱。
- **金额由服务端算**，不取 agent 写的数字：充值 = `原生金额 × 单位价值`（缺单位价值或汇率答 422，账户自带 key 和已移除供应商答 409）；退款 = 支付模块报价要退回的现金；赠额 = 赠出的面值；币种与策略不同时按计费的当前参考汇率折算，向上取整到 10⁻⁹。
- **窗口与判断**：固定 UTC 日和 ISO 周，按数据库时钟，计数器 `operations.cap_counters` 记 `reserved`、`committed` 和笔数。超过任一硬上限 → 422 `cap_exceeded`，不建运营操作；超过任一自主上限（含日笔数，释放的也算）→ 待审批提案；都在内 → 直接执行；两种都记入 `reserved`。自主上限只是审批线，人工批准也不能超过硬上限。提案等锁跨过 UTC 午夜答 409，新的一天重提。批准时按现在的策略重算硬上限：放宽不影响，调低到装不下以 `stale_revision` 结束并释放。
- **哪些类别不经过人**：只有充值。赠额和退款一律等负责人，自主上限对它们不起作用。
- **预留的结局**：驳回、撤回、作废、到期或批准时被目标拒绝 → 释放。充值：agent 用 `supplier_top_up_confirm` 附凭证确认到账转为 `committed`，或当天 UTC 结束时由清扫释放。赠额：批准的事务里以 agent 名义调计费同一个赠额函数（批次 ID 即运营操作 ID，只赠一次）后转 `committed`。退款：批准时冻结额度、写退款记录并以批准的负责人批准它（超过站点退款审批额度的仍要另一名管理员复核），操作停在 `executing`，任务 `operations.refund_outcome` 每分钟读结局：成功转 `committed`，失败释放，在途不动；冻结的额度或现金与提案时不同 → `stale_revision`，预留那一天已过 → 撤回冻结并 `expired`。已计入 `committed` 的不因之后的退款退回；要恢复额度只能由负责人调高上限。
- **对账**：任务 `operations.cap_reconcile` 每分钟把当前窗口计数器与 `money_actions` 加总比对；不一致就暂停该范围（`paused_at`、审计 `cap_policy.pause`、critical 告警 `operations.cap_drift`），暂停期间每笔提案都交负责人，硬上限照旧拒绝，数据库触发器兜底；负责人两步验证后按资金操作重算计数器（审计 `cap_counters.repair`）并清暂停。
- 上限是事前授权，不放在计费账本里；两者通过运营操作编号关联。

#### 售价的累计变动上限
- **包络**：每个站点一行 `operations.price_envelopes`：最低毛利率（基点）、单个模型单日变动（基点）、单日笔数、单日模型数。没有包络的站点答 422 `cap_exceeded`。
- **怎么量**：服务端从提案和当前版本算。变动 = 每个端点每个有效单价相对这个端点现价的 `|新 − 旧| ÷ 旧` 的最大值，向上取整；毛利率 = 每个端点每一项 `(售价 − 成本) ÷ 售价` 的最小值，向下取整，只看有成本的项。量不出比例（没有当前版本、端点现在没有价、分档口径变了、价格项增删或从零变非零）或成本未知，转人工。
- **判断**：量得出、毛利率不低于下限、当天变动与笔数都不超 → 直接执行并计数；否则建待审批提案，不计数、不预留。批准时重新刷新、重算、发布并计数（量不出比例的计 10000 基点）；提案被发布器换掉或当前版本变了 → `stale_revision`。计数器 `operations.price_counters` 只增不减，改回去也要再占一次变动。
- **发布售价**：`price_publish` 把自动发布器为主站某模型做的待确认提案按管理接口的同一个函数发布；永远不低于保本线，不能豁免。
- **改定价规则**：`pricing_rule_create`/`update` 按管理接口的同一个函数改主站一条规则。服务端对每种买家（站点每个等级，及有自己一层的每个账户）用 `billing.Sold.For`（见[计费的「定价」](billing.md#定价)）取改动前后实际卖的版本，不同的就是一笔变动；让某层现在卖不了（`unpriced`）的记成量不出比例的变动。合起来按包络判断，越线就回滚到保存点、建待审批提案；都在内就保留并计数，提交后本节点立即重建路由。规则 `rev` 变了 → `stale_revision`，与已有规则重复 → `conflict`。

### 控制面：只有负责人能改的设置

以下设置只能由负责人在管理后台两步验证后修改，运营接口、运营凭证和对话入口都改不了：审批策略和各类额度；转账的自主上限和硬上限；agent 限频（只能调低）；巡检周期和阈值；价格包络；模型来源和审批 AI 的配置；通知接收人；主站收款配置（见[支付](payments.md#收款渠道)）；运营凭证的创建、轮换、吊销和范围；运营接口和 agent 的启停；紧急停止后的恢复。

管理接口（`api/admin.yaml`）上的控制面：`/operations/credentials`、`/operations/cap-policies`（按版本设置，审计 `cap_policy.set`；`/repair`）、`/operations/price-envelopes`（审计 `price_envelope.set`）、`/operations/agent-limits`、`/operations/agent/stop`，要 `operations.manage`；审批在 `/operations/approvals`，要 `operations.approve`。写都要两步验证、CSRF、`reason` 和 `Idempotency-Key`。授予这两个权限本身是要两步验证的平台授权。

### 风险分级与审批
只读直接执行；日常、下架、售价和资金按「运营接口」写表里的默认审批。高风险操作（改供应商网址或凭证、移除供应商、发布路由预设、授予管理员、删除数据、增减服务器、升级）默认人工，必须进管理后台两步验证；凭证、权限、删除、部署类必须人工。不在运营接口里的高风险操作只能由负责人执行，agent 只能上报建议；供应商凭证明文不进 agent 的输入。服务端按"策略、目标模块自己的规则、硬上限"取最严的一档，由代码判定，不由 AI 判断。

- **审批记录**：`operations.approvals` 存运营操作、档位（现在只有 `human`）、状态、服务端生成的摘要、为什么要等（`reasons`）、到期时间、决定者和理由。指纹就是运营操作本身（应用角色改不了它的工具、目标和参数），所以批准的就是执行的；目标变了由目标模块按 `rev` 拒绝。
- **到期**：按数据库时钟 30 分钟，且不晚于当天 UTC 结束；到期的不能再批，不管清扫到没到。
- **批准**：先持有提出方凭证，凭证已吊销、停止或过期时什么都不执行，记 `canceled`；批准在同一事务里执行目标改动：成功 `succeeded`；目标变了（如 `stale_revision`）则回滚到保存点、操作以 `rejected` 结束；外部调用（退款）转入 `executing`。审批人不能是提出方。
- **审批页**：管理后台「运营审批」页（`/approvals`）列出并详述为什么要人决定和格式化的请求内容；agent 的理由标为不可信；只有 `decidable`（待决定、按数据库时钟未到期）的才有批准和驳回。
- **第二人规则**在目标模块的函数里，管理接口和运营接口调同一个函数；运营上限加在支付和计费的第二人规则之上，不替代它，也不能用 AI 审批代替。
- **第二个 AI 审批、一键批准令牌**未实现：AI 审批必须是与凭证 `proposer_vendors` 不同厂商的模型，找不到就转人工，控制面、第二人操作、凭证/权限/删除/部署和超硬上限的不给 AI。

### 紧急停止

- 负责人一键停止：一个事务里吊销所有运营凭证，运营监听对之后每个请求答 401，MCP 桥把它作为工具错误交给模型，桥重启时问不到 `GET /me` 就拒绝启动。
- 同一事务里作废全部待审批提案（操作和审批记 `canceled`、释放预留，回答里的 `canceled` 是个数）；`executing` 的外部调用不强行取消，按自己的期限结束，无法判断的标 `unknown` 等人工对账。
- 提案前先持有凭证行（`FOR SHARE`），所以停止要么在提案之前（提案 401），要么等它提交后一起作废。
- 恢复只有负责人两步验证后重建凭证，旧凭证和旧提案都不复活；停止和恢复记审计。

### 审计
- **操作记录**：`operations.operation_log` 记凭证认出之后的每个请求（含被守卫拒绝的）：凭证、运行 ID、工具名、理由、输入（超过 8 KiB 只记大小）、HTTP 状态、错误码、请求 ID、起止时间、运营操作编号。答案在记录写进数据库后才发出，写不进答 503；令牌不认识或超请求限频的不记。
- **审计日志**：每个改状态的操作在同一个事务里写平台审计，写不进整个改动失败。操作者：提案、执行、撤回是 `operations_agent:<凭证 ID>`；批准和驳回是负责人；后台任务是 `system:operations.*`。目标模块自己的审计以 agent 名义写在同一事务里。`detail` 不放密钥、凭证、对话内容、请求正文或供应商页面原文。
- **谁能读**：agent 读自己的记录和审批；读全平台审计和每天的摘要要 `audit.view` 和平台范围（只有站点范围 404，没有 `audit.view` 403），转给管理后台审计页的同一个处理器。条目文字在契约里标为数据、不是指令。
- **哈希链**：任务 `operations.audit_chain` 每分钟按 `(at, id)` 把已提交的审计条目接进 `operations.audit_chain`：SHA-256(前一条哈希 ‖ 条目的 RFC 8785 JSON 编码)，第一条之前是 32 个零字节，凭审计日志和链的导出就能在平台外重算；应用角色不能改、不能删链；只接早于 60 秒前、也早于本库每个开着的事务开始时刻的条目。每轮核对链头往回 1000 条，整条链每天核对一次。不一致（`late`、`missing`、`mismatch`、`broken`）时同事务写 `operations.audit_chain_faults`、审计 `audit_chain.halt`、发 critical `operations.audit_chain_fault`，此后接链和核对都停，怎么恢复待定。落后超两分钟、核对超一天分别发 warning。
- **异地副本**：由 `AXIOM_AUDIT_REPLICA_*` 六个变量配置（设一个就要设全；不设就不复制）。桶在部署之外，开版本控制和对象锁，凭证只能写新对象、读和列举。任务 `operations.audit_replica` 每分钟把核对通过的链写进 `audit-chain/v1/<首序号>-<末序号>.jsonl`，只凭桶就能重算整条链；写过的对象从不覆盖，冲突就停并发 critical `operations.audit_replica_conflict`（恢复到更早的库要换新桶，见[备份与恢复的「恢复」](../ops/backup-restore.md#恢复)）；桶不可用时链照常本地推进。写法见[模块 README](../../internal/operations/README.md#审计链)。
- **每天的摘要**：任务 `operations.audit_digest` 为每个已结束的 UTC 日做一份存进 `operations.audit_digests`（一天一行，应用改不了、删不掉）：当天运营操作、上限策略的预留与已用、审批、被拒的尝试，以及链头、故障数和核对完成时刻。负责人给 `operations.audit_digest` 配规则和渠道就每天收到合计。不变量：每天恰好一份且内容完整（D 结束且 D 结束前开始的事务都结束后才做；按数据库写下的时刻归日；可重复读快照；每次最多补 7 天；主键是日期，多节点同时做也只有一份）；事件键是日期、从不发恢复信号；规则必须告知则首通知后关闭，之后加的规则不补发；通知队列停了一天以上时信号留在 `platform.alert_signals`，恢复后每一天照常告知一次再关闭，不丢不重复。
- **保留**：审计和操作记录的保留期待定；与钱有关的至少和账本一样久；到期删除只由专门后台角色执行，删前确认链和副本完整。

### 失败、重试与回滚
| 情况 | 运营操作状态 | 上限 | 处理 |
|---|---|---|---|
| 校验、权限、站点范围失败；超过硬上限（422） | 不建 | 不动 | 稳定错误码；重试无副作用 |
| 需要审批 | `pending_approval` | 已预留 | 202 |
| 驳回、超时；撤回、凭证吊销或紧急停止；审批后目标变了或策略收紧；跨窗口 | `rejected`、`expired`、`canceled` | 释放 | 记审计；重新提案 |
| 数据库在提交前失败 | 回滚 | 不动 | 用同一幂等键重试 |
| 本地改动提交后崩溃 | `succeeded` | 已计入 | 目标改动、操作和审计同事务；重发返回结果 |
| 外部调用结果未知 | `executing`/`unknown` | 保持预留 | 不自动重发不幂等的调用；告警，人工按渠道证据对账 |
| 外部调用确定失败 | `failed` | 释放 | 重试新建操作 |

- **幂等**：运营操作对 `(凭证, 键)` 唯一；重发返回同一编号和**当前**状态；同键换内容或换操作答 409 `idempotency_key_reused`。
- **没有通用回滚**：已发生的钱只能由目标模块的退款、冲正或撤销补偿。一个操作只作用于一个对象，本地改动、计数器、操作和审计在一个事务里；外部调用靠运营操作编号、幂等键和对账收敛。agent 断开不取消已提交的改动；`executing` 的不能取消。

### 上线与兼容

- **能力门控**：运营监听的能力写进心跳，全部核心都支持后才创建凭证、启动 agent；MCP 桥连不上就拒绝启动，不退回管理或公网接口。控制面页面在全部核心支持后才显示，审批页不门控。
- **契约兼容**：v1 内只加操作、可选字段和错误码；删除、改含义或改必填字段升 v2；工具名只增不改。
- **失败关闭**：没有凭证、上限策略、包络或能力标记，或数据库、核心不可用时，一律拒绝资金写；读可以降级。`operations` 或 MCP 桥故障时 agent 停止，固定流程和告警照常。

### 运营看板
管理后台首页的运营看板显示所选时段（24 小时、7 天或 30 天，默认 24 小时）内本站的调用量、错误数、收入、供应商成本、现金净流入、付费用户、月流水、毛利率和留存率，以及调用最多的前 10 个账户和模型。每个数字下钻到已有的调用记录或订单页，地址带同一窗口和筛选。口径（收入、月流水、现金、成本不能互相替代）：

- **调用量与错误数**：`observability.call_log` 里窗口内开始的调用条数；错误是 `error_kind` 非空的。
- **收入**：窗口内已结算调用（`settled` 或 `cleanup_settled`）的 `charged` 之和，按站点记账货币，不含平台承担和免单部分（见[计费](billing.md)）。
- **供应商成本**：同一批调用的 `charged - profit` 之和；`profit IS NULL` 的调用计入 `unknown_cost_calls`，成本不按 0 计。
- **现金净流入**：`billing.transactions` 里 `credit` 或 `refund` 交易在 `cash` 科目上的合计，按支付币种分别列，时间轴是交易时间。调用费用和收入都不是现金。
- **付费用户与月流水**：`billing.credit_batches` 里 `source = 'paid'` 且窗口内创建的批次；付费用户是不同账户数，月流水是按批次锁定汇率折算的 `amount` 之和；赠额不算，退款和拒付不冲减。
- **毛利率**：`(收入 - 供应商成本) / 收入`，基点，可为负；只有收入大于 0 且 `unknown_cost_calls = 0` 才有值。
- **留存率**：当月（`until - 1ns` 所在 UTC 月）里，上月至少一次付费充值的账户中又付费的占比，基点；分母为 0 时没有值。
- **调用日志的覆盖**：窗口触及的每个整月分区都要在，缺一个就 `incomplete=true`，看板返回 `calls_incomplete`，页面说明调用量和排名不完整；其他指标不受归档影响。
- **金额的宽度**：汇总在 PostgreSQL 里用 `numeric` 算，以十进制文本返回，前端不转浮点。

### 业务目标
负责人在管理后台按站点给看板设月度目标；目标是运营数据，每次改动记审计 `targets.update`（带站点、月份、改前改后全部值和必填理由）。

- **指标**：调用量、收入、付费用户、月流水、毛利率、留存率是下限，错误数和供应商成本是上限；现金和排名不设目标。
- **折算**：一个目标覆盖一个 UTC 自然月。数量和金额按窗口与每个月的重叠时长折算（`目标 × 重叠时长 ÷ 该月时长`，纳秒整数比例，最后四舍五入一次，各月相加）；毛利率和留存率不折算，取 `until - 1ns` 所在月的原值。实际值不可用时只显示目标并说明原因。
- **权限与币种**：`sites.manage` 加两步验证，只能设管理会话所在的站点。金额目标带站点记账货币，只和同币种实际金额比较，记账货币改了旧目标不再对照；金额存 `numeric(38,0)`，比率是 0–10000 基点。
- **写入**：一次替换整月目标，没给的项就是清除，0 是真实目标；每月一个版本，版本不符答 `409 stale_revision`。八项整组走 `PUT /api/admin/v1/reports/targets/{month}/all`（带 `X-Axiom-Target-Metrics: all` 和 `all_metrics: true`，只带一个被拒）；旧路径 `/reports/targets/{month}` 只收前四项（调用、错误、收入、成本），带整组标志答 400，后四项保持原值。

### 防止被外部内容操纵

- 外部内容（中转站页面、上游报错、用户请求、Issue 正文）一律不可信；钱和凭证的参数不取自外部内容：充值收款方只能是接入时登记确认的那个，金额、汇率和上限由服务端算，agent 写的只作理由。
- 浏览器工具和统一出站客户端受同样网络限制：不能访问内网和云元数据地址（见[安全基线](../security.md#安全基线)）。

### 部署与节点管理

- 部署组件和 agent 分开运行，agent 令牌访问不到它；升级、增减服务器和删除数据都在部署组件里。
- 升级只接受 CI 构建并签名的版本：`scripts/ops/deploy.sh` 解析 `axiom` 和 `migrate` 的镜像，用 `scripts/ci/verify-release.sh` 按 digest 核对 cosign keyless 签名、workflow 身份和 SBOM，再固定该 digest 执行 pull、前端资源发布和 up；任何一项不符就不拉取、不启动（见[发布的「镜像签名与验证」](../ops/release.md#镜像签名与验证)）。
- **共用队列**：节点只取自己有 worker 的任务种类（见 [platform 的「任务队列」](../../internal/platform/README.md#任务队列)）。
- **启动自检**：`axiom serve` 依次读三份密钥文件（`AXIOM_MASTER_KEY_FILE`、`AXIOM_KEY_HASH_FILE`、`AXIOM_IDENTITY_KEY_FILE`；缺失、权限过宽或格式不对就不启动，报错只指出变量名）、核对数据库角色与表的安全设置、按 `max_connections` 和 `AXIOM_CORE_NODES` 算连接预算、检查兜底价表完整、读目录和端点售价；任何一步失败就退出。三份密钥由部署的 `keys` 服务首次启动时生成，放在与数据库同寿命的卷里；身份密钥单独一份，轮换它不牵连 API key 的哈希。
- **就绪**：`/readyz` 要等路由快照可用：快照里有端点，或供应商还一个端点都没有；供应商给了端点而一个都进不了快照时不就绪，原因在日志里（见[路由快照从哪来](routing.md#路由快照从哪来)）。入口节点每秒探一次核心的 `/readyz`，核心排空时入口也不再报告就绪。
- **停机**：先把 `/readyz` 置为未就绪、新请求答 503（`Retry-After: 1`，不缓存）；就绪过的节点等边缘摘流量（`AXIOM_SHUTDOWN_TIMEOUT` 的三分之一、最多 10 秒）。然后关监听，让在途请求和结算在 `AXIOM_SHUTDOWN_TIMEOUT`（默认 30 秒）里结束：期限前 5 秒取消上游尝试，最后 5 秒留给结算，没结算的交给清理。之后健康循环等已付费的试探写完成本（最多 65 秒），最后同时排空任务队列和调用记录写入，各有 `AXIOM_SHUTDOWN_TIMEOUT` 的期限。`stop_grace_period` 是 170 秒。页面文件在新旧构建重叠期间的做法见[发布的「滚动发布」](../ops/release.md#滚动发布)。
- **数据库健康检查**：启动期 2 分钟内失败不计入重试，之后每 10 秒探一次、连续 3 次失败才不健康，第一次 `pg_isready` 成功就健康；生产入口最长 `--wait-timeout 300`。
- **数据库切换不丢已确认的提交**：有备库时设 `synchronous_commit = on` 且至少一个同步备库；没有同步备库就不自动切换，主库故障人工恢复。生产用哪一种待定。切换演练见 [gateway 的「故障矩阵」](../../internal/gateway/README.md#故障矩阵)。

### 通知

- 渠道、分级和发送回执归记录与告警（[通知渠道](observability.md#通知渠道)、[监控与告警](observability.md#监控与告警)），接收人在控制面设置；告警直接从监控发出，不经过 agent。核心和外部在线监测各有一条最简单的告警通道直通负责人，运维节点出问题时仍可用。
- **审批通知**：提案时同事务发 `operations.approval_pending` 信号（键是审批 ID），决定、到期、撤回或作废时恢复；没有预置规则，负责人配规则和渠道才会收到；通知失败不影响审批排队。
- **账户异常花费**：收到 `observability.spend_anomaly` 后按[防滥用](../security.md#防滥用)核对，可疑 key 由站点管理员停用。
- **对话**：负责人可经 Hermes 的消息入口给 agent 下指令；指令只是请求，受同样权限和审批约束。

### 发现 bug，提交 Issue（计划）

agent 不接触 GitHub，调服务端提 Issue 工具：只收白名单字段（现象、时间、调用编号、复现线索），服务端统一脱敏、限频，GitHub 令牌只有该仓库提 Issue 的权限；已有相同未关闭 Issue 就追加证据；只提 Issue、不改代码。

### 浏览器自动化

可以登录、刷新令牌、读取页面上的价格和公告、创建 key（受数量和额度上限约束，见[供应商的「接入流程」](suppliers.md#接入流程)）。不做付款：agent 只提出充值，负责人付款后附凭证确认。

## 决策与理由

否决的方案和较长的推导见[存档](../archive/operations.md)。

| 决策 | 理由 |
|---|---|
| agent 在单独的运维节点，告警不依赖 agent，运维节点故障另有通道 | 监控和抢修的系统不能和被监控的一起倒下 |
| 运行框架用 Hermes Agent，规则、密钥和预算都在服务端 | 框架开源、不绑模型、随时可换；密钥进了 agent 就可能被诱导泄露 |
| 控制面只有负责人能改 | 否则被操纵的 agent 可以先改掉审批策略 |
| 运营接口独立契约、独立监听，MCP 由同一份契约生成 | 管理接口的权限面太大、挡不住控制面；HTTP 和 MCP 不会漂移 |
| 运营凭证是 `accounts` 的第三种操作者，`ops` 用途写成证书的 URI 备用名 | 人的会话会把人的全部权限交给模型；扩展密钥用法区分不了入口和运维 |
| MCP 桥用官方 Go SDK、无会话，凭证每次调用重读 | SDK 跟着规范升级；桥在调用间没有状态；轮换只换文件 |
| 一次调用一个对象，不提供批量写 | 审批、上限、审计和回滚都以对象为单位 |
| 答案在操作记录写入后才发出；操作记录和审计日志分开 | 不会有记录里没有的调用；读不淹没"谁改了什么" |
| 写的幂等键在运营操作表上唯一，重放答现在的状态 | 平台的幂等表存第一次的答案，等审批的操作会答出过时的状态 |
| 批准在同一个事务里执行目标改动，目标变了只回滚到保存点 | 没有"已批准未执行"的状态；批准和拒绝的原因都留下 |
| 提案前和批准前都持有凭证行 | 吊销或停止不会漏掉正在提交的提案 |
| agent 告警的合并键带凭证，另有 `alert_resolve` | 同一个问题只通知一次，恢复后下次是新事件；别的凭证改不了它 |
| 转账按金额累计，售价按包络累计 | 售价的损失取决于未来销量，折算要预测，可被操纵 |
| 固定 UTC 日/周窗口加计数器行锁 | 一行计数器就能原子判断；边界的代价由按对象、笔数和硬上限削弱 |
| 先预留后执行，未知结果保持预留，已用不因退款退回 | 钱不能被挤出去，也不能被再花一次 |
| 自主上限是审批线，硬上限是拒绝线，人工也不能越过 | 合法的超额提案要建得出来；要更高就在控制面改 |
| 退款和赠额一律人工，第二人规则仍适用 | 运营上限是额外一层，不替代第二人 |
| 没有策略或包络就拒绝；策略币种建了不变 | 失败关闭；计数器不记币种 |
| 对账不一致只暂停自主、转人工，修复按资金操作重算，暂停由触发器兜底 | 负责人仍看得到 agent 要什么；手填数字是绕过上限的口子 |
| 供应商的读只给平台自己的，条件在 suppliers 的查询里 | 账户自带的 key 是账户的数据；事后过滤会弄乱分页 |
| 改定价规则按买家实际付的价逐个计入包络，卖不出去的层也转人工 | 一条规则命中多个模型也绕不过 |
| 退款按报价的现金计入上限，负责人的批准同时是支付里的批准 | 上限约束离开平台的钱；申请人是凭证，第二人规则已满足 |
| 退款批准后停在 `executing`，结局由每分钟的任务读得 | 结局可能晚于当天；支付在下层，不能引用运营 |
| agent 只映射待映射的名字到分组里还没有名字的模型 | 别的映射会改走已经在走的流量 |
| 审计哈希成链、每天核对整条、异地只增不改；不一致就停 | 能悄悄改库的人也能改链；外键会让被删的条目连链一起消失 |
| Issue 经服务端工具提交，agent 不做付款 | 统一脱敏限频；没有 agent 能安全使用的付款方式 |
| 看板的收入和成本取结算行，现金只看 `cash` 科目，下钻复用已有页面 | 收入是权责发生、现金是收付实现 |
| 到期和能否决定都按数据库的 `clock_timestamp()` 判断 | 不受节点或浏览器时钟、等锁时间影响；前端不复刻判定 |
| `approval_wait` 每秒读一次，不用 `LISTEN`/`NOTIFY` | 不多占连接、不在每条结束路径发通知；晚一秒无所谓 |
| 审批通知、agent 告警和每天的摘要都用告警信号 | 规则、渠道、合并、回执和重试都已有 |
| agent 限频存在一行平台数据里，只能调低 | 负责人只能收紧；从下一个请求起生效，不用缓存失效 |
| 日笔数数每一笔提案 | 笔数约束打扰负责人的次数 |
| 充值的预留留到确认或当天结束；批准时按现在的策略重算硬上限 | 付款由负责人做，几分钟内完不成；无关的放宽不该作废待批的提案 |
| 变动取最大、向上取整，毛利率取最小、向下取整 | 包络永远不少算 |
| 赠额在批准的事务里赠出，批次 ID 是运营操作 ID | 计费按批次幂等，一个操作只赠一次 |
| 审计链除了等 60 秒还等所有开着的事务；摘要等这一天的事务结束、在快照里读、接着补 | 长事务的正常提交不能被当成篡改；不漏记、不缺天 |
| 调用日志的完整性按窗口检查缺月 | 最老分区还在不能证明每个月都在 |
| 目标按月设、按重叠时长折算，比率取结束月；后四项目标单独存表、共享版本 | 同一个目标在任何窗口都能对照；旧节点读目标不按指标过滤 |
| PostgreSQL 健康检查的启动期 2 分钟，生产入口最长等 5 分钟 | 崩溃恢复可能超过一分钟 |

## 待定问题

- 上限和包络的数值由负责人在控制面设；代码不带默认策略，没设就不动钱、不改价。
- 待批提案的 30 分钟（代码常量）是否调整。
- 审批 AI 的模型、厂商、默认开关、金额档，以及哪些高风险类别允许 AI 审批。
- 运营凭证的最长有效期、轮换周期和是否限制来源地址；现在到期时间由负责人创建时给出，来源由 `AXIOM_OPERATIONS_SOURCES` 按部署限制。
- 审计和操作记录的保留期。
- 审计链停下之后怎么恢复：把迟到的条目接在链尾、给被改条目补一条确认，还是另起一段链；现在只能停着，告警开着，审计照常写。
- 额度内 agent 直接退款或赠额是否开放；现在一律人工。
- 平台默认上限加站点覆盖；有第二个要定价的站点时再定。
- 供应商充值的实际付款渠道未接入。
- 节点管理里的升级、增减服务器和删除数据是否进入运营接口；现在只开放重启和摘除流量（计划）。
- 电话、短信服务商的选择，取决于是否有公司主体。
- 生产数据库的复制方式：一主一同步备库（可自动切换），或单主不自动切换（故障时人工恢复，停机更久）。

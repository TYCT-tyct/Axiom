# 运营

由 AI agent 执行日常运营：谁做什么、agent 怎么运行、权限和审批怎么控制、怎么通知负责人、怎么发现 bug。对应代码模块 `operations`；运维节点在部署拓扑中的位置见[总体架构](../architecture.md#部署拓扑)，告警的来源见记录与告警的设计。

## 要求

- 运营由 AI agent 执行，尽量减少负责人投入的时间（见[产品需求的「运营」](../product.md#运营)）。
- 运营 AI 在能力上拥有全面的权限；资金和高风险操作按风险受控。
- 运营 AI 不绑定某一家模型，可以用 DeepSeek、Codex 等；也不能因为中转站或 Axiom 自身出问题而瘫痪。
- 高风险操作除了人工审批，也可以由第二个 AI 分析后审批。
- 通知渠道尽量都支持：Telegram、微信、飞书、邮件、电话（紧急）等。
- 运营 AI 能发现 bug 并提交 Issue，供后续处理。

## 设计

### 三层分工

| 谁 | 做什么 | 例子 |
|---|---|---|
| 固定流程（代码） | 规则明确、要求快和稳定的事 | 同步、检测、熔断、按规则自动调价、端点自动下线、故障切换 |
| 运营 agent | 需要判断的事 | 处理异常、认领待映射的模型、协助接入供应商、裁决数据来源的冲突、提出定价建议、排查故障、发现 bug 并提 Issue |
| 负责人 | 超出 agent 权限的事 | 审批、定策略、处理 agent 上报的事 |

### agent 的组成

| 部分 | 是什么 | 谁负责 |
|---|---|---|
| 运行框架 | agent 的"大脑"：调用模型、规划、记忆、定时任务、与负责人对话 | 采用 Hermes Agent，可替换 |
| 工具 | 运营接口，以 MCP 工具的形式提供 | 我们 |
| 规则 | 权限、风险分级、审批、资金操作上限、审计 | 我们，在服务端执行 |
| 运行手册 | 各类运营任务的做法，以技能的形式提供给 agent | 我们，放在仓库里维护 |

- **控制全在服务端**：运行框架换成别的（比如 Codex，或我们自己写的），规则一条也不用改。负责人临时用 Claude Code 或 Codex 执行运维任务，也通过同样的 MCP 工具接入，受同样的约束。
- **Hermes Agent 的加固**：
  - 固定版本，运行在 Docker 沙箱里；
  - 只开放运营接口这一组工具和沙箱内的浏览器，不开放服务器的命令行；
  - 密钥从不以明文交给 agent，需要鉴权的操作由服务端代为执行；
  - agent 自己学到的记忆和技能会被定期检查，正式的运行手册以仓库里的为准。

### 模型来源

- **可配置**：后台登记多个模型来源，按顺序尝试，例如 DeepSeek 官方 API、OpenAI 官方 API、经 Axiom 网关。
- **至少一个直连**：至少有一个来源不经过中转站，也不经过 Axiom 自己。中转站或网关出问题时，agent 照样能工作。
- **按任务选模型**：日常巡检用便宜的模型，排查故障用强的模型。
- **预算**：每天的模型花费、单个任务的工具调用次数和 token 都有上限。
- **全部不可用时**：agent 停止工作，固定流程和告警照常运行。告警永远不依赖 agent。

### 运营接口

- 运营 agent 和管理后台用的是同一套接口，带 OpenAPI 说明，同时以 MCP 工具的形式提供。
- agent 以"操作者"的身份调用，持有带权限范围的令牌（见[账户与租户的「授权」](accounts.md#授权)）。
- 所有写操作都支持防重复编号和试运行；错误码稳定。
- 读操作不受限制：所有数据都能查。

### 风险分级与审批

每类操作对应一条审批策略。策略是后台数据，负责人随时可以调整：

| 操作类别 | 例子 | 默认策略 |
|---|---|---|
| 只读 | 查询、统计、读日志 | 直接执行 |
| 日常操作 | 上下架端点、调整权重、映射模型、重跑检测 | 直接执行，每日汇总 |
| 资金操作 | 修改定价规则、给供应商充值、给用户退款或补额度 | 额度内直接执行，超出则审批 |
| 高风险操作 | 修改供应商网址或凭证、授予管理员角色、删除数据、增减服务器 | 审批 |

审批方式有五种可选：直接执行；额度内直接执行；第二个 AI 审批；人工审批；AI 审批加人工确认。

- **第二个 AI 审批**：由服务端直接调用，使用与提出方不同的模型来源。审批 AI 看到的是结构化的提案和证据（要做什么、为什么、影响多大），不直接读外部网页的原文。提出操作的 agent 无法影响由谁来审、怎么审。
- **绝对上限**：不论选哪种审批方式，单笔资金操作超过绝对上限就只能由人批准。绝对上限只有负责人能修改。
- **由代码判断**：一个操作是否在额度内、需要哪种审批，由服务端代码按策略判定，不由 AI 判断。
- **人工审批的回执**：负责人在通知消息里点按钮批准，回执经通知中心签名后提交给服务端。agent 无法伪造批准。
- **紧急停止**：负责人可以一键暂停 agent。
- **留痕**：每个操作都记录理由、输入、结果和审批过程，可以回放；每天给负责人发一份摘要。

### 防止被外部内容操纵

- 来自外部的内容（中转站页面、上游报错、用户的请求内容）一律标记为不可信。
- 涉及钱和凭证的操作，参数不能取自外部内容。例如给供应商充值，收款方只能是接入时登记并确认过的那个。
- 高风险操作必须给出结构化的理由，并通过上文的审批。

### 通知

- **渠道是插件**：Telegram、飞书、企业微信、微信、邮件、短信、电话都留好接口。
  - 个人微信没有官方的机器人接口，经由企业微信或第三方推送服务送达；
  - 电话和短信需要接入语音、短信服务商。
- **按严重程度分级**：
  - 一般信息：进每日摘要；
  - 警告：发即时消息；
  - 严重：发即时消息，规定时间内无人确认就打电话升级。
- **通知中心运行在运维节点上**，告警直接从监控发出，不经过 agent。
- **对话**：负责人也可以通过 Hermes Agent 自带的消息入口（如 Telegram）直接和运营 agent 对话、下指令。

### 发现 bug，提交 Issue

- **从哪发现**：告警、错误日志、对账差额、调用记录中的异常。判断是代码问题后，在 GitHub 仓库提交 Issue，附上调用编号、时间、现象和复现线索。
- **先查重**：已有相同的未关闭 Issue 就追加证据，没有才新建。
- **先脱敏**：Issue 里绝不出现用户的对话内容、key 或任何密钥。
- **第一版只提 Issue，不改代码**：改代码仍然走正常的开发流程。以后可以让 agent 认领 Issue、提交修复 PR，经评审后由负责人决定是否合并。

### 浏览器自动化

- **可以做**：登录、刷新令牌、读取页面上的价格和公告、创建 key（受数量和额度上限约束，见[供应商的「接入流程」](suppliers.md#接入流程)）。
- **不做付款**：给中转站充值时，agent 算好"充哪家、充多少"发给负责人，负责人付款后，由 agent 核对是否到账。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 运营 agent 运行在单独的运维节点上 | 负责人提出。负责监控和抢修的系统不能和被监控的系统一起倒下 |
| 运行框架采用 Hermes Agent，规则留在服务端 | 它开源（MIT），不绑定模型，自带 MCP、定时任务、技能、记忆、子 agent 和消息入口（Nous Research 官网与 GitHub，2026-10），自己写这些工作量大且难做好；规则在服务端，框架可以随时替换 |
| 模型来源可配置，至少一个直连 | 负责人要求不绑定模型，并且不能因中转站出问题而瘫痪 |
| 告警不依赖 agent | agent 依赖模型，模型可能全部不可用；告警是最后一道防线 |
| 审批方式可配置，可由第二个 AI 审批 | 负责人提出。审批 AI 由服务端调用、使用不同的模型，不容易被同一段恶意内容同时骗过 |
| 绝对上限只有负责人能改 | 任何 AI 审批出错，损失都有上限 |
| 人工批准的回执经通知中心签名 | agent 即使被操纵，也无法伪造批准 |
| 通知渠道做成插件，尽量都支持 | 负责人要求；渠道各有限制（个人微信无官方接口，国内电话和短信需要主体），插件化后可以逐个接入 |
| 第一版只提 Issue，以后再自动提交修复 PR | 负责人同意。代码改动必须经过评审 |
| agent 不做付款 | 负责人同意。目前没有可供 agent 安全使用的付款方式 |

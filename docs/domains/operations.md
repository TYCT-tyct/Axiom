# 运营

由 AI agent 执行日常运营：谁做什么、agent 怎么运行、权限和审批怎么控制、怎么通知负责人、怎么发现 bug。对应代码模块 `operations`；运维节点在部署拓扑中的位置见[总体架构](../architecture.md#部署拓扑)。告警和通知渠道属于记录与告警（`observability` 模块），本文只写运营如何使用它们。

## 要求

- 运营由 AI agent 执行，尽量减少负责人投入的时间（见[产品需求的「运营」](../product.md#运营)）。
- 运营 AI 在能力上拥有全面的权限；资金和高风险操作按风险受控。
- 运营 AI 不绑定某一家模型，可以用 DeepSeek、Codex 等；也不能因为中转站或 Axiom 自身出问题而瘫痪。
- 高风险操作除了人工审批，也可以由第二个 AI 分析后审批。
- 通知负责人用记录与告警的通知渠道（见[记录与告警的「通知渠道」](observability.md#通知渠道)）。
- 运营 AI 能发现 bug 并提交 Issue，供后续处理。

## 设计

### 三层分工

| 谁 | 做什么 | 例子 |
|---|---|---|
| 固定流程（代码） | 规则明确、要求快和稳定的事 | 同步、检测、熔断、按规则自动调价、端点自动下线、故障切换 |
| 运营 agent | 需要判断的事 | 处理异常、认领待映射的模型、协助接入供应商、裁决数据来源的冲突、提出定价建议、排查故障、发现 bug 并提 Issue |
| 负责人 | 超出 agent 权限的事 | 审批、定策略、处理 agent 上报的事 |

### agent 的组成

| 部分 | 是什么 | 谁负责 |
|---|---|---|
| 运行框架 | agent 的"大脑"：调用模型、规划、记忆、定时任务、与负责人对话 | 采用 Hermes Agent，可替换 |
| 工具 | 运营接口，以 MCP 工具的形式提供（MCP 是 AI 调用外部工具的通用协议） | 我们 |
| 模型代理 | 运维节点上的一个小服务：保管模型的 key，按顺序尝试各个模型来源，执行花费预算 | 我们 |
| 规则 | 权限、风险分级、审批、额度上限、审计 | 我们，在核心节点的服务端执行 |
| 运行手册 | 各类运营任务的做法，以技能的形式提供给 agent | 我们，放在仓库里维护 |

- **控制全在服务端**：运行框架换成别的（比如 Codex，或我们自己写的），规则一条也不用改。负责人临时用 Claude Code 或 Codex 执行运维任务，也通过同样的 MCP 工具接入，受同样的约束。
- **agent 手里没有任何密钥**：
  - 模型的 key 由模型代理保管，agent 只能访问模型代理；
  - 登录中转站由我们的浏览器工具在服务端代为完成，agent 拿到的是已登录的页面，看不到密码；
  - agent 的运营令牌只能调用运营接口。

### Hermes Agent 的加固

- **固定版本**：锁定镜像摘要和依赖的哈希，每次升级都要评审。
- **沙箱**：运行在 Docker 沙箱里（隔离的容器，看不到宿主机）。只允许访问运营接口、模型代理和浏览器工具，其他出站网络一律禁止。
- **工具白名单**：只开放运营接口和浏览器工具；命令行、读写文件、执行代码的工具全部关闭，启动时检查，不符合就拒绝启动。
- **技能只读**：运行手册从仓库以只读方式挂载，agent 不能修改；它自己积累的记忆只当作参考笔记，视为不可信，不能改变规则。
- **对话入口**：只接受负责人账号的私聊，必须先配对；群聊关闭。

### 模型来源

- **可配置**：在模型代理里登记多个模型来源，按顺序尝试，例如 DeepSeek 官方 API、OpenAI 官方 API、经 Axiom 网关。
- **至少一个直连**：至少有一个来源不经过中转站，也不经过 Axiom 自己。中转站或网关出问题时，agent 照样能工作。
- **专用 key**：每个来源用专给运维的 key，并在模型厂商那边设置花费上限。
- **按任务选模型**：日常巡检用便宜的模型，排查故障用强的模型。
- **预算由模型代理执行**：每天的模型花费、单个任务的工具调用次数和 token 都有上限。
- **全部不可用时**：agent 停止工作，固定流程和告警照常运行。告警永远不依赖 agent。

### 运营接口

- 管理后台用 `api/admin.yaml`；运营接口以后另有一份契约、挂在自己的监听上，写操作的形状与管理接口一致，带 OpenAPI 说明，同时以 MCP 工具的形式提供。
- agent 以"操作者"的身份调用，持有带权限范围的令牌（见[账户与租户的「授权」](accounts.md#授权)）。
- 所有写操作都支持防重复编号（同一个操作重复提交只执行一次）和试运行（先看结果不真正执行）；错误码稳定。
- **默认能读**：业务和运行数据。
- **不能读**：明文密钥和对话内容。任何人都不能通过产品查看对话内容（见[记录与告警的「谁能看」](observability.md#谁能看)）。

### 控制面：只有负责人能改的设置

以下设置只能由负责人在管理后台修改，并且必须通过两步验证；运营接口、agent 的令牌和对话入口都无法修改：

- 审批策略和各类额度；
- 绝对上限、累计上限；
- 模型来源和审批 AI 的配置；
- 通知的接收人；
- 主站的收款配置（商户号、密钥、收款地址，见[支付](payments.md#收款渠道)）；
- agent 令牌的权限范围；
- 紧急停止后的恢复。

### 风险分级与审批

每类操作对应一条审批策略（策略本身属于上文的控制面）：

| 操作类别 | 例子 | 默认策略 |
|---|---|---|
| 只读 | 查询、统计、读日志 | 直接执行 |
| 日常操作 | 上下架端点、调整权重、映射模型、重跑检测、重启单个节点 | 直接执行，每日汇总 |
| 资金操作 | 修改定价规则、给用户退款或补额度、给供应商充值的建议 | 额度内直接执行，超出则人工审批 |
| 高风险操作 | 修改供应商网址或凭证、授予管理员角色、删除数据、增减服务器、升级版本 | 人工审批 |

审批方式有五种可选：直接执行；额度内直接执行；第二个 AI 审批；人工审批；AI 审批加人工确认。

- **额度防拆单**：额度不只看单笔，还按类别设每天、每周的累计上限，以及笔数上限和按对象的上限（比如每个用户、每个供应商）。定价规则的修改限制在负责人设定的利润率范围和单日变动幅度之内。
- **绝对上限**：不论选哪种审批方式，超过绝对上限就只能由人批准。
- **第二个 AI 审批**：
  - 由核心节点的服务端直接调用，使用与提出方不同厂商的模型；
  - 审批 AI 看到的影响范围（涉及多少钱、多少用户、哪些端点）由服务端从数据库算出，不用提出方自己写的说法；提出方写的理由作为不可信的数据给它参考；
  - 审批 AI 不可用时，自动转为人工审批，不会因此放行。
- **人工审批**：
  - 审批内容由服务端根据操作本身生成，不用 agent 写的文字，并附上管理后台的链接；
  - 资金操作可以在消息里一键批准：按钮带一次性令牌，绑定这个操作的指纹，限时、只能用一次；
  - 高风险操作必须进入管理后台，登录并通过两步验证后批准；
  - 批准的凭证由核心节点签发和校验，签名密钥不在运维节点上；
  - 等待审批超时即视为拒绝；
  - 在对话入口里说"同意"不算批准，也不能修改任何设置。
- **由代码判断**：一个操作是否在额度内、需要哪种审批，由服务端代码按策略判定，不由 AI 判断。

### 紧急停止

- 负责人可以一键停止 agent：服务端立即吊销 agent 的令牌，Hermes 的定时任务和对话入口同时停止，所有待审批的提案作废。
- 只有负责人通过两步验证后才能恢复。

### 审计

- 各模块在改动自己的事务里，把条目写进平台的审计日志（见[平台的「审计日志」](../../internal/platform/README.md#审计日志)）；运营接口的每个操作同样记录理由、输入、结果和审批过程。本模块读取和检索审计日志，按条目回放。
- 审计记录只由核心节点写入，只追加，用哈希链接成一条链，任何一条被篡改都能发现，并同步一份到运维节点以外的地方。接链和同步在条目提交之后进行，不在写入的事务里；具体做法待定。
- 每天给负责人发一份摘要。

### 防止被外部内容操纵

- 来自外部的内容（中转站页面、上游报错、用户的请求内容、Issue 正文）一律标记为不可信。
- 涉及钱和凭证的操作，参数不能取自外部内容。例如给供应商充值的建议，收款方只能是接入时登记并确认过的那个。
- 浏览器工具和统一的出站客户端受同样的网络限制：不能访问内网和云服务器的元数据地址（见[安全的「安全基线」](../security.md#安全基线)）。

### 部署与节点管理

- 部署组件和 agent 分开运行，agent 的令牌访问不到它。
- 升级只接受 CI 构建并签名的版本。
- 节点管理操作（重启、摘除流量、升级、增减服务器）按上文的风险分级审批。
- **滚动发布时新旧节点共用队列**：节点只取自己有 worker 的任务种类，旧节点不会把新版本登记的任务当作未知种类失败掉、耗掉尝试次数，任务由已有该 worker 的新节点执行（见 [platform 的「任务队列」](../../internal/platform/README.md#任务队列)）。
- **节点启动自检**：`axiom serve` 依次读三份密钥文件（`AXIOM_MASTER_KEY_FILE`、`AXIOM_KEY_HASH_FILE`、`AXIOM_IDENTITY_KEY_FILE`，缺失、权限过宽或格式不对就不启动，报错只指出变量名，不含路径和内容）、连数据库并核对角色与表的安全设置、按服务器的 `max_connections` 和 `AXIOM_CORE_NODES` 计算连接预算（算不下就退出，日志报出算出的数）、检查兜底价表完整、读一遍目录和供应商的端点与售价；任何一步失败整个进程退出，而不是带着残缺的状态接流量。三份密钥由部署的 `keys` 服务第一次启动时生成，放在与数据库同寿命的卷里：主密钥和哈希密钥丢了会让用户的二次验证、供应商凭证和 API key 全部失效；身份密钥单独一份，是因为它决定发往上游的会话标识，轮换它只会让上游的提示缓存重新建立，不应牵连 API key 的哈希。就绪（`/readyz`）要等路由快照可用：快照里有端点，或者供应商还一个端点都没有（刚部署，供应商要通过管理端添加）；供应商给了端点而没有一个进得了快照（缺模型规格或售价）时不就绪，原因在日志里（见[路由的「路由快照从哪来」](routing.md#路由快照从哪来)）。停机先把 `/readyz` 置为未就绪、对之后开始的请求答 503（带 `Retry-After: 1`，不缓存），在途请求不受影响；从没有就绪过的节点没有流量要等，直接进入下一步。就绪的节点等边缘按探测摘掉流量：`AXIOM_SHUTDOWN_TIMEOUT` 的三分之一、最多 10 秒。然后关公开、管理和节点监听，让在途请求、调用和结算在同一个 `AXIOM_SHUTDOWN_TIMEOUT`（默认 30 秒）里结束，期限前 5 秒取消上游尝试，最后 5 秒留给结算；到期还没结束的连接被关闭，没结算的交给清理，这段时间持有者的心跳照常发。之后停心跳与清理，健康循环等待已付费的试探读完并写成本、刷新变化（最多 55 + 10 秒），最后同时排空任务队列和调用记录的写入，各有自己的期限（都是 `AXIOM_SHUTDOWN_TIMEOUT`），所以一条长流用完了排空的期限、一个慢的任务也不会让记录丢掉。入口节点每秒探一次核心的 `/readyz`，核心一开始排空，入口就不再报告就绪，边缘也就不再往这条链路送新调用。`stop_grace_period` 要容得下最坏情况（边缘 10 秒、监听与调用 30 秒、健康 65 秒、队列与记录 30 秒、缓存退出最多 10 秒；部署给 170 秒）。新旧构建的页面文件怎么在重叠期间都取得动，见[发布的「滚动发布」](../ops/release.md#滚动发布)。
- **数据库切换不能丢已确认的提交**：已确认的结算和预留在主备切换后必须还在，否则钱会重复扣或漏扣。所以有备库时设 `synchronous_commit = on` 并至少有一个同步备库；没有同步备库就不做自动切换，主库故障时人工恢复。生产用哪一种待定（见下文「待定问题」）；两种都守得住钱的正确性，差别在费用和停机时间。切换演练在 M1 的端到端测试里做（见 [gateway 模块的「故障矩阵」](../../internal/gateway/README.md#故障矩阵)）。

### 通知

- **渠道、分级和发送回执归记录与告警**：见[通知渠道](observability.md#通知渠道)和[监控与告警](observability.md#监控与告警)；接收人在下文「控制面」里设置。本节只写运营怎么用它们。
- **通知中心运行在运维节点上**，告警直接从监控发出，不经过 agent。
- **审批通知**：审批请求走同一个通知渠道，见上文「风险分级与审批」。
- **运维节点自己出问题时**：核心节点和外部的在线监测服务各有一条最简单的告警通道（邮件、短信或电话），直接通知负责人，不经过运维节点。
- **账户异常花费**：`observability.spend` 每 10 分钟把每个账户最近一小时的花费、来源网段和模型与它自己的基线比较，命中后发 `observability.spend_anomaly` 事件到已配置的渠道；升级完成、全部节点都认识这个通知种类后，再把 `spend_detection.notify_users` 打开提醒账户用户（默认关闭）；收到后按[安全的「防滥用」](../security.md#防滥用)核对调用记录，可疑 key 由站点管理员停用（自动暂停尚未实现）。
- **对话**：负责人也可以通过 Hermes Agent 自带的消息入口（如 Telegram）直接和运营 agent 对话、下指令。对话里的指令只是请求，执行时同样受上文的权限和审批约束。

### 发现 bug，提交 Issue

- **从哪发现**：告警、错误日志、对账差额、调用记录中的异常。
- **怎么提交**：agent 不直接接触 GitHub，而是调用服务端的"提交 Issue"工具。
  - 工具只接受白名单字段（现象、时间、调用编号、复现线索），由服务端统一脱敏，确保 Issue 里没有对话内容、key 和任何密钥；
  - 工具限制提交频率；使用的 GitHub 令牌只有该仓库提 Issue 的权限。
- **先查重**：已有相同的未关闭 Issue 就追加证据，没有才新建。
- **第一版只提 Issue，不改代码**：改代码仍然走正常的开发流程。以后可以让 agent 认领 Issue、提交修复 PR，经评审后由负责人决定是否合并。

### 浏览器自动化

- **可以做**：登录、刷新令牌、读取页面上的价格和公告、创建 key（受数量和额度上限约束，见[供应商的「接入流程」](suppliers.md#接入流程)）。
- **不做付款**：给中转站充值时，agent 只给出"充哪家、充多少"的建议，负责人付款后，由 agent 核对是否到账。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 运营 agent 运行在单独的运维节点上 | 负责人提出。负责监控和抢修的系统不能和被监控的系统一起倒下 |
| 运行框架采用 Hermes Agent，规则留在服务端 | 负责人提出可以用 Hermes 这类框架，技术选型已授权开发者决定。它开源（MIT），不绑定模型，自带 MCP、定时任务、技能、记忆、子 agent 和消息入口（Nous Research 官网与 GitHub，2026-10）。没选自己写：记忆、技能、定时任务、对话入口都要自己实现，工作量大且难做好。没选 Claude Code / Codex 无界面运行：它们偏向编程场景，不擅长常驻运行和消息对话。它还没到 1.0、更新快，所以锁定版本、升级前评审；规则在服务端，框架可以随时替换 |
| agent 手里没有密钥，模型调用经模型代理 | 密钥一旦进入 agent，就可能被外部内容诱导泄露；预算也只有在服务端执行才可靠 |
| 控制面只有负责人能改 | 否则 agent 被操纵后，可以先把审批策略改掉，后面的审批就失去意义 |
| 额度按单笔、累计、笔数、对象同时限制 | 只看单笔的话，拆成许多小笔就能绕过 |
| 批准凭证由核心节点签发，密钥不在运维节点 | 运维节点被攻破时，也无法伪造负责人的批准 |
| 第二个 AI 审批由服务端调用不同厂商的模型，不可用时转人工 | 负责人提出。不同厂商的模型不容易被同一段恶意内容同时骗过；审批 AI 失效时不能变成自动放行 |
| 审计只由核心写入、哈希成链、异地留存 | 运维节点或 agent 出问题时，审计记录不能被抹掉 |
| 告警不依赖 agent，运维节点故障另有告警通道 | 告警是最后一道防线，不能和它监控的对象一起失效 |
| Issue 经服务端工具提交 | 由服务端统一脱敏和限频，agent 拿不到 GitHub 令牌 |
| 第一版只提 Issue，以后再自动提交修复 PR | 负责人同意。代码改动必须经过评审 |
| agent 不做付款 | 负责人同意。目前没有可供 agent 安全使用的付款方式 |

## 待定问题

- 电话、短信服务商的选择，取决于是否有公司主体
- 生产数据库的复制方式，部署前请负责人定：一主一同步备库（多一台机器的费用，可以自动切换），或单主不自动切换（故障时人工恢复，停机更久）

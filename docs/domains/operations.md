# 运营

由 AI agent 执行日常运营：谁做什么、agent 怎么运行、权限和审批怎么控制、怎么通知负责人、怎么发现 bug。对应代码模块 `operations`，代码的接口和不变量见[模块 README](../../internal/operations/README.md)；运维节点在部署拓扑中的位置见[总体架构](../architecture.md#部署拓扑)。告警和通知渠道属于记录与告警（`observability`），本文只写运营如何使用它们。

## 要求

- 运营由 AI agent 执行，尽量减少负责人投入的时间（见[产品需求的「运营」](../product.md#运营)）。
- 运营 AI 在能力上拥有全面的权限；资金和高风险操作按风险受控。
- 运营 AI 不绑定某一家模型；也不能因为中转站或 Axiom 自身出问题而瘫痪。
- 高风险操作除了人工审批，也可以由第二个 AI 分析后审批。
- 通知负责人用记录与告警的通知渠道（见[「通知渠道」](observability.md#通知渠道)）。
- 运营 AI 能发现 bug 并提交 Issue。

## 设计

### 三层分工

- **固定流程（代码）**：规则明确、要求快和稳定的事：同步、检测、熔断、按规则调价、端点自动下线、故障切换。
- **运营 agent**：需要判断的事：处理异常、认领待映射的模型、协助接入供应商、裁决数据来源的冲突、提出定价建议、排查故障、提 Issue。
- **负责人**：超出 agent 权限的事：审批、定策略、处理上报。

### agent 的组成

运行框架 Hermes Agent（调用模型、规划、记忆、定时任务、对话，可替换）；工具是运营接口的 MCP 工具；模型代理是运维节点上的小服务，保管模型 key、按顺序尝试模型来源、执行花费预算；规则（权限、风险分级、审批、上限、审计）在核心的服务端执行；运行手册以技能提供，放在仓库里。

- **控制全在服务端**：换运行框架不用改规则；负责人临时用 Claude Code 或 Codex 执行运维，也经同样的 MCP 工具、受同样的约束。
- **agent 手里没有密钥**：模型 key 在模型代理；中转站由服务端的浏览器工具代为登录，agent 拿到已登录的页面；运营令牌在运维节点的 MCP 桥，不交给模型。

### Hermes Agent 的加固

- **固定版本**：锁定镜像摘要和依赖哈希，每次升级都评审。
- **沙箱**：运行在 Docker 沙箱里，出站只允许 MCP 桥、模型代理和浏览器工具。
- **工具白名单**：只开放运营接口的 MCP 工具和浏览器工具；命令行、读写文件、执行代码的工具关闭，启动时检查，不符合就拒绝启动。
- **技能只读**：运行手册从仓库只读挂载；agent 自己的记忆只当不可信的参考笔记，不能改变规则。
- **对话入口**：只接受负责人账号的私聊，先配对；群聊关闭。

Hermes 的部署、白名单和沙箱放行还没有落地。

### 模型来源

- 模型代理里登记多个来源，按顺序尝试；至少一个不经过中转站也不经过 Axiom，网关出问题时 agent 照样工作。
- 每个来源用运维专用的 key，并在厂商处设花费上限；日常巡检用便宜的模型，排查故障用强的。
- 模型代理执行预算：每天的模型花费、单个任务的工具调用次数和 token 都有上限。
- 全部不可用时 agent 停止，固定流程和告警照常运行；告警永远不依赖 agent。

### 定时巡检

- Hermes 的定时任务按站点和供应商周期只读地巡检余额、模型和分组变化、端点健康、价格与成本、待映射模型，异常经 `alert_raise` 发出。
- 固定规则先判断（余额低于阈值、端点连续失败、价格超出包络、模型消失），规则判断不了的才交给 agent；阈值和周期在控制面，agent 不能改。
- 每轮有工具调用预算和页面读取上限；失败不无限重试，下一轮继续。巡检停了不影响调用路径和告警。

### 运营接口

运营接口是 agent 改动 Axiom 的唯一入口；读供应商页面走浏览器工具。

- **契约与监听**：契约 `api/operations.yaml`，前缀 `/api/operations/v1`，只挂在核心的运营监听（`AXIOM_OPERATIONS_ADDR`）。监听默认关闭；打开时只接受出示 `ops` 用途客户端证书的双向 TLS（由 `ca.crt` 签发、`clientAuth`、主题备用名有 URI `urn:axiom:node-purpose:ops`；入口节点的证书没有），来源按 `AXIOM_OPERATIONS_SOURCES` 限制（只看连接地址，不读转发头；监听不是回环地址又没配来源就拒绝启动）。唯一客户端是运维节点的 MCP 桥，它同时出示 `ops` 证书和运营凭证，缺一个都拒绝。
- **执行位置**：HTTP 处理器在 `cmd/axiom`，只经各模块的公开接口组合；读复用管理接口的处理器，`just api` 检查两份契约的同名定义逐字相同。
- **不是管理接口的副本**：只暴露 agent 需要的操作。控制面、用户与平台授权、商户与收款配置、数据删除、部署与升级、服务器增减只在管理后台，由负责人两步验证后操作。不提供批量资金写或批量高风险写：一次调用只作用于一个对象。
- **统一约定**：JSON；失败体 `{"error": {"code", "message", "fields"}}`，`code` 是稳定的封闭枚举；每个请求带 `X-Request-ID`，响应 `Cache-Control: no-store`；列表用键集游标（`cursor`、`limit`，默认 50、最大 200）；金额是十进制文本，单位是站点记账货币的十亿分之一，整数运算并查溢出。每个调用带 `reason`（1–1000 字；读放查询参数，写放请求体），可用 `X-Axiom-Run-ID` 标出所属运行。写必须带 `Idempotency-Key`（重发返回第一次的运营操作，并带 `Idempotency-Replayed: true`），可选 `dry_run`；读到的对象带 `rev` 的写要送回 `rev`，已变化答 409 `stale_revision`。请求体上限 1 MiB，写期限 30 秒，读 15 秒；外部调用不在数据库事务里做。
- **试运行**：`dry_run` 在一个回滚的事务里跑完全部检查，返回会从哪个状态开始（`approved` 或 `pending_approval`）；只写操作记录，受同样的权限和限频，不构成执行许可。
- **能读什么**：读不到明文密钥、供应商登录凭证和对话内容，调用记录只回元数据、费用和尝试。站点范围之外的资源和不存在的一样答 404；供应商只列平台自己的，账户自带的 key 不列、详情答 404。

**写**：每个写都带 `reason` 和 `Idempotency-Key`，可 `dry_run`。回答是运营操作对象：`operation_id`、`state`、`risk`、`approval`（编号、档位、到期）、`result` 或 `error`。本地完成答 200；等审批或外部调用未完成答 202；硬上限或校验拒绝答 422；状态冲突、幂等键复用答 409。

| 提出、确认供应商充值（`supplier_top_up_*`） | 充值 | `suppliers.manage`、`operations.money` | 上限内直接提出，超出人工；确认必须附付款凭证 |

端点权重由路由自动算，所以没有调权重。动钱的写在契约上标 `x-axiom-money: true`，守卫另查 `operations.money`。除告警和撤回外的写都要平台范围；售价和规则只作用于主站，凭证够不着主站答 404；赠额和退款的账户或订单站点不在凭证的站点里答 404。

各写的规则：

- **上下架模型**：提案时按 `rev` 和模型状态先拒绝目标一定会拒绝的（旧 `rev`、下架不在售的模型）。
- **端点开关**：审计 `supplier.endpoint.enabled`；启用不重置熔断（管理接口的才重置，见[端点评估](quality.md#三条摘除通道各归各的主人)）；下次重建路由时生效，同步不改回，负责人在 `setSupplierEndpointEnabled` 改回。
- **选用分组**：第一次选用起代号、之后不变，下次同步建 key、把已映射模型变成端点；取消选用退出路由、保留代号；分组已不在列表答 409。审计 `supplier_group.select`/`unselect`。
- **映射待映射模型**：把分组列为待映射的名字映射到目录模型，只对这个分组有效，结果是别名（`alias_id`、`upstream_name`、`model_id`、`revision`），审计 `supplier_alias.create`。下次同步后（分组选用、模型在售且有成本）它成为端点，真伪检测通过前不是 `verified`。只能映射正在等的名字：分组没列出、目录已认出、或被分组或整个供应商的别名盖住的答 409；只能映射到分组里还没有名字的模型：分组已有它的端点、已有名字解析到它或别名（含还没投影的）映射到它答 409；目录没有或已下架的模型答 422。纠正别名、整个供应商的别名、调用格式声明只在管理接口。供应商移除中或已移除时，端点、分组和映射的写都答 409 `conflict`。
- **赠额**：金额和到期按管理接口赠额的同一套规则（站点记账货币、单笔不超过 10,000 个币种单位、到期在未来），永远等负责人（202）。
- **退款**：经原渠道退回已付订单的一部分额度；按管理员退款的同一套规则（订单已支付或部分退款、额度没用掉也没过期、商户允许经渠道退款、没有在途退款），永远等负责人（202）。不提供线下退款。
- **告警**：`alert_raise` 发种类 `operations.agent_alert` 的信号，合并键 `<凭证 UUID>/<key>`（`key` 为 `[A-Za-z0-9._:/-]`，1–128 字符），带严重度（`info`、`warning`、`critical`）和摘要 `summary`（通知里负责人读到的那句话，最多 512 字节 UTF-8，不截断，按不可信文字对待）；信号在运营操作的事务里经 `alert.Persist` 持久化，编号就是运营操作编号，重发不多发；负责人给这个种类配规则和渠道才会收到。同一个键恢复前再发只累加次数、更新摘要，不再通知；`alert_resolve` 恢复这个键上未恢复的事件（没有就不改），之后再发是新事件；只能恢复自己凭证发的。事件约一分钟内出现在 `alerts_list`。
- **撤回**：`approval_withdraw` 撤回自己的待审批提案，不建运营操作，用平台的幂等表。

**状态机**：`pending_approval` → `approved`/`rejected`/`expired`/`canceled`；`approved` → `executing`/`rejected`/`expired`/`canceled`；`executing` → `succeeded`/`failed`/`unknown`；`unknown` 经对账到 `succeeded` 或 `failed`。`rejected`、`expired`、`canceled`、`failed`、`reverted` 是终态；配置类被补偿操作冲正后原操作记 `reverted`。重做就新建操作。现在批准的操作都在批准的事务里执行完（退款停在 `executing`），没有"已批准未开始"的状态。

**权限**：运营凭证用 `accounts` 已有的权限名，另加 `operations.read`（读自己的记录）、`operations.write`（告警、Issue、撤回、取消）、`operations.money`（资金操作的前置，敏感）、`operations.approve`（审批，敏感）、`operations.manage`（控制面，敏感）、`refunds.manage`（退款，敏感）；`nodes.view`、`nodes.manage` 随节点工具加入。迁移把 `operations.approve`、`operations.manage` 放进内置 `admin` 角色；`refunds.manage` 不在任何内置角色里。运营凭证不能持有 `operations.manage`、`operations.approve` 和 `platform_grants.manage`（代码和表的 CHECK 两处拒绝），所以 agent 不能审批自己、改策略或授予平台角色。

尚未实现的：一键令牌、审批 AI、MCP 桥的按任务预算、连续认证失败的告警、上面标为计划的工具。

#### 运营凭证

- **是什么**：`accounts` 的第三种操作者：256 位随机令牌，前缀 `op-ax-v1-` 带校验位，只在创建或轮换的那次响应里出现（幂等重放不带）；`accounts.agent_credentials` 只存带密钥的哈希、前缀和末四位。只在运营监听有效，不能登录、调模型或调公网接口。
- **权限与范围**：有自己的权限集合、站点范围（默认所有站点，可缩小）、是否带平台范围（默认不带）和提出方厂商列表。总带 `operations.read`，创建时自动加上、不能去掉。授权不经过账户或平台成员关系，也不套用人的会话级别和两步验证；按凭证的站点、平台范围和权限判断，平台级资源（全站供应商、审计、节点）要平台范围。
- **生命周期**：只在管理后台创建、轮换和吊销，要 `operations.manage`、两步验证和 CSRF；改范围没有，要改就新建再吊销旧的。到期时间创建时必填，只要求在未来。轮换时新旧令牌最多重叠 24 小时（默认 24，可设 0），再轮换时上一次的旧令牌立即失效，任何时刻最多两个有效。每个请求都查数据库，没有缓存：到期、吊销后下一次请求就失败，认证、吊销、停止和列表都把到期的当作不存在。最后使用时间最多每分钟写一次。
- **请求认证**：`Authorization: Bearer <token>` 加 `ops` 客户端证书；不读 Cookie，不要 CSRF 和 `Origin`，不开 CORS。缺、错、过期、吊销答 401，权限不足 403，范围外 404。
- **限频**（每张凭证、按核心节点在进程内计）：

  | 类别 | 上限 | 怎么计 |
  |---|---|---|
  | 请求 | 每分钟 600 | 令牌桶装每分钟次数的十分之一，均匀补 |
  | 资金写 | 每分钟 30、每小时 300 | 业务权限和 `operations.money` 之后、校验之前另扣；试运行和重放也算 |
  | 发告警 | 每小时 60 | 处理器在校验之后扣；试运行和重放也算，恢复不算 |
  | 计划：检测重跑、提 Issue | 每小时 30、10 | 随工具加入 |

  资金写和告警的桶各装窗口次数的一半、其余均匀回来，所以任何一个窗口都不超过设的次数；每类另记最近放行的时刻，调低后窗口里已放行的照样算。超过答 429 和 `Retry-After`；超限的资金写和告警进操作记录，超请求限频的不记。负责人可以在控制面 `/operations/agent-limits` 调低四项（`requests_per_minute` 1–600、`money_writes_per_minute` 1–30、`money_writes_per_hour` 1–300、`alerts_per_hour` 1–60），按读到的版本改，没给的项保持原值，审计 `agent_limits.set`；守卫每个请求读一次这一行，所以从下一个请求起生效。
- **紧急停止**：见「紧急停止」。吊销一张凭证也作废它的待审批提案。

#### MCP 映射

- **位置**：运维节点的 `axiom serve`（角色 `ops`）在回环地址 `AXIOM_MCP_ADDR` 上开 MCP 监听，只服务本机的 Hermes；不是回环 IP 就拒绝启动。运营凭证在 `AXIOM_OPERATIONS_TOKEN_FILE`（只能属主可读），每次工具调用重读，轮换只换文件；令牌只在桥进程里。Hermes 到桥用每次启动随机生成的本地令牌，桥写进 `AXIOM_MCP_TOKEN_FILE`（0600）；这个路径若和运营凭证或节点证书目录的 `node.crt`、`node.key`、`ca.crt` 是同一个文件（含经链接），桥在写之前拒绝启动。桥到核心用 `AXIOM_NODE_TLS_DIR` 的 `ops` 证书加运营凭证，地址 `AXIOM_OPERATIONS_URL`（`https`，不带路径）；从不跟随重定向，3xx 在启动时拒绝启动、在调用时是工具错误。
- **协议**：MCP 官方 Go SDK（`github.com/modelcontextprotocol/go-sdk`）的 Streamable HTTP，无会话（`Stateless`），每个请求一个 JSON 回答，不开 SSE；同时说无握手的 2026-07-28 版和更早带 `initialize` 的版本。SDK 拒绝 `Host` 不是本机的回环请求（防 DNS 重绑定），桥另用 `http.CrossOriginProtection` 拒绝浏览器跨源请求；请求体上限 1 MiB。
- **工具生成**：启动时从嵌入的契约（`operationsapi.GetSpec`）生成，一个操作一个工具，名字是 `x-mcp-name`，标 `x-mcp: false` 的不生成；服务端版本报契约的 `info.version`。输入 schema 是一个对象：参数和请求体属性按原名，两个头按 `idempotency_key`、`run_id`，引用全部展开，`additionalProperties: false`；契约里有桥不认识的请求头、重名参数，或 `not`、`discriminator`、OpenAPI 3.0 排他边界时桥拒绝启动。桥只拒绝多余的参数、缺少或会改变路径的路径参数（空、`.`、`..`）和对象或数组的参数，其余由核心校验。启动时以自己的理由调 `GET /me`，按凭证的权限（动钱的另要 `operations.money`，平台范围的要平台授权）决定提供哪些工具；没有的工具按未知工具拒绝；核心不答或拒绝这张凭证时拒绝启动。没有任意 HTTP、shell、文件、批准、策略、凭证或部署工具；`TestBridgeToolsFollowTheContract` 守着工具名单。
- **工具语义**：核心的回答原样作为文本返回，3xx、4xx、5xx 和发不出的调用标 `isError`。每个写都要调用方给 `idempotency_key`；写的回答在桥这边丢了（连接断开、超过 40 秒）时，工具错误说结果未知、用同一个键再调，核心按键返回第一次的操作。需要审批时返回 202 和 `approval_id`，不阻塞模型；`approval_wait` 先读一次（不是自己凭证的审批答 404），之后每秒读一次，审批被决定、撤回、作废或按数据库时钟到期就答，最迟 `wait_seconds`（1–10，默认 10）答当时的样子；一次等待按一次调用计频率、记一条操作记录。
- **注解**：读工具 `readOnlyHint: true`；会改配置或动钱的写 `destructiveHint: true`；带幂等键的写 `idempotentHint: true`；全部 `openWorldHint: false`。注解只影响客户端提示。
- **审批在带外**：批准和驳回只在管理后台（以后还有一次性令牌的审批通知），对话里说"同意"不算批准。

### 资金操作上限

上限约束 **agent 发起** 的运营操作。负责人在管理后台自己做的充值、退款、赠额按管理接口的两步验证和第二人规则执行，不占 agent 的额度，同样写审计；agent 的充值提案过期释放后负责人再自己付款的，按负责人发起的记录。两类上限分开计，都要 `operations.money`：

- **转账**（充值、退款、赠额）：按站点记账货币的整数金额累计，单位 10⁻⁹ 个币种单位。
- **售价**（发布售价、改定价规则）：按单价变动和笔数累计，不折算成金额。

#### 转账的累计金额上限

- **策略**：每个 `(类别, 站点)` 一行，站点为空是平台（平台供应商的充值记在平台上）；类别 `money.top_up`、`money.refund`、`money.credit`。策略有币种（建了不变）、五个自主上限（单笔、日、周、按对象每日、日笔数）和三个硬上限（单笔、日、周），硬上限不低于对应的自主上限。没有策略就不动钱。平台默认值加站点覆盖还没有。
- **金额由服务端算**，不取 agent 写的数字，每笔保存原生金额、币种、单位价值、汇率和计入的金额：
  - 充值：`原生金额 × 单位价值`，结算币种和策略不同再乘计费的当前参考汇率（不加充值缓冲），向上取整到 10⁻⁹；缺单位价值或汇率答 422 `unprocessable`，账户自带的 key 和已移除的供应商答 409。
  - 退款：支付模块报价要退回的现金；对象是订单的账户，范围是订单的站点。
  - 赠额：赠出的面值；对象是账户，范围是账户的站点。
  - 币种和策略不同时都按计费的当前参考汇率折算、向上取整到 10⁻⁹。
- **窗口**：固定 UTC 日和 ISO 周，按数据库时钟。计数器 `operations.cap_counters` 记类别的日、周和对象的日，各有 `reserved`、`committed` 和笔数。
- **判断**：超过任一硬上限 → 422 `cap_exceeded`（带上限、已用和本次金额），不建运营操作；超过任一自主上限（含日笔数）→ 建待审批提案；都在内 → 直接执行。两种都把金额记进 `reserved`、笔数加一。自主上限只是审批线：人工批准的金额可以超过它，但不能超过硬上限。日笔数数每一笔提案，释放的也算。
- **哪些类别不经过人**：只有充值。赠额和退款一律等负责人，自主上限对它们不起作用，只有硬上限拒绝；额度内直接退款或赠额要负责人另行决定（见「待定问题」）。
- **跨日**：提案等锁跨过 UTC 午夜就答 409、整体回滚，在新的一天重提，不把预留记进已经过去的窗口。
- **批准时**：重新锁住计数器，按现在的策略重算硬上限（窗口里已含这笔）：放宽不影响，调低到装不下以 `stale_revision` 结束并释放。资金操作仍记提案时的策略版本供审计。
- **预留的结局**：
  - 驳回、撤回、作废、到期或批准时被目标拒绝 → 释放（`reservation.release`）。
  - 充值：提案成功只表示负责人可以付款；agent 用 `supplier_top_up_confirm` 附凭证确认到账（同一张凭证、同一家供应商）转为 `committed`，或当天 UTC 结束时由每分钟的清扫释放；过了日再确认答 409。
  - 赠额：负责人批准时在批准的事务里按 `credit_grant` 存下的参数重读账户、按管理接口的规则重查，以 agent 的名义调计费的同一个赠额函数（额度批次 ID 就是运营操作 ID，一个操作只赠一次），再转为 `committed`（`proof` 记 `credit_batch:<ID>`）；账户不在、到期已过或硬上限调低到装不下 → `rejected` 并释放。
  - 退款：提案时在回滚的保存点里按批准时的同一个函数冻结、报价（之前先在短事务里经计费的 `PrepareRefund` 推进额度分配，批准前也一样）。批准时冻结额度、写退款记录（申请人是运营凭证，键是运营操作 ID），并以批准的负责人批准它；超过站点退款审批额度的仍要另一名管理员在退款复核里再批。冻结的额度或现金和提案时不同 → `stale_revision`；另有退款在途或商户已不允许经渠道退款 → `conflict`；拿到全部锁后发现预留那一天已过 → 撤回冻结，`expired`（`window_ended`），都释放。批准后操作停在 `executing`、预留留在 `reserved`（到期记成 9999-12-31，清扫释放不了），支付的轮询约两分钟内发出退款。任务 `operations.refund_outcome` 每分钟读执行中的退款：成功转 `committed`（`proof` 是退款 ID）、`succeeded`；失败（渠道失败或复核驳回）释放、`failed`（`target_failed`）；在途或未知不动。
  - 已计入 `committed` 的不因之后的退款或冲正退回；要恢复额度只能由负责人调高上限。
- **对账**：任务 `operations.cap_reconcile` 每分钟用一条语句把当前 UTC 日和 ISO 周的计数器和 `money_actions` 加起来的数比对（每笔按状态计入 `reserved` 或 `committed`，笔数不论状态）。不一致的范围在策略锁下再比一次，仍不一致就记 `paused_at`、审计 `cap_policy.pause`（每行现值和应有值，超 8 KiB 拆成带 `part`/`parts` 的几条）、发 critical 告警 `operations.cap_drift`。暂停期间这个范围的每笔提案都交给负责人（审批摘要的 `cap.paused` 为 true），硬上限照旧拒绝；数据库触发器 `refuse_autonomous_money_when_paused` 让暂停的范围里只有 `pending_approval` 的操作能写预留。负责人两步验证后修复：按资金操作重算当前窗口的每行计数器（缺的补上，没有资金的归零），清暂停，审计 `cap_counters.repair`（改前改后），解除告警；没有漂移的修复只清暂停。过去的窗口不再比对。
- **不放在计费账本里**：上限是事前授权，账本记已发生的钱，两者通过运营操作编号关联。

#### 售价的累计变动上限

- **包络**：每个站点一行 `operations.price_envelopes`：最低毛利率（0–10000 基点）、单个模型单日变动（基点，最大 10⁸）、单日笔数、单日模型数。没有包络的站点答 422 `cap_exceeded`。
- **怎么量**：服务端从提案和当前版本算，不取 agent 写的价格。变动是每个端点的每个有效单价相对**这个端点**现在收的价 `|新 − 旧| ÷ 旧` 的最大值，向上取整到基点；毛利率是每个端点每一项 `(售价 − 成本) ÷ 售价` 的最小值，成本取这个端点的（共用一份售价时取各端点成本的逐项上包络），向下取整到基点，只看有成本的项（和保本线同一组）。没有当前版本、端点现在没有价、上下文分档口径变了、一项价格增删或从零变非零 → 量不出比例；成本未知 → 没有毛利率；这两种都转人工。
- **判断**：量得出、毛利率不低于下限、模型当天已用变动加这一笔不超过单日变动、当天笔数没满、模型当天第一次改价时模型数也没满 → 直接执行并计数；否则带包络和已用数建待审批提案，不计数、不预留。批准时重新刷新、按那一刻的提案重算、发布并计数；量不出比例的计 10000 基点，超过 10⁸ 的计 10⁸ + 1。提案在批准前被发布器换掉或当前版本变了 → `stale_revision`。计数器 `operations.price_counters`（站点行：当天笔数和模型数；模型行：当天累计变动和笔数）只增不减，所以改回去也要再占一次变动。
- **发布售价**：`price_publish` 把自动发布器为主站某模型做的等待确认的提案（`pending` 或 `blocked`）按管理接口确认发布的同一个函数发布；服务端先像管理接口一样刷新提案；永远不低于保本线，也不能豁免。
- **改定价规则**：`pricing_rule_create`、`pricing_rule_update` 按管理接口的同一个函数改主站的一条规则（审计 `pricing_rule.create`/`pricing_rule.update`）。服务端锁主站的定价政策行、刷新提案，在保存点之后改规则、再刷新；对每种买家——站点的每个等级，以及前后有自己一层的每个账户——用计费的同一个选择函数（`billing.Sold.For`，见[计费的「定价」](billing.md#定价)）取改动前后实际卖的版本，不同的就是一笔变动（换了版本、开始卖、不再卖，含一层变成停卖）；同一个模型同一对版本只算一笔。改动换掉了某一层的提案而这一层现在卖不了（`unpriced`：没有端点、端点停用或成本未知）的，记成一笔量不出比例的变动，因为发布器以后会不经包络发布它。这些变动合起来按包络判断，任何一笔或合起来越线就回滚到保存点、规则和价格都不动，建待审批提案（摘要最多列 12 笔，另给总数）；都在内就保留并全部计数。一笔都没移动的改动直接执行，留下的待确认提案之后由 `price_publish` 或负责人按包络发布。保留的改动提交后本节点立即重建路由。批准时重做并计数；规则 `rev` 变了 → `stale_revision`，目标和人群与已有规则重复 → `conflict`。

### 控制面：只有负责人能改的设置

以下设置只能由负责人在管理后台两步验证后修改，运营接口、运营凭证和对话入口都改不了：

- 审批策略和各类额度；转账的自主上限和硬上限；agent 的限频（只能调低）；
- 巡检周期和阈值；价格包络；
- 模型来源和审批 AI 的配置；通知的接收人；
- 主站的收款配置（见[支付](payments.md#收款渠道)）；
- 运营凭证的创建、轮换、吊销和范围；
- 运营接口和 agent 的启停；紧急停止后的恢复。

管理接口（`api/admin.yaml`）上的控制面：`/operations/credentials`（列表、创建、`/{id}/rotate`、`/{id}/revoke`）、`/operations/cap-policies`（列表带暂停时间；`/{scope}/{category}` 按版本设置，审计 `cap_policy.set`；`/{scope}/{category}/repair`）、`/operations/price-envelopes`（列表；`/{site_id}` 按版本设置，审计 `price_envelope.set`）、`/operations/agent-limits`、`/operations/agent/stop`，要 `operations.manage`；审批在 `/operations/approvals`（列表、详情、`/approve`、`/reject`），要 `operations.approve`。写都要两步验证、CSRF、`reason` 和 `Idempotency-Key`。把这两个权限授予别人本身是要两步验证的平台授权。

### 风险分级与审批

只读直接执行；日常、下架、售价和资金按「运营接口」写表里的默认审批。高风险操作（改供应商网址或凭证、移除供应商、发布路由预设、授予管理员、删除数据、增减服务器、升级）默认人工，必须进管理后台两步验证；负责人可为指定类别开启 AI 审批，凭证、权限、删除、部署类仍必须人工。控制面只有负责人。

不在运营接口里的高风险操作只能由负责人在管理后台或部署组件执行，agent 只能上报建议；供应商凭证明文不进 agent 的输入，也不进运营接口。审批方式有五种：直接执行、额度内直接执行、第二个 AI、人工、AI 加人工确认。服务端按"策略、目标模块自己的规则、硬上限"取最严的一档；是否在额度内、要哪种审批由代码判定，不由 AI 判断。

- **审批记录**：`operations.approvals` 存运营操作、档位（现在只有 `human`）、状态（待批/批准/驳回/过期/作废）、服务端生成的摘要、为什么要等（`reasons`）、请求和到期时间、决定者（`<种类>:<ID>`）和理由。指纹就是运营操作本身：应用角色改不了它的工具、目标和参数（含目标的 `rev`），所以批准的就是执行的；目标变了由目标模块按 `rev` 拒绝。
- **到期**：按数据库时钟 30 分钟，且不晚于当天 UTC 结束；锁住后按 `clock_timestamp()` 判断，到期的不能再批，不管清扫到没到。清扫每分钟一次，把它和它的运营操作记为 `expired`（`system:operations.approval_expiry`）。
- **批准**：先持有提出方的凭证，凭证已吊销、停止或过期时什么都不执行，审批和操作记 `canceled`。批准在同一个事务里执行目标改动：成功是 `succeeded`；目标在提案后变了（目标模块拒绝，如 `stale_revision`），改动回滚到保存点，操作以 `rejected` 和那个错误码结束，批准照样记下。外部调用（退款）在批准事务里转入 `executing`。
- **审批页**：管理后台的「运营审批」页（`/approvals`）按状态筛、从新到旧，对象写名字。详情一句一条写为什么要人决定（`reasons`），再列格式化的请求内容（售价逐项列现在、提议和成本）和提出时的上限用量或包络；agent 的理由标为不可信，原始数据默认收起。摘要在提案时存下名字、币种和基础单价，`prices_complete` 为 false 时提示端点或档位的价要另外核对。只有 `decidable`（待决定、按数据库时钟未到期）的才有批准和驳回；结果按回答说明。
- **目标模块的规则**：退款、赠额等第二人规则在目标模块的函数和事务里，管理接口和运营接口调同一个函数。
- **退款与赠额默认人工**：运营上限加在支付和计费的第二人规则之上，不替代它，也不能用 AI 审批代替第二人。
- **第二个 AI 审批**（未实现）：由核心调用与凭证 `proposer_vendors` 每一个都不同厂商的模型，找不到就转人工；影响由服务端算，agent 的理由只作数据；只批类别 `ai_amount` 以内的金额，非金额的高风险按 `ai_enabled`；控制面、第二人操作、凭证/权限/删除/部署和超硬上限的不给 AI；不可用或回答不明确就转人工；驳回后冷却期内不能重复提交。
- **人工审批**：审批内容由服务端生成；资金操作以后可以一键批准：一次性令牌绑定指纹、审批编号、负责人和到期（默认 10 分钟），由核心密钥环的专用用途签名，GET 只渲染确认页、POST 才消费（未实现）。高风险操作只能进管理后台两步验证后批。审批人不能是提出方；agent 能撤回自己的提案，撤回记审计。
- **策略变化**：批准时重读策略，硬上限变低装不下就拒绝并释放；变松不影响已发出的提案；不论哪种审批都不能越过硬上限。

### 紧急停止

- 负责人一键停止：一个事务里吊销所有运营凭证（全局开关和 Hermes 的停止随 Hermes 部署加入），运营监听对之后每个请求答 401，MCP 桥把它作为工具错误交给模型，桥重启时问不到 `GET /me` 就拒绝启动。
- 同一个事务里作废全部待审批提案（操作和审批记 `canceled`、释放预留，回答里的 `canceled` 是个数）；`executing` 的外部调用不强行取消，按自己的期限结束，无法判断的标 `unknown` 等人工对账。
- 提案前先持有凭证行（`FOR SHARE`），所以停止要么在提案之前（提案 401），要么等它提交后把它一起作废。
- 恢复只有负责人两步验证后重建凭证，旧凭证和旧提案都不复活；停止和恢复记审计。

### 审计

- **操作记录**：`operations.operation_log` 记凭证认出之后的每个请求（含被守卫拒绝的）：记录 ID、凭证 ID、运行 ID、工具名、理由、输入（路径和查询参数，写还有请求体，都不含理由；规范 JSON 超过 8 KiB 只记大小）、HTTP 状态、错误码、请求 ID、开始和结束时间，写还有运营操作编号。答案先缓存在内存，记录写进数据库后才发出，写不进答 503。令牌不认识或超请求限频的不记。读不写审计日志。
- **审计日志**：每个改状态的操作在同一个事务里写平台审计，写不进整个改动失败。操作者：提案、执行和撤回是 `operations_agent:<凭证 ID>`；批准和驳回是负责人；过期 `system:operations.approval_expiry`；预留清扫和跨日过期 `system:operations.reservation_expiry`；对账 `system:operations.cap_reconcile`；退款结局 `system:operations.outcome`；审计链 `system:operations.audit_chain`。动作：`approval.request`/`approve`/`reject`/`expire`，`operation.execute`/`succeed`/`fail`/`reject`/`cancel`/`expire`，`reservation.commit`/`release`，`cap_policy.set`/`pause`，`cap_counters.repair`，`price_envelope.set`，`agent_limits.set`，`audit_chain.halt`；目标模块自己的审计（如 `model.retire`、`price.publish`、`credit.add`、`refund.request`）以 agent 的名义写在同一个事务里（`refund.approve` 以批准的负责人）。`detail` 不放密钥、凭证、对话内容、请求正文或供应商页面原文。
- **谁能读**：agent 读自己的记录和审批；读全平台审计（`audit_list`、`audit_get`）和每天的摘要（`audit_digests`，从新到旧，游标是上一页最后一天的日期）要 `audit.view` 和平台范围（只有站点范围答 404，没有 `audit.view` 答 403）。审计读转给管理后台审计页的同一个处理器：按操作者、动作、模块、目标、站点、账户和请求 ID 精确筛，从新到旧，默认最近 24 小时、最长 31 天，答案的 `since`、`until` 是实际窗口。条目里的文字在契约里写明为数据、不是指令。
- **哈希链**：任务 `operations.audit_chain` 每分钟按 `(at, id)` 顺序把已提交的审计条目接进 `operations.audit_chain`。哈希是 SHA-256(前一条的哈希 ‖ 条目的编码)，第一条之前是 32 个零字节；条目的编码是 RFC 8785 的 JSON 数组：`"axiom.audit.v1"`、条目 ID、`at`（UTC，微秒）、操作者种类和 ID、请求 ID、动作、模块、目标种类和 ID、站点、账户（没有为 `null`）、理由（没有为空字符串）和 PostgreSQL 打印的 `detail` 文本，所以凭审计日志和链的导出就能在平台外重算。应用角色不能改、不能删链。只接早于 60 秒前、也早于本库每个开着的事务开始时刻（`pg_stat_activity.xact_start`）的条目。
- **核对**：每轮先核对链头往回 1000 条；整条链每天核对一次，分多次做完，一轮开始满一天没核完发 warning `operations.audit_chain_check_overdue`。不一致四种：链头之前有没接上的条目（`late`）、链上的条目不见了或换了位置（`missing`）、条目被改（`mismatch`）、链本身断开或链上的时刻被改（`broken`）；发现时同一个事务里写 `operations.audit_chain_faults`、审计 `audit_chain.halt`、发 critical `operations.audit_chain_fault`，此后接链和核对都停下，怎么恢复待定。还没接的最早一条早于现在两分钟时发 warning `operations.audit_chain_lag`（`behind_seconds`），赶上就恢复。
- **异地副本**：由 `AXIOM_AUDIT_REPLICA_*` 六个变量配置（设一个就要设全，否则不启动；不设就不复制）。桶在部署之外，开版本控制和对象锁；凭证能写新对象、读和列举，不能覆盖或删除。任务 `operations.audit_replica` 每分钟把核对通过的链按每个对象最多 500 条写进 `audit-chain/v1/<首序号>-<末序号>.jsonl`，每行带 `seq`、`prev_hash`、`hash` 和哈希覆盖的字段数组，只凭桶就能重算整条链。进度按目标桶（端点加桶名）各记一行，换桶后新桶从第一条起复制。写过的对象从不覆盖，对象的范围首尾相接、不重叠；冲突（键里是别的字节，或范围里已有别的对象开头）就不写、发 critical `operations.audit_replica_conflict` 并停在这一批（恢复到更早的库要换新桶，见[备份与恢复的「恢复」](../ops/backup-restore.md#恢复)）。未复制的最早一条接上超过 10 分钟发 warning `operations.audit_replica_lag`，按目标分键。桶不可用时链照常本地推进。写法见[模块 README](../../internal/operations/README.md#审计链)。
- **每天的摘要**：任务 `operations.audit_digest` 每分钟看一次，为每个已结束的 UTC 日做一份，存进 `operations.audit_digests`（一天一行，应用改不了、删不掉，不限大小）：那一天的运营操作（按工具和现在的状态）、每条上限策略那一天的预留、已用、笔数和日上限、审批（按现在的状态）、被拒的尝试（运营接口答 4xx 的调用，按错误码），以及链头、故障数和整条核对最后完成的时刻。负责人给 `operations.audit_digest` 配一条最低 info 的规则和渠道就每天收到合计。不变量：
  1. 每天恰好一份，内容完整：D 的摘要在 D 结束、且 D 结束前开始的事务都已结束后才做（数据库时钟，边界同接链）；归日按数据库写下的时刻（操作的创建、审批的请求、调用记录的 `logged_at`）；在一个可重复读的快照里读。从上一份的后一天起按日期顺序做，每次最多 7 天，停机多久都补齐。主键是日期，插入成功的事务才发信号，多节点同时做也只有一份、一个信号。
  2. 事件由那个信号打开，键是日期，一天一个，从不发恢复信号。
  3. 规则必须告知，当且仅当渠道存在、种类相同、info 不低于它的最低严重度、值 1 不低于阈值（observability 的 `mustTell`）。每条必须告知的规则都有首通知回执、没有待发回执时事件关闭（没有这样的规则就第一次评估时关闭），不发恢复通知，之后加的规则不补发。
  4. 通知队列停了一天以上时信号留在 `platform.alert_signals`，恢复后每一天照常告知一次再关闭，不丢、不重复。
- **保留**：审计和操作记录的保留期待定；与钱有关的至少和账本一样久；到期删除只由专门的后台角色执行，删前确认链和副本完整。

### 失败、重试与回滚

| 情况 | 运营操作状态 | 上限 | 处理 |
|---|---|---|---|
| 校验、权限、站点范围失败 | 不建，只写操作记录 | 不动 | 稳定错误码；重试无副作用 |
| 超过硬上限 | 不建 | 不动 | 422 `cap_exceeded`；负责人调高后重试 |
| 需要审批 | `pending_approval` | 已预留 | 202；`approval_wait` 或 `approval_get` |
| 驳回、超时 | `rejected`、`expired` | 释放 | 记审计 |
| 撤回、凭证吊销或紧急停止 | `canceled` | 释放 | 记审计；可重新提交 |
| 数据库在提交前失败 | 回滚 | 不动 | 用同一个幂等键重试 |
| 本地改动提交后崩溃 | `succeeded` | 已计入 | 目标改动、操作和审计同事务；重发返回结果 |
| 外部调用在 `executing` 后结果未知 | `executing`/`unknown` | 保持预留 | 不自动重发不幂等的调用；告警，人工按渠道证据对账 |
| 外部调用确定失败 | `failed` | 释放 | 重试新建操作 |
| 审批后目标变了，或策略收紧 | `rejected` | 释放 | 重新提案、重新审批 |
| 已批准未开始，跨窗口 | `expired` | 释放 | 新窗口重新提案 |
| 回滚已完成的配置改动 | 原操作 `reverted`；新操作 `succeeded` | 按新操作检查 | 新操作链接原操作，受同样的审批和上限；价格回滚再占一次变动 |

- **幂等**：运营操作对 `(凭证, 键)` 唯一；重发返回同一个编号和**当前**状态，不执行第二次；同一个键换内容或换操作答 409 `idempotency_key_reused`。
- **没有通用回滚**：已发生的钱只能由目标模块的退款、冲正或撤销补偿；配置类用 `operation_revert`（计划）新建补偿操作。
- **部分写入**：一个操作只作用于一个对象；本地改动、计数器、操作和审计在一个事务里。外部调用和本地记录之间靠运营操作编号、幂等键和对账收敛。
- **取消**：agent 断开不取消已提交的改动或已发出的外部调用；`executing` 的不能取消。

### 上线与兼容

- **能力门控**：运营监听的能力写进心跳，全部核心都支持后才创建凭证、启动 agent；MCP 桥连不上就拒绝启动，不退回管理或公网接口。控制面页面在全部核心支持后才显示，审批页不门控。
- **契约兼容**：v1 内只加操作、可选字段和错误码；删除、改含义或改必填字段升 v2；工具名同样只增不改，运行手册按工具名引用。
- **失败关闭**：没有凭证、上限策略、包络或能力标记，或数据库、核心不可用时，一律拒绝资金写；读可以降级。`operations` 或 MCP 桥故障时 agent 停止，固定流程和告警照常。

### 运营看板

管理后台首页的运营看板显示所选时段内本站的调用量、错误数、收入、供应商成本、现金净流入、付费用户、月流水、毛利率和留存率，以及调用最多的前 10 个账户和模型（按调用量，附错误数）。时段可选最近 24 小时、7 天或 30 天，默认 24 小时；窗口在打开页面时算定，切换时段沿用同一个锚点。看板只看请求所在站点。

每个数字都下钻到已有的调用记录或订单页，地址带同一个窗口和筛选：现金打开订单页的账本流水视图（`cash=1`），付费用户、月流水和留存打开付费充值批次视图（`paid=batches`，留存从上一个 UTC 月第一天开始），其余打开调用记录。

口径（收入、月流水、现金、成本不能互相替代）：

- **调用量与错误数**：`observability.call_log` 里窗口内开始的调用条数；错误是 `error_kind` 非空的。调用开始取请求到达、准入之前的时刻，网关把同一个值写进 `billing.reservations.created_at` 和 `call_log.at`。
- **收入**：窗口内已结算调用（`state` 为 `settled` 或 `cleanup_settled`）的 `charged` 之和，按站点记账货币，不含平台承担和免单的部分（见[计费](billing.md)）；时间轴是调用的开始时间，更正改写同一行。
- **供应商成本**：同一批调用的 `charged - profit` 之和；`profit IS NULL` 的调用计入 `unknown_cost_calls`，成本不按 0 计入。
- **现金净流入**：`billing.transactions` 里 `kind` 为 `credit` 或 `refund` 的交易在 `billing.entries` 的 `cash` 科目上的合计，按支付币种分别列（账本没写币种的按站点记账货币），时间轴是交易时间。调用费用和收入都不是现金。
- **付费用户与月流水**：读 `billing.credit_batches` 里 `source = 'paid'`、`created_at` 在窗口内的批次。付费用户是不同 `account_id` 数；月流水是 `amount` 之和（按批次锁定汇率折成站点记账货币）。赠额不算；退款和拒付不冲减；月流水不是调用收入。
- **毛利率**：`(收入 - 供应商成本) / 收入`，基点，按代数值四舍五入，可为负；只有收入大于 0 且 `unknown_cost_calls = 0` 时才有值。
- **留存率**：付费账户的月环比。当月是 `until - 1ns` 所在的 UTC 自然月；分母是上一个月至少有一次付费充值的不同账户，分子是其中从当月第一天到 `until`（不含）又付费的；基点，四舍五入；分母为 0 时没有值。当月未结束时是月初至今的留存。
- **调用日志的覆盖**：调用记录按月归档后删除。`CallCoverage` 记下还在的月分区，窗口触及的每个整月都要在，缺一个就 `incomplete=true`，`available_since` 是最老的剩余月分区。看板据此返回 `calls_incomplete`，页面说明调用量和排名不完整；下钻的调用列表同样返回这两项。其他指标不受归档影响。
- **金额的宽度**：汇总在 PostgreSQL 里用 `numeric` 算，以十进制文本返回，可以超过 64 位；前端只格式化文本，不转浮点。

### 业务目标

负责人在管理后台按站点给看板设月度目标，看板把目标和实际值放在一起。目标是运营数据，不写进文档或配置；每次改动记审计。

- **哪些指标**：调用量、收入、付费用户、月流水、毛利率、留存率是下限，错误数和供应商成本是上限；看板只显示实际比目标多或少。现金（按币种分列）和排名不设目标。
- **周期与折算**：一个目标覆盖一个 UTC 自然月。数量和金额按窗口与每个月重叠的时长折算：`目标 × 重叠时长 ÷ 该月时长`，按纳秒参与整数比例，只在最后四舍五入一次到指标的最小单位（个数到 1，金额到十亿分之一），再把各月相加；没设目标的月不计入。毛利率和留存率不折算，取 `until - 1ns` 所在月的原值。
- **显示**：目标月份按页面语言选择并注明按 UTC。差距是实际减目标；实际值不可用时只显示目标并说明原因（调用日志不完整、有成本未知的调用、留存分母为 0）。
- **谁可以设**：`sites.manage` 加两步验证，和打开看板相同，没有新增权限；只能设管理会话所在的站点。
- **币种**：金额目标带站点记账货币，只和同币种的实际金额比较；记账货币改了以后旧目标不换算、不参与对照，直到按新币种重设。
- **范围**：金额目标存 `numeric(38,0)`，前端接受最多 38 位、至多 9 位小数的非负金额，不转浮点；比率目标是 0 到 10000 的整数基点，前端按百分比输入（最多两位小数）。
- **写入与并发**：一次替换整月目标，没给的项就是清除，0 是真实目标。每月一个从 0 开始的版本，每次成功写入（含清空）加一；版本不符答 `409 stale_revision` 且不写。八项整组走 `PUT /api/admin/v1/reports/targets/{month}/all`，同时带 `X-Axiom-Target-Metrics: all` 和请求体 `all_metrics: true`（只带一个被拒）；旧路径 `/reports/targets/{month}` 只收前四项（调用、错误、收入、成本），带整组标志答 400，后四项保持原值。看板响应的 `targets`、`metrics` 可选，没有 `metrics` 的节点只编辑前四项。
- **审计**：`targets.update`，带站点、月份、改动前后的全部目标值（没设的不出现，后四项保持时也记现值）和必填的理由（1–1000 字），与改动同一个事务。

### 防止被外部内容操纵

- 外部内容（中转站页面、上游报错、用户请求、Issue 正文）一律不可信；钱和凭证的参数不取自外部内容：充值的收款方只能是接入时登记确认的那个，金额、汇率和上限由服务端算，agent 写的只作理由。
- 浏览器工具和统一出站客户端受同样的网络限制：不能访问内网和云元数据地址（见[安全基线](../security.md#安全基线)）。

### 部署与节点管理

- 部署组件和 agent 分开运行，agent 的令牌访问不到它；升级、增减服务器和删除数据都在部署组件里。
- 升级只接受 CI 构建并签名的版本：`scripts/ops/deploy.sh` 从实际 Compose 配置解析 `axiom` 和 `migrate` 的镜像，用 `scripts/ci/verify-release.sh` 按 digest 核对 cosign keyless 签名、workflow 身份和 SBOM，再固定该 digest 执行 pull、前端资源发布和 up；任何一项不符就不拉取、不启动（见[发布的「镜像签名与验证」](../ops/release.md#镜像签名与验证)）。
- **共用队列**：节点只取自己有 worker 的任务种类（见 [platform 的「任务队列」](../../internal/platform/README.md#任务队列)）。
- **启动自检**：`axiom serve` 依次读三份密钥文件（`AXIOM_MASTER_KEY_FILE`、`AXIOM_KEY_HASH_FILE`、`AXIOM_IDENTITY_KEY_FILE`；缺失、权限过宽或格式不对就不启动，报错只指出变量名）、核对数据库角色与表的安全设置、按 `max_connections` 和 `AXIOM_CORE_NODES` 算连接预算、检查兜底价表完整、读目录和端点售价；任何一步失败就退出。三份密钥由部署的 `keys` 服务首次启动时生成，放在与数据库同寿命的卷里；身份密钥单独一份，轮换它不牵连 API key 的哈希。
- **就绪**：`/readyz` 要等路由快照可用：快照里有端点，或供应商还一个端点都没有；供应商给了端点而一个都进不了快照时不就绪，原因在日志里（见[路由快照从哪来](routing.md#路由快照从哪来)）。入口节点每秒探一次核心的 `/readyz`，核心排空时入口也不再报告就绪。
- **停机**：先把 `/readyz` 置为未就绪、新请求答 503（`Retry-After: 1`，不缓存）；就绪过的节点等边缘摘流量（`AXIOM_SHUTDOWN_TIMEOUT` 的三分之一、最多 10 秒）。然后关监听，让在途请求和结算在 `AXIOM_SHUTDOWN_TIMEOUT`（默认 30 秒）里结束：期限前 5 秒取消上游尝试，最后 5 秒留给结算，没结算的交给清理。之后健康循环等已付费的试探写完成本（最多 65 秒），最后同时排空任务队列和调用记录写入，各有 `AXIOM_SHUTDOWN_TIMEOUT` 的期限。`stop_grace_period` 是 170 秒，容得下最坏情况。页面文件在新旧构建重叠期间的做法见[发布的「滚动发布」](../ops/release.md#滚动发布)。
- **数据库健康检查**：启动期 2 分钟内失败不计入重试，之后每 10 秒探一次、连续 3 次失败才不健康，第一次 `pg_isready` 成功就健康；生产入口等它，最长 `--wait-timeout 300`。
- **数据库切换不丢已确认的提交**：有备库时设 `synchronous_commit = on` 且至少一个同步备库；没有同步备库就不自动切换，主库故障人工恢复。生产用哪一种待定。切换演练见 [gateway 的「故障矩阵」](../../internal/gateway/README.md#故障矩阵)。

### 通知

- 渠道、分级和发送回执归记录与告警（见[通知渠道](observability.md#通知渠道)和[监控与告警](observability.md#监控与告警)），接收人在控制面设置；告警直接从监控发出，不经过 agent。
- **审批通知**：提案时同一个事务里发 `operations.approval_pending` 信号（键是审批 ID，字段有工具、目标和到期时间），决定、到期、撤回或作废时恢复；没有预置规则，负责人给这个种类配规则和渠道才会收到。通知失败不影响审批排队，管理后台仍看得到。摘要、后台链接和一键令牌还没进通知。
- **运维节点出问题时**：核心和外部在线监测各有一条最简单的告警通道直通负责人。
- **账户异常花费**：收到 `observability.spend_anomaly` 后按[防滥用](../security.md#防滥用)核对，可疑 key 由站点管理员停用。
- **对话**：负责人可经 Hermes 的消息入口（如 Telegram）给 agent 下指令；指令只是请求，受同样的权限和审批约束。

### 发现 bug，提交 Issue（计划）

- 从告警、错误日志、对账差额和调用记录的异常里发现。
- agent 不接触 GitHub，调服务端的提 Issue 工具：只收白名单字段（现象、时间、调用编号、复现线索），服务端统一脱敏，限频，GitHub 令牌只有该仓库提 Issue 的权限。
- 已有相同的未关闭 Issue 就追加证据，没有才新建。只提 Issue、不改代码。

### 浏览器自动化

- 可以登录、刷新令牌、读取页面上的价格和公告、创建 key（受数量和额度上限约束，见[供应商的「接入流程」](suppliers.md#接入流程)）。
- 不做付款：agent 只提出充值、负责人付款后附凭证确认（见「转账的累计金额上限」）。

## 决策与理由

否决的方案和较长的推导见[存档](../archive/operations.md)。

| 决策 | 理由 |
|---|---|
| agent 在单独的运维节点，告警不依赖 agent，运维节点故障另有通道 | 监控和抢修的系统不能和被监控的一起倒下 |
| 运行框架用 Hermes Agent，规则、密钥和预算都在服务端 | 框架开源、不绑模型、随时可换；密钥进了 agent 就可能被诱导泄露 |
| 控制面只有负责人能改 | 否则被操纵的 agent 可以先改掉审批策略 |
| 运营接口独立契约、独立监听，MCP 由同一份契约生成 | 管理接口的权限面太大、挡不住控制面；HTTP 和 MCP 不会漂移 |
| 运营凭证是 `accounts` 的第三种操作者，`ops` 用途写成证书的 URI 备用名 | 人的会话会把人的全部权限交给模型；扩展密钥用法区分不了入口和运维 |
| MCP 桥用官方 Go SDK、无会话，凭证每次调用重读 | SDK 跟着规范升级；桥在调用间没有状态；轮换只换文件 |
| 一次调用一个对象，不提供批量写 | 审批、上限、审计和回滚都以对象为单位 |
| 答案在操作记录写入后才发出；操作记录和审计日志分开 | 不会有记录里没有的调用；读不淹没"谁改了什么" |
| 写的幂等键在运营操作表上唯一，重放答现在的状态 | 平台的幂等表存第一次的答案，等审批的操作会答出过时的状态 |
| 批准在同一个事务里执行目标改动，目标变了只回滚到保存点 | 没有"已批准未执行"的状态；批准和拒绝的原因都留下 |
| 提案前和批准前都持有凭证行 | 吊销或停止不会漏掉正在提交的提案 |
| 到期和能否决定都按数据库的 `clock_timestamp()` 判断，原因由判定函数在提案时给出 | 不受节点或浏览器时钟、等锁时间影响；前端不复刻判定 |
| `approval_wait` 每秒读一次，不用 `LISTEN`/`NOTIFY`（循环在 `awaitDecision`） | 不多占连接、不在每条结束路径发通知；晚一秒无所谓 |
| 审批通知、agent 告警和每天的摘要都用告警信号 | 规则、渠道、合并、回执和重试都已有 |
| agent 告警的合并键带凭证，另有 `alert_resolve` | 同一个问题只通知一次，恢复后下次是新事件；别的凭证改不了它 |
| agent 限频存在一行平台数据里，只能调低，每个请求读一次 | 负责人只能收紧；从下一个请求起生效，不用缓存失效 |
| 转账按金额累计，售价按包络累计 | 售价的损失取决于未来销量，折算要预测，可被操纵 |
| 固定 UTC 日/周窗口加计数器行锁 | 一行计数器就能原子判断；边界的代价由按对象、笔数和硬上限削弱 |
| 先预留后执行，未知结果保持预留，已用不因退款退回 | 钱不能被挤出去，也不能被再花一次 |
| 自主上限是审批线，硬上限是拒绝线，人工也不能越过 | 合法的超额提案要建得出来；要更高就在控制面改 |
| 日笔数数每一笔提案 | 笔数约束打扰负责人的次数 |
| 退款和赠额一律人工，第二人规则仍适用 | 运营上限是额外一层，不替代第二人 |
| 充值的预留留到确认或当天结束 | 付款由负责人做，几分钟内完不成 |
| 批准时按现在的策略重算硬上限 | 无关的放宽不该作废待批的提案 |
| 没有策略或包络就拒绝；策略币种建了不变 | 失败关闭；计数器不记币种 |
| 对账不一致只暂停自主、转人工，修复按资金操作重算，暂停由触发器兜底 | 负责人仍看得到 agent 要什么；手填数字是绕过上限的口子；不读新列的版本也绕不过 |
| 供应商的读只给平台自己的，条件在 suppliers 的查询里 | 账户自带的 key 是账户的数据；事后过滤会弄乱分页 |
| 改定价规则按买家实际付的价逐个计入包络，卖不出去的层也转人工 | 一条规则命中多个模型也绕不过；更具体的规则可能改了买家付的价而发布行没变 |
| 变动取最大、向上取整，毛利率取最小、向下取整；量不出比例的转人工、批准后计 10000 | 包络永远不少算 |
| 赠额在批准的事务里赠出，批次 ID 是运营操作 ID | 计费按批次幂等，一个操作只赠一次 |
| 退款按报价的现金计入上限，负责人的批准同时是支付里的批准 | 上限约束离开平台的钱；申请人是凭证，第二人规则已满足 |
| 退款批准后停在 `executing`，预留到期 9999-12-31，结局由每分钟的任务读得 | 结局可能晚于当天；支付在下层，不能引用运营 |
| agent 只映射待映射的名字到分组里还没有名字的模型 | 别的映射会改走已经在走的流量 |
| 审计哈希成链、每天核对整条、异地只增不改；链表不建外键，不一致就停 | 能悄悄改库的人也能改链；外键会让被删的条目连链一起消失 |
| 审计链除了等 60 秒还等所有开着的事务 | 长事务的正常提交不能被当成篡改 |
| 摘要等这一天的事务结束、在快照里读、按数据库时刻归日、接着补、不限大小 | 不漏记、不缺天，策略多了也不停住 |
| Issue 经服务端工具提交，agent 不做付款 | 统一脱敏限频；没有 agent 能安全使用的付款方式 |
| 看板的收入和成本取结算行，现金只看 `cash` 科目，下钻复用已有页面 | 结算行有 `charged` 和 `profit`；收入是权责发生、现金是收付实现 |
| 调用日志的完整性按窗口检查缺月 | 最老分区还在不能证明每个月都在 |
| 目标按月设、按重叠时长折算，比率取结束月 | 同一个目标在任何窗口都能对照；缩放比率会改变含义 |
| 后四项目标单独存表、共享版本，整组替换走新路径；写入加锁并比版本 | 旧节点读目标不按指标过滤；后提交的旧表单不会覆盖新目标 |
| PostgreSQL 健康检查的启动期 2 分钟，生产入口最长等 5 分钟 | 崩溃恢复可能超过一分钟；反复重启的容器到不了不健康 |

## 待定问题

- 上限和包络的数值由负责人在控制面设；代码不带默认策略，没设就不动钱、不改价。
- 待批提案的 30 分钟（代码常量）是否调整，由负责人定。
- 审批 AI 的模型、厂商、默认开关、金额档，以及哪些高风险类别允许 AI 审批。
- 运营凭证的最长有效期、轮换周期和是否限制来源地址；现在到期时间由负责人创建时给出，代码不设默认值和上限，来源由 `AXIOM_OPERATIONS_SOURCES` 按部署限制。
- 审计和操作记录的保留期；与钱有关的至少与账本同寿命。
- 审计链停下之后怎么恢复：把迟到的条目接在链尾、给被改的条目补一条确认，还是另起一段链；定下后在控制面加对应操作。现在只能停着，告警开着，审计照常写。
- 额度内 agent 直接退款或赠额是否开放；现在一律人工。
- 平台默认上限加站点覆盖；有第二个要定价的站点时再定。
- 供应商充值的实际付款渠道未接入：agent 只提案，负责人付款，agent 附凭证确认。
- 节点管理里的升级、增减服务器和删除数据是否进入运营接口；本设计只开放重启和摘除流量。
- 电话、短信服务商的选择，取决于是否有公司主体。
- 生产数据库的复制方式，部署前请负责人定：一主一同步备库（多一台机器，可以自动切换），或单主不自动切换（故障时人工恢复，停机更久）。

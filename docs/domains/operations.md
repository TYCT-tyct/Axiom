# 运营

由 AI agent 执行日常运营：谁做什么、agent 怎么运行、权限和审批怎么控制、怎么通知负责人、怎么发现 bug。对应代码模块 `operations`；运维节点在部署拓扑中的位置见[总体架构](../architecture.md#部署拓扑)。告警和通知渠道属于记录与告警（`observability` 模块），本文只写运营如何使用它们。

## 要求

- 运营由 AI agent 执行，尽量减少负责人投入的时间（见[产品需求的「运营」](../product.md#运营)）。
- 运营 AI 在能力上拥有全面的权限；资金和高风险操作按风险受控。
- 运营 AI 不绑定某一家模型，可以用 DeepSeek、Codex 等；也不能因为中转站或 Axiom 自身出问题而瘫痪。
- 高风险操作除了人工审批，也可以由第二个 AI 分析后审批。
- 通知负责人用记录与告警的通知渠道（见[记录与告警的「通知渠道」](observability.md#通知渠道)）。
- 运营 AI 能发现 bug 并提交 Issue，供后续处理。

## 设计

### 三层分工

| 谁 | 做什么 | 例子 |
|---|---|---|
| 固定流程（代码） | 规则明确、要求快和稳定的事 | 同步、检测、熔断、按规则自动调价、端点自动下线、故障切换 |
| 运营 agent | 需要判断的事 | 处理异常、认领待映射的模型、协助接入供应商、裁决数据来源的冲突、提出定价建议、排查故障、发现 bug 并提 Issue |
| 负责人 | 超出 agent 权限的事 | 审批、定策略、处理 agent 上报的事 |

### agent 的组成

| 部分 | 是什么 | 谁负责 |
|---|---|---|
| 运行框架 | agent 的"大脑"：调用模型、规划、记忆、定时任务、与负责人对话 | 采用 Hermes Agent，可替换 |
| 工具 | 运营接口，以 MCP 工具的形式提供（MCP 是 AI 调用外部工具的通用协议） | 我们 |
| 模型代理 | 运维节点上的一个小服务：保管模型的 key，按顺序尝试各个模型来源，执行花费预算 | 我们 |
| 规则 | 权限、风险分级、审批、额度上限、审计 | 我们，在核心节点的服务端执行 |
| 运行手册 | 各类运营任务的做法，以技能的形式提供给 agent | 我们，放在仓库里维护 |

- **控制全在服务端**：运行框架换成别的（比如 Codex，或我们自己写的），规则一条也不用改。负责人临时用 Claude Code 或 Codex 执行运维任务，也通过同样的 MCP 工具接入，受同样的约束。
- **agent 手里没有任何密钥**：
  - 模型的 key 由模型代理保管，agent 只能访问模型代理；
  - 登录中转站由我们的浏览器工具在服务端代为完成，agent 拿到的是已登录的页面，看不到密码；
  - agent 的运营令牌由运维节点上的 MCP 桥保管，只用于调用运营接口，不交给模型；模型只能发起工具调用。

### Hermes Agent 的加固

- **固定版本**：锁定镜像摘要和依赖的哈希，每次升级都要评审。
- **沙箱**：运行在 Docker 沙箱里（隔离的容器，看不到宿主机）。只允许访问运营接口的 MCP 桥、模型代理和浏览器工具，其他出站网络一律禁止。
- **工具白名单**：只开放运营接口的 MCP 工具和浏览器工具；命令行、读写文件、执行代码的工具全部关闭，启动时检查，不符合就拒绝启动。
- **技能只读**：运行手册从仓库以只读方式挂载，agent 不能修改；它自己积累的记忆只当作参考笔记，视为不可信，不能改变规则。
- **对话入口**：只接受负责人账号的私聊，必须先配对；群聊关闭。

### 模型来源

- **可配置**：在模型代理里登记多个模型来源，按顺序尝试，例如 DeepSeek 官方 API、OpenAI 官方 API、经 Axiom 网关。
- **至少一个直连**：至少有一个来源不经过中转站，也不经过 Axiom 自己。中转站或网关出问题时，agent 照样能工作。
- **专用 key**：每个来源用专给运维的 key，并在模型厂商那边设置花费上限。
- **按任务选模型**：日常巡检用便宜的模型，排查故障用强的模型。
- **预算由模型代理执行**：每天的模型花费、单个任务的工具调用次数和 token 都有上限。
- **全部不可用时**：agent 停止工作，固定流程和告警照常运行。告警永远不依赖 agent。

### 定时巡检

- Hermes 的定时任务按站点和供应商周期执行：余额与同步时间、模型和分组变化、端点健康与质量、价格与成本、待映射模型。巡检只读，走 `suppliers.view`、`catalog.view`、`pricing.view`；每轮结果写操作记录，异常通过 `alert_raise` 或通知渠道发出，不改配置。
- 固定规则先判断：余额低于阈值、端点连续失败、价格超出包络、模型消失等。规则能处理的按固定流程处理，规则判断不了的才交给 agent；阈值和巡检周期在控制面配置，agent 不能改。
- 每轮巡检有工具调用预算和页面读取上限；失败不无限重试，下一轮继续。巡检停了不影响调用路径和告警。

### 运营接口

运营接口是 agent 改动 Axiom 的唯一入口；读供应商页面走浏览器工具，不经过运营接口。下面是接口设计，按「上线与兼容」的分片落地。现状：第一片已实现——契约 `api/operations.yaml`、核心的运营监听、运营凭证与控制面的凭证管理和紧急停止、读工具 `whoami`、`operation_log_list`、`suppliers_list`、`suppliers_get`、`pending_mappings_list`、`models_list`、`model_get`、`calls_list`、`call_get`，以及每次调用的操作记录。第二片的审批引擎已实现：运营操作和审批的表、第一个写工具 `model_set_status`（上架直接执行，下架等负责人批准）、`operations_list`、`operation_get`、`approvals_list`、`approval_get`、`approval_wait`、`approval_withdraw`，管理接口的审批列表、详情、批准和驳回，到期清扫，以及审批通知的告警信号；管理后台的审批页（`/approvals`）也已实现；一键令牌和审批 AI 还没有。第三片的转账上限已实现：控制面的上限策略（`/operations/cap-policies`）、计数器与预留，以及第一个资金写，供应商充值的提出与确认（`supplier_top_up_propose`、`supplier_top_up_confirm`）；随后加上了上限用量的读工具 `caps_get`、资金写的单独限频，以及每分钟的上限对账、对不上就暂停自主资金操作和负责人的修复（`/operations/cap-policies/{scope}/{category}/repair`）。第三片的售价包络也已实现：控制面的包络（`/operations/price-envelopes`）、售价计数器、读工具 `prices_list` 和售价的写 `price_publish`（发布自动发布器等待确认的提案），`caps_get` 同时列出包络和当天的用量；改定价规则还没有。第三片的赠额也已接入上限：agent 用 `credit_grant` 提出给某个账户赠额，按站点的 `money.credit` 上限预留，总要负责人批准，批准时以 agent 的名义赠出并计入已用。第四片的 MCP 桥已实现：运维节点按 `AXIOM_MCP_ADDR` 在回环地址上把契约的每个操作作为一个 MCP 工具提供给本机的 Hermes，并转发给核心的运营监听（见「MCP 映射」）；Hermes 本身的部署、工具白名单和沙箱放行还没有。日常写的端点开关也已实现：`endpoint_set_enabled` 直接启用或停用一个端点，agent 据巡检调整路由。接入供应商的两个日常写也已实现：`supplier_group_select` 选用或取消选用供应商的分组，`supplier_model_map` 把分组里待映射的名字映射到目录模型。告警也已实现：读工具 `alerts_list` 列出平台的告警事件，`alert_raise` 和 `alert_resolve` 让 agent 经同一套规则和渠道告警负责人、问题过去后再恢复。第五片的审计哈希链也已实现：每条已提交的审计条目在提交后由每分钟的任务接进 `operations.audit_chain`，每天把整条链和审计日志重新核对一遍，发现被改、被删或插到链头之前的条目就停止接链并告警（见「审计」的「防篡改」）；链每分钟复制到部署之外的桶（配了副本桶时），每个 UTC 日结束后做一份负责人的摘要并发告警信号（见「审计」的「异地复制和摘要现在的实现」）；对账还没有。审计的读也已实现：`audit_list`、`audit_get` 按管理后台审计页的同一套查询读全平台的审计条目，`audit_digests` 读每天的摘要（见「审计」的「谁能读」）。控制面的 agent 限频也已齐：负责人可以调低请求、每分钟和每小时的资金写和发告警（见「运营凭证」的「限频」）。其余读工具（余额、端点、路由预览、节点）、其余写工具、退款和桥的按任务预算随后续分片落地。接口面是公开契约，资金规则和它一起按「谁拍板」需要负责人同意；负责人 2026-11-04 在[评论](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6498764672)批准本设计，原话：「12同意，3待定后续会做现在成本高不推荐。4测评我会单独做一个项目一个网站 5.写一个demo」；第 2 项即本设计，覆盖运营接口、MCP 映射、审批、资金上限和审计。

- **契约与监听**：运营接口另有一份 OpenAPI 契约 `api/operations.yaml`，路径前缀 `/api/operations/v1`，挂在核心节点的运营监听上（`AXIOM_OPERATIONS_ADDR`），不挂在公网、管理或节点监听上。监听默认关闭；打开时只接受带 `ops` 用途客户端证书的双向 TLS 连接（由 `ca.crt` 签发、`clientAuth`，且主题备用名里有 URI `urn:axiom:node-purpose:ops`；入口节点的证书没有它），来源再按 `AXIOM_OPERATIONS_SOURCES` 限制（只看连接地址，不读转发头；监听不是回环地址又没配来源就拒绝启动）。运维节点上的 MCP 桥是唯一客户端，它同时出示`ops` 用途的节点证书和运营凭证；只有运营凭证、没有`ops` 用途的节点证书的连接一样拒绝。
- **执行位置**：HTTP 处理器在 `cmd/axiom`，和两个现有接口一样只经各模块的公开接口组合；权限、审批、资金上限、操作记录和审计链在 `operations` 模块。运维节点上的 Go 程序只新增一个回环地址上的 MCP 监听，不连数据库、不读密钥环、不跑任务队列，也不持有任何业务数据；它把工具调用经`ops` 用途的节点证书和运营凭证转发给核心。这样 MCP 桥被攻破时，攻击者拿到的是运营凭证；数据库、供应商凭证和用户数据在核心，模型 key 和供应商会话在运维节点的其他进程，按各自的边界加固。
- **不是管理接口的副本**：只暴露 agent 需要的操作。控制面（审批策略、上限、运营凭证、模型来源、通知接收人、紧急停止）、用户与平台授权、商户与收款配置、数据删除、部署与升级、服务器增减都不在运营接口里；它们只在管理后台，由负责人两步验证后操作。第一版也不提供批量资金写或批量高风险写，一次调用只作用于一个对象，防止一次调用绕过按对象的审批和上限。
- **统一约定**：JSON；失败体是平台的 `{"error": {"code", "message", "fields"}}`，`code` 是封闭枚举，错误码稳定；每个请求带 `X-Request-ID`，响应 `Cache-Control: no-store`；列表用键集游标（`cursor`、`limit`，默认 50、最大 200）；金额是十进制文本，单位是站点记账货币的十亿分之一，运算用整数并检查溢出；每个工具调用都带 `reason`（读放 `reason` 查询参数，写放请求体；1–1000 字；不用请求头，因为头里放不下 UTF-8 的理由），agent 可以用 `X-Axiom-Run-ID` 头标出所属的运行，读的进操作记录，写的同时进审计；写操作必须带 `Idempotency-Key`（同一个键重发返回第一次的运营操作编号，并用 `Idempotency-Replayed: true` 标出），可选 `dry_run`；读到的对象带 `rev` 的写操作要把 `rev` 送回，已变化返回 409 `stale_revision`。请求体上限 1 MiB，写请求期限 30 秒，普通读请求 15 秒，`approval_wait` 最多等 10 秒；外部调用不在数据库事务里做（见「失败、重试与回滚」）。
- **试运行**：所有写操作支持 `dry_run`。服务端按真实数据重新计算影响、需要的审批、会预留的上限和会改动的对象，返回预览，仍写操作记录（标明 `dry_run`），但不写运营操作、不预留、不写审计、不调用目标模块；预览结果不构成执行许可，真正执行时全部重算。试运行也受权限和频率限制，不能借它探测别的站点。
- **默认能读**：供应商、余额、分组、模型、端点、健康度、价格、路由、告警、调用记录的元数据、节点状态。不能读明文密钥、供应商登录凭证、对话内容；调用记录只回元数据、费用和尝试，不回请求与响应正文。
- **读接口**（`GET`，除特别说明）：

  | 资源 | 操作与说明 | 权限 |
  |---|---|---|
  | 供应商 | 列表、详情、余额与同步时间、分组、端点模型、待映射模型；不返回凭证明文 | `suppliers.view` |
  | 端点与健康 | 列表、详情、当前质量/延迟/成功率、路由成员资格、启用状态与权重 | `suppliers.view` |
  | 模型与价格 | 模型、名字、参考价、当前售价、定价规则、价格版本 | `catalog.view`、`pricing.view` |
  | 路由 | 当前预设与默认链；`POST /routing/preview` 计算一个模型会走哪些端点（安全的 POST，不改数据） | `suppliers.view`、`catalog.view` |
  | 告警与调用 | 告警事件与送达回执（`GET /alerts`，`alerts_list`，平台范围，已实现）、调用元数据与尝试（不含正文） | `calls.search`、`calls.inspect` |
  | 运营记录 | 自己的调用记录（`GET /log`）、自己的运营操作（`GET /operations`、`GET /operations/{id}`）、自己的提案所等的审批（`GET /approvals`，`approvals_list`：从新到旧，可按审批状态筛，按审批编号翻页，每条带它的运营操作）、某个审批所等的运营操作（`GET /approvals/{id}`）和等负责人决定（`GET /approvals/{id}/wait`，`approval_wait`，见「MCP 映射」的「工具语义」），以及凭证够得着的范围的上限和当前日、周的用量（`GET /caps`，`caps_get`；站点凭证只看自己站点的策略，平台的要平台范围），都已实现；审计条目需要单独授权（`GET /audit`，`audit_list`；`GET /audit/{entry_id}`，`audit_get`；每天的摘要 `GET /audit/digests`，`audit_digests`；平台范围，已实现，见「审计」的「谁能读」） | `operations.read`，审计另需 `audit.view` |
  | 自身凭证 | `GET /me`：凭证 ID、站点范围、是否平台范围、权限、提出方厂商、到期时间；不含令牌 | `operations.read` |
  | 节点 | 节点列表、角色、心跳、健康、当前版本 | `nodes.view` |

- **写接口**（`POST`/`PUT`，都带 `reason` 和 `Idempotency-Key`，都可 `dry_run`；回答是一个运营操作对象：`operation_id`、`state`（`pending_approval`/`approved`/`executing`/`succeeded`/`failed`/`unknown`/`canceled`/`expired`/`rejected`/`reverted`）、`risk`、`approval`（编号、要求档位、到期）、`cap`（类别、窗口、上限、已用、本次、硬上限）、`result` 或 `error`。本地同步完成返回 200；等审批或外部调用未完成返回 202，带 `next_check_after_seconds`；被硬上限或校验拒绝返回 422；状态冲突、指纹变化、幂等键复用返回 409）：

  | 操作 | 风险类别 | 权限 | 默认审批 |
  |---|---|---|---|
  | 端点启用/停用、调权重、重跑检测 | 日常 | `suppliers.manage` | 直接执行，每日汇总 |
  | 映射待映射模型、选择供应商分组 | 日常 | `suppliers.manage` | 直接执行，每日汇总 |
  | 上架模型（恢复） | 日常 | `catalog.manage` | 直接执行，每日汇总 |
  | 下架模型 | 下架 | `catalog.manage` | 人工 |
  | 确认供应商单位余额价值 | 单位价值 | `suppliers.manage` | 与适配器提示一致时直接执行，否则人工 |
  | 发布售价、修改定价规则 | 售价 | `pricing.manage` 和 `operations.money` | 价格包络内直接执行，超出人工 |
  | 提出供应商充值 | 充值 | `suppliers.manage` 和 `operations.money` | 累计上限内直接提出，超出人工；实际付款仍由负责人完成 |
  | 确认供应商充值到账 | 充值 | `suppliers.manage` 和 `operations.money` | 直接执行；必须附付款凭证；agent 提案的金额计入累计上限，负责人自己发起的只记录 |
  | 发起退款 | 退款 | `refunds.manage` 和 `operations.money` | 人工；支付模块的第二人规则同时适用 |
  | 给账户赠额 | 赠额 | `credits.grant` 和 `operations.money` | 人工；计费模块的规则同时适用 |
  | 发布路由预设 | 高风险 | `sites.manage` | 人工，必须进管理后台并两步验证 |
  | 重启单个节点、摘除流量 | 日常 | `nodes.manage` | 直接执行，每日汇总 |
  | 升级、增减服务器、删除数据 | — | — | 不在运营接口里 |
  | 发告警与恢复自己发的告警、提 Issue、撤回自己的待审批提案、取消自己的未开始操作 | 日常 | `operations.write` | 直接执行，限频 |

资金类操作在资金上限服务接入前不生成工具、不开放接口。充值和赠额已接入上限（见「转账的累计金额上限」的「现在的实现」）；退款还没有接入，不生成工具，agent 只能发告警或 Issue 建议，由负责人处理。

现在实现的写：`PUT /models/{id}/status`（`model_set_status`）的上架是日常、直接执行，下架等负责人审批；`POST /approvals/{id}/withdraw`（`approval_withdraw`）撤回自己的待审批提案（`dry_run` 时在一个回滚的事务里跑完撤回的检查，什么都不留下）。提案时按 `rev` 和模型状态先拒绝目标模块执行时一定会拒绝的（旧 `rev`、下架不在售的模型），不让负责人去批一个注定失败的提案；`dry_run` 只回操作会从哪个状态开始（直接执行是 `approved`，要审批是 `pending_approval`），不写、不调目标模块。`POST /suppliers/{id}/top-ups`（`supplier_top_up_propose`）提出充值，`POST /suppliers/{id}/top-ups/{operation_id}/confirm`（`supplier_top_up_confirm`）附付款凭证确认到账，两者都要 `suppliers.manage` 和 `operations.money`，契约上标 `x-axiom-money: true`，`dry_run` 在一个回滚的事务里跑完全部检查。`POST /prices/{model_id}/publish`（`price_publish`）发布主站一个模型等待确认的售价提案，要 `pricing.manage` 和 `operations.money`，包络内直接执行、超出等负责人（见「售价的累计变动上限」的「现在的实现」）；`GET /prices`（`prices_list`）读主站的售价和提案。`POST /accounts/{account_id}/credit-grants`（`credit_grant`）提出给账户赠额，要 `credits.grant` 和 `operations.money`、平台范围，账户的站点不在凭证的站点里就和不存在一样答 404；金额和到期时间按管理接口赠额的同一套规则读（站点记账货币、单笔不超过 10,000 个币种单位、到期在未来），永远等负责人批准（202），`dry_run` 在一个回滚的事务里跑完全部检查。`PUT /suppliers/{id}/endpoints/{endpoint_id}/enabled`（`endpoint_set_enabled`）启用或停用供应商的一个端点（`suppliers_get` 列出端点和开关），要 `suppliers.manage`、平台范围，日常、直接执行，以 agent 的名义经 suppliers 写审计 `supplier.endpoint.enabled`，结果是开关现在的值；各节点下一次重建路由时生效，同步从不改回，负责人在管理接口 `setSupplierEndpointEnabled` 改回；供应商移除中或已移除答 409 `conflict`，`dry_run` 在一个回滚的事务里跑完全部检查。`POST /alerts`（`alert_raise`）发一条种类为 `operations.agent_alert`、合并键是 `<凭证 UUID>/<key>`（`key` 由 agent 给，`[A-Za-z0-9._:/-]`，1–128 个字符；结果里给出完整的合并键）的告警，`POST /alerts/resolve`（`alert_resolve`）恢复这个键上未恢复的事件；两者要 `operations.write`、不要平台范围（告警是 agent 自己对负责人说的话，不读平台数据），日常、直接执行，信号在运营操作的事务里经 `alert.Persist` 持久化、编号就是运营操作的编号，所以重发不会多发一次。告警带严重度（`info`、`warning`、`critical`）和摘要 `summary`：摘要就是通知里负责人读到的那句话，最多 512 字节 UTF-8（约 170 个汉字，信号字段的上限），按 agent 的不可信文字对待；信号字段还有运营操作编号，从通知能查回是谁、为什么发的。通知走告警的同一套规则和渠道：负责人给 `operations.agent_alert` 加一条规则并绑定渠道才会收到，按严重度分级。同一个键在事件恢复前再发只累加次数、更新摘要，不再通知；`alert_resolve` 之后再发是新的事件。恢复一个没有未恢复事件的键什么都不改；只能恢复这张凭证自己发的告警：合并键带着凭证，另一张凭证用同样的 `key` 发或恢复的是它自己的事件，覆盖不了、也恢复不了别人的；其他种类按各自的规则恢复或由负责人关闭。结果是 `kind`、`key` 和 `resolved`，事件约一分钟内（告警消费者每分钟一轮）出现在 `alerts_list` 里。`GET /alerts`（`alerts_list`）要 `calls.search` 和平台范围，从新到旧列出告警事件和送达回执，`open=true` 只列未恢复的，用键集游标翻页。`PUT /suppliers/{id}/groups/{group_id}`（`supplier_group_select`）选用或取消选用供应商的一个分组（`suppliers_get` 列出分组），`POST /suppliers/{id}/groups/{group_id}/model-mappings`（`supplier_model_map`）把这个分组列为待映射的名字（`pending_mappings_list` 列出）映射到一个目录模型（`models_list`），只对这个分组有效；两者都要 `suppliers.manage`、平台范围，日常、直接执行，经 suppliers 的同一个函数以 agent 的名义写审计（`supplier_group.select`/`supplier_group.unselect`、`supplier_alias.create`），供应商移除中或已移除答 409 `conflict`，`dry_run` 在一个回滚的事务里跑完全部检查。选用的结果是分组现在的 `selected` 和 `codename`：第一次选用时起代号、之后不变，下一次同步给它建 key、把它的已映射模型变成端点；取消选用让它退出路由、保留代号；选用已不在列表里的分组答 409 `conflict`，要的状态和现在一样时什么都不改、照样成功。映射的结果是别名（`alias_id`、`upstream_name`、`model_id`、`revision`），名字离开待映射队列；下一次同步后，分组选用且模型在售、有成本时它就是一个端点，和其他端点一样接流量，真伪检测通过之前不是 `verified`，`:exacto` 和只走已验证端点的预设不选它。只能映射正在等的名字：分组没列出、目录已认出，或分组、整个供应商的别名已盖住的名字答 409 `conflict`；也只能映射到分组里还没有名字的模型：分组已有这个模型的端点、分组列出的名字已解析到它，或有别名（含下一次同步还没投影的）把分组列出的名字映射到它时同样答 409 `conflict`，因为一个分组的一个模型只有一个端点，新名字可能接管它；目录没有或已下架的模型答 422 `unprocessable`。纠正已有别名、建整个供应商的别名、声明适配器推不出的调用格式仍只在管理接口，理由见「决策与理由」。表里的调权重没有对应的存储：端点的权重由路由按健康度和号池自动算，不是人设的值，所以不提供；重跑检测随后续分片。其余写操作和 `operation_cancel` 尚未实现；`approved` 的操作现在都在批准它的事务里执行完，没有"已批准未开始"的可取消状态。

状态机：`pending_approval` 可到 `approved`、`rejected`、`expired`、`canceled`；`approved` 可到 `executing`、`rejected`、`expired`、`canceled`；`executing` 可到 `succeeded`、`failed`、`unknown`；`unknown` 经对账到 `succeeded` 或 `failed`。`rejected`、`expired`、`canceled`、`failed`、`reverted` 是终态；`succeeded` 已结算，配置类被补偿操作冲正后原操作记 `reverted`，资金类原操作不改状态、由目标模块的退款/冲正记录关联。要重做就新建操作，不复用旧状态、旧批准或旧预留。

- **新增权限**：运营接口和运营凭证使用 `accounts` 已有的权限名，另加 `operations.read`（读自己的操作记录，不敏感）、`operations.write`（告警、Issue、撤回、取消，不敏感）、`operations.money`（所有资金操作的前置范围，敏感）、`operations.approve`（审批，敏感）、`operations.manage`（控制面，敏感）、`refunds.manage`（退款，敏感）、`nodes.view` 与 `nodes.manage`（节点读取与管理）。`operations.approve` 和 `operations.manage` 只授予负责人（迁移把两者放进内置 `admin` 角色）；运营凭证不能持有这两个权限中的任何一个（代码和表的 CHECK 两处拒绝），所以 agent 不能审批自己、不能改策略和上限。现在声明了 `operations.read`、`operations.write`、`operations.money`、`operations.approve` 和 `operations.manage`；其余随用到它们的写操作加入。资金操作同时要求 `operations.money` 和对应的业务权限，只有日常权限的凭证花不了钱。

#### 运营凭证

- **是什么**：运营凭证是 `accounts` 的第三种操作者，和用户会话、管理 key 并列：一串 256 位随机令牌，带 `op-ax-v1-` 前缀和校验位，只在创建时显示一次；存在 `accounts.agent_credentials`，表里只存带密钥的哈希、哈希密钥版本、前缀和末四位。它不是用户、不是会话、不是调用 key，不能登录控制台、管理后台或调用模型，也不能调用公网接口；只在运营监听上有效。
- **权限与范围**：凭证有自己的权限集合、站点范围（默认所有站点，可缩到部分站点）、是否带平台范围（默认不带）和提出方厂商列表（审批 AI 用来避开同厂商），权限名和角色里的完全同一套。每张凭证至少带 `operations.read`，创建时自动加上、不能去掉；否则它连自己的操作记录都读不到，MCP 桥也无法用 `GET /me` 过滤工具。校验走 `accounts` 授权入口的新分支：凭证不经过 `Target` 的账户/平台成员关系，也不套用人的会话级别、管理面或两步验证；按凭证的站点范围、平台范围和权限集合判断，平台级资源（全站供应商、审计、节点）要单独授予平台范围。两步验证发生在负责人创建、修改或轮换它的控制面操作上。站点范围之外的资源和不存在的资源一样返回 404，不透露存在。
- **生命周期**：只能在管理后台创建、改范围、轮换和吊销，要求 `operations.manage`、两步验证和 CSRF（接口见「控制面」；改范围尚未提供，要改就新建再吊销旧的）；创建时还要选提出方厂商列表，审批 AI 据此避开与提出方同厂商的模型。轮换时新旧令牌可以重叠最多 24 小时（默认 24，可设 0），给 MCP 桥换文件的时间；再次轮换时上一次留下的旧令牌立即失效，任何时刻最多两个令牌有效。旧令牌到期或吊销后下一次请求就失败，没有缓存：每个请求都查数据库。令牌只在创建或轮换的那次响应里出现，幂等重放的响应不带令牌。凭证的到期时间由负责人在创建时为每张凭证给出（必填，只要求在未来；代码不带默认值和上限，最长有效期的规则见「待定问题」），到期后和吊销一样：认证、吊销、紧急停止和列表都把它当作已不存在；另记最后一次使用时间（最多每分钟写一次）；连续认证失败的告警尚未实现。负责人可以给每个运行环境建一张凭证，审计按凭证 ID 区分。
- **请求认证**：`Authorization: Bearer <token>`，外加 `ops` 用途的客户端证书。服务端按哈希查凭证，核对未过期、未吊销、站点范围和操作要求的权限；不读 Cookie，不要 CSRF，不要 `Origin`，不开放 CORS。缺凭证、错凭证、过期和吊销都返回 401，权限不足返回 403，站点范围外返回 404。
- **限频**：每张凭证每分钟最多 600 个请求、突发 60（现在按核心节点各自计数，令牌桶在进程内；MCP 桥只连 `AXIOM_OPERATIONS_URL` 一个核心地址，多核心共享计数等多核心部署时再定）；资金写每分钟 30、每小时 300（守卫在业务权限和 `operations.money` 之后、校验之前，按凭证在本节点另扣一次，试运行和重放也算）；检测重跑每小时 30；发告警每小时 60（处理器在校验之后扣，试运行和重放也算，恢复不算）；提 Issue 每小时 10。超过返回 429 和 `Retry-After`；限频的资金写和告警记进操作记录，超过请求限频的没有记录（见「审计」）。这些是上限也是默认值，负责人可以调低：控制面 `/operations/agent-limits` 的 `requests_per_minute`（1–600）、`money_writes_per_minute`（1–30）、`money_writes_per_hour`（1–300）、`alerts_per_hour`（1–60），按读到的版本改、没给的项保持原值，记审计 `agent_limits.set`；没设过的项就是上限。守卫在认出凭证之后、每个请求读一次这一行，按凭证在本节点扣请求的令牌桶（装每分钟次数的十分之一，按每分钟的次数均匀补），资金写和告警用同一次读到的值，所以调低从 agent 的下一个请求起在每个核心节点生效。资金写的两个桶和告警的桶各装窗口次数的一半、其余在窗口里均匀回来（每分钟 30 是 15 次起、每 4 秒回一次；每小时 300 是 150 次起、每 24 秒回一次；每小时 60 是 30 次起、每 2 分钟回一次），所以任何一个窗口里不超过设的次数。令牌桶只记它按自己的补充速度何时装满，调低后会忘掉窗口里已经放行的次数，所以每类另记最近放行的时刻（最多设的次数个）：窗口里已放行设的次数就拒绝，等最早的那次离开窗口；这样调低时窗口里已放行的照样算，请求也确实每分钟不超过设的次数。滚动发布期间旧核心不读新加的三项，按上限放行，也拒绝带这三项的设置（400）；全部核心升级后调低才处处生效。检测重跑和提 Issue 的工具还没有，它们的限频随工具加进同一行。核心和 MCP 桥各执行一次，桥的预算按每次 agent 任务算，防止模型循环刷工具；桥的预算尚未实现，现在只有核心的限频。
- **紧急停止**：吊销所有运营凭证（现在由此实现停止：没有活的凭证，运营监听对每个请求都答 401，MCP 桥把它作为工具错误交给模型，桥重启时问不到 `GET /me` 就拒绝启动；全局开关和 Hermes 的停止随 Hermes 的部署落地），下一个请求立即 401；同一个事务里待审批的提案作废（运营操作和审批都记 `canceled`，答案里的 `canceled` 是作废的个数），已经在执行的外部调用按「失败、重试与回滚」收尾。吊销一张凭证也同样作废它的待审批提案。提案前先持有凭证行（`FOR SHARE`），所以停止要么在提案之前、提案被 401 拒绝，要么等它提交后把它一起作废。恢复只有负责人两步验证后重建凭证，旧凭证不会复活。

#### MCP 映射

- **位置**：运维节点的 Go 程序（`axiom serve`，角色 `ops`）在回环地址 `AXIOM_MCP_ADDR` 上开一个 MCP 监听，只服务本机的 Hermes（同一台机器，或与桥共用网络命名空间的容器）；地址不是回环 IP 就拒绝启动。它不连数据库；运营凭证在 `AXIOM_OPERATIONS_TOKEN_FILE` 里，文件只能属主可读（同节点密钥的检查），每次工具调用都重读一次，所以轮换只需换文件、不用重启，令牌只存在于桥进程，模型和工具结果都看不到它。Hermes 到桥用每次启动随机生成的本地令牌认证（`Authorization: Bearer`，常数时间比较）：桥启动时把它写进 `AXIOM_MCP_TOKEN_FILE`（权限 0600，整文件替换，Hermes 要以同一用户读它），上一次启动的令牌随之失效；这个路径若与运营凭证或节点证书目录里的 `node.crt`、`node.key`、`ca.crt` 是同一个文件（换一种写法、经链接也算），桥在写任何东西之前拒绝启动，不让令牌把它们换掉。桥到核心用 `AXIOM_NODE_TLS_DIR` 里带 `ops` 用途的节点证书加运营凭证，地址是 `AXIOM_OPERATIONS_URL`（`https`，不带路径）；桥从不跟随重定向，否则凭证和写的请求体会被带到回答所指的地方（同一主机的明文端口也算），核心本来不重定向，所以 3xx 在启动时是拒绝启动、在调用时是工具错误。没有用 stdio：那会把凭证放进 agent 的进程空间，桥也无法独立升级和限频。
- **协议**：用 MCP 官方的 Go SDK（`github.com/modelcontextprotocol/go-sdk`，v1.8.0）提供 Streamable HTTP：无会话（`Stateless`），每个请求一个 JSON 回答，不开 SSE 流；同时说 2026-07-28 的无握手版本和更早的带 `initialize` 的版本，由 SDK 按请求协商。SDK 拒绝经回环地址到达、`Host` 却不是本机的请求（防 DNS 重绑定），桥另用 `http.CrossOriginProtection` 拒绝浏览器的跨源请求；请求体上限 1 MiB，与运营接口相同。理由见「决策与理由」。
- **工具生成**：一个契约操作对应一个 MCP 工具，工具名用契约里的 `x-mcp-name`（稳定的 lower_snake_case），输出就是运营接口的 JSON；契约里标了 `x-mcp: false` 的操作不生成工具。工具从程序嵌入的契约（`operationsapi.GetSpec`）在启动时生成，所以工具列表随构建固定，服务端版本报的是契约的 `info.version`；运行时不接受任意 HTTP 地址、shell 或文件工具。输入 schema 是一个对象：路径参数、查询参数和请求体的属性按原名，两个请求头按 `idempotency_key`（`Idempotency-Key`）和 `run_id`（`X-Axiom-Run-ID`），每个引用都展开、不留 `$ref`，`additionalProperties: false`；契约里出现桥不认识的请求头、重名的参数，或 `not`、`discriminator`、OpenAPI 3.0 的排他边界这类在 JSON Schema 里读法不同的关键字时桥拒绝启动，不把少于核心检查的描述交给模型。桥只拒绝工具不收的参数、缺少或会改变路径的路径参数（空、`.`、`..`）和给参数传对象或数组，其余校验都由核心按同一份契约做。桥在启动时用自己的理由调用 `GET /me`，按凭证的权限（动钱的另要 `operations.money`，平台范围的要平台授权）决定提供哪些工具；没有权限的工具不出现，直接调用按未知工具拒绝。核心不答或拒绝这张凭证时桥拒绝启动。滚动发布时桥和核心的契约可以不同：新桥调到旧核心还没有的操作，得到的是 404 的工具错误；旧桥不提供新操作，读 `GET /me` 时跳过不认识的字段。新增工具是兼容变更；改名或删除要升契约主版本并改运行手册，`TestBridgeToolsFollowTheContract` 守着工具名单。
- **工具语义**：读工具直接返回数据；写工具返回运营操作对象（`operation_id`、`state`、`approval`、`cap`、`result`）。核心的回答原样作为文本内容返回，3xx、4xx 和 5xx 标 `isError`，模型读得到错误码；桥发不出的调用同样是工具错误。每个工具都要求 `reason`，每个写都要求调用方给 `idempotency_key`（契约的必填头）；连接复用失败时 Go 的 HTTP 客户端只重发带 `Idempotency-Key` 的请求或读，用的是同一个键。写在桥这边丢了回答（核心没答完、连接断开、超过 40 秒）时，工具错误会说结果未知、用同一个 `idempotency_key` 再调一次，核心按键返回第一次的运营操作，不会执行两次；模型层重试也可以用返回的 `operation_id` 查状态。需要审批时返回 202 和 `approval_id`，不阻塞模型；agent 用 `approval_wait` 做最多 10 秒的长轮询，或先做别的事再 `approval_get`。`approval_wait` 先读一次（不是自己凭证的审批立即答 404），负责人还能决定时每秒再读一次，审批一被决定、撤回、作废或按数据库时钟过了到期时间就答，最迟到 `wait_seconds`（1–10，默认 10）答它当时的样子；答出的审批还是 `pending` 就是等的这段时间没人决定。一次等待按一次调用计频率、记一条操作记录。
- **注解**：读工具标 `readOnlyHint: true`；会改配置或动钱的写工具标 `destructiveHint: true`；带幂等键的写工具标 `idempotentHint: true`；全部 `openWorldHint: false`。注解只影响客户端提示，真正的权限、审批和上限由核心执行。
- **工具清单**（按资源分组，完整列表以契约生成物为准）：`suppliers_list`、`suppliers_get`、`supplier_balance`、`supplier_groups`、`supplier_models`、`supplier_group_select`、`supplier_model_map`、`endpoints_list`、`endpoint_get`、`endpoint_set_enabled`、`endpoint_set_weight`、`endpoint_probe`、`models_list`、`model_get`、`model_set_status`、`prices_list`、`price_publish`、`pricing_rule_update`、`routing_preview`、`routing_preset_publish`、`alerts_list`、`alert_raise`、`alert_resolve`、`issue_create`、`operations_list`、`operation_get`、`operation_cancel`、`operation_revert`、`approvals_list`、`approval_get`、`approval_wait`、`approval_withdraw`、`caps_get`、`calls_list`、`call_get`、`audit_list`、`audit_get`、`audit_digests`、`whoami`、`nodes_list`、`node_restart`、`node_drain`、`supplier_top_up_propose`、`supplier_top_up_confirm`、`refund_request`、`credit_grant`。不生成 `approve`、`reject`、`cap_set`、`policy_set`、`credential_*`、`deploy` 这类工具。
- **审批在带外**：批准和驳回只能在管理后台或带一次性令牌的审批通知里做，不在 MCP 工具里。对话入口里说"同意"不算批准，模型也不能自己调用批准工具。

### 资金操作上限

资金操作分两类，各自有累计上限，单位不同：

- **转账**：供应商充值、退款、赠额。按站点记账货币的整数金额累计，单位是 10⁻⁹ 个币种单位。这是本节的重点。
- **售价**：发布售价、修改定价规则。按单价变动和笔数累计，不折算成金额。理由见「决策与理由」：折算需要预测销量，预测可被操纵，也会让上限随模型、时段漂移；售价的损失由最低毛利率和单日变动幅度直接约束，已经是累计上限。

上限约束的是 **agent 发起** 的运营操作；负责人在管理后台自己做的充值、退款、赠额按管理接口的两步验证和第二人规则执行，不占 agent 的额度，但同样写审计。只有 agent 提案并占有额度的充值才计入；提案过期释放后，负责人再自己付款的，按负责人发起的操作记录，不算回 agent 的额度。硬上限约束的也是运营接口里的 agent 操作，不是负责人的管理操作。

#### 转账的累计金额上限

- **维度**：每个站点、每个类别（`money.top_up`、`money.refund`、`money.credit`）各有单笔、每日、每周、每日笔数、按对象（供应商、账户）每日和硬上限。单笔是自主执行的上限；每日/每周/按对象是累计上限；硬上限是任何对 agent 操作的审批都不能越过的绝对上限，超过就拒绝，只能由负责人在控制面调高后重试。负责人可以给平台设默认值，再按站点覆盖；没有策略就是拒绝，不是不限。
- **金额怎么算**：服务端从数据库算，不取 agent 写的数字。充值按供应商确认的单位余额价值把原生金额换成站点记账货币，再按当时汇率折算，向上取整到 10⁻⁹；缺单位价值或汇率就拒绝。退款按支付模块给出的退款报价（额度、币种、汇率）算。赠额按赠出的额度面值算。每一笔同时保存原生金额、原生币种、单位价值、汇率和计入上限的金额，审计可以复算。
- **窗口**：固定 UTC 日（00:00 起）和 ISO 周（周一起）。固定窗口的代价是边界上可能连续用两个窗口的额度；按对象上限、笔数上限和硬上限会削弱这一点。滚动窗口要保存并扫描每一笔，锁的范围也更大，当前运营量下不值得；以后量上来再评估。待审批提案默认 30 分钟到期，已批准但未开始的运营操作默认 5 分钟执行期限，两者都不晚于当前 UTC 日结束；跨窗口或超期的待批提案和未开始操作在窗口结束时过期并释放，需要在新窗口重新提、重新审批，避免用昨天的额度执行今天的钱。已经进入 `executing` 的外部调用不受此限；结果未知时保留原窗口的预留，不转入新窗口。
- **计数器**：`operations.cap_counters` 每个 `(站点, 类别, 窗口类型, 窗口开始, 对象类型, 对象 ID)` 一行，记 `reserved`（已预留未定）、`committed`（已成功）和笔数，整数，初值 0，运算检查溢出。类别行和对象行都要更新；`reserved + committed + 本次金额` 只对**硬上限**是必须成立的拒绝线，自主/累计上限只是审批线：待批或人审的金额可以超过它，但不能超过硬上限。硬上限按策略定义到单笔或某个窗口；按窗口的用对应计数器行检查，按单笔的只检查本次金额。笔数上限同样只决定审批，不是拒绝线。已成功的金额不会因为后来的退款、撤销或反向操作自动退回；要恢复额度只能由负责人在控制面调高。这样"花掉、退回、再花"不能在同一窗口里循环。
- **原子执行**：一笔转账按下面的顺序在一个数据库事务里完成：
  1. 处理器从目标模块读出对象、金额、币种、汇率、单位价值和影响范围，生成规范化指纹；参数里有任何 agent 自由文本都不参与金额计算。
  2. 打开平台范围事务，先锁目标行（供应商、账户或模型），再按固定顺序锁上限策略行（`FOR SHARE`）和计数器行（`FOR UPDATE`，先类别后对象，按主键升序）。锁顺序全模块一致，避免死锁。
  3. 逐维检查：超过硬上限 → 回滚，422 `cap_exceeded`，不建运营操作；超过自主/累计上限但在硬上限内 → 建待审批提案，把金额记入 `reserved`，记下预留窗口和 `expires_at`，提交后等审批；在自主额度内 → 记入 `reserved`，状态 `approved`（本地改动在同一个事务里直接进 `succeeded`），同样记下窗口和 `expires_at`。
  4. 本地改动（数据库内的价格、额度、退款冻结）在同一个事务里调用目标模块接受调用方事务的函数，写完运营操作、计数器、审计一起提交；任一步失败全部回滚，不留下预留。
  5. 外部调用（渠道退款、未来的自动充值）在事务提交后才发；发之前在一个事务里锁运营操作，并按第 2 步的顺序锁计数器，核对仍在原预留窗口内且未超过执行期限，把状态改成 `executing` 并记审计；跨窗口或超期就改 `expired`、释放、不调用。结果回来后在另一个事务里把 `reserved` 转成 `committed`（成功）或释放（确定失败，状态 `failed`）；结果未知则保持 `reserved`，状态 `unknown`，告警，等人工对账；跨窗口的未知结果保留原窗口的预留，不转入新窗口。
  6. 审批通过时重新锁运营操作、审批、目标行和计数器行（按第 2 步的顺序），核对指纹、`rev`、策略版本、硬上限、当前窗口和执行期限；窗口或执行期限变了改 `expired`，指纹、`rev`、策略版本或硬上限变了改 `rejected`，都释放，不拿旧批准去执行新操作。
- **审批与上限的关系**：累计上限决定"能不能不经过人"；硬上限决定"能不能做"。超出累计上限的提案可以转人工，但金额必须在硬上限内；人工批准不会把金额从计数器里去掉，批准后仍然占用额度，可以超过自主/累计阈值，但不能超过硬上限。硬上限只能由负责人在控制面改，改的时候要两步验证并记审计。审批 AI 的上限不高于人工上限，且不能碰硬上限。
- **失败与对账**：确定失败释放 `reserved`；超时、连接断开、进程崩溃等无法判断的结果保持 `reserved`，不自动重试不幂等的外部调用。每分钟的对账任务按 `operations.money_actions` 重算当前窗口的计数器，和 `cap_counters` 比对；不一致就告警，并暂停该站点该类别的自主资金操作，直到负责人两步验证后修复。修复也在锁内重算，不手工改数字。
- **现在的实现**：类别有 `money.top_up` 和 `money.credit`。策略按 `(类别, 站点)` 一行，站点为空是平台（平台供应商的充值没有站点，记在平台上）；负责人给平台设默认值、再按站点覆盖还没有做，哪个范围没有策略就不动钱。策略有币种（建了不变）、五个自主上限（单笔、日、周、对象日、日笔数）和三个硬上限（单笔、日、周），硬上限不能低于对应的自主上限。充值的金额是 `原生金额 × 单位价值`，供应商的结算币种和策略不同时再乘计费的当前参考汇率（不加充值缓冲），向上取整到 10⁻⁹；缺单位价值或汇率回 422 `unprocessable`，账户自带的 key 和已移除的供应商回 409。提案在上限内直接成功（预留），超出自主上限等负责人，超出硬上限回 422 `cap_exceeded`、不建运营操作；提案等锁时跨过了 UTC 午夜就回 409、整体回滚，在新的一天重提。同一个键的重试先找原来的操作，不再读供应商，所以成功之后供应商被移除也拿得回。充值提案成功只表示负责人可以付款，预留一直占着，直到 agent 用 `supplier_top_up_confirm` 附凭证确认到账（转为 `committed`），或当天 UTC 结束时由每分钟的清扫释放；过了日再确认回 409，负责人仍可以自己付款，那一笔不算 agent 的额度。批准时按现在的策略重算硬上限（窗口里已含这笔预留）：放宽的不影响，调低到装不下它的以 `stale_revision` 结束并释放；资金操作仍记下提案时的策略版本，供审计。对账：`operations.cap_reconcile` 在 `money` 队列上每分钟一轮，用一条语句把当前 UTC 日和 ISO 周的计数器和 `money_actions` 加起来的数比对（每笔按状态计入日、周和对象日的 `reserved` 或 `committed`，笔数不论状态都算）；一条语句看到的是一个快照，同一个事务里改的资金操作和计数器要么都看到、要么都看不到，所以进行中的提案不会被当成不一致。对不上的范围和类别，在锁住策略行（`FOR UPDATE`）后再比一次，仍不一致就在策略行上记 `paused_at`、以 `system:operations.cap_reconcile` 记 `cap_policy.pause`（每行计数器的现值和应有值；审计的 `detail` 上限 8 KiB，行多时按大小拆成几条，带 `part`/`parts` 编号，修复同样），并发 critical 告警 `operations.cap_drift`；已经暂停的不重复记、不重复告警。暂停期间这个范围的每笔提案都交给负责人（审批摘要的 `cap.paused` 为 true），硬上限照旧拒绝。负责人两步验证后调修复：锁策略行（等进行中的提案）、按固定顺序锁当前窗口的全部计数器，把每行设为资金操作加起来的数（缺的行补上，没有资金的行归零），清掉暂停、记 `cap_counters.repair`（改前改后）、解除告警；没有漂移的范围修复只是清掉暂停。只比当前窗口：过去的窗口不再参与判断。确认、释放和清扫在动计数器之前也先 `FOR SHARE` 持有策略，和提案、批准一样：修复持有策略和已有的计数器后要补回缺的行，不持有策略的确认若先补了这一行再等修复的计数器，两边就互相等待。滚动发布和回滚：不认识 `paused_at` 的旧节点会把额度内的提案直接预留，所以数据库在 `money_actions` 上加了触发器 `refuse_autonomous_money_when_paused`，暂停的范围里只允许为 `pending_approval` 的操作写预留；旧节点的这种提案整体回滚（它答 500），新节点在暂停时本来就建待批提案，碰不到它。提案持有策略的 `FOR SHARE`、暂停要 `FOR UPDATE`，所以暂停要么在提案之前、要么在它提交之后。赠额（`money.credit`）的范围是账户所在的站点，对象是账户；计入上限的是赠出的面值，策略的币种和站点记账货币不同时按计费的当前参考汇率折算、向上取整到 10⁻⁹。赠额一律交给负责人（「退款与赠额默认人工」），这个类别的自主上限不起作用，只有硬上限拒绝；提案时预留，负责人批准时在批准的事务里按 `credit_grant` 存下的参数（金额、币种、到期时间）重读账户、按管理接口的规则重新检查，以 agent 的名义调用计费的同一个赠额函数（额度批次的 ID 就是运营操作的 ID，一个操作只赠一次），再把预留转为 `committed`（`proof` 记 `credit_batch:<ID>`，确认它的操作就是它自己）；账户不在了、到期时间已过、硬上限被调低到装不下它，批准都以 `rejected` 结束并释放。审批 AI、一键令牌和操作回答里的 `cap` 字段还没有；`cap` 的内容在审批摘要里给负责人看，agent 用 `caps_get` 读上限和用量。
- **不放在计费账本里**：上限是授权控制，不是钱；它要在钱动之前判断，还要跨供应商、退款、赠额统一计数。账本记录的是已经发生的钱，不能代替事前预留；两者通过运营操作编号关联，各自可对账。

#### 售价的累计变动上限

- **包络**：每个站点可以设最低毛利率、单个模型单日单价变动幅度、单日改价笔数和单日改价模型数。服务端按当前成本和定价规则算出新售价、毛利率和变动幅度，不取 agent 写的价格；成本未知时不能自主改价，转人工。
- **累计**：`operations.price_counters` 有模型行 `(站点, 模型, UTC 日)` 和站点行 `(站点, NULL, UTC 日)`：模型行记该模型累计的单价变动绝对值（向上和向下都算）和笔数，站点行记当天改过价的模型数和总笔数；某个模型当天第一次改价时站点行的模型数加一。发布售价和修改定价规则在同一个事务里锁价格行、模型行和站点行，检查包络，写价格、计数器、运营操作和审计；失败全部回滚。回滚一次改价也要再占用一次变动额度，不能用"改过去再改回来"绕过单日幅度。
- **与转账分开**：售价不占转账的金额计数器；两类操作都要求 `operations.money`，但各有各的上限和审批。一个模型一天内改价太多或幅度太大，转人工；人工批准后仍然记入计数器。
- **现在的实现**：agent 能做的售价写只有发布：`price_publish` 把自动发布器为主站某个模型做的、等待确认的提案（`pending` 或 `blocked`）按管理接口确认发布的同一个函数发布出去，永远不低于保本线，也不能豁免保本线；改定价规则还没有。包络每个站点一行（`operations.price_envelopes`：最低毛利率、单个模型单日变动、单日笔数、单日模型数，都是基点或整数），没有包络的站点回 422 `cap_exceeded`。服务端先像管理接口一样刷新提案，再从提案和当前版本算两个数：变动是每个端点的每个有效单价相对**这个端点**现在收的价 `|新 − 旧| ÷ 旧` 的最大值，向上取整到基点；毛利率是每个端点每一项 `(售价 − 成本) ÷ 售价` 的最小值，成本取这个端点自己的成本（共用一份售价时取模型各端点成本的逐项上包络），向下取整到基点，只看有成本的项，和保本线检查同一组项。没有当前版本、某个端点现在没有价、上下文分档的口径变了、一项价格增删或从零变成非零，变动就量不出比例；成本未知就没有毛利率；这两种都转人工。都量得出、毛利率不低于下限、模型当天已用的变动加这一笔不超过单日变动、当天笔数没满、模型当天第一次改价时模型数也没满，就直接发布并计数；否则带包络和已用数建待审批提案，不计数，负责人批准时重新刷新、按批准那一刻的提案重算、发布并计数（量不出比例的变动按 10000 基点计；单日变动的限值最多 10⁸ 基点，比它大的变动按它加一计，当天这个模型不再落进包络）。提案在批准前被发布器换掉、或当前版本变了，批准以 `stale_revision` 结束。计数器 `operations.price_counters` 有站点行（当天笔数和模型数）和模型行（当天累计变动和笔数），只增不减。

### 控制面：只有负责人能改的设置

以下设置只能由负责人在管理后台修改，并且必须通过两步验证；运营接口、运营凭证和对话入口都无法修改：

- 审批策略和各类额度；agent 的限频（只能调低，不能超过代码里的上限）；
- 绝对上限、累计上限、硬上限；
- 巡检周期和阈值；
- 价格包络（最低毛利率、单日变动幅度、单日笔数）；
- 模型来源和审批 AI 的配置；
- 通知的接收人；
- 主站的收款配置（商户号、密钥、收款地址，见[支付](payments.md#收款渠道)）；
- 运营凭证的创建、轮换、吊销、站点范围和权限范围；
- 运营接口和 agent 的启停；紧急停止后的恢复。

控制面的管理接口操作要求 `operations.manage`（凭证、上限、策略、启停）或 `operations.approve`（审批），两者都是敏感权限，只授予负责人；把其中一个授予别人本身就是高风险操作。agent 的凭证不能持有这两个权限。控制面的接口也在管理接口（`api/admin.yaml`），按资源分：`/operations/credentials`（列表、创建；`/{id}/rotate`、`/{id}/revoke`，已实现）、`/operations/cap-policies`（列表，带暂停时间；`/{scope}/{category}` 按读到的版本设置；`/{scope}/{category}/repair` 按资金操作重算计数器并恢复，已实现）、`/operations/price-envelopes`（列表；`/{site_id}` 按读到的版本设置，已实现）、`/operations/agent-limits`（agent 的限频：读现在生效的值和上限，按读到的版本调低，已实现：请求、每分钟和每小时的资金写、发告警四项）、`/operations/agent/stop`（已实现）；`operations.manage` 由迁移给内置的 `admin` 角色，授予这个角色本身是要两步验证的平台授权；审批在 `/operations/approvals`（已实现列表、详情、批准、驳回）。写都要求两步验证、CSRF、`reason` 和 `Idempotency-Key`。

### 风险分级与审批

每类操作对应一条审批策略（策略本身属于上文的控制面）：

| 操作类别 | 例子 | 默认策略 |
|---|---|---|
| 只读 | 查询、统计、读日志 | 直接执行 |
| 日常操作 | 上下架端点、调整权重、映射模型、重跑检测、重启单个节点、发告警、提 Issue | 直接执行，每日汇总 |
| 下架模型 | 把模型从目录下架 | 人工审批 |
| 售价 | 发布售价、修改定价规则 | 价格包络内直接执行，超出人工审批 |
| 资金操作 | 给供应商充值的提案、退款、补额度 | 充值提案在累计上限内直接提出，超出人工；退款和赠额默认人工，见下 |
| 高风险操作 | 修改供应商网址或凭证、移除供应商、发布路由预设、授予管理员角色、删除数据、增减服务器、升级版本 | 默认人工，必须进管理后台并两步验证；负责人可以为指定类别开启第二个 AI 或 AI 加人工确认，凭证/权限/删除/部署类仍必须人工 |
| 控制面 | 审批策略、上限、运营凭证、模型来源、通知接收人、启停 | 只有负责人，管理后台加两步验证 |

不在运营接口里的高风险操作（修改供应商网址或凭证、移除供应商、授予管理员、删除数据、增减服务器、升级）只能由负责人在管理后台或部署组件执行；运营接口不提供入口，agent 只能上报建议。供应商凭证明文不进 agent 的输入，也不进运营接口的请求或响应。

审批方式有五种可选：直接执行；额度内直接执行；第二个 AI 审批；人工审批；AI 审批加人工确认。服务端按"策略、目标模块自己的规则、硬上限"三者取最严的一档，不由 agent 判断。

- **审批接口**：审批的读写在管理接口，不在运营契约：`GET /api/admin/v1/operations/approvals`、`GET /api/admin/v1/operations/approvals/{id}`、`POST /api/admin/v1/operations/approvals/{id}/approve`、`POST /api/admin/v1/operations/approvals/{id}/reject`、`POST /api/admin/v1/operations/approvals/{id}/withdraw`。读要求 `operations.approve` 和两步验证；写还要求 CSRF、`reason` 和 `Idempotency-Key`。一键令牌的批准入口是 `POST .../approve?token=...`，GET 只渲染确认页。agent 的运营契约只有 `GET /approvals`、`GET /approvals/{id}`、`POST /approvals/{id}/withdraw`，没有批准和驳回。现在实现了管理接口的列表、详情、批准和驳回，以及运营契约的 `GET /approvals/{id}`（回答它所等的运营操作）和撤回；负责人在管理后台的「运营审批」页决定：列表按状态筛选、从新到旧，对象先写名字（账户名和所有者邮箱、供应商名、模型的公开名字），待决定的写还剩几分钟到期；每个审批一页，先用一句一条说明为什么要人决定（超过了哪个自主上限、包络管不住什么、范围已暂停，或这一类总要人；赠额总要人，它的自主上限不约束什么，所以只写这一条）：原因由服务端在提案时判定、随审批返回（`reasons`，运营契约里 agent 读到的审批也带），页面只把每个代码写成一句；再列格式化的请求内容（金额按币种、售价逐项列现在、提议和成本）、提出时的上限用量或售价包络（超出或查不了的行标出），agent 的理由单独作为不可信的文字显示，原始数据收在默认关闭的「原始数据」里；服务端说还能决定的（`decidable`：待决定、按数据库时钟未到期，和批准时的判断同一个时钟）才有批准和驳回，结果按回答说明（执行了、批准后目标已变没有执行、提出方的凭证已不在而作废）。为此服务端在提案时的摘要里多存了赠额账户所有者的邮箱，以及售价的模型名字（`slug`、公开的 `name`）、站点币种（`currency`）和每个计费项现在、提议和成本的基础单价（`current`、`proposed`、`cost`，只存基础单价，不存上下文和服务档位，也不存各端点自己的价，摘要不会超过 8 KiB），以及这些基础单价是否就是两边收的全部价格（`prices_complete`：两边都不按端点定价、也没有上下文或服务档位才是 true）；不全时页面不说「没列出的价格不变」，提示端点或档位的价格要另外核对，因为端点的价可以在模型上包络不变时变化；旧的提案没有这些，页面只显示 ID 和包络。管理接口的撤回、一键令牌和审批 AI 尚未实现。批准前先持有提出方的凭证，凭证已吊销、停止或过期时什么都不执行，审批和运营操作记 `canceled`（滚动发布期间旧节点的吊销和停止不作废提案，靠这一步兜住）。批准在同一个事务里执行目标改动：成功是 `succeeded`；目标在提案后变了（目标模块拒绝，如 `stale_revision`），改动回滚到保存点，运营操作以 `rejected` 和那个错误码结束，批准本身照样记下。
- **目标模块的规则**：退款、赠额等"必须第二人"的规则放在目标模块的函数和事务里，管理接口和运营接口调用同一个函数；不能只在管理接口的 HTTP 守卫里检查，否则运营接口会绕过第二人。
- **额度防拆单**：额度不只看单笔，还按类别设每天、每周的累计上限，以及笔数上限和按对象的上限（比如每个用户、每个供应商）。定价规则的修改限制在负责人设定的利润率范围和单日变动幅度之内。拆成多笔、换一个对象、跨日边界都受对应的计数器约束。
- **硬上限**：不论选哪种审批方式，超过硬上限一律拒绝；负责人只能在控制面调高上限后重试。人工审批不能越过硬上限，AI 审批也不能。
- **退款与赠额默认人工**：支付模块现在要求另一个管理员批准退款，计费的人工调账也有第二人规则；运营上限是加在它们之上的一层，不替代第二人。这两类也不能用第二个 AI 审批代替第二人；要放开只能先改目标模块的规则并单独评审。额度内的 agent 直接退款/赠额要在资金上限服务接入并评审后，由负责人单独决定是否开放；本设计默认不开放。
- **第二个 AI 审批**：
  - 由核心节点的服务端直接调用，使用与提出方不同厂商的模型；提出方的厂商由运营凭证上的 `proposer_vendors` 配置，不由 agent 自己报；模型代理使用的厂商必须都在这个列表里，创建或修改凭证时校验；审批 AI 要和列表里的每个厂商都不同，找不到不同厂商就转人工；
  - 审批 AI 看到的影响范围（涉及多少钱、多少用户、哪些端点、上限前后）由服务端从数据库算出，不用提出方自己写的说法；提出方写的理由作为不可信的数据给它参考；
  - 审批 AI 只能批准自己类别 `ai_amount` 以内的金额；非金额类的高风险按类别的 `ai_enabled` 开关，不受 `ai_amount` 限制。高风险默认不允许 AI，负责人可以在控制面按类别开启，但控制面、目标模块要求第二人的操作、凭证/权限/删除/部署和超过硬上限的金额一律不能由 AI 批；
  - 审批 AI 不可用、超时或回答不明确时，自动转为人工审批，不会因此放行；审批 AI 的模型、版本、提示版本和回答哈希记在审批记录里；
  - 审批 AI 驳回后这次运营操作结束；agent 不能马上用同一个内容重复提交，冷却期内只能通知负责人。负责人可以在管理后台另行处理。
- **人工审批**：
  - 审批内容由服务端根据操作本身生成，不用 agent 写的文字，并附上管理后台的链接；金额、对象、上限前后、影响范围和目标模块的规则都在里面；
  - 资金操作可以在消息里一键批准：按钮带一次性令牌，绑定这个操作的指纹、审批编号、负责人和到期时间，限时（默认 10 分钟）、只能用一次；令牌用核心节点密钥环里的专用用途签名，密钥不在运维节点上；GET 只渲染确认页，POST 才消费令牌，避免链接预览误批；
  - 高风险操作必须进入管理后台，登录并通过两步验证后批准，没有一键令牌；
  - 批准的凭证由核心节点签发和校验；等待审批超时即视为拒绝，释放预留并记审计；
  - 在对话入口里说"同意"不算批准，也不能修改任何设置；agent 不能调用批准工具，不能批准自己提出的操作；
  - 审批人不能是提出方；负责人可以撤回自己的待审批提案，agent 也可以撤回自己发起的提案，撤回都记审计。
- **审批记录**：`operations.approvals` 保存运营操作编号、要求档位、状态（待批/批准/驳回/过期/作废）、服务端生成的影响摘要、请求时间、到期时间、决定者（`<种类>:<ID>`）和理由；AI 模型与回答哈希、一次性令牌哈希和消费时间、策略版本随审批 AI、一键令牌和审批策略加入。指纹就是运营操作本身：应用角色改不了操作的工具、目标和参数（参数里有目标的 `rev`，以后还有金额、币种和策略版本），所以批准的就是执行的；目标变了由目标模块在执行时按 `rev` 拒绝，操作以 `rejected` 结束，要重新提案、重新审批。待批的审批在数据库时钟的 30 分钟后到期，且不晚于当天 UTC 结束；到期的不能再批准，不管清扫任务到没到（锁住后按数据库当前时刻判断，等锁的时间也算），清扫每分钟一次，把它和它的运营操作记为 `expired`。
- **策略变化**：待审批的提案带着发起时的策略版本。执行时重新读策略：变严或硬上限变低就拒绝并释放；变松不影响已经发出的提案，但仍按新策略重算硬上限。这样不能在策略收紧前抢跑，也不会因为无关的放宽重复打扰负责人。
- **由代码判断**：一个操作是否在额度内、需要哪种审批，由服务端代码按策略判定，不由 AI 判断。

### 方案对比

运营接口有三条路可走。选 A。

| | A：独立契约、独立监听、运维节点 MCP 桥（选中） | B：复用管理接口，给 agent 一个平台服务用户或长期会话 | C：MCP 直接做在核心里，不另做 HTTP 接口 |
|---|---|---|---|
| 权限面 | 只暴露运营需要的操作，控制面不在里面 | 管理接口的 131 个操作全部暴露，只能靠逐个处理器过滤 | 工具面就是全部接口，没有独立的 HTTP 契约 |
| 认证 | 独立运营凭证 + `ops` 客户端证书，只在运营监听有效 | 人的会话/服务用户，要模拟 MFA、CSRF、Origin 和管理域名；令牌能做的事和会话一样多 | 进程内身份，审计和吊销要另做 |
| 审批与上限 | `operations` 中间层统一执行，所有写操作走同一套 | 要改每个管理处理器；上限、审批、幂等和审计容易漏 | 能做，但和核心的请求路径耦合，测试要起 MCP 客户端 |
| MCP 映射 | 契约生成工具，HTTP 和 MCP 不漂移 | 手写或反射管理操作，工具名和权限不稳定 | MCP 就是唯一接口，没有 OpenAPI 给人和其它客户端 |
| 故障隔离 | 运营节点只跑桥，不碰数据库；核心数据面不变 | agent 会话进了管理面，管理面和运营面一起暴露 | MCP 代码在核心里，桥和核心一起升级、一起故障 |
| 滚动发布 | 新监听、新契约，旧节点不受影响，能力门控后启用 | 改管理接口和守卫，新旧节点行为不一致 | 改核心启动和路由，回滚面更大 |
| 代价 | 多一份契约、一个桥和一套凭证；代码量比复用管理接口多 | 看似省事，实际要在 131 个处理器上补风险分级，且无法把控制面挡在外面 | 少一个 HTTP 跳，但少了契约、测试面和独立升级 |

- **不选 B**：管理接口是浏览器面，认证是人的会话加两步验证、CSRF 和 Origin；给 agent 一个长期会话等于把人的全部权限复制给一个可能被提示注入的模型。平台服务用户加角色也解决不了控制面：角色会连审批策略、凭证、收款配置一起授予，逐个处理器过滤既容易漏，也把运营规则散在 131 个地方。
- **不选 C**：MCP 是给模型用的协议，不是给人和运维脚本用的稳定契约；只有 MCP 时，测试要起 MCP 客户端，负责人临时用 curl 或别的框架也接不进来，运营规则还和核心的启动、路由、发布绑在一起。A 让 HTTP 契约成为唯一事实来源，MCP 只是一个生成出来的适配器。

### 紧急停止

- 负责人可以一键停止 agent：在一个事务里吊销所有运营凭证并置全局停止开关，运营监听对之后的所有请求答 401；Hermes 的定时任务、对话入口和 MCP 桥同时停止。
- 所有待审批的提案立即作废，释放预留并记审计；状态为 `approved` 但还没开始的操作取消并释放；状态为 `executing` 的外部调用不强行取消——它可能已经在供应商或支付渠道执行，取消只会让结果更不清楚——让它按自己的期限结束并记录结果，无法判断的标 `unknown` 等人工对账。
- 只有负责人通过两步验证后才能恢复；恢复要重新创建凭证，旧凭证不会复活，旧的待审批提案不会恢复。
- 停止和恢复本身记审计，操作者是负责人。

### 审计

- **每次工具调用都有操作记录**：`operations.operation_log` 记记录 ID、凭证 ID、agent 运行 ID、工具名、站点、目标、风险类别、策略版本、幂等键（写操作）、规范化输入（脱敏，最多 8 KiB）、理由、状态、运营操作编号和审批编号（写操作）、预留与计入上限的金额、结果摘要（最多 8 KiB）、错误码、开始和结束时间。现在实现的是读和日常写用到的列：记录 ID、凭证 ID、运行 ID、工具名（`x-mcp-name`）、理由（读取自查询参数，写取自请求体）、输入（路径和查询参数，写还有请求体，都不含理由；按规范 JSON 的字节数计，超过 8 KiB 只记大小；列是 `json` 不是 `jsonb`，数据库量的就是代码写进去的那些字节）、HTTP 状态、错误码、请求 ID、开始和结束时间，写操作还有运营操作编号；其余列随资金写加。凭证认出之后的每个请求都记，守卫拒绝的（权限、范围、参数）也记；答案先缓存在内存里，记录写进数据库后才发出，写不进就答 503、不发答案。令牌不认识或超限频的请求没有凭证可记，不记。读操作也记，但不写审计日志；它是 agent 可回放的调用记录，不是"谁改了钱"的凭证。
- **每个改状态的操作都写平台审计日志**：在改动自己的事务里调用平台的审计写入，和运营操作、计数器、目标改动同成同败；写不进就整个改动失败。运营操作和审批请求的操作者是 `operations_agent:<凭证 ID>`（新增的操作者种类）；批准/驳回的操作者是负责人（`user`）或审批 AI（`system:operations.ai_approval`），过期是 `system:operations.approval_expiry`。动作名是 `operation.execute`、`operation.succeed`、`operation.fail`、`operation.reject`、`operation.cancel`、`approval.request`、`approval.approve`、`approval.reject`、`approval.expire`（模块列已经是 `operations`，动作名保持两段）。现在写入的是 `approval.request`、`approval.approve`、`approval.reject`、`approval.expire`、`operation.succeed`、`operation.reject`（批准后目标已变）和 `operation.cancel`（撤回、吊销和停止），资金操作另有 `reservation.commit`（agent 确认到账，或负责人批准的赠额赠出时）和 `reservation.release`（提案结束或过了日，清扫的操作者是 `system:operations.reservation_expiry`），控制面改上限记 `cap_policy.set`（改前改后的全部上限和版本），对账暂停记 `cap_policy.pause`（操作者 `system:operations.cap_reconcile`），负责人修复记 `cap_counters.repair`（每行计数器改前改后），改售价包络记 `price_envelope.set`（改前改后），审计链发现不一致记 `audit_chain.halt`（操作者 `system:operations.audit_chain`）；`operation.execute` 和 `operation.fail` 随外部调用加入。目标模块自己的审计（如 `model.retire`、发布售价的 `price.publish`、赠额的 `credit.add`）以 agent 的名义写在同一个事务里。审计的 `detail` 放运营操作编号、审批编号、金额与币种、上限前后、目标模块的行 ID、改前改后的价格/状态/权重；不放密钥、凭证明文、对话内容、请求正文或供应商页面原文。理由字段只放 agent 写的理由，视为不可信文本。
- **谁能读**：agent 通过运营接口读自己的操作记录和审批；读全平台审计需要 `audit.view`，由负责人决定给不给。负责人和管理员用管理后台的审计页检索，沿用平台的 `audit.List`/`audit.Get` 和范围规则。审计条目属于平台数据，租户范围读不到。agent 读审计用 `GET /audit`（`audit_list`）和 `GET /audit/{entry_id}`（`audit_get`），处理器转给管理后台的同一个处理器，所以筛选和答案与审计页一样：按操作者、动作、模块、目标、站点、账户和请求 ID 精确筛，从新到旧，默认读最近 24 小时、最长 31 天，答案里的 `since`、`until` 是实际读的窗口。两者都要 `audit.view` 和平台范围：只有站点范围的凭证读审计和读一条都答 404，没有 `audit.view` 答 403。条目的理由和 `detail` 里有用户、供应商、管理员和 agent 写的文字，契约把它们写明为数据、不是指令（见「防止被外部内容操纵」）。每天的摘要用 `GET /audit/digests`（`audit_digests`）读，同样要 `audit.view` 和平台范围，从新到旧，游标是上一页最后一天的日期；管理后台没有摘要页，负责人经告警渠道收到摘要的合计。
- **防篡改**：`operations.audit_chain` 按 `(at, id)` 顺序给每条已提交的审计条目接链，一行的内容是序号、审计条目 ID、前一条的哈希和本条哈希（SHA-256，覆盖规范化后的审计字段）。接链由一个带会话锁的 worker 做，不在审计写入的事务里；worker 只处理 `at` 早于当前时间至少 60 秒的条目，给还在提交中的事务留出窗口；如果仍看到比链头更早的新条目，停止接链并告警，不把它插到链中间。worker 落后超过 60 秒告警，链断或哈希不匹配立即告警并停掉自动处理。链和条目定期复制到运维节点以外的对象存储，对象存储开版本控制和对象锁，写凭证只允许写新对象、不能覆盖或删除；对象存储不可用时链照常本地推进，复制落后告警。每天给负责人发摘要：按类别的操作数、资金操作与上限、审批、被拒绝的尝试、链的进度和复制状态。
- **防篡改现在的实现**：接链是 `archive` 队列上每分钟一轮的任务 `operations.audit_chain`，在事务级咨询锁下进行，每个事务最多接 500 条。一条链（`seq` 从 1 起）的哈希是 SHA-256(前一条的哈希 ‖ 条目的编码)，第一条之前是 32 个零字节；条目的编码是一个 RFC 8785 的 JSON 数组：`"axiom.audit.v1"`、条目 ID、`at`（UTC，精确到微秒，如 `2026-11-08T01:02:03.456789Z`）、操作者种类和 ID、请求 ID、动作、模块、目标种类和 ID、站点、账户（没有的是 `null`）、理由（没有的是空字符串）和 PostgreSQL 打印的 `detail` 文本，所以平台之外拿审计日志和链的导出就能重算（`TestLinkHash` 用另行计算的值固定了它）。表上的触发器只收接在链头之后的一条（`seq` 连续、`prev_hash` 等于前一条的哈希），应用角色不能改、不能删。哪些条目能接：除了 60 秒，还要早于本数据库里每个还开着的事务的开始时刻（`pg_stat_activity` 的 `xact_start`，应用的会话是同一个角色，彼此看得见）——条目的 `at` 就是它的事务开始的时刻，比所有开着的事务都早的条目不可能还没提交，所以长事务提交的条目不会被误判为「比链头更早」，只是让链等它，等得久了就是落后告警；60 秒只用来兜住刚开始还没登记开始时刻的事务和看不见的其他角色。每一轮先核对链头往回 1000 条：每条接在前一条之后，审计日志按 `(at, id)` 排在这个位置的正是它的条目，条目重算的哈希和链上的一致；每天从第一条起把整条链这样核对一遍：同一种任务带 `whole` 也每分钟跑一次，上一轮核对结束且开始已满一天就开新的一轮（目标是当时的链头），否则接着核对进行中的那一轮，每次最多 20 个事务、每个事务 500 条，核对到的位置和这一批在同一个事务里存进 `operations.audit_chain_checks`，所以一次被期限或故障打断的核对由下一次接着做，不从头再来；一轮开始满一天还没核对完，发 warning 告警 `operations.audit_chain_check_overdue`，核对完就恢复。核对每条时还比较链上记的时刻和条目的时刻：接链按链头的时刻往后读条目，链头的时刻被单独改到将来会让接链悄悄停下，所以它和条目不一致也算链本身断开。不一致分四种：链头之前有没接上的条目（`late`）、链上的条目不见了或换了位置（`missing`）、条目被改（`mismatch`）、链本身断开或链上的时刻被改（`broken`）；发现时在同一个事务里写进 `operations.audit_chain_faults`（应用不能改、不能删），以 `system:operations.audit_chain` 记审计 `audit_chain.halt`（种类、序号、条目 ID），发 critical 告警 `operations.audit_chain_fault`，此后接链和核对都不再进行，告警由负责人在告警页关闭；恢复接链的做法待定（见「待定问题」）。每一轮结束时，还没接的最早一条比开始可接的时刻晚了 60 秒以上（即早于现在两分钟），就发 warning 告警 `operations.audit_chain_lag`（`behind_seconds`），赶上了就恢复。库里的链挡得住手工改一条审计或漏记，挡不住能同时改审计日志和链的数据库管理员，那要靠下面的异地副本。
- **异地复制和摘要现在的实现**：副本桶由 `AXIOM_AUDIT_REPLICA_*` 六个变量配置（和程序自己的 `AXIOM_OBJECTSTORE_*` 同样的规则，设了一个就要设全，否则不启动），不设就不复制，摘要里报 `unconfigured`。桶在部署之外，开版本控制和对象锁；凭证能写新对象、读对象、列举桶，不能覆盖或删除：复制在写前要读回同一个键（见下），而没有列举权限时 S3 对不存在的键答 403 而不是 404，这样的 403 当错误报出、不当作「没有」。任务 `operations.audit_replica` 每分钟一轮，把上次复制之后已接上的链按每个对象最多 500 条写进 `audit-chain/v1/<首序号>-<末序号>.jsonl`（序号各 20 位，键按链的顺序排列）；每行是一个规范 JSON 对象：`seq`、`prev_hash`、`hash`（十六进制）和 `entry`——正是哈希覆盖的那个字段数组，所以只凭桶里的对象，按上文的公式就能从第一条重算整条链。只复制和审计日志核对通过的链（和接链的核对同一个函数），不通过的留给接链的核对记故障。复制的位置存在 `operations.audit_replica`；对象写成功后才推进，推进前没存下就由下一轮重写同样的字节。写之前先读这个键：已有且字节相同就跳过；字节不同说明库里的链和已复制的不一致，不覆盖，发 critical 告警 `operations.audit_replica_conflict`（键是对象键），复制停在那里；没有才写，带 `If-None-Match: *`，让要求这个条件的桶策略能拒绝覆盖（SeaweedFS 3.80 不理这个条件，所以先读）。还没复制的最早一条接上已超过 10 分钟，发 warning 告警 `operations.audit_replica_lag`（`behind_links`、`behind_seconds`），赶上了就恢复；这一步用自己的 10 秒期限，复制被任务的期限打断时也照样判断落后。桶不可用时链照常在本库推进。每天的摘要由任务 `operations.audit_digest` 每分钟看一次：从上一份摘要的后一天起（还没有摘要时从昨天起）往后，一天结束、且这一天结束前开始的事务都已结束（和接链同一条边界：60 秒之前，且早于本库每个还开着的事务的开始时刻），才做这一天，每次最多补 7 天，所以停机跨了几天，恢复后按日期顺序补齐。一天的内容在一个可重复读的快照里读出：那一天的运营操作（按工具和现在的状态）、资金上限（每条策略那一天的预留、已用、笔数和日上限、硬日上限、日笔数上限）、审批（按现在的状态）、被拒绝的尝试（运营接口答 4xx 的调用，按错误码），以及做摘要时的链头、故障数、整条核对最后完成的时刻和复制的位置与状态（`unconfigured`、`behind`、`current`）；存进 `operations.audit_digests`（一天一行，内容应用改不了、删不掉），同一个事务发 info 告警 `operations.audit_digest`，键是那一天的日期，字段是各项合计、链头、故障数和复制状态，所以多个节点也只做一份、只发一次，每一天的通知是自己的告警事件，有自己的回执和重试。任务从不恢复这个事件：告警模块按通知处理这一种类，在每条匹配的规则都告知过之后自己关闭，关闭时不发恢复通知；没有规则时第一次评估就关闭，之后才加的规则不补发以前的摘要。负责人在告警配置里给这个种类加一条最低 info 的规则和渠道（不用设重复间隔），就每天收到一份；完整内容用 `audit_digests` 读。
- **保留**：审计和操作记录的保留期待定，由负责人决定；与钱有关的条目至少和账本保留一样久。到期删除只由专门的后台角色执行，应用角色不能删；删除前先确认链和异地副本完整。

### 失败、重试与回滚

| 情况 | 运营操作状态 | 上限 | 处理 |
|---|---|---|---|
| 校验、权限、站点范围失败 | 不建运营操作，只写操作记录 | 不动 | 返回稳定错误码；同一请求重试不会产生副作用 |
| 超过硬上限 | 不建 | 不动 | 422 `cap_exceeded`，带上限、窗口、已用和本次金额；负责人调高上限后重试 |
| 需要审批 | `pending_approval` | 已预留 | 202；通知负责人；`approval_wait` 或 `approval_get` |
| 审批驳回 | `rejected` | 释放 | 记审计；通知 agent；同一内容在冷却期内不能重复提交 |
| 审批超时 | `expired` | 释放 | 记审计；通知 agent；同一内容在冷却期内不能重复提交 |
| 提案人/负责人撤回 | `canceled` | 释放 | 记审计；通知 agent；同一内容可重新提交 |
| 已批准但未开始，跨窗口或超执行期限 | `expired` | 释放 | 在 `approved → executing` 的事务里检查；新窗口重新提案、重新审批，不复用旧批准 |
| 数据库在提交前失败 | 回滚 | 不动 | 用同一个幂等键重试；不会留下运营操作或预留 |
| 本地改动提交后崩溃 | `succeeded` | 已计入 | 目标改动、运营操作和审计同事务；重发返回结果，不会重复执行 |
| 外部调用标记 `executing` 后崩溃，发没发不清楚 | `executing`/`unknown` | 保持预留 | 幂等的按同一个外部幂等键查询或重发；不幂等的告警，人工按渠道证据对账，不自动重发 |
| 外部调用确定失败 | `failed` | 释放 | 记录渠道错误；重试新建操作，不复用旧批准或旧预留 |
| 外部调用超时/断连 | `unknown` | 保持预留 | 不自动重试不幂等的调用；告警，人工按渠道证据对账；确认失败才释放 |
| 外部调用确认成功、记录失败 | `executing` | 保持预留 | 运营操作编号作为外部幂等键；重试只更新记录，不重复调用；对账任务收敛 |
| 审批后目标变了（`rev` 或指纹不符） | `rejected` | 释放 | 409 `stale_revision`；重新准备、重新审批，不拿旧批准执行新对象 |
| 策略收紧或硬上限降低 | `rejected` | 释放 | 执行前重读策略；变松不影响已发出的提案 |
| 凭证被吊销或紧急停止 | 新请求 401；`pending_approval`/`approved` 改 `canceled` | 释放待批和未开始的 | `executing` 让它结束；未知的按对账处理 |
| 回滚一次已完成的配置改动 | 原操作 `reverted`；新操作 `succeeded` | 按新操作重新检查 | 不删除、不改写原操作；新操作链接原操作编号，受同样的审批和上限；价格回滚再占一次变动额度 |

- **幂等**：写操作必须有 `Idempotency-Key`。运营操作表对 `(凭证, 键)` 唯一，第一次的运营操作编号和初始响应同事务保存；重发返回同一个编号和当前状态，不执行第二次。同一个键换内容、换操作或换凭证返回 409 `idempotency_key_reused`。审批也带幂等键；一次性令牌只能用一次，重放批准返回第一次的结果。
- **没有通用回滚**：已经发生的钱只能由目标模块的退款、冲正或撤销路径补偿，运营接口不改原金额、不删记录。配置类改动用 `operation_revert` 新建一个补偿操作，带上原操作编号和改前值；它按新操作重新走权限、审批和上限，原操作永久保留。成功的资金操作即使后来被退款或撤销，也不自动退回上限；要恢复额度只能由负责人调高上限。
- **部分写入**：一个运营操作只作用于一个对象；本地改动、计数器、运营操作和审计在一个事务里，不存在只写一半。跨对象的批量操作不提供；需要批量时由负责人在管理后台做，或者 agent 逐个对象调用，每个对象各自审批、各自计数。外部调用不在事务里；它和本地记录之间用运营操作编号、幂等键和对账任务收敛。
- **取消与期限**：agent 断开不会取消已经提交的本地改动或已经发出的外部调用；请求上下文取消只停止等待，不停止已经开始的记账。未开始的 `approved` 操作可以取消（`canceled`）；到窗口结束或执行期限会自动 `expired`，不是只有人工取消才过期；`executing` 的不能取消，只能等结果或对账，跨窗口的未知结果保留原预留。

### 上线与兼容

- **能力门控**：运营监听只在支持它的核心节点上打开；节点的能力写进心跳，负责人看到所有核心都支持后，才创建运营凭证并启动 agent。滚动发布期间旧核心没有这个监听，运维节点的 MCP 桥连不上就拒绝启动，不会退回管理接口或公网接口。管理后台的控制面同样按能力门控：旧核心不提供新路由，页面在全部核心支持后才显示，滚动期间负责人不会点到一半失败。审批页不另做门控，理由见「决策与理由」。
- **分片落地**：1）契约、运营凭证、读接口、操作记录；2）审批引擎、管理后台审批页、通知；3）资金上限、计数器、价格包络、目标模块接入；4）MCP 桥、工具白名单、沙箱放行；5）审计链、异地复制、对账。每一片都能单独构建、单独发布，后一片依赖前一片。
- **资金接入顺序**：支付和计费的退款/赠额在第三片接入运营上限之前保持现在的第二人规则；接入后两者同时生效，取更严的一档。运营接口的退款/赠额工具在接入前不生成，避免出现"有入口、没上限"。
- **契约兼容**：v1 内只加操作、加可选字段、加错误码；删除操作、改含义或改必填字段升 v2。MCP 工具名和输出字段同样只增不改；运行手册按工具名引用，改名要一起改。运营操作和上限表是新增表，旧节点不写也不读；滚动期间旧节点不提供运营接口，也不影响调用路径。
- **失败关闭**：没有运营凭证、没有上限策略、没有能力标记、数据库或核心不可用时，运营接口一律拒绝资金写；读可以降级，但不会放行写。`operations` 模块或 MCP 桥故障时 agent 停止，固定流程和告警照常运行。

### 运营看板

管理后台的首页是运营看板：所选时段内本站的调用量、错误数、收入、供应商成本、现金净流入、付费用户、月流水、毛利率和留存率，以及调用最多的账户和模型。负责人可以给除现金和两个排名外的八项设月度业务目标，看板把目标和实际值放在一起（见下文「业务目标」）。每个数字都能下钻到已有的调用记录或订单页，地址里带着同一个窗口和对应的筛选条件；调用链接还带着本站的 `site_id`，现金链接打开订单页的账本流水视图（`cash=1`），不新建页面。付费用户、月流水和留存打开订单页的付费充值批次视图（`paid=batches`），按充值批次的 `created_at` 列出记录：前两者用看板窗口，留存从上一个 UTC 月的第一天开始，才能看到分母那一批账户的付款；订单的创建时间不是这个时间轴，因此不能按订单 `created_at` 筛。毛利率打开同一个站点和窗口的调用记录。

时段可选最近 24 小时、7 天或 30 天，默认 24 小时；窗口在打开页面时算定，切换时段时沿用同一个锚点，所以新的数字和它的链接仍指向同一时段。聚合只读报表用的表和索引（`billing.reservations`、`billing.transactions` 与 `billing.entries`、`billing.credit_batches`、`observability.call_log`），范围由索引限定，不在打开页面时扫全表。

口径如下。收入、月流水和现金是三件不同的事，成本是另一件，不能互相替代：

- **调用量与错误数**：`observability.call_log` 里在窗口内开始的调用条数；错误是其中 `error_kind` 非空的条数。调用开始的时刻是请求到达、准入之前的那一个：网关把同一个值写进 `billing.reservations.created_at` 和 `call_log.at`，所以调用和它的钱不会因为准入耗时分别落进窗口的两边。升级前写入的预留仍保留它们当时的 `created_at`（准入之后），这是历史数据，不追改；同一个窗口里它们与调用日志可能相差一次准入的耗时。
- **收入**：窗口内已结算调用（`state` 为 `settled` 或 `cleanup_settled`）的 `charged` 之和，即用户实付，按站点的记账货币。`charged` 是实收：余额底线封顶时由平台承担的部分和免单的部分都不在收入里（见[计费](billing.md)）。时间轴是调用的开始时间（`created_at`，与调用日志的 `at` 同一个值）；更正（例如供应商事后校正用量）改写同一行，仍落在这次调用的窗口里，不会在更正发生的窗口里重复计一次。窗口结束前还没结算的调用在结算后回到它自己的开始时间，不算进当前窗口。
- **供应商成本**：同一批调用的 `charged - profit` 之和，按站点的记账货币。`profit` 是结算时算出的利润，`profit = charged - 成本`，所以这个差就是供应商成本（含汇率换算），不是用收入减利润去估。**成本未知**（`profit IS NULL`，例如供应商的成本还没到或无法换算）的调用单独计入 `unknown_cost_calls`，它们的成本**不按 0 计入** `cost`（[#319](https://github.com/TYCT-tyct/Axiom/issues/319)）；未知成本不为 0 时，收入减成本不能当作利润。
- **现金净流入**：`billing.transactions` 里 `kind` 为 `credit` 或 `refund` 的交易在 `billing.entries` 的 `cash` 科目上的合计，按**支付币种**分别列出（与站点记账货币不同的，就是用户实际付款的币种；账本没写币种的按站点记账货币）。它只算真正收到和退出去的钱：**调用记录里的费用不是现金，收入也不是现金**。充值进来的是预付款，调用时才转为收入；退款是现金流出，不冲减调用收入。时间轴是交易发生的时间，和调用的时间轴不同，所以同一个窗口里现金和收入不必对得上。现金数字下钻到订单页的现金流水：按交易时间列出同一窗口的 `cash` 分录，带账户、金额、订单或线下渠道；较早订单的退款和线下充值都在里面，不受订单 `created_at` 的限制。
- **付费用户与月流水**：都读 `billing.credit_batches` 里 `source = 'paid'` 的批次，时间轴是批次的 `created_at`。付费用户是这些批次涉及的不同 `account_id` 数；同一个账户在窗口内充值多次只算一个。月流水是这些批次的 `amount` 之和，即充值授予的额度，按批次锁定汇率折算成站点的记账货币。赠送额度不是付费；退款和拒付不冲减这两个数——它们改变的是现金和剩余额度，月流水回答的是窗口内付费充值带来了多少额度。**月流水不是调用收入**：充值进来的是预付款，调用结算时才按实际用量转为收入。
- **毛利率**：`(收入 - 供应商成本) / 收入`，以基点表示（1 基点 = 0.01%），按代数值四舍五入到基点；成本高于收入时为负。只有窗口收入大于 0 且 `unknown_cost_calls = 0` 时才有实际值：成本合计不包含成本未知的调用，把未知当 0 会算出一个偏高的毛利率，所以那种窗口不显示毛利率，也不显示它的差距。
- **留存率**：按付费账户做月环比留存。窗口结束所在的 UTC 自然月是当月；分母是上一个 UTC 自然月内至少有一次付费充值的不同账户，分子是其中从当月第一天到窗口结束（`until`，不含）至少又有一次付费充值的账户。留存率 = 分子 ÷ 分母，以基点表示，四舍五入。窗口结束在月首时（`until` 正好是某月第一天），当月是上一个月：用 `until - 1ns` 所在的月判断。当月还没结束时这是月初至今的留存，不是整月预测；分母为 0 时没有实际值。这个口径只用现有的充值批次，不需要新增埋点，衡量的是付费账户是否继续付费，不是注册后的首次付费。
- **调用最多的账户和模型**：窗口内调用条数最多的前 10 个，附各自的错误数；按调用量排序，不是按消费排序。
- **调用日志的覆盖边界**：调用记录按月归档，归档确认后整个月从 PostgreSQL 删除。是否完整按请求窗口判断：`CallCoverage` 记下还在的月分区，窗口覆盖的每个整月都必须还在，缺任何一个月就返回 `incomplete=true`。不能只看最老分区——保留任务记下某个月归档失败后仍会继续处理更晚的月份（[`retention.go`](../../internal/observability/retention.go)），可能出现 10 月还在、11 月已删、12 月还在的空洞，最老分区还在但窗口仍不完整。`available_since` 是最老的剩余月分区，它之前的调用确定已归档；一个分区都不剩时省略它。看板据此返回 `calls_incomplete`，页面明确显示调用量和两个排名不完整，不把已归档的调用当成零；收入、成本和现金来自账本与预留，付费用户、月流水和留存来自充值批次，都不受调用日志归档影响，仍覆盖整个窗口。下钻的调用列表用同一规则：`incomplete` 与 `available_since` 跟着列表返回，窗口触到归档月时页面说明列表不完整，空结果不等于这个窗口没有调用。
- **金额的宽度**：汇总在 PostgreSQL 里用 `numeric` 计算，以十进制文本返回，不经过 `int64` 或浏览器的 JSON number；因此一个窗口的收入、成本、月流水或现金合计可以超过 64 位（单笔写入账本的金额仍须放得下 64 位）。前端只格式化这个文本，不把它转成浮点数。

### 业务目标

负责人给运营看板设业务目标，看板把目标值和实际数字放在一起对照。目标是运营数据，不写进文档，也不放进配置：负责人在管理后台按站点设置、随时调整，每次改动记审计（[产品需求](../product.md#运营)只要求有这件事）。

- **哪些指标有目标**：调用量、错误数、收入、供应商成本、付费用户、月流水、毛利率、留存率八项。调用量、收入、付费用户、月流水、毛利率和留存率是下限（至少达到），错误数和供应商成本是上限（最多允许）；看板不替负责人判断好坏，只显示实际比目标多或少，方向由指标本身决定。毛利率按代数值比较，实际为负时也在目标之下。现金不设目标：它按支付币种分别列，折成一个数会丢掉汇率和实际到账的信息；调用最多的账户和模型是排名，不是可加总的业务量。两者都不设。
- **付费用户**：窗口内 `billing.credit_batches` 中 `source = 'paid'` 的不同 `account_id` 数。充值批次的时间是 `created_at`；同一个账户多次充值只算一个。赠送额度不是付费，调用过但没付费的账户也不是。
- **月流水**：窗口内同一批付费充值批次的 `amount` 之和，即充值授予的额度，按批次锁定汇率折算成站点的记账货币。它不是调用收入：充值进来的是预付款，调用结算时才按实际用量转为收入。退款和拒付不冲减月流水，它们改变现金和剩余额度；这个指标回答窗口内付费充值带来了多少额度。
- **毛利率**：`(收入 - 供应商成本) / 收入`，以基点表示（1 基点 = 0.01%），按代数值四舍五入到基点，成本高于收入时为负。只有窗口收入大于 0 且 `unknown_cost_calls = 0` 时才有实际值；成本合计不含成本未知的调用，把未知当作 0 会算出偏高的毛利率，所以这种窗口显示目标但不显示实际值和差距。
- **留存率**：按付费账户做月环比留存。窗口结束所在的 UTC 自然月是当月；分母是上一个 UTC 自然月内至少有一次付费充值的不同账户，分子是其中从当月第一天到窗口结束（`until`，不含）至少又有一次付费充值的账户。留存率 = 分子 ÷ 分母，以基点表示，四舍五入。窗口结束在月首时（`until` 正好是某月第一天），当月是上一个月：用 `until - 1ns` 所在的月判断。当月还没结束时是月初至今的留存，不是整月预测；分母为 0 时没有实际值。这个口径只用现有的充值批次，不需要新增埋点，衡量的是付费账户是否继续付费，不是注册后的首次付费。
- **周期与折算**：一个目标覆盖一个 UTC 自然月，存为该月第一天。看板的窗口（24 小时、7 天、30 天）可以跨月，数量和金额目标按窗口与每个月重叠的时长折算：`目标 × 重叠时长 ÷ 该月时长`，四舍五入到指标的最小单位（调用量、错误数、付费用户到 1，金额到十亿分之一），再把各月相加。重叠时长按纳秒参与整数比例计算，只在最后的目标单位上四舍五入一次；带毫秒的窗口跨月时不会因为先截断整秒而少算。折算假设业务在月内均匀发生，不按历史曲线外推；某个月没设目标就不计入，不把缺目标当成 0。毛利率和留存率是比率，不折算：取窗口结束所在 UTC 自然月（`until - 1ns` 所在月）的目标原值。比率的分母由窗口本身决定，按比例缩放目标会改变它的含义。
- **显示**：目标月份用页面语言的月份名和年份选择，不用跟随浏览器语言的原生月份输入；控件旁写明月份按 UTC 定义，页面上的其他时间按查看者的时区显示并标出时区。看板在调用、错误、收入、成本和现金这组卡片之外单列「经营数据」：付费用户、月流水、毛利率、留存率各一张卡片。差距是实际减目标：数量是实际个数减折算后的目标，金额是实际金额减折算后的目标，比率是实际基点减目标基点；实际值不可用时只显示目标并说明原因。
- **实际值不完整时**：调用量和错误数仍显示目标；调用日志不完整时它们的实际值不完整，差距不显示。收入来自账本，不受调用日志归档影响；成本也来自账本，但 `profit IS NULL` 的调用没有已知供应商成本，成本合计不包含它们。窗口内有这种调用时，成本仍显示目标，差距不显示，并单独提示成本未补齐；补齐后再显示确定差距。付费用户、月流水和留存来自充值批次，不受调用日志归档影响；留存的分母为 0 时显示目标但不显示实际值和差距，并说明上月没有可留存的付费账户。目标本身是整月值，不因日志归档或成本补齐而改变。现金和排名不设目标。
- **谁可以设**：和打开看板相同的 `sites.manage` 权限，并且要两步验证。这个权限属于内置的 `admin` 角色：负责人在管理后台用带 `admin` 角色的账号，也可以把这项权限授予其他管理员。站点内账户所有者的 `owner` 角色不含管理接口权限，所以不另设 owner 专用权限；运营 agent 的令牌走运营接口，不在这份管理接口上。没有新增权限：能改目标的人本来就能改站点设置。目标属于站点，管理会话在哪个站点就只能设哪个站点。
- **币种**：金额目标带站点的记账货币，只和同币种的实际金额比较。站点的记账货币改了以后，旧目标保留原币种，不换算、不参与新币种的对照；看板把该指标当作没有可用目标，直到负责人按新币种重设。月流水和调用收入都按站点的记账货币；付费用户、毛利率和留存率没有币种。
- **金额和比率的范围**：金额目标存为 `numeric(38,0)`，最多 38 位十进制数字，不套用账本单笔金额的 `int64` 限制；目标是可以超出 64 位的计划数，输入和输出都保留十进制文本的每一位。前端接受最多 38 位、至多 9 位小数的非负金额，不把金额转成浮点数。毛利率和留存率的目标是 0 到 10000 的整数基点，前端按百分比输入（最多两位小数），换算成基点后提交；毛利率的实际值可以为负，目标本身不能为负。
- **写入与并发**：一次替换这个月目标的整体；前四项走旧路径，八项整组替换走 `/reports/targets/{month}/all`。请求里没给的项就是清除，0 是真实目标（例如错误数目标为 0）。前四项存在 `operations.targets`，后四项存在 `operations.commercial_targets`；分表是为了滚动发布时旧节点按原查询读 `operations.targets` 不会遇到不认识的指标，两张表共用 `operations.target_revisions` 的版本。主键都是站点、指标、月份。每月有一个从 0 开始的版本：未写入时为 0，每次成功写入（包括清空）加一。读取目标时一并返回版本；写入在一个事务里先锁住这个站点和月份（advisory lock），再读旧值和版本，和请求携带的版本比较，不符就返回 `409 stale_revision` 且不写，随后写新值、更新版本、记审计，一起提交。这样两个管理员同时编辑时，后提交的旧表单不会把先提交的新目标恢复成旧值；前端保留打开表单时的快照，收到 409 后重新加载当前目标再提交。
- **审计**：每次改动记 `targets.update`，带站点、月份、改动前后的全部目标值（没设的项不出现）和理由；理由必填（1–1000 字），和改动同一个事务。旧页面只改前四项时，后四项的现值也原样记进改动前后，审计不会看起来像被清空。审计不写目标以外的业务数据。
- **滚动发布**：看板响应里的 `targets` 和它里面的 `metrics` 都是可选字段。旧节点没有 `metrics`；新页面遇到没有 `metrics` 的节点只编辑和提交前四项，不显示后四项，也不发送它们。新节点的 `metrics` 列出八项，新页面编辑全部八项，并把整组替换写到 `PUT /api/admin/v1/reports/targets/{month}/all`，同时带 `X-Axiom-Target-Metrics: all` 和请求体的 `all_metrics: true`。这个路径是新节点才有的：旧节点没有路由，直接返回 404，不会把整组请求误当成四项写入；只带请求头或只带请求体标志的请求也会被新节点拒绝。旧路径只接受前四项，新节点在旧路径上收到整组标志会返回 400；没有标志时保留后四项原值，仍记一条包含它们现值的审计。反过来，旧页面不发送后四项，旧节点本来就不认识它们；新页面在旧节点上也不会发送 `metrics` 里没有的字段。迁移先于新节点执行；新表让旧节点继续按原查询工作。

### 防止被外部内容操纵

- 来自外部的内容（中转站页面、上游报错、用户的请求内容、Issue 正文）一律标记为不可信。
- 涉及钱和凭证的操作，参数不能取自外部内容。例如给供应商充值的建议，收款方只能是接入时登记并确认过的那个；金额、汇率和上限由服务端从数据库算，agent 写的内容只作为理由。
- 审批摘要由服务端生成，agent 的理由单独标注为不可信；审批 AI 也只把 agent 的理由当数据，不执行里面的指令。
- 浏览器工具和统一的出站客户端受同样的网络限制：不能访问内网和云服务器的元数据地址（见[安全的「安全基线」](../security.md#安全基线)）。

### 部署与节点管理

- 部署组件和 agent 分开运行，agent 的令牌访问不到它。
- 运营监听在核心上，默认关闭；打开时只接受带 `ops` 用途客户端证书的双向 TLS，来源按地址限制。运维节点的 MCP 桥用`ops` 用途的节点证书加运营凭证连接，不直接连数据库。运营监听的就绪随核心的能力标记；没有能力标记的节点不接运营请求。
- 升级只接受 CI 构建并签名的版本：生产入口 `scripts/ops/deploy.sh` 从实际 Compose 配置解析 `axiom` 和 `migrate` 的镜像，用 `scripts/ci/verify-release.sh` 按 digest 核对 cosign keyless 签名、workflow 身份和 SBOM，再固定该 digest 执行 pull、前端资源发布和 up；未签名、身份不符、digest 不一致或验签失败时不拉取、不启动（[发布的「镜像签名与验证」](../ops/release.md#镜像签名与验证)）。
- 节点管理操作（重启、摘除流量、升级、增减服务器）按上文的风险分级审批；运营接口只开放重启单个节点和摘除流量，升级、增减服务器和删除数据仍在部署组件，agent 的令牌访问不到。
- **滚动发布时新旧节点共用队列**：节点只取自己有 worker 的任务种类，旧节点不会把新版本登记的任务当作未知种类失败掉、耗掉尝试次数，任务由已有该 worker 的新节点执行（见 [platform 的「任务队列」](../../internal/platform/README.md#任务队列)）。
- **节点启动自检**：`axiom serve` 依次读三份密钥文件（`AXIOM_MASTER_KEY_FILE`、`AXIOM_KEY_HASH_FILE`、`AXIOM_IDENTITY_KEY_FILE`，缺失、权限过宽或格式不对就不启动，报错只指出变量名，不含路径和内容）、连数据库并核对角色与表的安全设置、按服务器的 `max_connections` 和 `AXIOM_CORE_NODES` 计算连接预算（算不下就退出，日志报出算出的数）、检查兜底价表完整、读一遍目录和供应商的端点与售价；任何一步失败整个进程退出，而不是带着残缺的状态接流量。三份密钥由部署的 `keys` 服务第一次启动时生成，放在与数据库同寿命的卷里：主密钥和哈希密钥丢了会让用户的二次验证、供应商凭证和 API key 全部失效；身份密钥单独一份，是因为它决定发往上游的会话标识，轮换它只会让上游的提示缓存重新建立，不应牵连 API key 的哈希。就绪（`/readyz`）要等路由快照可用：快照里有端点，或者供应商还一个端点都没有（刚部署，供应商要通过管理端添加）；供应商给了端点而没有一个进得了快照（缺模型规格或售价）时不就绪，原因在日志里（见[路由的「路由快照从哪来」](routing.md#路由快照从哪来)）。停机先把 `/readyz` 置为未就绪、对之后开始的请求答 503（带 `Retry-After: 1`，不缓存），在途请求不受影响；从没有就绪过的节点没有流量要等，直接进入下一步。就绪的节点等边缘按探测摘掉流量：`AXIOM_SHUTDOWN_TIMEOUT` 的三分之一、最多 10 秒。然后关公开、管理和节点监听，让在途请求、调用和结算在同一个 `AXIOM_SHUTDOWN_TIMEOUT`（默认 30 秒）里结束，期限前 5 秒取消上游尝试，最后 5 秒留给结算；到期还没结束的连接被关闭，没结算的交给清理，这段时间持有者的心跳照常发。之后停心跳与清理，健康循环等待已付费的试探读完并写成本、刷新变化（最多 55 + 10 秒），最后同时排空任务队列和调用记录的写入，各有自己的期限（都是 `AXIOM_SHUTDOWN_TIMEOUT`），所以一条长流用完了排空的期限、一个慢的任务也不会让记录丢掉。入口节点每秒探一次核心的 `/readyz`，核心一开始排空，入口就不再报告就绪，边缘也就不再往这条链路送新调用。`stop_grace_period` 要容得下最坏情况（边缘 10 秒、监听与调用 30 秒、健康 65 秒、队列与记录 30 秒、缓存退出最多 10 秒；部署给 170 秒）。新旧构建的页面文件怎么在重叠期间都取得动，见[发布的「滚动发布」](../ops/release.md#滚动发布)。
- **数据库健康检查按真实启动时间，等待以健康检查为准**：PostgreSQL 的健康检查在 2 分钟的启动期内不把失败计入重试，之后每 10 秒探一次、连续 3 次失败才判为不健康；第一次 `pg_isready` 成功就立即标记健康。生产入口等待这个条件，并用 `--wait-timeout 300`（5 分钟）兜住反复重启、永远到不了不健康的容器；CI 的部署检查不另设期限，由步骤的 40 分钟上限兜住。
- **数据库切换不能丢已确认的提交**：已确认的结算和预留在主备切换后必须还在，否则钱会重复扣或漏扣。所以有备库时设 `synchronous_commit = on` 并至少有一个同步备库；没有同步备库就不做自动切换，主库故障时人工恢复。生产用哪一种待定（见下文「待定问题」）；两种都守得住钱的正确性，差别在费用和停机时间。切换演练在 M1 的端到端测试里做（见 [gateway 模块的「故障矩阵」](../../internal/gateway/README.md#故障矩阵)）。

### 通知

- **渠道、分级和发送回执归记录与告警**：见[通知渠道](observability.md#通知渠道)和[监控与告警](observability.md#监控与告警)；接收人在下文「控制面」里设置。本节只写运营怎么用它们。
- **通知中心运行在运维节点上**，告警直接从监控发出，不经过 agent。
- **审批通知**：审批请求走同一个通知渠道，带服务端生成的摘要、影响范围、到期时间和管理后台链接；资金操作带一次性批准令牌。通知发送失败不影响审批排队，管理后台仍能看到待审批项。现在的实现：提案时在同一个事务里发出 `operations.approval_pending` 告警信号（键是审批 ID，字段有工具、目标和到期时间），决定、到期、撤回或作废时恢复；没有预置规则，负责人在告警配置里给这个种类加一条规则和渠道才会收到（和支付差异等信号相同，见[记录与告警](observability.md#通知渠道)）。摘要、管理后台链接和一键令牌尚未进入通知。
- **运维节点自己出问题时**：核心节点和外部的在线监测服务各有一条最简单的告警通道（邮件、短信或电话），直接通知负责人，不经过运维节点。
- **账户异常花费**：`observability.spend` 每 10 分钟把每个账户最近一小时的花费、来源网段和模型与它自己的基线比较，命中后发 `observability.spend_anomaly` 事件到已配置的渠道；升级完成、全部节点都认识这个通知种类后，再把 `spend_detection.notify_users` 打开提醒账户用户（默认关闭）；收到后按[安全的「防滥用」](../security.md#防滥用)核对调用记录，可疑 key 由站点管理员停用（自动暂停尚未实现）。
- **对话**：负责人也可以通过 Hermes Agent 自带的消息入口（如 Telegram）直接和运营 agent 对话、下指令。对话里的指令只是请求，执行时同样受上文的权限和审批约束。

### 发现 bug，提交 Issue

- **从哪发现**：告警、错误日志、对账差额、调用记录中的异常。
- **怎么提交**：agent 不直接接触 GitHub，而是调用服务端的"提交 Issue"工具。
  - 工具只接受白名单字段（现象、时间、调用编号、复现线索），由服务端统一脱敏，确保 Issue 里没有对话内容、key 和任何密钥；
  - 工具限制提交频率；使用的 GitHub 令牌只有该仓库提 Issue 的权限。
- **先查重**：已有相同的未关闭 Issue 就追加证据，没有才新建。
- **第一版只提 Issue，不改代码**：改代码仍然走正常的开发流程。以后可以让 agent 认领 Issue、提交修复 PR，经评审后由负责人决定是否合并。

### 浏览器自动化

- **可以做**：登录、刷新令牌、读取页面上的价格和公告、创建 key（受数量和额度上限约束，见[供应商的「接入流程」](suppliers.md#接入流程)）。
- **不做付款**：给中转站充值时，agent 只给出"充哪家、充多少"的建议，负责人付款后，由 agent 核对是否到账。运营接口的 `supplier_top_up_propose` 记录建议并预留上限，`supplier_top_up_confirm` 附付款凭证后确认到账并把金额转为已用；两步都不由 agent 动钱。

## 决策与理由

技术选择按负责人的 2026-10-28 委托作出：「遇到问题自己解决问题和判断最优而不是问我。」（[原文](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)）。委托只覆盖实现方式；运营接口这个公开接口和资金规则本身已由负责人 2026-11-04 批准，原话和范围见「待定问题」。表中涉及资金规则的行（转账/售价怎么计上限、硬上限、退款/赠额默认人工）是设计定论；在资金上限服务接入前，现有支付和计费的第二人规则照旧，不按本表放开。

| 决策 | 理由 |
|---|---|
| 运营 agent 运行在单独的运维节点上 | 负责人提出。负责监控和抢修的系统不能和被监控的系统一起倒下 |
| 运行框架采用 Hermes Agent，规则留在服务端 | 负责人提出可以用 Hermes 这类框架，技术选型已授权开发者决定。它开源（MIT），不绑定模型，自带 MCP、定时任务、技能、记忆、子 agent 和消息入口（Nous Research 官网与 GitHub，2026-10）。没选自己写：记忆、技能、定时任务、对话入口都要自己实现，工作量大且难做好。没选 Claude Code / Codex 无界面运行：它们偏向编程场景，不擅长常驻运行和消息对话。它还没到 1.0、更新快，所以锁定版本、升级前评审；规则在服务端，框架可以随时替换 |
| agent 手里没有密钥，模型调用经模型代理 | 密钥一旦进入 agent，就可能被外部内容诱导泄露；预算也只有在服务端执行才可靠 |
| 控制面只有负责人能改 | 否则 agent 被操纵后，可以先把审批策略改掉，后面的审批就失去意义 |
| 额度按单笔、累计、笔数、对象同时限制 | 只看单笔的话，拆成许多小笔就能绕过 |
| 批准凭证由核心节点签发，密钥不在运维节点 | 运维节点被攻破时，也无法伪造负责人的批准 |
| 第二个 AI 审批由服务端调用不同厂商的模型，不可用时转人工 | 负责人提出。不同厂商的模型不容易被同一段恶意内容同时骗过；审批 AI 失效时不能变成自动放行 |
| `approval_wait` 每秒读一次数据库，不用 `LISTEN`/`NOTIFY` | 一次等待最多读 11 次，每次是一个只读事务里的三条主键查询，读与读之间不占连接；每张凭证的频率限制（每分钟 600、突发 60）同时限住了并发的等待。`LISTEN` 要给每个核心节点另占一条专用连接（连接预算里只有 River 的那一条），还要在负责人决定、到期清扫、撤回、作废的每条路径上都发 `NOTIFY`，漏一条就退回轮询的延迟；负责人决定后 agent 最多晚一秒看到，对等人决定的事无所谓。等待的循环在 `awaitDecision`，用 `testing/synctest` 按假时钟测 |
| 审计只由核心写入、哈希成链、异地留存 | 运维节点或 agent 出问题时，审计记录不能被抹掉 |
| 审计链除了等 60 秒，还等本库所有开着的事务（`pg_stat_activity.xact_start`） | 条目的 `at` 是事务开始的时刻，超过 60 秒才提交的事务（长的后台任务）会写出比链头更早的条目；只等固定时长，这样的正常提交就会被当成篡改、整条链停下。按开着的事务定边界，长事务只让链晚一点接、落后告警，不会误停；一条 `pg_stat_activity` 查询的代价。60 秒仍保留，兜住刚开始还没登记的事务和看不见的其他角色 |
| 每轮只核对链头往回 1000 条，整条链每天核对一次，核对的位置存在库里分多次做完 | 每分钟核对整条链的代价随审计日志一直增长；最近的条目被改在一分钟内发现，更早的在一天内发现。整条核对随日志变长会超过任务的 10 分钟期限，位置只放在内存里时每次都从头开始、永远到不了后段，所以每次只做 20 个事务、位置随每一批提交，下一次接着做。链只在本库时，能悄悄改旧条目的人也能改链，真正的保证来自异地留存 |
| 副本按链的序号分对象写，键带首末序号，写前先读、字节不同就停下告警 | 对象只增不改，桶的对象锁才守得住；推进位置失败后的重试写的是同样的字节，读回比较就知道是自己写过的，不必依赖桶支持 `If-None-Match`（SeaweedFS 3.80 不支持）。一轮读到的链比失败那轮多时会多出一个首序号相同的对象，两个对象重叠的那些行字节相同，核对程序按序号去重即可。否决的做法：按固定 1000 条一个对象：链不满一千条时副本一直落后；每轮覆盖一个「最新」对象：要能覆盖，凭证就也能抹掉记录 |
| 副本的凭证与程序的对象存储分开（`AXIOM_AUDIT_REPLICA_*`） | 调用记录的归档要删除过期对象，它的凭证必须能删；副本的凭证不能删也不能覆盖，所以是另一个桶、另一对凭证，和备份的凭证一样不与归档共用 |
| 每天的摘要是告警信号加 `audit_digests` 表，一天一个事件（键是日期），告知之后由告警模块关闭，关闭不发恢复通知 | 通知渠道、回执和重试都在告警里，不另造发送通道；信号字段最多 16 个、每个 512 字节，放得下合计和状态，完整内容放表里由接口读。每天一个事件，每份摘要有自己的回执，迟到或还没送达时来了下一天的，也不会互相覆盖。否决的做法：一个固定键的事件每天替换字段、靠规则的重复间隔送：重复按上次送达计时，摘要晚做几分钟就会再送一遍旧的，前一次还没送达时新的一份会覆盖它而漏掉一天；事件不关：开着的事件每分钟都要评估，一年后挤占真故障的评估名额；由任务过一天发恢复信号来关：通知队列积压超过一天时，摘要和关闭的信号在同一批里消费，事件还没告知就已关闭，这一天就漏发了；关闭时照常发恢复通知：每天多一条没有意义的消息 |
| 摘要等这一天的事务都结束、在一个快照里读、从上一份接着补 | 操作的时间是它的事务开始的时刻，午夜前开始、午夜后提交的操作在零点那一刻还看不见，只等日历过去会把它永远漏掉；用接链同一条边界等它提交。几张表分开读时，中间提交的到期清扫会让「操作还在等审批」和「审批已过期」同时出现，所以用一个可重复读的只读事务。只做「昨天」的话，任务停过一天那一天就永远缺；从上一份的后一天接着做，每次最多 7 天，停多久都能补齐 |
| 副本凭证要有列举权限 | 写前先读回同一个键，靠的是「不存在」答 404；S3 对没有 `s3:ListBucket` 的调用方把不存在的键答 403。先写再读的办法在不执行 `If-None-Match` 的桶（SeaweedFS 3.80）上会覆盖对象，所以保留先读，要求列举权限；列举只看得到键名，不能改写 |
| 链表不对审计日志建外键，发现不一致后停止接链、等负责人 | 外键会让被删掉的条目连同它的链一起消失，正是要发现的事；停下而不是跳过，是设计「不把它插到链中间」的要求，告警会一直开着 |
| 哈希覆盖 RFC 8785 的字段数组，`detail` 取 PostgreSQL 打印的 jsonb 文本 | 字段数组没有歧义，平台之外的核对程序照着就能重算；jsonb 的文本对同一个值总是相同，不用在 Go 里重排一遍 |
| 告警不依赖 agent，运维节点故障另有告警通道 | 告警是最后一道防线，不能和它监控的对象一起失效 |
| Issue 经服务端工具提交 | 由服务端统一脱敏和限频，agent 拿不到 GitHub 令牌 |
| 第一版只提 Issue，以后再自动提交修复 PR | 负责人同意。代码改动必须经过评审 |
| agent 不做付款 | 负责人同意。目前没有可供 agent 安全使用的付款方式 |
| 运营接口独立契约、独立监听，MCP 桥在运维节点 | 管理接口是人用的浏览器面，权限面太大；另做一份契约可以只暴露 agent 需要的操作，HTTP 和 MCP 由同一份契约生成，不会漂移。MCP 桥放在运维节点，核心仍只碰数据库和密钥。否决的做法：复用管理接口（131 个操作逐个过滤，控制面挡不住）；MCP 直接做在核心（没有独立契约，测试和升级都耦合） |
| MCP 桥用 MCP 官方的 Go SDK，无会话、每个请求回一个 JSON；工具在启动时从程序嵌入的契约生成，凭证文件每次调用重读 | MCP 在 2026-07-28 版去掉了 `initialize` 握手和会话，改成每个请求自带协议版本（[规范变更](https://modelcontextprotocol.io/specification/2026-07-28/changelog)，2026-11-06 查），客户端正在两代之间迁移；官方 SDK v1.8.0 同时说两代、跟着规范升级（许可证 Apache-2.0，部分旧代码 MIT），总体架构的技术选型已把 MCP 的官方 SDK 列为选 Go 的理由之一；负责人 2026-11-07 同意用它（「同意用官方开发包（推荐）」，[记录](https://github.com/TYCT-tyct/Axiom/pull/688#issuecomment-6710138043)），并随 MCP 规范升级。无会话是因为桥在两次调用之间没有要记住的东西；一问一答的工具调用不需要 SSE 流。工具从嵌入的契约生成：核心的守卫读的也是这一份，同一个构建里两边不会漂移，也省掉一份要保持最新的生成物。凭证每次重读，是为了轮换时换文件即可，Hermes 手里的本地令牌不用跟着变。否决：自己写 JSON-RPC（要逐版追握手、请求头和版本协商）；stdio（凭证进 agent 的进程）；把工具生成成 Go 代码（内容与嵌入的契约相同，多一份生成物）；只在启动时读凭证（轮换要重启桥，Hermes 也要重新取本地令牌） |
| 运营凭证是 `accounts` 的第三种操作者，不是用户会话或管理 key | 人的会话带 MFA、CSRF、Origin 和站点域名，长期会话等于把人的全部权限复制给模型；管理 key 只能在自己的账户内管理调用 key，范围不对。独立凭证可以按运行环境吊销、按权限和站点收窄，且只在运营监听有效。代价是新增一种操作者和一张表；收益是控制面和运营面的认证彻底分开 |
| 运营接口只暴露运营需要的操作，不提供批量资金/高风险写 | 一次调用一个对象，审批、上限、审计和回滚都以对象为单位；批量接口会让一次批准覆盖多个对象，拆单和越权更难发现。需要批量时由负责人在管理后台做，或 agent 逐个调用，各自计数 |
| 转账按金额累计，售价按包络累计，不把售价折算成金额 | 售价的损失取决于未来销量，折算要预测；预测可被操纵，也会让上限随模型和时段漂移。利润率下限和单日变动幅度直接约束售价；转账的现金流出按金额累计。两类都要求 `operations.money`，各有计数器 |
| 固定 UTC 日/周窗口加计数器行锁 | 固定窗口可以用一行计数器加行锁原子判断，不需要串行化事务或扫描历史；代价是边界上可能连续用两个窗口，由按对象、笔数和硬上限削弱。滚动窗口要保存每笔并加更大的锁，当前运营量下不值得 |
| 先预留后执行，成功转已用，确定失败释放，结果未知保持预留 | 钱不能在检查之后、执行之前被另一笔操作挤出去；也不能在结果不明时把额度放回去让 agent 再花一次。预留是唯一的在途状态；对账任务只收敛明确的结果，不猜 |
| 已批准但未开始的跨窗口操作过期，不续用旧批准 | 否则昨天的批准会在今天再执行一次，两个窗口各算一次；过期后在新窗口重新提案、重新审批，已经进入 `executing` 的未知结果保留原窗口预留 |
| 自主/累计上限是审批线，硬上限是拒绝线 | 待批或人审的金额可以超过自主阈值，否则合法的超额提案建不出来；硬上限仍不可越过。笔数上限同样只决定审批 |
| 运营操作状态含 `rejected` 等终态，重做新建操作 | 审批驳回、指纹/版本失效和策略收紧是正常结果，契约必须有对应状态；终态不复用，避免旧批准、旧预留和旧状态被再次执行 |
| 硬上限超过即拒绝，人工审批不能越过 | 上限是负责人的授权边界，不是审批人的橡皮图章；如果人工可以无限批准，被操纵的 agent 只要刷审批就可能把额度耗光。负责人要更高额度，应在控制面显式改上限，留审计和两步验证 |
| 退款和赠额默认人工，目标模块的第二人规则仍适用 | 支付和计费现在都要求另一个管理员批准；运营上限是额外一层，不替代第二人。额度内的直接退款/赠额要等资金上限服务上线并评审后由负责人单独决定，本设计不顺手放宽 |
| 审批绑定指纹、服务端生成影响、一次性令牌、超时即拒绝 | 防止批准 A 执行 B、防止 agent 写的文字影响审批人、防止令牌重放；超时即拒绝避免无限期挂着。高风险必须后台加两步验证，因为一键令牌只适合金额有限、影响可逆的资金操作 |
| 审批 AI 默认关闭，开启时只能用不同厂商、低于人工上限、失败转人工；高风险按类别开启，控制面、第二人、凭证/删除/部署不给 AI | 不同厂商降低同一段注入同时骗过提出方和审批方的概率；默认关闭是因为 AI 审批不是必须的，先用人审建立基线。高风险有 AI 审批是产品要求，但按类别授权，凭证、权限、删除和部署不交给 AI。AI 不可用时转人工，不能变成自动放行 |

| 运营凭证的令牌单独一张表，轮换时旧令牌记到期时间 | 一张凭证在重叠期内有两个有效令牌，按令牌哈希查找要两个都能命中；放在凭证行上要两套哈希列和两条唯一索引。令牌表以哈希为主键，部分唯一索引保证只有一个当前令牌 |

| agent 的映射只给分组列为待映射的名字建分组别名，且只映射到分组里还没有名字的模型；纠正别名、整个供应商的别名和调用格式声明留在管理接口 | 设计把「映射待映射模型」列为日常、直接执行，因为一个待映射的名字还没有端点、不接流量，映射只是让它从下一次同步起成为一个新端点，错了由真伪检测发现并告警，影响面是一个新端点。别的映射会改走已经在走的流量：分组别名会盖过整个供应商的别名和目录的识别，纠正会把正在接流量的端点换成另一个模型，整个供应商的别名一次作用于所有分组、建了不能改，这些都超出"日常"。待映射的名字映射到分组已有的模型也一样：投影按「分组 + 模型」只留一个端点，别名算精确映射，优先于目录识别出的候选名字，两个精确的名字按清单里的先后取第一个，所以新名字在原名字只是候选或排在它前面时会接管原端点，改掉它的上游名字、格式和成本计划，新名字没有成本时原端点还会变成成本未知、退出路由；所以分组已有这个模型的端点、已解析到它的名字或映射到它的别名（含还没投影的，否则连续两次映射就能绕过）时拒绝。两条判断都在 suppliers 的 `MapPending` 里、和建别名在同一把锁下，而不是只靠 HTTP 处理器。要求分组（路径里的 `group_id`）也让 agent 建的每个别名都能由负责人在管理接口用 `rev` 纠正。否决：照搬管理接口的 `mapSupplierModel`（agent 能改走现有流量）；只拒绝已有同范围别名（盖不住整个供应商的别名和目录识别出的名字） |
| 包络每个站点一行，没有就拒绝 | 和转账的"没有策略就不动钱"一致，失败关闭；平台默认值加站点覆盖等有第二个站点要定价时再做 |
| 操作记录和审计日志分开 | 每次工具调用都进操作记录，读也能回放；审计只记状态改变，保持"谁改了什么"的清晰和可检索。合成一张表会让读操作淹没审计，或者让读也进入不可变的审计链 |
| 回滚是补偿操作，成功的资金操作不自动返还上限 | 删除或改写原记录会毁掉审计；自动返还上限会让"花掉、退回、再花"在同一窗口循环。补偿操作重新走审批和上限，原操作永久保留 |
| 上线按能力门控，没有凭证或没有策略时失败关闭 | 滚动发布时旧核心没有运营监听，不能让 agent 退回管理接口；没有策略时默认拒绝，避免"忘配就是不限" |
| 运营看板的收入与成本取自 `billing.reservations` 的结算行，不另建汇总表，也不用调用日志的费用 | `charged` 是用户实付，`profit = charged - 成本` 是结算时算出的利润，两列就在同一行，收入和成本不需要新的数据结构；`profit IS NULL` 时成本未知，单独计数而不按 0 计，符合 [#319](https://github.com/TYCT-tyct/Axiom/issues/319) 的要求。调用日志里的费用不是结算记录：它的写入不在结算事务里，进程崩掉时可能少一条已结算的调用；账本视图的结算分录是净额，算不出每条调用的成本。汇总表要由多个写入方按站点、账户、模型、天维护并回填历史，容易和结算漂移；窗口查询由 `00032` 与 `00041` 的索引限定（见[计费](../../internal/billing/README.md)），当前体量下是有限的范围扫描。数据量涨到范围扫描不可接受时再加汇总，合同和页面口径不变 |
| 现金只看账本的 `cash` 科目，按支付币种列出，不把调用费用当现金 | 收入是权责发生（调用时已收费），现金是收付实现（充值到账、退款出账）：充值进来的是预付款，消费时才转为收入；退款是现金流出，不冲减调用收入。把调用日志的费用当现金，会把还没收到的钱和已经收到的预付款混为一谈。按支付币种是因为站点可以收多种货币，折成记账货币会丢掉汇率和实际到账的信息 |
| 下钻复用已有的调用记录和订单页，站点、模型和结果作为可选查询参数；现金用订单页的流水视图，付费充值用订单页的批次视图 | 不为看板新建页面：窗口、账户、模型、结果都是已有页面本来就能筛的维度，放进地址后链接可分享、可收藏，返回时窗口不变。现金不能按订单的 `created_at` 下钻：较早订单的退款和线下充值会落在窗口之外，所以订单页的 `cash=1` 视图读账本交易本身。付费用户、月流水和留存也不能按订单的 `created_at` 下钻：订单可能在窗口开始前创建、窗口内才入账，线下充值甚至没有订单；`paid=batches` 视图直接读 `billing.credit_batches` 的付费批次，按批次 `created_at` 列出与指标同一口径的记录。地址里的筛选参数都是可选的，新旧节点滚动发布期间都能读 |
| 调用日志的 `at` 和预留的 `created_at` 用同一个准入前时刻 | 两处各取一次时间时，一次跨过窗口边界的准入会让调用算进窗口而它的钱算到下一个窗口，或者反过来。网关在接收请求时取一次时间，随预留请求传入并用于调用记录；延迟仍从执行开始算，不把准入耗时算进上游延迟。历史预留保持原值，口径文档写明 |
| 调用日志的完整性按请求窗口检查缺月，不只看最老分区，也不查归档清单 | 保留任务允许较老月份归档失败后继续删除更晚的月份，最老分区不能证明窗口内每个月都还在；`CallCoverage` 读一次月分区集合，`Covers(since, until)` 逐个检查窗口触及的整月，缺月才标不完整，窗口完全落在还在的月份里仍是完整的。代价是每次看板/列表读一次系统目录、最多判断窗口跨过的几个月份；`available_since` 仍取最老分区，说明确定已归档的起点。边界按整月，已归档月的迟到写入落在默认分区，但那个月本身不完整，仍标为不完整而不是把它算成完整 |
| 看板只看请求所在站点，不做站点选择器 | 管理会话属于一个站点，M1 的订单和设置页也是这个范围；跨站点的对照属于平台控制台，不在 M3 的运营看板里 |
| 复用 `sites.manage`，不新增目标专用权限 | 看板本来就只对 `sites.manage` 开放，能看看板的人就是运营负责人或管理员，目标只是看板数据。新增权限要同步角色、迁移和前端，还会多出“能看看板但不能设目标”的无意义组合。`owner` 是站点内账户所有者的角色，不含管理接口权限；负责人在后台用带 `admin` 角色的账号 |
| 数量和金额目标按月设、按窗口重叠时长折算；毛利率和留存率取窗口结束所在月份，不折算 | 负责人设的是月度经营目标，24 小时、7 天、30 天只是观察窗口；按重叠时长折算让同一个目标在任何窗口都能对照，跨月时各月分别折算后相加。比率的分母由窗口决定，按比例缩放百分比会改变它的含义，所以只取结束月。给每个时段各设一套会让负责人重复维护、口径互相矛盾；按历史同期外推需要历史基线，第一版没有 |
| 业务目标存 `operations.targets` 和 `operations.commercial_targets`，不写进配置，也不写进文档 | 目标是运营数据，负责人随时调整；配置要重启或发布，文档会过期。存在管理数据里，权限、审计和滚动发布都沿用管理接口的做法；产品文档只规定要有这件事，不写具体目标值 |
| 后四项单独存表，共享版本，整组替换走旧节点没有的新路径 | 旧节点按月份范围读 `operations.targets` 时不按指标过滤，新指标混进去会让旧看板整体失败；分表让旧节点继续工作，共享 `target_revisions` 又让两个版本的编辑器只看到一个顺序。整组替换走 `/reports/targets/{month}/all`，并同时要求 `X-Axiom-Target-Metrics: all` 和请求体的 `all_metrics: true`：旧节点没有这条路径，会在写入前返回 404，不会把整组请求当成四项写入；旧路径只接受前四项，新页面在没有 `metrics` 时也只发前四项。这样滚动发布的两个方向都不会清掉对方的数据或报假成功 |
| 金额目标带站点记账货币，币种不符时不换算、不比较 | 汇率会变，换算后的目标不是负责人当初设的数；把两种货币的实际金额当成一个数比较会算错。宁可显示该指标没有可用目标，也不悄悄换一个数 |
| 现金和排名不设目标 | 现金按支付币种分别列，折成一个数会丢掉汇率和到账信息；排名不是可加总的业务量，目标对排名没有意义。调用量、错误数、收入、成本、付费用户、月流水、毛利率和留存率覆盖可考核的经营结果 |
| PostgreSQL 健康检查的启动期设为 2 分钟，生产入口的最长期限覆盖它 | 共享主机上非正常停止后的崩溃恢复 40 秒时仍在 fsync 数据目录、48 秒时仍报 `the database system is starting up`（#605），旧的 30 秒启动期加 3 次 10 秒重试在恢复完成前就判为不健康；2 分钟是实测下界的 2.5 倍。启动期不影响就绪，只推迟把真正不恢复的数据库判为不健康；生产入口保留 5 分钟的最终期限：postgres 的 `restart: unless-stopped` 会让反复崩溃的容器每次都重置启动期，永远到不了不健康，而生产入口没有 CI 的步骤上限；CI 的部署检查不另设期限，由步骤的 40 分钟上限兜住 |
| 一次写入替换整月目标，按站点和月份加 advisory lock，并用月份版本拒绝旧表单，审计同事务 | 目标是一套整体，半套新半套旧会让看板显示互相矛盾的口径；锁的粒度足够小，不阻塞别的站点或月份。锁只串行写入，不能识别表单读到的是旧值，所以版本不符时返回 409，避免后提交的旧表单静默覆盖新目标。审计和改动同事务，未记录的成功改动不能留下 |

## 待定问题

- **已批准**：运营接口、运营凭证和资金上限是公开接口和资金规则；负责人 2026-11-04 在[评论](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6498764672)批准本设计，原话：「12同意，3待定后续会做现在成本高不推荐。4测评我会单独做一个项目一个网站 5.写一个demo」；第 2 项即本设计，覆盖运营接口、MCP 映射、审批、资金上限和审计。
- 累计上限的默认数值、窗口、类别和按对象的上限由负责人定；代码只带初始值，后台可改。
- 待批提案的 30 分钟、已批准未开始的 5 分钟执行期限是否调整，由负责人定；代码带默认值，后台可改。
- 审批 AI 的模型、厂商、默认开关、金额档，以及哪些高风险类别允许 AI 审批，由负责人定。
- 运营凭证的最长有效期、轮换周期和是否限制来源地址由负责人定；现在每张凭证的到期时间由负责人创建时给出，代码不设默认值和上限，要统一的上限时作为控制面的设置加入；来源由 `AXIOM_OPERATIONS_SOURCES` 按部署限制。
- 审计和操作记录的保留期由负责人定；与钱有关的至少与账本同寿命。
- 审计链停下之后怎么恢复：现在只能停着（告警开着，审计照常写），负责人查明原因后，是把迟到的条目接在链尾、给被改的条目补一条确认，还是另起一段链，待定；做法定下后在控制面加对应的操作。
- 额度内 agent 直接退款/赠额是否开放，待资金上限服务上线并评审后由负责人定；现在默认人工。
- 供应商充值的实际付款渠道仍未接入：agent 只提案，负责人付款，agent 附凭证确认到账。
- 节点管理里的升级、增减服务器和删除数据是否进入运营接口，还是只留在部署组件；本设计只开放重启和摘除流量。
- 电话、短信服务商的选择，取决于是否有公司主体
- 生产数据库的复制方式，部署前请负责人定：一主一同步备库（多一台机器的费用，可以自动切换），或单主不自动切换（故障时人工恢复，停机更久）

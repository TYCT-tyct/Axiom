# 供应商

怎么把官方 API、中转站、号池接进来，读懂它们的余额、分组、价格和用量，并在调用时挑选凭证、发出请求。对应代码模块 `suppliers`，调用路径上的接口见[模块 README](../../internal/suppliers/README.md)。概念之间的关系见[术语与核心概念](../glossary.md)，成本计划和对账见[计费](billing.md#供应商成本)。

## 要求

- 三类供应商通过同一套接口接入（见[产品需求的「供给侧」](../product.md#供给侧)）。
- 中转站多数基于 new-api、sub2api，约一成是自研系统；我们通常只有普通用户账号。
- 自研系统需要单独适配；以后不再接入的，适配可以干净地移除。
- 号池一般是自建的 sub2api、new-api、CPA 等系统；除非必要，不自己写号池模块，但要预留。
- 官方 API：实现主流的基础适配，暂不接入，只作预留。
- 接入、同步、变化处理尽量自动，人只处理例外。

## 设计

### 适配器：管理面和调用面

| | 管理面 | 调用面 |
|---|---|---|
| 做什么 | 登录、读余额、读分组和价格并生成成本计划、读模型列表、读逐笔扣费记录、创建 key | 用哪种协议发请求（OpenAI、Anthropic、Gemini、Responses）、鉴权方式、路径和各家怪癖 |
| 由什么决定 | 对方运行的系统 | 对方支持的协议；一个中转站通常支持好几种 |

- **两者独立组合**：一个管理面可以搭配多种调用协议，不为每种组合重写。
- **能力声明**：每个适配器声明自己能做什么，例如能否查逐笔记录、能否自动建 key、能否流式调用上游、是否把客户端断开传到上游，以及各接口允许的访问频率。系统按声明使用它，比如查不到逐笔记录的供应商被标为高风险，不能流式调用或不传递取消的端点在准入时一次预留足（见[计费](billing.md#预留与结算)）。是否传递取消只是默认值，以按端点实测的为准（见[计费的「客户端断开」](billing.md#客户端断开)）。
- **按请求对上逐笔记录**：调用面从上游的响应头里取出对方的请求号（对账键），记在尝试上，管理面凭它查这次的扣费记录：new-api 是 `X-Oneapi-Request-Id`，sub2api 是 `X-Client-Request-Id`（2026-10-14 本地实测，见[计费的「供应商成本」](billing.md#供应商成本)）。这些头不返回给客户端（见[接入与对外接口的「转发规则」](gateway.md#转发规则)）。
- **对账键什么时候落库**：结算时，这个请求全部尝试的成本和对账键在计费的结算事务里一次写入，与账本的供应商成本同成同败。请求进行中不再另记一份（[没有对账日志](../../internal/suppliers/README.md#没有对账日志)）：崩溃留下的预留由清理释放并记一行丢失的请求，带这条请求冻结的路线。

### 三档适配器

| 档 | 用于 | 怎么加 |
|---|---|---|
| 内置适配器 | 常见系统和官方 API | 写代码 |
| 声明式适配器 | 自研中转站中只是接口路径和字段名不同的那些 | 在后台填一份配置（登录地址、余额字段位置等），不改代码 |
| 浏览器自动化 | 前两档做不到的事 | 运营 agent 操作网页 |

第一版的内置适配器：

- **普通用户身份**：
  - new-api：适配新版的个人访问令牌和登录令牌，也兼容旧版的访问令牌；
  - sub2api：登录令牌加刷新令牌；
  - 通用 OpenAI 兼容：只有 API key，通过 OpenAI 兼容的余额接口读取余额。
- **管理员身份，用于自建号池**：sub2api 管理接口、new-api 管理接口、CPA（CLIProxyAPI）。CPA 的情况见下文「号池」。
- **官方 API（预留）**：OpenAI、Anthropic、Gemini 三种协议的调用面，加上最基本的管理面。这三种协议的调用面同时也是转换和检测的基准。

### 代码组织：适配器可以干净地移除

- 每个适配器是 `suppliers` 内部的一个独立包，带着自己的测试样本（录制的真实响应）和契约测试。
- 所有适配器在一张注册表里登记，各占一行。
- 适配器放在 `suppliers` 的 `internal/` 下，其他模块在编译层面就无法引用，见[总体架构的「AI 好写好维护」](../architecture.md#ai-好写好维护)。
- 移除一个适配器：删除它的目录和注册表里的那一行，不影响其他代码。声明式适配器只是一条后台数据，直接删除即可。
- 适配器能识别对方系统的版本，按版本选择对应的接口，不靠到处写特殊判断。

### 接入方式逐级兜底

每个适配器按顺序尝试：

1. 账号密码登录，调接口；
2. 遇到人机验证，由人登录一次，之后用刷新令牌或个人访问令牌保持登录；
3. 只用 API key 能访问的接口，例如 OpenAI 兼容的余额接口；
4. 浏览器自动化兜底，由运营 agent 操作。

### 接入流程

1. **填写网址和账号**：
   - 网址和之后所有的访问，包括识别系统类型的探测请求，都走统一的出站客户端，防止借我们的服务器访问内网（见[安全的「安全基线」](../security.md#安全基线)）。
   - 核对域名，防止把账号填进仿冒站。
   - 能用令牌就不存密码；必须存密码时加密存储。
2. **识别系统并选适配器**：new-api 有公开的状态接口，sub2api 有特征接口。
3. **选分组**：读出分组和倍率，由人选择要使用哪些分组。
4. **绑定 key**：M1 不自动建 key。适配器只读，key 由人在对方站点建好，Axiom 按对方的 ID 绑定（见本节的决策表）；移除供应商时 Axiom 清除自己存的密文，对方那边的 key 由人吊销，清单在审计记录里。自动建 key、移除时自动吊销，随适配器的写能力加入。
5. **确认单位余额价值**：适配器读出提示值，由负责人或运营 agent 确认；值存在本模块的 `suppliers.unit_values` 表（只追加，最新一行生效），确认之前这家供应商的端点不进路由。怎么换算成本见[计费的「供应商成本」](billing.md#供应商成本)。
6. **生成成本计划和端点**，进入检测队列（见[端点评估](quality.md)）。

### 调用面

- 调用一个端点：`Acquire` 在内存里按比较交换占一个凭证的名额（最闲的、未冷却、未过期的、滚动 60 秒的请求没用完的），`Attempt.Send` 发请求并把非 2xx 交给适配器归类，`Done` 释放名额并给出带对账键的回执；热路径不读库、不解密。每分钟的计数与并发位在同一步取，窗口是 61 个一秒桶组成的滚动一分钟，时钟在账号锁里读、按首次准入起的单调秒计（[模块 README 的「并发与速率」](../../internal/suppliers/README.md#并发与速率)）。凭证被拒、额度用尽、被要求等待时，按适配器说的时间让它歇着。
- **快照会过期**：调用用的端点来自 `Reload` 建的内存快照。最后一次成功的 `Reload` 之后 30 到 35 秒 `Routable()` 返回 `ErrStale`（重建每 5 秒一次），路由重建失败，路由快照再按自己的最长陈旧时间过期，节点约 1 分钟后对所有调用回 503 `overloaded`，同时 `/readyz` 回 503、负载均衡摘掉节点（见[路由的就绪](routing.md)），直到一次 `Reload` 成功。代价是整节点短暂停路由，换来的是期间被停用或移除的供应商只多接约 1 分钟流量，而不是无限期接下去。这是 `Reload` 整体失败（读不了库）时的取舍；单个凭证的 key 打不开只让那一家供应商离开本节点快照，不让 `Reload` 失败（见[模块 README 的「调用面」](../../internal/suppliers/README.md#调用面)）。
- **没有对账日志**：请求进行中不再记「哪些尝试到过供应商、对账键是什么、有没有交付」。一次结算把每个尝试的成本、对账键、端点、用量与供应商单位下的估算一次写进 `attempt_costs`，与计费的账同一次提交，所以已结算的尝试都有凭证；崩溃留下的预留由清理释放并留一行丢失的请求，带这条请求冻结的路线，钱最可能落在这些端点上。崩溃前那一刻的尝试没有任何记账；周期对账把无法匹配的超期扣费暂挂，由人归属，这个窗口就是代价。
- 结算时 billing 在自己的事务里调用 `RecordAttempts`，一次写入这个请求全部尝试的成本和对账键，与成本分录同成同败；`EndRequest` 在同一个事务里告知请求已有定论；对账见[计费的「供应商成本」](billing.md#供应商成本)。

### 供应商别名与待映射

中转站和供应商列出的模型名（上游名字）五花八门，按以下顺序映射到目录里的模型：

1. 查供应商别名：只在该供应商或分组内有效。同一个写法在不同中转站可能指不同模型，例如某站的 `gpt-4` 实际可能是 gpt-4o；`:free`、`:batch` 这类后缀也在这里映射。
2. 用目录的内部识别查公开和内部名字，归一化后匹配（见[模型目录的「名字解析」](catalog.md#名字解析)）。归一化不去掉日期，不同日期的版本不会被合并。
3. 仍然对不上，由运营 agent 提出映射建议。
4. 映射后，用真伪检测确认它确实是这个模型（见[端点评估](quality.md)）。目录说明某个名字不能当版本证据时，它只是候选，必须经真伪检测确认。

- **没有候选**：前三步都没有结果的上游名字进入"待映射"队列，不生成端点，不进路由。
- **有候选**：按接入流程第 6 步生成端点，标为待验证并进入检测队列，与[产品](../product.md)的「自动化」一致：能否接流量由预设的规则决定，预设可以要求只走已验证的端点。真伪检测判定不是这个模型时，端点下线，映射退回"待映射"队列。**M1 没有真伪检测**（`internal/quality` 还不存在）：候选名字的端点同样生成并接流量，「待验证」标记和检测队列随 quality。

### 凭证

- 加密存储（见[安全基线](../security.md#安全基线)）。
- 刷新令牌时"比较后再写"，防止并发刷新互相覆盖。
- 每个凭证有自己的并发上限和每分钟请求上限（1 到 100,000，可空），由管理员通过管理 API 设定（新绑定默认并发 4、每分钟不限）；同一上游账号的全部凭证与端点共用 RPM，按待选凭证的配置上限判断是否准入；RPM 在节点内按账号计数，并发和有限 RPM 均按存活核心节点静态分份额（交接与故障边界见[模块的并发与速率](../../internal/suppliers/README.md#并发与速率)），同一上游账号下各 key 并发上限之和应不超过上游账号并发（账号级独立并发准入仍待实现）；遇到对方限流自动退避。滚动发布期间旧节点可能写入更大的值，新节点按 100,000 读，数据库的上限 CHECK 待旧节点退出后再加。
- **状态和冷却存在本模块**：`credentials.status` 用来筛可用凭证（`active`）；冷却的实时值只在核心进程内——`rest()` 只写进程里的冷却时刻，`Acquire` 按它和 `expires_at` 挑凭证。`cooldown_until` 列已存在，但今天没有代码写入它，是否把冷却持久化待定。被上游拒绝、额度用尽、被要求等待时，按适配器给的时间让它歇着，冷却到期后重新参与挑选，没有单独的试探状态。端点的熔断不在这里，归端点评估，见[端点评估的「健康与熔断」](quality.md#健康与熔断)；检测和真实流量走同一个调用面，被拒的凭证同样歇着，检测不另存一份凭证健康。
- 凭证可以绑定固定出口（见[总体架构的「部署拓扑」](../architecture.md#部署拓扑)）。M1 只有 `direct`：`credentials.egress_id` 列已存在，调用路径不读它。

### 同步与变化

- **按供应商限速**：
  - 普通用户账号频繁登录或查询，可能被对方限流甚至封号，预付的余额也会跟着受损。所以每个适配器声明各接口允许的访问频率，同步严格遵守，并加入随机抖动。
  - 例如 new-api 的登录和 key 日志接口默认每 20 分钟只允许 20 次，运营方可以改（new-api 源码，2026-10）。
- **先用便宜的接口**：能从一次请求得到的信息，不分多次去拿。
- **默认频率**：价格、分组、模型列表默认几分钟一次；余额更频繁；逐笔扣费记录在限速范围内批量拉取。
- **账号异常立即停止轮询**：比如登录失败、被封，同时告警，等人处理；人换上新的登录后它从现在接着同步，已经读过的扣费记录不重读（见[供应商模块的「持久化」](../../internal/suppliers/README.md#持久化)）。
- **读取进度要接得上**：分组的目录和 key 清单可能比一个限速窗口允许读的更长。读到一半被限速时，进度随同步状态存下、任务结束，下一次（别的任务、别的节点也一样）接着读，不为了等限速重开占着一个队列工人，也不从头读、不跳过任何一页。
- **发现变化就发事件**：改价、改倍率、新模型、下架、余额不足。变化写成 `sync_events`；登录失效、同步需处理、任务停止和低余额事件由每分钟的持久消费者转为平台告警；消费位置与信号原子提交，恢复、去重和重试见[告警设计](observability.md#告警信号事件与规则e5-3)。首次上线只上报当前未恢复问题，避免历史回放风暴；价格和快照仍靠 5 秒一次的定时重建跟上。
- **落到表上**：一次同步把刚读到的清单写成行——分组（`supplier_groups`）、每个分组的上游名字及它映射到的目录模型（`supplier_models`）、端点（`endpoints`）和端点的成本计划（`cost_schedules`）。路由和后台读的是这些行，不是同步的状态。
  - 只有映射到上架目录模型、并且那个模型有成本计划的名字才有端点；映射不上、或模型没上架（如草稿）的名字只留在 `supplier_models` 里等映射，不生成端点，见[供应商别名与待映射](#供应商别名与待映射)。一个分组下两个名字指向同一个模型时只有一个端点：用名字本身带版本的那个（如带日期），都不带的取排序第一个；候选名字要先过真伪检测。
  - 分组卖不了给我们（订阅分组、按小时计价）时，清单里它的模型没有调用格式：那些名字不成行、也没有端点，原来的端点改为"成本未知"退出路由，分组恢复可调用时同一个端点回来。
  - 同一份清单读两次，这几张表一行都不改：行只在内容不同时才写，成本计划按指纹只追加一版。下架的分组和模型标为不存在而不是删除，端点改为"成本未知"并退出路由，清单再出现时还是原来那些行。
  - 端点的启用开关归人：同步不会重新打开人停用的端点。
- **余额是路由条件**：M1 的门槛是供应商的余额大于 0——余额还没读到过、为 0 或透支的供应商，端点不进路由快照；新接入的供应商在第一次余额同步之前（最多约 1 分钟）不可路由，节点此时报「not ready」是预期的。余额低于阈值时发 `BalanceLow` 事件。按请求的完整生成成本上界过滤、出现「余额不足」的失败后让整家供应商歇着已接入：调用路径只读快照，后台合并并限速请求余额同步，新正余额或完整成功的检测恢复；规则与取舍见[路由](routing.md#决策与理由)。余额低时降低端点权重尚未接入。由运营 agent 补充值，受资金操作上限约束。

### 号池

- **接入方式**：号池是自建的 sub2api、new-api 或 CPA，我们以管理员身份接入。
- **能看到的比普通中转站多**：
  - sub2api 和 CPA 能提供每个账号的健康状况和额度窗口（如 5 小时、每周），new-api 不提供；
  - 号池系统自己负责在账号之间调度，我们按分组路由，不直接挑选账号；
  - 账号层面的信息用于监控和估算剩余容量：额度窗口快用完时降低该分组的权重，账号大量失效时告警。
- **出网**：号池账号的出网代理在号池系统里配置，可以指向我们的出口节点，也可以指向外部的固定 IP 代理。我们的出口只负责 Axiom 到号池这一段。
- **CPA 的用量**：
  - CPA 从 6.10 版起不再内置用量统计，逐笔用量只能从它的用量队列读取；
  - 这个队列"读一条删一条"，记录只在内存里保留，默认 60 秒，最长 3600 秒，而且要先开启用量发布才有数据（CLIProxyAPI 文档，2026-10）。

  所以我们的采集程序必须一直运行，把记录按我们的请求 ID 写入数据库并去重；保留时间设为最长；同一个 CPA 上不能再挂别的采集程序，否则记录会被抢走。采集中断而丢失的部分，按"只能看到余额变化"的方式对账。
- **部署要求**：sub2api 存储凭证时没有加密，所以号池系统部署在内网，磁盘加密，管理端口只对 Axiom 开放。
- **管理员凭证**：权限极高，只给号池专用，权限尽量小。定期轮换；一旦泄露，立即吊销并重置号池里的账号。
- **支出**：号池的支出（订阅费、代理、封号损失）记入计费，用于计算号池成本。
- **预留**：自己写号池模块只作预留。它在系统里也只是一个适配器，需要时替换即可，其他部分不受影响。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 凭证并发与有限账号 RPM 采用后台静态份额，按节点 ID 分余数，额度小于人数时允许 0 份额 | 开发者按 #313 E3-3 任务卡及[负责人委托](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)确定。对比共享 Redis 槽位（容量利用率高，但每次调用增加共享计数、释放和故障清理）与仅按本地 N 等分（调用便宜，但扩容交接可超额），选完整成员列表确认，旧占用先排空再确认，新节点等待所有旧成员，保持存活核心的准入总额；代价是扩容短期欠用、低额度偏向排序靠前的节点。OpenRouter [Limits](https://github.com/OpenRouterTeam/docs/blob/main/api_reference/limits.mdx)（2026-10-28）强调增加 key 不增加全局额度；参考 sub2api 的共享槽位，但沿用 Axiom 已定的后台份额以守住调用预算。心跳失联不能证明上游孤儿请求已经停止，故不将失联回收描述为上游执行总量的保证 |
| 适配器分成管理面和调用面 | 对方运行的系统和支持的协议是两件独立的事；分开后可以自由组合，不用为每种组合重写 |
| 三档适配器 | 约一成的自研中转站大多只是接口路径和字段名不同，用配置就能接；配置也做不到的才交给浏览器自动化 |
| 每个适配器独立成包，移除只删目录和一行登记 | 负责人要求自研中转站的适配以后可以干净移除，避免代码冗杂 |
| 接入方式逐级兜底 | 来自团队成员的实践经验：多数站点用接口即可，遇到人机验证由人登录一次，剩下的交给浏览器自动化 |
| 同步按供应商限速，先用便宜的接口 | 普通用户账号被限流或封号，会连带损失预付余额 |
| 号池用自建的现成系统，以管理员身份接入，按分组路由 | 负责人决定。订阅账号的登录、刷新和风控对抗由这些系统的社区持续维护；账号之间的调度交给它们，我们不重复做 |
| CPA 的用量由常驻采集程序落库 | 它的用量队列读一条删一条、只在内存里保留，不及时取走就永久丢失 |
| 官方 API 只做主流基础适配，暂不接入 | 负责人决定。三种主流协议本来就是转换和检测的基准 |
| 供应商别名和待映射队列归本模块，不进目录 | 上游名字只在该供应商内有意义，全局共用会把请求映射到错误的模型；目录在模块依赖里位于本模块之下，不能引用供应商 |
| 刷新令牌时比较后再写 | 并发刷新互相覆盖会让账号掉线；sub2api 采用同样做法（sub2api 源码，2026-10） |
| M1 的接入向导：探测 → 创建 → 选分组 → 绑定上游已有的 key → 确认单位余额价值；Axiom 不在对方站点建 key | 适配器现在只读，写能力以后用单独的可选接口加入（[suppliers 的「适配器」](../../internal/suppliers/README.md#适配器)），所以 key 由人在对方建好，Axiom 按对方的 ID 绑定，文本由同步读取并封存。创建立即返回 `connecting`，登录和读取在同步里做、页面轮询：对方的登录可能要数秒，前端的请求 10 秒就超时。否决的做法：请求里同步登录：慢，失败原因混进请求错误；现在就自动建 key：适配器没有写能力 |
| 移除当场完成：状态直接是 `removed`，登录行删除，所有凭证的密文清空、凭证标为 `erased` 而行保留；不等在途，也不最后再读一次扣费记录 | 密文留得越久越是风险；在途的尝试手里已有解密后的 key（`Reload` 时读进内存），结算写成本要用的外键指向凭证行，行在就够。扣费记录每 2 分钟读一次，移除可能丢掉最后不到 2 分钟的记录；逐条对账会报告缺失的扣费，按 key 按天总数的补偿尚未实现（见[计费的对账现状](billing.md#供应商成本)）。Axiom 在 M1 不写对方，所以对方那边的 key 由人吊销，清单就是已清除（`erased`）的凭证行上的 `upstream_key_ref`，审计记录只记个数（`keys_to_revoke_count`；审计详情有 8192 字节的上限，不列 ID）。参考：new-api 删渠道是立即硬删整行（`model/channel.go`），sub2api 删账号是立即删除并清调度快照（`backend/internal/repository/account_repo.go`，表带软删除），两家都不等在途、不做最后读取；我们介于两者之间，比 sub2api 严（不留凭证），比 new-api 保住成本历史。否决的做法：分步移除（等在途、读尽记录、再删密文）：多一个持久化的状态机，上游不可达时会延长密文留存；硬删凭证行：成本记录指向它的外键断掉。以后要加最后一次读取，加在擦除之前，不用撤回 `erased` 状态。 |
| 供应商的地址和账号创建后不改，换凭证是单独的操作，移除也是 | 地址不变，旧凭证就送不到新主机（表的列级授权已如此）；换凭证、移除是高风险操作（[运营](operations.md#风险分级与审批)），单列出来才能单独审批、审计。否决的做法：一个「修改供应商」入口：审批策略分不开 |
| 换登录就唤醒同步，不另做「恢复」操作 | 停在「需处理」是登录不能用了，换上登录就说明可以再试；再要人点一次「恢复」，两步里漏一步供应商就一直停着，而它看起来只是「需处理」。状态复位（失败清零，已完成的清单和扣费位置保留，未完成的清单位置作废）、清租约、加代次都在换登录的同一个事务里，要么整个生效要么不生效，握着旧登录的节点写不进新状态。否决的做法：单独的恢复操作：要同时改 `suppliers.status` 和引擎的状态，多做一个人会忘的步骤；自动定时重试「需处理」的供应商：对方的封禁不是重试能解决的，只会白费请求 |
| 待映射是独立的队列，映射建的是供应商别名（可限定到一个分组） | 对不上的名字不生成端点，不进路由，在队列里一个个处理；别名只追加，纠正靠更窄范围的新别名，和模型名字「从不重新指向」同理。否决的做法：直接改端点的模型：同一个写法在别的中转站可能是别的模型 |
| 凭证的并发和每分钟请求上限由管理员设定，默认并发 4、每分钟不限（上限 100,000）；并发按凭证、RPM 按上游账号在节点内存里 | 同一上游账号的全部 key 和端点共用 RPM，新增 key 不增加额度；上限仍按待选凭证应用，共享一份额度的 key 应设相同值；上限改一次就存在行上，节点的下一次重建快照（5 秒）生效，调用路径仍是内存里的一次比较交换加一次加锁计数，不为限流加事务。窗口是 61 个按首次准入起的单调秒索引、各带秒标记的一秒桶，时钟在账号锁里读，过期桶读作 0：[now-60, now] 的合计覆盖所有以现在结束的滚动 60 秒，所以任意滚动 60 秒不超过上限；没有计时器，内存不随上限增长，代价是边界上最多少放行不到一秒的请求。[suppliers 的「并发与速率」](../../internal/suppliers/README.md#并发与速率) 写了窗口和竞态的处理。否决的做法：只按地址或账号在适配器的桶里限速（那是同步自己的限速，不能用来拒用户请求）；计数放数据库（每次调用一次事务）；多发一个令牌桶依赖（`golang.org/x/time/rate`，令牌补充口径不等同按秒计数的滚动窗口）；保存每次请求的时间戳（内存随上限增长，未设限的 key 更会无限增长）。并发和有限 RPM 按上文的核心静态份额划分；节点间不借空闲额度，扩容时保留旧窗口并排空，进程退出或失联后保留其成员视图到最后可能准入的 61 秒窗口结束，避免回收额度重复计入旧窗口，代价是临时欠用；首次从旧二进制升级须停旧核心并等 61 秒；TPM 等有可信的额度数据再加 |
| 单位余额价值按供应商单独存一张只追加的表（`suppliers.unit_values`），最新一行生效 | 它是供应商余额的属性，和结算货币一起归供应商；只追加、最新一行生效，一次尝试才能按回执里的行 id 复算（id 目前只在内存里的回执中，要复算已结算的尝试需先给 `attempt_costs` 加 `unit_value_id` 列），旧账不动；读进快照后成本换算仍是纯内存。否决的做法：按端点存：同一份余额要逐端点改，漏一个就算错；存在 billing：钱的数据离开供应商，结算还要跨模块查 |
| 分组和 key 清单的位置与同步状态一起存下，被限速的任务结束 | 每节点同步队列只有 4 个工人，持着租约等限速重开会阻塞其他供应商。下一任务用新适配器接着读，只在完整清单读完后替换对外状态；位置不含凭证，配置代次改变就作废。位置另存 `sync_states.listing`（迁移 `00013`），保留旧节点能读的状态格式；位置还绑定状态版本，旧节点写过后重读清单，避免恢复过期结果。否决的做法：继续在任务里等（占工人、重启丢进度）；把位置加入严格解码的状态 JSON（滚动发布时旧节点拒绝） |

# 账户与租户

谁能登录、钱和 key 归谁、谁能做什么、站点怎么配置。对应代码模块 `accounts`，表结构、查找与缓存、接口和测试见[模块 README](../../internal/accounts/README.md)。概念之间的关系见[术语与核心概念](../glossary.md)，这里只写本模块的要求和设计。

## 要求

- 用户、账户按站点隔离；C 类企业团队和 D 类二级站点的数据结构从第一版起具备（见[产品需求](../product.md#用户与市场)）。
- 第一版的登录方式：邮箱（密码或验证码）、GitHub、Google、LinuxDO、通行密钥（passkey）。
- 站点之间的差异（登录方式、注册策略、等级、品牌）全部是站点的后台配置，不写死在代码里。
- 从第一版起记录邀请关系。
- 停用 key、工作区、账户或站点后，下一次调用即被拒绝，多个节点同样成立（[Issue #23](https://github.com/TYCT-tyct/Axiom/issues/23)）。

## 设计

### 不变量

以下规则由数据库约束或代码断言保证，任何操作都不能破坏：

1. 账户、工作区、key 属于同一个站点。账户数据的每张表直接存 `site_id` 和 `account_id`（都不为空），由复合外键与"key → 工作区 → 账户 → 站点"保持一致，写入后不能修改。
2. 成员必须是账户所在站点的用户。
3. 每个账户恰好有一个默认工作区，不能删除；每个账户至少有一个所有者。
4. 个人账户只有它的主人一个成员。
5. 只有主站上的账户能开设站点。
6. 授权的范围必须在操作者所属的站点之内，唯一的例外见下文「授权」。
7. key 能否使用（key、工作区、账户、站点和域名的停用，key 的删除、过期、IP 白名单、可用模型）每次调用都以数据库为准，不以缓存为准。

### 登录与会话

控制台支持邮件找回密码和已登录改密码；两种流程沿用因素版本、审计和邮件 outbox，安全约束与取舍见[决策与理由](#决策与理由)。

- **M1 的范围**：邮箱 + 密码，开启了两步验证的再过验证器 App（TOTP）或恢复码；注册只有邀请码。第三方登录、通行密钥、邮箱验证码、邮箱验证、人机验证和开放注册在 M2。M1 忘记密码仅由运维用命令行重设。
- **邮件找回密码**：控制台提交邮箱和邮件语言（zh/en，默认 en），已有、不存在、停用和别站的邮箱都返回相同的 202 空响应。请求路径只规范化、限流、写站点范围的请求并入队，不查用户、不生成令牌、不发信；数据库或队列故障对所有邮箱都报失败，避免成功文案相同但耗时暴露账户。每个邮箱使用独立于登录的桶（复用站点的邮箱登录阈值，默认 15 分钟 10 次），IP 共用登录的桶；Valkey 故障沿用按节点数分摊的本地计数，成功不返还次数。
- **重置链接**：后台处理最新请求；仅为本站启用的用户用 crypto/rand 生成 256 位令牌，令牌表只存 SHA-256 哈希，绑定用户、factor_version 和最新请求编号；请求提交起 30 分钟到期。新请求提交立即使旧链接失效；后台重试不重复签发。链接取数据库中本站启用的 HTTPS 控制台域名（优先本次请求使用、且仍属于本站的启用域名；它停用或不支持 HTTPS 时才按字典序回退），路径 `/reset-password#token=…`，片段避免令牌进入 HTTP 请求日志或 Referer；不取 Host、转发头或调用方回调地址。邮件含站点名称、中英文正文和到期说明，经 outbox 与令牌同事务落库。这里交付 API 和邮件，消费链接的页面由账户页面能力接入。
- **完成重置**：提交令牌与新密码；无效、过期、已消费、旧请求、别站或因素版本变化都返回同一种无效链接错误。锁定最新请求，再锁用户，条件消费令牌、按注册相同规则校验和 argon2id 哈希密码、提升 factor_version、记录 `user.password_set` 审计、入队密码已变更通知，同一事务成败；失败不消耗令牌。不会自动登录，所有旧会话、恢复码和半完成登录失效；保留 TOTP，下一次登录仍需第二因素；通知明确告知旧恢复码失效，登录后重新生成。
- **邮箱边界**：注册与找回入口同时要求可打印 ASCII、`net/mail.ParseAddress` 成功且解析地址等于原串。历史无效邮箱的改密码返回 422、凭据保持不变，避免通知失败变成 500。运维核验用户身份后，主站用户可用 `axiom user set-password --email 'a@b@c'` 重设（替换为用户现存邮箱，新密码只从标准输入提供，不写入命令参数或 shell 历史）；该命令不依赖 SMTP，也不发送变更通知，运维需另行告知用户。它记录审计、作废旧会话和恢复码，但保留 TOTP；用户用新密码和 TOTP 登录后重新生成恢复码。命令用法见[模块 README 的「命令行」](../../internal/accounts/README.md#命令行)。
  现有命令仅支持主站，且不会修正邮箱；无效邮箱仍不能收找回邮件或在控制台改密码。目前没有通用改邮箱命令或接口，二级站点用户及需要恢复邮件能力的用户，需由运维另行准备并审查邮箱数据修复，核验新邮箱归属及本站唯一性，保留原用户和账户身份；不能用新建用户代替修复。
- **已登录改密码**：需当前密码和新密码、有效控制台会话与 CSRF；开了 TOTP 时要求本次会话达到契约已有的 mfa 等级。按用户的失败桶限制猜当前密码，慢哈希在锁外计算，再锁用户核对会话的因素版本。改动、审计与通知同事务提交；提升 factor_version 后签发同等级的新会话给当前设备，其余会话和旧恢复码失效；已开启 TOTP 时在同一事务补发恢复码，响应中可选的 `recovery_codes` 仅显示一次。通知语言由本次请求指定，默认 en。
- **失败与运维**：SMTP 未配置时找回和改密码都明确返回暂不可用；入队失败回滚。异步签发或 SMTP 失败由 River 重试，最终失败通过 `queue.job_discarded` 日志和 `axiom.pg.queue.discarded_jobs` 指标告警（筛选 `accounts.password_reset`、`mail.send`）；统一的请求说明应提示没收到可稍后重试，不按邮箱提供投递状态。待处理邮箱只放在有 RLS 的请求行，处理完清空；River 参数只有请求 ID，无邮箱或令牌。请求与令牌到期后由 archive 队列每分钟清理，每次每表最多 1000 行；失败积压时恢复后继续清理。没有可用域名或历史地址不合法等永久失败在提交清空邮箱后结束，不重试；临时故障保留至重试或到期清理。错误以 `accounts.password_reset.failed` 记录 job_id、attempt、类别及 SQLSTATE，不记 SQL detail 或原始错误。
- **登录方式**：代码实现各种登录方式；每个站点在后台选择开启哪些，并填写自己的第三方登录应用凭证（二级站点用自己的）。
- **登录域名**：一个站点可以有多个域名，但必须指定一个固定的登录域名。通行密钥和第三方登录的回调都绑定这个域名。
- **不自动合并身份**：同一邮箱的第三方登录不会自动并入已有用户；只能在已登录状态下手动绑定，防止通过第三方账号接管别人的账户。
- **会话存在服务端**：浏览器里只放一个不透明的令牌，存在脚本读不到的 Cookie 里（HttpOnly、Secure、SameSite=Lax）。会改数据的请求另外校验 CSRF 令牌和来源。会话只在签发它的站点和监听面（控制台或管理后台）上有效。会话有空闲超时和最长有效期，时长由站点配置。用户可以查看登录设备、踢掉某台设备、一键退出全部设备（M2）。
- **改了认证因素，旧的全部作废**：密码、TOTP、恢复码合称认证因素。改密码、开启或重置两步验证、重建恢复码之后，这个用户的旧会话、旧恢复码和进行到一半的登录立即失效，不靠逐条吊销。
- **两步验证**：
  - 支持验证器 App（TOTP）和通行密钥，开启时发一组一次性恢复码；
  - 持有敏感权限（权限上有标记）的人必须开启，平台管理员和站长的员工都包括在内；敏感操作只认本次会话做过两步验证，先登录、后开启或后被授权的会话不会因此变强；
  - 普通用户自愿开启，站点也可以要求本站用户必须开启；
  - 开启后，用第三方登录也要过两步验证。
- **注册策略**由站点配置：开放、邀请码、关闭；人机验证；邮箱域名黑白名单；注册频率限制。
- **验证等级**是数据：邮箱已验证、手机已验证、已实名；站点决定要求到哪一级。
- **唯一性**：邮箱和第三方登录身份在同一站点内唯一，不同站点之间互不影响。
- 密码用 argon2id 哈希。这是专为密码设计的慢哈希，数据库泄露后也很难暴力破解。
- **登录前的尝试有上限**：按 IP、邮箱、用户和每次待验证的登录分别计数，次数用尽后等待，不锁账户；上限是站点配置，默认值见模块 README。IP、邮箱和用户的桶在配了 Valkey 时由节点共享，不可用时按节点数等分到进程内；IP 按与网关相同的来源分组计（IPv4 映射地址还原，IPv6 按 /64）。共享键只放邮箱和 IP 的 HMAC；算法、建键前的粗 IP 桶和故障切换见 [kv 的登录设计](../../internal/platform/kv/README.md#每种用途)。

### 账户、成员、工作区

- 每个用户注册时自动获得一个个人账户。
- 企业账户有多个成员。一个用户可以同时属于自己的个人账户和同站点的多个企业账户，在控制台切换。
- 每个账户可以另建多个工作区，例如分开生产和测试环境。每个工作区有自己的 API key、预算和默认设置。个人用户的界面不显示工作区，直到他创建第二个。

### 授权

- **权限**是代码里定义的一件具体能做的事，例如创建 key、查看账单、调整用户余额。每个权限声明自己能在哪些范围上授予，以及是否属于敏感权限。
- **角色**是一组权限，存在后台。系统自带一套默认角色（所有者、管理员、成员、财务、只读、客服）。平台可以定义在所有站点通用的角色；站点可以定义只在本站使用的角色。
- **授予**：把一个角色在某个范围（平台、站点、账户、工作区）上授予一个操作者，并遵守以下规则：
  - 授予的范围必须在操作者所属的站点之内；
  - 唯一的例外：站长账户的成员，可以获得这个账户所开设站点的范围；
  - 平台范围只能授予主站用户，平台管理员就是持有平台范围角色的主站用户；
  - 授予者只能授予自己拥有的权限，范围不能超出自己的范围，所以没人能借授权给自己升级；
  - 授予随成员关系存在：成员被移除或用户注销时，由此产生的授予在同一个事务里撤销。
- 每次授权只交出覆盖本次操作目标的租户范围，不是操作者所有授予的并集。
- 所有接口都调用本模块判断权限。资金操作上限和审批由 `operations` 模块在授权之上再加一层；改动由做改动的模块记入平台的审计日志。
- M1 只有两种授予：注册时成为个人账户的所有者；运维用命令行授予平台角色。

### API key

- **调用 key**用来调模型。可以设置：名称、所属工作区、创建人、花费上限（可按日、周、月在 UTC 零点自动重置；新建的 key 默认带每日花费上限，金额是站点设置，可以修改）、过期时间（只能在创建时设）、可用模型、预设、IP 白名单、速率限制、启用或停用。速率限制随限流器加入，M1 没有。
- **管理 key**是一种操作者，在某个工作区或整个账户上持有角色，不能调用模型。表结构从第一版就有，接口在 M2。它可以：
  - 在自己的范围内创建、修改、删除调用 key，调用 key 的上限不能超过工作区预算。
  - 它不能做这些事：创建管理 key、修改工作区或账户的预算、碰账单和支付。
  - 它必须设置过期时间，最长期限由站点配置。可以设置的项目：名称、范围与角色、过期时间、IP 白名单、启用或停用。
- **格式**：站点配置的前缀 + 256 位的随机串 + 校验位。主站的前缀是 `sk-ax-v1-`。前缀让二级站点使用自己的品牌；校验位能在离线时发现输错的 key。站点改前缀不影响已发出的 key，旧 key 照常显示原前缀。
- **存储**：只存带密钥的哈希（见[安全的「安全基线」](../security.md#安全基线)），并记下哈希密钥的版本，轮换哈希密钥时旧 key 不会全部失效。完整的 key 只在创建时显示一次，界面上显示前缀和末四位。删除是终态，删除后不能恢复。
- **数量与创建频率**：每个账户最多保有多少把未删除的调用 key（默认 100）、每小时最多能创建多少把（默认 50，已删除的也算，所以删掉再建绕不过去）。限额分两层：站点设一个缺省，账户可以有自己的，盖过站点的；每个限额单独往上找，没设的用站点的，站点也没设的用默认。两层都在后台改（站点在站点设置页的「key 限额」，账户在账户页），要 `sites.manage`，填理由，记审计。数量在插入 key 的同一个事务里检查：先锁账户行再数，两个请求同时建最后一把时，后一个要等前一个提交后才数，所以不会都成功；一小时按库的时钟数，不看各节点自己的时间。到数量上限是 409（错误码 `too_many_keys`），删掉一把旧 key 才能再建；超过频率是 429 并带 `Retry-After`（使数量降到限额以下的那把 key 满一小时的时间）；两种响应都写明生效的限额和账户现有的真实数量。调低限额不会删掉已有的 key，超过的账户只是不能再建。
- **改动的审计**：创建、修改、删除各记一条，与改动同一个事务成败。修改的条目记下改了哪几项，以及名称、停用、花费上限、重置周期的改前改后值；可用模型和 IP 白名单只记「变了」——模型最多 256 个、每个 200 字，会超过条目 8 KiB 的上限，而地址是日志不记的个人信息。key 的文本和哈希从不进日志。
- **使用范围**：key 只能在所属站点登记的 API 域名上使用。域名与 key 不属于同一站点时，返回和"key 不存在"完全相同的错误，不透露这个 key 属于别的站点。
- **接入地址**：新建 key 的对话框在 key 还在屏幕上时给出接入指引——三种调用格式的 curl 示例，以及 Claude Code、Codex、Cursor 的配置。地址取本站登记的 API 域名的 origin（快照里的 `Site.APIBase`，控制台读到的 `api_base_url`）：控制台在站点的公开域名上，调用去的是 API 域名，所以这个地址不按控制台的域名拼，也不用请求头里的 Host。OpenAI 形状的客户端用 `origin/v1`，Anthropic 的客户端用 `origin`，它自己接 `/v1/messages`。站点没有启用的 API 域名时省略 `api_base_url`，对话框只显示 key；查询接入地址失败时显示错误和重试，保留明文 key。多个 API 域名优先选择 HTTPS，再按 origin 字典序选择。
- **认出与准入分两步**：认出 key（它是谁、属于哪个工作区和账户）查内存缓存，缓存只存创建后不会变的对应关系；能否使用在准入事务里读数据库判定，预设、可用模型、等级也在这里读出，路由用它们，再由计费在同一事务里预留；事务里只做内存计算和预留，满载排队在事务之外，不占数据库连接。所以停用不需要通知缓存，任何节点上的下一次调用都会被拒绝。已经通过准入的调用照常完成，与计费"请求一旦开始不中途掐断"一致。

### 限额怎么生效

- 一次调用要同时满足所有适用的限制，以最严的为准：账户余额、工作区预算、key 的花费上限、等级和 key 上的速率限制。
- 工作区预算和 key 的花费上限都可以按日、周、月重置，也可以设不重置的总额；同时设置时各自生效，取最严。
- 花费计数和预留都由 `billing` 管理。本模块打开准入事务，在其中读出 key 的花费上限、工作区预算和账户的等级，作为参数交给计费；计费在同一个事务里连同在途预留一起检查（见[计费的「预留与结算」](billing.md#预留与结算)）。

### 等级

- 每个站点定义自己的等级。等级是一组账户层级的默认值：速率限制、可用的模型和预设。加价不在这里：给某个等级用的加价是计费的一条定价规则，人群指定为这个等级，见[计费的「定价」](billing.md#定价)；等级表本身不存加价。
- 账户进入某个等级的方式：手动指定，或按后台配置的规则自动升级，例如累计充值达到某个数额。
- **默认等级**：每个站点指定一个默认等级。新账户注册时进入站点当时的默认等级；以后改默认等级不影响已有账户。未登录的访客看到的价格也按默认等级算（见[前端的「页面清单」](../frontend.md#页面清单)）。

### 站点

- 主站、二级站点、站长和收款方式之间的关系，见[术语与核心概念](../glossary.md#关键关系)中的「主站也是站点」和「二级站点由主站上的一个账户开设」。
- **站点的配置**：
  - 域名：可以有多个，每个标明用途（控制台、API、管理后台），证书自动签发；
  - 品牌和主题、登录方式与第三方登录应用、注册策略、等级、key 前缀；
  - 收款渠道（二级站点用站长自己的商户账户）、数据留存的默认值、状态。
- **配置项由负责的模块各自声明**，例如收款渠道由 `payments` 声明，登录方式由本模块声明。第三方登录应用和收款渠道的密钥按[安全基线](../security.md#安全基线)信封加密存储。
- **只认登记过的域名**：请求按域名认出站点，只接受站点登记过的域名，其他一律拒绝。生成链接一律用站点配置的域名，不用请求头里的 Host。
- **站长员工按角色分工**：例如客服只能查看用户、财务可以调整余额，角色的范围限定在这个站点。

### 给用户的邮件

- **归本模块**：收件人（用户和账户成员）、模板、站点品牌和多语言都在这里。找回密码与密码变更通知已接入（见[登录与会话](#登录与会话)），验证码与其余提醒随各自功能接入。投递在 `platform`：SMTP 发送、消息组装、按收件人的限流和重试都在 [platform 的 mail](../../internal/platform/mail/README.md)，这里只决定收件人、模板和正文。记录与告警的通知渠道是发给运维的（见[记录与告警的「通知渠道」](observability.md#通知渠道)），与这里分开。
- **谁触发**：验证码、找回密码、异地登录由本模块触发；余额不足、充值到账由 billing、payments 触发；key 异常花费由 observability 按调用记录检测后触发（见[安全的「防滥用」](../security.md#防滥用)），key 泄露由密钥扫描发现后触发；模型切换与迁移由 catalog 触发（M1 之后，见[模型的生命周期](catalog.md#模型的生命周期)）。其他模块把事件和值交给本模块，不各自拼邮件。
- **写法**：只链到站点登记过的域名，不信任 Host 和转发头；正文不插入用户可控的内容；链接带一次性令牌，用完即失效。
- **送达**：验证码、找回密码这类登录必需的邮件，发送失败要让用户重试并告警；其余提醒异步发送、失败重试，不影响调用和计费。用户在设置里关掉的提醒类型不发；模型切换与迁移的通知必须送达，不能关闭（见[前端的「通知」](../frontend.md#页面清单)）。
- **下层怎么触发**：catalog 在本模块下面，不能引用本模块；它声明一个发送通知的接口，由 `cmd/axiom` 接到本模块（见[总体架构的规则 5](../architecture.md#模块边界规则)）。billing、payments 这些在本模块上面的模块可以直接调用。

### 配置链

- **范围从上到下**：平台 → 站点 → 等级 → 账户 → 工作区 → API key。等级是一组账户层级的默认值；账户上显式设置的值优先于等级。
- **每项配置由负责它的模块在代码里声明**：
  - 默认值；
  - 允许在哪几层设置；
  - 下层能修改的界限；
  - 合并方式，共三种：
    - 默认值类：最具体的那层生效；
    - 限额类：各层同时生效，取最严；
    - 名单类：如可用模型、IP 白名单，各层取交集。
- **存储与生效**：各层设置的值存在本模块，保存时校验并记审计；生效值算好后放进核心的内存快照。
- M1 不做通用的配置链：key 的设置存在 key 上，站点的安全与会话参数存在站点设置里，默认值在代码里。

### 停用与注销

- 管理接口分别用账户 `/suspension` 暂停/恢复调用、用户 `/sign-in` 禁用/启用登录，均要求 MFA、`users.manage`、幂等键和原因；平台授予 `/platform-grants/{role}` 撤销/恢复要求 `platform_grants.manage`，列表接口给出各角色的最新授予状态。每个状态变更同事务记审计；相同状态不重复写审计。
- 站点、域名、用户、账户、工作区、key 都能单独停用。停用立即生效：每次调用在准入事务里读数据库核对 key、工作区、账户、站点和域名的状态，与缓存无关。账户停用只暂停调用，控制台登录仍可用；其余条件有效的 key 在准入返回 403。停用用户只阻止登录并吊销全部会话，恢复后需重新登录；要让 key 不能用，停用账户或 key。
- 本模块的停用是管理员的开关；计费的「余额不足」和「暂停」是另一回事，见[计费的「风控状态」](billing.md#风控状态)，两者在同一个准入事务里检查。
- **注销用户**：
  - 抹去个人信息，财务记录保留，因为账本不可修改；
  - 剩余余额按站点的退款政策处理（见[计费](billing.md#额度批次)）；
  - 对话内容和调用记录按[记录与告警](observability.md#待定问题)中的规则处理；
  - 注销完成后，同一邮箱可以重新注册，得到的是一个全新的用户。
- 账户的唯一所有者、站长账户的所有者不能直接注销：前者要先转让所有权，后者还要先停用自己的站点。

### 邀请关系

- 每个用户有自己的邀请码和邀请链接。通过它们注册时，记下邀请人（用户）。
- 邀请人在注册那一刻确定，之后不能修改。邀请人必须是同站点的另一个已有用户，不能自己邀请自己。

## 决策与理由

E4-6/7/8 与充值权限依据同一[负责人授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)实现，新增接口、账户安全计数及权限的决定如下：

| 决策 | 理由 |
|---|---|
| 登录阈值用独立的站点 `/login-limits` 接口整体替换，所有响应成员可选 | 复用现有五列和默认值；扩展通用设置会使旧页面清空新阈值。节点 30 秒内重载，当前节点立即刷新 |
| 账户暂停调用与用户禁用登录分别改各自的 status | 复用现有准入与会话校验，不增加热路径查询；已知且其他条件有效的 key 遇到账户暂停返回 403，其余无效 key 仍为 401。账户暂停保留控制台登录，以便充值和申诉 |
| 用户禁用时在用户行锁内吊销全部会话，恢复只允许重新登录 | 单靠 status 会让暂停期间没使用的会话在恢复后复活；不递增因素版本，保留恢复码的有效性 |
| 平台授予撤销为终态，恢复插入新授予；按用户锁串行，恢复必须有历史授予且权限为操作者现有权限的子集 | 不清除 revoked_at，不破坏现有 RLS 的终态保证；拒绝用恢复接口创造新角色或扩权 |
| 安全事件写现有审计日志，只含站点、用户、会话及请求 ID 和固定分类 | 不存邮箱、IP、User-Agent、密码、验证码、令牌；失败在独立事务提交，不随认证失败回滚。成功注册、密码登录及 MFA 完成与其状态同事务记录 |
| 每站点一行安全计数，保存当前 UTC 分钟与尚未采样的完整窗口峰值；后台每站点每分钟至多一条信号 | 请求不持久化平台信号，不争用全局消费锁；固定内存保留完整窗口峰值，避免窗口复位吞掉攻击。积压时合并峰值而非无限保存历史；消费时逐条评估完整样本，后续恢复不能抹掉首通知。只计猜凭证，限流拒绝、表单错误和正常会话失效不计 |
| 新权限由迁移写入角色的 additional_permissions，旧 permissions 投影不变；新快照合并两列并忽略未知名字 | 仅修改新版本加载器不能保护仍运行的旧二进制。新增列使旧查询不见新名字，避免迁移先行造成全站快照过期；迁移权限拼写由测试核对。待旧节点退场前不合并两列 |
| `balance.top_up` 给 owner、admin、finance，viewer 只读 | 财务可以买额度，普通成员和观察者不能发起支付；getOrder 与余额仍用 balance.view。listPaymentMethods 会创建报价，故也属于四个受保护操作 |
| 账户暂停用 403 与 OpenRouter 错误外壳 | 2026-10-29 核实 [OpenRouter 官方错误文档](https://github.com/OpenRouterTeam/docs/blob/main/api_reference/errors-and-debugging.mdx)：403 用于权限拒绝，Chat/Responses 的 error.code 为 HTTP 数字，Messages 用 permission_error；只为新增暂停拒绝使用此形状，不改既有错误码 |


邮件找回与改密码按[负责人授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)落地已有设计。记录原文：“所以，按已有设计落地的数据模型、对外接口、数据保存规则和计费口径，由编排者决定，并写进领域文档的「决策与理由」；独立评审照常进行。”本次覆盖请求重置、完成重置、已登录改密码三个控制台操作，`password_reset_requests`、`password_reset_tokens` 两张表及到期清理规则；以下保留各项决定的理由。部署、花钱、对外发消息和法律文本仍由负责人拍板。

| 决策 | 理由 |
|---|---|
| 找回密码采用持久化异步签发，不采用同步查用户再发信或随机延时 | 同步方案会因数据库与 outbox 的额外工作暴露时序；固定或随机延时不能覆盖故障、负载和排队。请求统一入队使账户存在性完全不参与响应路径，代价是多一张站点请求表，以及签发与过期清理任务 |
| 找回请求按 IP 与邮箱分别限流，邮箱复用可调的站点登录阈值并独立计数 | IP 桶限制广撒邮箱的洪泛，邮箱桶限制收件人轰炸；共享计数与故障等分避免多节点扩大攻击次数。复用现有设置而非新增硬编码上限，登录成功也不会返还找回次数 |
| 重置链接只取数据库中的本站 HTTPS 控制台域名，令牌放 URL 片段 | 防止 Host、转发头或调用方返回地址把凭证带到攻击者域名；片段不随普通 HTTP 请求或 Referer 发送，减少日志泄露 |
| 已登录改密码仍验证当前密码，TOTP 开启时要求 mfa 会话 | 单独偷到 Cookie 或密码不能绕过已开启的第二因素；锁内再核对因素版本，阻止旧密码已验证的并发操作在重置后生效 |
| 令牌 256 位随机、只存哈希、30 分钟过期，并绑定最新请求及因素版本 | 超过 128 位底线抵抗猜测；哈希减少数据库泄露后的可用凭证。到期删除请求和令牌，避免永久保留邮箱摘要；请求行锁与用户锁串行化重发、消费及因素变化，条件更新保证一次性；复用注册校验和哈希避免密码策略分叉。30 分钟由开发者按任务卡建议选择，兼顾收信延迟和暴露窗口 |
| 重置不自动登录，改密码保留当前设备的新会话，审计与通知必须同事务 | 邮箱证明不能代替 TOTP；通知入队失败时回滚，避免无通知的凭证变化。已登录改密码补发恢复码；邮箱重置只告知登录后重建，避免邮箱单独持有者拿到可替代 TOTP 的码。参考 new-api 的 `controller/misc.go:254–330`、`controller/user.go`，sub2api 的 `backend/internal/handler/auth_handler.go:590–680`、`backend/internal/service/auth_service.go:1534–1665`（2026-10-28，只读本地参考）：两者统一文案但在请求中分支查用户；Axiom 移到持久队列防时序枚举。new-api 返回新生成密码，sub2api 先消费缓存令牌再写密码；Axiom 让用户选择新密码，并把消费与凭证更新放进同一数据库事务，避免部分成功 |
| OpenRouter 只对公开资料能验证的行为作对照 | 2026-10-28 查证 [登录页](https://openrouter.ai/sign-in)、[支持页](https://openrouter.ai/support) 和 [条款 §3.1](https://openrouter.ai/terms)：支持账户密码，公开文档未说明重置令牌、TTL、撤销会话或通知的保证，登录表单由客户端加载，无法据此验证找回细节；这些不写成 OpenRouter 的承诺。Axiom 按任务卡明定可测试的不变量，原因是自有认证与多租户隔离需要明确保证 |
| 账户下设工作区，每个账户自带默认工作区 | 负责人同意。企业要按项目或环境分开 key 和预算。OpenRouter 的 key 都属于工作区，未指定时进默认工作区，预算可设在工作区上（OpenRouter 文档《Workspaces》《Create a new API key》，2026-10）。现在加只多一张表，以后再插这一层要迁移所有 key。OpenRouter 的默认工作区可以删，删后未归属的 key 全部失效；我们不允许删，避免一次误操作停掉所有 key |
| 统一授权：权限在代码，角色是数据，按范围授予 | 负责人同意。平台管理员、站长的员工、企业财务、管理 key、运营 agent 都用同一套规则，不为每类操作者另写权限逻辑 |
| 授予只能是授予者权限的子集 | 杜绝通过授权给自己或别人升级权限 |
| 站长在主站登录管理站点；一个账户可开多个站点 | 负责人同意。站长只需一个身份，员工按角色分工；经营多个品牌的站长不用开多个账户 |
| 二级站点由站长自己收款 | 负责人决定。Axiom 不经手终端用户的钱，不需要做提现、分账，也不涉及支付牌照 |
| 手机号和微信登录暂不做 | 负责人决定。它们需要公司主体和备案网站才能申请 |
| 会话存在服务端，不用 JWT | 可以立即踢掉设备、吊销会话；JWT 签发后在过期前无法收回 |
| 不按邮箱自动合并第三方身份 | 防止有人用同一邮箱注册第三方账号，接管别人的账户 |
| 管理 key 与调用 key 分开；管理 key 不能创建管理 key、不能改预算 | 管理 key 不能调模型这一点与 OpenRouter 一致（OpenRouter 文档《Management API Keys》，2026-10）。泄露一把管理 key，损失也限制在它的范围和预算之内 |
| key 的花费上限可按日、周、月重置；过期时间只能在创建时设 | 与 OpenRouter 一致（OpenRouter 文档《Create a new API key》《API Key Audit》，2026-10） |
| key 只能在所属站点的域名上使用 | 负责人同意。避免"A 站的 key 在 B 站用，按哪个站计价"的歧义 |
| 限额取最严，配置分三种合并方式 | 默认值、限额、名单的语义本来就不同，混用一种规则必然出错 |
| 每个账户的 key 数在插入 key 的同一个事务里、取账户行锁之后数 | 先数后插在并发下会超上限：两个创建同时读到"还剩一个"就都插入。锁和插入在同一个事务里，计数必然看到前一个提交，不需要唯一约束（每把 key 本来就不同，约束不上）或多节点的协调。new-api（`controller/token.go:326`）和 sub2api（`api_key_service.go:442`）都是先数后插 |
| 每小时创建数按库的时钟数，含已删除的 key | 窗口起点和建 key 的时间要出自同一个时钟，各节点的时钟有差就会让同一小时超限额。删除不返还次数与 sub2api 一致（它按固定窗口累计创建次数，删除不返还）；它的计数在缓存里、缓存出错就放行，这里的数据在库里，不放行 |
| key 限额分站点、账户两层，账户的盖过站点的，各有自己的接口 | 任务卡要求后台可按账户调整。站点的限额不放进整体替换的站点设置，免得发布前打开的旧页面把它抹掉 |
| 修改 key 的审计记改了什么，可用模型和 IP 白名单只记「变了」 | 模型列表最多 256 个、每个 200 字，写进去会超过条目 8 KiB 的上限；地址是日志不记的个人信息（[平台的「审计日志」](../../internal/platform/README.md#审计日志)） |
| 从第一版起记录邀请关系，且不能修改 | 负责人同意。邀请关系只能在注册时记下，事后补不回来；不能修改才能防止刷返利 |
| 租户表直接存 `site_id` 和 `account_id`，用复合外键保持一致 | 开发者按负责人授权决定（Issue #23）。行级安全的策略只看本行的列，查询不用连表；只存在上层、靠推导的话，每条策略都要连到上层的表，而上层的表本身也受行级安全约束。复合外键让存下的两列不可能与"key → 工作区 → 账户 → 站点"不一致 |
| key 能否使用每次调用在准入事务里读库；缓存只存不会变的对应关系 | 开发者按负责人授权决定（Issue #23 评论，2026-10-14）。缓存里存状态再靠失效来停用，两轮反方审查都找到了反例：并发的缓存填充交出旧状态、提交确认丢失、多节点之间的通知断线。读库的代价是准入事务里多一条查询，计入[性能](../performance.md#延迟预算)准入那一格 |
| M1 登录只有邮箱 + 密码 + TOTP，注册只有邀请码 | 开发者按负责人授权决定（Issue #23）。M1 是负责人自用，这些足够完成注册、登录、开启两步验证的验收；第三方登录、通行密钥、找回密码邮件都要外部服务或发邮件，放到 M2 |
| 内部 ID 用 UUIDv7，对外显示带类型前缀的 TypeID（如 `acct_…`） | 开发者按负责人授权决定。UUIDv7 按时间递增，索引友好；对外的前缀让人一眼看出是什么 ID，误把工作区 ID 填成 key ID 时直接报错。ID 暴露创建时间，可以接受 |
| 主站的 key 前缀是 `sk-ax-v1-` | 开发者按负责人授权决定。与 OpenRouter 的 `sk-or-v1-` 同形，用户一眼能认出；带版本号，以后改格式时新旧 key 能区分 |
| 新账户进入站点当时的默认等级，访客看到的也是它的价 | 负责人在对话中授权开发者按推荐决定（2026-10-13，见[前端的「决策与理由」](../frontend.md#决策与理由)）。访客注册后付的就是看到的价；改默认等级只影响以后注册的账户，已有账户的价格不会被意外改动 |
| 会话与两步验证的接口在控制台和管理两份契约里各一套，注册不自动登录 | 会话只在签发它的监听面有效，管理后台的人要能在管理后台里开启两步验证，不必先去控制台。注册成功后页面用同一组凭证调登录：两个操作的限次和 CSRF 起点各守各的规则。否决的做法：注册同时签发会话：注册多一种会话来源；两个面共用一套路径：管理接口要挂到公网 |
| key 的设置用 `PUT` 整体替换，创建后只能改设置不能改过期时间；没写的限制就是不限 | 与「过期时间只能在创建时设」一致；Go 生成的类型分不清「没写」和「写成 null」，整体替换没有这个歧义。否决的做法：带 `null` 的 `PATCH`：要引入可空类型 |
| 给用户的邮件归 accounts：收件人、模板、站点品牌在这里；投递是 `platform` 的通用 SMTP（经 River 队列），生产邮件服务商在上线邮件找回前配置验证 | 邮件是登录和账户的一部分（验证码、异地登录），模板和语言按站点；一个地方拼邮件，各模块只交触发和值。否决的做法：新建一个通知模块：它只为用户邮件存在，却要横跨所有模块；各模块自己发：模板、品牌、退订和失败重试各写一遍 |

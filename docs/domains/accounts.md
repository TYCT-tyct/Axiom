# 账户与租户

谁能登录、钱和 key 归谁、谁能做什么、站点怎么配置。对应代码模块 `accounts`，表结构、查找与缓存、接口和测试见[模块 README](../../internal/accounts/README.md)。概念之间的关系见[术语与核心概念](../glossary.md)，这里只写本模块的要求和设计。

## 要求

- 用户、账户按站点隔离；C 类企业团队和 D 类二级站点的数据结构从第一版起具备（见[产品需求](../product.md#用户与市场)）。
- 第一版的登录方式：邮箱（密码或验证码）、GitHub、Google、LinuxDO、通行密钥（passkey）。
- 账户可以自带供应商 key（BYOK）：请求优先走自己的 key，失败后回落到 Axiom 的端点，除非这把 key 明确不许回落。key 保存后不再显示，也不进日志；供应商拒绝认证的 key 被标记并跳过；控制台可以添加、测试、停用和删除。
- 站点之间的差异（登录方式、注册策略、等级、品牌）全部是站点的后台配置，不写死在代码里。
- 从第一版起记录邀请关系。
- 站点发布服务条款和隐私政策时，注册必须接受当前版本；已登录用户在新版本发布后先接受才能继续。
- 停用 key、工作区、账户或站点后，下一次调用即被拒绝，多个节点同样成立（[Issue #23](https://github.com/TYCT-tyct/Axiom/issues/23)）。

## 设计

账户还持有命名请求配置，由控制台的 key 查看/管理权限或管理 key 进行 CRUD；存储与审计见[accounts README](../../internal/accounts/README.md#命名请求配置)，合并与调用行为见[路由](routing.md#命名预设)。配置不能替代调用 key 的模型授权。路由预设是另一件事：它是 key 的端点筛选、排序和最高单价，存 routing 的表，见[路由](routing.md#路由预设)；命名请求配置不是路由预设。


### 不变量

以下规则由数据库约束或代码断言保证，任何操作都不能破坏：

1. 账户、工作区、key 属于同一个站点。账户数据的每张表直接存 `site_id` 和 `account_id`（都不为空），由复合外键与"key → 工作区 → 账户 → 站点"保持一致，写入后不能修改。
2. 成员必须是账户所在站点的用户。
3. 每个账户恰好有一个默认工作区，不能删除；每个账户至少有一个所有者。
4. 个人账户只有它的主人一个成员。
5. 只有主站上的账户能开设站点。
6. 授权的范围必须在操作者所属的站点之内，唯一的例外见下文「授权」。
7. key 能否使用（key、工作区、账户、站点和域名的停用，key 的删除、过期、IP 白名单、可用模型）每次调用都以数据库为准，不以缓存为准。
8. 站点的 `logo_hash` 要么为空，要么指向本站点 `site_logos` 的一行；一个公开的 logo 地址永远返回同样的字节。前者由外键保证，后者由地址里的 SHA-256 保证。

### 登录与会话

控制台支持邮件找回密码、已登录改密码、查看和控制登录设备、更换两步验证的 TOTP；这些流程沿用因素版本和审计，密码流程还经邮件 outbox，安全约束与取舍见[决策与理由](#决策与理由)。

- **范围**：邮箱 + 密码，开启了两步验证的再过验证器 App（TOTP）、恢复码或通行密钥；注册有邀请码和开放（邮箱验证）两种，开放注册默认关闭。GitHub、Google、LinuxDO 第三方登录和通行密钥已实现；邮箱验证码仍在 M2。
- **注册方式**：站点在 `sites.registration` 选 `invite`、`closed` 或 `open`；默认 `invite`，开放注册默认关闭。邀请码流程不变；开放注册只在这一个模式里生效。
- **开放注册**：站点开启后，页面在人机校验开启时先解证明，再提交邮箱和语言。服务端在库里读注册模式和默认等级，校验邮箱、域名名单和工作量证明，然后按（站点、规范化邮箱）写一条待验证请求；这条请求不保存口令，同一邮箱再次请求会替换前一条并让旧链接失效。除了格式错误、域名不允许、人机校验失败和频率超限，提交一律返回 202 `verification_sent`，不告诉匿名调用者邮箱是否已注册。点击链接前没有用户、账户或工作区。
- **验证链接**：后台用 crypto/rand 生成 256 位令牌，只存 SHA-256 哈希；链接是 `https://<控制台域名>/console/verify-email#token=…`，绑定待验证请求、站点和控制台域名，24 小时过期且只能使用一次。点击时页面要求设置密码；服务端先花一次该 IP 的认证预算，按令牌查到请求后先做未过期和域名名单的廉价检查，再在锁外算 argon2id，最后在站点范围锁请求，重查未过期、令牌哈希、域名名单和邮箱未被占用；不重查注册模式，已发出的 24 小时链接仍可用；站点停用后链接失效。创建用户、个人账户、默认工作区、余额行和所有者成员关系，写入 `email_verified_at`，删除待验证请求并记 `security.registration` 同事务；任一步失败整体回滚。注册不自动登录，页面带用户去登录。未知、过期、已使用或别站的令牌统一返回 422 `invalid_verification`；链接有效但邮箱已被注册返回 409 `email_taken`。
- **注册同意**：站点用管理接口发布版本化的服务条款和隐私政策，正文是站长的纯文本，代码不内置、不改写、不预置任何真实条款。注册必须提交当前版本的 `(kind, version)`：邀请码在 `register` 提交，开放注册在 `verify-email` 提交。服务端在建用户的事务里重读当前版本，缺失、过期或多出都返回 403 `consent_required`，用户、账户、工作区和接受记录同成同败；站点没有文档时不要求。已登录用户每次认证在会话事务里比较当前版本与最新接受版本；未接受时 `getSession` 返回 `consent.required`，`acceptLegalDocuments` 可以接受，其他控制台操作返回 403 `consent_required`。接受记录按 `(user, kind, version)` 唯一，重复接受不改首次时间。文档按 `(site, kind, version)` 追加，正文不改不删，新版本是下一个编号；管理接口是独立的 `/api/admin/v1/sites/{site_id}/legal-documents`，按 `(kind, version)` 游标分页读版本、发布新版本，发布要 MFA、`sites.manage`、CSRF、幂等键和理由，审计只记类型、版本、长度和 SHA-256，不记正文。控制台的 `GET /api/console/v1/legal` 无需会话，返回每种类型的当前版本。
- **人机校验**：自托管的工作量证明，不依赖第三方服务。页面在浏览器里找十进制 nonce，使 SHA-256(`axiom-registration-v1`、换行、站点 TypeID、换行、规范化邮箱、换行、nonce) 的前导零位数达到站点设定值；服务端用同样的输入重算。默认 18 位，站点可设 12 到 24 位。证明与站点和邮箱绑定，换一个邮箱即失效；服务端不保存挑战，也没有可重放的挑战表。
- **域名与频率**：站点的邮箱域名 allow/deny 列表在写入时转小写、去空白、去重，每项最多 100 个；一项覆盖它的子域名，deny 优先，allow 为空表示不限。一次注册同时计入已有的按 IP 桶和新增的按（站点、邮箱域名）桶；配了 Valkey 时共享计数，不可用时按节点数分摊到进程内。成功不返还次数。管理接口在同一事务写模式和设置并记 `site_registration.update`；审计只存域名名单的数量和 SHA-256，不复制整份名单，100 项的合法配置也不会超过审计条目上限。
- **邮件找回密码**：控制台提交邮箱和邮件语言（zh/en，默认 en），已有、不存在、停用和别站的邮箱都返回相同的 202 空响应。请求路径只规范化、限流、写站点范围的请求并入队，不查用户、不生成令牌、不发信；数据库或队列故障对所有邮箱都报失败，避免成功文案相同但耗时暴露账户。每个邮箱使用独立于登录的桶（复用站点的邮箱登录阈值，默认 15 分钟 10 次），IP 共用登录的桶；Valkey 故障沿用按节点数分摊的本地计数，成功不返还次数。
- **重置链接**：后台处理最新请求；仅为本站启用的用户用 crypto/rand 生成 256 位令牌，令牌表只存 SHA-256 哈希，绑定用户、factor_version 和最新请求编号；请求提交起 30 分钟到期。新请求提交立即使旧链接失效；后台重试不重复签发。链接取数据库中本站启用的 HTTPS 控制台域名（优先本次请求使用、且仍属于本站的启用域名；它停用或不支持 HTTPS 时才按字典序回退），路径 `/console/reset-password#token=…`，片段避免令牌进入 HTTP 请求日志或 Referer；不取 Host、转发头或调用方回调地址。邮件含站点名称、中英文正文和到期说明，经 outbox 与令牌同事务落库。这里交付 API 和邮件，消费链接的页面由账户页面能力接入。
- **完成重置**：提交令牌与新密码；无效、过期、已消费、旧请求、别站或因素版本变化都返回同一种无效链接错误。锁定最新请求，再锁用户，条件消费令牌、按注册相同规则校验和 argon2id 哈希密码、提升 factor_version、记录 `user.password_set` 审计、入队不可关闭的密码已变更通知，同一事务成败；失败不消耗令牌。不会自动登录，所有旧会话、恢复码和半完成登录失效；保留 TOTP，下一次登录仍需第二因素；通知明确告知旧恢复码失效，登录后重新生成。
- **邮箱边界**：注册与找回入口同时要求可打印 ASCII、`net/mail.ParseAddress` 成功且解析地址等于原串。历史无效邮箱的改密码返回 422、凭据保持不变，避免通知失败变成 500。运维核验用户身份后，主站用户可用 `axiom user set-password --email 'a@b@c'` 重设（替换为用户现存邮箱，新密码只从标准输入提供，不写入命令参数或 shell 历史）；该命令不依赖 SMTP，也不发送变更通知，运维需另行告知用户。它记录审计、作废旧会话和恢复码，但保留 TOTP；用户用新密码和 TOTP 登录后重新生成恢复码。命令用法见[模块 README 的「命令行」](../../internal/accounts/README.md#命令行)。
  现有命令仅支持主站，且不会修正邮箱；无效邮箱仍不能收找回邮件或在控制台改密码。目前没有通用改邮箱命令或接口，二级站点用户及需要恢复邮件能力的用户，需由运维另行准备并审查邮箱数据修复，核验新邮箱归属及本站唯一性，保留原用户和账户身份；不能用新建用户代替修复。
- **已登录改密码**：需当前密码和新密码、有效控制台会话与 CSRF；开了第二因素（TOTP 或通行密钥）时要求本次会话达到契约已有的 mfa 等级。按用户的失败桶限制猜当前密码，慢哈希在锁外计算，再锁用户核对会话的因素版本。改动、审计与不可关闭的密码变更邮件同事务提交；提升 factor_version 后签发同等级的新会话给当前设备，其余会话和旧恢复码失效；已开启 TOTP 时在同一事务补发恢复码，响应中可选的 `recovery_codes` 仅显示一次。通知语言由本次请求指定，默认 en。
- **失败与运维**：SMTP 未配置时找回和改密码都明确返回暂不可用；入队失败回滚。异步签发或 SMTP 失败由 River 重试，最终失败通过 `queue.job_discarded` 日志和 `axiom.pg.queue.discarded_jobs` 指标告警（筛选 `accounts.password_reset`、`mail.send`）；统一的请求说明应提示没收到可稍后重试，不按邮箱提供投递状态。待处理邮箱只放在有 RLS 的请求行，处理完清空；River 参数只有请求 ID，无邮箱或令牌。请求与令牌到期后由 archive 队列每分钟清理，每次每表最多 1000 行；失败积压时恢复后继续清理。没有可用域名或历史地址不合法等永久失败在提交清空邮箱后结束，不重试；临时故障保留至重试或到期清理。错误以 `accounts.password_reset.failed` 记录 job_id、attempt、类别及 SQLSTATE，不记 SQL detail 或原始错误。
- **登录方式**：邮箱 + 密码始终可用；GitHub、Google、LinuxDO 由每个站点在后台单独开启，填入自己的 OAuth 应用 client ID/secret 后生效，未配置即关闭（二级站点用自己的应用）。secret 与 TOTP 密钥一样信封加密存放，`site_oauth_providers` 只保存密文。
- **第三方登录流程**：每次发起生成一次性 state（库里只存 SHA-256，10 分钟过期）、一个同时写入 `__Host-` Cookie 的随机 nonce 和 PKCE verifier；回调必须在发起它的浏览器里带回这个 nonce，state 才被消费，否则别人发来的完整回调 URL 不能在受害者浏览器里把受害者登进攻击者的账户。三家都用 S256 PKCE（GitHub OAuth App 自 2025 年 7 月起支持），并叠加一次性 state、浏览器 nonce 和固定回调域名。回调只接受站点登录域名，只按 provider 的 subject（GitHub 数字 id、Google `sub`、LinuxDO `id`）查找已绑定身份；未绑定的 subject 返回 `account_not_linked`，不会注册新用户，也不会按邮箱并入已有账户。登录同样计入每 IP 的登录预算。回调的 303 目标都在控制台挂载点 `/console` 下：成功回 `/console/`，绑定回 `/console/security`，失败回 `/console/sign-in?oauth=failed`。
- **登录域名**：一个站点可以有多个控制台域名，但第三方登录和通行密钥必须指定其中一个作为登录域名；未开启这两项时可以不设。登录域名必须是本站已启用的控制台域名；第一次设置可以在已保存 provider 之后，但一旦已有通行密钥、第三方身份或已配置 provider，就不能再移动它（否则回调地址和 RP ID 会漂移）。其他控制台域名上发起第三方登录或通行密钥会被拒绝，登录页把访客带到登录域名。
- **通行密钥**：WebAuthn，RP ID 是登录域名、origin 是它登记的源；注册、登录和第二因素都要求 user verification，注册选项要求 discoverable（resident key）。通行密钥既是独立登录方式（discoverable，无需先输邮箱），也是密码之后的第二因素：用户一旦有通行密钥，**登录域名上**的密码登录只得到待验证会话，必须再过 TOTP、恢复码或通行密钥之一；其他控制台域名跑不了 WebAuthn 仪式，只有通行密钥、没有 TOTP 的用户在那里会被拒绝并引导到登录域名，同时有 TOTP 的用户可以在那里用 TOTP 完成，管理后台则保留可用的密码会话（其中敏感操作仍需 TOTP，故管理后台不把通行密钥算作已开启的两步验证）。已有通行密钥的用户从密码会话或管理后台开启 TOTP 时，必须先在本次会话证明通行密钥；否则只拿到密码的人可以新增一个管理后台能完成的第二因素。新旧节点混跑时，旧节点不执行这项检查，但数据库触发器会拒绝它在同一用户上新增 TOTP，直到新节点用事务级证明标记放行。每个用户最多 10 个；注册和删除都要当前密码，并按用户的失败桶计错，已开启第二因素时还要求本次会话是 `mfa`；删除后其他会话全部失效，TOTP 开着时返回新的恢复码。站点关闭通行密钥前，用户须先删完自己的通行密钥，否则密码登录会卡在页面已无法提供的第二因素上。注册流程把发起时的 RP ID/origin 记在一次性仪式里，落库前在站点锁下重读开关和登录域名：管理员在仪式进行中关闭通行密钥或移动登录域名时，旧页面无法把凭证写进新配置。存储的签名计数器只增不减；回退的断言直接拒绝，同一计数器的并发断言只有一个能写入，计数器从非零回到零也不会被接受。
- **不自动合并身份**：第三方身份只能在已登录状态下手动绑定，绑定回调必须回到发起它的同一会话，防 CSRF 和状态串用；同一 provider 每个用户只能绑一个身份，同一 subject 全站只能属于一个用户。绑定和解绑都要提升 factor_version、TOTP 开着时重发恢复码并记审计（`user.identity_link` / `user.identity_unlink`），不按邮箱匹配或合并；绑定流程的码用会话令牌派生的密钥加密后存在新会话行上（不占密钥环版本），撤销会话的触发器清空，控制台读一次即清。
- **会话存在服务端**：浏览器里只放一个不透明的令牌，存在脚本读不到的 Cookie 里（HttpOnly、Secure、SameSite=Lax）。会改数据的请求另外校验 CSRF 令牌和来源。会话只在签发它的站点和监听面（控制台或管理后台）上有效。会话有空闲超时和最长有效期，时长由站点配置。已登录用户可以在控制台查看登录设备、踢掉某一台、一键退出全部其他设备；控制台 API 已交付，页面随 #317 接入。
- **设备列表与撤销**：列表只含当前用户在本站控制台的有效会话（未撤销、未过期、未超空闲、因素版本当前），按创建时间倒序最多 100 条，标出当前设备，给出创建时间、最后使用时间、IP 分组和客户端摘要；待验证登录、管理后台会话和因素变更后已失效的会话不在其中。IP 只返回登录预算所用的分组（IPv4 原样、IPv6 取其 /64），客户端只返回从 User-Agent 固定记号得出的摘要，原始值不回显。撤销单台只接受列表里能看到的、非当前会话的 ID；一键退出结束全部其他控制台会话，连待验证登录一起结束，但不越过监听面去撤销管理后台会话。撤销不改因素版本，只把会话标为已撤销。
- **更换两步验证的 TOTP**：已通过两步验证的控制台会话要再证明一次当前因素——当前 TOTP 码或一枚未用恢复码——并提交新密钥里的一个码，才用新密钥替换旧密钥；因素未开启返回 409。旧的 TOTP、全部旧恢复码和其他会话随因素版本提升失效，当前设备拿到新的恢复码和 `mfa` 会话。两个码任一错误都计入每用户的失败次数；当前因素码的消费、换密钥、审计和新会话同一事务，失败时旧因素和恢复码保持可用。丢失验证器和恢复码的用户仍由运维用命令行 `reset-mfa` 重置。
- **改了认证因素，旧的全部作废**：密码、TOTP、恢复码合称认证因素，通行密钥和第三方身份也是能登录的凭证。改密码、开启、更换或重置两步验证、重建恢复码、增删通行密钥、绑定或解绑第三方身份之后，这个用户的旧会话、旧恢复码和进行到一半的登录立即失效，不靠逐条吊销。这些操作共用同一个收尾：加版本，TOTP 开着时重发一组恢复码，给当前设备签发原等级的新会话；没开 TOTP 的用户不补发恢复码。绑定第三方身份的答案是一次重定向，新码不能放进响应，于是用会话令牌派生的密钥加密后存在新会话行上，控制台用 `takeRecoveryCodes` 读一次、读后即清空；撤销会话的触发器清空这两列，旧节点发出的撤销也覆盖。
- **两步验证**：
  - 支持验证器 App（TOTP）和通行密钥，TOTP 开启时发一组一次性恢复码；有通行密钥但没有 TOTP 的用户不再补发恢复码；
  - 持有敏感权限（权限上有标记）的人必须开启，平台管理员和站长的员工都包括在内；敏感操作只认本次会话做过两步验证，先登录、后开启或后被授权的会话不会因此变强；
  - 普通用户自愿开启，站点也可以要求本站用户必须开启；
  - 开启后，用第三方登录也要过两步验证。
- **注册策略**由站点配置：开放（要求邮箱验证、人机校验、域名黑白名单和注册频率限制）、邀请码、关闭；开放默认关闭。
- **验证等级**是数据：邮箱已验证、手机已验证、已实名；站点决定要求到哪一级。
- **唯一性**：邮箱和第三方登录身份在同一站点内唯一，不同站点之间互不影响。
- 密码用 argon2id 哈希。这是专为密码设计的慢哈希，数据库泄露后也很难暴力破解。
- **登录前的尝试有上限**：按 IP、邮箱、用户和每次待验证的登录分别计数，次数用尽后等待，不锁账户；上限是站点配置，默认值见模块 README。IP、邮箱和用户的桶在配了 Valkey 时由节点共享，不可用时按节点数等分到进程内；IP 按与网关相同的来源分组计（IPv4 映射地址还原，IPv6 按 /64）。共享键只放邮箱和 IP 的 HMAC；算法、建键前的粗 IP 桶和故障切换见 [kv 的登录设计](../../internal/platform/kv/README.md#每种用途)。

### 账户、成员、工作区

- 每个用户注册时自动获得一个个人账户。
- 企业账户有多个成员。一个用户可以同时属于自己的个人账户和同站点的多个企业账户，在控制台切换。
- 每个账户可以另建多个工作区，例如分开生产和测试环境。每个工作区有自己的 API key、预算和默认设置。个人用户的界面不显示工作区，直到他创建第二个。

### 授权

- **权限**是代码里定义的一件具体能做的事，例如创建 key、查看账单、调整用户余额。每个权限声明自己能在哪些范围上授予，以及是否属于敏感权限。
- **角色**是一组权限，存在后台。系统自带一套默认角色（所有者、管理员、成员、财务、只读、客服）。平台可以定义在所有站点通用的角色；站点可以定义只在本站使用的角色。
- **授予**：把一个角色在某个范围（平台、站点、账户、工作区）上授予一个操作者，并遵守以下规则：
  - 授予的范围必须在操作者所属的站点之内；
  - 唯一的例外：站长账户的成员，可以获得这个账户所开设站点的范围；
  - 平台范围只能授予主站用户，平台管理员就是持有平台范围角色的主站用户；
  - 授予者只能授予自己拥有的权限，范围不能超出自己的范围，所以没人能借授权给自己升级；
  - 授予随成员关系存在：成员被移除或用户注销时，由此产生的授予在同一个事务里撤销。
- 每次授权只交出覆盖本次操作目标的租户范围，不是操作者所有授予的并集。
- 所有接口都调用本模块判断权限。资金操作上限和审批由 `operations` 模块在授权之上再加一层；改动由做改动的模块记入平台的审计日志。
- **运营凭证**：运营 agent 是独立的操作者种类，权限名和角色里的完全同一套，但由控制面直接授予权限集合、站点范围和是否平台范围，不经过成员关系；凭证只在运营监听有效，不能登录、不能调用模型，也不能持有 `operations.approve` 或 `operations.manage`。创建、轮换、吊销都要求负责人的两步验证，详见[运营的「运营凭证」](operations.md#运营凭证)。
- M1 只有两种授予：注册时成为个人账户的所有者；运维用命令行授予平台角色。运营凭证是以后加的第三种操作者，不走成员授予。

### API key

- **调用 key**用来调模型。可以设置：名称、所属工作区、创建人、花费上限（可按日、周、月在 UTC 零点自动重置；新建的 key 默认带每日花费上限，金额是站点设置，可以修改）、过期时间（只能在创建时设）、可用模型、路由预设（`preset_id`，见[路由](routing.md#路由预设)）、IP 白名单、速率限制、启用或停用。业务速率限制由后台配置，见下文。
  - **路由预设**：新建 key 时可以指定，也可以不指定；不指定时服务端从工作区往上，按 工作区 → 账户 → 站点 → 平台 找到最近一层设置，解析成一个具体预设 ID 写在 key 上；某层设置了但指向不可见、已停用或币种不符的预设时返回 409 `preset_default_invalid`，不跳过；所有层都没有设置才用平台 allow-all。创建出的 key 上是具体 ID，没有“跟随默认”的状态；要改选一个当前可见的预设，或重新选当前默认的 ID。默认值以后改变只影响新 key。落章已经实现（控制台和管理 key 建的调用 key 都在创建事务里解析；在默认的接口上线前是 409 `conflict`，之后是 `preset_default_invalid`）；指定预设的接口字段和站点开关随预设接口一起上线，打开开关前所有节点都不得早于落章那一版，见[路由的「滚动发布、失败与性能」](routing.md#滚动发布失败与性能)。只能选本站、本账户、本工作区可见的预设，跨租户的 ID 返回 404，不透露存在。选择沿用 key 的 `api_keys.manage`；管理 key 自己没有预设，也不能给自己设，签发调用 key 时可以设置；`accounts.api_keys` 的 `CHECK (kind = 'call' OR preset_id IS NULL)`（迁移 00032/00033）保证这一点。功能版接口字段是 `preset_id`：创建时省略按默认链，显式传非零 ID 就用它；显式零 UUID 返回 400 `preset_not_selectable`。修改时省略保持，传入必须是可见的非零 ID；没有“清空为无预设”的用法（旧 key 的 NULL 保留）。
- **管理 key** 是独立的程序化操作者，由控制台的 `api_keys.manage` 与 `api_keys.view` 权限共同签发（创建参数 `kind: management`），必须在将来到期。范围固定为本站自己的账户，角色固定为调用 key 管理员；不能调用模型、创建或修改管理 key、修改账户或工作区预算、访问控制台的账单或支付；只读的 `/api/v1/key` 和 `/api/v1/credits` 例外，OpenRouter 的管理 key 也读这两个接口（见[接入的决策](gateway.md#决策与理由)）。
  - `/api/v1/keys` 的 GET/POST 和 `/api/v1/keys/{hash}` 的 GET/PATCH/DELETE 使用 Bearer 管理 key，不接受调用 key 或登录 Cookie。创建只返回一次明文；hash 是非秘密的、不带连字符的 key UUID，客户端应当作不透明标识保存。
  - 新调用 key 默认继承管理 key 的花费上限及重置周期、可用模型、IP 白名单、到期时间。路由预设不从管理 key 继承（管理 key 没有预设）；调用 key 未指定时按[路由的默认链](routing.md#路由预设)解析。显式设置只能收紧；有花费上限的管理 key 不允许清除上限或改变重置周期（不同窗口不能简单比较大小）。过期时间不能晚于管理 key，不能指定其他账户的工作区或伪造创建人。修改已有调用 key 时，纯收紧允许保留原有到期等上界之外的设置（例如停用旧的永久 key），因为不新增授权；扩大权限或重新启用仍须满足全部边界。管理 key 的上限是每把调用 key 的签发上界，不是额外的汇总消费池；所有调用仍受账户余额和工作区预算约束。之后由控制台收紧管理 key 不追溯撤销已签发的调用 key，需显式停用或删除调用 key。
  - 所有操作每次读库验证站点、域名、账户、工作区、状态、到期和 IP；更改与管理 key 行锁内的授权、审计同事务，审计主体为 `management_key:<uuid>`。每把管理 key 每个数据库 UTC 分钟最多 60 个请求，跨节点共享；无效操作也消耗次数，429 带 `Retry-After`，数据库故障不放行。创建管理 key 与调用 key 共用账户数量和每小时创建上限。
- **格式**：站点配置的前缀 + 256 位的随机串 + 校验位。主站的前缀是 `sk-ax-v1-`。前缀让二级站点使用自己的品牌；校验位能在离线时发现输错的 key。站点改前缀不影响已发出的 key，旧 key 照常显示原前缀。
- **存储**：只存带密钥的哈希（见[安全的「安全基线」](../security.md#安全基线)），并记下哈希密钥的版本，轮换哈希密钥时旧 key 不会全部失效。完整的 key 只在创建时显示一次，界面上显示前缀和末四位。删除是终态，删除后不能恢复。
- **列表、搜索与筛选**：控制台的 `/api/console/v1/keys` 按创建顺序倒序列出账户的 key（含停用与过期），游标是上一页最后一把 key 的 ID。可选参数：`name` 是不分大小写的名称子串（字面匹配，`%`、`_` 不是通配符），`prefix` 是不分大小写的前缀，`status` 取 `active`、`disabled`、`expired`（过期的先算过期，再分是否停用），`created_after` 含、`created_before` 不含。没有筛选（或筛选稠密）时，读完一页的代价随这一页读到的行数增长，不随账户的 key 历史增长；稀疏筛选会沿索引顺序读到足够一页或读完匹配范围，但同样不排序、不回表重排（#408）。查询沿 `(account_id, id DESC)` 的索引顺序读，过滤在读取时进行。`status` 的过期与否用数据库的 `statement_timestamp()` 判。`cmd/axiom` 用目录快照给每把 key 附一个可选的 `retired_models`：key 的可用模型里已被目录下线的名字；没有、或读请求的节点没有可用快照时省略，页面就不提示。路由预设摘要（`preset_id`、名称、作用域、版本）也由控制台向 routing 批量取，是可选的 `preset` 字段；旧节点省略，页面显示“未知”。响应里的 `filters` 回显本节点实际应用的筛选；旧节点没有这个字段且会忽略筛选参数，页面在确认回显匹配前不展示它的行（滚动发布期间）。列表不按最后使用时间筛选：本模块没有这个时间，原因见[决策与理由](#决策与理由)。
- **数量与创建频率**：每个账户最多保有多少把未删除的 key（默认 100）、每小时最多能创建多少把（默认 50，已删除的也算，所以删掉再建绕不过去）。限额分两层：站点设一个缺省，账户可以有自己的，盖过站点的；每个限额单独往上找，没设的用站点的，站点也没设的用默认。两层都在后台改（站点在站点设置页的「key 限额」，账户在账户页），要 `sites.manage`，填理由，记审计。数量在插入 key 的同一个事务里检查：先锁账户行再数，两个请求同时建最后一把时，后一个要等前一个提交后才数，所以不会都成功；一小时按库的时钟数，不看各节点自己的时间。到数量上限是 409（错误码 `too_many_keys`），删掉一把旧 key 才能再建；超过频率是 429 并带 `Retry-After`（使数量降到限额以下的那把 key 满一小时的时间）；两种响应都写明生效的限额和账户现有的真实数量。调低限额不会删掉已有的 key，超过的账户只是不能再建。
- **改动的审计**：创建、修改、删除各记一条，与改动同一个事务成败。修改的条目记下改了哪几项，以及名称、停用、花费上限、重置周期、路由预设 ID 的改前改后值；可用模型和 IP 白名单只记「变了」——模型最多 256 个、每个 200 字，会超过条目 8 KiB 的上限，而地址是日志不记的个人信息。路由预设的规则由 routing 的审计记，key 的审计只记 ID。key 的文本和哈希从不进日志。
- **使用范围**：key 只能在所属站点登记的 API 域名上使用。域名与 key 不属于同一站点时，返回和"key 不存在"完全相同的错误，不透露这个 key 属于别的站点。
- **接入地址**：新建 key 的对话框在 key 还在屏幕上时给出接入指引——三种调用格式的 curl 示例，以及 Claude Code、Codex、Cursor 的配置。地址取本站登记的 API 域名的 origin（快照里的 `Site.APIBase`，控制台读到的 `api_base_url`）：控制台在站点的公开域名上，调用去的是 API 域名，所以这个地址不按控制台的域名拼，也不用请求头里的 Host。OpenAI 形状的客户端用 `origin/v1`，Anthropic 的客户端用 `origin`，它自己接 `/v1/messages`。站点没有启用的 API 域名时省略 `api_base_url`，对话框只显示 key；查询接入地址失败时显示错误和重试，保留明文 key。多个 API 域名优先选择 HTTPS，再按 origin 字典序选择。
- **认出与准入分两步**：认出 key（它是谁、属于哪个工作区和账户）查内存缓存，缓存只存创建后不会变的对应关系；能否使用在准入事务里读数据库判定，路由预设、可用模型、等级也在这里读出，路由用它们，再由计费在同一事务里预留；事务里只做内存计算和预留，满载排队在事务之外，不占数据库连接。所以停用不需要通知缓存，任何节点上的下一次调用都会被拒绝。已经通过准入的调用照常完成，与计费"请求一旦开始不中途掐断"一致。

### 限额怎么生效

- 一次调用要同时满足所有适用的限制，以最严的为准：账户余额、工作区预算、key 的花费上限、等级和 key 上的速率限制。
- 工作区预算和 key 的花费上限都可以按日、周、月重置，也可以设不重置的总额；同时设置时各自生效，取最严。
- **扣费顺序**：账户可以在控制台的设置页选 `subscription_first`（默认）、`wallet_first`、`subscription_only`、`wallet_only` 四个顺序之一，也可以跟随站点默认；站点默认由管理员在站点设置里改。账户没选时用站点默认，站点没设时用 `subscription_first`。准入查询把生效值随 key 的 42 字节准入快照带下来，网关不再多查一次；一次调用只用一个来源，两个 `only` 不互相回退。滚动升级期间只要还有旧节点存活，生效值就是默认的 `subscription_first`，设置接口也拒绝非默认值；新节点心跳汇总存活节点的支持情况，旧节点退出后自动开放。实现见[计费的「资金来源」](billing.md#资金来源)。
- 花费计数和预留都由 `billing` 管理。本模块打开准入事务，在其中读出 key 的花费上限、工作区预算和账户的等级，作为参数交给计费；计费在同一个事务里连同在途预留一起检查（见[计费的「预留与结算」](billing.md#预留与结算)）。

### 业务速率限制

账户、等级、调用 key 的 `rate_requests` 是后台数据：null 继承，0 不限，正数为一个网关速率窗口内的请求数（默认一分钟）。账户覆盖等级，等级未设置时使用代码默认 6000；key 未设置时继承账户的有效值。等级是每个账户的默认值，不是整个等级共用一个池。账户计数聚合所有 key，key 自己的限制和节点保护同时生效；key 不限也不能绕过账户或节点保护。管理 key 不参与模型调用限流。

计数在准入前按不可变的账户/key 标识取一次，准入事务读取最新策略再判定，排队或上游重试不重复计数。调用与 count_tokens 分开计数、应用相同业务策略。key 的尝试始终计数，不返还；超过节点保护 KeyRate/CountRate 的尝试不推进共享或本地账户池，因此失控 key 的节点保护拒绝不会挤占兄弟 key 的账户额度。业务 key 限额只在准入事务里读到，业务 key 拒绝及其后的准入失败仍消耗账户池，可能影响同账户的其他 key；给 key 设低业务额度并不提供完全隔离。Valkey 超时退回同步维护的本地计数，故障期间可能按节点数放大，恢复后直接采用共享计数。默认账户聚合额度影响已有多 key 账户，上线前必须完成[发布前的账户速率核对](../ops/release.md#账户速率限额上线前核对)。

后台 `GET/PUT /api/admin/v1/rate-limits/{target}/{id}` 支持 tier/account/key；PUT 要求平台 MFA、sites.manage、CSRF、幂等键与理由，配置和前后值审计同事务提交。普通 key 设置及管理 key API 不写这些后台字段。

### 等级

- 每个站点定义自己的等级。等级是一组账户层级的默认值：速率限制、可用的模型。路由预设不按等级：产品规定的链是平台 → 站点 → 账户 → 工作区（见[配置链](#配置链)）。加价不在这里：给某个等级用的加价是计费的一条定价规则，人群指定为这个等级，见[计费的「定价」](billing.md#定价)；等级表本身不存加价。
- 账户进入某个等级的方式：手动指定，或按后台配置的规则自动升级，例如累计充值达到某个数额。
- **默认等级**：每个站点指定一个默认等级。新账户注册时进入站点当时的默认等级；以后改默认等级不影响已有账户。未登录的访客看到的价格也按默认等级算（见[前端的「页面清单」](../frontend.md#页面清单)）。

### 站点

- 主站、二级站点、站长和收款方式之间的关系，见[术语与核心概念](../glossary.md#关键关系)中的「主站也是站点」和「二级站点由主站上的一个账户开设」。
- **站点的配置**：
  - 域名：可以有多个，每个标明用途（控制台、API、管理后台），证书自动签发；
  - 品牌和主题（品牌色、站点名称和 logo）、登录方式与第三方登录应用、注册策略、等级、key 前缀；
  - 收款渠道（二级站点用站长自己的商户账户）、数据留存的默认值、状态。
- **配置项由负责的模块各自声明**，例如收款渠道由 `payments` 声明，登录方式由本模块声明。第三方登录应用和收款渠道的密钥按[安全基线](../security.md#安全基线)信封加密存储。
- **只认登记过的域名**：请求按域名认出站点，只接受站点登记过的域名，其他一律拒绝。生成链接一律用站点配置的域名，不用请求头里的 Host。
- **站长员工按角色分工**：例如客服只能查看用户、财务可以调整余额，角色的范围限定在这个站点。
- **站点 logo**：一个站点至多一个，由后台的 `/api/admin/v1/sites/{site_id}/logo` 读、换、清；控制台的 `getSite` 在 `logo_url` 里给出地址，没有时省略。文件只收 SVG、PNG、WebP，最大 256 KiB；PNG 和 WebP 每边 1 到 1024 像素。SVG 在保存前按允许列表重建：只留绘制用的元素和表现属性，去掉 `script`、事件属性、`style`、`foreignObject`、图片、链接、动画和任何外部引用（`href` 只能是本文件里的 `#id`），带 DTD 的文件直接拒绝；重建后的字节才是保存、哈希和发送的内容。字节存在 `accounts.site_logos`，按 `(站点, SHA-256)` 追加，`sites.logo_hash` 指向当前一张；换 logo 只移动指针，旧地址继续返回旧字节。公开地址是本站控制台域名下的 `/api/console/v1/site/logo/<sha256>`，管理域名下另有一份同内容的 `/api/admin/v1/site/logo/<sha256>`，两者都返回 `Cache-Control: public, max-age=31536000, immutable`，因为地址已经由内容决定；不引入对象存储，256 KiB 的上限让数据库足以承担，写入与审计也在同一个事务里。控制台、官网、管理后台的登录页和侧栏显示 logo，加载失败或没有时显示站点名称；管理后台的公开 `getAdminSite` 在管理域名给出名称和同源的 `logo_url`，设置页用 `data_url` 预览当前图片。决定与放弃的方案见[决策与理由](#决策与理由)。

### 给用户的邮件

- **归本模块**：收件人（用户和账户成员）、模板、站点品牌和多语言都在这里。找回密码与密码变更通知已接入（见[登录与会话](#登录与会话)），验证码与其余提醒随各自功能接入。投递在 `platform`：SMTP 发送、消息组装、按收件人的限流和重试都在 [platform 的 mail](../../internal/platform/mail/README.md)，这里只决定收件人、模板和正文。记录与告警的通知渠道是发给运维的（见[记录与告警的「通知渠道」](observability.md#通知渠道)），与这里分开。
- **谁触发**：验证码、找回密码、异地登录由本模块触发；余额不足、充值到账由 billing、payments 触发；账户异常花费由 observability 按调用记录检测后触发（见[安全的「防滥用」](../security.md#防滥用)），key 泄露由密钥扫描发现后触发；模型切换与迁移由 catalog 触发（M1 之后，见[模型的生命周期](catalog.md#模型的生命周期)）。其他模块把事件和值交给本模块，不各自拼邮件。
- **写法**：只链到站点登记过的域名，不信任 Host 和转发头；正文不插入用户可控的内容；链接带一次性令牌，用完即失效。
- **送达**：验证码、找回密码这类登录必需的邮件，发送失败要让用户重试并告警；其余提醒异步发送、失败重试，不影响调用和计费。用户在设置里关掉的提醒类型不发；模型切换与迁移的通知必须送达，不能关闭（见[前端的「通知」](../frontend.md#页面清单)）。
- **下层怎么触发**：catalog 在本模块下面，不能引用本模块；它声明一个发送通知的接口，由 `cmd/axiom` 接到本模块（见[总体架构的规则 5](../architecture.md#模块边界规则)）。billing、payments 这些在本模块上面的模块可以直接调用。

### 用户提醒与站内公告

用户提醒与运维告警分开：低余额、充值到账、认证因素变化、账户异常花费各有开关，默认开启邮件（账户异常花费的提醒在升级完成前不生产，见下文），低余额阈值默认 5 额度（十亿分之一额度存储），可选一个 HTTPS Webhook。偏好属于登录用户，当前仅个人账户；邮箱取本站用户，正文带站点名称，语言为 zh/en。因素开关控制后台的 TOTP、恢复码等因素邮件和因素 Webhook，不影响改密码、完成密码重置时必发的安全邮件，也不影响找回密码邮件；这些提醒只是通知，不暂停 key，也不替代平台运维的告警和调查。

二级站点的收款配置变更另有一条必发的 `site_payment_changed`：支付模块在保存商户配置的同一个事务里调用 `RecordSitePaymentNotice`，收件人是该站点 owner account 的活跃用户，主站没有 owner，不写；这一条在 `noticeEnabled` 里恒为开，没有偏好开关。正文有主站品牌、被改的二级站点名称（`detail`）、标题和“若不是你操作”的处置建议，不含商户号、密钥、网关地址或改动前后值。保存失败时通知与审计一起回滚；每次改动生成新的来源，保存事务和接口幂等键保证同一次改动只写一条，唯一键挡住同一用户的重复行。

billing 在账本写入同事务记余额变化 journal（含变动前后余额和是否为充值），后台每分钟以每批最多 1000 行集合消费；低余额仅在余额从不低于阈值跌至阈值以下时通知，充值恢复后再次跌破可以再发，忽略在途预留的瞬时变化。因素版本每次改变由 accounts 同事务记录事件，覆盖密码、TOTP、恢复码及管理员/命令行重置。余额阈值在 journal 消费时判定；发送开关、地址和语言在派发时一起读取并冻结到 outbox/任务，后续修改不取消已派发任务。同一来源、种类和用户只生成一条提醒。邮件进入既有 outbox，SMTP 不可用时保持待派发，不阻塞认证与充值；投递失败由 River、outbox 和运维丢弃告警可见；历史非法邮箱另记提醒的 email_failed，不影响其他用户；邮件未配置时，同一提醒的可选 Webhook 一并等待配置，避免将没有邮件兜底的通知视为已派发。Webhook 正文只有稳定通知 ID、种类、时间、金额/因素版本，站点支付通知另带 `detail`（被改的二级站点名称），经 egress 防 SSRF、无重定向、10 秒期限，最多五次 River 持久重试；仅 2xx 成功，重试正文不变，接收方须按通知 ID 去重。用户 Webhook 不携带调用内容或凭证、不提供签名认证；URL 不进入任务或审计。Webhook 带 currency（因素事件可忽略），value 金额为十亿分之一站点额度。邮件与 Webhook 均为至少一次；旧节点的密码邮件未标记 email_done，滚动期间可能多收到一封因素提醒；新旧节点的密码变更安全邮件均不可关闭。已派发通知保留 30 天，尚未结束的 Webhook 不清理。

账户异常花费由 observability 在检测事务里调用 `RecordSpendAnomalyNotices` 写入：同一账户一轮检测只写一条，三种信号合并，每次异常生成一个随机来源，唯一约束让重试或并发运行不重复；`spend_anomaly` 默认开启，关闭后不写新提醒，恢复不补发。邮件正文只有站点名称、异常种类标题、金额（地区或模型信号没有金额）和处置建议，Webhook 正文只有稳定 ID、种类、金额和时间；都不含调用内容、IP 原文或凭证。邮件说清“若不是你”时停用不认识的 key 并联系站点运营。旧客户端提交偏好时不带 `spend_anomaly`，服务端在同一条 upsert 里保留已存值，不因字段缺失重新打开，也不会用先前读到的旧值覆盖并发提交的新值。滚动发布期间，detector 的提醒生产由 `spend_detection.notify_users` 控制、默认关闭，等全部节点认识这个种类后再打开，因为升级前的派发器会领取不认识的种类并标记已派发却不发送；升级后的派发器只领取自己认识的种类，以后再加种类时新提醒会等一个认识它的节点来发。

公告对外 ID 使用 `ann_` TypeID，站点沿用 `site_` TypeID。公告为本站一般信息，独立于必须送达的迁移/切换通知，不发送邮件、没有已读或强制确认状态。管理员使用 MFA、sites.manage、幂等键及审计发布纯文本标题和正文，指定必填的 UTC 起止时间，撤下后不可恢复。控制台只列本站满足 starts_at <= 当前时间 < ends_at 且未撤下的公告（最多 100 条，最新优先），正文作为文本显示，无 HTML；入口使用未加样式的 details，覆盖加载、空、错误和旧节点不可用状态。

### 配置链

- **范围从上到下**：平台 → 站点 → 等级 → 账户 → 工作区 → API key。等级是一组账户层级的默认值；账户上显式设置的值优先于等级。
- **每项配置由负责它的模块在代码里声明**：
  - 默认值；
  - 允许在哪几层设置；
  - 下层能修改的界限；
  - 合并方式，共三种：
    - 默认值类：最具体的那层生效；
    - 限额类：各层同时生效，取最严；
    - 名单类：如可用模型、IP 白名单，各层取交集。
- **路由预设是产品单独规定的默认值链**：平台 → 站点 → 账户 → 工作区，不经过等级；预设本身由 routing 保存，key 创建时解析成具体 ID 落在 key 上，之后改默认不影响旧 key。解析时某层默认无效返回 409，不回退到更宽的层（见[路由](routing.md#路由预设)）。
- **存储与生效**：各层设置的值存在本模块，保存时校验并记审计；生效值算好后放进核心的内存快照。路由预设例外，规则存 routing 的表，key 只存一个 ID。
- M1 不做通用的配置链：key 的设置存在 key 上，站点的安全与会话参数存在站点设置里，默认值在代码里。

### 自带的供应商 key（BYOK）

账户可以保存自己的供应商 key。一把 key 是一个账户归属的供应商（`owner_scope=account`），由 suppliers 模块保存和管理：key 文本与供应商凭证走同一套信封加密（`suppliers.credentials`，用途 `key`），控制台只在保存时接收一次明文，之后只给末四位，任何响应都不返回 key；供应商名、分组、凭证、端点和成本计划都是 suppliers 的表，账户在控制台看到的是自己账户可见的那些行。

- **支持范围**：M1 支持 OpenAI 官方的 key（适配器 `openai`，地址 `https://api.openai.com`，调用格式 chat、responses、completions、embeddings）。Anthropic、Google 等要各自的适配器，尚未接入；请求里给出未知的 provider 返回 422。
- **建一把 key 时**：在一个事务里写供应商（状态 `byok`，不参与同步、没有登录行）、一个分组（倍率 1）、该 key 对应的全部目录模型（作者等于 provider，已上架且没有 `:free`）、每个模型一个端点与一份**全零成本计划**、一条状态为 `active` 的凭证（上限 8 个并发，不限每分钟请求）、一条金额为 1、单位价值为 1 的供应商余额与单位价值，使路由能像普通端点一样挑到它。全零成本计划是明确的：用户自己付给供应商，Axiom 的成本是 0；售价按 [计费的「定价」](billing.md#定价) 的 BYOK 服务费收。
- **列表**：控制台按账户读 `status='byok'` 的供应商和自己的凭证，返回名称、provider、末四位、启用状态、是否被拒绝、是否允许回落和创建时间；不返回 key 文本、密文或上游地址。
- **测试**：`POST /api/console/v1/provider-keys/{id}/test` 用保存的 key 向供应商发一次最小请求（OpenAI 的 `GET /v1/models`，10 秒期限）。成功把被拒绝的凭证恢复为 `active`；401 标记 `rejected`；403 可能是地区封锁而不是 key 无效，和其他失败一样只报告不可判定、不改状态，避免供应商故障或封锁把用户的 key 永久标坏。
- **停用与删除**：停用把凭证置为 `disabled`，下一次调用就不再选它；启用把 `disabled` 置回 `active`，被拒绝的仍是 `rejected`；删除把供应商置为 `removed`、凭证置为 `erased` 并清掉密文（沿用供应商移除的擦除），路由下一次重建就不再包含它。已有的尝试成本行仍指向凭证 ID，不删除。
- **被拒绝**：供应商以 401 拒绝时，适配器把失败归为 `CredentialRejected`（403 是 `NotPermitted`，不标记 key）；调用路径对账户归属的凭证把状态写成 `rejected` 并让本节点的凭证立刻休息。`rejected` 不参与挑选，重启后也不会被选；只有测试成功才会恢复。若这把 key 不许回落，见[路由](routing.md#一个请求的路由步骤)。
- **路由预设**：预设对 BYOK 一视同仁：来源类别、数据政策、产品成绩、验证和最高单价都照常过滤；自带 key 不豁免 `data_collection`/ZDR 等数据政策，端点属性没有记录时按最坏情形，严格预设会排除它。BYOK 的优先级和 `fallback=false` 仍按路由的规则，预设不能把平台端点重新放进来。细节见[路由](routing.md#路由预设)的 BYOK。
- **不变量**：明文只在 `suppliers.credentials.ciphertext` 里，任何接口、日志、审计和错误都不含它；一把 key 只对所属账户可见（行级安全与路由的 `Owner`）；被拒绝的 key 永远不会被选中；端点只能引用本站点、本账户的供应商。
- **滚动发布**：新状态 `byok`、新凭证状态 `rejected` 和 `hint` 列都是新增，但旧节点并非看不见它们：旧节点的 `ListLiveSuppliers` 按 `status <> 'removed'` 读供应商，会把 `byok` 行交给启动时的适配器检查，`openai` 不在旧节点的注册表里，节点因此拒绝启动。所以 `AXIOM_BYOK` 默认 `off`：先让所有节点上线认识 `byok`/`rejected` 的版本，再由站点打开；打开前不建 key，旧节点也不会有机会看到。打开后建的 key 在旧节点上仍不接管，旧节点建的普通供应商不受影响。
- **失败**：供应商 outage、限流、请求错误走供应商已有的失败分类和回退；用户 key 失效只影响这把 key（`rejected`），不摘除同账户的其他 key，也不影响平台端点。

### 停用与注销

- 管理接口分别用账户 `/suspension` 暂停/恢复调用、账户 `/tier` 调整等级、用户 `/sign-in` 禁用/启用登录，均要求 MFA、`users.manage`、幂等键和原因；平台授予 `/platform-grants/{role}` 撤销/恢复要求 `platform_grants.manage`，列表接口给出各角色的最新授予状态。每个状态变更同事务记审计；相同状态不重复写审计。
- 站点、域名、用户、账户、工作区、key 都能单独停用。停用立即生效：每次调用在准入事务里读数据库核对 key、工作区、账户、站点和域名的状态，与缓存无关。账户停用只暂停调用，控制台登录仍可用；其余条件有效的 key 在准入返回 403。停用用户只阻止登录并吊销全部会话，恢复后需重新登录；要让 key 不能用，停用账户或 key。
- 本模块的停用是管理员的开关；计费的「余额不足」和「暂停」是另一回事，见[计费的「风控状态」](billing.md#风控状态)，两者在同一个准入事务里检查。
- **注销用户**：
  - 抹去个人信息，财务记录保留，因为账本不可修改；
  - 剩余余额按站点的退款政策处理（见[计费](billing.md#额度批次)）；
  - 对话内容和调用记录按[记录与告警](observability.md#待定问题)中的规则处理；
  - 注销完成后，同一邮箱可以重新注册，得到的是一个全新的用户。
- 账户的唯一所有者、站长账户的所有者不能直接注销：前者要先转让所有权，后者还要先停用自己的站点。

### 邀请关系

- 每个用户有自己的邀请码和邀请链接。通过它们注册时，记下邀请人（用户）。
- 邀请人在注册那一刻确定，之后不能修改。邀请人必须是同站点的另一个已有用户，不能自己邀请自己。

## 后台系统设置

`/api/admin/v1/sites/{site_id}/system-settings` 读取站点名称和注册方式，也可改名称；请求里省略 `registration` 时在站点行锁内保留当时的注册方式（包括由注册策略接口设置的 open），给出时只接受 invite/closed。名称编辑只提交名称，不把表单打开后别人改过的注册方式写回去；响应里的 `name_editable` 标明本节点是否接受这种保存，旧节点不返回该字段时设置页把名称保持只读并说明等升级。修改需 MFA、平台 `sites.manage`、CSRF、幂等键和理由，与审计同事务，站点快照随后刷新。收款开关、充值额度上下限和充值缓冲由同路径的 `/payments` 资源交给 payments 读写。

同源的 `/api/admin/v1/sites/{site_id}/legal-documents` 按 `(kind, version)` 游标分页读版本、发布新版本：正文是站长的纯文本，版本号由服务端在站点行锁内取下一个，正文不改不删；发布需 MFA、`sites.manage`、CSRF、幂等键和理由，审计只记类型、版本、长度和 SHA-256。控制台的 `/api/console/v1/legal` 公开返回当前版本，`/legal/accept` 记录已登录用户的接受；已发布文档的站点在用户接受前只放行读会话、接受和退出。

同源的 `/api/admin/v1/sites/{site_id}/brand` 读写站点的品牌色：`#rrggbb` 或空（空就是默认配色），小写存储，改后本节点立即重载快照、其他节点在重载间隔内跟上；修改同样需 MFA、`sites.manage`、CSRF、幂等键和理由。控制台的 `GET /api/console/v1/site` 在站点设置了品牌色时返回 `brand_color`，页面据此生成深浅两套配色（[前端](../frontend.md#主题与自由度)）；没有设置或旧节点不返回时用默认配色。

平台 `/api/admin/v1/settings/mail` 读写共享 SMTP 覆盖配置。配置整包信封加密（含地址与用户名），只返回是否启用、非密连接设置和是否有密码，审计仅记配置变更、不存值。密码不进入幂等指纹，指纹只区分是否提供密码。省略密码复用原密码；修改服务器、端口或用户名必须重填密码，避免把旧凭证发往新服务器。此传输配置在节点启动时生效；返回 `restart_required` 明示保存后需重启节点，无数据库覆盖时使用环境变量。`/settings/mail/tests` 同步测试已保存配置并返回 accepted/rejected/failed/disabled，失败不返回 SMTP 原文，日志按请求 ID 留下不含凭证/收件人的分类诊断；管理保存和实际拨号都执行 egress 公网地址策略，DNS 解析结果经校验后直接钉住 IP。测试需 MFA、sites.manage、CSRF、幂等键及理由，每会话每分钟最多 10 次，使用独立测试 sender，不占用普通邮件的共享收件人冷却；不返回收件人。SMTP accepted 只表示服务器接收，不保证最终到达收件箱；网络中断结果可能未知，不自动重发。收款测试用已保存商户的只读查询探测，不创建订单或转钱。

## 决策与理由

品牌色用独立的 `/brand` 资源读写，不放进系统设置的整体替换：旧页面保存名称或注册策略时不会把不认识的品牌色抹掉；字段可缺省，旧节点读写的契约照常工作。颜色只校验 `#rrggbb`，与浅色、深色底色的对比由前端 `brandStyle` 调整而不是拒绝；写入在站点行锁内做，审计记改前和改后的值。接口和契约字段按[负责人授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)中的「遇到问题自己解决问题和判断最优而不是问我。」落地，仍按对外接口变更独立评审。

账户等级改动用独立的 `PUT /api/admin/v1/accounts/{account_id}/tier`，不放进账户详情或整体更新：页面只提交目标等级和理由，旧页面保存账户的其他内容时不会把等级覆盖回读到的值。请求要求 MFA、`users.manage`、CSRF、幂等键和理由，成功返回 204，与暂停/恢复调用、禁用/启用登录一致；同一等级是空操作，不写审计。目标等级必须属于账户所在的站点，否则 422 并把原因放在 `fields./tier_id`；账户不存在 404，等级编号格式不对 400。改动在账户行锁内写 `tier_id`，同事务记 `account.tier_change`，`detail` 存改前和改后的等级名；准入事务每次调用都读 `tier_id`，所以改完下一次调用就按新等级，不依赖快照刷新。接口和对外契约按[负责人授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)中的「遇到问题自己解决问题和判断最优而不是问我。」落地，仍需独立评审。

SMTP 管理配置选择保存时检查、实际 TCP 拨号时再次校验整组 DNS 答案并钉住 IP，复用平台 egress 策略；仅保存时检查无法阻止 DNS 重绑定，仅限制测试入口又会漏掉重启后的通知邮件。环境变量配置同样遵守公网策略，不增设生产内网例外。幂等指纹不包含密码而只标记是否提交，避免数据库备份里的无盐摘要绕过信封加密；同一键更换密码仍重放首次结果，变更密码需换键。

业务限流按[授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)中的「遇到问题自己解决问题和判断最优而不是问我。」落地 E4-2/P13。

| 决策 | 理由 |
|---|---|
| 复用账户、等级、key 的可空整数列，默认只在代码里；0 不限 | 无新策略表或快照失效协议；已有账户自动继承，滚动发布只加列。未设置与不限必须可区分 |
| 账户覆盖等级，key 独立限制并与账户取交集 | 等级本来就是账户默认值；按等级汇总会让一个账户消耗其他账户的额度 |
| 预检一次脚本同时计账户与 key，事务里读策略 | 对比预检前查策略或事务内再访问 Valkey，选择不增加任何热路径往返且立即应用更改的做法；排队只重判策略 |
| 节点保护超限在原 count 脚本中跳过账户计数，本地同样跳过；业务 key 拒绝仍计账户 | 节点额度无需查库，单次往返即可隔离超出它的洪泛；业务额度在稍后的准入事务才确定。拒绝后补偿扣回会引入窗口交替、缓存超时后执行结果未知以及共享/本地两处回退的一致性问题，暂不采用；明确保留业务 key 拒绝可挤占同账户额度的取舍 |
| 继续本地全额兜底、不因缓存故障拒绝全部请求 | 沿用 kv 已有业务计数故障语义；不是严格全局硬配额，钱仍由 PostgreSQL 检查 |
| 账户范围只增读当前指定等级，原站点/平台写权限不变 | 准入不能为读取等级而把范围扩大到整站；按账户主键取指定等级 ID 的 InitPlan 保持范围检查有界 |
| 后台专用资源写限额 | 用户或管理 key 不能扩大业务额度；独立 PUT 避免旧页面覆盖未知字段；行锁与审计保证并发修改可追溯 |
| 账户等级用独立的 `/tier` 资源修改，成功返回 204 并支持幂等重放 | 与 `/suspension`、`/sign-in` 同一种状态变更：只提交目标等级和理由，不会把页面没打开过的其他账户字段写回。等级必须属于账户所在的站点，否则 422 `fields./tier_id`；同一等级是空操作，不写审计。准入事务本来就读账户的 `tier_id`，改完下一次调用即按新等级，不需要快照失效 |

风险与检查：共享计数并发与租户隔离、null/0/覆盖、缓存故障与恢复、排队不重复计数、最新策略读取、429 头及预算预留均由行为测试覆盖；性能由 bench-compare 检查，不新增依赖。

| 新增 go-webauthn v0.18.2 依赖，而不是自己解析 CBOR 和 attestation | 这是认证边界，attestation、COSE 公钥、签名计数器和 clone 检测都容易写错；库只增加 7 个间接依赖，换来经过审计的协议实现。代价是版本跟随上游，已锁定并纳入 Dependabot |
| 登录域名在有通行密钥、第三方身份或 provider 后不可移动（第一次设置不受限） | RP ID 和 callback URI 都绑定域名；迁移它们会让已注册的凭证和已配置的回调失效，宁可要求先移除这些资产 |
| 绑定/解绑第三方身份、增删通行密钥、改密码和 TOTP 的变更共用一个收尾（加版本、重发恢复码、签发会话），并写审计，同一事务 | 这些操作都改变谁能登录，旧会话必须立即失效；收尾只写一处，新操作不会漏掉版本或恢复码。审计和变更同事务，审计失败则变更回滚。绑定身份的响应是重定向，新码用会话令牌派生的密钥加密后存在新会话行上并由 `takeRecoveryCodes` 读一次，不放进 URL 或 Cookie；不占密钥环的版本，旧节点迁移后仍能启动，撤销时由触发器清空。通行密钥的增删还要求当前密码，已开启第二因素时要求 mfa 会话；注册落库前在站点锁下重读开关和登录域名 |
| 数据库触发器拒绝为持有通行密钥的用户写入控制台 `password` 会话，也拒绝未经通行密钥证明的新 TOTP | 滚动发布时旧节点不认识通行密钥，会在密码登录后直接签发密码会话，旧版后台还能在没有通行密钥检查的情况下开启 TOTP；应用层检查管不到旧节点。触发器是两个版本都会执行的共同约束，迁移同时吊销已有会话；新节点在锁内证明通行密钥后用事务级标记放行，管理面不跑 WebAuthn 但也不能成为增开 TOTP 的旁路 |

| OpenRouter 只对公开资料能验证的行为作对照 | 2026-10-28 查证 [登录页](https://openrouter.ai/sign-in)、[支持页](https://openrouter.ai/support) 和 [条款 §3.1](https://openrouter.ai/terms)：支持账户密码，公开文档未说明重置令牌、TTL、撤销会话或通知的保证，登录表单由客户端加载，无法据此验证找回细节；这些不写成 OpenRouter 的承诺。Axiom 按任务卡明定可测试的不变量，原因是自有认证与多租户隔离需要明确保证 |

| 新账户进入站点当时的默认等级，访客看到的也是它的价 | 负责人在对话中授权开发者按推荐决定（2026-10-13，见[前端的「决策与理由」](../frontend.md#决策与理由)）。访客注册后付的就是看到的价；改默认等级只影响以后注册的账户，已有账户的价格不会被意外改动 |
| 会话与两步验证的接口在控制台和管理两份契约里各一套，注册不自动登录 | 会话只在签发它的监听面有效，管理后台的人要能在管理后台里开启两步验证，不必先去控制台。邀请码注册成功后页面用同一组凭证调登录；开放注册要等邮件链接点击后才有用户，页面再带人去登录。两个操作的限次和 CSRF 起点各守各的规则。否决的做法：注册同时签发会话：注册多一种会话来源；两个面共用一套路径：管理接口要挂到公网 |
| key 列表的筛选只读 `accounts.api_keys` 的现有列，最后使用时间不提供 | 搜索和状态筛选必须在大账户下仍是一页的开销：查询沿 `(account_id, id DESC)` 索引读，过滤随读进行，游标仍是 key ID（#408）。最后使用时间没有现成来源：在准入事务里给 key 行写时间会把写和锁加进每次调用；从 `call_log` 推导要跨模块扫历史或为每页再查一次，都会让页面的代价随调用量增长。目录里已下线的模型由控制台读快照后附 `retired_models`，账户模块仍不依赖目录。否决的做法：新增 `last_used_at` 并在准入时写；从调用记录实时聚合最后使用时间 |
| key 的设置用 `PUT` 整体替换，创建后只能改设置不能改过期时间；没写的限制就是不限 | 与「过期时间只能在创建时设」一致；Go 生成的类型分不清「没写」和「写成 null」，整体替换没有这个歧义。否决的做法：带 `null` 的 `PATCH`：要引入可空类型 |
| 密码变更安全邮件不可由用户提醒偏好关闭 | 保留已有安全保证，避免仅持密码的登录者关闭邮件后改密；因素开关只影响后台因素邮件及 Webhook，无需为普通提醒偏好引入新的凭据验证协议 |
| journal 按集合转换，单轮预算耗尽正常结束 | 每笔收费都有 journal，逐行往返无法随平台请求量扩展；每批删除返回最多 1000 行，accounts 一条 INSERT SELECT 判定，派发独立排空，维护每轮一次，避免正常积压触发 River 丢弃告警 |
| 用户提醒复用邮件 outbox，billing journal 与因素事件同事务持久化；一般公告单独存 accounts | 比较同步发信与持久事件，选择后者隔离 SMTP/Webhook 故障；比较轮询余额当前值与消费余额变动，选择后者避免漏过快速充值/消耗的阈值穿越。journal 增加账本事务的一次行写入，但不增加网络往返或调用路径的 Go 分配；消费后删除。比较依附运维规则与用户偏好，选择独立偏好防止跨租户地址和规则混用。表与接口按授权「遇到问题自己解决问题和判断最优而不是问我。」落地（[授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)），仍须独立评审 |
| 采用 sub2api 的首次向下穿越判断，通知改为持久消费；公告不引入已读与定向规则 | 2026-10-29 只读参考 `sub2api/backend/internal/service/balance_notify_service.go` 的 old >= threshold 且 new < threshold，采用定点整数替代 float；参考 new-api 的用户类型偏好，但不复制进程内发送与限流。sub2api 公告含 targeting/reads/draft，本卡只需要发布/撤下/有效期，不加这些机制 |
| OpenRouter 的用户提醒私有设置未确认，阈值和公告语义采用本项目默认 | 2026-10-29 查询公开文档与 [设置入口](https://openrouter.ai/settings/preferences)，未找到可核验的逐类型通知/公告契约；不把未核实行为当基线。5 额度、可关闭后台因素提醒（密码安全邮件始终必发）、未签名用户 Webhook 是本次实现取舍 |

站点 logo（Issue #279）按[负责人授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)落地，原文「遇到问题自己解决问题和判断最优而不是问我。」覆盖存储、公开接口和数据模型；部署、花钱和对外发消息仍由负责人拍板。独立评审照常进行。

| 决策 | 理由 |
|---|---|
| logo 字节存在 PostgreSQL 的 `accounts.site_logos`，每个 `(站点, SHA-256)` 一行，`sites.logo_hash` 指向当前行 | 仓库还没有对象存储，一个 logo 至多 256 KiB 且只有站长上传，放进数据库就能与审计、站点锁同事务，部署不增加第二个存储系统。按内容追加而不是覆盖，保证已经发出的地址永远返回同样的字节，不会让旧页面或缓存拿到新图；上限让历史增长可以忽略。放弃对象存储：为一项小配置引入新的故障域、生命周期和鉴权；放弃只存一行原地覆盖：内容寻址的长缓存会失效 |
| 只收 SVG、PNG、WebP；SVG 按元素和属性的允许列表重建，PNG 解码头部核对尺寸，WebP 先限制尺寸，再完整解码校验 | 允许列表比“删掉危险标签”的拒绝列表可靠：脚本、事件属性、`style`、外部 `href`、`url(http…)`、`foreignObject` 和 DTD 都不在输出里，设计工具带来的元数据也一并去掉。PNG 只信任解码器读到的尺寸，WebP 在尺寸限制后完整解码，挡住宣称很小、实际很大的解压炸弹；WebP 用 Go 官方的 `golang.org/x/image/webp` 完整解码（标准库没有 WebP 解码器），只有 VP8X 头或截断的数据不会入库；1024 像素和 256 KiB 的上限同时约束页面和数据库。拒绝 GIF 和 AVIF：当前没有解码器，且 logo 的用处不需要动画 |
| 公开地址带 SHA-256，返回 `public, max-age=31536000, immutable`；后台读取另给 data URL 预览 | 地址由内容决定，缓存一年也不会看到旧内容，换 logo 就是换地址；旧地址继续可用。控制台和官网只需要 `getSite.logo_url`，不必为 logo 增加一次数据库读；后台设置页用 `data_url` 在 `img-src 'self' data:` 下预览，公开接口仍是同源图片，不依赖外部服务或 `blob:`。`PUT` 的响应不带 data URL，避免幂等记录重复保存整张图 |
| 不新增站点 logo 的公开写接口；后台写要 MFA、`sites.manage`、CSRF、幂等键和理由，审计 `site_logo.update` | 复用现有管理接口的授权与幂等机制；logo 是站点配置，不是用户内容，线上只有平台管理员能改。审计只记 hash、类型、尺寸和字节数，不复制图片 |
| 管理后台的登录页和侧栏也显示站点 logo，登录前由一个公开的 `getAdminSite` 提供 | 验收要求控制台与后台登录页、侧栏都显示该站点的 logo；管理域名本身属于一个站点，品牌信息与 `getSite` 一样是公开的，不需要会话。后台仍保留管理语境：名称来自站点，页面标题和导航不变。logo 走管理域名下的公开地址，和页面同源，满足 `img-src 'self'`；设置页只预览，不改变版式 |

站点注册同意（Issue #325）按[负责人授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)中的「遇到问题自己解决问题和判断最优而不是问我。」落地数据模型和对外接口；法律文本本身仍由负责人提供，代码只用固定的占位文本测试，不写真实条款。部署和对外发消息仍由负责人拍板，独立评审照常进行。

| 决策 | 理由 |
|---|---|
| 文档按 `(站点, 类型, 版本)` 追加，正文只插不改不删；当前版本是该类型的最大版本，不另设当前指针 | 接受记录引用版本，必须永远指向当时给人看的文本；更正只能发新版本并让所有人重新同意，否则“同意过”会变成对未读文本的同意。最大版本由主键前缀直接得到，发布在站点行锁内取下一个编号，两个并发发布不会撞号；不设当前指针就没有指针与行不一致的第二种状态 |
| 注册时在创建用户的事务里重读当前版本并写接受行，开放注册把同意放到 `verify-email` | 开放注册在点击链接前没有用户可挂接受记录；邀请码则在 `register` 就有。把校验放在建用户事务内，版本过期和并发发布不会留下没有接受记录的用户。接受记录只插不改：首次时间就是同意时间 |
| 已登录用户每次认证在会话事务里比较当前版本；未接受时只放行读会话、接受和退出，其他控制台操作 403 `consent_required` | 发布新版本要立即生效，不能等 30 秒快照；比较在已有会话查询里做，不多一次往返。`getSession` 的未接受列表让页面知道要显示什么，接受接口不受拦截，否则用户会被锁死；退出也放行，避免用户只能强行清 Cookie |
| 站点没有文档时不要求同意 | 机制只交付机制，不替站长决定何时上线条款；升级不改变未配置站点的行为。文档未发布就要求同意会让所有现有站点在升级后立即不可用 |
| 首份文档只在全部服务节点和页面都支持同意机制后发布；发布后不把流量切回不认识该机制的旧版本 | 旧节点没有新查询和守卫，不检查 `legal_documents`；混合部署期间发布，注册和已登录请求会随负载均衡结果被放行或拒绝。表是新增的，旧节点不会因迁移失败，所以只能由发布顺序保证。页面也要先有入口，否则用户被 403 锁住 |
| 文本是公开数据，接受记录是账户数据；响应只回纯文本 | 注册页未登录就要显示文本，和站点 logo 一样按公开数据读；接受记录属于用户，按账户数据受行级安全约束。正文不渲染 HTML，页面按文本显示，避免站长粘贴的标记变成脚本 |
| 管理接口独立 `/legal-documents`，发布要 MFA、`sites.manage`、CSRF、幂等键和理由，审计只记版本、长度和摘要 | 与品牌色、注册策略一样不并入整体替换，旧页面不会抹掉不认识的字段；审计条目上限 8 KiB，正文最多 65536 字符，复制进去会让合法发布失败 |

自带供应商 key（BYOK，Issue #330 P16）按[负责人批准](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6566970847)中的「1-4自己判断」落地。能力默认关闭：站点设置 `AXIOM_BYOK=on` 后才接受建 key，开启本身是负责人的产品决定；关闭时产品范围与[产品路线](../product.md)的「以后」一致，不因为代码合入而提前。接口、存储与保管规则由编排者决定并写在这里，独立评审照常进行。

| 决策 | 理由 |
|---|---|
| 一把 key 是一个账户归属的供应商，复用 `suppliers` 的供应商、分组、凭证、端点和成本计划，不新建一套 key 表 | 凭证的信封加密、行级安全、凭证挑选、并发与每分钟上限、尝试成本、失败分类和路由快照都已经在 suppliers 里；另建一套会把加密、隔离、限流和失败路径各写第二遍。OpenRouter 的 BYOK 也是“供应商 + 凭证”的模型（[BYOK](https://openrouter.ai/docs/guides/overview/auth/byok)，2026-11-02）。代价是账户侧多一个很薄的接口，供应商表多一个 `byok` 状态 |
| 新供应商状态 `byok`，不新增 `is_byok` 列 | 旧节点的 `ListRoutable` 和 `ListSyncDue` 都按状态过滤，不认 `byok` 就不路由也不去同步；若沿用 `active`，旧节点会把这个供应商当成普通供应商送去同步，适配器不存在会一直失败重试。新状态仍不能把旧节点直接留在线上：旧节点的 `ListLiveSuppliers` 按 `status <> 'removed'` 读，会在启动检查里遇到 `byok` 而拒绝启动，所以先用默认关闭的 `AXIOM_BYOK` 让所有节点升级，再打开。 |
| 端点的成本计划全零，售价按站点的 BYOK 费率收 | 用户自己付给供应商，Axiom 的成本确实是 0；成本计划是路由和计费挑端点、算成本用的既有结构，填 0 比新增“无成本”分支少一条路径。费率按同模型参考价的比例（见[计费](billing.md#定价)），与 OpenRouter 一致 |
| 每次调用仍然先做准入和预留 | 即使成本为 0，服务费仍要占用余额、受余额底线和限额约束；把 BYOK 调用排除在准入之外会让它成为绕过预算和限流的通道 |
| 被拒绝的 key 写 `rejected` 并跳过，只有测试成功才恢复 | 供应商明确说 key 无效时继续重试既无效又可能触发对方的防护；持久化让重启和别的节点也不再选它。测试成功是唯一恢复路径，避免“停用再启用”把坏 key 放回路由。局限：供应商 401 之外的临时故障不标记，只走既有冷却 |
| 控制台复用 `api_keys.view/manage` 权限，不新增权限 | BYOK key 和调用 key 一样是账户凭证，能看/管账户 key 的人就是能看/管自带 key 的人；新增权限要迁移所有角色，且没有独立的职责分离需求 |

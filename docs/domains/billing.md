# 计费

钱怎么表示、成本怎么算、售价怎么定、余额怎么冻结和结算、账怎么记。对应代码模块 `billing`。概念之间的关系见[术语与核心概念](../glossary.md)，钱的通用规则见[总体架构的「工程原则」](../architecture.md#工程原则)。

## 要求

- 售价 = 实际服务该请求的供应商成本 + 加价（见[产品需求的「计价」](../product.md#计价)）。
- 计算必须正确，任何配置都不能让平台亏本卖。
- 加价方式多样且可配置；供应商改价后自动跟随，不需要人工。
- 内部用美元记账；真实汇率可以作为开关，为防波动可以略贵。
- 中转站一般用固定货币和固定的分组倍率，涨价体现为倍率变化。
- 会有其他中转站把 Axiom 当上游高频调用，单个账户的高并发不能成为瓶颈。
- 额度默认不过期，可以单独设置；退款需要人工审核；政策都可以按站点修改。

## 设计

### 钱的表示

- **额度**是站点的记账单位：1 额度 = 1 个单位的站点记账货币。主站用美元；二级站点可选美元或人民币。中转站习惯的"¥1 = $1"写法只是二级站点界面上的显示符号。
- **最小单位**是十亿分之一额度，用 64 位整数存储。
- **计算**：一个请求的各计费项先用不会溢出的大整数精确计算，加总后只取整一次。
- **取整方向一律对平台有利**：向用户收的钱向上取整，估算的成本向上取整，汇率朝不亏的方向折算；充值换成额度时向下取整。
- **显示与存储分开**：
  - 存储永远是精确值，只在显示时格式化；
  - 汇总先用精确值相加再显示，不把显示出来的数字再加起来；
  - 真实货币（充值、退款）按各自的最小单位处理，例如分、美分。
- **余额字段是账本合计的物化值**：每次记账在同一个事务里更新它；对账程序持续核对两者是否一致。

### 汇率

- **只在币种不同时换算**：例如主站上用人民币充值，或者人民币成本要折成美元。人民币收、人民币付不经过汇率。
- **每对货币一个参考汇率**，按"基础货币 / 报价货币 / 数值"带类型存储。参考汇率有两种来源：
  - 固定值；
  - 每天自动获取的真实汇率（开关）。

  人工覆盖要写理由、留审计；保存时与参考值偏离过大（比如把 7.1 填成了 0.14）就拒绝；真实汇率大幅波动时告警。
- **两个方向各设缓冲**：用户充值按对平台有利的方向换算；折算成本时把成本往高处算。
- **每笔交易当场锁定所用汇率**并记录下来，以后不再重算。
- **二级站点和主站币种不同**：由站长设定"1 本站额度 = 多少主站额度"，这只影响二级站点自己的定价；平台永远按主站额度向站长扣费，不承担二级站点的汇率风险。

### 额度批次

- **每次额度进账都是一个批次**：付费充值、赠送、兑换码、人工调整。每个批次记下来源、金额、是否可退，以及可选的过期时间。默认不过期；站点可以给某类来源（比如赠送）设默认有效期，管理员也可以给单个批次设过期时间。
- **消费时先用最早到期的批次**，不过期的最后用。这个分配由后台任务按消费总额计算，不在调用路径上增加写入。
- **批次到期**：剩余额度作废，按"额度过期"记账。
- **退款**：只有付费买来、没用掉、没过期的部分能退；必须人工或运营 agent 审核，受资金额度上限约束；退款政策由站点配置。用户注销前会提示剩余余额。

### 供应商成本

- **结算货币和单位价值**：每个供应商有结算货币（人民币或美元），并记录"1 单位余额 = 多少钱"。
  - 大多数中转站是 ¥1 = 1；new-api 系统默认是 7.3，站长可改（new-api 源码，2026-10）。
  - 适配器读出提示值，接入时由负责人或运营 agent 确认；之后发生变化，按生效时间记新值，旧账不动。
- **成本计划**：适配器为每个端点生成一份"用量 → 成本"的计算表，以供应商的结算货币计。它覆盖输入、输出、缓存读、缓存写（5 分钟 / 1 小时）、推理、图片、按次工具费、按上下文长度分档、分时段价格、服务等级。
  - "官方价 × 分组倍率"只是最简单的一种计划。new-api 的按次价格与表达式分档，sub2api 的价格覆盖、分时段与长上下文倍率，都由适配器翻译进同一张表。
  - 计费模块只认成本计划，不知道任何中转系统的细节。
- **官方 API**：官方价，有折扣就扣除。
- **号池**：成本计划可选"官方价 × 系数"，或"实际支出（订阅费、代理、封号损失）平摊并平滑"，按号池分组配置；实际支出始终单独统计。
- **每次尝试都记成本**：包括失败和被回退的尝试。收到上游任何字节之后不再重试别的端点。
- **实际成本以供应商的记录为准**：
  - new-api 用请求编号查逐笔扣费记录，sub2api 查实际费用；
  - 只能看到余额变化的供应商，按余额变化做整体对账，并标为高风险：同步更频繁，保本线更高；
  - 估算和实际对不上就告警，这也能发现偷改倍率、虚报用量。

### 定价

- **规则**由四部分组成：定价对象、适用人群、方法、约束。
- **优先顺序固定**：
  - 定价对象从具体到宽泛：端点 → 分组 → 供应商 → 模型 → 模型厂商 → 来源类型 → 全部；
  - 适用人群：指定等级 → 全部；
  - 先比定价对象再比适用人群，所以任何两条规则都能比出先后；两条规则的对象和人群完全相同时，拒绝保存。
- **方法**：
  - 成本加成：成本 ×（1 + 比例）+ 固定加价；比例也可以按利润率填写；
  - 参考价倍率：参考价 × 倍率。参考价有官方价时用官方价，否则由运营设定；可以选择按汇率换算，或者把参考价的数字直接计入本站货币（中转站惯例）；
  - 固定价：直接写出各计费项的价格。
- **约束**：
  - 保本线：售价不低于"成本 ×（1 + 最低利润率）"，按真实货币比较。触到保本线时自动提价并通知；单次提价超过上限就暂停这个端点并告警；
  - 相对参考价的上下限；
  - 显示取整。
- **作用范围**：平台和每个二级站点各有一套规则。二级站点的规则只给本站用户定价；站长自己的成本永远是主站对其等级的售价。
- **价目表**的计费项与成本计划一致；按次收费的项目（如联网搜索）也在其中。
- **自动重算**：成本计划、单位价值、汇率任何一个变化都会自动重算售价；变化超过阈值才发布新价格，避免来回跳动。
- **价格版本**：每次发布生成一个价格版本，连同当时的成本一起锁定。请求开始时锁定版本，结算按同一版本；长请求进行中成本发生变化，差额在对账中体现。
- **预览**：修改规则前可以预览各模型的售价和利润；运营 agent 也通过预览提交修改。

### 冻结与结算

- **冻结的状态**：已冻结 → 已结算 / 已释放 / 已超时。冻结单独存放，不是账本分录。
- **冻结多少**：预估输入（取偏大的估计）+ 输出上限，按锁定的价格版本计算。输出上限取请求里的最大输出和该模型配置的上限中较小的那个，避免并发多的账户被误拒。
- **钱不够时**：在调用上游之前返回 402，并指明是余额、工作区预算还是 key 上限不够。请求一旦开始，就不会因为余额中途掐断。
- **允许小额透支**：结算金额超过冻结额时照常扣，余额可以变成小额负数；负余额的账户在充值前拒绝新请求。透支超过站点配置的上限时，账户转入冻结状态并告警。
- **一个事务内完成**：冻结时检查账户余额、工作区预算和 key 上限，加锁顺序固定为账户 → 工作区 → key。
- **节点崩溃**：
  - 每笔冻结属于某个核心节点，节点定时报到；
  - 长请求定期把已产生的用量写入冻结记录；
  - 节点失联后，清理程序按最后记录的用量结算；没有记录就释放冻结，并发出"结算丢失"事件，交给供应商对账补齐。
  - 请求必须等自己的冻结写入数据库后才调用上游，所以节点在此之前崩溃不会丢钱。
- **热点账户**：按账户把几毫秒内的冻结和结算合并成一个事务，规则与逐笔处理完全相同。它是性能手段，由压测决定何时启用。
- **二级站点的请求**：
  - 同时冻结终端用户和站长两个账户，结算时用一笔交易同时记账；
  - 站长余额不足时，对终端用户返回通用错误，不泄露站长的财务信息，同时通知站长。

### 免单规则

- **不收费的条件**：输出 token 为 0，并且结束原因为空或出错。只有推理或只调用工具的回复有输出 token，照常收费。
- **按次计费的项目**（如联网搜索）照常收费。
- **记账**：免掉的上游成本记为免单损失；单个账户的免单次数异常时告警。
- **二级站点**：终端用户免单时，站长也免单。
- **用户中途取消**：立即中断上游，按已生成的部分收费。

### 账本

- **一张表**：所有记账在一张按月分区的表里，用"站点 + 货币"区分各站点的账。
- **科目**：用户与站长的余额、平台收入、二级站点收入、各供应商的预付余额（按币种）、供应商成本、汇兑损益、免单损失、额度过期、退款、赠送。
- **各种事件的记法都是固定的**：
  - 充值：收款渠道 → 用户余额（按锁定汇率）；
  - 结算：用户余额 → 收入；
  - 尝试成本：供应商预付余额 → 供应商成本；
  - 站长扣费：站长余额 → 平台收入；
  - 另有退款、额度过期、免单、冲正。
- **去重与更正**：交易按"请求编号 + 类型"去重；记错了不改原记录，记一笔冲正。
- **合并写入时**：账本按批次记，每个请求的明细另存并引用批次，批次金额必须等于明细合计。

### 风控状态

- **账户状态**：正常、负余额（拒绝新请求）、冻结（拒付、欺诈或透支超限）。
- 退款和冻结抢同一把锁，防止先退款再花钱。

### 自带货源的服务费

- 站点自带货源、用户自带厂商 key（以后的功能）：平台按"参考价 × 比例"收服务费，可以设每月免费额度。不用成本加成，因为平台在这种情况下没有成本，加成后结果仍是 0。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 每个站点用自己的记账货币，主站为美元 | 负责人同意用美元记账。二级站点可以用人民币，这样中转站"¥1 = $1"的惯例不需要一个假"美元"来表达 |
| 计算中途不取整，取整一律对平台有利 | 逐项取整会累积误差，缓存读这类便宜的计费项误差可达一倍以上；每次最多多收十亿分之一额度，保证永远不少收 |
| 汇率是开关，加两个方向的缓冲，交易时锁定 | 负责人要求。同币种进出不受汇率影响；跨币种的波动由缓冲承担；锁定后的账永远可追溯 |
| 二级站点的换算率由站长设定 | 负责人同意。平台按主站额度扣站长，不承担二级站点的汇率风险 |
| 额度批次，先用最早到期的批次 | 负责人要求额度默认不过期，但可以单独设置有效期；批次还能区分付费额度和赠送额度，决定哪些能退 |
| 成本计划由适配器生成 | 中转站的计价远不止"基础价 × 倍率"：new-api 有按次价格、表达式分档和工具附加费，sub2api 有价格覆盖、分时段和长上下文倍率（new-api、sub2api 源码，2026-10）。统一成一张表，计费模块不随中转系统变化 |
| 实际成本以供应商记录为准 | 估算会因同步滞后而失真；对账还能发现偷改倍率和虚报用量 |
| 每次尝试都记成本 | 失败和被回退的尝试同样花钱，不记就会高估利润 |
| 定价规则按两条轴、固定顺序比较 | "最具体者优先"在多个条件维度下比不出先后；固定顺序保证结果唯一 |
| 触到保本线就自动提价，超出上限则暂停端点 | 负责人要求不能亏本；自动提价满足"全自动"，设上限可以防止价格突变 |
| 钱不够时在请求开始前拒绝，允许小额透支 | 负责人同意。与 OpenRouter 的进行中额度检查一致，余额不足返回 402（OpenRouter 文档《Limits》，2026-10）；new-api 和 sub2api 也允许透支（源码，2026-10）。中途掐断会破坏 Claude Code 正在进行的修改 |
| 冻结是状态机，节点崩溃按检查点结算 | 否则崩溃后冻结的钱会永远卡住，或被错误释放 |
| 免单采用 OpenRouter 的定义 | 原定义"没有输出就不收费"可以被利用：发长提示词、故意让模型拒答，我们照付上游。OpenRouter 只在输出为 0 且结束原因为空或出错时免单，按次收费的项目照收（OpenRouter 文档《Zero Completion Insurance》，2026-10） |
| 不用 TigerBeetle 记账 | 它为高频记账而设计，但正式环境建议 6 台专用机器，集群规模建好后不能改，导出数据还需要 RabbitMQ（TigerBeetle 文档，2026-10），与单机起步冲突。PostgreSQL 加按账户合并写入已经够用 |
| 热点账户的合并写入由压测决定何时启用 | 规则不变，只是性能手段；先测量再启用，不提前增加复杂度 |
| 自带货源按参考价收服务费 | 成本加成在成本为零时算出 0；OpenRouter 对自带 key 也是按它本应收取的价格的比例收费（OpenRouter 文档《BYOK》，2026-10） |

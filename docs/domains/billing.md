# 计费

钱怎么表示、成本怎么算、售价怎么定、余额怎么冻结和结算、账怎么记。对应代码模块 `billing`。概念之间的关系见[术语与核心概念](../glossary.md)，钱的通用规则见[总体架构的「工程原则」](../architecture.md#工程原则)。

## 要求

- 售价 = 实际服务该请求的供应商成本 + 加价（见[产品需求的「计价」](../product.md#计价)）。
- 计算必须正确，任何配置都不能让平台亏本卖。
- 加价方式多样且可配置；供应商改价后自动跟随，不需要人工。
- 内部用美元记账；真实汇率可以作为开关，为防波动可以略贵。
- 中转站一般用固定货币和固定的分组倍率，涨价体现为倍率变化。
- 会有其他中转站把 Axiom 当上游高频调用，单个账户的高并发不能成为瓶颈。
- 额度默认不过期，可以单独设置；退款需要人工审核；政策都可以按站点修改。

## 设计

### 钱的表示

- **额度**是站点的记账单位：1 额度 = 1 个单位的站点记账货币。主站用美元；二级站点可选美元或人民币。中转站习惯的"¥1 = $1"写法只是二级站点界面上的显示符号。
- **金额**：最小单位是十亿分之一额度，用 64 位整数存储；汇总和统计用更宽的整数类型，不会溢出。
- **单价**：价目表和成本计划里的单价用精确小数存储。单价可能小于最小单位，例如每个 token 0.3 个最小单位，所以不能用整数存。
- **计算**：一个请求的各计费项先用精确的大整数分数计算，加总后只取整一次。
- **取整方向一律对平台有利**：向用户收的钱向上取整，估算的成本向上取整，汇率朝不亏的方向折算；充值换成额度时向下取整。
- **显示与存储分开**：
  - 存储永远是精确值，只在显示时格式化；
  - 汇总先用精确值相加再显示，不把显示出来的数字再加起来；
  - 真实货币（充值、退款）按各自的最小单位处理，例如分、美分。
- **余额字段是账本合计的物化值**：每次记账在同一个事务里更新它；对账程序持续核对两者是否一致。
- **可用余额** = 余额 − 进行中冻结的合计。

### 汇率

- **只在币种不同时换算**：例如主站上用人民币充值，或者人民币成本要折成美元。人民币收、人民币付不经过汇率。
- **每对货币一个参考汇率**，按"基础货币 / 报价货币 / 数值"带类型存储。参考汇率有两种来源：
  - 固定值；
  - 每天自动获取的真实汇率（开关）。

  人工覆盖要写理由、留审计；保存时与参考值偏离过大（比如把 7.1 填成了 0.14）就拒绝；真实汇率大幅波动时告警。
- **两个方向各设缓冲**：充值换算按对平台有利的方向；定价时把成本往高处算。缓冲只影响充值换算和定价；账上一律按锁定的参考汇率记账，差额记入汇兑损益。
- **每笔交易当场锁定所用汇率**并记录，以后不再重算。
- **二级站点和主站币种不同**：由站长设定"1 本站额度 = 多少主站额度"，这只影响二级站点自己的定价；平台永远按主站额度向站长扣费，不承担二级站点的汇率风险。

### 额度批次

- **每次额度进账都是一个批次**：付费充值、赠送、兑换码、人工调整。每个批次记下来源、金额、可选的过期时间；付费批次还记下每 1 额度实际付了多少钱和锁定的汇率。
- **过期时间**：默认不过期；站点可以给某类来源（比如赠送）设默认有效期，管理员也可以给单个批次设过期时间。
- **分配规则**：消费时先用最早到期的批次，不过期的最后用。分配由后台任务按时间顺序重放每一笔消费，结果确定且可复算，不在调用路径上增加写入。
- **到期**：批次在到期那一刻失效，到期时剩余的额度作废，按"额度过期"记账。记账任务每分钟运行一次；到期后、记账前这一小段时间里被花掉的部分，会让余额变成小额负数，按透支处理。
- **退款**：只有付费、没用掉、没过期的部分能退。办理时先在账户锁内把分配补算到当下；退还的金额按该批次当初的付款价和锁定汇率折算，与今天的汇率无关。必须人工或运营 agent 审核，受资金操作上限约束；退款政策由站点配置。用户注销前会提示剩余余额。

### 供应商成本

- **结算货币和单位余额价值**：每个供应商有结算货币（人民币或美元），并记录它的单位余额价值，即"1 单位余额 = 多少钱"。
  - 大多数中转站是 ¥1 = 1；new-api 系统默认是 7.3，站长可改（new-api 源码，2026-10）。
  - 适配器读出提示值，接入时由负责人或运营 agent 确认；之后如有变化，按生效时间记新值，旧账不动。
- **成本计划**：适配器为每个端点生成一份"用量 → 成本"的计算表，以供应商的结算货币计。它覆盖输入、输出、缓存读、缓存写（5 分钟 / 1 小时）、推理、图片、按次工具费、按上下文长度分档、分时段价格、服务等级。
  - "官方价 × 分组倍率"只是最简单的一种计划。new-api 的按次价格与表达式分档，sub2api 的价格覆盖、分时段与长上下文倍率，都由适配器翻译进同一张表。
  - 计费模块只认成本计划，不知道任何中转系统的细节。
- **官方 API**：官方价，有折扣就扣除。
- **号池**：成本计划可选"官方价 × 系数"，或"实际支出（订阅费、代理、封号损失）平摊并平滑"，按号池分组配置；实际支出始终单独记账。
- **每次尝试都记成本**，包括失败和被回退的尝试。已经向客户端转发任何内容之后，不再换端点。上游没有返回用量的尝试（比如超时），先按估算记一笔并打上标记，由对账补正。
- **以供应商的记录为准**：
  - 读取方式：new-api 用请求编号查逐笔扣费记录，sub2api 查实际费用；
  - 只能看到余额变化的供应商，按余额变化做整体对账，并标为高风险：同步更频繁，保本线更高；
  - 对用户的售价以请求时锁定的价格版本为准，不再变动；我们这边估算成本与供应商实际扣费的差额，记一笔成本调整；
  - 差额在容差内视为正常（成本按向上取整估算，会与供应商的取整方式略有偏差），超出容差就告警，这也能发现偷改倍率和虚报用量。

### 定价

- **规则**由四部分组成：定价对象、适用人群、方法、约束。
- **优先顺序固定**：
  - 定价对象从具体到宽泛：端点 → 分组 → 供应商 → 模型 → 模型厂商 → 来源类型 → 全部；
  - 适用人群：指定等级 → 全部；
  - 先比定价对象再比适用人群，所以任何两条规则都能比出先后；两条规则的对象和人群完全相同时，拒绝保存。
- **方法**：
  - 成本加成：成本 ×（1 + 比例）+ 固定加价；比例也可以按利润率填写；
  - 参考价倍率：参考价 × 倍率。参考价有官方价时用官方价，否则由运营设定；可以选择按汇率换算，或者把参考价的数字直接计入本站货币（中转站惯例）；
  - 固定价：直接写出各计费项的价格。
- **约束**：
  - **保本线**：每个计费项的售价都不低于该项成本 ×（1 + 最低利润率），成本按定价用的保守汇率折算。触到保本线时自动提价并立即发布，不受发布阈值限制，同时通知；单次提价超过上限就暂停这个端点并告警。
  - **相对参考价的上下限**。
  - **价格取整**：单价向上取整到展示精度，保证页面上显示的单价就是实际收取的单价。
- **作用范围**：平台和每个二级站点各有一套规则。二级站点的规则只给本站用户定价，同样有保本线，成本是站长的进价，站长可以调整最低利润率；站长自己的进价永远是主站对其等级的售价。
- **价目表**的计费项与成本计划一致；按次收费的项目（如联网搜索）也在其中。
- **自动重算**：成本计划、单位余额价值、汇率任何一个变化都会自动重算售价。降价或小幅涨价在变化超过阈值时才发布，避免价格来回跳；触到保本线的涨价立即发布。
- **价格版本**：每次发布生成一个价格版本，连同当时的成本一起锁定。请求开始时锁定版本，结算按同一版本；长请求进行中成本发生变化，差额在对账中体现。
- **预览**：修改规则前可以预览各模型的售价和利润；运营 agent 也通过预览提交修改。

### 冻结与结算

- **冻结的状态**：已冻结 → 已结算 / 已释放 / 超时结算 / 超时释放。每次状态变化都是"比较后再写"，同一笔冻结只能落到一个终态。冻结单独存放，不是账本分录。
- **冻结多少**：
  - 预估输入（取偏大的估计，图片、PDF 也计入）+ 输出上限 + 按次工具费的上限，按回退计划里最贵的那个端点的价格计算；
  - 输出上限取请求里的最大输出和该模型配置的上限中较小的那个，避免并发多的账户被误拒；
  - 回退时不会走到比冻结价更贵的端点。
- **钱不够时**：冻结后的可用余额不得低于"负的透支上限"，否则在调用上游之前返回 402，并指明是余额、工作区预算还是 key 上限不够。请求一旦开始，就不会因为余额中途掐断。
- **透支**：结算金额超过冻结额时照常扣，余额可以变成小额负数；负余额的账户在充值前拒绝新请求。透支上限按账户设置，默认值由站点配置，在冻结时就检查。
- **一个事务内完成**：冻结时检查账户余额、工作区预算和 key 上限。加锁顺序固定：先按账户编号从小到大锁账户，再锁工作区，最后锁 key；退款也用同样的顺序。
- **节点崩溃**：
  - 每笔冻结属于某个核心节点，节点定时报到；
  - 长请求定期把已产生的用量写入缓存，作为检查点。检查点只是尽力保存的证据，丢了也不影响账的正确性；
  - 节点失联后，清理程序处理它名下的冻结：有检查点的按检查点结算（超时结算），没有的释放（超时释放），并发出"结算丢失"事件，交给供应商对账补齐；
  - 如果节点只是网络中断，之后带着真实用量回来，而冻结已被清理，就把差额记为一笔补扣，不会因为去重而丢掉；
  - 请求必须等自己的冻结写入数据库后才调用上游，所以节点在此之前崩溃不会丢钱。
- **热点账户**：按账户把几毫秒内的冻结和结算合并成一个事务，规则与逐笔处理完全相同。它是性能手段，由压测决定何时启用。
- **二级站点的请求**：
  - 同时冻结终端用户和站长两个账户，结算时用一个事务分别记两边的账；
  - 站长余额不足时，对终端用户返回通用错误，不泄露站长的财务信息，同时通知站长。

### 免单规则

- **免单条件**：上游返回的输出 token 为 0，并且结束原因为空或出错，并且不是客户端主动取消。只有推理或只调用工具的回复有输出 token，照常收费。
- **客户端主动取消的请求从不免单**：立即中断上游，按上游报告的用量收费；上游没有报告用量时，按我们自己的估算收费。
- **按次计费的项目**（如联网搜索）照常收费。
- **上限**：每个账户、每个站点每天的免单成本有上限，超过后当天自动停止免单，并告警。
- **二级站点**：终端用户免单时，站长也免单，共用上面的上限。

### 账本

- **一张表**：所有记账在一张按月分区的表里，用"站点 + 货币"区分各站点的账。每个事件在每本账里借贷各自平衡；跨币种或跨站点的事件，在每本账里各记平衡的一组分录。
- **科目**：现金（按收款渠道和币种）、用户与站长的余额、平台收入、二级站点收入、供应商预付余额（按供应商和币种）、供应商成本、号池支出、赠送支出、汇兑损益、拒付损失、额度过期收入。
- **事件与分录**：

| 事件 | 借 | 贷 |
|---|---|---|
| 用户充值 | 现金 | 用户余额（按锁定汇率折算，差额记汇兑损益） |
| 赠送、兑换码 | 赠送支出 | 用户余额 |
| 请求结算 | 用户余额 | 平台收入（二级站点为站点收入） |
| 站长进货 | 站长余额 | 平台收入 |
| 尝试成本 | 供应商成本 | 供应商预付余额 |
| 成本调整（对账差额） | 供应商成本 | 供应商预付余额（差额为负时借贷对调） |
| 给供应商充值 | 供应商预付余额 | 现金 |
| 号池实际支出 | 号池支出 | 现金 |
| 退款 | 用户余额 | 现金 |
| 额度过期 | 用户余额 | 额度过期收入 |
| 拒付 | 拒付损失 | 现金 |
| 补扣（结算丢失后补回） | 用户余额 | 平台收入 |
| 冲正 | 原分录借贷对调 | |

- **免单不额外记账**：免单只是不记"请求结算"这一笔，尝试成本照常记入供应商成本，并打上"免单"标记，报表据此统计免单损失。
- **去重与更正**：交易按"请求编号 + 尝试序号 + 事件类型"去重；记错了不改原记录，记一笔冲正。
- **合并写入时**：同一组请求在账本里记为一笔汇总交易，每个请求的明细另存并引用它，汇总金额必须等于明细合计。

### 风控状态

- **账户状态**：正常、负余额（拒绝新请求）、暂停（拒付、欺诈或透支超过上限）。
- 退款与冻结按同样的顺序加锁，防止先退款再花钱。

### 自带货源的服务费

- 站点自带货源、用户自带厂商 key（以后的功能）：平台按"参考价 × 比例"收服务费，可以设每月免费额度。不用成本加成，因为平台在这种情况下没有成本，加成后结果仍是 0。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 每个站点用自己的记账货币，主站为美元 | 负责人同意用美元记账。二级站点可以用人民币，这样中转站"¥1 = $1"的惯例不需要一个假"美元"来表达 |
| 计算中途不取整，取整一律对平台有利 | 逐项取整会累积误差，缓存读这类便宜的计费项误差可达一倍以上；每次最多多收十亿分之一额度，保证永远不少收 |
| 汇率是开关，加两个方向的缓冲，交易时锁定；账上按参考汇率记 | 负责人要求。同币种进出不受汇率影响；跨币种的波动由缓冲承担；账上不记缓冲后的汇率，利润和供应商余额才不会漂移 |
| 二级站点的换算率由站长设定 | 负责人同意。平台按主站额度扣站长，不承担二级站点的汇率风险 |
| 额度批次，先用最早到期的批次；分配由后台按时间顺序重放 | 负责人要求额度默认不过期，但可以单独设有效期；批次还区分付费和赠送，决定哪些能退。没选"每次结算时实时扣减批次"：那样每个请求都要多写一行，热点账户压力加倍 |
| 退款按当初付款价和锁定汇率折算 | 按今天的汇率退，会出现"按缓冲后汇率充值、按有利汇率退款"的套利 |
| 成本计划由适配器生成 | 中转站的计价远不止"基础价 × 倍率"：new-api 有按次价格、表达式分档和工具附加费，sub2api 有价格覆盖、分时段和长上下文倍率（new-api、sub2api 源码，2026-10）。统一成一张表，计费模块不随中转系统变化 |
| 售价锁定，成本以供应商记录为准 | 用户看到的价格必须确定；估算成本会因同步滞后而失真，对账既修正利润，又能发现偷改倍率和虚报用量 |
| 每次尝试都记成本，去重键包含尝试序号 | 失败和被回退的尝试同样花钱；不带尝试序号，回退时第二笔成本会被当成重复丢掉 |
| 定价规则按两条轴、固定顺序比较 | "最具体者优先"在多个条件维度下比不出先后；固定顺序保证结果唯一 |
| 保本线按计费项检查，触线涨价立即发布 | 负责人要求不能亏本；只看总价时，某个计费项可能单独低于成本；发布阈值不能压住保本涨价 |
| 钱不够时在请求开始前拒绝，透支有上限 | 负责人同意。与 OpenRouter 的进行中额度检查一致，余额不足返回 402（OpenRouter 文档《Limits》，2026-10）；new-api 和 sub2api 也允许透支（源码，2026-10）。中途掐断会破坏 Claude Code 正在进行的修改。冻结按回退计划里最贵的端点和工具费上限计算，透支才真正有界 |
| 冻结是状态机，检查点存在缓存里 | 否则节点崩溃后冻结的钱会永远卡住或被错误释放。检查点放在数据库会给每路长流增加周期性写入（5000 路流每 10 秒约 500 次每秒）；放在缓存里丢了也只是退回供应商对账，正确性不受影响 |
| 免单采用 OpenRouter 的定义，取消不免单，免单有上限 | 原定义"没有输出就不收费"可以被利用：发长提示词、故意让模型拒答或立即断开，我们照付上游。OpenRouter 只在输出为 0 且结束原因为空或出错时免单，按次收费的项目照收（OpenRouter 文档《Zero Completion Insurance》，2026-10） |
| 不用 TigerBeetle 记账 | 它为高频记账而设计，但正式环境建议 6 台专用机器，集群规模建好后不能改，导出数据还需要 RabbitMQ（TigerBeetle 文档，2026-10），与单机起步冲突。PostgreSQL 加按账户合并写入已经够用 |
| 热点账户的合并写入由压测决定何时启用 | 规则不变，只是性能手段；先测量再启用，不提前增加复杂度 |
| 自带货源按参考价收服务费 | 成本加成在成本为零时算出 0；OpenRouter 对自带 key 也是按它本应收取的价格的比例收费（OpenRouter 文档《BYOK》，2026-10） |

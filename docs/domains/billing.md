# 计费

钱怎么表示、成本怎么算、售价怎么定、余额怎么预留和结算、用量从哪来、账怎么记。对应代码模块 `billing`，调用路径上的接口、预留的状态和写入的数据见[模块 README](../../internal/billing/README.md)。概念之间的关系见[术语与核心概念](../glossary.md)，钱的通用规则见[总体架构的「工程原则」](../architecture.md#工程原则)。

## 要求

- 售价 = 实际服务该请求的供应商成本 + 加价（见[产品需求的「计价」](../product.md#计价)）。
- 计算必须正确，任何配置都不能让平台亏本卖。
- 加价方式多样且可配置；供应商改价后自动跟随，不需要人工。
- 内部用美元记账；真实汇率可以作为开关，为防波动可以略贵。
- 中转站一般用固定货币和固定的分组倍率，涨价体现为倍率变化。
- 会有其他中转站把 Axiom 当上游高频调用，单个账户的高并发不能成为瓶颈。
- 额度默认不过期，可以单独设置；退款需要人工审核；政策都可以按站点修改。
- 六条红线，每条都由下文的机制和[怎么验证](#怎么验证)里的测试守着：
  1. 钱守恒：每次变动都是借贷平衡的账本记录，余额等于记录之和；
  2. 不重复扣：同一请求的同一次尝试只结算一次；
  3. 不会算不出钱：上架前检查价目表完整，运行中缺价有兜底，不因此拒绝结算或不收钱；
  4. 欠款有硬上限：调用的收费从不让余额低于余额底线（拒付这类支付冲回不是调用收费，见[风控状态](#风控状态)）。每个预留都含它可能超出的最大量（超额额度），准入把所有在途预留一起计入；收费在写入时检查，万一超出可用余额，超出部分由平台承担、记录并告警，不记在用户账上；
  5. 可解释：每笔费用都有明细和用量来源，改账只追加冲正；
  6. 可对账：每天自己对平，并与供应商对平。

## 设计

### 钱的表示

- **额度**是站点的记账单位：1 额度 = 1 个单位的站点记账货币。主站用美元；二级站点可选美元或人民币。中转站习惯的"¥1 = $1"写法只是二级站点界面上的显示符号。
- **金额**：最小单位是十亿分之一额度，用 64 位整数存储；汇总和统计用更宽的整数类型，不会溢出。
- **单价**：价目表和成本计划里的单价是十进制定点数，用 64 位整数存储，单位是 10⁻¹⁵ 个币种单位每计费单位（每个 token 或每次）：最多 15 位小数，每单位最多 1000 个币种单位，超出就拒绝保存。单价可能远小于金额的最小单位，例如每个 token 0.3 个最小单位，所以不用金额的单位存。
  - 录入的单价只能从十进制文本构造。
  - 算出来的单价从精确分数向上取整：成本计划里官方价乘分组倍率的结果可能超过 15 位小数（例如每 token 0.000000075 × 0.123456789），向上取整到 10⁻¹⁵，与"估算的成本向上取整"一致；售价的单价向上取整到展示精度（见[定价](#定价)的价格取整）。
- **计算**：价目表先算出一个请求的精确金额，用 128 位整数表示，单位同单价；用量和单价都有上限，这个范围内不会溢出，运算仍逐步检查。汇率和加价倍率不是有限小数（例如 1 人民币 = 10/71 美元），乘它们时转成精确的大整数分数，全部算完后只取整一次。
- **转成金额时检查范围**：精确值转成金额时向上取整。用量在入口和上游回报处都有上限（见[用量来源与暂估](#用量来源与暂估)），结算金额又受预留约束，超出金额的存储范围只可能是程序错误：用断言守住，不回绕。
- **取整方向一律对平台有利**：向用户收的钱向上取整，估算的成本向上取整，汇率朝不亏的方向折算；充值换成额度时向下取整。
- **显示与存储分开**：
  - 存储永远是精确值，只在显示时格式化；
  - 汇总先用精确值相加再显示，不把显示出来的数字再加起来；
  - 真实货币（充值、退款）按各自的最小单位处理，例如分、美分。
- **余额字段是账本合计的物化值**：每次记账在同一个事务里更新它；对账程序持续核对两者是否一致。
- **可用余额** = 余额 − 在途预留。

### 汇率

- **只在币种不同时换算**：例如主站上用人民币充值，或者人民币成本要折成美元。人民币收、人民币付不经过汇率。
- **每对货币一个参考汇率**，按"基础货币 / 报价货币 / 数值"带类型存储。参考汇率有两种来源：
  - 固定值；
  - 每天自动获取的真实汇率（开关）。

  人工覆盖要写理由、留审计；保存时与参考值偏离过大（比如把 7.1 填成了 0.14）就拒绝；真实汇率大幅波动时告警。
- **两个方向各设缓冲**：充值换算按对平台有利的方向；定价时把成本往高处算。缓冲只影响充值换算和定价；账上一律按锁定的参考汇率记账，差额记入汇兑损益。
- **每笔交易当场锁定所用汇率**并记录，以后不再重算。一个请求的汇率在预留时锁定，结算（以及以后接回的校正）都用它。
- **二级站点和主站币种不同**：由站长设定"1 本站额度 = 多少主站额度"，这只影响二级站点自己的定价；平台永远按主站额度向站长扣费，不承担二级站点的汇率风险。

### 资金来源

- 调用的钱从账户的某个资金来源扣。M1 只有一种：余额钱包。
- 订阅套餐（M2）作为另一种资金来源接入，账本和结算流程不变（new-api 也把钱包和订阅抽象成同一个资金来源接口，new-api 源码 `service/funding_source.go`，2026-10）。

### 额度批次

- **现状**：每次手动加额度都写一个批次（来源只有赠送），管理员可以给它设过期时间；分配、到期已实现（代码结构见[模块 README 的「额度批次的分配与到期」](../../internal/billing/README.md#额度批次的分配与到期)）。付费、兑换码、人工调整这几种来源，以及退款、拒付，随支付设计，还没有。
- **每次额度进账都是一个批次**：付费充值、赠送、兑换码、人工调整。每个批次记下来源、金额、可选的过期时间；付费批次还记下实付金额（付款币种的最小单位）、其中的手续费、入账额度和入账所用的汇率，退款和拒付按它们折算。管理员手动加额度时要选来源：赠送，或线下付款（记付款价，按"用户充值"记账，收款渠道记为线下）。
- **过期时间**：默认不过期；站点可以给某类来源（比如赠送）设默认有效期，管理员也可以给单个批次设过期时间。
- **分配规则**：消费时先用最早到期的批次，不过期的最后用；同时到期的先用赠送，后用付费，再按先后。分配由后台任务按账本里的先后顺序重放账户余额的每一笔变动，结果确定且可复算，不在调用路径上增加写入：从头重放和从上次存下的位置接着重放结果相同。重放的规则：额度进账开出批次，并先还清此前超出所有批次的扣费（欠款）；扣费按上面的顺序用批次，批次用不到的记为欠款；**冲回（扣费退回用户余额）待定**（[#277](https://github.com/TYCT-tyct/Axiom/issues/277)，暂估校正是第一个会产生它的）：现在账本里没有任何代码产生非零的冲回，重放遇到就停下这个账户并报错、计入失败指标，不会悄悄记错。真做时要满足两条：一个请求的冲正加重新结算要按请求净额处理，不能把原来扣在会到期的批次上的额度，在期间有了更早到期的新批次时换成不到期的额度；批次耗尽并存下之后才发生的冲回，也要被周期扫描选中，不能因为批次缓存里剩余为 0 就永远不重放。不变量：重放到最新后，各批次剩余之和减去欠款，恰好等于余额；任何批次的已用加已作废不超过金额；有欠款时没有批次还剩额度。
- **到期**：批次在到期那一刻失效，到期时剩余的额度作废，按"额度过期"记账。记账任务每分钟运行一次（队列上的周期任务，只有队列的领导节点插入），对每个有到期批次的账户，先在不加锁的短事务里分页把分配重放到接近最新（长历史的账户不会因此长时间占着锁），再在账户的余额行锁内补齐、作废：只作废这一刻这个批次仍未花掉的部分；到期后、记账前被花掉的部分算作有效使用。作废的金额不超过 min(余额 − 在途预留 − 余额底线, max(0, 余额 − 在途预留))，因为底线 ≤ 0，就是 max(0, 余额 − 在途预留)：**底线是给扣费用的额度，不给作废用**，作废从不制造欠款。按到期先后依次作废，在途预留占着的部分留到下一轮。所以作废不会让在途请求的结算越线：结算最多收 余额 − 底线 − 其他在途预留，作废后余额仍不低于在途预留，该请求自己的预留一定收得下，平台不承担任何金额。同一批次可以分几轮作废，每笔"额度过期"交易的版本号是它作废前该批次已作废的累计额，因此不重复；一轮没有可作废的就什么也不写。重放结果与余额对不上的账户不作废，报错等人处理。
- **隔离与进度**：每个账户有自己的时间预算（30 秒），一轮有总预算（5 分钟，都小于队列的任务期限）；一个账户超时或出错就计数、记日志，继续下一个账户，任务本身不算失败（失败的任务会退避重试，并挡住下一轮的插入，一个坏账户会拖住所有账户）。扫描的位置（最后处理的账户 ID）存在 `billing.expiry_cursor`，一轮用完预算就停，下一轮从那里接着，扫到末尾再从头开始，所以排在后面的账户不会被前面一直失败的账户饿着。
- **排障**：计数器 `axiom.billing.expire.failures`（每个失败的账户加 1）或 Error 日志「credit could not be written off」，一轮最多列 20 个账户，其余给总数。常见原因：重放结果与余额对不上（日志里写明各自的数；先查这个账户有没有绕过账本直接改过余额），或被长事务占着余额行锁。要让一个账户的分配重新来过：因为作废都记在账本里，从头重放能复现全部结果，在超级用户下把该账户 `balances` 的 `allocated_seq`、`allocated_at`、`allocated_id`、`unfunded` 改回默认值（0、`epoch`、全零 UUID、0），再把它的 `credit_batches` 的 `consumed`、`expired` 清零，下一轮会重新放一遍；清零到下一轮之间，该账户的到期暂时不动。
- **退款**：只有付费、没用掉、没过期、没被冻结的部分能退。办理时先在账户锁内把分配补算到当下，同样不动在途预留占着的部分（补算分配即代码里的 `loadAllocation` 加 `catchUp`）；可退额度 = min(该批次剩余 − 已冻结, max(0, 余额 − 在途预留 − 全部冻结))，与作废一样不用余额底线。随后**冻结**这部分额度，再由支付调用渠道（流程见[支付的「退款」](payments.md#退款)）：冻结不改余额、不记分录，但准入时不算可用余额、分配时跳过它、到期时不作废它；渠道成功时在一个事务里转成"退款"分录，失败时解冻。**冻结和解冻是重放的事件**：与到期作废一样，在余额行锁内各记一笔带序号的交易（没有分录，只占一个序号），分配按序号重放到它时才改这个批次的冻结额，所以从头重放时每笔扣费看到的是它当时的冻结额，与现场一致；不这样做，当前的冻结额会作用到全部历史扣费上，重放结果与现场不同，批次剩余可能小于冻结额，转成退款时把批次扣成负数。**退还的金额**按该批次记下的实付和入账额度的比例折算：净付款额 = 实付 − 其中的手续费（站点政策为退手续费时就是实付；一笔订单用哪种由它的第一笔退款按当时的政策定下，之后的退款沿用，政策中途改了也不会让余数变成负数），一笔退款退 ⌊退款额度 × 净付款额 ÷ 入账额度⌋，让累计退款额度达到入账额度的那一笔退净付款额减去此前已退的金额；所以任何拆法下累计退款都不超过净付款额，全额退款恰好等于它。与今天的汇率无关，也与订单的报价无关：过期后按到账汇率入账的批次，按它实际的付款和额度算。必须人工或运营 agent 审核，受资金操作上限约束；退款政策由站点配置。用户注销前会提示剩余余额。
- **拒付**：扣回该批次的入账额度减去已成功退款的额度（已退的不重复扣），已经用掉的部分让余额变成负数（见[风控状态](#风控状态)）。

### 供应商成本

- **结算货币和单位余额价值**：每个供应商有结算货币（人民币或美元）和单位余额价值，即"1 单位余额 = 多少钱"；两者是供应商的数据，由供应商模块存和确认（见[供应商的「接入流程」](suppliers.md#接入流程)），计费按尝试开始时的回执里的值换算成本。
  - 大多数中转站是 ¥1 = 1；new-api 系统默认是 7.3，站长可改（new-api 源码，2026-10）。
  - 接入时用适配器读出的提示值，由负责人或运营 agent 确认；此后按每次给该供应商充值的实付金额和到账余额加权平均，追加新值，旧账不动。新值从节点的下一次 Reload 起生效，所以节点用的是它最近一次 Reload 时的快照，不一定是当时最新的一行。
  - 确认之前，这个供应商的端点不进路由。每次尝试按它开始时节点快照里的那个值换算，回执带着那个值和它的行 id（行 id 目前只在内存里的回执中，`attempt_costs` 没有 `unit_value_id` 列；要按 id 复算已结算的尝试，先给它加这一列，是兼容的改动）：原生金额 × 单位余额价值 = 结算币种的金额，精确相乘，转成金额时向上取整一次。结算币种与站点的记账货币不同时要经[汇率](#汇率)，汇率还没有实现之前这类尝试的成本记为未知：账上记 0。
- **成本计划**：适配器为每个端点生成一份"用量 → 成本"的计算表，按供应商的原生单位计（new-api 是每 token 多少 quota，sub2api 是美元），币种写 `XXX`（不涉及货币），由计费换算成钱。它用目录的价目表结构，计费项和条件以[模型目录的「价目表的结构」](catalog.md#价目表的结构)为准。
  - "官方价 × 分组倍率"只是最简单的一种计划。new-api 的按次价格与表达式分档，sub2api 的价格覆盖与长上下文倍率，都由适配器翻译进同一张表。价目表不支持分时段价格（负责人决定，Issue #24），带分时段价格的端点不使用；其他价目表还表达不了的，在它支持之前同样不使用。
  - 成本计划写明该供应商是否对按次项目（如联网搜索）收费：实测 new-api（v1.0.0-rc.44）和 sub2api（0.2.16）都没有对联网搜索单独收费，sub2api 的扣费恰好等于各 token 项之和（2026-10-14 本地实测）。对账核实这一点。
  - 计费模块只认成本计划，不知道任何中转系统的细节。
- **官方 API**：按官方原价计算，不考虑优惠和折扣；实际少付的部分体现在对账后的利润里。
- **号池**：成本计划可选"官方价 × 系数"，或"实际支出（订阅费、代理、封号损失）平摊并平滑"，按号池分组配置；实际支出始终单独记账。
- **每次尝试都记成本**，包括失败和被回退的尝试。已经向客户端转发任何内容之后，不再换端点。上游没有返回用量的尝试（比如超时），先按估算记一笔并打上标记，由对账补正。
- **以供应商的记录为准**（**M1 现状**：逐条匹配、容差判定、摘牌、暂挂和告警已由 River 每分钟运行；启动和换主也运行，重复或迟到不重复记版本。归属与版本事件落在供应商表里，billing 消费事件、成本分录校正、按 key 按天总数及余额变化对账尚未接入。任务边界见[供应商模块的「对账」](../../internal/suppliers/README.md#对账)，账本每天自己对平见[账本](#账本)。下面同时列出目标设计）：
  - 逐条记录按我们的请求对上：new-api 中转站按它返回的响应头 `X-Oneapi-Request-Id` 精确查询，被取消的请求也查得到；sub2api 中转站按它返回的响应头 `X-Client-Request-Id` 对上用量列表里的 `request_id`（多一个 `client:` 前缀），普通用户的用量列表能看到这个字段，但不能按它筛选，所以翻最近的记录去对；它不采用调用方自己传的这个头。自有号池以管理员身份按请求号查。以上均为 2026-10-14 本地实测（new-api v1.0.0-rc.44、sub2api 0.2.16）。
  - 某条记录缺失时，退回按 key 按天的总数对账；只能看到余额变化的供应商，按余额变化做整体对账，并标为高风险：同步更频繁，保本线更高；
  - 每天对账：逐条记录与我们记的成本比对，供应商余额的变化与同期成本比对；
  - 对用户的售价以请求时锁定的价格版本为准，不随供应商的记录变动；我们这边估算成本与供应商实际扣费的差额，记一笔成本调整；
  - 差额在容差内视为正常（成本按向上取整估算，会与供应商的取整方式略有偏差），超出容差就告警并提示更新成本计划，这也能发现偷改倍率和虚报用量。
  - **一次尝试至多对上一笔扣费，一笔扣费至多对上一次尝试**。对账键相同的尝试有两个以上时哪个都不对上（分不清是哪个）。容差 = 供应商自己的取整（new-api 每笔取整到 1 quota，sub2api 十位小数）加估算的 1%（后台可调）。实际高于估算且超出容差（估算偏低）：该端点立即改回"成本未知"、退出路由并告警，损失上限是两次对账之间的调用；低于估算只告警。估算漏了没有定价的项，或上游没有用量，不做这个判断。
  - **宽限和暂挂**：扣费记录 30 分钟（后台可调）还没有对上的尝试，状态改为"暂挂"：不记账、不猜是哪个用户，在报表里单列，由运营人员或 agent 归到某个丢失的请求（billing 把该请求的暂估调整为这些扣费之和），或确认为"未归属成本"（记供应商成本，不向任何用户收费）。暂挂或已归属之后真实的尝试才到（节点带着尝试回来），扣费改归到这次尝试，旧归属在同一次更改里撤销。有对账键的尝试过了宽限仍没有扣费记录，只告警，之后到达照常对上。
  - **事件带版本**：扣费记录每次变化（对上、暂挂、归属）版本加一，同一事务里写一条 `ChargeSettled` 事件（扣费记录、版本、归属、实际与估算金额、判定）。billing 按（扣费记录，版本）幂等处理，并把它已记的分录调整到最新版本所描述的状态；以 `actual` 对照它自己已记的金额算调整，事件里的估算只供参考。
  - 只支持钱包资金：订阅扣的是订阅窗口不是钱包，扣费记录带资金来源，不是钱包的供应商暂停并告警。
  - **M1 的对账只到成本**：供应商记录只用于成本和差额，不动用户收费（[用量来源与暂估](#用量来源与暂估)）；版本事件已写入 `charge_events`；上面这些把暂估调整到记录的账本变更，随事件消费与校正作业接回时再加（[#28](https://github.com/TYCT-tyct/Axiom/issues/28)）。
- **供应商余额**：低于阈值时告警；付不起这次请求预估成本的端点不进路由（见[路由](routing.md#一个请求的路由步骤)）。M1 还没有按这次请求的预估成本过滤，也没有供应商报告余额不足后让整家休息（[#228](https://github.com/TYCT-tyct/Axiom/issues/228)）。

### 定价

- **规则**由四部分组成：定价对象、适用人群、方法、约束。
- **优先顺序固定**：
  - 定价对象从具体到宽泛：端点 → 分组 → 供应商 → 模型 → 模型厂商 → 来源类型 → 全部。**M1 只生效模型、模型厂商、全部三种**：路由快照里没有按端点、分组、供应商、来源类型区分的价格，所以保存或预览其余几种会被拒绝（422，指向 `/rule/target/kind`），与下面的人群同理；
  - 适用人群：指定账户 → 指定等级 → 全部（与 sub2api 的"用户专属 > 分组 > 默认"同理，sub2api 源码，2026-10）。**M1 只接受"全部"**：路由快照和它锁定的价格是一个节点一份，给某个账户或等级的规则没法按人群生效，所以保存或预览这样的规则会被拒绝（422，指向 `/rule/audience/kind`），而不是接受后悄悄按"全部"的价收费；按账户、按等级的加价在快照可以按人群区分之后再做，存储形式和上面的优先顺序已经为它留好；
  - 先比定价对象再比适用人群，所以任何两条规则都能比出先后；两条规则的对象和人群完全相同时，拒绝保存。
- **加价规则只有这一处**：给某个等级或某个账户的加价，是这里的一条规则，人群指向它；等级表本身不存加价（见[账户与租户的「等级」](accounts.md#等级)）。
- **方法**：
  - 成本加成：成本 ×（1 + 比例）+ 固定加价；比例也可以按利润率填写。M1 保存或预览会被拒绝（422，指向 `/rule/method/kind`）：它要以供应商的成本为底，随 M2；
  - 参考价倍率：参考价 × 倍率。参考价取模型目录里为该模型选定的价格来源：LiteLLM 价格库、OpenRouter、官方价格页或手填（见[模型目录的「目录基线」](catalog.md#目录基线)）；可以选择按汇率换算，或者把参考价的数字直接计入本站货币（中转站惯例）。M1 只实现这一种和固定价，而且这一种只在参考价本身就是本站货币时给得出售价：数字照抄，即 `face`。参考价是别的币种时照抄等于按 1:1 换汇，没有汇率依据；要靠汇率换算的（`exchange`，缺省的换算方式同样算）和成本加成（`cost_plus`）也不在 M1 之内，保存和预览都会被拒绝（422，指向 `/rule/method/currency_conversion`、`/rule/method/kind`），不接受之后悄悄不生效。参考价是别的币种的模型，`face` 规则也给不出售价，预览里逐条报出来；
  - 固定价：直接写出各计费项的价格。
- **计费项**：输入、输出、缓存读、缓存写（5 分钟 / 1 小时）、推理、音频进出、图片进出、按次工具（联网搜索、代码执行，代码当前也按次数计，厂商实际按容器时长收，口径待定，见 [#28](https://github.com/TYCT-tyct/Axiom/issues/28)），每项一个单价；推理没有单独定价时按同档的输出价计。长上下文按用量分档；标准档以外的服务等级（flex、priority、fast）各有完整的一套单价，没录的计费项是缺价，不沿用标准档（见[模型目录的「价目表的结构」](catalog.md#价目表的结构)）。逐项单价学 sub2api 和 LiteLLM，不学 new-api 的倍率套倍率。
- **约束**：
  - **保本线**：售价的价目表和成本计划按用量区间比较：两边的门槛合在一起把用量切成若干区间，在每个区间里、对每个计费项，售价的生效单价都不低于成本的生效单价 ×（1 + 最低利润率），成本按定价用的保守汇率折算。生效单价指该区间所在档位的单价，含缺价回退（推理按输出价）。只比同一档的单价不够：成本 128k 以上每百万 $2.50，售价 200k 以上才从 $1.375 涨到 $2.75，两边逐档比较都过关，150k 的提示词却按 $1.375 卖出 $2.50 的成本。两边的门槛口径不同就无法这样比较，这样的端点在支持之前不使用。触到保本线时自动提价并立即发布，不受发布阈值限制，同时通知；单次提价超过上限时，新的价格版本不给这个端点售价并告警，路由按"没有售价"把它排除（不改供应商那边的端点启用状态）。**M1 没有保本线**（[#234](https://github.com/TYCT-tyct/Axiom/issues/234)）：售价只是参考价乘倍率，或固定价，不与成本比较；供应商调高分组倍率时平台可能亏本卖。M1 的补偿是对账发现估算偏低就让端点退出路由，但它只判断成本估算是否准确，不验证售价是否高于成本；准确估算配上过低售价的亏损风险仍由保本线解决。
  - **相对参考价的上下限**。
  - **价格取整**：单价向上取整到展示精度，保证页面上显示的单价就是实际收取的单价。
- **作用范围**：平台和每个二级站点各有一套规则。二级站点的规则只给本站用户定价，同样有保本线，成本是站长的进价，站长可以调整最低利润率；站长自己的进价永远是主站对其等级的售价。
- **价目表**的计费项与成本计划一致；按次收费的项目（如联网搜索）也在其中。
- **上架门槛**：上游可能报告的每个计费项都有售价，模型才能上架；已知的按次项目没有模型自己的单价时，用该类项目的站点默认单价（见[价目表缺项](#价目表缺项)）。没有售价的模型在调用前拒绝。门槛按模型检查，不在调用前逐个请求特征拒绝；运行中出现我们不认识的计费项时按[价目表缺项](#价目表缺项)处理。它查的是售价本身，不问上游实际回报了什么：模型只声明标准档时，只有标准档的售价就是完整的；上游偶尔在别的等级服务它，那次调用按[价目表缺项](#价目表缺项)收。站点默认单价只补售价，不补参考价：参考价是模型自己的官方价，上架时仍要覆盖它声明的每一项（`catalog/admin_price.go` 的 `covers`）。
- **参考价的安全阀**：自动同步来的参考价先过合理性检查（单位、缓存读价不高于输入价等；缓存写可以高于输入价，如 Anthropic 的 5 分钟写入是输入价的 1.25 倍、1 小时写入是 2 倍），不过就不采用并告警；变化超过阈值要管理员确认后才用于重算。售价永远不低于保本线。
- **自动重算**（**M1 现状**：售价在路由快照每次重建时，按规则对目录快照里的参考价现算，快照每 5 秒重建、目录快照另有 5 秒轮询，所以参考价变了，售价最多十来秒后就跟着变；没有发布动作、变化阈值和保本线，成本也不参与定价，[#234](https://github.com/TYCT-tyct/Axiom/issues/234)。下面是目标设计）：成本计划、单位余额价值、汇率、参考价任何一个变化都会自动重算售价。参考价跟踪的是该模型选定的价格来源；它的变化不靠事件传过来，而是比对状态（[总体架构的规则 2](../architecture.md#模块边界规则)允许的另一种做法）：价格版本记下所用参考价的版本，后台任务默认每 5 分钟按选用规则重新选一次（选定来源有站点币种的价格就用它，没有才用其他币种按汇率换算），选出的版本与记下的不同就重算；所以站点币种的价格后来才录入时，也会换过去。漏掉的变化下一轮补上，所以参考价的变化最多滞后一个周期进入重算。降价或小幅涨价在变化超过阈值时才发布，避免价格来回跳；触到保本线的涨价立即发布。
- **价格版本**（**M1 现状**：版本只是规则 ID、规则 rev 和参考价行的摘要，随快照现算，不是一次发布；它没有写进预留行和调用记录，所以 M1 看不到某次调用用的价格版本。下面是目标设计）：每次发布生成一个价格版本，连同当时的成本一起锁定。请求在预留时锁定版本，结算按同一版本；长请求进行中成本发生变化，差额在对账中体现。固定价不读参考价，它的版本里参考价那一项为空，发布参考价不会让固定价换版本。
- **预览**：修改规则前可以预览各模型的售价（`PreviewPricing`）；利润要每端点的成本，随 M2 的成本侧一起加入。运营 agent 也通过预览提交修改。一条规则把某个模型的单价乘过了单价能表示的上限时，只有那个模型按没有售价处理并告警：倍率的上限取决于规则套到哪个模型的参考价上，保存规则时看不到，而一个模型不该让整站的售价一起失败。

### 预留与结算

- **M1 现状：每次预留都是全额**。路由快照里的端点没有输出速度，没有条目能分段，所以下面的分段预留、追加和超额额度在 M1 都不运行，输出一律按上限预留（接线见 [#229](https://github.com/TYCT-tyct/Axiom/issues/229)）。守卫：路由在没有配置分段大小时不会把任何条目标为可分段，报价遇到可分段却没有配置分段大小或超额额度的条目则报错，而不是少预留。
- **预留**是一笔挂起的转账：从余额里先划出一段，结算时过账，多余的作废，与 TigerBeetle 的两阶段转账（挂起 → 过账 / 作废）相同。它记在 PostgreSQL 里，不放缓存；单独存放，不是账本分录，不改余额。一个请求按段追加预留，这叫分段预留。
- **预留的状态**：挂起 → 已结算 / 已释放 / 清理已释放（`cleanup_settled` 是旧库里留下的，不再写入）。每次状态变化都是"比较后再写"，每个请求恰好由一次结算或清理落定；状态之间怎么转移见 [billing 模块的「预留的状态」](../../internal/billing/README.md#预留的状态)，清理见下文「持有者与截止时间」。
- **准入**（调用上游之前，一个事务）：
  - 查账户状态，以及 key、工作区、站长（二级站点）的各项限额，全部在预留时一起扣，不在事后检查。限额的时间窗口在准入时按 UTC 锁定，追加和结算都记回这个窗口；
  - **每个条目自己报价**：可分段的条目（见下文「一次预留足」）报第一段 = 输入上界 + 首段输出 + 按次项目的最大次数（请求写了上限就用它，否则用模型的默认最大次数，后台数据）+ 超额额度；不可分段的报全额，输出按上限。预留取保留下来的条目报价的最大值，所以回退时不会走到比它更贵的条目；按次项目一开始就预留足，所以追加等待期间上游发起的搜索也已覆盖，追加只管输出；
  - 输入按可以证明的上界预留，不用估算：文本的 token 数不超过它的字节数（按字节编码的分词器产生的 token 不会多于字节）；每张图片按该厂商单张图片的最大 token 数，每个文件按单页的最大 token 数乘单个文件的最大页数，没有可靠的页数上限时按上下文长度（网关只数文件个数、不解析页数；这些都是模型数据，见[模型目录的「目录基线」](catalog.md#目录基线)）。M1 的模型数据里没有这些，图片和文件都按上下文长度预留，所以带图片或文件的请求预留很大，余额小的账户会被拒；收费用的暂估不用这个上界，见「用量来源与暂估」；合计不超过模型的上下文长度。输入在上游开始回答时就已经花掉，截断输出追不回来，所以只有上界才能守住欠款上限；
  - **一个请求里有多次内部采样时，输入按采样次数计**：服务端工具（联网搜索、代码执行）每用一次，模型就重新读一遍上下文。采样次数 = 1 + 各服务端工具的最大次数之和（请求没写就用该条目模型的默认最大次数，所以按条目在报价时算），请求开启了服务端压缩（Anthropic 的 `context_management`、Responses 的 `compaction`）时再乘 2。第一次采样的输入按上一条的上界，之后每次按模型的上下文长度，各次按自己的上下文分档单独报价后相加；服务端搜索回填的结果计入输入（见 [catalog 模块](../../internal/catalog/README.md)），只有这样才有上界；
  - **服务端工具必须有上限**：请求开启了联网搜索或代码执行，却没有写最多用几次，而模型也没有默认的最大次数，这笔费用就没有上界，没有任何预留能罩住它（超出预留的部分按余额底线截断，由平台承担）。这样的请求在调用上游之前就拒绝，回 400 `invalid_request`，说明要写上限（Messages 联网搜索的 `max_uses`、Responses 的 `max_tool_calls`）；Chat 的联网搜索和 Messages 的代码执行没有可写的上限字段，回的是「该格式暂不支持这个工具」；写了上限就按上限预留，模型有默认值的也照常。路线里任何一个条目没有上界，整个请求都拒绝，因为预留取各条目的最大值，回退可能落到那个条目上；
  - **服务等级只算端点提供的**：没写等级的请求可能按标准或优先档服务，但只会落在端点实际提供的等级上，所以报价取请求允许的等级与端点提供的等级的交集（再加标准档）。端点提供哪些等级来自目录里模型可报告的等级，所以这个收窄以目录准确为前提：上游报告了列表之外的等级，那次调用的各项按兜底价收并标暂估，模型不会因此被移出路由（见[价目表缺项](#价目表缺项)）；
  - 输入不假设缓存命中：缓存可能已失效，回退也可能换到别的端点。所以输入按这次请求可能产生的最贵输入侧单价预留：带 1 小时缓存标记的按 1 小时缓存写价，带 5 分钟标记的按 5 分钟缓存写价，否则按普通输入价；上游可能不带标记就报告缓存写时（OpenAI 格式），未标记的输入也按缓存写价预留，理由同缓存读；模型可能报告缓存读时，缓存读价也一起取最高，因为固定售价、各服务等级和分档不保证缓存读比输入便宜；
  - 对用户和站长两边都要求"余额 − 在途预留 − 本次预留（含超额额度）≥ 余额底线"。报价超过余量的条目从路线里删掉，一遍完成（见[路由](routing.md#一个请求的路由步骤)）；首选条目被删，才在调用上游之前返回 402，并指明是余额、工作区预算还是 key 上限不够；
  - **余额行是一个账户资金写入的唯一串行点**：预留、追加、结算、退款、清理都先锁账户的余额行，工作区和 key 的花费计数只在持有它时修改；同时涉及两个账户（二级站点）时按账户编号从小到大锁；
  - 请求必须等预留写入数据库后才调用上游，所以节点在此之前崩溃不会丢钱。
- **转发中追加**：
  - 边读边累计花费，从读到上游第一个字节起，包括开始转发前暂存的部分、非流式聚合的部分和客户端断开后读完的部分：上游已报告的输入侧项用准数（如 Anthropic 在流的开头报告输入和缓存）；输出按已读到的内容字节数计（token 不会多于字节，这是上界，不会低估；计哪些字节见 [protocol 的「转发（草图）」](../../internal/protocol/README.md#转发草图)的「字节上界」）。输出侧在最后的用量事件之前报告的数只是下界（Anthropic 在流的开头报的 `output_tokens` 是 1），所以在那之前输出取已报告的数与字节上界中较大的一个；联网搜索按事件计数；
  - 当前段用掉 40%–60% 时申请下一段，比例每个请求随机取一次，避免同时开始的请求一起追加。按这次尝试绑定的条目的价格版本计价，申请的是累计目标，只增不减，各项限额一起查；写库次数随段数增长，不随事件数增长；
  - 当前段在追加提交前用完时，暂停转发，最多等一个追加等待期限（后台数据，默认 1 秒）；
  - 超时或追加失败就中断上游（供应商传递取消时）并结束回答，按各格式的方式发标准错误事件：余额或某个 key 的额度不足时是 `credits_insufficient`，说明回答已截断；数据库出错或超时是 `billing_unavailable`（见[接入与对外接口的「错误」](gateway.md#错误)）；
  - **超额额度**：从当前段用完到上游真正停止生成，还会多出一点输出：追加等待期限，加上从上游生成到网关看到、从发出取消到上游停止计费的延迟上限（后台数据），乘以模型的最快输出速度（每秒 token，模型数据），再乘输出单价。它在第一段里一起预留、一直保留到结算，所以并发的多个请求各自用满超额额度，账户也不会低于底线；
  - 每段的大小和每个模型的默认输出上限都是后台数据。请求没写输出上限时用模型的默认值。
- **一次预留足**：分段预留要能截断才有用。以下情况各自独立判断，按条目和这个请求判断（路由在路线里给每个条目标明），这样的条目在准入时按上限报价（输出上限加按次项目的最大次数），这次尝试不追加、不截断：
  - **不能持续观测计费进度**：网关在适配器允许时一律以流式调用上游，客户端要的是非流式也一样，由网关聚合后一次返回，这样进度看得见。仍看不到的，例如推理 token 不在流里显示（模型如此，或请求要求隐藏推理），或上游不能流式，就属于这种情况。某个模型在某种调用格式下是否在流里显示推理进度，是模型数据（见[模型目录的「目录基线」](catalog.md#目录基线)）；能否流式调用由适配器声明。
  - **不传递取消**：有的中转站在我们断开后仍把上游读完，并按全量向我们扣费（sub2api 源码 `gateway_upstream_response.go` 的 "continuing to drain upstream for billing"；2026-10-14 本地实测 sub2api 0.2.16：30 段里第 3 段断开，仍按 300 个输出 token 全量扣费），截断省不了钱。怎么判断见下文「客户端断开」。
  - **超额额度接近输出上限**：分段省不下多少，不如一次预留足。
- **结算**（回答结束前同步完成，一个事务）：
  - 去重键是"请求 ID + 尝试序号"（学 sub2api 的 `usage_billing_dedup` 表，sub2api 源码，2026-10）；
  - 按[免单规则](#免单规则)收费，记账本：用户余额 → 收入，二级站点同时记站长那一笔；释放预留；更新 key 和工作区的花费计数；记每次尝试的供应商成本和对账键——同一个事务里还写供应商侧的那一行（哪次尝试、多少钱、哪个对账键、哪个端点），所以供应商成本与账本上的成本同成同败（[总体架构的模块边界规则](../architecture.md#模块边界规则)）；
  - 请求进入终态（已结算、已释放、清理释放）的那个事务里告诉供应商这个请求有定论了（`EndRequest`），时间取写预留行的数据库时钟；清理释放时同一个事务里还写一行丢失的请求，带这条请求冻结的路线（[持有者与截止时间](#持有者与截止时间)）；
  - 实际金额在预留（含超额额度）之内；万一超出（例如模型实际输出比设定的最快速度还快），按余额底线的写入规则处理；
  - 费用写进流的最后一个事件，用量来自估算的标为暂估；
  - 结算写不进时，执行它的进程带着准确用量继续重试，直到预留的截止时间之前；之后由清理接管（见[持有者与截止时间](#持有者与截止时间)）。客户端看到什么见[接入与对外接口的「用量与费用」](gateway.md#用量与费用)。
- **余额底线**：按账户设置，默认值由站点配置，默认 0，可以设为负数。
  - 写入规则：每笔收费（结算、迟到的补扣、按兜底价收的费用）在写入时检查，最多收 余额 − 底线 − 其他请求的在途预留（本请求自己的预留可用），超出部分由平台承担，记入科目「平台承担」（[账本](#账本)）并告警：事务提交后记一条 Error 日志（请求、应收、实收、承担的金额），并计入 `axiom_billing_platform_borne_total` 和 `axiom_billing_platform_borne_amount_total`（承担的金额，单位十亿分之一额度）。它只在假设被打破时发生：模型输出比设定的最快速度还快、不认识的计费项第一次出现、清理释放后迟到的结算带回的补扣、上游把我们按较低等级预留的调用服务在更贵的等级而兜底价高过按那次预留留的额度。这是有记录的意外损失，不是配置让平台亏本卖。
  - 余额不够新请求的预留时拒绝新请求，充值后自动恢复，不是封号。
- **热点账户**：按账户把几毫秒内的预留和结算合并成一次提交，规则与逐笔处理完全相同；落库后才发出带费用的最后一个事件。它是性能手段，由压测决定何时启用。规模化以后，节点预领一段额度在本地预留（电信预付费按段授予额度的做法，RFC 4006）。
- **二级站点的请求**：
  - 同时预留终端用户和站长两个账户，结算时用一个事务分别记两边的账；
  - 站长余额不足时，对终端用户返回通用错误，不泄露站长的财务信息，同时通知站长；终端用户被封顶少收的部分由平台还是站长承担，待定（二级站点随 M2，[#28](https://github.com/TYCT-tyct/Axiom/issues/28)）。

### 持有者与截止时间

进程崩溃、活着但漏了结算、数据库长时间不可用，都要有人把挂起的预留收尾。

- **持有者**：每个核心进程启动时生成一个持有者，它准入的预留挂在它名下。进程靠心跳续期；心跳停了超过有效期再加宽限，清理程序回收它：回收之后它名下不能再新增或追加预留，清理再处理它名下仍挂起的预留。数据库短暂不可用后，没被回收的进程能续上。
- **谁来跑**：节点启动后由 `Billing.Run` 一个循环做这三件事，不分三处调度：每 TTL 的三分之一发一次心跳（配置要求心跳周期不超过 TTL 的三分之一，错过一次心跳持有者仍然活着；`Alive` 在 TTL 减 5 秒之后为假，网关据此不再发起新的尝试）；启动时立即、之后每 30 秒回收一次过期的持有者，再接管到期的预留，一次最多接管 5 批、每批 200 个，积压更多的留给后面几轮，因为一轮不返回就连心跳也停了，节点会把自己回收掉。心跳发现自己的持有者已被回收时循环返回 `ErrReaped`，节点随即退出重启，用新的持有者：此后这个进程写的东西不再被承认。其他的心跳失败只记日志，下一次再发，`Alive` 变假期间不接新的尝试。第二个节点启动时的第一轮回收只回收过了有效期和宽限的持有者，不会动正在心跳的节点。
- **截止时间**：每笔预留另有截止时间（准入 + 单次调用最长 + 结算宽限）。过了仍挂起的，不论持有者是否活着都由清理处理。
- **清理一律记丢失的请求并释放**：过了截止时间仍挂起、或持有者已被回收的预留，清理只释放（`cleanup_released`）、不收费，同时让供应商侧留下一行丢失的请求，带这条请求冻结的路线（保留了哪些端点，见 [suppliers 的「没有对账日志」](../../internal/suppliers/README.md#没有对账日志)）：这个请求可能被上游收过钱，钱最可能落在这些端点上。迟到的结算照常向用户收费（见下）。
  - 崩溃的节点没来得及留下任何尝试，所以清理没有可收的依据；结算事务里写下的成本行已经和账本的供应商成本同成同败，不会漏掉已提交的结算。
  - 内容已交到客户端、结算事务还没提交时节点崩了，也是这一种：这次交付的尝试没有成本行，对账键也不保存，由供应商的逐笔记录补齐；请求按丢失的记，迟到的结算若来了，就把它找回来。
- **为什么清理不收钱**：我们参考的两家里，sub2api 是后付费——用量在转发成功之后才提交计费（sub2api 源码 `backend/internal/handler/gateway_handler.go`，2026-10-18 查），进程在转发之后、提交之前崩掉，那边同样的情形也是这笔调用没被收过。清理时手上没有用户看到的用量；按我们自己估的数收钱，与结算那一刻用户最终看到的数不一样。所以宁可这次先不收，等迟到的结算带真实用量来收；它不来，平台就承担这一次的成本，与免单的性质相同。
- **迟到的结算**：持有者被回收后，原进程的结算仍可能到达，不会因为去重而丢掉。它带着这个请求完整的结局和真实用量，所以按正常规则收费：客户端取消照收、非流式聚合成功照收、没有内容交到客户端的按免单规则；与清理已收的多退少补，并把丢失的请求标为已解决。迟到的结算若没有任何尝试（调用从没到过上游，例如客户端在调用上游之前就走了），不收费，也把丢失的请求标为已解决。释放的钱可能已被后续请求用掉，所以补扣按余额底线的写入规则，最多扣到底线，其余由平台承担。
- 崩溃时平台承担的，是最后一次成功结算之后那一段里上游向供应商发生的成本，M1 由丢失的请求记录在案，等对账跑起来再补；清理每释放一笔预留，按单次释放的金额记一条警告日志（请求和金额）。

### 用量来源与暂估

- **优先用上游报告的用量**。上游报告的用量超出上限或自相矛盾（例如输入侧减出负数）时，视为没有报告，按下一条处理并告警。
- **流断了、上游没报完或报告无效**：上游报告了的计费项一律保留，只估缺的项：输入按请求估（比例见下一条），输出按已转发的文本估，按次项目按已转发的事件计数；这次费用标为暂估。例如 Anthropic 断在 `message_start` 之后时，输入和缓存是准数、只估输出；断在它之前，或 OpenAI 的流没有输入用量时，输入也要估。new-api 对 Claude 流也是这样只补缺失的项（new-api 源码 `relay/channel/claude/relay-claude.go` 的 `HandleStreamFinalResponse`，2026-10）。
- **暂估**：上游报告的项照收，缺的项估出来，这次费用标为暂估，预留里没用掉的部分结算时一次释放。暂估就是这次收费，不按供应商记录重算用户费用（按记录重算的校正作业见 [#28](https://github.com/TYCT-tyct/Axiom/issues/28)，M1 没有生产者）：之后才到的记录只用于对账，不动这次收费。暂估本身用最好的估计：输入用历史比例按字节估（见[性能的「调用路径上的规则」](../performance.md#调用路径上的规则)），不用上界。有历史比例之前用固定比例：输入的文本按 4 字节 1 个 token，每张图片按 1600 个 token、每个文件按 4096 个 token，模型数据里的单张图片或单个文件的上界更小时取上界（预留仍按上界，两者分开：暂估不能高过预留，预留不能低过用户可能花的）；输出按已读到的正文、推理和工具参数按 3 字节 1 个 token，不低于上游已报告的数；都向上取整，都不超过预留覆盖的上界。

### 客户端断开

- 传递取消的供应商：立即中断上游，按已产生的用量收费，从不免单。
- 不传递取消的供应商会把上游读完、按全量向我们扣费，中断也省不了钱。这时我们也继续读完上游（不再转发给客户端），拿到上游报告的完整用量，照常结算，用户按全量付费，在计费说明里写明。这样费用几秒内就是准数，不用先按预留上限收、事后再退，按 ESC 中断不会让余额先被扣走一整段上限。
- 2026-10-14 本地实测：new-api 把断开传到上游，Anthropic 格式的输入和缓存按 `message_start` 精确计费、输出按已转发的文本估算，OpenAI Chat 格式两者都估算；sub2api 按全量扣费。
- **是否传递取消是端点属性**：适配器按所接中转系统的源码和实测给默认值，端点级的实测（流中断开后对照中转站记录的输出数和时延，记下实测时间）以后覆盖它。new-api 默认传递：它在客户端离开时关上游连接（new-api 源码 `relay/helper/stream_scanner.go:304-307`，只对流式成立，而 Axiom 对它一律以流式调用）。sub2api 默认不传递：读完上游才计费（sub2api 源码 `gateway_upstream_response.go`）。站点前面若有不传递断开的代理，平台多付的差额由对账发现（[#227](https://github.com/TYCT-tyct/Axiom/issues/227)）。OpenRouter 也是按端点声明是否支持取消，并据此决定断开后是否继续计费，不是一律按不传递（OpenRouter 文档「Stream cancellation」，2026-10-18 查）。M1 的预留全部是全额，所以这个属性在 M1 只决定断开之后是立即取消上游，还是继续读完它。
- 取消不直接动钱：预留只经结算或清理落定。

### 价目表缺项

上游报告了价目表没有的计费项，或这次调用落在价目表没有定价的地方时，从不免费：

- **已知的按次项目**（如联网搜索）：每种都有一个站点级的默认单价，是后台数据，由价格来源初始化；模型没有这一项的单价时用默认单价。每种已知的按次项目都必须有有效的默认单价（币种、单位正确，不为 0），启动时和管理员修改时检查，不合格就不启动或拒绝保存。
- **我们不认识的计费项**：第一次出现时，这个模型停止接受新请求（移出路由）并告警，直到管理员给它定价。已经在途的请求按兜底价收，标为暂估：像 token 的按该模型最高的 token 单价，否则按最高的按次默认单价。这个请求按兜底价的估算同样受余额底线的写入规则约束。兜底价不一定高于实际成本，所以风险只限于这个计费项第一次出现时已经在途的请求。这个估算之后没有校正作业：收费写完就定了，供应商的记录只进平台的成本（[「用量来源与暂估」](#用量来源与暂估)）。
- **价目表定价不了这次调用**：上游把这次调用服务在售价没定价的服务等级（供应商的分组强制 `service_tier=priority`，而售价只有标准档），或某个 token 项在那个等级里没有单价时，计价把用量不为零的各项报告为缺价，结算按兜底价收并标暂估：token 按该模型全部服务等级和档位里最高的 token 单价，按次项目按该项目的站点默认单价（准入补上的就是它；模型自己在别的等级写的按次单价在这里用不上，和 token 不同，理由见决策表）。这不是我们不认识的计费项，模型不因此移出路由：门槛查的是售价能不能给出价，上游回报什么是运行时的事（见[「预留与结算」](#预留与结算)的服务等级一条）。免单时 token 这部分算模型用量，不收；按次项目照收。

### 免单规则

- **免单条件**：上游报告的输出 token 为 0（输出加推理两个计费项之和，每次采样都报告了输出；`Usage.OutputTotal`，不含音频、图片输出，是否并入待定，[#28](https://github.com/TYCT-tyct/Axiom/issues/28)），并且结束原因为空或出错，并且不是客户端主动取消。只有推理或只调用工具的回复有输出 token，照常收费。没有上游用量的不免单。免单只看这几条，与这次调用值多少钱、当天已经免了多少次无关。
- **收费的尝试**：收费的是请求的最后一次尝试，不论成败，按它的结局收费；之前被回退的尝试只记成本。
- **没有内容交到客户端的失败，不收模型用量的费用**：对齐 OpenRouter（帮助中心「Zero Completion Insurance」与价格页「Are failed or fallback attempts billed? No」，2026-10 查）。"交到客户端"：流式指已向客户端写出正文、推理或工具调用，非流式指内容随响应返回。

| 最后一次尝试的结局 | 向用户收费 |
|---|---|
| 确知未执行：请求没写完，或适配器把上游返回的这个非 2xx 归为该供应商在执行前就拒绝的（例如参数校验的 400、401、403、余额不足的 402、429） | 不收，用量确知为 0；尝试成本按 0 记 |
| 没有内容交到客户端：2xx 之后、开始转发之前失败；结果未知（请求已写完，之后没拿到响应头或用量，或返回了其他非 2xx，如 5xx、504 和认不准的状态：供应商成本按估算记、由对账补正）；非流式聚合失败且不返回内容（含 Messages 的非流式） | 模型用量不收，平台记成本；已执行的按次项目（如联网搜索）照收。平台承担的部分算作免单损失，只记成本、不计入用户收费 |
| 内容已交到客户端后出错、截断、超时；非流式聚合失败、内容随错误返回（Chat、Responses） | 按用量（缺的项暂估），再套免单条件 |
| 客户端取消 | 按用量或暂估，从不免单 |
| 正常结束 | 按用量，再套免单条件 |

- **以收费的那次尝试的结局为准，客户端是否之后才断开不改变它**：第一次尝试失败、没有内容交到客户端，准备下一次时客户端断开，收费的仍是那次失败的尝试，按上表"没有内容交到客户端"那一行，不收模型用量。只有收费的那次尝试本身是因为客户端离开而结束的，才是"客户端取消"，从不免单。这是对上表的澄清：表本来就按最后一次尝试的结局分行。
- **按次计费的项目**（如联网搜索）照常收费；**上游不收费的拒答**跟着不收。

### 账本

- **一张表**：所有记账在一张按月分区的表里，用"站点 + 货币"区分各站点的账。每个事件在每本账里借贷各自平衡；跨币种或跨站点的事件，在每本账里各记平衡的一组分录。
- **科目**：现金（按收款渠道和币种）、用户与站长的余额、平台收入、二级站点收入、手续费收入、渠道手续费、供应商预付余额（按供应商和币种）、供应商成本、号池支出、赠送支出、汇兑损益、拒付损失、额度过期收入、平台承担。
- **事件与分录**：

| 事件 | 借 | 贷 |
|---|---|---|
| 用户充值 | 现金（用户付的总额） | 用户余额（按锁定汇率折算，差额记汇兑损益）、手续费收入 |
| 渠道扣费（交易手续费、拒付手续费、链上归集费） | 渠道手续费 | 现金 |
| 赠送、兑换码 | 赠送支出 | 用户余额 |
| 请求结算 | 用户余额（实收）、平台承担（应收减实收，不少收时没有） | 平台收入（应收；二级站点为站点收入） |
| 站长进货 | 站长余额 | 平台收入 |
| 尝试成本 | 供应商成本 | 供应商预付余额 |
| 成本调整（对账差额） | 供应商成本 | 供应商预付余额（差额为负时借贷对调） |
| 给供应商充值 | 供应商预付余额 | 现金 |
| 号池实际支出 | 号池支出 | 现金 |
| 退款 | 用户余额（退还手续费时另借手续费收入） | 现金 |
| 额度过期 | 用户余额 | 额度过期收入 |
| 拒付 | 用户余额（按入账所用的汇率扣回这笔充值未退款的额度，可以变成负数，差额记汇兑损益）、手续费收入（冲回这笔的手续费） | 现金（被拉回的总额） |
| 坏账核销（负余额确认收不回） | 拒付损失 | 用户余额 |
| 补扣（结算丢失后补回） | 用户余额 | 平台收入 |
| 冲正 | 原分录借贷对调 | |

- **费用校正**（暂估校正、缺项兜底改按实际成本）：冲正当前有效的那笔请求结算，再按校正后的金额记一笔新的请求结算，两笔在同一个事务里提交，都引用原请求。每次校正有自己的幂等键：请求 ID + 尝试序号 + "校正" + 供应商记录的版本号；重复投递返回同一个结果；同一请求再次校正用更新的版本，冲正的是当前有效的那笔结算。**M1 没有校正**：没有生产者，暂估在结算时就定死（[用量来源与暂估](#用量来源与暂估)），接回它见 [#28](https://github.com/TYCT-tyct/Axiom/issues/28)。今天带版本号的交易只有迟到的结算（版本号 −1），它冲正的也是清理记的那笔。
- **平台承担**：它是账本科目，也是请求明细里的应收（`price`，规则算出、封顶前）与实收（`charged`）之差；用户余额只记实收，供应商成本照记，所以该请求的利润自然减少。少收只有余额封顶这一种原因，没有单独的原因字段，也不区分是哪种意外，待定（[#28](https://github.com/TYCT-tyct/Axiom/issues/28)）。
- **免单不额外记账**：免单只是不记"请求结算"这一笔，尝试成本照常记入供应商成本，并打上"免单"标记，报表据此统计免单损失。
- **每日自平**：队列上的周期任务 `billing.reconcile`，节点启动时先跑一次，之后每 24 小时一次，多节点时只有队列的领导节点插入，所以只跑一份。它只读，找出分录合计不为 0 的交易，和余额与账本合计不符的账户；每个问题记一条 Error 日志（最多列 20 条，其余给总数）并计入 `axiom_billing_reconcile_problems_total`。与供应商逐条对账是另一件事，M1 没有运行（[#227](https://github.com/TYCT-tyct/Axiom/issues/227)）。
- **去重与更正**：交易按"请求 ID + 尝试序号 + 事件类型"去重，费用校正另加版本号；记错了不改原记录，记一笔冲正。M1 里带版本号的只有迟到的结算（版本号 −1）。
- **合并写入时**：同一组请求在账本里记为一笔汇总交易，每个请求的明细另存并引用它，汇总金额必须等于明细合计。

### 风控状态

- **账户状态**：正常、余额不足（不够新请求的预留时拒绝新请求，充值后自动恢复）、暂停（只用于拒付和欺诈，人工解除）。
- 退款与预留都先锁账户的余额行，防止先退款再花钱。
- 管理员动钱的操作（加额度、改价、冲正、退款）都记审计：谁、何时、为什么；超过阈值的要二次确认。

### 用户看得到什么

- 每次调用的明细：各项用量、单价、价格版本、用量来源、是否暂估。M1 不显示价格版本（它没有写进预留行和调用记录，见[定价](#定价)）。
- 余额流水和低余额提醒（提醒的收件人、模板和站点品牌见[账户与租户的「给用户的邮件」](accounts.md#给用户的邮件)）。

### 自带货源的服务费

- 站点自带货源、用户自带厂商 key（以后的功能）：平台按"参考价 × 比例"收服务费，可以设每月免费额度。不用成本加成，因为平台在这种情况下没有成本，加成后结果仍是 0。

### 怎么验证

- **性质测试**：随机生成请求序列，包括崩溃、重试、并发和截断，始终满足账本平衡、余额等于记录之和、不重复扣、调用收费不使余额低于底线（拒付、坏账除外）、"平台承担"只出现在记录在案的三种情况里；迟到的结算重复投递、并发投递和两次投递结果确定。
- **验收用例**：追加预留的写库被阻塞而上游继续生成时，等满期限就中断上游并截断，消耗不超过超额额度；同一账户的多个并发请求同时用满超额额度，余额不低于底线；多个暂估请求同时结算，余额不越过底线；清理释放后余额被后续请求用掉、迟到的结算再带回补扣时，最多扣到底线，其余记为平台承担；模型输出比设定的最快速度还快时，同样只扣到底线并告警；不认识的计费项第一次出现时模型移出路由，在途请求按兜底价暂估。
- **回放**：录制的真实流（正常、断开、`message_start` 之前出错、没有最终用量、用量无效、搜索循环、非流式长输出）的结算结果固定。
- **故障注入**：结算前后杀进程、数据库超时。
- **监控**：暂估占比、缺项次数、平台承担的金额和次数、对账偏差、成本漂移、截断和拒绝次数；新 key 的用量突增告警。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 每个站点用自己的记账货币，主站为美元 | 负责人同意用美元记账。二级站点可以用人民币，这样中转站"¥1 = $1"的惯例不需要一个假"美元"来表达 |
| 计算中途不取整，取整一律对平台有利 | 逐项取整会累积误差，缓存读这类便宜的计费项误差可达一倍以上；每次最多多收十亿分之一额度，保证永远不少收 |
| 汇率是开关，加两个方向的缓冲，交易时锁定；账上按参考汇率记 | 负责人要求。同币种进出不受汇率影响；跨币种的波动由缓冲承担；账上不记缓冲后的汇率，利润和供应商余额才不会漂移 |
| 二级站点的换算率由站长设定 | 负责人同意。平台按主站额度扣站长，不承担二级站点的汇率风险 |
| 额度批次，先用最早到期的批次；分配由后台按账本顺序重放，到期在账户锁内按重放结果作废 | 负责人要求额度默认不过期，但可以单独设有效期；批次还区分付费和赠送，决定哪些能退。没选"每次结算时实时扣减批次"：那样每个请求都要多写一行，热点账户压力加倍。批次的做法与 Stripe、Metronome 的额度授予相同。new-api、sub2api 都没有额度到期：它们的有效期只限制兑换码在多久之前能兑换（new-api 源码 `model/redemption.go` 的 `ExpiredTime`，sub2api 源码 `backend/internal/service/redeem_code.go` 的 `ExpiresAt`，2026-10-18 查），兑到账上的额度不过期，所以这里照本文设计，没有可参考的实现 |
| 账本交易带一个序号，重放按序号而不是时间 | 时钟会回拨，一次结算的冲回和结算两笔交易可以同一微秒；序号在账户锁内取（写动用户余额的交易时，同一条语句先锁余额行），同账户的余额变动按提交先后递增。序号之前的老交易没有序号，排在最前，按时间和 ID 排，这个键不变，所以每次重放相同；之前没有任何代码分配批次或让批次到期，老交易的先后不影响结果 |
| 作废只封顶到 余额 − 在途预留，不用余额底线 | 负责人授权由 AI 判断（「全部由ai自己判断」，2026-10-19，PR #299 评审后）。底线是给扣费用的额度；用它作废，用户会因为赠送到期而欠下真钱（底线 −50、预留 200、批次 300：按底线作废 150，结算 200 后余额 −50；不用底线作废 100，结算 200 后余额 0）。预留一定收得下这一点两种封顶都成立 |
| 退款按批次的实付与入账额度之比折算，累计不超过净付款额 | 按今天的汇率退，会出现"按缓冲后汇率充值、按有利汇率退款"的套利；按订单报价的成交价退，过期后按到账汇率入账的批次会多退（下单锁 7.40、过期后人民币升到 7.00，付 74.00 元入 10.571 美元，全退时按 7.40 折算退 78.22 元） |
| 冻结、解冻是带序号的重放事件，与到期作废同样处理 | 分配只由账本决定才能从头重放复现；冻结若只是余额行上的一个数，重放时会把今天的冻结额用到全部历史扣费上 |
| 成本计划由适配器生成 | 中转站的计价远不止"基础价 × 倍率"：new-api 有按次价格、表达式分档和工具附加费，sub2api 有价格覆盖、分时段和长上下文倍率（new-api、sub2api 源码，2026-10）。统一成一张表，计费模块不随中转系统变化 |
| 售价按我们的价目表计，锁定版本；成本以供应商记录为准 | 用户看到的价格必须确定。没选"完全跟随中转站扣费"：用户看不到确定价格，而且普通用户在 sub2api 上不能按请求号筛选记录。估算成本会因同步滞后而失真，对账既修正利润，又能发现偷改倍率和虚报用量 |
| 每次尝试都记成本，去重键包含尝试序号 | 失败和被回退的尝试同样花钱；不带尝试序号，回退时第二笔成本会被当成重复丢掉 |
| 定价规则按两条轴、固定顺序比较 | "最具体者优先"在多个条件维度下比不出先后；固定顺序保证结果唯一 |
| 加价只写成计费的定价规则，人群是等级或账户，等级表不存加价 | 一套规则只有一个存储处，预览、保本线和价格版本都按同一份规则算；等级只是分层的人群，改加价不用动等级。否决的做法：等级上存默认加价、规则再覆盖：两处都能改价，优先级和预览要说清两套 |
| 保本线按用量区间、按计费项检查，触线涨价立即发布 | 负责人要求不能亏本；只看总价时，某个计费项可能单独低于成本；只比同一档会漏掉两边门槛不同的区间；发布阈值不能压住保本涨价 |
| 分段预留，追加不到就截断回答；余额有底线，默认 0 | 负责人同意（Issue #28，2026-10-14）。欠款有硬上限：输入按上界预留，输出按字节计量不会低估，每个预留含超额额度，准入把所有在途预留一起计入，收费写入时最多扣到底线；假设被打破时由平台承担并告警，损失有记录，不转嫁成用户的欠款。没选"先放行、事后扣、允许欠"（new-api、sub2api 的做法，new-api 源码 `service/billing.go`，2026-10）：欠多少没有上限，并发和搜索循环都能欠很多。没选"按最大花费一次预留足"（刷卡预授权的做法）：长上下文、没写输出上限的请求会被大量误拒。按段授予额度来自电信预付费的信用控制（RFC 4006） |
| 看不到计费进度或不传递取消的端点，在准入时按上限一次预留足；上游尽量用流式调用 | 分段预留靠"看得见进度、截得断"才有上限。非流式调用和不显示推理 token 的流，在返回之前就可能花掉整笔输出；不传递取消的中转站在我们断开后仍按全量扣费（sub2api 源码与 2026-10-14 实测）。两件事各自判断：能取消不等于看得见进度。上游一律用流式，能让大多数请求留在分段预留里 |
| 预留输入按上界、不假设缓存命中；暂估用最好的估计 | 输入在开始回答时就已花掉，截断输出追不回来，只有上界才守得住欠款上限；缓存会失效，回退会换端点。暂估若也用上界，用户看到的费用会系统性偏高 |
| 预留记在数据库，挂在可回收的持有者上并带截止时间；崩溃后由清理记丢失的请求，连同这条请求冻结的路线，不用缓存里的检查点 | sub2api 的在途预留放在 Redis，Redis 故障时直接放行（sub2api 源码 `billing_cache_service.go` 的 fail-open，2026-10）。按段追加后，数据库里的预留本身就跟上了进度；真实用量以供应商逐条记录为准，缓存检查点只会给每路长流增加周期性写入。持有者加截止时间让进程死了、活着但漏了结算、数据库长时间不可用都有人收尾，回收之前的进程能续上；没选按节点租约的过期时间判断：时间可能过时，清理与写入没有互斥，数据库恢复后会回收活着的进程。已结算的尝试有与账本同一次提交的成本行，崩溃留下的只有「这个请求可能花了钱、可能在哪些端点」，记在丢失的请求里 |
| 余额行是账户资金写入的唯一串行点，先锁它再读计数 | 同一账户的预留、追加、结算、退款、清理只要一把锁，不会死锁；读已提交隔离下锁之后的新语句才看得到锁前的提交。没选按账户、工作区、key 的顺序逐个加锁：多一把锁就多一次等待，计数仍要另外读 |
| 清理一律不向用户收费，收费留给迟到的结算 | 收费在结算时才确定，不在转发前：sub2api 也在转发成功之后才提交用量计费（sub2api 源码 `backend/internal/handler/gateway_handler.go`，2026-10-18 查），进程在转发之后、提交之前崩掉时，那边这笔调用同样没收过。清理手上没有用户看到的用量；收一笔就是按自己估的数收，与结算那一刻用户最终看到的数对不上。不收的代价是这次调用的成本由平台承担，与免单同性质，可统计、可告警；迟到的结算带着真实用量来时照常收，所以只有结算永远不来的请求才由平台承担。没选 new-api 的做法：它在准入时就按估算把额度预消费掉（new-api 源码 `service/billing.go`，2026-10），等于按估算向用户收，而我们没有冲正估算的校正作业（[#28](https://github.com/TYCT-tyct/Axiom/issues/28)），记错就一直错 |
| 每个条目自己报价，预留取保留条目报价的最大值，一遍删掉付不起的 | 不可分段的条目要全额，可分段的只要首段；删掉付不起的全额条目后，自动按首段预留，不误拒只够付首选端点的用户 |
| 输入上界按内部采样次数乘 | 服务端工具和压缩每次采样都重新计输入，否则没有可证明的上界。代价：带搜索的请求预留更大 |
| 没有内容交到客户端的失败不收模型用量，平台记成本 | 开发者按负责人在 Issue #28 对计费设计的授权决定（2026-10-14）。对齐 OpenRouter：出错或被回退的尝试不收模型 token，即使上游向它收了；已执行的按次服务照收（价格页 FAQ「Are failed or fallback attempts billed?」、帮助中心「Zero Completion Insurance」，2026-10 查）。用户为没拿到内容的 502 付钱难以解释，平台承担的部分从成本账上统计并告警。偏离 OpenRouter 的一处：内容已交到客户端后出错仍按用量收（OpenRouter 对出错结束一律不收），因为中转站对已生成的部分照样向我们收费，内容也已交付 |
| 用量以上游报告为准；缺的项才估，标暂估，没用掉的预留结算时释放 | 用户看得到哪些是估的；保留上游已报告的项，估算范围最小。M1 不按供应商记录改用户的费用（没有生产者，见 Issue #28），所以不必为等记录留着预留：留着的钱会挡住这个账户后面的请求，而记录永远等不到 |
| 上架门槛按模型检查；已知按次项目用站点默认单价；不认识的计费项让模型停止接受新请求，在途请求按兜底价暂估，从不免费；定价不了的等级或 token 项也按兜底价收 | 红线是不会算不出钱，也不因计价拒绝已经发生的调用。停止接受新请求把风险限制在第一次出现时已经在途的请求。没选"调用前按请求特征拒绝"：拒绝清单要随各家新功能不停维护，误拒正常请求；没选"按预留金额收"：向一次失败或缺价的请求收整笔预留不可解释。售价只给一部分等级定价（模型没声明 priority，供应商的分组强制 `service_tier=priority`，sub2api 源码 `backend/ent/schema/group.go` 的 `force_openai_fast`）是已写下的规则：那次调用按兜底价收并标暂估，不移出路由——移出路由会让一次正常交付的调用既回 404 又收 0。token 取价目表里最高的 token 单价，按次项目取站点默认单价而不取模型自己在别的等级写的价：价目表没有的等级里，模型的按次价一项也没被补进锁定的价目表（`Fill` 只补价目表里已有的等级），而站点默认价一定在；按模型自己的价收会让同一个工具在等级之间收出两种价，且模型没写这一项时无价可用 |
| 暂估输入里，每张图片 1600 个 token，每个文件 4096 个 token，各取模型数据里的上界与它的较小者；预留仍按上界 | 开发者按负责人委托的 M1 质量审计决定（2026-10-18）。原来暂估和预留用同一个上界，上游没报告输入（Responses 只在 `response.completed` 里报，用户按 ESC 取消时就没有）时，带一张图就按整个上下文收，200k 的模型多收约百倍。1600：Anthropic 文档按 28×28 像素一个视觉 token，标准档单图上限 1568（vision 文档，2026-10-18 查）；new-api 的 `tokenkit/image.go` 在不知道尺寸时按 1024×1024 估，各家结果 520 到 1373；取 1568 加每图几个框架 token 再取整，不低于 new-api 对任何一家的估值，略偏高，与输出按 3 字节估的方向一致。4096：new-api 对非图片文件一律按 4096（`service/token_counter.go:166-169`）；Anthropic 的 PDF 文档里一页约 1500–3000 token 的文本加一张页图，一页约 3000–4600，4096 落在中间。已知偏差：高分辨率档（Opus 4.7 起单图上限 4784）的大截图会少估到约三分之一，多页 PDF 少估；少估由平台承担，只发生在上游没报告输入的那一次，本地按尺寸计数随 [#203](https://github.com/TYCT-tyct/Axiom/issues/203) 替换。没选继续按上界：多收两个数量级；没选现在就做本地按尺寸计数：每家的规则不同，#203 一起做 |
| 是否传递取消，适配器按所接系统的源码和实测给默认值，端点级的实测以后覆盖；不是没实测一律按不传递 | 开发者按负责人委托的 M1 质量审计决定（2026-10-18）。new-api 在客户端离开时关上游连接，sub2api 读完才计费，两家本来就不同；OpenRouter 也是按端点声明，不是一律不传递。一律按不传递的代价是用户每次按 ESC 都按整段回答付费，而 M1 没有分段，预留上一分不省。风险：站点前面有不传递断开的代理时平台多付，靠对账发现（[#227](https://github.com/TYCT-tyct/Axiom/issues/227)） |
| 免单只由三条规则决定：确知未执行、零输出、没有内容交到客户端；取消不免单，没有上游用量不免单，没有每日上限 | 原定义"没有输出就不收费"可以被利用：发长提示词、故意让模型拒答或立即断开，我们照付上游。OpenRouter 只在输出为 0 且结束原因为空或出错时免单，按次收费的项目照收（OpenRouter 文档《Zero Completion Insurance》，2026-10）。没有上游用量时无法确认输出为 0。上限由负责人决定删除（2026-10）：金额不该决定收不收，两家参考实现也都没有；平台为免单付的成本照记、可统计、可告警 |
| 有历史比例之前，暂估按固定比例：输入的文本 4 字节 1 个 token（图片和文件见下一行），输出 3 字节 1 个 token，向上取整，不超过预留的上界 | 开发者按负责人在 Issue #147 的授权决定（2026-10-16）。原来按 1 字节 1 个 token 的上界估，英文约 4 字节 1 个 token，查不到供应商记录时多收约四倍。输出取 3 偏向多估，因为输出单价通常是输入的数倍。输入的 4 字节比例对中文偏低：一个汉字 3 字节、常见分词器约 1–1.5 字一个 token，即每 token 约 3–4.5 字节，偏差有界，这条已知偏差记在 Issue #147 第 4 项。之后参考 new-api 在上游缺用量时用本地分词器计数的做法，按模型族换成本地分词器，再换成按模型统计的历史比例。没选继续按上界：可解释但系统性多收；没选直接上分词器：每族一个分词器，工作量和内存都在调用路径上，先把比例定下来 |
| 单位余额价值按供应商存，只追加，最新一行生效；节点在重建快照时读进内存，尝试按开始时的值换算，回执带着那一行的 id；确认之前供应商不进路由 | 它是供应商余额的属性，与管理接口按供应商确认一致；读进快照让成本换算仍是纯内存计算，结算路径上不多一次查询；只追加，再加上回执里的 id，用的值就能按 id 复原，不靠时间推断（节点用的是它最近一次 Reload 时的快照）；id 目前只在内存里的回执中，把它写进 `attempt_costs` 是兼容的改动，要按 id 复算已结算的尝试时再做。没选按端点存：同一份余额要逐端点改，漏一个就算错；没选结算时查库：钱的路径上多一次往返；没选把单位价值折进成本计划：计划和对账都按原生单位，每次充值改值就要重写全部计划 |

# 模型目录

有哪些模型、叫什么名字、官方规格和官方价格是什么。对应代码模块 `catalog`。概念之间的关系见[术语与核心概念](../glossary.md)。

## 要求

- 模型的标准 ID 采用 OpenRouter 的 `厂商/模型` 格式，厂商原生的名字也能直接使用。
- 目录基线自动同步，主要参考 OpenRouter，并与其他公开来源交叉核对。
- 价格一律按原价计算，不考虑任何优惠。
- 按上下文长度变化等复杂价格必须正确获取、正确计算。

## 设计

### 模型与名字

- **标准 ID**：`厂商/模型`，例如 `anthropic/claude-sonnet-4.5`。
- **公开别名**：厂商原生的名字，例如 `claude-sonnet-4-5-20250929`，可以直接调用，这样 Claude Code、Codex 不改配置就能接入。公开别名全局唯一：保存时如果同一个别名已经指向另一个模型，拒绝保存。
- **供应商别名**：某个中转站里对模型的写法，只在该供应商（或分组）范围内有效，只用于映射，不对外公开。同一个写法在不同中转站可能指不同模型，例如某站的 `gpt-4` 实际可能是 gpt-4o。
- **版本**：不带日期的名字指向一个带日期的具体版本。带日期的名字只对应它自己那个版本，永远不会被合并到别的版本。

### 模型的生命周期

- **状态**：草稿 → 上架 → 计划下线（带下线日期）→ 已下线。
- **新模型**：厂商发布新模型后，同步自动生成草稿，由运营 agent 审核后上架。
- **切换与迁移**：不带日期的名字换版本、下线模型的别名迁移到替代模型，都会改变用户实际用的模型和价格：
  - 切换前通知受影响的用户；
  - 新版本或替代模型更贵、能力更低时，默认需要人确认；
  - 切换时刻之后开始的请求按新模型的价格版本计费，之前开始的请求不受影响；
  - 切换记入审计。

### 名字映射

中转站和供应商的模型名五花八门，按以下顺序映射到标准模型：

1. 查该供应商的供应商别名，再查公开别名；
2. 用规则归一化后再匹配，例如统一大小写和分隔符。归一化不会去掉日期，不同日期的版本不会被合并；
3. 仍然对不上，由运营 agent 提出映射建议；
4. 映射后，用真伪检测确认它确实是这个模型（见[端点评估](quality.md)）。

认不出来的名字进入"待映射"队列，不上架。

### 目录基线

- **内容**：上下文长度、最大输出、输入输出类型、能力、支持的参数、知识截止时间、官方价目表。
- **来源**：
  - OpenRouter 的模型接口：每个模型的价格和规格，无需 key 即可读取（OpenRouter 网站的定价页，2026-10）；
  - models.dev：开源模型数据库，用 `tiers` 表达分档价格（models.dev，2026-10）；
  - LiteLLM 的模型价格表：用 `input_cost_per_token_above_200k_tokens` 这类字段表达超过 20 万 token 后的价格（LiteLLM 仓库，2026-10）；
  - 厂商自己的模型列表和价格文档。厂商文档是最终依据。
- **分档数据**：OpenRouter 的价格不一定带分档。分档价格优先以厂商文档为准，其次参考 models.dev 和 LiteLLM。
- **交叉核对**：各来源一致才自动更新。不一致就不自动采用，先告警，交给运营 agent 判断，必要时请人确认。
- **价格变化也有发布阈值**：目录价是参考价倍率规则的输入，它的变化和售价一样，超过阈值才发布（见[计费的「定价」](billing.md#定价)）。
- **OpenRouter 不可用时的退路**：如果它的使用条款不允许，或接口不可用，降级为 models.dev 加厂商文档，功能不受影响。
- **只用原价**：厂商的限时优惠、批量折扣都不进入目录。

### 价目表的结构

目录里的官方价目表、计费的价目表、适配器生成的成本计划，三者使用同一个结构，只是用途不同：

- 目录价目表记录官方原价，作为参考价；
- 成本计划记录供应商的原价，作为成本；
- 计费的价目表记录我们的售价。

结构包括：

- **计费项**：输入、输出、缓存读、缓存写（5 分钟 / 1 小时）、推理、图片、音频、按次工具费（如每千次联网搜索）。
- **条件**：
  - 按上下文长度分档。每一档必须声明三件事：
    - 门槛按什么算（Anthropic 按输入加缓存读写的合计，Google 按提示词 token）；
    - 计法：是"整单按档"（超过门槛后整个请求都按高档计价，Anthropic 和 Google 的长上下文就是这样），还是"超出部分按档"；
    - 哪些计费项随档位变化，例如输出价是否也变。
  - 分时段价格；
  - 服务等级，例如 flex、priority。
- **倍率型条件**：中转站常见的"满足条件时整体乘一个倍率"，例如 sub2api 的长上下文倍率，也用同一结构表达：条件 + 对哪些计费项乘多少。
- **单价**用精确小数存储（见[计费的「钱的表示」](billing.md#钱的表示)）。

### 计算正确的保障

- 每个模型家族都把厂商文档里的计价示例做成测试用例：给定用量，算出的金额必须和文档一致。
- 价目表和供应商实际扣费持续对账（见[计费的「供应商成本」](billing.md#供应商成本)）。如果某条规则写错了，对账差额会立刻暴露。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 标准 ID 用 OpenRouter 的 `厂商/模型`，厂商原生名字作为公开别名 | 负责人同意。兼容 OpenRouter 的客户端，同时让 Claude Code、Codex 这类只认原生名字的工具开箱可用 |
| 公开别名全局唯一，中转站的写法只在该供应商内有效 | 同一个写法在不同中转站可能指不同模型；全局共用会把用户请求映射到错误的模型 |
| 归一化不去掉日期 | 去掉日期会把同一模型的不同版本合并，价格和能力都可能不同 |
| 切换版本或迁移别名要通知，变贵或能力下降默认需人确认 | 否则用户的价格会被悄悄抬高，能力也可能下降 |
| 只用原价，不考虑优惠 | 负责人决定。OpenRouter 也按供应商的原价计费（OpenRouter 网站的定价页，2026-10）；按原价估成本只会偏高，不会亏 |
| 分档必须声明门槛口径、计法和受影响的计费项 | 各家的门槛口径不同，两种计法在超过门槛时差额很大；不声明就会算错 |
| 多来源交叉核对，不一致不自动采用，厂商文档为最终依据 | 任何单一数据集都可能滞后或出错；错误的参考价会通过定价规则传导到售价 |
| 1M 上下文、思考模式算端点能力，不另建模型 | 同一个模型在不同端点上能力不同；另建模型会让同一个模型分裂成多个条目 |

# 记录与告警

记录什么、怎么分类、存在哪、保留多久、怎么取用；以及监控、告警和通知渠道。对应代码模块 `observability`，代码接口和不变量见[模块 README](../../internal/observability/README.md)。数据留存的产品规则见[产品需求的「数据留存」](../product.md#数据留存)。

## 要求

- 记录要全面、完整、分类清楚、便于筛选，用于追溯，将来也可能用于训练模型。
- 对话内容完整保存，包括图片、文件等上传的内容；保存与否由平台统一决定，存储空间就绪前先关闭。
- Axiom 是 API 调用平台：任何人都不能通过产品查看对话内容。
- 告警不依赖运营 agent（见[运营](operations.md)）。

## 设计

### 记录的三类数据

| 类别 | 内容 |
|---|---|
| 调用记录 | 每次调用的元数据（见「写入时记全」） |
| 对话内容 | 请求和回复的完整正文 |
| 运行数据 | 指标、日志、链路追踪，不含正文和密钥，存放在运维节点上的监控系统 |

### 写入时记全

有些信息只有请求发生的那一刻才知道，必须当场记下：

| 类别 | 内容 |
|---|---|
| 谁 | 站点、账户、工作区、key、终端用户标识、IP |
| 用什么 | 客户端应用、应用自己报的归因、会话和子 agent 编号、请求类别 |
| 走了哪 | 模型、端点和来源类别、出口、每次尝试、路由过程 |
| 结果 | 用量（含原生 token 与写入时能确定的物理输入）、售价和价格版本、成本、是否流式、是否缓存命中、延迟、首字时间、结束原因、错误类型、是否免单（只由三条免单规则决定） |
| 权利 | 用户当时同意的协议版本；产出内容的模型是否允许用于训练 |

写入标签的空值表示未知，不表示没有。

- **终端用户标识**：来自请求自己的终端用户字段：OpenAI 各格式取 `user`，没有时取 `safety_identifier`；Messages 只取 `metadata.user_id`，顶层多出的 `user` 不算。空白或非字符串记为没有。保存的是 HMAC-SHA256，输入是账户和标识，密钥由节点身份密钥按这一用途派生（与发往上游替换标识的派生值不同）；同一标识在两个账户里是两个终端用户，身份密钥轮换后新旧哈希对不上。Claude Code 把设备和会话写进 `metadata.user_id`，所以它的「终端用户」实际按会话区分。
- **会话**取客户端自己指名的会话：请求体 `session_id`（三种对话格式），没有时依次取 `X-Session-Id`、`X-Claude-Code-Session-Id`、Codex 的 `session_id` 请求头，空白的跳过；去掉控制字符，超过 128 字符截断（请求本身最多 256）。路由退而使用的提示缓存键和 `metadata.user_id` 不记成会话。**子 agent 编号**没有可靠来源，记空值。
- **请求类别**按到达的端点：三种对话格式 `chat`，旧版补全 `completions`，向量 `embeddings`，重排 `rerank`，Responses 压缩端点 `compact`。
- **客户端应用**从 `User-Agent` 识别：含 `claude-cli` 或 `Claude Code` 记 `claude-code`，含 `codex` 记 `codex`，其余为空。
- **应用归因**：客户端在 `HTTP-Referer`、`X-OpenRouter-Title`（旧名 `X-Title` 也认）和 `X-OpenRouter-Categories` 里声明，与 OpenRouter 的[应用归因头](https://openrouter.ai/docs/app-attribution)同名；这些头不转发给上游（[接入与对外接口的「转发规则」](gateway.md#转发规则)）。值去掉控制字符、按列宽截断；`app_referer` 对绝对 URL 只留 scheme、host 和 path（userinfo、查询串和片段常带令牌）；类别规范成最多两个小写连字符名字；不合法的部分记空值。
- **错误类型**：调用的是客户端收到的统一错误类型（[接入与对外接口的「错误」](gateway.md#错误)），流式中途出错的是流结尾那个；上游正常结束、整份回复已透传或客户端已离开（结束原因 `cancelled`）的为空；执行中崩溃的记 `internal_error`。每次尝试的：2xx 之前失败的记适配器给的原因（`rate_limited`、`credential_rejected`、`upstream_error`、`unknown`、`transport`，与熔断原因同名）；2xx 之后读流失败、空回复、续预留失败的记网关判定的统一类型；客户端在尝试结束前离开的记 `cancelled`；成功为空。服务端工具循环里这一轮本身无法继续的记在这次尝试上；网关自己执行的搜索失败算调用的错误。
- **首字时间**：尝试从它开始算到上游第一段内容；调用从请求到达（读请求体、排队和准入之前，与 `at` 同一时刻）算到回答它的那次尝试的第一段内容。延迟从同一时刻算到调用结束，所以首字时间不大于延迟。没有内容的尝试、整份透传的回复和缓存命中记 0。
- **每次尝试单独一行**：端点、供应商、来源类别、出口、从 1 起的序号、起止时间、首字时间、结果和错误类型；请求 ID 加序号是它的键，供应商的成本和对账键按同一对键关联。路由过程留在调用的 `route`，不重复存。
- **用户同意**：准入事务随 key 读出所有者对服务条款和隐私政策各自同意过的最新版本，写成 `kind:locale:version`，两种都有时逗号连接（`terms:zh:3,privacy:zh:2`）；一种都没同意过写 `none`；已发布但还没同意的新版本不算。同意协议不等于允许训练：训练许可仍写不允许，由以后的训练规则决定。
- **模型许可**：部分厂商的条款限制用其输出训练竞争模型，所以每条记录都标明产出它的模型是否允许用于训练。

### 对话内容记录什么

对话内容保存功能已冻结，保存正文的写入路径没有接入，开关保持关闭；打开前先完成容量与成本评估。规则如下。

- 客户端发来的完整请求（消息、系统提示、工具定义、参数及多模态内容）、返回的完整回复（正文、推理内容、工具调用），以及每次尝试与上游之间的原始交互。
- 正文保持原样，不改写、不脱敏。请求头和响应头只按白名单记必要的几项；任何凭证一律不记。
- 写入与调用记录无关：先写入本节点有容量上限的磁盘缓冲，再异步上传，绝不让请求失败；流式回复在结束或客户端取消时写入已产生的部分；缓冲满或桶不可用时告警并记录丢失条数；重启后继续上传缓冲。

### 分类：两层标签

| 层 | 什么时候打 | 例子 |
|---|---|---|
| 写入标签 | 请求发生时，确定无疑 | 客户端应用、模型、来源类别、语言、是否用了工具、是否带图片或文件 |
| 分析标签 | 后台异步分析得出 | 任务类型、领域、是否成功完成、质量信号、是否含个人信息或敏感内容 |

分析标签由可配置的分类器打：先用规则，复杂的再用模型批量处理，不进调用路径；分类用的模型只能是自己部署的或负责人在控制面登记的，有预算上限，可抽样；分类器升级后可重新打标签；对话内容保存关闭期间只有写入标签。

### 存储

| 层 | 存什么 | 存在哪 |
|---|---|---|
| 热 | 近期的调用记录和标签 | PostgreSQL，按月分区；调用和它的尝试按同一组月份分区 |
| 温 | 较早的调用记录 | 对象存储里的 gzip CSV，带清单（列名、类型、行数、SHA-256） |
| 冷 | 对话内容、长期归档 | 对象存储的低价存储层 |
| 永久 | 账本、财务记录、汇总统计 | PostgreSQL |

- **存储桶**：程序只有一个 S3 兼容的桶，由 `AXIOM_OBJECTSTORE_*` 配置；没配置时归档关闭，调用记录全部留在 PostgreSQL。归档对象写在 `call-log/v1/<YYYY-MM>/` 下。
- **调用记录到期**：按分区整块转层，不逐行。整月早于热窗口（`hot_days`，默认 90 天，0–3650，管理员数据；0 表示全部留在 PostgreSQL）的 `call_log` 与 `call_attempt` 分区先导出到对象存储，清单确认两份对象都完整后才从 PostgreSQL 删除；快照后有迟到写入时整月重写，绝不按旧清单删除。归档对象不删，所以「调用记录全部保存」仍成立。账本、汇总统计和审计各有自己的保留，不随调用记录删除。
- **缺月的窗口**：PostgreSQL 能否完整回答一个窗口，看窗口覆盖的每个整月是否都还在，缺一个月（含较老月份归档失败而较新月份已删的中间空洞）就标为不完整。`available_since` 是最老的剩余月分区。看板和调用列表把触到已归档月份的窗口标为不完整，不把归档当成零（[运营的「运营看板」](operations.md#运营看板)）；收入、成本和现金来自预留与账本，不受影响。
- **对话内容**（冻结）：按消息存、每条只存一次，图片和文件按内容只存一份，调用记录保存引用；去重只在同一账户内，指纹是带账户密钥的 HMAC-SHA256，拿到桶文件列表也判断不了内容在不在。键是 `content/v1/<site>/<account>/<blob>`。内容被多次引用，按最后一次被引用的时间到期，最后一个引用它的调用到期后才转冷或删除。表 `content_keys`、`content_blobs`、`content_refs`、`content_exports` 都只有平台范围可见（[模块 README 的「表」](../../internal/observability/README.md#表)）。

### 写入路径

一条已经服务的调用必须留下记录：产品要求调用记录全部保存、不能关闭，所以过载时不丢新记录；节点保不住下一条记录时，它拒绝新调用，而不是服务一条没有记录的调用。做法是准入预占、本机预写日志（spill）、组提交 fsync、顺序批量入库、满了拒绝；格式与恢复见[模块 README 的「写入」](../../internal/observability/README.md#写入)。

1. **准入预占**：gateway 准入时 `Admit` 占一个记录位置。位置总数 `Capacity`（5000）包含在途调用和已落盘未入库的记录；满了答 503 `overloaded`。
2. **响应前持久化**：结算写成或交给后台之后、结尾写出之前，gateway `Commit` 这条调用和它的每次尝试：追加到 `AXIOM_CALL_LOG_DIR` 的段文件，等一轮组提交 fsync 才返回。客户端看到结尾时记录已在磁盘上，崩溃和断电都由下一次启动重放；并发的 `Commit` 共用一次 fsync。
3. **顺序入库**：后台写协程按段内顺序只读到已 fsync 的位置，每 500 条或 200 ms 写一批，一个事务里先写 `call_log` 再写 `call_attempt`；`ON CONFLICT DO NOTHING` 让重放不产生重复行。写成功才推进确认位置、删掉已确认的段；排空时把活动段也换掉。每次写入期限 10 秒，失败退避重试（100 ms 起翻倍，上限 5 s）直到成功；数据库暂时不可达时调用不等待。
4. **单写者**：一个 spill 目录只归一个进程（`flock`），第二个进程启动失败；每个节点用自己的持久目录。
5. **启动恢复**：最后一段末尾残缺的记录是还没返回的 `Commit`，截掉；长度完整但校验和不符的是损坏，启动失败而不是悄悄跳过。已确认位置之前的不重放。
6. **失败**：数据库说数据本身有问题（SQLSTATE 22/23）或编码失败时，不跳过坏行：保留整批、标记不可记录，`Admit` 从此拒绝，gateway 答 503；已预占位置的在途调用仍能 `Commit`。磁盘写或 fsync 失败同样标记不可记录；这次已结算的调用补不回记录，日志和 `records.lost` 指出请求 ID。单条记录上限 64 KiB，磁盘上限约 `Capacity × (64 KiB + 8) + 8 MiB`，另有至多 `Capacity` 个停放的待定记录。
7. **结算留给后台的调用**：前台结算没在期限内写成时，结尾写「费用待定」，gateway 照样在结尾之前 `Commit` 一条待定记录（用量、售价、价格版本和免单留空，`billing_pending` 为真），停放在 spill 目录的 `pending/` 下，同样在结尾前持久并占着这次调用的位置。后台结算提交后，已结算记录照常进段文件并替换它；结算放弃或交给清理时，待定记录移进段文件成为这次调用的记录；节点在这之前死掉的，下次启动先把停放的记录移进段文件。所以一次调用只有一条记录进入数据库，调用日志仍然只插入。
8. **按账本补全待定记录**：进了段文件的待定记录，结算仍可能已经提交（节点死在结算提交之后、已结算记录落盘之前，或最后一次尝试在放弃之后才提交）。写库者插入有待定记录的批之前，在同一事务里按请求 ID 读 billing 已结算的收费（更正之后的值），加 `FOR SHARE` 锁等还在提交的尝试；读到的用账本的用量、档位、价格版本、实收和免单补全这一行再插入，读不到的存成待定（计入 `records.unsettled`），这是最终结果。补全发生在唯一一次插入之前，表仍然只插入。没有待定记录的批不读账本。
9. **旧版本挡在外面**：不认识待定记录的旧版本会把它存成价格为 0 的已结算调用；进了段文件的待定记录只写进段头为 `AXIOM-WAL-2` 的段，旧版本遇到就拒绝启动。回滚到更早的版本前，先让当前版本把 spill 写完（[发布前](../ops/release.md)）。

**崩溃与断电的边界**：`Commit` 返回之后的记录不会因崩溃或断电丢失；`Commit` 返回之前崩溃的调用，客户端也没有收到完整结尾。结算留给后台的调用同样只有一行记录：结算提交过的带账本金额，没提交的（清理释放预留、不收费）是待定行；不存在「账本收了钱、记录却一直待定」的行。

**待定行不读成零**：账户自己的读取（调用列表和 CSV 导出、汇总、活动、`generation` 和按 ID 取）跳过它；运营的追溯和后台调用列表标出待定、不给价格；花费异常检测和看板只数调用，待定行的售价加 0。

**记录还没写进数据库时**，按调用编号查询返回 404，不由账本补（[接入与对外接口的「用量与费用」](gateway.md#用量与费用)）。

### 加密与密钥

对话内容加密已冻结。每个账户有自己的数据密钥，由平台密钥环封装后存在 `observability.content_keys`，主密钥不在数据库里（[安全的「安全基线」](../security.md#安全基线)）；正文对象用 HKDF-SHA256 派生的 AES-256-GCM 子密钥加密，摘要用另一子密钥的 HMAC-SHA256，换账户或换 blob 都解不开。数据密钥随数据库备份，主密钥另有备份；丢失密钥等于永久丢失该账户全部内容。销毁一个账户的数据密钥使其全部内容立即无法读取；不可逆，只作用于内容，不影响调用记录和账本；只有负责人经两步验证、二次确认后才能执行。Responses 的会话状态单独保存。

### 保留与开关

- **调用记录**：始终保存，不能关闭。明细在热层保留 `hot_days` 后转入温层，汇总统计长期保存。spill 满时拒绝新调用是背压而不是开关。
- **对话内容**：是否保存是平台级开关，站点和账户都不能修改；对象存储客户端（[platform/objectstore](../../internal/platform/objectstore/README.md)）、内容表、账户密钥、去重引用和受控导出已落地，保存正文的写入路径和到期回收还没接入，开关保持关闭；打开后默认保留 90 天，后台可调，也可设为长期保存（到期转入冷层，不删除）。
- **账本和财务记录**不受保留设置影响，始终保留。
- **Responses 的会话状态**是续接功能的内部数据，单独保存，不受内容开关影响（[接入与对外接口](gateway.md#responses-的会话状态)）。

### 谁能看

- **调用记录（不含内容）**：用户和企业账户管理员看自己账户的；站长看本站用户的；平台运维和运营 agent 都可以看。
- **对话内容和会话状态**：任何人都不能通过产品的任何界面或接口查看，包括用户本人、企业账户、站长、平台运维和运营 agent。
- **唯一的取用方式**：由负责人发起的受控导出。

### 用户调用记录查询与导出

控制台的调用记录接口都要 `calls.view`，只读本账户可见的元数据，在账户范围里查询（行级安全只放行这个账户的行）。所有响应的新成员可选，旧节点缺失时页面显示不可用，不当成空值或 `false`。

- **列表** `listCalls`：时间、模型、客户端应用、key、工作区、成功/报错、请求 ID 可组合筛选；成功表示 `error_kind` 为空，报错表示非空，不按 HTTP 状态或最后一次尝试推测。每页默认 50、最多 200 条，按 `(at, id)` 倒序键集翻页。`status_filter` 回显生效的状态筛选；最近报错由服务端按报错筛选取最新五条。带可选 `attempt_count`；`fell_back=true` 筛选尝试数大于 1 的调用（含模型侧循环），由 `fell_back_filter` 回显，只用于列表，聚合与导出不接受。
- **详情** `getCall`：可选 `attempts` 与 `route`。尝试按序号排列，只有公开端点代号、来源类别、起止时间、首字毫秒、结果、错误类型和可确定的收费标记，不含供应商真名、成本、出口或凭证；路由摘要只有预设 ID/版本、过滤原因计数、原样的 `excluded_more`、首选端点公开代号及 `fastest_unmeasured` / `preset_unavailable`，不重建被省略的候选。代号只从当前可路由快照解析，端点退休或快照不可用时省略。旧记录没有尝试时返回空数组，没有路由或形状不兼容时省略摘要。
- **收费标记** `charged` 指用户实收，不是供应商成本：有账单明细时以校正后的实收为准，否则取调用记录；实收为零时所有尝试为 false；不同端点回退只有最终尝试为 true；重复最终端点可能属于合并结算的模型侧循环，这组尝试省略标记，页面显示未知。
- **汇总** `aggregateCalls`（`GET /api/console/v1/calls/aggregate`）：按 UTC 日、模型或 key 汇总调用次数和用户实收，货币分开；是观测汇总，不是账本对账，尚未入库的调用不在其中。金额（十亿分之一单位）和次数是十进制整数文本，合计可以超过 int64，只有这个响应放宽 19 位限制。默认最近 30 天、最多 31 天，最多 1000 组，超出拒绝，不返回不完整的总计。
- **会话** `listCallSessions`（`GET /api/console/v1/calls/sessions`）：按客户端指名的非空 `session_id` 归组，沿用列表筛选，先过滤后归组。每个会话、币种一行：`calls`（精确整数文本）、`price`（十亿分之一单位金额文本与币种）、`main_model`（匹配调用最多的公开模型，同次数按模型名字节序）、`client_app`（最新匹配调用）、`first_at` / `last_at`。没有客户端会话的调用不出现，不用路由粘性的回退身份造会话，不读正文。默认最近 30 天，窗口非空、最多 31 天，含起点不含终点；匹配的已结算会话调用超过 100000 条时整页拒绝，不返回截断合计。每页默认 50、最多 200 行，按 `(last_at, 最新调用 UUID)` 倒序翻页，游标带签名，绑定账户、窗口和全部筛选，篡改或换筛选续用都答 400；后续请求原样带回返回的 `since` / `until`。翻页不是冻结快照。
- **导出** `GET /api/console/v1/calls/export`：相同筛选下的调用元数据 CSV，没有正文、凭证、成本、端点和路由，不打开内容的受控导出权限。同一只读快照内先探测最多 10001 条，超过 10000 行答 400、不开始下载；未超限时每批 200 条边读边发。默认最近 30 天，最多 31 天；`X-Export-Since` / `X-Export-Until` 给出实际窗口。金额用九位小数的精确文本；每格首个非空白字符为 `= + - @` 时前加单引号。成功响应始终完整，不靠 trailer 表示截断；中途失败终止流。
- **用量统计** `getUsageStatistics`（`GET /api/console/v1/usage/statistics`）：只查小时汇总表，不扫明细。可按模型、key、工作区筛选或分组。每个桶按货币返回用户实收、请求数、成功数与输入/输出/缓存读/缓存写 token；日和周由小时相加，周从 UTC 星期一开始。输入是 `input + audio_in + image_in`；输出是 `output + reasoning + audio_out + image_out`，与活动接口一致，Messages 已含思考的 `output` 不重复加；缓存写合并 5 分钟与 1 小时两项；不算首字百分位。范围 `[since, until)` 最多 90 天，`granularity=hour` 最多 7 天，另有 `day`（默认）、`week`；起止必须对齐 UTC 整点；默认到最近已结束的小时，向前 30 天（小时粒度 7 天）。边缘桶只含范围内的小时；空桶和没有调用的分组省略。`compare=previous` 返回前一段等长范围的合计，同一快照、同一筛选。范围不合法或结果超过 10000 行答 400，10 秒期限。
- **token 与比率**：只加实际报告的字段，完全没报告的项省略。缓存命中率只用同时报告缓存读与物理输入的调用算 `sum(cache_read) / sum(physical_input)`，`cache_rate_requests` 给出参与请求数，分母为零时省略。成功率是 `successes / requests`。
- **汇总的新鲜度**：调用入库的同一事务由触发器追加待汇总 journal（重复插入不触发），后台每分钟把 journal 累加进 UTC 小时行；迟到记录加回它自己的小时。迁移前已有的行一次性回填，只覆盖仍在 PostgreSQL 的调用；`backfill_complete=false` 时历史结果不完整。已结束小时在 journal 消费完后才与 `listCalls` 的价格和一致；调用日志归档不删汇总。

以上查询都只读 PostgreSQL 尚存的热记录，待定记录一律排除，尚在本机 spill 的调用还没进来。窗口、请求和 socket 写入受 10 秒期限，客户端断开取消查询。用户看到的分项售价由编排层在读到可见调用之后，按请求编号批量读 billing；调用记录只保存价格版本，不复制发票（[计费](billing.md#用户看得到什么)）。

### 受控导出
受控导出（冻结）是取用对话内容的唯一方式，只在运维命令 `axiom content` 里实现，不进入控制台、管理 API 或运营 agent 的工具。`keygen`、`approve`、`decrypt` 在负责人的机器上运行；只有 `export` 在服务器上运行，只接受 `--approval` 一个参数，范围全部来自签名。

- **批准**：负责人离线持有两把独立的 Ed25519 签名私钥和一把 X25519 解密私钥；服务端只配置三把公钥（`AXIOM_CONTENT_EXPORT_SIGNING_KEY`、`AXIOM_CONTENT_EXPORT_SECOND_SIGNING_KEY`、`AXIOM_CONTENT_EXPORT_ENCRYPTION_KEY`），原始 32 字节文件，拒绝组或他人可写的文件和目录及符号链接。批准文件覆盖动作、版本、两个签名者指纹、接收公钥指纹、`[since, until)`、站点、账户、目标绝对路径、格式、签发/失效时间和随机数，两把私钥对同一份 RFC 8785 规范 JSON 各签一次，两把都验签通过、未过期、与配置一致才接受；最长有效 7 天，一次性使用，签发时间最多比服务器时钟快 5 分钟。
- **审计**：先验签，再在平台范围事务里写 `content_exports` 和 `content_export.start` 审计（批准摘要唯一，拒绝重放）；完成写 `content_export.complete` 与输出 SHA-256，失败尽力写 `content_export.fail`。
- **范围与格式**：按引用的创建时间选，可再限定站点或账户，最长 366 天；导出 `request` 和 `response` 两类，并纳入响应缓存（`gateway.response_cache`，同一段对话的短期副本，写进 `cache.jsonl` 和 `cache/<cache_id>`）。删除账户时两者都要删（[安全的「内容安全」](../security.md#内容安全)）。输出是 gzip 的 tar，含批准文件、清单和原样正文，不改写、不脱敏。
- **加密**：每个文件生成临时 X25519 密钥，与负责人公钥做 ECDH，经 HKDF-SHA256 派生 AES-256-GCM 密钥，按 64 KiB 分块认证，缺最后一块或尾部多字节都拒绝；落盘前就是密文，服务端和操作者任何时刻都看不到明文文件；目标必须是不存在的绝对路径，先写临时文件再用硬链接发布，不覆盖。
- **保管与边界**：销毁账户数据密钥不影响已导出的文件；导出后的保管由负责人负责；丢失 X25519 私钥就解不开已导出的文件。命令以平台权限运行，能改二进制或读进程内存的运维仍可绕过应用层约束，所以只让受信的运维账号执行，签名防的是伪造范围、目标和接收方。正文写入只能在所有节点都认识 `content_keys` 之后开始，开启后不能回退到旧二进制执行 `keyring retire`。

### 追溯

从任意一条调用记录都能串起：它的每次尝试（同一个请求 ID 和序号）、路由过程（调用的 `route`）、账本交易（`billing.transactions.request_id`）、供应商的扣费记录（同一个请求 ID 和序号），以及运营 agent 对它做过的操作。请求 ID 是唯一的关联键，调用记录不抄账本 ID（[模块 README 的「追溯」](../../internal/observability/README.md#追溯)）。已经归档离开 PostgreSQL 的月份，追溯返回空。

### 监控与告警

- **指标与链路的约定**：命名、标签基数上限、采样与导出见 [platform 的「遥测」](../../internal/platform/README.md#遥测)。
- **指标**：每个端点、供应商、节点、模型的请求量、错误率、延迟；收入、利润率、各供应商余额；底线指标的达成（[总体架构的「底线指标」](../architecture.md#底线指标)）。指标不按账户、key、用户区分；按账户和按 key 的异常（盗用、泄露）从调用记录算（[安全的「防滥用」](../security.md#防滥用)）。
- **被丢弃的作业**：River 用尽重试或救援都会把任务标为 `discarded`。队列每分钟扫描 `river.river_job` 里的 `discarded` 任务，在 `platform.discarded_jobs` 认领一行（主键任务 ID），记 error 日志 `queue.job_discarded`，累加 `axiom.pg.queue.discarded_jobs`；告警按增量。认领并上报后，终态满 24 小时才删任务和认领行。节点只取自己有 worker 的任务种类，滚动发布时旧节点不消耗新种类的尝试次数。被丢弃的邮件任务保留待发行供排查（[mail 的「队列与重试」](../../internal/platform/mail/README.md#队列与重试)）。
- **告警规则是后台数据**：阈值、持续时间、严重程度都可配置；另有自动的异常检测。
- **在哪里判断**：River 消费者在核心节点判断，独立于运营 agent。最关键的健康检查同时在核心节点和外部在线监测服务上判断，运维节点故障时经直通通道告警（[运营的「通知」](operations.md#通知)）。
- **防告警风暴**：同类告警合并，一次故障只通知一次；可以设静默时段。
- **分级通知**：一般信息进每日摘要；警告发即时消息；严重的发即时消息，规定时间内无人确认就打电话。电话升级待定（[#731](https://github.com/TYCT-tyct/Axiom/issues/731)）：现在只有邮件和 Webhook 及投递状态。严重告警同时唤醒运营 agent 排查。

### 告警信号、事件与规则（E5-3）
告警通道已冻结，只写现行行为。

- **信号入口**：各模块只依赖 `platform/alert` 的 `Sink`：`Raise(kind, key, severity, fields)` 和 `Resolve(kind, key)`，返回是否进入有界本机缓冲；严重度 `info`、`warning`、`critical`；字段只能是不含正文、凭证和个人信息的运维元数据。调用不等数据库、不借用业务事务；缓冲满或输入越界返回错误，调用方保留原有日志和指标。异步写入 `platform.alert_signals` 后才跨节点持久，入缓冲到提交前崩溃仍可能丢；需要持久的来源用 `alert.Persist` 或在自己的业务事务里持久化。
- **事件**：`observability.alerts` 每分钟读最多 1000 条信号，消费与事件变更同事务。同一 `(kind, key)` 最多一个未恢复事件；反复 raise 更新次数和字段，不重复通知；恢复后再 raise 是新事件。状态 `firing → delivered → resolved`；没安排过首通知的短暂事件不发恢复通知。窗口计数类信号（安全样本、支付窗口样本、`routing.preset_refuses_all`）逐条评估，事件保留当前窗口值。
- **规则**：种类、阈值（信号的 `value`，缺省 1）、持续秒数、最低严重度、渠道、UTC 静默起止分钟（可跨午夜，两端相同表示关闭；静默期间持久等待，恢复通知也遵守）和重复间隔（默认 0，即每次故障每渠道一次首通知）。首通知失败的事件只留 failed 恢复回执；变更规则不撤回已排入的通知；同一种类不能有两条规则指向同一渠道。
- **默认规则**有五条，默认无渠道，管理员绑定后才发送，不猜收件人：`observability.write_lag`（待写数至少 4000，持续 60 秒）、`billing.settlement_anomaly`、`queue.discarded`、`observability.records_lost`、`observability.spend_anomaly`。其他种类都没有预置规则，管理员要自己新增规则并绑定已验证的渠道；没有规则时事件仍持久可查。
- **来源**：写入积压（每分钟采样 spill 待写数 `records.pending`，不在 `Commit` 里发）与记录丢失（只在计数增加时上报，不可逆，管理员调查后关闭）；结算与账本自平、供应商对账差异（与业务同事务持久化，需人工调查关闭）；支付差异和验签/查询/限流窗口计数（每节点按 UTC 分钟，每个完整窗口发一次完整计数，合并键含节点身份）；账户猜凭证失败峰值与账户暂停；供应商持久事件（按 `(version, seq)` 记消费位置，由新的成功观测或明确的恢复事件恢复，信号不带上游文字）；路由 `routing.preset_refuses_all`；目录 `catalog.*`（[模型目录的「官方价格页」](catalog.md#官方价格页)）。用户通知走租户的邮件 outbox，不进平台运维事件。

| 种类 | 合并键 | 恢复方式 |
|---|---|---|
| `observability.write_lag` / `observability.records_lost` | 节点 | 两次空采样或正常关停 / 管理员关闭 |
| `queue.discarded` | 任务种类 | 管理员关闭 |
| `billing.settlement_anomaly` | `unknown_items` / `platform_borne` | 缺项清除后自动恢复 / 人工调查关闭 |
| `billing.reconciliation_difference` | `ledger` | 下一次自平正常 |
| `payments.discrepancy` / `payments.query_paused` | 差异记录 UUID / 商户 TypeID | 标记已调查 / 暂停后成功查单 |
| `payments.verify_failed` / `payments.query_failed` / `payments.rate_limited` | `<节点>/callbacks`、`/queries`、`/orders` | 下一个完整分钟没有同类事件 |
| `payments.merchant_unreadable` | `<节点>/<商户 TypeID>` | 商户配置重新打开 |
| `accounts.authentication_failures` / `accounts.account_suspended` | 站点 / 账户 TypeID | 下一个完整低值或零窗口 / 操作员解除暂停 |
| `operations.agent_alert` | `<运营凭证 UUID>/<agent 给的键>` | agent 调 `alert_resolve`，或管理员关闭（[运营的「运营接口」](operations.md#运营接口)） |
| `routing.preset_refuses_all` | `<节点>/<预设 UUID>` | 该节点下一个路由成功过的一分钟窗口 |
| `catalog.page_changed` / `catalog.page_failed` / `catalog.page_overdue` | 页面 UUID | 人工处理 / 取数成功或停用页面 |
| `suppliers.login_expired` / `sync_attention` / `task_stopped` / `low_balance` / `pool_capacity` / `sources_unavailable` / `exhausted` | 供应商 UUID（任务、分组加后缀；`exhausted` 为 `all`） | 新的成功观测、明确的余额恢复、`pool_low` 行消失或可用来源重新出现 |
| `suppliers.reconciliation_difference` | 分类（`under_estimated`、`held`、`unmatched` 等） | 人工调查关闭 |
| `alert.channel_unavailable` | 渠道 ID | 最新周期自测成功，或删除渠道 |
| `observability.spend_anomaly` | `<账户 UUID>/spend/<币种>` / `/region` / `/model` | 下一轮检测中该异常消失 |

- **邮件渠道**：经 `platform/mail` outbox 和 River `mail.send_tracked` 发送；回执 pending、queued、delivered（SMTP 接受，不表示已读）、failed；网络投递至少一次，最多五次尝试。
- **Webhook 渠道**：HTTPS POST JSON，经 platform egress 的地址策略，不跟随重定向，10 秒期限，只有 2xx 算接收；JSON 在派发时冻结（通知 `id`、故障 `event_id`、`sequence`（首通知 0，重复递增，恢复 -1）、`kind/key/severity/fields`、`state`），重试不改正文、每次重签时间。`X-Axiom-Signature` 为 `t=<Unix秒>,v1=<HMAC-SHA256 十六进制>`，签名输入是时间戳、一个点和原始正文；接收端应恒定时间比较、拒绝超出正负 5 分钟的时间戳、按通知 ID 去重至少 24 小时、重复接收也返回 2xx。网络失败经 River 退避最多 5 次后记 failed；目标非法或没有签名密钥直接记 failed，不发无签名请求。签名密钥由管理员单独写入（32–512 个 UTF-8 字节），信封封存并绑定渠道和目标地址，不出现在配置、回执、审计和任务里；轮换后一小时内同时带新旧两个 `v1`。只在所有核心节点都认识 Webhook 后才配置。
- **渠道自测**：每个已配置渠道立即自测，之后每小时一次，走同一发送和回执路径，不受静默影响；按最新终态测试回执发 `alert.channel_unavailable`（不发往故障渠道本身），测试成功或删除渠道时恢复。
- **通知类事件**（`alert.test`、运营每日摘要 `operations.audit_digest`）报的是一件事而不是故障：不发恢复；只经匹配的规则告知，这些规则都生成了首通知且没有待发通知时自己关闭。
- **清理**：已恢复且所有通知都终态的事件保留 30 天，每分钟最多清理 100 个。
- **管理 API**：签名密钥设置/轮换、规则与渠道整体读取/替换（修订号乐观锁，拒绝悬空渠道引用）、事件分页（每页 100 条）、最近 100 条回执、测试发送、人工关闭事件；写操作要 MFA、平台范围的 `sites.manage`、幂等键、修订号与审计；规则和事件只有平台范围可读写。

### 账户花费异常检测（E4-12）
冻结的功能。`observability.spend` 每 10 分钟离线检测一次，不在调用路径上：取最近窗口（默认 1 小时），与账户自己在前一段基线（默认 24 小时）里的同一时长比较；没有跨账户基线；只检查窗口里有调用且基线有调用的账户。三种信号：**花费暴涨**（同时达到绝对下限且不低于基线每小时花费的倍数，按币种）、**陌生来源地区**（出现基线里没有的 IP 网段，IPv4 /16、IPv6 /32，不依赖 GeoIP，且调用达到次数下限）、**平时不用的模型**。都发 `observability.spend_anomaly`（warning），一个账户同时命中几种时事件各自保留，用户只收到一封提醒；状态在 `observability.spend_anomalies`，第一次命中时同一事务插入状态行、持久化信号并写用户提醒，状态行在就不再发，异常消失时删行并发一次恢复。

阈值存在 `observability.spend_detection`（管理 API 的 `spend_detection` 对象整体读写，保存时校验）：默认开启、窗口 1 小时（15 分钟–1 天）、基线 24 小时（不短于窗口、最长 7 天）、花费下限 5 额度、3 倍（1–1000）、陌生网段和模型各 5 次；关闭检测会恢复所有仍在发生的状态。用户提醒走 accounts 的偏好（`notification_preferences.spend_anomaly` 默认开启）、outbox 和可选 Webhook；总开关 `spend_detection.notify_users` 默认关闭，等所有节点都认识这个种类后由管理员打开；邮件只有站点名称、异常种类、金额（地区和模型信号没有金额）和处置建议，Webhook 只有稳定 ID、种类、金额和时间，都不含调用内容、IP 原文或凭证。自动暂停 key 不在本期（[安全的「决策与理由」](../security.md#决策与理由)）。检测失败只让本轮任务重试，不影响调用和计费。

### 通知渠道

- 渠道是插件：Telegram、飞书、企业微信、微信（经企业微信或第三方推送）、邮件、短信、电话；现在已接邮件和 Webhook。个人微信没有官方机器人接口；电话和短信需要接入服务商，电话升级待定（[#731](https://github.com/TYCT-tyct/Axiom/issues/731)）。
- 每个渠道都有发送回执和失败重试，并定期发测试消息确认可用。
- 接收人由运营的控制面决定（[运营的「控制面」](operations.md#控制面只有负责人能改的设置)）。

### 用户提醒与站内公告

余额不足、到账、认证因素变化属于 accounts 的用户偏好与模板，不使用平台运维规则和接收地址，经 SMTP outbox 和可选的用户 HTTPS Webhook 异步投递。站内公告是本站一般信息，见[账户领域的「用户提醒与站内公告」](accounts.md#用户提醒与站内公告)，不等于必须送达的模型迁移通知。

### 给用户看的

控制台里有调用记录（不含内容）、用量统计，可以导出；调用记录查询接口见[接入与对外接口](gateway.md#用量与费用)。

## 后台检索

管理调用列表按请求 ID、账户、站点、时间组合检索，另可带精确模型名和结果（`ok`/`error`），默认最近 24 小时、最多 31 天，50 条一页、最多 200 条，按 `(at, id)` 倒序游标分页，10 秒期限。客服持平台 `calls.search` 只读摘要（请求、账户、时间、模型、结果、延迟、用户收费），没有成本、端点、供应商、IP 或路由；完整 trace 和按序号排列的尝试要 MFA 加平台 `calls.inspect`。内置 admin 角色有 `calls.search`、`calls.inspect` 和 `audit.view`，support 只有 `calls.search`；不复用控制台的 `calls.view`，免得平台成员的授权扩大成全平台检索。审计只读列表与详情要 `audit.view`，可按账户、站点、操作者、模块、动作、目标和请求 ID 精确过滤，同样有界时间窗和键集分页。没有清空接口。列表回传实际 `since`/`until`，后续页原样使用。

管理后台的调用记录页只显示摘要；持 `calls.inspect` 的会话才看到进 trace 的链接，trace 页展示成本、路由原始 JSON 和尝试。审计详情在同时持 `calls.search` 时把请求 ID 链到调用列表，链接带覆盖该条目的 31 天窗口。权限不足 403、已清理的条目 404、旧节点缺少的可选成员显示「当前节点不可用」。运营看板读同一站点和窗口里的总调用数、错误数和前 10 个账户与模型；字段可选，旧节点没有时显示不可用而不是 0。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 对话内容由平台统一决定是否保存，站点和账户不能关闭 | 产品需求：记录要全面完整，用于追溯和将来的训练 |
| 任何人都不能通过产品查看对话内容，只经受控导出取用 | 产品需求：Axiom 是 API 调用平台，不提供查看对话的功能 |
| 正文保持原样，不改写、不脱敏 | 产品需求要求信息完整，后续处理由负责人自行完成 |
| 记录 IP、终端用户标识、同意的协议版本和模型许可 | 这些只能在写入时记下，事后补不回来；用于追溯、防滥用和训练的合规前提 |
| 同意版本取所有者在准入时已同意的最新版本，随准入行读出 | API 调用由 key 发起、协议由所有者同意；同一行读出不多一次往返，未同意的版本不能算同意 |
| 准入预占 + 本机 spill（组提交 fsync）+ 顺序批量入库，满了拒绝新调用；不把记录写进结算事务 | 记录在结尾前已持久，崩溃和断电都能重放，数据库慢不拖慢调用，磁盘和数量都有上限；写进结算事务会让日志的故障回滚整笔钱，也让 billing 写 observability 的表（比较过的做法见[存档](../archive/observability.md#写入路径比较过的做法)） |
| 数据本身被拒时不跳过坏行，标记不可记录并拒绝新调用 | 跳过一条坏行等于之后的调用无记录地服务；停写把故障变成可见的 503，记录留在 spill 等修复 |
| 待定记录先停放在本机，只有一条记录进库，入库前按账本补全 | 结尾前记录必须持久，而调用日志必须只插入，归档的行数核对和重放去重才成立；加锁读账本不依赖推算结算可能提交的时刻 |
| 进段文件的待定记录用新段头挡住旧版本 | 旧版本会把它存成价格为 0 的已结算调用；代价是有这种段时要先排空再回滚 |
| 每次尝试单独一行，与调用同一个请求 ID 和序号 | 追溯要直接列出每次尝试的端点、出口、时间和结果；只存路由 JSON 没有类型和耗时 |
| 调用、尝试和账本只用请求 ID 关联，不存账本 ID | 请求 ID 是账本自己的键，抄一份会旧会缺 |
| 调用记录按月归档到对象存储，确认后才删分区；热窗口是管理员数据 | 整月一次处理，没有确认的副本就不删，归档对象不删所以「全部保存」仍成立；按行 TTL 与分区不合 |
| 对象存储只经 S3 接口，`platform/objectstore` 一份实现，备份也走它，但备份桶与程序桶分开 | 云厂商和自托管 SeaweedFS 只换配置；备份凭证只进 ops 容器，程序被攻破也碰不到恢复一台机器所需的一切 |
| 去重用带账户密钥的指纹，按最后引用时间清理 | 无密钥的指纹会泄露内容是否存在；按时间整块清理会误删仍被引用的内容 |
| 内容写入经本地缓冲异步上传，绝不让请求失败 | 存储故障不能影响用户的调用 |
| 数据密钥分层、备份，销毁只由负责人执行 | 密钥丢失等于内容永久丢失；销毁不可逆，必须有人确认 |
| 正文导出由负责人离线双签名批准，并加密到负责人公钥 | 服务端不能凭管理员权限读正文；两把独立私钥保留两步验证，X25519 让导出文件在服务端只有密文；代价是负责人要自己备份私钥 |
| 内容表和响应缓存都只用平台范围 RLS，导出同时包含两者 | 产品接口即使漏条件也读不到正文；缓存可能含尚未入内容表的回复 |
| 分类只用自己部署或明确登记的模型 | 对话内容不能随意流向第三方 |
| 指标不按账户、key、用户区分 | 否则指标数量失控，拖垮监控系统 |
| 告警经有界缓冲 → 持久信号表 → River 消费 | 同步入库会让数据库故障拖慢调用，纯进程 channel 不能跨节点恢复；接受入缓冲到提交前的崩溃窗口 |
| 用数据库唯一约束与消费事务合并事件，不用进程内去重 | 两节点并发、重启和重试时仍只有一个事件 |
| Webhook 冻结正文、每次重签时间；在既有回执上实现 | 长退避后时间戳仍新鲜，重试正文不变；复用去重、规则与恢复，不引入第二套事件系统 |
| 花费异常的状态和阈值各用一张平台表 | 状态要跨节点、重启和告警配置替换保持只通知一次；阈值与规则 body 分开，旧节点整体替换规则时不丢 |
| 通知渠道做成插件 | 渠道各有限制（个人微信无官方接口，国内电话和短信要主体），插件化后逐个接入 |
| 终端用户哈希含账户、密钥按用途派生；同意协议不等于允许训练 | 两个账户的同名用户不该被关联；许可取决于协议正文和以后的训练规则 |
| 不可逆故障按来源身份认领；花费异常用 IP 网段近似地区 | 高水位会漏掉迟提交或回填的来源；GeoIP 是新的数据依赖，网段足以发现 key 被拿到别处 |
| 用量范围对齐 UTC 小时、空桶省略；缓存命中率只用有报告的物理输入与缓存读 | 小时汇总回答不了半小时，明确拒绝比隐式舍入更可核对；缺字段是未知，当作零会稀释比率 |
| 会话游标带签名；聚合金额用独立响应契约；控制台详情按白名单投影 | 篡改和换筛选续用要 400；两个 int64 的合计已超 19 位；白名单不会泄露供应商和出口 |
| 用户元数据导出与内容受控导出分开 | 复用账户 RLS 和 `calls.view`，不扩展正文访问权 |
| 聚合和导出在服务器上算，导出先探测再流式发 | 客户端一页代表不了全部，浮点累加丢精度；先拒绝超限而不用 trailer，下载方不需特殊处理就不会把半份当完整 |
| 用量页独立 `getUsageStatistics`，保留 `aggregateCalls` | 小时表回答不了明细筛选，两套存储和限制塞进一个操作会让语义难以判定；独立路径在旧节点上明确 404 |
| 插入事务里的触发器写 journal，增量累加小时表，旧行一次游标回填 | 按事件时间高水位会漏迟到记录；触发器让所有写入路径遵守同一规则，消费与累加原子提交 |
| 会话列表按有界明细归组，不建会话汇总 | 小时表没有会话维度，也回答不了任意窗口和筛选；固定输入预算在归组前拒绝大窗口，省掉汇总的写入、回填和一致性成本 |
| `HTTP-Referer` 只存 scheme、host 和 path | userinfo、查询串和片段常带令牌或密码，而调用记录会长期展示给工作区成员与站点管理员 |
| 后台摘要与详情用不同接口和权限，审计只读 | 独立的摘要类型避免前端隐藏字段泄漏成本；复用请求 ID 关联，不复制一份 trace 存储 |

## 待定问题

- 用户注销时对话内容如何处理：销毁该账户的数据密钥，还是按用户协议继续保留；以及调用记录里的 IP 和终端用户标识是否匿名化。待有公司主体、确定用户协议后决定。
- 存储容量与成本的估算，在打开对话内容保存之前完成，包括 Responses 会话状态的占用。
- 多桶与容量：归档现在只写一个桶；容量接近上限时告警、新加桶、按时间段分配和迁移旧数据都还没有实现。
- 归档的在线读取与恢复演练：现在只有对象和清单，追溯对已离开热窗口的月份返回空；届时用清单的列类型和摘要校验。
- 内容对象是否打包成较大的段、回收任务的批量与冷层迁移。
- 调用记录筛选索引在持续满批写入下的吞吐，随[性能](../performance.md#怎么验证)的压测一起量。
- 对话内容的全文检索，以后再做。

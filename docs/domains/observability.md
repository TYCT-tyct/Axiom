# 记录与告警

记录什么、怎么分类、存在哪、保留多久、怎么取用；以及监控、告警和通知渠道。对应代码模块 `observability`。数据留存的产品规则见[产品需求的「数据留存」](../product.md#数据留存)。

## 要求

- 记录要全面、完整、分类清楚、便于筛选，用于追溯，将来也可能用于训练模型。
- 对话内容完整保存，包括图片、文件等上传的内容；保存与否由平台统一决定，存储空间就绪前先关闭。
- Axiom 是 API 调用平台：任何人都不能通过产品查看对话内容。
- 告警不依赖运营 agent（见[运营](operations.md)）。

## 设计

### 记录的三类数据

| 类别 | 内容 |
|---|---|
| 调用记录 | 每次调用的元数据（见下文「写入时记全」） |
| 对话内容 | 请求和回复的完整正文 |
| 运行数据 | 指标、日志、链路追踪，不含正文和密钥，存放在运维节点上的监控系统 |

### 写入时记全

有些信息只有请求发生的那一刻才知道，必须当场记下：

| 类别 | 内容 |
|---|---|
| 谁 | 站点、账户、工作区、key、终端用户标识、IP |
| 用什么 | 客户端应用（从请求头识别 Claude Code、Codex 等）、会话和子 agent 编号、请求类别 |
| 走了哪 | 模型、端点和来源类别、出口、每次尝试、路由过程 |
| 结果 | 用量、售价和成本、延迟、结束原因、错误类型、是否免单（只由三条免单规则决定，没有上限可越） |
| 权利 | 用户当时同意的协议版本；产出内容的模型是否允许用于训练 |

- **终端用户标识**用带密钥的哈希保存，无法通过穷举还原。
- **每次尝试单独一行**：记端点、供应商、来源类别、出口、从 1 起的尝试序号、开始与结束时间、首字时间、结果和错误类型；调用的请求 ID 加尝试序号就是它的键，供应商的成本和对账键也按这一对键关联。路由过程留在调用的 `route` 里，不重复存尝试。
- **用户同意**：把对话用于训练，通常需要在用户协议中写明并取得同意。所以每条记录都记下用户当时同意的协议版本。用户协议这个功能还没有，在它存在之前每条记录的版本写 `none`（不写空值，库拒绝空值；也不编一个没人同意过的版本号），训练许可写不允许；协议有了之后，写入处改为取用户当时同意的版本，已写下的 `none` 补不回，也就不会被当作同意过。
- **客户端应用**在请求到达时从 `User-Agent` 识别：含 `claude-cli` 或 `Claude Code` 的记 `claude-code`，含 `codex` 的记 `codex`，其余为空；它补不回，所以只在写入时记。
- **模型许可**：部分模型厂商的条款限制用其输出训练与之竞争的模型，OpenRouter 为此提供了只路由到允许蒸馏的模型的参数（OpenRouter《Provider Routing》，2026-10）。所以每条记录都标明产出它的模型是否允许用于训练。

### 对话内容记录什么

- 客户端发来的完整请求：所有消息、系统提示、工具定义、参数，以及图片、PDF、音频、文件等多模态内容。
- 返回给客户端的完整回复：正文、推理内容、工具调用。
- 每次尝试与上游之间的原始交互，用于追溯格式转换和上游的问题。
- 正文保持原样，不改写、不脱敏。请求头和响应头只按白名单记录必要的几项；任何凭证（我们的 key、上游的 key、客户端的鉴权头、Cookie、登录令牌）一律不记录。

### 分类：两层标签

| 层 | 什么时候打 | 例子 |
|---|---|---|
| 写入标签 | 请求发生时，确定无疑 | 客户端应用、模型、来源类别、语言、是否用了工具、是否带图片或文件 |
| 分析标签 | 后台异步分析得出 | 任务类型（写代码、翻译、问答等）、领域、是否成功完成（有无重试、报错、中途取消）、质量信号、是否含个人信息或敏感内容 |

- 分析标签由一组可配置的分类器打：先用规则，复杂的再用模型批量处理，不进调用路径。
- 分类用的模型只能是自己部署的，或负责人在控制面里明确登记的；对话内容不能随意发给第三方。分类有预算上限，可以抽样。
- 分类器升级后，可以对历史数据重新打标签。对话内容保存关闭期间没有正文可分析，只有写入标签。

### 存储

| 层 | 存什么 | 存在哪 |
|---|---|---|
| 热 | 近期的调用记录和标签 | PostgreSQL，按时间分区；调用和它的每次尝试按同一组月份分区 |
| 温 | 较早的调用记录 | 对象存储里的列式文件 |
| 冷 | 对话内容、长期归档 | 对象存储的低价存储层 |
| 永久 | 账本、财务记录、汇总统计 | PostgreSQL |

- **存储桶是插件**：可以同时接多个存储桶（云厂商的对象存储或自建），按时间段分配；容量接近上限时告警，新加一个桶就能继续写，旧数据可以迁移。
- **去重**：编程工具每一轮都重发完整历史，所以对话按消息存储、每条只存一次，图片和文件按内容只存一份，调用记录里保存引用。
  - 去重只在同一账户内进行，去重用的指纹是带账户密钥的哈希，拿到存储桶文件列表的人也无法判断某段内容在不在；
  - 消息打包成较大的文件段存放，避免对象数量过多，也满足低价存储层的最小对象要求。
- **到期与清理**：
  - 调用记录按时间分区，整块转入下一层或删除，不逐行处理。sub2api 因为没有保留策略，日志涨到 100GB 以上（sub2api issue #7921，2026-10）；
  - 对话内容被多次调用引用，所以按"最后一次被引用的时间"判断是否到期：最后一个引用它的调用到期后，它才转冷或删除，由后台的整理任务定期回收。

### 写入路径

- **调用记录**异步批量写入，不在调用路径上。**队列满时丢弃新记录并计数，请求从不等待**：调用记录是观测数据，不能因为数据库慢而拖慢或失败调用；容量与节点的在途名额相当，只有写入持续跟不上到达时才会丢，丢失的条数进入指标和退出时的报告，可以据此告警。写失败退避重试，直到成功。进程崩溃丢的是最近一次成功写入之后的记录：数据库正常时约 1–2 秒，数据库故障时更多，这时结算也写不进，钱按[计费的「持有者与截止时间」](billing.md#持有者与截止时间)处理。记录还没写入时，按调用编号查询返回 404，不由账本补（见[接入与对外接口的「用量与费用」](gateway.md#用量与费用)）。
- **内容写入绝不让请求失败**：先写入本节点上有容量上限的磁盘缓冲，再异步上传到存储桶。
- **流式回复**：在结束或客户端取消时，把已产生的部分写入缓冲。
- **缓冲满或存储桶不可用**：告警并记录丢失的条数，请求照常完成。节点重启后，缓冲里尚未上传的内容继续上传。

### 加密与密钥

- **分层**：每个账户有自己的数据密钥，用来加密对话内容和 Responses 会话状态；数据密钥再由主密钥加密后保存，主密钥不在数据库里（见[安全的「安全基线」](../security.md#安全基线)）。
- **备份**：数据密钥随数据库一起备份，主密钥另有备份；丢失密钥等于永久丢失这个账户的全部内容。
- **销毁**：销毁一个账户的数据密钥，它的全部内容立即无法读取。这一操作不可逆，只作用于内容，不影响调用记录和账本；只有负责人经两步验证、二次确认后才能执行。

### 保留与开关

- **调用记录**：始终保存，不能关闭。明细在热层保留一段时间后转入温层，汇总统计长期保存；具体时长是后台配置。过载时队列满会丢弃新记录并计数（见「写入路径」），这是降级而不是开关，指标和退出报告都会给出丢失条数。
- **对话内容**：
  - 是否保存是平台级的开关，站点和账户都不能修改；
  - 存储空间就绪前先关闭；
  - 打开后默认保留 90 天，后台可调，也可以设为长期保存（到期转入冷层，不删除）。
- **账本和财务记录**不受保留设置影响，始终保留。
- **Responses 的会话状态**是续接功能所需的内部数据，单独保存，不受对话内容开关影响（见[接入与对外接口](gateway.md#responses-的会话状态)）。

### 谁能看

- **调用记录（不含内容）**：
  - 用户和企业账户管理员看自己账户的；
  - 站长看本站用户的；
  - 平台运维和运营 agent 都可以看。
- **对话内容和会话状态**：任何人都不能通过产品的任何界面或接口查看，包括用户本人、企业账户、站长、平台运维和运营 agent。
- **唯一的取用方式**：由负责人发起的受控导出（见下文）。

### 受控导出

- **发起**：只有负责人能发起，需要通过两步验证，每次都记入审计。导出任务在服务端解密，负责人和任何人都不直接接触密钥。
- **筛选**：可以按调用记录和标签的任意组合筛选，例如"最近三个月、Claude Code 发起、写代码类、成功完成、用户已同意、模型允许训练"。
- **内容**：导出的是原始数据，不改写、不脱敏，后续处理由负责人自行完成。
- **落点**：数据集写入负责人指定的加密存储位置，附带清单，列出每一条来源记录的引用，可以追溯。数据集的保管和清理由负责人负责；之后再销毁某个账户的密钥，不影响已经导出的数据集。

### 追溯

从任意一条调用记录都能串起：它的每次尝试（同一个请求 ID 和尝试序号，`call_attempt`）、路由过程（调用里的 `route`）、账本交易（同一个请求 ID，`billing.transactions.request_id`）、供应商的扣费记录（同一个请求 ID 和尝试序号），以及运营 agent 对它做过的操作。

### 监控与告警

- **指标与链路的约定**：命名、标签的基数上限、采样与导出配置见 [platform 的「遥测」](../../internal/platform/README.md#遥测)；各模块只按那里的规则加指标。
- **被丢弃的作业**：River 在任务用尽重试后把它标为 `discarded`，作业从此不再运行；最后一次尝试所在的节点消失时，River 的救援（JobRescuer）也会直接把它标为 `discarded`，不经过 worker 或错误回调。队列每分钟扫描一次持久化的 `river.river_job`（`state = 'discarded'`），为每个任务在 `platform.discarded_jobs` 记一行（主键是任务 ID），并按 `kind` 记 error 日志 `queue.job_discarded`（`job_id`、`kind`、`attempt`）和累加 `axiom.pg.queue.discarded_jobs`（Prometheus 里是 `axiom_pg_queue_discarded_jobs_total`）。认领行让同一任务在重启、另一个节点或再次扫描时不再上报；扫描事务若在上报后回滚，下一次会重复上报，所以指标计的是上报次数，告警按增量而不是总数。River 自己的清理不删除 `discarded` 任务（`DiscardedJobRetentionPeriod` 为 -1），所以未认领的旧任务不会先被删掉；扫描认领并上报后，只有任务终态已满 24 小时才删除任务和认领行，未满 24 小时的留到以后。节点只取自己有 worker 的任务种类（`FetchOnlyKnownKinds`），滚动发布期间旧节点不取新版本登记的种类，不消耗尝试次数，任务留给有该 worker 的节点。告警规则按 `kind` 收窄。被丢弃的邮件任务不删它的待发行，那一行留着供排查（[mail 的「队列与重试」](../../internal/platform/mail/README.md#队列与重试)）。
- **指标**：每个端点、供应商、节点、模型的请求量、错误率、延迟；收入、利润率、各供应商余额；底线指标的达成情况（见[总体架构的「底线指标」](../architecture.md#底线指标)）。指标只按这些维度区分，不按账户、key、用户区分，避免数量失控；按账户的统计从调用记录里算。按 key 的异常（如 key 盗用、泄露）也从调用记录算，不建按 key 的指标（见[安全的「防滥用」](../security.md#防滥用)）。
- **告警规则是后台数据**：阈值、持续时间、严重程度都可配置；另有自动的异常检测，例如某个端点的错误率突然升高。
- **在哪里判断**：当前 River 消费者在核心节点判断，独立于运营 agent；独立运维故障域随 M3 交付。最关键的几项健康检查同时在核心节点和外部在线监测服务上判断，运维节点故障时它们通过直通通道告警（见[运营的「通知」](operations.md#通知)）。
- **防告警风暴**：同类告警合并，一次故障只通知一次；可以设置静默时段。
- **分级通知**：一般信息进每日摘要；警告发即时消息；严重的发即时消息，规定时间内无人确认就打电话。严重告警同时唤醒运营 agent 排查。

### 告警信号、事件与规则（E5-3）

各模块只依赖 `platform/alert` 的 `Sink`：`Raise(kind, key, severity, fields)` 和 `Resolve(kind, key)`，返回是否进入有界本机缓冲。严重度为 `info`、`warning`、`critical`；字段只允许不含正文、凭证和个人信息的运维元数据。调用不等待数据库、不借用业务事务。缓冲满或输入越界返回错误并由调用方保留原有日志/指标。异步写入 `platform.alert_signals` 后才具有跨节点持久性；入缓冲到提交前崩溃仍可能丢失，不能把非阻塞返回当作持久确认。持久来源可以调用 `alert.Persist`，使用独立后台事务；废弃作业在扫描事务里直接持久记录，和认领一起提交。

River 的 `observability.alerts` 每分钟读取最多 1000 条信号。持久写入和读取用同一个事务 advisory lock 排序，消费与事件变更同事务提交；独立事务评估规则、派发通知并清理历史，不继续占用信号消费锁，重启可由其他节点继续。同一 `(kind, key)` 最多一个未恢复事件；反复 raise 更新次数和最后字段，不重复创建通知。恢复后再 raise 是新的事件。状态为 `firing → delivered → resolved`；送达前恢复可以直接变为 `resolved`，未曾安排首通知的短暂事件不发恢复通知。

规则是后台数据：种类、数值阈值（信号 `value` 字段，缺省 1）、持续秒数、最低严重度、渠道、UTC 静默起止分钟和重复间隔。静默支持跨午夜；两端相同表示关闭。默认重复间隔 0，表示每次故障每渠道只有一次首通知；非零允许定期提醒；前次送达从送达时间起算，前次失败从该回执的创建时间起算，pending/queued 期间不叠加任务。静默期间持久等待，恢复通知也遵守静默，并等待之前通知进入终态；首通知失败的事件只留 failed 恢复回执，不发没有首通知的恢复邮件。变更规则不撤回已经排入的通知。默认四条规则：`observability.write_lag`（待写数至少 4000（含正在重试的批次；节点容量 5000），持续 60 秒）、`billing.settlement_anomaly`、`queue.discarded`、`observability.records_lost`（后三者至少 1，立即）；默认无渠道，管理员绑定后才发送，不猜收件人。

写入器提供队列深度和丢失总数，每分钟后台采样，不在 `Enqueue` 里发送。写入积压未达到任何此类规则的阈值时只更新已有事件，不新建事件；连续两次空采样才恢复，正常关停排空后补发恢复信号。结算异常采样 `billing.UnknownItems`（结算见到未知计费项后持久保存的待处理状态），清除后恢复；结算的平台承担损失在提交后经同一非阻塞入口立即上报，每日自平从账本正向平台承担分录累计数修复丢失的即时信号；每日账本自平将差异数量与恢复信号同事务持久化；供应商对账将低估下架、高估、暂挂、超时未匹配和无效数据按分类计数同事务持久化，日志保留具体排查对象。平台承担损失和供应商对账分类是需人工调查的事件，管理员关闭，不把下一轮没有新增问题当作恢复；废弃作业按任务种类合并，持久记录后清理原行不会漏报。记录丢失只在计数增加时上报，是不可逆事件，按节点合并；废弃作业和记录丢失由管理员调查后关闭。正常关停在排空后恢复写入积压；崩溃、失联不能证明恢复，其遗留事件仍需管理员关闭。供应商持久事件 E5-2 经每分钟的 River 消费者转入同一信号入口；每个供应商按 `(version, seq)` 记录持久消费位置，位置和信号同事务提交，每页最多 1000 条，供应商分页继续任务；首次接入只报告当前未恢复状态，不回放已恢复历史。覆盖登录失效、同步需处理、任务停止、低余额；低余额由明确恢复事件恢复，登录和任务以失败事件的 LastOK 基线与更高同步版本验证新的成功观测后恢复，不比较数据库与节点墙钟，换凭证本身不算恢复。各供应商无可用来源时发 `suppliers.sources_unavailable`（每分钟最多 100 家，持久游标轮转），全平台无可用供应商来源时发 `suppliers.exhausted`，沿用已有可路由查询并检查凭证到期；无配置时不产生新告警，退役来源的旧故障需人工关闭。信号只含内部标识和分类，不带事件的上游文字；用户通知 E5-4 继续用租户邮件 outbox，不能把用户数据塞进平台运维事件。

信号种类与合并键供管理员配置规则（恢复判断见上面的来源约定）：

| 种类 | 合并键 | 恢复方式 |
|---|---|---|
| `billing.settlement_anomaly` | `unknown_items` / `platform_borne` | 缺项清除后自动恢复 / 损失人工调查关闭 |
| `billing.reconciliation_difference` | `ledger` | 下一次自平正常 |
| `suppliers.login_expired` / `suppliers.sync_attention` | 供应商 UUID | 验证新的成功观测 |
| `suppliers.task_stopped` | 供应商 UUID + `/任务名` | 该任务验证新的成功观测 |
| `suppliers.low_balance` | 供应商 UUID | 明确的余额恢复事件 |
| `suppliers.sources_unavailable` / `suppliers.exhausted` | 供应商 UUID / `all` | 可用来源重新出现 |
| `suppliers.reconciliation_difference` | `under_estimated` / `over_estimated` / `held` / `unmatched` / `invalid` | 人工调查关闭 |
| `alert.channel_unavailable` | 渠道 ID | 最新周期自测成功 |

首批渠道为邮件，经 `platform/mail` outbox 和 River `mail.send_tracked` 发送（旧节点不认识此种类，避免漏回执）；通知的持久回执区分 pending（等待派发）、queued（已在 outbox）、delivered、failed，delivered 表示 SMTP 接受，不表示收件人阅读。邮件发送后、回执提交前崩溃可能重发（至少一次）；故障合并保证只安排一次通知，不声称网络投递恰好一次。失败留在事件回执和 River，最多五次尝试。管理员可手动排测试消息，测试也留回执。Webhook（E5-5）使用 HTTPS POST JSON，经 platform egress 的地址策略、无重定向和每次 10 秒期限；只将 2xx 视为接收成功。JSON 在派发时冻结，包含通知 `id`、故障 `event_id`、通知 `sequence`（首通知 0，重复递增，恢复 -1）、告警 `kind/key/severity/fields` 和 `state`（firing/resolved/test），同一回执重试不改变正文；每次重签当前时间。`X-Axiom-Signature` 为 `t=<Unix秒>,v1=<HMAC-SHA256十六进制>`，签名输入是时间戳的 ASCII、一个点和原始 HTTP 正文。接收端应恒定时间比较签名、拒绝超出正负 5 分钟的时间戳，并按通知 ID 去重至少 24 小时；重复接收也返回 2xx。按 event_id 分开跟踪故障，resolved 对该故障是终态，迟到的首通知不能再开启它；不能用 kind/key 的旧恢复关闭之后的新故障。River 持久退避重试最多 5 次，任务参数只有回执 ID；接收后、回执落库前崩溃可重发，网络语义仍是至少一次。签名密钥由管理员单独写入，32–512 个 UTF-8 字节，按 secret 信封封存，配置、回执、审计和任务均不含密钥。密钥按渠道及目标地址绑定；轮换后一小时同时带新旧两个 v1，接收端可在窗口内只认识任意一个；为保证旧密钥的完整窗口，窗口内再次轮换返回修订冲突。初始化未绑定规则的渠道后先设置密钥，再绑定规则；未设置时留失败回执，不发无签名请求。滚动升级期间应在所有核心节点升级完成后才配置 Webhook，旧节点的邮件调度器不理解新渠道。

新增信封表受[平台信封清单检查](../../internal/platform/README.md#凭证加密)约束：迁移后，旧程序的启动和主密钥命令会因未知信封存储而拒绝继续。已有旧节点可继续运行，迁移后的重启必须使用识别该表的新版本；渠道只在全部节点升级后启用，回滚须保留新清单，不能用旧主密钥命令跳过该存储。

每个已配置渠道立即自测，之后每小时自测，复用同一发送和回执路径，不受静默时段影响；同一渠道的周期测试未终态时不叠加。每分钟消费者根据最新终态测试回执发布 `alert.channel_unavailable`，后续最新测试成功才恢复；旧探测的晚到结果不覆盖新探测；调度先于事件评估取得配置锁，最新回执的健康信号在独立消费阶段提交，发送回调不与信号消费反序加锁。该类事件不向故障渠道本身发送，仍须管理员配置其他渠道的规则；所有渠道故障时依靠后台回执和外部监测。

已恢复且所有首通知、重复与恢复通知均已终态的事件保留 30 天，每分钟最多清理 100 个，其回执和持续窗口一起删除。待恢复事件保留在部分索引里，历史量不影响每次最多 100 个事件的评估。

管理 API 提供单独的签名密钥设置/轮换、规则与渠道整体读取/替换、事件按 ID 分页读取（每页 100 条）、最近 100 条回执、测试发送、人工关闭事件。写操作沿用 MFA、平台范围的 `sites.manage` 权限、幂等键、修订号与审计；所有新增响应成员可选。邮件使用保留的全零站点 ID 作为 outbox 归属（不能对应真实站点），站点范围读不到，规则和事件仅平台范围可读写，不向账户查询开放。

### 通知渠道

- 渠道是插件：Telegram、飞书、企业微信、微信（经企业微信或第三方推送）、邮件、短信、电话；第一版尽量全部接入。
  - 个人微信没有官方的机器人接口，经由企业微信或第三方推送服务送达；
  - 电话和短信需要接入语音、短信服务商。
- 每个渠道都有发送回执和失败重试，并定期发送测试消息，确认渠道可用。
- 接收人由运营的控制面决定（见[运营的「控制面」](operations.md#控制面只有负责人能改的设置)）。

### 给用户看的

- 控制台里有调用记录（不含内容）、用量统计，可以导出。
- 调用记录查询接口（见[接入与对外接口](gateway.md#用量与费用)）。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 选择有界缓冲 → 持久信号表 → River 消费，而非同步入库或纯进程 channel | 同步入库能在返回时保证持久，但数据库故障会拖慢调用；纯 channel 不支持跨节点恢复。选择明确的提交边界和可重放持久来源，接受提交前崩溃窗口，开发者默认，不代表负责人表态 |
| 用数据库唯一约束与消费事务合并事件，不用进程内去重缓存 | 两节点并发、重启和任务重试仍维持一个事件；缓存无法保证 |
| 在既有回执上增加 Webhook、封存密钥表和探测位置；供应商用平台消费位置表 | 复用 #421 的去重、规则与恢复，不引入第二套事件系统。比较直接在同步提交中发信号与消费持久事件，选择后者以读取既有积压且不扩大同步租约事务；每个供应商一笔有界事务。比较冻结签名与每次重签，选择冻结正文、重签时间以覆盖长退避。新增表和管理操作依据负责人授权「遇到问题自己解决问题和判断最优而不是问我。」（[2026-10-28 授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)），独立评审仍执行 |
| OpenRouter 基线为异步目的地和加密凭证，运维通知另用故障事件协议 | [Broadcast](https://openrouter.ai/docs/guides/features/broadcast/overview)（2026-10-29 查证）描述调用链路导出，不能当作运维规则/恢复语义的依据；本次不发送调用正文 |
| 对话内容由平台统一决定是否保存，站点和账户不能关闭 | 负责人决定。记录要全面完整，用于追溯和将来的训练 |
| 任何人都不能通过产品查看对话内容 | 负责人决定。Axiom 是 API 调用平台，不提供查看对话的功能，内容只经受控导出取用 |
| 正文保持原样，不改写、不脱敏 | 负责人要求信息全面完整，后续处理由负责人自行完成 |
| 记录 IP 和终端用户标识 | 负责人要求记录全面；也用于防滥用和追溯。用户标识用带密钥的哈希 |
| 记录用户同意的协议版本和模型许可 | 负责人知悉训练用途有合规前提，要求功能完整；这两项只能在写入时记下，事后补不回来 |
| 去重用带账户密钥的指纹，按最后引用时间清理 | 无密钥的指纹会泄露"某段内容是否存在"；按时间整块清理会误删仍被引用的内容 |
| 内容写入经本地缓冲异步上传，绝不让请求失败 | 存储故障不能影响用户的调用 |
| 调用记录异步批量写，队列满了丢弃新记录并计数，不阻塞调用 | 调用记录始终保存的开关不在这里：过载时宁可少记也不能拖慢或失败调用；容量与在途名额相当，丢失有指标和退出报告，可以告警。否决背压到节点名额：数据库的慢会变成调用的慢；否决丢弃最旧的：会悄悄丢掉已经接受的记录 |
| 每次尝试单独一行，与调用同一个请求 ID 和序号 | 追溯要能直接列出每次尝试的端点、出口、时间和结果；供应商的成本按同一对键关联，不重复存。否决只在调用里存一段路由 JSON：没有类型和耗时，查询要解 JSON |
| 数据密钥分层、备份，销毁只由负责人执行 | 密钥丢失等于内容永久丢失；销毁不可逆，必须有人确认 |
| 分类只用自己部署或明确登记的模型 | 对话内容不能随意流向第三方 |
| 存储桶做成插件，分层存储 | 负责人计划以后再加存储空间、长期保存；分层能控制成本 |
| 调用记录的写入有界队列、批量、重试到成功，数据本身被拒的单条跳过并计数 | 数据库的短暂故障不丢记录，也不能因一条坏记录堵死写入；队列满时的丢弃见上一行。代码层面的做法见[模块 README](../../internal/observability/README.md) |
| 指标不按账户区分 | 按账户、key、用户区分会让指标数量失控，拖垮监控系统 |
| 通知渠道做成插件，尽量都支持 | 负责人要求；渠道各有限制（个人微信无官方接口，国内电话和短信需要主体），插件化后可以逐个接入 |
| 控制台的调用记录只有 `OwnCall` 的字段，列表和详情是同一种结构 | 尝试由 observability 存，用户可见的子集还没有模块能提供；先开放现有的，之后加字段向后兼容。契约先承诺了做不到的字段，处理器就得造假数据。否决的做法：现在就把尝试和路由放进详情：违背「用户看不到成本、端点和路由」的边界还没划清 |

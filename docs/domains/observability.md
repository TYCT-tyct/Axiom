# 记录与告警

记录什么、怎么分类、存在哪、保留多久、怎么取用；以及监控、告警和通知渠道。对应代码模块 `observability`。数据留存的产品规则见[产品需求的「数据留存」](../product.md#数据留存)。

## 要求

- 记录要全面、完整、分类清楚、便于筛选，用于追溯，将来也可能用于训练模型。
- 对话内容完整保存，包括图片、文件等上传的内容；保存与否由平台统一决定。
- Axiom 是 API 调用平台：任何人都不能通过产品查看对话内容。
- 告警不依赖运营 agent（见[运营](operations.md)）。

## 设计

### 记录的三类数据

| 类别 | 内容 | 存在哪 |
|---|---|---|
| 调用记录 | 每次调用的元数据（见下文「写入时记全」） | PostgreSQL，按时间分区 |
| 对话内容 | 请求和回复的完整正文 | 对象存储，压缩并加密 |
| 运行数据 | 指标、日志、链路追踪，不含正文和密钥 | 运维节点上的监控系统 |

### 写入时记全

有些信息只有请求发生的那一刻才知道，必须当场记下：

| 类别 | 内容 |
|---|---|
| 谁 | 站点、账户、工作区、key、终端用户标识（哈希后）、IP |
| 用什么 | 客户端应用（从请求头识别 Claude Code、Codex 等）、会话和子 agent 编号、请求类别 |
| 走了哪 | 模型、端点和来源类别、出口、每次尝试、路由过程 |
| 结果 | 用量、售价和成本、延迟、结束原因、错误类型、是否免单 |
| 权利 | 用户当时同意的协议版本；产出内容的模型是否允许用于训练 |

- **用户同意**：拿对话训练模型，需要用户协议写明并取得同意，海外的 GDPR、国内的《个人信息保护法》都有要求。所以每条记录都记下用户当时同意的协议版本。
- **模型许可**：Anthropic、OpenAI 等厂商的条款限制用其模型的输出训练与之竞争的模型；OpenRouter 为此提供了只路由到允许蒸馏的模型的参数（OpenRouter《Provider Routing》，2026-10）。所以每条记录都标明产出它的模型是否允许用于训练。

### 对话内容记录什么

- 客户端发来的完整请求：所有消息、系统提示、工具定义、参数，以及图片、PDF、音频、文件等多模态内容。
- 返回给客户端的完整回复：正文、推理内容、工具调用。
- 每次尝试与上游之间的原始交互，用于追溯格式转换和上游的问题。
- 记录保持原样，不改写、不脱敏。唯一的例外是任何凭证（我们的 key、上游的 key、客户端的鉴权头）一律不记录。

### 分类：两层标签

| 层 | 什么时候打 | 例子 |
|---|---|---|
| 写入标签 | 请求发生时，确定无疑 | 客户端应用、模型、来源类别、语言、是否用了工具、是否带图片或文件 |
| 分析标签 | 后台异步分析得出 | 任务类型（写代码、翻译、问答等）、领域、是否成功完成（有无重试、报错、中途取消）、质量信号、是否含个人信息或敏感内容 |

- 分析标签由一组可配置的分类器打：先用便宜的规则，复杂的再用小模型批量处理，不进调用路径。
- 分类器升级后，可以对历史数据重新打标签。

### 存储

| 层 | 存什么 | 存在哪 |
|---|---|---|
| 热 | 近期的调用记录和标签 | PostgreSQL，按时间分区 |
| 温 | 较早的调用记录 | 对象存储里的列式文件 |
| 冷 | 对话内容、长期归档 | 对象存储的低价存储层 |
| 永久 | 账本、财务记录、汇总统计 | PostgreSQL |

- **存储桶是插件**：可以同时接多个存储桶（云厂商的对象存储或自建），按时间段分配；容量接近上限时告警，新加一个桶就能继续写，旧数据可以迁移。
- **去重**：编程工具每一轮都重发完整历史，所以对话按消息存储、每条只存一次，图片和文件按内容只存一份；调用记录里保存引用。去重只在同一账户内进行。
- **加密**：每个账户用自己的数据密钥加密。需要彻底删除某个账户的全部内容时（例如法律要求的删除），销毁它的密钥即可，所有内容立即无法读取。
- **到期**：清理任务按分区整块转入下一层或删除，不逐行处理。sub2api 因为没有保留策略，日志涨到 100GB 以上（sub2api issue #7921，2026-10）。

### 保留与开关

- **调用记录**：始终保存，不能关闭。明细在热层保留一段时间后转入温层，汇总统计长期保存；具体时长是后台配置。
- **对话内容**：
  - 是否保存是平台级的开关，站点和账户都不能修改；
  - 打开后默认保留 90 天，后台可调，也可以设为长期保存（到期转入冷层，不删除）。
- **账本和财务记录**不受保留设置影响，始终保留。
- **Responses 的会话状态**是功能所需的数据，单独保存，不受对话内容开关影响（见[接入与对外接口](gateway.md#responses-的会话状态)）。

### 谁能看

- **调用记录（不含内容）**：
  - 用户和企业账户管理员看自己账户的；
  - 站长看本站用户的；
  - 平台运维和运营 agent 都可以看。
- **对话内容**：任何人都不能通过产品的任何界面或接口查看，包括用户本人、企业账户、站长、平台运维和运营 agent。
- **唯一的取用方式**：由负责人发起的受控导出（见下文）。

### 受控导出

- 只有负责人能发起，需要通过两步验证，每次都记入审计。
- 可以按调用记录和标签的任意组合筛选，例如"最近三个月、Claude Code 发起、写代码类、成功完成、用户已同意、模型允许训练"。
- 导出的是原始数据，不改写、不脱敏。后续处理由负责人自行完成。
- 生成的数据集可以追溯到每一条来源记录。

### 追溯

从任意一条调用记录都能串起：它的每次尝试、路由过程、账本交易、供应商的扣费记录，以及运营 agent 对它做过的操作。

### 监控与告警

- **指标**：每个端点、供应商、节点的请求量、错误率、延迟；收入、利润率、各供应商余额；底线指标的达成情况（见[总体架构的「底线指标」](../architecture.md#底线指标)）。
- **告警规则是后台数据**：阈值、持续时间、严重程度都可配置；另有自动的异常检测，例如某个端点的错误率突然升高。
- **防告警风暴**：同类告警合并，一次故障只通知一次；可以设置静默时段。
- **分级通知**：一般信息进每日摘要；警告发即时消息；严重的发即时消息，规定时间内无人确认就打电话。严重告警同时唤醒运营 agent 排查。
- **告警不依赖运营 agent**；运维节点自己出问题时另有直通负责人的通道（见[运营的「通知」](operations.md#通知)）。

### 通知渠道

- 渠道是插件：Telegram、飞书、企业微信、微信（经企业微信或第三方推送）、邮件、短信、电话。
- 每个渠道都有发送回执和失败重试，并定期发送测试消息，确认渠道可用。

### 给用户看的

- 控制台里有调用日志（不含内容）、用量统计，可以导出。
- 调用记录查询接口（见[接入与对外接口](gateway.md#用量与费用)）。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 对话内容由平台统一决定是否保存，站点和账户不能关闭 | 负责人决定。记录要全面完整，用于追溯和将来的训练 |
| 任何人都不能通过产品查看对话内容 | 负责人决定。Axiom 是 API 调用平台，不提供查看对话的功能，内容只经受控导出取用 |
| 记录保持原样，不改写、不脱敏 | 负责人要求信息全面完整，后续处理由负责人自行完成 |
| 记录用户同意的协议版本和模型许可 | 负责人知悉训练用途有合规前提，要求功能完整；这两项只能在写入时记下，事后补不回来 |
| 按消息去重、按账户加密 | 编程工具每轮重发完整历史，去重后存储量大幅下降；按账户加密让不同账户互不关联，也能在法律要求时彻底删除 |
| 存储桶做成插件，分层存储 | 负责人计划以后再加存储空间、长期保存；分层能控制成本 |
| 按分区整块清理和转存 | 逐行删除在数据量大时会拖垮数据库；sub2api 的教训 |
| Responses 会话状态不受对话内容开关影响 | 负责人授权开发者按用户体验判断。内容保存关闭期间，续接功能仍然可用 |

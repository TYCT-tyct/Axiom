# 记录与告警

记录什么、怎么分类、存在哪、保留多久、怎么取用；以及监控、告警和通知渠道。对应代码模块 `observability`。数据留存的产品规则见[产品需求的「数据留存」](../product.md#数据留存)。

## 要求

- 记录要全面、完整、分类清楚、便于筛选，用于追溯，将来也可能用于训练模型。
- 对话内容完整保存，包括图片、文件等上传的内容；保存与否由平台统一决定，存储空间就绪前先关闭。
- Axiom 是 API 调用平台：任何人都不能通过产品查看对话内容。
- 告警不依赖运营 agent（见[运营](operations.md)）。

## 设计

### 记录的三类数据

| 类别 | 内容 |
|---|---|
| 调用记录 | 每次调用的元数据（见下文「写入时记全」） |
| 对话内容 | 请求和回复的完整正文 |
| 运行数据 | 指标、日志、链路追踪，不含正文和密钥，存放在运维节点上的监控系统 |

### 写入时记全

有些信息只有请求发生的那一刻才知道，必须当场记下：

| 类别 | 内容 |
|---|---|
| 谁 | 站点、账户、工作区、key、终端用户标识、IP |
| 用什么 | 客户端应用（从请求头识别 Claude Code、Codex 等）、会话和子 agent 编号、请求类别 |
| 走了哪 | 模型、端点和来源类别、出口、每次尝试、路由过程 |
| 结果 | 用量、售价和成本、延迟、结束原因、错误类型、是否免单 |
| 权利 | 用户当时同意的协议版本；产出内容的模型是否允许用于训练 |

- **终端用户标识**用带密钥的哈希保存，无法通过穷举还原。
- **用户同意**：把对话用于训练，通常需要在用户协议中写明并取得同意。所以每条记录都记下用户当时同意的协议版本。
- **模型许可**：部分模型厂商的条款限制用其输出训练与之竞争的模型，OpenRouter 为此提供了只路由到允许蒸馏的模型的参数（OpenRouter《Provider Routing》，2026-10）。所以每条记录都标明产出它的模型是否允许用于训练。

### 对话内容记录什么

- 客户端发来的完整请求：所有消息、系统提示、工具定义、参数，以及图片、PDF、音频、文件等多模态内容。
- 返回给客户端的完整回复：正文、推理内容、工具调用。
- 每次尝试与上游之间的原始交互，用于追溯格式转换和上游的问题。
- 正文保持原样，不改写、不脱敏。请求头和响应头只按白名单记录必要的几项；任何凭证（我们的 key、上游的 key、客户端的鉴权头、Cookie、登录令牌）一律不记录。

### 分类：两层标签

| 层 | 什么时候打 | 例子 |
|---|---|---|
| 写入标签 | 请求发生时，确定无疑 | 客户端应用、模型、来源类别、语言、是否用了工具、是否带图片或文件 |
| 分析标签 | 后台异步分析得出 | 任务类型（写代码、翻译、问答等）、领域、是否成功完成（有无重试、报错、中途取消）、质量信号、是否含个人信息或敏感内容 |

- 分析标签由一组可配置的分类器打：先用规则，复杂的再用模型批量处理，不进调用路径。
- 分类用的模型只能是自己部署的，或负责人在控制面里明确登记的；对话内容不能随意发给第三方。分类有预算上限，可以抽样。
- 分类器升级后，可以对历史数据重新打标签。对话内容保存关闭期间没有正文可分析，只有写入标签。

### 存储

| 层 | 存什么 | 存在哪 |
|---|---|---|
| 热 | 近期的调用记录和标签 | PostgreSQL，按时间分区 |
| 温 | 较早的调用记录 | 对象存储里的列式文件 |
| 冷 | 对话内容、长期归档 | 对象存储的低价存储层 |
| 永久 | 账本、财务记录、汇总统计 | PostgreSQL |

- **存储桶是插件**：可以同时接多个存储桶（云厂商的对象存储或自建），按时间段分配；容量接近上限时告警，新加一个桶就能继续写，旧数据可以迁移。
- **去重**：编程工具每一轮都重发完整历史，所以对话按消息存储、每条只存一次，图片和文件按内容只存一份，调用记录里保存引用。
  - 去重只在同一账户内进行，去重用的指纹是带账户密钥的哈希，拿到存储桶文件列表的人也无法判断某段内容在不在；
  - 消息打包成较大的文件段存放，避免对象数量过多，也满足低价存储层的最小对象要求。
- **到期与清理**：
  - 调用记录按时间分区，整块转入下一层或删除，不逐行处理。sub2api 因为没有保留策略，日志涨到 100GB 以上（sub2api issue #7921，2026-10）；
  - 对话内容被多次调用引用，所以按"最后一次被引用的时间"判断是否到期：最后一个引用它的调用到期后，它才转冷或删除，由后台的整理任务定期回收。

### 写入路径

- **调用记录**异步批量写入，不在调用路径上。队列容量与节点的在途名额相当；满了时，请求在释放名额之前等待写入，背压到节点名额，不丢弃；写失败退避重试。进程崩溃丢的是最近一次成功写入之后的记录：数据库正常时约 1–2 秒，数据库故障时更多，这时结算也写不进，钱按[计费的「持有者与截止时间」](billing.md#持有者与截止时间)处理。记录还没写入时，按调用编号查询返回 404，不由账本补（见[接入与对外接口的「用量与费用」](gateway.md#用量与费用)）。
- **内容写入绝不让请求失败**：先写入本节点上有容量上限的磁盘缓冲，再异步上传到存储桶。
- **流式回复**：在结束或客户端取消时，把已产生的部分写入缓冲。
- **缓冲满或存储桶不可用**：告警并记录丢失的条数，请求照常完成。节点重启后，缓冲里尚未上传的内容继续上传。

### 加密与密钥

- **分层**：每个账户有自己的数据密钥，用来加密对话内容和 Responses 会话状态；数据密钥再由主密钥加密后保存，主密钥不在数据库里（见[安全的「安全基线」](../security.md#安全基线)）。
- **备份**：数据密钥随数据库一起备份，主密钥另有备份；丢失密钥等于永久丢失这个账户的全部内容。
- **销毁**：销毁一个账户的数据密钥，它的全部内容立即无法读取。这一操作不可逆，只作用于内容，不影响调用记录和账本；只有负责人经两步验证、二次确认后才能执行。

### 保留与开关

- **调用记录**：始终保存，不能关闭。明细在热层保留一段时间后转入温层，汇总统计长期保存；具体时长是后台配置。
- **对话内容**：
  - 是否保存是平台级的开关，站点和账户都不能修改；
  - 存储空间就绪前先关闭；
  - 打开后默认保留 90 天，后台可调，也可以设为长期保存（到期转入冷层，不删除）。
- **账本和财务记录**不受保留设置影响，始终保留。
- **Responses 的会话状态**是续接功能所需的内部数据，单独保存，不受对话内容开关影响（见[接入与对外接口](gateway.md#responses-的会话状态)）。

### 谁能看

- **调用记录（不含内容）**：
  - 用户和企业账户管理员看自己账户的；
  - 站长看本站用户的；
  - 平台运维和运营 agent 都可以看。
- **对话内容和会话状态**：任何人都不能通过产品的任何界面或接口查看，包括用户本人、企业账户、站长、平台运维和运营 agent。
- **唯一的取用方式**：由负责人发起的受控导出（见下文）。

### 受控导出

- **发起**：只有负责人能发起，需要通过两步验证，每次都记入审计。导出任务在服务端解密，负责人和任何人都不直接接触密钥。
- **筛选**：可以按调用记录和标签的任意组合筛选，例如"最近三个月、Claude Code 发起、写代码类、成功完成、用户已同意、模型允许训练"。
- **内容**：导出的是原始数据，不改写、不脱敏，后续处理由负责人自行完成。
- **落点**：数据集写入负责人指定的加密存储位置，附带清单，列出每一条来源记录的引用，可以追溯。数据集的保管和清理由负责人负责；之后再销毁某个账户的密钥，不影响已经导出的数据集。

### 追溯

从任意一条调用记录都能串起：它的每次尝试、路由过程、账本交易、供应商的扣费记录，以及运营 agent 对它做过的操作。

### 监控与告警

- **指标与链路的约定**：命名、标签的基数上限、采样与导出配置见 [platform 的「遥测」](../../internal/platform/README.md#遥测)；各模块只按那里的规则加指标。
- **被丢弃的作业**：River 在任务用尽重试后把它标为 `discarded`，作业从此不再运行；最后一次尝试所在的节点消失时，River 的救援（JobRescuer）也会直接把它标为 `discarded`，不经过 worker 或错误回调。队列每分钟扫描一次持久化的 `river.river_job`（`state = 'discarded'`），为每个任务在 `river.axiom_discarded_job` 记一行（主键是任务 ID），并按 `kind` 记 error 日志 `queue.job_discarded`（`job_id`、`kind`、`attempt`）和累加 `axiom.pg.queue.discarded_jobs`（Prometheus 里是 `axiom_pg_queue_discarded_jobs_total`）。认领行让同一任务在重启、另一个节点或再次扫描时不再上报；扫描事务若在上报后回滚，下一次会重复上报，所以指标计的是上报次数，告警按增量而不是总数。认领行保留 7 天，长于 River 对 `discarded` 任务的 24 小时保留；告警规则按 `kind` 收窄，校正是其中一种，排障步骤见 [billing 的「被丢弃的校正作业」](../../internal/billing/README.md#被丢弃的校正作业)。
- **指标**：每个端点、供应商、节点、模型的请求量、错误率、延迟；收入、利润率、各供应商余额；底线指标的达成情况（见[总体架构的「底线指标」](../architecture.md#底线指标)）。指标只按这些维度区分，不按账户、key、用户区分，避免数量失控；按账户的统计从调用记录里算。
- **告警规则是后台数据**：阈值、持续时间、严重程度都可配置；另有自动的异常检测，例如某个端点的错误率突然升高。
- **在哪里判断**：告警规则在运维节点上判断；最关键的几项健康检查同时在核心节点和外部在线监测服务上判断，运维节点故障时它们通过直通通道告警（见[运营的「通知」](operations.md#通知)）。
- **防告警风暴**：同类告警合并，一次故障只通知一次；可以设置静默时段。
- **分级通知**：一般信息进每日摘要；警告发即时消息；严重的发即时消息，规定时间内无人确认就打电话。严重告警同时唤醒运营 agent 排查。

### 通知渠道

- 渠道是插件：Telegram、飞书、企业微信、微信（经企业微信或第三方推送）、邮件、短信、电话。
- 每个渠道都有发送回执和失败重试，并定期发送测试消息，确认渠道可用。

### 给用户看的

- 控制台里有调用记录（不含内容）、用量统计，可以导出。
- 调用记录查询接口（见[接入与对外接口](gateway.md#用量与费用)）。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 对话内容由平台统一决定是否保存，站点和账户不能关闭 | 负责人决定。记录要全面完整，用于追溯和将来的训练 |
| 任何人都不能通过产品查看对话内容 | 负责人决定。Axiom 是 API 调用平台，不提供查看对话的功能，内容只经受控导出取用 |
| 正文保持原样，不改写、不脱敏 | 负责人要求信息全面完整，后续处理由负责人自行完成 |
| 记录 IP 和终端用户标识 | 负责人要求记录全面；也用于防滥用和追溯。用户标识用带密钥的哈希 |
| 记录用户同意的协议版本和模型许可 | 负责人知悉训练用途有合规前提，要求功能完整；这两项只能在写入时记下，事后补不回来 |
| 去重用带账户密钥的指纹，按最后引用时间清理 | 无密钥的指纹会泄露"某段内容是否存在"；按时间整块清理会误删仍被引用的内容 |
| 内容写入经本地缓冲异步上传，绝不让请求失败 | 存储故障不能影响用户的调用 |
| 调用记录异步批量写，队列满了背压到节点名额，不丢弃 | 调用记录始终保存，满了丢弃就违反这一点；写进结算事务会让每个请求的热事务多一次插入 |
| 数据密钥分层、备份，销毁只由负责人执行 | 密钥丢失等于内容永久丢失；销毁不可逆，必须有人确认 |
| 分类只用自己部署或明确登记的模型 | 对话内容不能随意流向第三方 |
| 存储桶做成插件，分层存储 | 负责人计划以后再加存储空间、长期保存；分层能控制成本 |
| 调用记录的写入有界队列、批量、重试到成功，数据本身被拒的单条跳过并计数 | 记录不能丢，也不能因一条坏记录堵死网关；代码层面的做法见[模块 README](../../internal/observability/README.md) |
| 指标不按账户区分 | 按账户、key、用户区分会让指标数量失控，拖垮监控系统 |
| 控制台的调用记录只有 `OwnCall` 的字段，列表和详情是同一种结构 | 尝试、路由和费用明细由 suppliers、billing 按同一个请求 ID 保存，用户可见的子集还没有模块能提供；先开放现有的，之后加字段向后兼容。契约先承诺了做不到的字段，处理器就得造假数据。否决的做法：现在就把尝试和路由放进详情：违背「用户看不到成本、端点和路由」的边界还没划清 |

## 待定问题

- 用户注销时对话内容如何处理：销毁该账户的数据密钥，还是按用户协议继续保留；以及调用记录里的 IP 和终端用户标识是否匿名化。待有公司主体、确定用户协议后决定
- 存储容量与成本的估算，在打开对话内容保存之前完成，包括 Responses 会话状态的占用
- 对话内容的全文检索，以后再做

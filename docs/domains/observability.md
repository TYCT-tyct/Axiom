# 记录与告警

记录什么、怎么分类、存在哪、保留多久、怎么取用；以及监控、告警和通知渠道。对应代码模块 `observability`。数据留存的产品规则见[产品需求的「数据留存」](../product.md#数据留存)。

## 要求

- 记录要全面、完整、分类清楚、便于筛选，用于追溯，将来也可能用于训练模型。
- 对话内容完整保存，包括图片、文件等上传的内容；保存与否由平台统一决定，存储空间就绪前先关闭。
- Axiom 是 API 调用平台：任何人都不能通过产品查看对话内容。
- 告警不依赖运营 agent（见[运营](operations.md)）。

## 设计

### 记录的三类数据

| 类别 | 内容 |
|---|---|
| 调用记录 | 每次调用的元数据（见下文「写入时记全」） |
| 对话内容 | 请求和回复的完整正文 |
| 运行数据 | 指标、日志、链路追踪，不含正文和密钥，存放在运维节点上的监控系统 |

### 写入时记全

有些信息只有请求发生的那一刻才知道，必须当场记下：

| 类别 | 内容 |
|---|---|
| 谁 | 站点、账户、工作区、key、终端用户标识、IP |
| 用什么 | 客户端应用（从 `User-Agent` 识别 Claude Code、Codex 等）、应用自己报的归因（`HTTP-Referer`、`X-OpenRouter-Title`、`X-OpenRouter-Categories`）、会话和子 agent 编号、请求类别 |
| 走了哪 | 模型、端点和来源类别、出口、每次尝试、路由过程 |
| 结果 | 用量（含原生 token 与写入时能确定的物理输入）、售价和成本、是否流式、延迟、结束原因、错误类型、是否免单（只由三条免单规则决定，没有上限可越） |
| 权利 | 用户当时同意的协议版本；产出内容的模型是否允许用于训练 |

- **终端用户标识**用带密钥的哈希保存，无法通过穷举还原。
- **每次尝试单独一行**：记端点、供应商、来源类别、出口、从 1 起的尝试序号、开始与结束时间、首字时间、结果和错误类型；调用的请求 ID 加尝试序号就是它的键，供应商的成本和对账键也按这一对键关联。路由过程留在调用的 `route` 里，不重复存尝试。
- **用户同意**：把对话用于训练，通常需要在用户协议中写明并取得同意。所以每条记录都记下用户当时同意的协议版本。用户协议这个功能还没有，在它存在之前每条记录的版本写 `none`（不写空值，库拒绝空值；也不编一个没人同意过的版本号），训练许可写不允许；协议有了之后，写入处改为取用户当时同意的版本，已写下的 `none` 补不回，也就不会被当作同意过。
- **客户端应用**在请求到达时从 `User-Agent` 识别：含 `claude-cli` 或 `Claude Code` 的记 `claude-code`，含 `codex` 的记 `codex`，其余为空；它补不回，所以只在写入时记。
- **应用归因**也在请求到达时记：应用自己的名字和类别由客户端在 `HTTP-Referer`、`X-OpenRouter-Title`（旧名 `X-Title` 也认）和 `X-OpenRouter-Categories` 里声明，与 OpenRouter 的[应用归因头](https://openrouter.ai/docs/app-attribution)同名（2026-10-29 核对）。这些头不转发给上游（见[接入与对外接口的「转发规则」](gateway.md#转发规则)）。值按列宽截断、去掉控制字符，`app_referer` 对绝对 URL 只留 scheme、host 和 path，不是绝对 URL 的值保留清洗后的文本；类别规范成最多两个小写连字符名字；空白或不合法的部分不记，记成空值。
- **模型许可**：部分模型厂商的条款限制用其输出训练与之竞争的模型，OpenRouter 为此提供了只路由到允许蒸馏的模型的参数（OpenRouter《Provider Routing》，2026-10）。所以每条记录都标明产出它的模型是否允许用于训练。

### 对话内容记录什么

- 客户端发来的完整请求：所有消息、系统提示、工具定义、参数，以及图片、PDF、音频、文件等多模态内容。
- 返回给客户端的完整回复：正文、推理内容、工具调用。
- 每次尝试与上游之间的原始交互，用于追溯格式转换和上游的问题。
- 正文保持原样，不改写、不脱敏。请求头和响应头只按白名单记录必要的几项；任何凭证（我们的 key、上游的 key、客户端的鉴权头、Cookie、登录令牌）一律不记录。

### 分类：两层标签

| 层 | 什么时候打 | 例子 |
|---|---|---|
| 写入标签 | 请求发生时，确定无疑 | 客户端应用、模型、来源类别、语言、是否用了工具、是否带图片或文件 |
| 分析标签 | 后台异步分析得出 | 任务类型（写代码、翻译、问答等）、领域、是否成功完成（有无重试、报错、中途取消）、质量信号、是否含个人信息或敏感内容 |

- 分析标签由一组可配置的分类器打：先用规则，复杂的再用模型批量处理，不进调用路径。
- 分类用的模型只能是自己部署的，或负责人在控制面里明确登记的；对话内容不能随意发给第三方。分类有预算上限，可以抽样。
- 分类器升级后，可以对历史数据重新打标签。对话内容保存关闭期间没有正文可分析，只有写入标签。

### 存储

| 层 | 存什么 | 存在哪 |
|---|---|---|
| 热 | 近期的调用记录和标签 | PostgreSQL，按时间分区；调用和它的每次尝试按同一组月份分区 |
| 温 | 较早的调用记录 | 对象存储里的 gzip CSV，带清单（列名、类型、行数、SHA-256） |
| 冷 | 对话内容、长期归档 | 对象存储的低价存储层 |
| 永久 | 账本、财务记录、汇总统计 | PostgreSQL |

- **存储桶是插件**：可以同时接多个存储桶（云厂商的对象存储或自建），按时间段分配；容量接近上限时告警，新加一个桶就能继续写，旧数据可以迁移。
- **去重**：编程工具每一轮都重发完整历史，所以对话按消息存储、每条只存一次，图片和文件按内容只存一份，调用记录里保存引用。
  - 去重只在同一账户内进行，去重用的指纹是带账户密钥的哈希，拿到存储桶文件列表的人也无法判断某段内容在不在；
  - 消息打包成较大的文件段存放，避免对象数量过多，也满足低价存储层的最小对象要求。
- **到期与清理**：
  - 调用记录按时间分区，整块转入下一层或删除，不逐行处理。整月早于热窗口（`hot_days`，默认 90 天，管理员数据）的 `call_log` 与 `call_attempt` 分区先导出到对象存储，清单确认两份对象都完整后才从 PostgreSQL 删除；删除事务对分区加排他锁并核对行数，快照后的迟到写入会让整月重写，绝不按旧清单删除；归档对象本身不删，所以「调用记录全部保存」仍成立。没有配置对象存储时一律留在 PostgreSQL：没有确认的副本就不删。sub2api 因为没有保留策略，日志涨到 100GB 以上（sub2api issue #7921，2026-10）；
  - 调用日志删掉整月后，PostgreSQL 是否还能完整回答按窗口判断：窗口覆盖的每个整月都还在才算完整，缺一个月就标为不完整。较老月份归档失败而较新月份已删时，最老分区还在但窗口仍会因空洞标为不完整。`available_since` 给出最老的剩余月分区，它之前确定已归档。看板和调用列表据此把触到已归档月份的窗口标为不完整，不把归档当成零（见[运营的「运营看板」](operations.md#运营看板)）；
  - 账本、汇总统计和审计各有自己的保留，不随调用记录删除；保留任务只拼自己两张表的分区名，从不碰 `billing`；
  - 对话内容被多次调用引用，所以按"最后一次被引用的时间"判断是否到期：最后一个引用它的调用到期后，它才转冷或删除，由后台的整理任务定期回收。

### 写入路径

- **调用记录**异步批量写入，不在调用路径上。**队列满时丢弃新记录并计数，请求从不等待**：调用记录是观测数据，不能因为数据库慢而拖慢或失败调用；容量与节点的在途名额相当，只有写入持续跟不上到达时才会丢，丢失的条数进入指标和退出时的报告，可以据此告警。写失败退避重试，直到成功。进程崩溃丢的是最近一次成功写入之后的记录：数据库正常时约 1–2 秒，数据库故障时更多，这时结算也写不进，钱按[计费的「持有者与截止时间」](billing.md#持有者与截止时间)处理。记录还没写入时，按调用编号查询返回 404，不由账本补（见[接入与对外接口的「用量与费用」](gateway.md#用量与费用)）。
- **内容写入绝不让请求失败**：先写入本节点上有容量上限的磁盘缓冲，再异步上传到存储桶。
- **流式回复**：在结束或客户端取消时，把已产生的部分写入缓冲。
- **缓冲满或存储桶不可用**：告警并记录丢失的条数，请求照常完成。节点重启后，缓冲里尚未上传的内容继续上传。

### 加密与密钥

- **分层**：每个账户有自己的数据密钥，用来加密对话内容和 Responses 会话状态；数据密钥再由主密钥加密后保存，主密钥不在数据库里（见[安全的「安全基线」](../security.md#安全基线)）。
- **备份**：数据密钥随数据库一起备份，主密钥另有备份；丢失密钥等于永久丢失这个账户的全部内容。
- **销毁**：销毁一个账户的数据密钥，它的全部内容立即无法读取。这一操作不可逆，只作用于内容，不影响调用记录和账本；只有负责人经两步验证、二次确认后才能执行。

### 保留与开关

- **调用记录**：始终保存，不能关闭。明细在热层保留一段时间后转入温层，汇总统计长期保存；具体时长是后台配置。过载时队列满会丢弃新记录并计数（见「写入路径」），这是降级而不是开关，指标和退出报告都会给出丢失条数。
- **对话内容**：
  - 是否保存是平台级的开关，站点和账户都不能修改；
  - 对象存储客户端已经就绪（[platform/objectstore](../../internal/platform/objectstore/README.md)），但保存正文的写入路径还没有接入，开关保持关闭；打开前要先有按账户加密、去重引用和到期回收；
  - 打开后默认保留 90 天，后台可调，也可以设为长期保存（到期转入冷层，不删除）。
- **账本和财务记录**不受保留设置影响，始终保留。
- **Responses 的会话状态**是续接功能所需的内部数据，单独保存，不受对话内容开关影响（见[接入与对外接口](gateway.md#responses-的会话状态)）。

### 谁能看

- **调用记录（不含内容）**：
  - 用户和企业账户管理员看自己账户的；
  - 站长看本站用户的；
  - 平台运维和运营 agent 都可以看。
- **对话内容和会话状态**：任何人都不能通过产品的任何界面或接口查看，包括用户本人、企业账户、站长、平台运维和运营 agent。
- **唯一的取用方式**：由负责人发起的受控导出（见下文）。

### 用户调用记录查询与导出

控制台 `calls.view` 只允许读本账户可见的元数据：时间、模型、客户端应用、key、工作区、成功/报错、请求 ID 可组合筛选；成功表示 `error_kind` 为空，报错表示非空，不根据 HTTP 状态或最后一次尝试推测。最近报错由服务端按报错筛选后取最新五条，不能先取一页普通调用再在浏览器筛选。列表可选 `status_filter` 回显已应用的状态筛选，旧节点缺失时最近报错显示不可用，不把普通调用当成报错。

`GET /api/console/v1/calls/aggregate` 按 UTC 日、模型或 key 汇总调用次数和用户实际收费，货币分别分组；这是调用记录的观测汇总，不是账本对账，异步未写入或丢弃的调用不在其中。金额和次数用十进制整数文本，金额单位为十亿分之一；合计可以超过 int64；聚合金额契约允许超过单笔金额的 19 位限制，不放宽其他读写接口的单笔金额约束。默认最近 30 天、最多 31 天，最多 1000 组，超出拒绝并要求缩小筛选，不能返回不完整的总计。

`GET /api/console/v1/calls/export` 导出相同筛选下的调用元数据，无正文、凭证、成本、端点和路由。账户范围与普通查询相同，不打开下述内容的受控导出权限。使用同一个只读快照，写 CSV 前先按相同筛选和索引顺序有界探测最多 10001 条匹配键；超过 10000 行答 400，要求缩小时间窗或筛选，不开始 CSV 下载。未超限时按索引顺序每批 200 条边读边发，返回游标之后的全部匹配行；默认最近 30 天，最多 31 天。CSV 金额用九位小数的精确货币文本，不经浮点数。每格首个非空白字符为 `= + - @` 时在原值前加单引号，CSV 引号另由标准编码器处理。不依赖 HTTP trailer 或下载客户端读取响应头来判断是否截断：成功响应始终完整，超限在写入前拒绝。普通响应头 `X-Export-Since` / `X-Export-Until` 给出实际采用的窗口（包括默认值）。中途失败终止流，不能在 CSV 后追加 JSON。请求及 socket 写入受 10 秒期限控制，断开取消快照。

### 受控导出

- **发起**：只有负责人能发起，需要通过两步验证，每次都记入审计。导出任务在服务端解密，负责人和任何人都不直接接触密钥。
- **筛选**：可以按调用记录和标签的任意组合筛选，例如"最近三个月、Claude Code 发起、写代码类、成功完成、用户已同意、模型允许训练"。
- **内容**：导出的是原始数据，不改写、不脱敏，后续处理由负责人自行完成。
- **落点**：数据集写入负责人指定的加密存储位置，附带清单，列出每一条来源记录的引用，可以追溯。数据集的保管和清理由负责人负责；之后再销毁某个账户的密钥，不影响已经导出的数据集。

### 追溯

从任意一条调用记录都能串起：它的每次尝试（同一个请求 ID 和尝试序号，`call_attempt`）、路由过程（调用里的 `route`）、账本交易（同一个请求 ID，`billing.transactions.request_id`）、供应商的扣费记录（同一个请求 ID 和尝试序号），以及运营 agent 对它做过的操作。

### 监控与告警

- **指标与链路的约定**：命名、标签的基数上限、采样与导出配置见 [platform 的「遥测」](../../internal/platform/README.md#遥测)；各模块只按那里的规则加指标。
- **被丢弃的作业**：River 在任务用尽重试后把它标为 `discarded`，作业从此不再运行；最后一次尝试所在的节点消失时，River 的救援（JobRescuer）也会直接把它标为 `discarded`，不经过 worker 或错误回调。队列每分钟扫描一次持久化的 `river.river_job`（`state = 'discarded'`），为每个任务在 `platform.discarded_jobs` 记一行（主键是任务 ID），并按 `kind` 记 error 日志 `queue.job_discarded`（`job_id`、`kind`、`attempt`）和累加 `axiom.pg.queue.discarded_jobs`（Prometheus 里是 `axiom_pg_queue_discarded_jobs_total`）。认领行让同一任务在重启、另一个节点或再次扫描时不再上报；扫描事务若在上报后回滚，下一次会重复上报，所以指标计的是上报次数，告警按增量而不是总数。River 自己的清理不删除 `discarded` 任务（`DiscardedJobRetentionPeriod` 为 -1），所以未认领的旧任务不会先被删掉；扫描认领并上报后，只有任务终态已满 24 小时才删除任务和认领行，未满 24 小时的留到以后。节点只取自己有 worker 的任务种类（`FetchOnlyKnownKinds`），滚动发布期间旧节点不取新版本登记的种类，不消耗尝试次数，任务留给有该 worker 的节点。告警规则按 `kind` 收窄。被丢弃的邮件任务不删它的待发行，那一行留着供排查（[mail 的「队列与重试」](../../internal/platform/mail/README.md#队列与重试)）。
- **指标**：每个端点、供应商、节点、模型的请求量、错误率、延迟；收入、利润率、各供应商余额；底线指标的达成情况（见[总体架构的「底线指标」](../architecture.md#底线指标)）。指标只按这些维度区分，不按账户、key、用户区分，避免数量失控；按账户的统计从调用记录里算。按 key 的异常（如 key 盗用、泄露）也从调用记录算，不建按 key 的指标（见[安全的「防滥用」](../security.md#防滥用)）。
- **告警规则是后台数据**：阈值、持续时间、严重程度都可配置；另有自动的异常检测，例如某个端点的错误率突然升高。
- **在哪里判断**：当前 River 消费者在核心节点判断，独立于运营 agent；独立运维故障域随 M3 交付。最关键的几项健康检查同时在核心节点和外部在线监测服务上判断，运维节点故障时它们通过直通通道告警（见[运营的「通知」](operations.md#通知)）。
- **防告警风暴**：同类告警合并，一次故障只通知一次；可以设置静默时段。
- **分级通知**：一般信息进每日摘要；警告发即时消息；严重的发即时消息，规定时间内无人确认就打电话。严重告警同时唤醒运营 agent 排查。

### 告警信号、事件与规则（E5-3）

各模块只依赖 `platform/alert` 的 `Sink`：`Raise(kind, key, severity, fields)` 和 `Resolve(kind, key)`，返回是否进入有界本机缓冲。严重度为 `info`、`warning`、`critical`；字段只允许不含正文、凭证和个人信息的运维元数据。调用不等待数据库、不借用业务事务。缓冲满或输入越界返回错误并由调用方保留原有日志/指标。异步写入 `platform.alert_signals` 后才具有跨节点持久性；入缓冲到提交前崩溃仍可能丢失，不能把非阻塞返回当作持久确认。持久来源可以调用 `alert.Persist`，使用独立后台事务；废弃作业在扫描事务里直接持久记录，和认领一起提交。

River 的 `observability.alerts` 每分钟读取最多 1000 条信号。持久写入和读取用同一个事务 advisory lock 排序，消费与事件变更同事务提交；独立事务完成常规规则评估、派发通知并清理历史，不继续占用信号消费锁（完整安全样本和支付窗口样本在消费时先评估，事件保留当前窗口值供规则判断，通知回执冻结创建时的展示字段；后续低值或恢复不会改写已排队的突发，也不会让历史峰值继续满足持续条件），重启可由其他节点继续。同一 `(kind, key)` 最多一个未恢复事件；反复 raise 更新次数和当前字段，不重复创建通知。恢复后再 raise 是新的事件。状态为 `firing → delivered → resolved`；送达前恢复可以直接变为 `resolved`，未曾安排首通知的短暂事件不发恢复通知。

规则是后台数据：种类、数值阈值（信号 `value` 字段，缺省 1）、持续秒数、最低严重度、渠道、UTC 静默起止分钟和重复间隔。静默支持跨午夜；两端相同表示关闭。默认重复间隔 0，表示每次故障每渠道只有一次首通知；非零允许定期提醒；前次送达从送达时间起算，前次失败从该回执的创建时间起算，pending/queued 期间不叠加任务。静默期间持久等待，恢复通知也遵守静默，并等待之前通知进入终态；首通知失败的事件只留 failed 恢复回执，不发没有首通知的恢复邮件。变更规则不撤回已经排入的通知。默认五条规则：`observability.write_lag`（待写数至少 4000（含正在重试的批次；节点容量 5000），持续 60 秒）、`billing.settlement_anomaly`、`queue.discarded`、`observability.records_lost`（后三者至少 1，立即）和 `observability.spend_anomaly`（至少 1，立即）；默认无渠道，管理员绑定后才发送，不猜收件人。支付补充的 `payments.discrepancy`、`payments.query_paused`、`payments.verify_failed`、`payments.query_failed`、`payments.rate_limited` 和 `payments.merchant_unreadable` 不在这五条中：管理员必须在告警配置中分别新增这些种类的规则（最低 warning、持续 0 秒、重复间隔 0），按能容忍的每分钟次数设阈值（例如验签 10、查询 5、限流 20；商户配置解不开通常设 1），绑定已验证的邮件渠道；保留当前其他规则与渠道并使用当前 rev 提交。仅给默认五条绑定渠道不会发送支付通知。验签失败、查询失败和限流拒绝在每个服务节点的 UTC 分钟窗口结束时发出该窗口的完整计数（从 1 起就发，`value` 是计数），规则阈值决定是否通知；商户配置解不开在每个商户第一次失败时发出，`value` 为 1，合并键带节点身份，见下表。没有支付规则/渠道时，差异行和信号转成的事件仍持久可查，通知尚未启用。

写入器提供队列深度和丢失总数，每分钟后台采样，不在 `Enqueue` 里发送。写入积压未达到任何此类规则的阈值时只更新已有事件，不新建事件；连续两次空采样才恢复，正常关停排空后补发恢复信号。结算异常采样 `billing.UnknownItems`（结算见到未知计费项后持久保存的待处理状态），清除后恢复；支付差异和日对账异常通过 `payments.discrepancy` 同业务事务持久化，商户查单暂停通过 `payments.query_paused` 持久化；验签失败、查询确认失败和限流拒绝在节点内按分钟窗口计数，每个完整窗口结束时经非阻塞入口发一次完整计数（1 次也发），消费时逐条评估，事件保留当前窗口值、回执冻结创建时的展示字段，后续低值重置持续条件且不改写已排队的突发；商户配置解不开按商户首次失败发一次；调查完成、成功恢复查单、上报后的下一个完整分钟没有同类事件或商户配置重新打开时清除对应信号。窗口计数每种信号每个键只占一个计数器，不为每个请求写数据库；合并键包含节点身份，一个节点的恢复不会替另一个节点恢复，遗留事件由管理员关闭。结算的平台承担损失在提交后经同一非阻塞入口立即上报，首次启用在接收调用前仅登记历史损失，不重放历史；每日自平按有正向平台承担分录的结算交易身份（请求、尝试序号及修订号）修复丢失的即时信号，即时写入与补报用同一持久来源身份，只在信号真正持久化时认领，已消费或人工关闭的同一损失不重开；每日账本自平将差异数量与恢复信号同事务持久化；供应商对账将低估下架、高估、暂挂、超时未匹配和无效数据按分类计数同事务持久化，日志保留具体排查对象。平台承担损失和供应商对账分类是需人工调查的事件，管理员关闭；未匹配尝试按请求和尝试序号持久认领，只对首次过宽限后见到的身份计数，迟到或回填完成时间的记录也不漏报，不把下一轮没有新增问题当作恢复；废弃作业按任务种类合并，持久记录后清理原行不会漏报。记录丢失只在计数增加时上报，是不可逆事件，按节点合并；废弃作业和记录丢失由管理员调查后关闭。正常关停在排空后恢复写入积压；崩溃、失联不能证明恢复，其遗留事件仍需管理员关闭。账户模块的 `accounts.authentication_failures` 以站点为键，每站点每分钟至多上报一次数据库共享的完整 UTC 分钟猜凭证失败峰值；配置相应规则（如每分钟 20 次、立即）与渠道后，只在阈值达到时创建事件。消费时逐条评估安全样本，避免同批后续低值/恢复覆盖已完成的突发；下一个完整低值或零窗口恢复，详见[账户模块](../../internal/accounts/README.md#注册登录与会话)。供应商持久事件 E5-2 经每分钟的 River 消费者转入同一信号入口；每个供应商按 `(version, seq)` 记录持久消费位置，位置和信号同事务提交，每页最多 1000 条，供应商分页继续任务；首次接入只报告当前未恢复状态，不回放已恢复历史。覆盖登录失效、同步需处理、任务停止、低余额；低余额由明确恢复事件恢复，号池容量由告警桥比较 `pool_low` 行恢复（分组离开回答而清空行也算），登录和任务以失败事件的 LastOK 基线与更高同步版本验证新的成功观测后恢复，不比较数据库与节点墙钟，换凭证本身不算恢复；登录失效与其他同步需处理分别保留恢复基线，原因改变不遗失此前故障。各供应商无可用来源时发 `suppliers.sources_unavailable`（每分钟最多 100 家，持久游标轮转），全平台无可用供应商来源时发 `suppliers.exhausted`，沿用已有可路由查询并检查凭证到期；无配置时不产生新告警，退役来源的旧故障需人工关闭。信号只含内部标识和分类，不带事件的上游文字；用户通知 E5-4 继续用租户邮件 outbox，不能把用户数据塞进平台运维事件。

账户暂停由 `accounts.SetAccountSuspended` 在同一事务持久化 `accounts.account_suspended`：暂停为 critical，解除时恢复，合并键是账户 TypeID；它没有预置规则，管理员需要新增规则并绑定渠道，解除时清除事件。

官方页面监测把审核项、健康状态与上述三类 catalog 信号同事务保存，不修改参考价；管理员须另配这三类规则和渠道，默认五条规则不会自动覆盖。取数周期和恢复条件见[目录模块](../../internal/catalog/README.md#参考价的录入)。

首批渠道为邮件，经 `platform/mail` outbox 和 River `mail.send_tracked` 发送（旧节点不认识此种类，避免漏回执）；通知的持久回执区分 pending（等待派发）、queued（已在 outbox）、delivered、failed，delivered 表示 SMTP 接受，不表示收件人阅读。邮件发送后、回执提交前崩溃可能重发（至少一次）；故障合并保证只安排一次通知，不声称网络投递恰好一次。失败留在事件回执和 River，最多五次尝试。管理员可手动排测试消息，测试也留回执。Webhook（E5-5）使用 HTTPS POST JSON，经 platform egress 的地址策略、无重定向和仅出站请求的 10 秒期限，回执落库沿用作业期限；只将 2xx 视为接收成功。JSON 在派发时冻结，包含通知 `id`、故障 `event_id`、通知 `sequence`（首通知 0，重复递增，恢复 -1）、告警 `kind/key/severity/fields` 和 `state`（firing/resolved/test），同一回执重试不改变正文；每次重签当前时间。`X-Axiom-Signature` 为 `t=<Unix秒>,v1=<HMAC-SHA256十六进制>`，签名输入是时间戳的 ASCII、一个点和原始 HTTP 正文。接收端应恒定时间比较签名、拒绝超出正负 5 分钟的时间戳，并按通知 ID 去重至少 24 小时；重复接收也返回 2xx。按 event_id 分开跟踪故障，resolved 对该故障是终态，迟到的首通知不能再开启它；不能用 kind/key 的旧恢复关闭之后的新故障。River 持久退避重试最多 5 次，目标非法或无签名密钥直接记失败，其他网络失败重试至第 5 次后记失败并正常完成；仅救援丢弃或未能持久回执等意外失败进入 `queue.discarded`。任务参数只有回执 ID；接收后、回执落库前崩溃可重发，网络语义仍是至少一次。签名密钥由管理员单独写入，32–512 个 UTF-8 字节，按 secret 信封封存，配置、回执、审计和任务均不含密钥。密钥按渠道及目标地址绑定；轮换后一小时同时带新旧两个 v1，接收端可在窗口内只认识任意一个；为保证旧密钥的完整窗口，窗口内再次轮换返回修订冲突；设置或轮换后令周期探测立即到期，在下一轮消费者中重试，已有在途探测不叠加。初始化未绑定规则的渠道后先设置密钥，再绑定规则；未设置时留失败回执，不发无签名请求。滚动升级期间应在所有核心节点升级完成后才配置 Webhook，旧节点的邮件调度器不理解新渠道。

新增信封表受[平台信封清单检查](../../internal/platform/README.md#凭证加密)约束：迁移后，旧程序的启动和主密钥命令会因未知信封存储而拒绝继续。已有旧节点可继续运行，迁移后的重启必须使用识别该表的新版本；渠道只在全部节点升级后启用，回滚须保留新清单，不能用旧主密钥命令跳过该存储。

每个已配置渠道立即自测，之后每小时自测，复用同一发送和回执路径，不受静默时段影响；同一渠道的周期测试未终态时不叠加。每分钟消费者根据最新终态测试回执发布 `alert.channel_unavailable`，后续最新测试成功或删除渠道时恢复；删除时在消费阶段发布恢复并删除探测位置；旧探测的晚到结果不覆盖新探测；调度先于事件评估取得配置锁，最新回执的健康信号在独立消费阶段提交，发送回调不与信号消费反序加锁。该类事件不向故障渠道本身发送，仍须管理员配置其他渠道的规则；所有渠道故障时依靠后台回执和外部监测。

已恢复且所有首通知、重复与恢复通知均已终态的事件保留 30 天，每分钟最多清理 100 个，其回执和持续窗口一起删除。待恢复事件保留在部分索引里，历史量不影响每次最多 100 个事件的评估。

管理 API 提供单独的签名密钥设置/轮换、规则与渠道整体读取/替换、事件按 ID 分页读取（每页 100 条）、最近 100 条回执、测试发送、人工关闭事件。写操作沿用 MFA、平台范围的 `sites.manage` 权限、幂等键、修订号与审计；所有新增响应成员可选。邮件使用保留的全零站点 ID 作为 outbox 归属（不能对应真实站点），站点范围读不到，规则和事件仅平台范围可读写，不向账户查询开放。

### 账户花费异常检测（E4-12）

账户金额、来源地区和模型组合的突变由 `observability.spend` 离线检测，每 10 分钟一次，不在调用路径上。每次以受控的当前时间取最近一小时，和账户自己在前 24 小时里的同一时长比较；没有跨账户的“全站基线”，因为不同客户的正常用量差几个数量级，拿别人的用量当基准会把大客户一直标成异常。最近窗口里有调用的账户才会被检查，账户没有基线调用时直接跳过，避免新客户的第一笔正常调用被判成异常。

- **花费暴涨**：最近窗口的花费同时达到绝对下限，且不低于基线每小时花费的倍数。下限挡住“基线几乎为零、多花一分钱就是无穷倍”的情况；倍数而不是固定金额，让大小客户用同一套规则。按币种分开判断，不同币种不相加。
- **陌生来源地区**：最近窗口出现基线里没有的网段，且该网段的调用达到次数下限。仓库没有 GeoIP 依赖，所以用调用记录里的 IP 网段近似地区：IPv4 取 /16，IPv6 取 /32，取网段时用 `network(set_masklen(...))` 清零主机位，同一网段内的地址换一个不会变成陌生地区，多个地址也会合并计数；审批和排查时按网段而不是国家。若要按国家/城市判断，替代方案是引入 GeoIP 数据库并定期更新，代价是新的数据依赖、许可和更新流程，本期不引入。
- **平时不用的模型**：最近窗口调用了基线里没有的模型，且达到次数下限。它和地区信号一起覆盖“key 被拿到别处、换成别的模型跑”的常见形态。

三种信号都发 `observability.spend_anomaly`，严重度 warning，键为 `<账户 UUID>/spend/<币种>`、`<账户 UUID>/region`、`<账户 UUID>/model`；字段里带账户、窗口秒数、基线秒数和证据（金额、次数、基线、比值、网段或模型，最多列 8 项并注明省略数量）。一个账户在一次检测里同时命中三种时，事件各自保留，用户只收到一封提醒；同一异常期间后来才出现的第二种信号也不再补发提醒，异常消失后才算结束。

检测状态在 `observability.spend_anomalies`：`(account_id, kind)` 一行表示正在发生。第一次命中时，同一事务插入状态行、持久化信号，并调用 accounts 的 `RecordSpendAnomalyNotices` 写用户提醒；重复运行看到行已存在就不再发信号或提醒，直到异常消失再删除行、发恢复信号。状态放在数据库而不是 `alert_windows`：替换告警规则会清空后者，检测状态必须跨节点、重启和配置变更保持“一次异常只通知一次”。事务提交前崩溃则整体回滚，下一轮重新检测；提交后、消费前崩溃由信号表接管。恢复也随状态删除提交，重复恢复不会产生第二个事件。

阈值是后台数据，存在 `observability.spend_detection`，由管理 API 的 `spend_detection` 对象整体读写；不设默认规则里的常量。默认开启、1 小时/24 小时、花费下限 5 额度（十亿分之一）、3 倍、陌生网段和模型各 5 次。允许的范围见契约（窗口 15 分钟到 1 天，基线不短于窗口且不超过 7 天，倍数 1–1000），保存时校验。窗口下限和调度间隔是配套的：任务每 10 分钟跑一次，短于最短窗口，两轮之间的突发至少落在后一轮的窗口里，不会卡在两个窗口中间；重叠也吸收迟到的运行。迁移追加默认规则时先看容量（最多 32 条）和 ID 是否被占用：满了就保留原配置不追加，ID 被占用就用下一个空闲的 `spend-anomaly-N`，不会把合法配置写成应用自己校验不过的状态；配置已满时管理员要自己加一条 kind 为 `observability.spend_anomaly` 的规则。检测对象和规则/渠道分开存：滚动发布中旧节点整体替换 `alert_configuration.body` 时不认识这个字段，分开存才不会被静默丢掉；管理 GET 合并返回，管理 PUT 省略该对象时保留原值。关闭检测会把仍在发生的状态全部恢复，避免留下无人处理的事件。

用户提醒走 accounts 现有的偏好、outbox 和可选 Webhook：`notification_preferences.spend_anomaly` 默认开启，关闭后不再写新的提醒；提醒的生产默认关闭（`spend_detection.notify_users`），等全部节点都认识 `spend_anomaly` 这个种类后再由管理员打开：旧节点的派发器会领取它不认识的种类并标记已发送却不发送，检测和告警渠道不受这个开关影响，打开后只对之后新发生的异常写提醒；一次异常只写一条（同一账户同一轮合并），邮件正文只有站点名称、异常种类标题、金额（地区或模型信号没有金额）和处置建议，Webhook 正文只有稳定 ID、种类、金额和时间，都不含调用内容、IP 原文或凭证。提醒里的“若不是你”指引停用不认识的 key 并联系站点运营；自动暂停 key 不在本期，理由见[安全的「决策与理由」](../security.md#决策与理由)。

检测失败只让本轮 River 任务重试，不影响调用、计费或用户请求；查询默认只读最近 25 小时（窗口加基线，后台可调至最多 8 天）的调用记录，按只给检测器用的 `(at, account_id)` 部分索引取最近账户集合，再按账户聚合，不扫全表。检测延迟最多一个 10 分钟周期；节点与数据库时钟偏差由部署的 NTP 约束，和既有周期告警相同。

### 通知渠道

- 渠道是插件：Telegram、飞书、企业微信、微信（经企业微信或第三方推送）、邮件、短信、电话；第一版尽量全部接入。
  - 个人微信没有官方的机器人接口，经由企业微信或第三方推送服务送达；
  - 电话和短信需要接入语音、短信服务商。
- 每个渠道都有发送回执和失败重试，并定期发送测试消息，确认渠道可用。
- 接收人由运营的控制面决定（见[运营的「控制面」](operations.md#控制面只有负责人能改的设置)）。

### 用户提醒与站内公告

E5-4 的余额不足、到账、认证因素变化属于 accounts 的用户偏好与模板，不使用平台运维规则和接收地址；经 SMTP outbox 和可选用户 HTTPS Webhook 异步投递。E5-6 公告是本站一般信息，后台发布/撤下、有效期与控制台入口见[账户领域的「用户提醒与站内公告」](accounts.md#用户提醒与站内公告)，不等于必须送达的模型迁移通知。

### 给用户看的

- 控制台里有调用记录（不含内容）、用量统计，可以导出。
- 调用记录查询接口（见[接入与对外接口](gateway.md#用量与费用)）。

## 后台检索

管理调用列表以请求 ID、账户、时间组合检索，默认最近 24 小时、最多 31 天，50 条一页、最多 200 条；按 `(at,id)` 倒序游标分页。客服持平台 `calls.search` 只读摘要（请求、账户、时间、模型、结果、延迟、用户收费），没有成本、端点、供应商、IP 或路由；`calls.inspect` 单独开放完整 trace 和按尝试序号排列的尝试。审计只读列表与详情需 `audit.view`，可按账户、站点、操作者、模块、动作、目标和请求 ID 精确过滤，同样有界时间窗和键集分页。没有清空接口。列表回传实际 since/until，后续页应原样使用以固定默认窗口；审计 detail 和 route 保留原始 JSON 数字，不经 float64。接口超时 10 秒，查询按实际参数规划并沿索引顺序读取。

管理后台的调用记录页只做客服层：按请求 ID、账户和时间筛选，列出摘要，不显示成本、端点或路由；持 `calls.inspect` 的会话才看到进入 trace 的链接，trace 页展示成本、路由的原始 JSON 和按尝试序号排列的尝试。审计页按上述字段精确筛选，详情把 `detail` 按原始 JSON 显示，并在同时持有 `calls.search` 时把请求 ID 链到调用列表；链接带上覆盖该条目的 31 天时间窗，不落回默认的 24 小时。两页都用返回的 `since`/`until` 翻下一页，默认窗口不会被后续页悄悄改变；权限不足按 403、已被清理的条目按 404、旧节点缺少的可选成员按“当前节点不可用”显示，不把缺失当成空值或 `false`。

OpenRouter 基线（2026-10-29）：[Support](https://openrouter.ai/support) 提供 Activity 用量查询和工单入口；Axiom 的客服摘要与运维详情是内部权限分层，不改变用户记录的访问边界。

## 决策与理由

用户调用 API 的分项售价由编排层在读取可见调用之后，按请求编号调用 billing 的账户范围批量读取；调用记录只保存已有价格版本，不复制发票或访问 billing 的表。冻结结算依据和金额由 billing 唯一持有，接口语义见[计费](billing.md#用户看得到什么)。

| 决策 | 理由 |
| 后台摘要与详情使用不同接口和权限；审计只读 | 序列化独立摘要类型，避免前端隐藏字段泄漏成本；复用现有请求 ID 关联，拒绝复制一份 trace 存储。沿时间/账户/请求及审计精确筛选的有序索引取页，避免 OFFSET 或先读全量排序。按 [负责人授权](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)「遇到问题自己解决问题和判断最优而不是问我。」落地，独立评审由流水线安排 |
|---|---|
| 用户元数据导出与内容受控导出分开 | #317 要求用户导出自己能读的调用记录；复用账户 RLS 和 `calls.view`，不扩展正文访问权。按 [负责人授权](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)「遇到问题自己解决问题和判断最优而不是问我。」落地接口与数据导出规则，仍需独立评审 |
| 查询时在服务器聚合；按页流式导出而非浏览器攒页 | 客户端一页无法代表全部调用，金额浮点累加会丢精度。数据库用 numeric 求和转文本；导出只保留一页内存，固定时间窗、行数、组数和请求期限限制资源。导出选择先探测并拒绝超限，不选 trailer 续传：[Fetch Response](https://fetch.spec.whatwg.org/#response-class) 不暴露 trailer，直接下载也不能要求用户读取头部（2026-10-29 查证），因此客户端无需特殊处理就不会误把半份数据当完整导出。不加汇总表或后台导出任务，避免本阶段不必要的写入和任务状态 |
| 复用筛选、独立有序索引，组合筛选保留剩余条件 | 模型/应用/新筛选共用 custom plan 查询，省去每种组合的 SQL 副本；key、工作区与成功/报错各有账户前缀的有序索引；状态用 `IS DISTINCT FROM` 保持真/假两侧都能匹配布尔索引，避免大量报错时寻找稀疏成功记录扫描整段历史。请求 ID 复用主键。不建组合的幂集索引，组合筛选可能检查所选索引中更多候选；列表事务用局部 `enable_sort=off` 防止相关筛选估计过低时退回位图排序，聚合不禁用排序。EXPLAIN 回归守住首页和深页的顺序及块预算 |
| 聚合金额使用独立响应契约 | 单笔 `Money` 限制 19 位，两个 int64 上限的合计已有 20 位；不放宽所有读写接口的金额约束，聚合的金额对象独立允许更长的整数文本，金额与货币仍作为整体返回。响应契约回归直接验证大合计的 JSON |
| UTC 日汇总、同币种相加、窗口与结果有界 | 对齐 [OpenRouter Activity](https://openrouter.ai/docs/guides/features/activity) 的按模型/key 分析与筛选后导出，及 [activity API](https://openrouter.ai/docs/api/api-reference/analytics/get-user-activity-grouped-by-endpoint) 的 UTC 时间口径（2026-10-29 查证）；Axiom 使用精确文本，不公开供应商成本，31 天适合原始明细查询。界面方案待定，本轮只接现有最近报错查询 |
| 选择有界缓冲 → 持久信号表 → River 消费，而非同步入库或纯进程 channel | 同步入库能在返回时保证持久，但数据库故障会拖慢调用；纯 channel 不支持跨节点恢复。选择明确的提交边界和可重放持久来源，接受提交前崩溃窗口，开发者默认，不代表负责人表态 |
| 用数据库唯一约束与消费事务合并事件，不用进程内去重缓存 | 两节点并发、重启和任务重试仍维持一个事件；缓存无法保证 |
| 在既有回执上增加 Webhook、封存密钥表和探测位置；供应商用平台消费位置表 | 复用 #421 的去重、规则与恢复，不引入第二套事件系统。比较直接在同步提交中发信号与消费持久事件，选择后者以读取既有积压且不扩大同步租约事务；每个供应商一笔有界事务。比较冻结签名与每次重签，选择冻结正文、重签时间以覆盖长退避。新增表和管理操作依据负责人授权「遇到问题自己解决问题和判断最优而不是问我。」（[2026-10-28 授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)），独立评审仍执行 |
| 不可逆故障另认领来源身份，不用完成时间高水位 | 活跃事件去重不能阻止人工关闭后被同一来源重开；完成时间高水位会漏掉迟提交或回填的尝试。复用平台位置表，以请求/尝试或结算交易的请求、尝试序号与修订号为身份，认领与信号同事务；即时损失只在异步写入器真正持久化后认领，与每日补报竞争同一身份。代价是每个已认领的不可逆来源（含历史基线）保留一条认领，随原财务事实保留；首次启用只种历史损失身份，正常调用不增加 SQL |
| OpenRouter 基线为异步目的地和加密凭证，运维通知另用故障事件协议 | [Broadcast](https://openrouter.ai/docs/guides/features/broadcast/overview)（2026-10-29 查证）描述调用链路导出，不能当作运维规则/恢复语义的依据；本次不发送调用正文 |
| 对话内容由平台统一决定是否保存，站点和账户不能关闭 | 负责人决定。记录要全面完整，用于追溯和将来的训练 |
| 任何人都不能通过产品查看对话内容 | 负责人决定。Axiom 是 API 调用平台，不提供查看对话的功能，内容只经受控导出取用 |
| 正文保持原样，不改写、不脱敏 | 负责人要求信息全面完整，后续处理由负责人自行完成 |
| 记录 IP 和终端用户标识 | 负责人要求记录全面；也用于防滥用和追溯。用户标识用带密钥的哈希 |
| 记录用户同意的协议版本和模型许可 | 负责人知悉训练用途有合规前提，要求功能完整；这两项只能在写入时记下，事后补不回来 |
| 去重用带账户密钥的指纹，按最后引用时间清理 | 无密钥的指纹会泄露"某段内容是否存在"；按时间整块清理会误删仍被引用的内容 |
| 内容写入经本地缓冲异步上传，绝不让请求失败 | 存储故障不能影响用户的调用 |
| 调用记录按月归档到对象存储，确认后才删 PostgreSQL 分区；热窗口是管理员数据 | 整月一次 `COPY`，不逐行；清单最后写、删除前按清单核对字节数，没有确认的副本就不删，桶不可用或窗口为 0 时全留。归档对象不设到期，所以「全部保存、不能关闭」仍在；账本、汇总、审计各按自己的规则保留。按[负责人授权](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)「遇到问题自己解决问题和判断最优而不是问我。」落地，独立评审仍执行。否决按行 TTL：与分区整块处理和索引不合；否决不归档直接删：无法恢复；否决把归档放进 billing：跨模块写彼此的存储 |
| 调用记录异步批量写，队列满了丢弃新记录并计数，不阻塞调用 | 调用记录始终保存的开关不在这里：过载时宁可少记也不能拖慢或失败调用；容量与在途名额相当，丢失有指标和退出报告，可以告警。否决背压到节点名额：数据库的慢会变成调用的慢；否决丢弃最旧的：会悄悄丢掉已经接受的记录 |
| 每次尝试单独一行，与调用同一个请求 ID 和序号 | 追溯要能直接列出每次尝试的端点、出口、时间和结果；供应商的成本按同一对键关联，不重复存。否决只在调用里存一段路由 JSON：没有类型和耗时，查询要解 JSON |
| 数据密钥分层、备份，销毁只由负责人执行 | 密钥丢失等于内容永久丢失；销毁不可逆，必须有人确认 |
| 分类只用自己部署或明确登记的模型 | 对话内容不能随意流向第三方 |
| 存储桶做成插件，分层存储 | 负责人计划以后再加存储空间、长期保存；分层能控制成本 |
| 调用记录的写入有界队列、批量、重试到成功，数据本身被拒的单条跳过并计数 | 数据库的短暂故障不丢记录，也不能因一条坏记录堵死写入；队列满时的丢弃见上一行。代码层面的做法见[模块 README](../../internal/observability/README.md) |
| 指标不按账户区分 | 按账户、key、用户区分会让指标数量失控，拖垮监控系统 |
| 通知渠道做成插件，尽量都支持 | 负责人要求；渠道各有限制（个人微信无官方接口，国内电话和短信需要主体），插件化后可以逐个接入 |
| 控制台的调用记录只有 `OwnCall` 的字段，列表和详情是同一种结构 | 尝试由 observability 存，用户可见的子集还没有模块能提供；先开放现有的，之后加字段向后兼容。契约先承诺了做不到的字段，处理器就得造假数据。否决的做法：现在就把尝试和路由放进详情：违背「用户看不到成本、端点和路由」的边界还没划清 |
| `HTTP-Referer` 只存应用 URL 的 scheme、host 和 path | 应用身份按站点识别，不需要查询串；userinfo、查询串和片段常带 OAuth code、access token 或密码，调用记录会通过控制台列表和详情长期展示给工作区成员与站点管理员，不能留下这些凭证。不是绝对 URL 的值按原文本清洗后保留，不能因此丢掉归因 |

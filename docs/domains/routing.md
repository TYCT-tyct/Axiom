# 路由

每个请求走哪个端点、经哪个出口，失败了怎么回退。对应代码模块 `routing`，调用路径上的接口见[模块 README](../../internal/routing/README.md)。端点属性和熔断见[端点评估](quality.md)，预留规则见[计费](billing.md#预留与结算)，凭证的选择和并发上限见[供应商](suppliers.md#凭证)。

## 要求

- 路由在核心内存中完成，只读路由快照（见[总体架构的「模块边界规则」](../architecture.md#模块边界规则)）。
- 能力不支持的端点直接排除（见[产品需求的「售卖形式」](../product.md#售卖形式)）。
- 排序策略和各种条件是后台数据，由预设选择。
- 默认策略是价格加权随机；跨模型回退默认关闭。

## 设计

### 路由快照从哪来

快照由核心节点从各模块已公开的数据组装，不在调用路径上查库（见[总体架构的「模块边界规则」](../architecture.md#模块边界规则)）：

- **哪些端点**：供应商模块给出已启用的、成本已知的、分组已选用、有可用凭证的端点，以及发给上游的模型名（`upstream_name`）、这个端点能用的调用格式、按分组倍率缩放好的成本计划、供应商是否流式和是否传递取消（`suppliers.Service.Routable()`，见[供应商的「调用面」](../../internal/suppliers/README.md#调用面)）。映射不到目录模型、模型不在上架状态、或没有成本计划的端点不在其中（见[供应商的「同步与变化」](suppliers.md#同步与变化)）。
- **模型规格**：目录给出上下文长度、输出上限、是否流式和能力位（`catalog.Model.Serving()`，见[模型目录的 README](../../internal/catalog/README.md)）。规格里没写全四项的模型不进快照：猜一个上限会让端点带着错的上限接流量。
- **售价**：每个模型按站点的定价规则对目录的参考价计算（`billing.SalePrices`），没有规则给出售价的模型不进快照（见[计费的「定价」](billing.md#定价)）；快照是一个节点一份，所以只有对所有人定价的规则算数，对某个账户或档位的规则不进快照；用量里出现过没人定价的字段的模型留在快照里并标记，路由以 `UnknownItem` 拒绝它（见[计费的「价目表缺项」](billing.md#价目表缺项)）。
- **其余**：熔断、健康度、质量和置信度、吞吐与延迟来自[端点评估](quality.md)；`internal/quality` 还没有，所以这几项在组装处取中性值 1，不偏向也不惩罚任何端点，等质量模块有了数据再换。供应商余额（恒视为够付，从不降权）、出口（恒为 1 个）、输出速度（未知，所以条目都不能分段预留）也都没有填（`gateway/route.go` 的 `endpointOf`）。

组装在节点里由 `gateway.RouteDeps` 完成（`internal/gateway/route.go`）：节点启动时读一次所有来源并发布第一份快照，之后每 5 秒重建一次并整体替换（供应商端点快照另有每 5 秒一次的 `Reload`，所以后台的改动到路由生效最长约 10 秒），路由拒绝比现有更旧的快照；某个来源读不出来，这一次不换，上一份留着，过了路由的最长陈旧时间就停止路由，而不是继续往可能已经变了的端点上发。每个端点一条，缺目录模型、规格或售价的模型的所有端点一起被排除，售价不全（没有给模型可能报告的某一项或某一服务等级定价，固定价不经上架门槛检查，所以要在这里查）的也一样；日志写明模型与原因，同一个原因在连续的重建里只记一次，原因变了或模型好了又坏了才再记，所以“为什么这个模型 404”总能从日志里查到，而日志不会每 5 秒一行。只有一个预设：ID 全零，允许所有来源类别和数据政策，最多 4 次尝试。供应商的来源类别当前一律按中转站、数据政策按可能用于训练取最坏情形，因为没有任何地方记录供应商怎么处理数据，要求不留存的预设不会因为一个没人填过的值而路由过去。

节点在快照里至少有一个端点、或者供应商一个端点都还没有（刚部署，供应商要通过管理端添加）时报告就绪；供应商给了端点而没有一个能进快照时不报告，因为每个调用都会 404，原因只在日志里。

### 一个请求的路由步骤

1. **认模型**：请求里的名字 → 标准模型（见[模型目录的「名字解析」](catalog.md#名字解析)）。请求带了备选模型列表时一并解析；key 的可用模型同样约束备选模型。
2. **取候选**：快照里服务这个模型的端点。只保留：
   - 这个账户看得到的：平台的、本站的、本账户自带的；
   - 已启用、没在熔断中；
   - 供应商余额够付这次请求的预估成本。余额低于告警线但还够付时，只降低权重。M1 尚未接入：组装处视余额为够付，也不降权。
3. **过滤**，都是硬条件：
   - 能力：请求用到的工具、图片、PDF、结构化输出、参数；预估输入加最大输出不超过上下文；
   - 格式：请求用到只有原格式才能表达的能力时（例如 Anthropic 的 beta 功能、推理签名），只保留原生支持这种格式的端点；M1 只把 Chat 请求转换给 Messages、Responses 端点，同格式 Chat 的改写还没有，所以 Chat 请求只落在原生支持这两种格式之一的端点上，Messages、Responses 请求只落在原生支持自己格式的端点上（见[接入的「转发规则」](gateway.md#转发规则)）；
   - 预设：来源类别、最低质量分和置信度、是否只走已验证的端点、数据政策；
   - 请求里的临时覆盖，规则见下文「请求覆盖」；
   - 出口：至少有一个能连通该端点的出口。供应商的地区限制会排除不符合的出口，比如官方 API 不接受来自香港的请求。
4. **排序**：见下文「排序的先后」。
5. **生成回退路线**：按顺序排出最多 3 个条目。每个条目带着自己的价格版本、输出上限和能否分段预留（见[计费的「一次预留足」](billing.md#预留与结算)），跨模型的条目也一样；同时设定最多尝试几次、准入后多久不再发起新的尝试。路线在预留之前定死，之后只会缩短，不会延长。
6. **预留**：每个条目自己报价，预留取保留条目的最大值；付不起的条目一遍删掉，首选条目被删才拒绝（见[计费的「预留与结算」](billing.md#预留与结算)）。计费只返回保留了哪些条目，由网关按它裁剪路线。

M1 只有 `direct` 一个出口，调用直接走它，不按下面的规则选。出口选择的设计：每个端点附带一份可用出口的排序（按实测的线路延迟和成功率，见[端点评估](quality.md)）。执行时：
- 供应商模块先挑凭证；
- 凭证绑定了固定出口的，就用那个出口；绑定的出口不可用时，换这个端点的另一个凭证；
- 没有绑定的，用排序第一的出口。
- 出口连不上只算出口的问题，不计入端点的熔断。

### 请求覆盖

请求可以用兼容 OpenRouter 的 `provider` 参数临时调整路由，规则与[配置链](accounts.md#配置链)一致：

- 过滤条件（只走、排除、来源、数据政策）只能比预设更严，不能放宽；
- 最高价只能比预设更低。最高价按计费项分别设定，比较的是这个账户实际要付的售价；
- 排序方式和指定顺序可以替换预设的；
- 指定顺序并关闭回退时（`allow_fallbacks: false`），只在指定的端点之间按顺序尝试；
- 性能条件（最低吞吐、最高延迟）是偏好，不满足的端点排到后面，不会被排除。这与 OpenRouter 一致。

### 排序的先后

1. 请求或预设明确指定的顺序；
2. 会话粘住的端点，只要它通过了全部过滤且健康；
3. 预设选定的排序策略：

| 策略 | 怎么排 | 对应 OpenRouter（《Provider Routing》，2026-10） |
|---|---|---|
| 均衡（默认） | 价格加权随机：越便宜被选中的概率越大，再乘上健康度和质量分的系数 | 默认的价格加权负载均衡 |
| 最便宜 | 按价格从低到高 | `sort: price`；`:floor` 第一版不支持（见[模型目录的「名字解析」](catalog.md#名字解析)） |
| 最快 | 按吞吐或首字延迟 | `sort: throughput` / `latency`；`:nitro` 第一版不支持 |
| 质量优先 | 按质量分和置信度 | — |

- **按请求类别选策略**：预设可以按 Claude Code 发来的请求类别（主对话、子 agent、工作流、压缩、辅助请求）选用不同的策略，例如辅助请求走便宜端点；默认不启用（见[接入与对外接口](gateway.md#转发规则)）。
- **工具调用请求**：在"均衡"和"质量优先"下，带工具调用的请求按端点在真实流量中的工具调用错误率重新排序（参考 OpenRouter《Auto Exacto》，2026-10）。"最便宜"和"最快"下不重排，因为重排会打乱粘性、降低缓存命中。

### 会话粘性

- **会话标识**按顺序取：请求里的 `session_id` 或 `prompt_cache_key`；Claude Code、Codex 各自携带的会话字段；都没有时，用"账户 + 模型 + 对话开头内容的哈希"推出。
- **怎么粘**：同一会话优先走上一次的端点。M1 里写回还没有接入：网关只读粘性表（`Router.Stuck`），成功后写（`Stick`）和收到标记后忘记（`Forget`）都没有调用方，所以粘性表是空的，粘性不生效（[Issue #26](https://github.com/TYCT-tyct/Axiom/issues/26)）。回退到别的端点成功后，会话改粘新的端点。收到 Claude Code 的"上下文已压缩"标记（`x-claude-code-context-compacted`）时，旧缓存已经作废，借此时机重新选择。
- **透传给上游**：透传的不是客户端原始的会话标识，而是用账户密钥派生出的不透明标识。这样不同租户都用 `default` 这类常见值时，不会在上游串到一起，也不泄露客户端的标识。sub2api 这类系统据此把同一会话固定在同一个账号上，缓存才能命中。
- **只在划算时粘**：只有缓存读取比普通输入便宜时才启用（与 OpenRouter 一致，见 OpenRouter《Prompt Caching》，2026-10）；端点不健康或已满载时不粘。
- **有效期**在后台配置。会话与端点的对应关系存在缓存里，丢失只会让下一次请求重新选择，不影响正确性。

### 失败怎么办

"已转发内容"指已经把第一段正文、推理内容或工具调用发给了客户端。在此之前，网关先暂存上游的开头事件，所以出错仍然可以换端点；在此之后出错，就只能在流里报错（见[总体架构的「一次调用怎么走」](../architecture.md#一次调用怎么走)）。

| 上游的情况 | 处理 |
|---|---|
| 限流（429）、过载（529）、5xx、超时（含 408）、连接失败 | 换下一个端点 |
| 上下文超长、请求过大（413）、参数不支持、模型不存在（404） | 换下一个端点；这些往往只是这一家的限制，同时报告给端点评估，用来学习真实上限 |
| 供应商的内容审核拒绝 | 换下一个端点；各家的审核尺度不同 |
| 供应商余额不足（402 或同义错误） | 换下一个端点；通知供应商模块立即同步余额并告警 |
| 鉴权失败（401、403） | 同一端点换另一把凭证，这把凭证歇着；组里没有可用凭证时换下一个端点；如果像是出口的问题（人机验证页、地区拦截），换出口再试；供应商模块按结果让这个凭证歇着（见[供应商的「凭证」](suppliers.md#凭证)） |
| 返回 200，但在任何正文之前就结束，或者输出为空 | 当作失败，换下一个端点 |
| 其他的请求格式错误（400） | 直接返回给客户端；换哪家结果都一样 |

- **单个请求**：尝试次数和总等待时间都有上限。
- **按供应商的重试预算**：某个供应商在一段时间内接收的重试请求，不能超过它正常流量的一定比例。用完后，重试不再发往这个供应商，但仍可发往其他供应商。这能防止上游一抖动就被重试流量压垮；sub2api 出现过空流反复重试造成的风暴（sub2api issue #7895，2026-10）。
- **跨模型回退**：默认关闭。只有请求给出了备选模型列表（OpenRouter 的 `models` 参数），或者预设开启了，才会换模型。

### 没有可用端点时

以下情况返回不同的错误，错误里写明被过滤的原因；状态码见[接入与对外接口的「错误」](gateway.md#错误)：
- 模型不存在（404）；
- 永久性的没有可用端点（404）：没有端点支持请求用到的能力、上下文长度或格式，端点都被预设或请求覆盖过滤掉了，或没有售价；
- 暂时性的没有可用端点（503）：全部熔断、供应商余额不足、重试预算用完；
- 所有尝试都失败（502）；
- 所有候选端点都已满载：先短暂排队等待，等待时间在后台配置，等不到就返回 429，并告诉客户端多久后重试。排队在准入事务之外：结束事务（还没有预留）再等，醒来后只重做准入和路由，不再访问缓存、不重复计限流；排队的请求不占数据库连接（见 [accounts 的「认出与准入」](../../internal/accounts/README.md#认出与准入)）。

### 容量感知

- 凭证的并发上限由供应商模块执行（见[供应商的「凭证」](suppliers.md#凭证)）。路由只看端点层面的负载。
- **端点负载、429 降权、凭证占位和重试预算在核心节点的进程内**：路由时不访问缓存；多个核心节点时（M2）在后台同步，硬上限不依赖共享的数字。
- **调用路径上同步访问缓存至多一次**，在准入之前，只取限流计数和会话粘性；M1 只有一个核心节点，这两样也在进程内。M2 放进缓存后超时 20ms，超时按缓存不可用处理：限流保守计数、不粘。限流计数是速率计数，不需要释放；粘性在调用结束后异步写回。
- 收到 429 时快速降低该端点的权重，恢复正常后逐步加回。

具体的上限、队列和同步方式见 [gateway 模块的「并发、背压与共享状态」](../../internal/gateway/README.md#并发背压与共享状态)。

### 路由记录

每次调用都记录路由过程：
- 哪些候选被过滤、原因是什么；
- 最终选了哪个端点和出口；
- 每次尝试的结果。

用户可以通过调用记录查询接口查看，运营 agent 排查问题时直接读这份记录。

### 耗时

路由的计算只读内存，耗时 p99 不超过 1 毫秒。会话粘性在准入事务之前取好（见上文「容量感知」）。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 默认策略是价格加权随机，而不是永远最便宜 | 负责人同意。全部流量压到最便宜的一家，它很快会被限流或耗尽余额；加权随机能分散负载，便宜的仍然拿大头。与 OpenRouter 的默认负载均衡一致（OpenRouter《Provider Routing》，2026-10） |
| 跨模型回退默认关闭 | 负责人同意。悄悄换模型会让用户拿到能力和价格都不同的结果；OpenRouter 也只在请求给出 `models` 时才跨模型回退 |
| 路线在预留前定死；预留时删掉付不起的条目 | 路线可以在预留之后变化的话，"预留有上限"就不成立；按最贵条目预留又不能误拒只够付首选端点的用户 |
| 端点负载和降权在进程内，缓存只在准入前访问一次 | 排队醒来时负载和名额都在进程内，再读缓存没有新信息；每多一次缓存往返，首字延迟就多一次网络往返 |
| 先挑凭证，再定出口 | 凭证可能绑定固定出口，出口必须服从凭证；出口故障不应该冤枉端点 |
| 请求覆盖只能收紧过滤条件 | 与配置链"下层只能在上层允许的范围内修改"一致；预设可能由账户管理员为成员的 key 设定，不能被单个请求绕过 |
| 排序先看指定顺序，再看粘性，最后看策略 | 否则随机选择和工具调用重排会让每次请求换一家，缓存永远不命中；OpenRouter 也指出它的工具调用重排会和粘性冲突（OpenRouter《Auto Exacto》，2026-10） |
| 透传给上游的会话标识由账户密钥派生 | 客户端常用相同的会话值，原样透传会让不同租户在上游串到一起，并泄露客户端的标识 |
| 上下文超长、内容审核等"像 400"的错误也换端点 | 这些往往只是某一家的限制，换一家可能就成功 |
| 凭证范围的失败（401、403）先换同一端点的另一把凭证 | 这类失败只说明这把凭证不行，不该丢掉还有可用凭证的端点；new-api 也是停用出错的渠道再重试另一个。凭证全部歇着后才换下一个端点 |
| 重试预算按供应商计算 | 全局只有一个预算的话，一家出故障就会拖累所有健康的供应商 |

## 待定问题

- 暂无

# 路由

每个请求走哪个端点、经哪个出口，失败了怎么回退。对应代码模块 `routing`。端点属性见[端点评估](quality.md)，冻结与回退的计费规则见[计费](billing.md#冻结与结算)。

## 要求

- 路由在核心内存中完成，只读路由快照（见[总体架构的「模块边界规则」](../architecture.md#模块边界规则)），耗时不超过 1 毫秒。
- 能力不支持的端点直接排除（见[产品需求的「售卖形式」](../product.md#售卖形式)）。
- 排序策略和各种条件是后台数据，由预设选择。
- 默认策略是价格加权随机；跨模型回退默认关闭。

## 设计

### 一个请求的路由步骤

1. **认模型**：请求里的名字 → 标准模型（见[模型目录的「名字映射」](catalog.md#名字映射)）；如果请求带了备选模型列表，一并解析。
2. **取候选**：快照里服务这个模型的端点。只保留：
   - 这个账户看得到的：平台的、本站的、本账户自带的；
   - 已启用、没在熔断中；
   - 供应商余额充足。
3. **过滤**，都是硬条件：
   - 能力：请求用到的工具、图片、PDF、结构化输出、参数；预估输入加最大输出不超过上下文；
   - 预设：来源类别、最低质量分和置信度、是否只走已验证的端点、数据政策；
   - 请求里的临时覆盖（兼容 OpenRouter 的 `provider` 参数）：只走、排除、指定顺序、最高价、数据政策；
   - key 的可用模型。
4. **排序**：按预设选定的策略打分（见下文「排序策略」）。
5. **选出口**：每个端点在能连通它的出口里，按实测的延迟和成功率挑选；凭证绑定了固定出口的，用绑定的出口。
6. **生成回退路线**：按顺序排出若干个"端点 + 出口"组合，并设定最多尝试几次、总共等多久。

冻结金额按这条回退路线里最贵的端点计算；回退时不会走到比冻结价更贵的端点（见计费）。

### 排序策略

策略是后台数据，每个预设选一种：

| 策略 | 怎么排 | 对应 OpenRouter |
|---|---|---|
| 均衡（默认） | 价格加权随机：越便宜被选中的概率越大，再乘上健康度和质量分的系数 | 默认的价格加权负载均衡 |
| 最便宜 | 按价格从低到高 | `sort: price`、`:floor` |
| 最快 | 按吞吐或首字延迟 | `sort: throughput` / `latency`、`:nitro` |
| 质量优先 | 按质量分和置信度 | — |

- **工具调用请求**：带工具调用的请求，按端点在真实流量中的工具调用错误率重新排序（参考 OpenRouter 的 Auto Exacto）。预设可以关闭这一步，例如更看重缓存命中的场景。
- **性能条件**：请求可以要求最低吞吐、最高延迟（按百分位），对应 OpenRouter 的 `preferred_min_throughput`、`preferred_max_latency`。

### 会话粘性

- **会话标识的来源**，按顺序取：
  - 请求里的 `session_id` 或 `prompt_cache_key`；
  - Claude Code、Codex 各自携带的会话字段；
  - 都没有时，用"账户 + 对话开头内容的哈希"推出。
- **怎么粘**：同一会话尽量走上一次的端点，并把会话标识透传给上游，让 sub2api 这类系统也把同一会话固定在同一个账号上，缓存才能命中。
- **只在划算时粘**：只有缓存读取比普通输入便宜时才启用；端点不健康时立即解除。
- **有效期**在后台配置。会话与端点的对应关系存在缓存里，丢失只会让下一次请求重新选择，不影响正确性。

### 回退与重试

- **换下一个端点**：限流（429）、上游 5xx、超时、连接失败，并且还没有向客户端转发任何内容。
- **不换，直接返回**：请求本身有问题（400）。换哪家结果都一样。
- **凭证失效**（401、403）：换下一个端点，同时熔断这个凭证并告警。
- **重试预算**：
  - 单个请求的尝试次数和总等待时间都有上限；
  - 全局还有一个重试比例的上限，防止上游一抖动就被重试流量压垮。sub2api 出现过空流反复重试造成的风暴（sub2api issue #7895，2026-10）。
- **跨模型回退**：默认关闭。只有请求里明确给出了备选模型列表（OpenRouter 的 `models` 参数），或者预设开启了，才会换模型。

### 容量感知

- 每个凭证、每个端点记录进行中的请求数，不超过已知的并发上限。并发计数跨核心节点共享，存在缓存里。
- 收到 429 时快速降低该端点的权重，恢复正常后逐步加回。

### 路由记录

每次调用都记录路由过程：
- 哪些候选被过滤掉、原因是什么；
- 最终选了哪个端点和出口；
- 每次尝试的结果。

用户可以通过调用记录查询接口查看，运营 agent 排查问题时直接读这份记录。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 默认策略是价格加权随机，而不是永远最便宜 | 负责人同意。全部流量压到最便宜的一家，它很快会被限流或耗尽余额；加权随机能分散负载，便宜的仍然拿大头。与 OpenRouter 的默认负载均衡一致（OpenRouter《Provider Routing》，2026-10） |
| 跨模型回退默认关闭 | 负责人同意。悄悄换模型会让用户拿到能力和价格都不同的结果；OpenRouter 也只在请求给出 `models` 时才跨模型回退 |
| 策略、条件都是后台数据 | 新的路由偏好不需要改代码 |
| 粘性只在缓存读取更便宜时启用 | 不划算时粘性只会降低负载均衡的效果；与 OpenRouter 的规则一致（OpenRouter《Prompt Caching》，2026-10） |
| 400 不重试，401、403 换端点并熔断凭证 | 请求错误换哪家都一样；凭证失效是这个凭证的问题，不该拖累整个请求 |
| 重试有单请求和全局两层预算 | 防止上游故障时重试流量放大故障 |
| 每次调用记录路由过程 | 用户和运营 agent 都能看到为什么走了这条路，排查问题不靠猜 |

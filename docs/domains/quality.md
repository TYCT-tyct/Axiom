# 端点评估

一个端点到底能做什么、是不是真的、好不好、稳不稳，全部靠测量得出。对应代码模块 `quality`。端点属性的种类和获取原则见[产品需求的「端点属性」](../product.md#端点属性)，这里写怎么测、怎么合并。

## 要求

- 评估尽可能全面、自动；人只处理机器判断不了的情况。
- 端点属性靠实测，不靠自报。
- 可以借助外部评测网站的结果。
- 端点坏了自动摘除、有限地试探、好了自动恢复；重新检测仍异常则下线并告警；人停用的端点永远不被自动恢复。

## 设计

### 依据与合并

"依据"指一个属性值是从哪里得来的。

- **六种依据**：目录基线、供应商自报、主动检测、线上观测、外部评测、人工或运营 agent 覆盖。
- **依据的有效性分别处理**：运营测量、真伪与产品成绩有各自的置信度和有效期；结构事实不按时间过期，来源类别随配置和证据重判。目录在同步后更新，供应商自报、外部评测与人工覆盖尚无统一合并器。

- **合并要求**（尚无通用执行器，已实现分支以下文规则为准）：
  - 能力和真伪类：任何一个可信的失败证据都会降低置信度；但要多次独立确认，才判定为"不支持"或"假冒"，一次失败不下结论；
  - 速度和稳定类：以线上观测为准；
  - 人工覆盖必须写理由，与实测冲突时告警。
- **使用**：路由预设按属性和置信度筛选端点；`min_score` 用的是产品成绩（0–100），不是运营质量分（0–1），见[路由](routing.md#路由预设)。

### 主动检测

当前主动请求包括恢复试探和随机真伪挑战，固定题库提供评分与记录入口。下表是检测要求的覆盖面；通用后台题库、官方参考响应采集和结构事实检测器尚未实现，不表示这些项目已经自动运行。

| 类别 | 检测什么 | 示例方法 |
|---|---|---|
| 能力 | 工具、图片、PDF、推理、缓存、结构化输出、参数 | 发出需要该能力的请求，检查响应 |
| 上下文与输出 | 真实的上下文上限、最大输出 | 大海捞针；要求长输出，看是否被截断 |
| 真伪 | 是不是声称的那个模型（型号、变体与版本） | 随机挑战里自报精确型号并与目录声明的模型身份规范化比对（同厂商更小的变体是矛盾）；固定文本的 token 数与官方计数对比；Claude 推理块的签名（由 Anthropic 服务端生成，中转站无法伪造）；知识截止时间；已知答案的行为题 |
| 来源 | 上游来自哪里 | 指纹：响应头、消息 ID 格式、用量字段特征 |
| 注入与虚报 | 是否被塞了系统提示、是否虚报用量 | 输入 token 数与应有的对比；诱导复述隐藏指令 |
| 篡改 | 是否改动了模型的输出 | 让模型原样返回指定内容，例如工具调用、网址、代码片段，再逐字比对 |
| 协议与计费合规 | 响应字段、流式事件顺序、用量字段是否符合官方规范 | 与官方基线响应逐字段比对 |
| 质量 | 实际水平 | 一小套固定题，与官方基线的成绩对比 |

- **重点防篡改**：编程工具会执行模型给出的命令和代码。中转站篡改输出，就等于在用户机器上执行别人的代码，所以篡改检测是必测项。
- **官方参考**：当前固定题评分保存官方题分；用于真伪与合规的逐版本参考响应采集尚未实现。

### 检测要像真实流量

恢复试探和真伪检测走生产出口、生产凭证与同一调用面，题目参数和发送时刻随机化；固定题库不通过接口暴露。线上工具参数检查不另发请求。抽样签名、token 偏差、消息 ID、用量合规校验及检测与真实流量长期不一致告警尚未实现。

### 真伪检测

`Verified` 表示随机挑战最近通过、仍在有效期内且此后没有矛盾；调用路径只读快照。它核对目录声明的型号、变体和作者，不证明权重与官方一致。

- **挑战题**：一次真实生成，要求按一个 JSON 模板回答，所有值在一次生成里给出：
  1. 原样回显一个随机的十六进制串；
  2. 两个随机小整数之和；
  3. 一个随机四位数与三位数的积；
  4. 一个随机 6–9 位字母数字串的倒序；
  5. 该串的字符数；
  6. 它正在服务的**精确模型名和版本**；
  7. 创造它的公司。

  模板不告诉它声称的型号（否则它只要抄），题面和答案也不落库。回显、求和、乘积和倒序证明对面在生成且没有被改写；字符数测指令跟随；型号与**目录模型的身份**比对（`Claimed.Model` 是目录 slug，`Claimed.Name` 是目录声明的厂商原生有效名，都取自目录快照；不是可能被供应商别名映射的上游名字），公司名与目录里作者的显示名比对（简称也算，`Mistral` 对 `Mistral AI`）。例如上游名字是 `gpt-4`、目录映射到 `gpt-4o` 时，真实 `GPT-4o` 的回答通过；拿上游名字去比会把正常端点判成不确定。随机串、数字、乘数、字符串和长度每次都不同；检测走生产出口和生产凭证，与真实请求同一条调用面（上文「检测要像真实流量」）。只检测平台的端点：站点和账户自带的端点花的是 key 所有者的钱，和试探同一条规则。
- **型号怎么比**（`modelVerdict`）：先把回答和目录模型的身份规范化——小写，去掉提供商前缀、`@`/`:` 后缀、日期和能识别的发布号（`2024-08-06`、`20241022`、`0613`、`preview-06-05`、`08-2024`），但**保留**型号线、训练和功能限定词（`chat`、`instruct`、`audio`）以及变体词（`mini`、`nano`、`haiku`、`sonnet`、`opus`、`flash`、`pro`、`7b`/`70b` 等）。无法识别的后缀（如无日期的 `latest`、`preview` 或任意厂商后缀）不当作说明词删掉；它们让名字保留，通常因此无法确认相等。规范化后相等（允许只差日期或发布号）为相符。只有双方属于**同一条可识别的型号线**（家族和版本等非变体部分相同）、且写出的变体不同（`mini`/`haiku`/`flash`，`70b` 对 `8b`），或声称没有变体而回答是更小的变体（如 `gpt-4o` 对 `gpt-4o-mini`、`o1` 对 `o1-mini`、`claude-sonnet-4-5` 对 `claude-haiku-4-5`）才判矛盾。无法归到声称型号线的别名、不同型号线，或带额外功能后缀的名字（如 `gpt-4o` 对 `gpt-4o-audio-preview`、`gpt-4o` 对 `gpt-4.1-mini`、`gpt-4o` 对 `gpt-custom-mini`、`llama-3-70b` 对 `llama-3-70b-instruct`、`llama-2-70b` 对 `llama-2-70b-chat`）只算不确定：不能因为一个不认识的 `mini` 后缀就把正常别名判成假冒，也不能把不同功能变体当成同一个模型。日期快照之间的差异不算降级：`gpt-4o-2024-08-06` 回答 `GPT-4o` 仍是通过；同一型号线换日期要等官方基线才能分辨。
- **判定**（`judgeVerification`）：
  - **通过**：回显、和、积、倒序、字符数、作者和型号全部对上；
  - **矛盾**：作者是目录里另一个作者且没有声称的作者；或同一条可识别型号线（家族和版本等非变体部分相同）的变体与声称的不同（更小的 `mini`、`haiku`、`flash`，或 `70b` 对 `8b`），说明是另一档；
  - **不确定**：拒答、答非所问、回答里没有可解析的完整 JSON 对象（纯散文、行列表、截断的 JSON）、算错一个已知答案、型号无法归到声称的型号线（目录没有的别名、不同型号线或额外功能后缀）、超时或传输失败。不确定不改变上一次的结论，也不增加矛盾计数。取回复中第一个可解析 JSON 对象（允许前导散文或代码围栏），要求 nonce 字段存在；先判作者/型号矛盾，再核对已知答案，矛盾优先于算错。不从散文或其他字段里拼答案。
- **调度资格**：仅选未熔断、没有待处理变化或在途检测、未暂停且有资金的平台端点；目录身份或上游名不可比较时按首次重试间隔再查。
- **时刻与置信度**：通过时记下时刻，置信度在结果有效期（默认 24 小时，后台可改）内从 1 线性衰减到 0；检测周期（默认 6 小时，后台可改）后重新检查，带 ±10% 抖动。调度沿用试探的并发上限和每小时预算，先让恢复试探，再排真伪检测；预算不够时记 `axiom.quality.verification` 的 `deferred`。修改检测周期或首次重试时，已排定的下一次检测按上次检测时刻和结果重算：通过的用新周期，矛盾的用新起点重新退避，没得出确定结论的按新重试；正在执行的检测不改，完成时按新值排下一次。
- **未知与失败分开**：
  - 从未检测、或最近一次通过已超过结果有效期（默认 24 小时，后台可改）：未知，`:exacto` 不选它；
  - 一次矛盾：`Verified` 立即为假（失败关闭），但还不断言"假冒"，默认 15 分钟后重查，矛盾按 15 分钟、30 分钟……退避，封顶检测周期；不确定按首次重试间隔再试（起点和周期后台可改）；
  - 自上次通过或配置重置后累计 `verifyFailures`（3）次矛盾（不确定既不增加也不清零）：判定为假冒，仍按退避重查，直到重新通过。
- **证据边界**：通过只证明这次挑战的自报与已知答案相符；静态假接口、未伪装的换型号或输出改写可能被识别，但能答对题并伪装自报的模型、同型号的不同日期快照及量化差异不能据此区分。`:exacto` 仅承诺使用有效验证结果；默认按运营质量优先，显式 `provider.sort` 可覆盖排序；无已验证端点返回 503 `no_endpoint`（原因 `not_verified`）。

- **证据绑定配置**：一条检测证据只说明它检测过的配置。证据记下目录模型、上游名字和所用格式，投影里任一变化就立即作废（`Verified` 为假、矛盾计数清零、假冒告警解除）并马上重查；检测途中配置变了，回来的答案丢弃，记 `stale`。路由读 `MeasuredFor`，配置不符时即使循环还没来得及清也不把 `Verified` 交出去；同一个端点 ID 换了上游名字，新上游不会继承旧的通过。
- **按节点、不落库**：结果和健康度一样只在进程内（模块边界规则第 3 条：调用路径不查库）。重启后未知、`:exacto` 失败关闭，第一次检测完成前不接 `:exacto` 流量；持久化与跨节点采纳尚未实现。
- **开关**：`AXIOM_MODEL_VERIFICATION` 默认 `on`；设为 `off` 时这一节不发检测，所有端点保持未验证、`:exacto` 失败关闭（503 `not_verified`）。这是为了能关掉这笔后台支出。

### 来源类别与指纹

[产品需求](../product.md#端点属性)要求"来源类别在后台增改，每个类别可配识别规则（指纹）"。类别是质量模块的后台数据，路由只按类别筛选，不自己猜来源。

#### 数据模型

| 字段 | 含义 |
|---|---|
| `slug` | 稳定标识，`^[a-z][a-z0-9-]{0,31}$`，创建后不改；停用后也不复用，预设和调用记录里的 slug 因此永远指同一个类别。`official`、`cloud`、`relay` 是迁移写入的三个种子。 |
| `name`、`name_zh` | 管理后台的显示名，英文 1–100 字、中文最多 100 字且可空（空时显示英文名）。改名不改 slug。 |
| `description` | 给管理员看的说明，可空，最多 500 字。 |
| `position` | 识别顺序，范围 0–1,000,000，小的先匹配；未停用的类别之间唯一。回退类别固定排在最后，不参与匹配。 |
| `fallback` | 只有一个类别是回退（种子里的 `relay`）：没有规则匹配、或端点还没有成功响应时归入它。回退类别的规则必须为空。 |
| `system` | `official`、`cloud`、`relay` 为真：可以改显示名；`official`、`cloud` 还可以改规则和顺序，`relay` 作为回退不能改位置或规则；三者都不能删除或改 slug。预设和文档按这三个 slug 表达官方、云厂商和中转来源，删除会让已有规则失去含义。 |
| `rules` | 识别规则，见下。空规则表示永不匹配（回退类别除外）。 |
| `revision`、`created_at`、`updated_at`、`deleted_at` | 乐观并发、审计时间与软删除。停用只把 `deleted_at` 写上，slug 保留。 |

- **类别是数据**：`official` 表示厂商自己的 API，`cloud` 表示云托管，`relay` 表示其余来源；路由只比较 slug，新增类别不用改路由代码。
- **类别数量有上限**（32），每个类别最多 8 个条件，所有类别引用的不同响应头合计最多 32 个。上限让每个端点的指纹证据有固定大小，调用路径不因为后台数据增长而分配。

#### 识别规则

一条规则是若干条件和一个组合方式（`all` / `any`）。一个类别的一组条件只读两类证据：

| 证据 | 条件 | 运算 |
|---|---|---|
| 响应头 | `header` 是头名，大小写不敏感；比较第一个值 | `present`、`absent`、`equals`、`prefix`、`suffix`、`contains` |
| 用量项 | `item` 是计费项名（`cache_read`、`reasoning` 等，见 `catalog.Item`） | `present`（这次响应由上游报告了非零值；网关自己估算补上的不算）、`absent` |

```json
{
  "match": "all",
  "conditions": [
    {"evidence": "header", "name": "anthropic-ratelimit-requests-limit", "operator": "present"},
    {"evidence": "header", "name": "server", "operator": "equals", "value": "cloudflare"}
  ]
}
```

- 头值按原样比较，不折叠大小写；`present` 只看头在不在，空值也算在。头名先规范成 `textproto.CanonicalMIMEHeaderKey`，数据库和 API 里存规范形式。`equals`/`prefix`/`suffix`/`contains` 的值 1–256 字节；`present`/`absent` 不带值。
- `absent` 只在观测时规则实际查过这个头、且响应里没有它时成立；观测时没被任何规则引用的头是"未知"，不是"缺失"，所以新规则引用旧证据里没有的头时，`present` 和 `absent` 都不命中，按失败关闭落到回退。
- 规则格式不写正则、脚本或响应正文：正则会被不可信的头值拖进灾难性回溯，正文则超出"指纹"的范围并把调用内容带进质量模块。消息 ID 和正文里的特征需要协议层先把它们交出来，见「待定问题」。
- 类别的 `position` 决定先匹配谁，第一个匹配的类别胜出；回退类别只在都不匹配时使用。修改规则就是修改类别本身，不保留旧版本：规则是识别数据，不是价格或计费事实，审计记录保留了每次改动的完整前后值。

#### 怎么评估

- **证据只来自成功的响应**：网关在每次 `judge` 判为成功的尝试结束时把响应头和上游报告的用量项放进 `quality.Observation`；失败、超时、没有响应、2xx 之后的空正文或断流不算证据，错误页的响应头不能改变类别。头和用量取自同一次响应：服务端搜索循环里一次尝试有多跳，证据只取第一跳（响应头所属的那一跳），两跳各自的特征不能拼成任何一次响应都不满足的规则。上游没报告、由网关估算的用量项不算"报告了"。
- **只留规则用得到的头**：质量模块按当前规则引用的头名取第一个值（超过 256 字节截断并记下被截断），连同用量位图存在端点的进程内状态里；被截断的值仍是原值的前缀，规则的值又不超过 256 字节，所以 `prefix` 和找到了的 `contains` 是准确的，而 `equals`、`suffix` 取决于丢掉的尾部，判为不匹配（失败关闭）。`Observe` 不查库、不分配。没被任何规则引用的头不保存，所以后台不会无意收集无关的响应头。
- **按顺序判定**：编译后的规则在每次类别数据刷新时生成，`Observe` 逐类别、逐条件比较，第一个匹配的类别写进端点状态；没有匹配、没有成功响应、或类别数据为空时是回退类别。证据绑定端点的目录模型、上游名字和它能调用的格式：`Prepare` 看到配置变了就清掉证据，旧配置的响应头不会给新配置定类别；尝试发出时的配置与 `Prepare` 当前配置不符时，迟到的结果直接丢弃。
- **规则改了以后**：节点每 5 秒重读类别表和规则（`quality.source_classes`），内容有变化就重新编译，并用每个端点已保存的证据重新判定一遍；新规则引用了一个以前没人看过的头时，该端点在下一次 2xx 之前没有这个头的证据，按失败关闭落到回退类别。
- **到路由**：路由快照每 5 秒重建一次，`MeasuredFor` 把端点的类别 slug 按值写进 `routing.Endpoint.Class`；读的配置与 `Prepare` 当前发布的不同（例如读到旧供应商快照的路由构建）时给回退类别，和不给它其他配置的结构事实一样；预设按 slug 过滤。节点重启后读表恢复类别**定义**；端点的响应证据不落库，重启后回到回退类别，等下一次 2xx 重判。类别和规则改动都不需要重启进程。分类结果不落库、不跨节点共享，各节点按自己看到的真实响应判定；这与健康度、真伪检测的处理一致（模块边界规则第 3 条）。
- **对端点的影响**：类别不是端点的持久属性，规则变化只改变下一次快照里端点属于谁。已经在途的调用用计划时冻结的端点继续完成；新请求在快照替换后按新类别过滤。一个类别被停用后，规则里引用它的预设只是不再匹配它（失败关闭）；后台列表不再显示这个类别。

#### 后台与审计

- 管理接口：`GET /api/admin/v1/source-classes`、`POST /api/admin/v1/source-classes`、`PUT /api/admin/v1/source-classes/{slug}`、`DELETE /api/admin/v1/source-classes/{slug}`，需要 `sites.manage` 和两步验证。写操作带 `Idempotency-Key`、`reason` 和（更新/停用时）读到的 `rev`；`rev` 过期返回 409 `stale_revision`，不覆盖别人的修改。幂等键绑定路径里的 slug 和请求体：同一个键换一个类别重放返回 409 `idempotency_key_reused`，不会把另一个类别的结果当成这次的。
- 审计：创建、修改、停用各写一条 `source_class.create`、`source_class.update`、`source_class.delete`，带理由和完整的 before/after（slug、名字、顺序、规则、revision）。表的写入和审计在同一个事务里；读不写审计。

### 线上观测

每次尝试提交延迟、吞吐、错误、结束原因和工具调用语法检查结果；缓存与用量信息由网关记录。输入 token 偏差校验、从上下文错误自动学习上限尚未接入结构事实检测器。工具错误率目前只测参数是否为合法 JSON：

  - **怎么测**：协议层读上游流时，把每个客户端工具调用的参数片段逐段交给一个固定状态的 JSON 语法检查（只记打开的容器和当前读到哪个记号，不缓存参数，嵌套最多 `jsonx.MaxDepth` 层），调用结束时看它是不是恰好一段 JSON 文本：Messages 在 `tool_use` 块的 `content_block_stop`，Responses 在 `function_call` 的 `response.output_item.done`（读它的完整 `arguments`），Chat 没有单个调用的结束事件，在 `[DONE]` 时检查。重复的成员名不算错，与客户端 `JSON.parse` 一致；没有任何参数（空串、Messages 不发增量）算合法，因为无参数工具就这样返回，宁可漏判也不冤枉端点。Chat 一个回答的前 8 个调用逐个检查，之后的只计数不检查，让流的状态保持固定大小。参数片段只在读到它的那个事件里引用事件缓冲，用完即清，流失败或缓冲收缩后不再持有。结果是 `protocol.Progress.ToolChecks`（检查了的调用数）和 `ToolErrors`（其中不合法的数），在回答的结尾一起报告：Messages 在带停止原因的 `message_delta`，Responses 在 `response.completed`，Chat 在 `[DONE]`；跨格式转换时照样带上。回答因输出上限停下（Chat 的 `length`、Messages 的 `max_tokens`、Responses 的 `response.incomplete`）时两个数都不报：调用是被截断的，不是模型写错的，与 OpenRouter 只统计"以工具调用结束"的请求一致。
  - **怎么算**：网关在尝试结束时把回答的 `ToolChecks`、`ToolErrors` 交给 `Observe`。正常结束（`Done`）、判为成功、且检查过调用的回答算一个样本，有任一调用出错记 1、否则记 0，一个回答不论几个调用都只算一次，与 OpenRouter 按请求统计一致；被截断的回答里调用没有结束，不算。网关因为客户端格式接不住参数而让尝试失败时（`protocol.FaultToolInput`），只要协议层已在回答结尾检查过这些调用，这次尝试也记 1：错误样本与健康度分开判定，健康度不计它（模型写错了，端点没有坏），错误率照样要计，否则 Claude Code 这类 Messages 客户端看到的工具错误恰好进不了统计。Chat 流转给 Messages 客户端在 `[DONE]` 时拒绝，停止原因已知，因 `length` 停下的回答本来就不拒绝，所以计入。聚合成 Messages 回复时，聚合在工具块结束就拒绝，那时还没读到停止原因，分不清是写错还是被 `max_tokens` 截断，所以不计（没有检查数），宁可漏判；要计它得让聚合在读到停止原因后再拒绝，而停止原因所在的结尾事件到结算后才交给聚合，提前拒绝又会改变客户端看到的结果和计费，当前不计。样本进与首字延迟相同的加权平均（α = 0.2），样本 ≥ 5 且最近一个在 30 分钟内才算"测过"，否则 `ToolErrorRate` 为 0，路由不因没数据而重排。各节点各自统计，不落库，和延迟、速度一样。
  - **还没测的**：工具名是否在请求里、参数是否符合 schema。两者都要在调用路径上拿到请求声明的工具名和 schema，并在响应里逐个调用保留参数做校验；schema 校验还要选一个 JSON Schema 实现和草案版本（OpenRouter 用 Draft 7）。见「待定问题」。

### 外部评测

外部评测尚未接入。可用来源包括 Artificial Analysis 的能力、速度和延迟数据，OpenRouter 的端点数据，以及中转站检测网站的公开报告；使用条件需在接入时核实。外部结果只能辅助自有实测，不单独决定结论。正式 key 不交给第三方检测网站；需要外部检测时只用可撤销、低额度的测试 key。

### 实测的能力与上限

端点的能力和上限按实测覆盖目录：

| 字段 | 实测怎么覆盖目录 | 没有实测时 |
|---|---|---|
| 能力（工具、图片、PDF、推理、提示缓存、结构化输出、服务端工具） | 测出可用的位加上（目录没声明的也加），测出不可用的位去掉；没有实测的位保留目录值 | 目录值 |
| 请求参数（采样、输出上限、停止等） | 同上，按位覆盖 | 目录值 |
| 上下文长度 | 有实测值就替换目录值，更高或更低都替换；没测过用目录值 | 目录值 |
| 最大输出 | 同上 | 目录值 |

事实按**调用格式**分开保存：Chat 的检测结论只用于 Chat，Responses 的只用于 Responses。同一端点的不同原生格式可以有不同能力、参数和上限；路由按请求实际调用的上游格式读取对应的那一份（`gateway/endpoint.go` 的 `endpointOf` 写入 `routing.Endpoint.Specs`，`Plan` 按 `callFormat` 选择），不会把第一个格式的结论套到另一个格式。对外的模型页和端点发现只有一个端点对象、没有格式参数，所以取所有原生格式的**交集与下限**（`Endpoint.Surface`）：只有一个格式支持的能力不声称，只有一个格式能接受的上限不声称，避免用户看到路由会拒绝的支持。

- **只收确认结论**：检测须多次独立确认后调用 `Measure`，不能把单次请求失败直接写成不支持；目前结构事实检测器尚未实现，无测量时全部沿用目录。
- **新鲜度按配置绑定，不按时间过期**：一条事实只属于测它时的目录模型、上游名字和调用格式，任一项变化立即作废，等新配置重新测。`Monitor.Prepare` 在每次成功的路由重建前发布当前配置，并记录供应商快照的单调 `Routable.Generation`；路由构建和健康循环可能交错，旧 Generation 的 `Prepare` 直接被拒绝，不会把 `current` 改回旧配置或清掉新配置已经记录的事实。`Measure` 在端点锁内比较当前配置，旧配置的结果返回 `false`；旧 Generation 的 `Prepare` 不会把它改回旧配置，所以迟到测量仍被拒绝。能力与上限是结构事实，不会随时间自己恢复；按时间回退到目录会把实测证明做不了的请求重新发过去，所以不设过期。后来的检测可以翻转它：测出支持就清掉以前的"不支持"，测出更长的上限就替换短的那个。
- **重启与节点**：结构事实只在节点内存，重启回到目录值；不跨节点采纳。
- **发布不需要重启**：每次成功的快照重建都由 `MeasuredFor` 把事实按格式取回，`endpointOf` 为每个原生格式写出 `routing.Spec`（`Caps`、`Parameters`、`Context`、`MaxOutput`），`Plan` 按 `callFormat` 读取。端点的 `Caps`、`Parameters`、`Context`、`MaxOutput` 同时保持所有原生格式的交集与下限，供模型页和发现接口在没有格式参数时使用。重建每 5 秒一次，所以正常情况下一次翻转最迟约 5 秒后进入 `Plan`；构建失败时沿用上一份快照，事实也跟着晚到。替换快照不丢事实。调用路径仍只读快照，不加锁、不查库（[性能的「调用路径上的规则」](../performance.md#调用路径上的规则)）。

- **实测优先**：检测须走网关同一条协议并多次独立确认。新增的能力或参数若缺少配套方言、参数清单或计费项，请求准备或计费仍会拒绝或标为缺项，不按未知价格放行。

### 健康与熔断

端点近期失败达到窗口与独立来源阈值时熔断；实际摘除由启动模式控制。已实现本节点测量、降权、离线、告警、慢启动、持久化、租约试探和管理员重新启用时重置；独立管理重置、立即试探、按端点自动摘除开关、线路健康与跨节点定期采纳尚未实现。

#### 三条摘除通道，各归各的主人

一个端点能被路由，要三样同时成立；每样只有它的主人能改，所以"自动不覆盖人工"靠数据的归属保证，不靠各处代码记得判断：

| 通道 | 存在哪 | 谁写 | 怎么回来 |
|---|---|---|---|
| 人停用 | `suppliers.endpoints.enabled` | 只有管理员；同步从不写它（[供应商的「同步与变化」](suppliers.md#同步与变化)） | 只有管理员重新启用 |
| 成本未知 | `suppliers.endpoints.cost_state` | 供应商的同步与对账（估低摘牌只作用于仍使用该次尝试计划的端点，见[供应商成本](billing.md#供应商成本)） | 同步拿到新的成本计划 |
| 熔断 | `quality.endpoint_health`（本节） | 本模块：真实流量的证据、试探结果、管理员的重置 | 试探通过；没有试探的端点由真实请求成功恢复；管理员重置或重新启用 |

- 熔断从不写 `enabled` 或 `cost_state`：每个模块只读写自己的表（[总体架构的「模块边界规则」](../architecture.md#模块边界规则)第 1 条）。所有模块共用一个应用角色 `axiom_app`，数据库的授权分不开模块，所以由测试守住：一个测试扫描本模块的全部 SQL，不得出现 `suppliers.` 的表；另一个测试核对熔断、恢复、重置前后这两列不变。
- 人停用的端点不在 `suppliers.Service.Routable()` 里，所以既不被路由、也不被试探；熔断状态留着，但不起作用。
- **人重新启用时清掉自动状态**：管理接口 `PUT /api/admin/v1/suppliers/{supplier_id}/endpoints/{endpoint_id}/enabled` 写 `enabled: true`（端点本来就启用也算）时，`cmd/axiom` 在同一个事务里先调 suppliers 的 `SetEndpointEnabled`，再调本模块的 `ResetHealth`，同成同败（第 5 条：quality 可以引用 suppliers，反过来不行，所以由组装层同时调两边）。重置总是让 `epoch` 加一（没有健康行时建一行），所以任何节点上基于旧状态的变化，包括已在内存里熔断、还没写进库的那次，写入时都会落败；同时关上熔断、退避归零、清除离线标记和试探租约、从此刻起慢启动，记一条 `reset` 事件；库里的熔断原本开着且是强制模式时，同事务解除这次事故的告警。重新启用就是"人认为它好了"，旧的失败证据不该再挡住它；它要是真坏，会按下面的规则再次熔断。
  - 提交后处理请求的节点用 `AdoptReset` 立即换上新状态，丢掉它基于旧状态排队的变化；如果它在这之间已经从库里读到了重置（或重置之后的新状态）并在其上有了新变化，`AdoptReset` 不覆盖。其他节点没有定期重读健康行，只在它们基于旧 `epoch` 的下一次变化或试探认领在条件更新上落败时，从库里采纳重置后的状态，不会发出这次试探。这个时刻没有上界：既不试探（站点和账户自带的、只有直接格式的端点，或试探预算用完时）、又因有别的候选而收不到真实请求的端点，可能一直按旧熔断当最后备选或离线，直到它有新的变化或节点重启；定期采纳尚未实现。
  - 运营 agent 的启用（`endpoint_set_enabled`）不重置：自动的证据不由另一个自动的操作推翻，熔断照常等试探或真实请求恢复。停用不碰熔断。

#### 健康的对象

- **端点**（分组 × 模型）是熔断的对象：路由只选端点（[术语表](../glossary.md)第 6 条）。
- **线路尚未实现**：供应商 × 出口的建连、DNS、TLS 失败不计入端点；独立线路熔断、HTTP 层恢复试探和无出口排除属于待定实现。
- **疑似出口拦截**（响应是 HTML 页面，`newapi/quirks.go` 与 `sub2api/quirks.go` 归为出口范围加 `SuspectedEgressBlock`）既不计端点、也不计线路，只记日志和指标 `axiom.quality.suspected_block`：租户提示词里的代码片段就可能触发供应商的 WAF 返回 HTML，按它熔断，一个租户就能把整家供应商摘掉。
- **凭证的健康不在这里，归[供应商的「凭证」](suppliers.md#凭证)**：状态、冷却和在途数都在那里。检测和真实流量走同一个调用面，被拒的凭证同样歇着，本模块不另存一份凭证健康。

#### 什么算一次失败

按一次尝试说明了端点本身的什么来判，不看请求的内容；拿不准的一律不计，因为误计让一个租户就能替所有人摘端点。网关在尝试结束时报给本模块（`quality.Observe`，带账户、凭证、结局类别和预估输入 token 数）；判定表只有这一份，表驱动测试逐项覆盖：

| 尝试的结局 | 对健康 | 理由 |
|---|---|---|
| 上游正常结束；已提交（交付了首段正文、推理或工具调用）之后客户端离开 | 成功 | 端点在正常回答 |
| 端点范围的 5xx（`UpstreamError`）、过载或"无可用渠道"（`Overloaded`）、状态码 ≥ 500 的 `Unknown`、模型不存在（`ModelNotFound`） | 失败 | 与请求内容无关。`ModelNotFound` 的模型名来自端点的 `upstream_name`；一把没有该模型权限的 key 也会这样回答，所以它受下文"独立来源"约束 |
| 状态码 < 500 的端点范围 `Unknown`（如未分类的 404、408、413、415、422） | 不计，记指标 `unclassified` | 这些多半由请求引起（超大请求就是 413）；认出来的再补进适配器的分类 |
| 请求已写出、连接断了或没有回应（`Transport`，作用范围是端点） | 失败 | 上游收下了请求却不回答 |
| 等响应头超时（`errHeaderWait`）、提交前空闲超时（`errIdle`） | 预估输入 ≤ 32768 token 时记为**辅助**失败，否则不计 | 20 万 token 的输入预填充本来就可能超过 60 秒，隐藏的推理也会让提交前很久没有内容；阈值是代码默认值（当前不可后台编辑）。辅助失败进窗口、算进失败数，但单靠它们不能熔断（见「摘除」）：租户在低流量的推理模型上用长推理就能制造 60 秒没有内容 |
| 2xx 之后：连接断开、流在结束事件之前中断、事件无法解析、200 没有正文；提交后断流、空闲超时 | 失败 | 正常流未完成 |
| 流里的错误事件 | 类别是服务端错误（Anthropic `api_error`、`overloaded_error`，OpenAI `server_error` 及各格式的同义类别）时失败；限流、上下文超长、内容审核、请求错误和认不出的类别不计 | 它们都是 `ErrUpstream`，类别由 `protocol.FaultOf` 给出 |
| 模型输出不合规，如工具调用的参数不是 JSON | 不计 | 这是模型生成的内容，不是端点坏了；工具调用的错误率另记（上文「线上观测」） |
| 限流（`RateLimited`） | 不计 | 由路由暂停（`Router.Block`）和 429 降权处理 |
| 上下文超长、内容审核、其他 400（`ContextTooLong`、`ContentRejected`、`BadRequest`） | 不计 | 换个请求就会成功。上下文超长另作"真实上限"的证据 |
| 凭证范围（401、403、额度用尽、`NotPermitted`）、分组范围、供应商范围（余额不足） | 不计 | 凭证歇着归 suppliers；余额不足归 供应商暂停和余额过滤 |
| 出口范围 | 不计入端点；线路健康尚未实现，疑似拦截只记指标 | 见上文「健康的对象」 |
| 失败时客户端已经离开（`isGone`），单次调用最长到期，网关自己的原因（内存不足、追加没批准、持有者失效、退出） | 不计 | 取消引起的传输错误、我们自己的期限和资源，都不是端点的错 |

"不计"的结局不进下面的窗口：既不算失败，也不算成功。

#### 摘除

- **窗口**：每个端点在本节点记最近最多 32 个计入的结局（成功或失败），每个带来源和凭证的固定大小标识、以及是不是辅助失败，存在一个固定大小的结构里，由该端点自己的锁保护，`Observe` 不分配。**来源**是账户的所有者用户：同一个人的几个账户算一个来源，由准入结果带给网关。暂时无法取得所有者的账户仍按原规则准入，结局只更新实测、不进入熔断窗口；不能把缺失标识当作独立证据。与上一个计入的结局相隔超过 10 分钟时窗口清空：昨天的失败不和今天的连起来。这是接受的取舍：每隔 10 分钟以上才有一个请求的死端点永远凑不满窗口、不会熔断，代价是每个这样的请求白耗一次尝试再回退，每小时最多约 6 次，而健康度照样下降，均衡策略少分给它。
- **熔断的条件**，同时满足：
  1. 窗口里有 n 个结局时，失败 ≥ max(5, ⌈n/2⌉)，且最近 3 个都是失败；
  2. **至少一个硬失败**：窗口里的失败中至少有一个不是辅助失败，即 5xx、过载、模型不存在、传输错误或流中断（判定表里两种超时以外的失败）；
  3. **独立来源**：这些失败至少来自 2 个来源；端点在 `Routable()` 里有至少 2 把可用凭证时，还要至少来自 2 把凭证。窗口里全部计入的结局（成功和失败）只来自 1 个来源时（自带端点、只有一个租户的站点），条件 1 提高到失败 ≥ max(10, ⌈3n/4⌉) 且最近 5 个都失败。单来源使用提高后的阈值，凭证独立条件仍适用。

- 试探和真伪检测的可编辑项见「调度与预算」；摘除窗口和测量阈值仍是代码常量，按端点的自动摘除开关尚未实现。
- **全局模式**：启动变量 `AXIOM_HEALTH_MODE` 默认 `observe`，照常计数、判定并记 `would_remove` / `would_restore`，不排除端点、不发恢复试探、不发健康告警；下一个计入的成功结束观察中的熔断。`enforce` 才实际降权、离线与试探。模式不是后台热更新设置；真伪检测由独立开关控制。
- 熔断在**本节点立即生效**：路由快照里的端点持有指向本模块实时状态的指针（与 routing 自己的暂停和在途数同一种做法，快照替换不丢），`Plan` 的过滤和 `Router.Blocked` 的复查都读它，不等快照重建。
- **先降权后离线**：熔断端点有健康候选时不接流量；候选全部熔断时保持原排序作最后备选，`Blocked` 只拒绝已离线的端点。第一次失败试探标记离线后，正常路线与最后备选都排除它；全部离线时返回 503 `no_endpoint`，原因 `breaker_open`，带 `Retry-After`。平台生成端点即使最后备选真实请求成功，也仍需试探确认恢复。
- **重新检测仍失败才下线并告警**：平台端点熔断本身只记 `removed` 事件、不告警（自带端点在熔断时发 `owned_endpoint_removed` 通知所有者，见下文「谁的端点试探」）；第一次到期试探仍失败时，把端点标为离线（`offline` 事件）并发出 `endpoint_still_down` 警告，之后的失败试探只更新退避，不重复告警。离线标记复用持久行的 `warned` 列，不另加状态；试探通过或管理员重置时清除并解除告警。
- 熔断不调用 `Router.Block`：暂停是上游说了"等多久"，熔断是我们判断它坏了，两者分开记、分开到期；暂停也不清空窗口。

#### 健康度

- 健康度是成功率的指数加权平均：每个计入的结局（成功取 0、失败取 1）按 α = 0.2 更新错误率，健康度 = 1 − 错误率；没有样本时为 1。与 sub2api 的做法相同。
- 用途：健康度是质量分的可靠性因子（见「质量分、吞吐与延迟」）；低于 0.5 时会话不再粘在这个端点（路由的 `stickyMinHealth`）。"最便宜""最快"不乘健康度，所以部分失败的端点在这两个策略下不降权，只有上面的熔断管它们。
- 试探的结果也按一次结局计入健康度和质量分（通过记 0、失败记 1，不确定的不计），但不进熔断窗口：试探是我们自己的请求，不满足"不同来源"的独立性（见「试探」）。
- 熔断前发出、熔断后才结束的请求更新健康度，但不改变熔断状态。

#### 试探

- **时间**：熔断后默认 30 秒第一次试探（起点后台可改）；没通过就把间隔翻倍，最长 10 分钟（上限固定，所以起点也不能超过它）；起点最短 1 秒，因此退避有 10 级（1、2、4……512、600 秒），旧表的 5 级上限不再够用；每次加 ±25% 的随机抖动，再裁到起点至 10 分钟的范围。到期的试探按到期时刻从早到晚出队。
- **上限**：每个端点同一时刻最多一个试探；每个节点同时最多 4 个、每小时最多 600 个（默认值在代码里，后台可改）。到了上限，到期的试探顺延，端点继续降权（有别的候选时不接流量，没有时仍作最后备选），记指标并告警。试探是平台生成端点的主要恢复证据；没有按需提前的路径，也没有别的证据能替它确认。
- **暂停期间不试探**：端点或它的供应商在暂停中（上游给了 `Retry-After`，或余额不足）时，试探推迟到暂停结束，不计结果、不占预算。quality 不能引用 routing，所以由 quality 定义只读接口（"这个端点和供应商暂停到什么时候"），`routing.Router` 实现，`cmd/axiom` 接上（模块边界规则第 5 条）。
- **供应商快照陈旧**：`Routable()` 报错时不发检测；恢复后将到期试探在当前首次试探延迟范围内重新抖动（默认 30 秒），再按到期顺序调度。
- **发什么**：一次真正的生成，用 `suppliers.Service.TestEndpoint`（[供应商的「用真实生成测试端点」](../../internal/suppliers/README.md#用真实生成测试端点)）走真实调用面，用端点原生的一种生成格式（chat、messages、responses 或 completions，取端点支持的第一种），流式，输出上限 16 个 token，不开推理。只有 embeddings、rerank 等直接格式的端点答不了生成题，不排试探。凭证选与上一次试探不同的一把（端点有不止一把时），一把坏 key 不会让端点一直试不过。随机组合四种简短问法与 64 个整数，形成 256 种不同长度的生成题；抖动控制发送节奏。后台题库与定期轮换尚未实现；这些小题只判断生成通路，不作为防作弊或真伪证据（上文「检测要像真实流量」）。真伪检测是另一条通路（见「真伪检测」）：它要求一次 JSON 回答，包含回显、和、积、倒序、字符数、精确型号和作者，输出上限 `verifyOutput`（256）个 token。
- **怎么判**：2xx 且流正常结束（任何结束原因，包括到了输出上限），或流里出现首段内容并随后正常结束，就算通过；失败按上表判。试探**不提前取消**，读到流结束：不传递取消的供应商（sub2api 一类）照样生成到底并收费，提前断开只会让我们记的成本少于对方扣的。
- **结果也是质量证据**：通过与失败各按一次结局更新质量分和置信度（见「质量分、吞吐与延迟」），不确定的结局不算；试探不进熔断窗口。平台生成端点的恢复只靠本轮试探通过；没有试探的端点靠一次真实请求成功。
- **不确定的结果不算**：拿不到凭证、试探遇到限流、凭证范围的失败、出口失败、预算用完，这次试探既不通过也不失败，按原间隔再排（限流按上游给的等待时间）。
- **谁付钱**：平台承担，检测不经 billing 预留和结算。`RecordTest` 在发起检测的事务里写带“检测”标记的成本行，按输入 token 上界和输出上限估价；事务提交后对账认领该行，但检测扣费不参与估低判定。生成后事务回滚造成缺行时，扣费仍按供应商规则暂挂，见[测试端点](../../internal/suppliers/README.md#用真实生成测试端点)。
- **谁的端点试探**：只试探仍在可路由集合里的平台生成端点；站点和账户自带端点、仅支持直接格式的平台端点不试探、不自动离线，熔断后只作最后备选，熔断之后发出的真实请求成功即恢复。自带端点熔断时通知账户或站点所有者。人停用的端点不试探。
- 只试探熔断中、仍在 `Routable()` 里的端点；人停用的端点从不试探。
- **试探通过不等于真实可用**：一次 16 token 的生成说明不了带工具、长上下文、推理的请求能成功，也挡不住专门放行试探的中转站；真伪由下文「真伪检测」单独判定，恢复后的真实流量再按窗口判断。

#### 恢复

- 端点关上熔断的方式：本轮（当前 `epoch`）的试探通过；没有试探的端点由一次真实请求成功恢复；管理员重置或重新启用。关上时清空窗口、清除离线标记并解除告警，`epoch` 加一；过期的试探结果丢弃。
- **慢启动**：恢复后它在本节点的并发上限从 1 开始，每 5 秒翻倍，约 1 分钟后取消，用的是路由已有的满载判断（`MaxConcurrent`、`full()`；`full()` 也检查凭证容量，见[路由的「容量感知」](routing.md#容量感知)）；只在这个请求还有别的端点可用时生效，单端点模型不因此排队。这对所有策略都有效："最便宜""最快"下恢复的端点不会立刻接下全部流量、再被压垮。
- 恢复后健康度还低（熔断前的失败还在加权平均里），均衡策略分给它的流量也少，随着成功回升；会话要等健康度回到 0.5 以上才粘过来。
- **退避的级别**在恢复后保留，直到恢复后连续 10 个计入的结局都成功，或稳定运行 10 分钟没有再熔断，才回到 30 秒：试探能过、真实请求却总失败的端点会等得越来越久。

#### 持久化与多节点

- **调用路径上只用进程内的状态**（模块边界规则第 3 条）：窗口、健康度、熔断开关都在内存里，`Observe` 不查库、不分配。
- **状态与事件**：后台写 `quality.endpoint_health`，保存端点的状态、epoch、熔断时刻、原因、失败数、退避级别、下次/上次试探时刻与结果、租约所有者与截止时间、所用凭证和离线标记。条件更新要求 epoch 等于已读版本，成功后加一；仅获胜者在同一事务写 `quality.health_events` 和持久告警信号。每秒刷新，失败按 1–30 秒退避；调用路径经容量 1024 的值通道交接，满时推迟新变化并计 `axiom.quality.health.deferred`，下个计入结局重新判定；已接收变化保留重试，崩溃可能丢掉尚未提交的变化。
- **试探用租约认领**：比较后再写，一个端点同一时刻只有一个节点在试探。
- **启动时**读出熔断中的行，照原来的退避接着试探，重启不会让坏端点重新接流量。
- **多节点边界**：健康行没有定期跨节点采纳；启动、回收后重新出现、条件更新或租约竞争失败时才读库。窗口与健康度始终由各节点独立统计。
- **保留与回收**：`health_events` 保留 90 天，后台按天删除；同一端点 10 分钟内来回的熔断与恢复合并成一行"反复"，更新计数与最新投递状态，抖动的端点不会让表无界增长。不在 `Routable()` 里超过一天的端点，从进程内的表里回收，行留在库里；端点再次出现时，先读回自己的行，再发布路由快照。

#### 告警与指标

- **事件**（`quality.health_events`，经 `platform` 的告警信号报告，由 observability 汇总、去重、发送；规则、去重和投递归 observability）：`removed`（只记事件，不告警：端点已降权，等重新检测）→ `offline`（警告：重新检测仍失败，端点下线；原因类别、窗口里的失败数和来源数、最后一次失败的请求 ID 在事件行里）→ `endpoint_still_down` 信号；`endpoint_restored`（信息：离线了多久、怎么恢复的）；`owned_endpoint_removed`（熔断即通知站点或账户的所有者，不发给平台运维——自带端点没有试探，这是熔断时唯一的信号）；`model_unavailable`（严重：上架模型的平台端点全部离线，请求都回 503；全部降权时仍有最后备选；自带端点不参与平台告警的触发或解除）、`probe_budget_exhausted`（警告）；`observe` 模式下是 `would_remove` / `would_restore`，只计数不告警。同一端点的同一种变化只报一次，反复的合并：一次故障的离线信号按故障时刻取源 ID，后续失败的试探和重启都不重复发送。恢复时同事务解除 `endpoint_still_down`（并兼容 `endpoint_offline`）；恢复信息作为已完成事件保留，不持续重复通知。试探预算告警按稳定节点名归并，只在开始顺延时触发，恢复调度时解除；节点启动后首次正常调度也解除上次进程遗留的预算告警。真伪的 `endpoint_fake`（严重：累计三次身份矛盾、期间没有通过或配置重置）走同一个告警接口，只发信号、不写 `quality.health_events`；之后通过或检测配置变化时解除。
- **指标**（不带端点 ID 作标签，避免高基数；按端点的细节在后台视图）：`axiom.quality.health.transitions`（`kind` 当前为 endpoint，`to`，`cause`，`mode`）、`axiom.quality.health.open`、`axiom.quality.probes`（`result`：passed、failed、inconclusive、deferred）、`axiom.quality.probe.duration`（只计实际发出请求的试探）、`axiom.quality.verification`（`result`：passed、contradicted、inconclusive、stale、deferred）、`axiom.quality.unclassified`、`axiom.quality.suspected_block`。

#### 产品成绩（固定测评题）

产品需求把质量分定义为「固定测评题的成绩，以官方直连为 100」（[product.md 的「端点属性」](../product.md#端点属性)）。它回答"答得好不好"，和下面「质量分、吞吐与延迟」的运营质量分回答的"快不快、稳不稳"是两件事：一个端点可以很快很稳却答错，也可以答对但很慢；两个字段分别记录、分别过滤，不互相折算。

- **题库与版本**：题库是编进二进制的 `internal/quality/benchmark-v2.json`，34 道题覆盖算术与推理、指令遵循与转换、代码输出、事实、结构化输出和两段带要点的解释；每道题有稳定的 `id`、问题、输出上限和一组固定判定：去首尾空白后精确相等、忽略大小写的包含或多选一、JSON 对象指定字段相等、解析后 JSON 值相等。判定不用正则、脚本或另一个模型：答案是不可信输入，判定必须是有限、可复现的固定运算。一道题有多个 checks 时按通过的 checks 比例计一道题的分，所以 34 道题满分是 34 个"题分"，不是 37 个 check。题库的 `version` 加文件字节的 SHA-256（`BenchmarkSet.Hash`）是它的身份；改任何一个字节就是换题库，旧成绩和官方基线全部失效，必须换文件名和版本。题库不通过任何公开或管理接口暴露；检测请求走生产出口和生产凭证，和真实流量混在一起。
- **官方基线**：每个目录模型在官方直连（平台端点、来源类别为 `official`，且是目录作者自己的 API）上跑同一套题，得到该模型的锚。本模块能强制的是平台端点、生成格式和覆盖；来源类别与目录作者由运行器在调用前确认，分错了会把非官方服务当成锚。一个模型一个题库版本只有一条基线，后一次官方运行替换前一次；更旧的运行不能覆盖更新的基线。官方端点本身也按这条基线得 100。基线先落库再发布内存：`quality.benchmark_baselines` 按 `(model_id, version)` 一行，记官方端点、运行时刻、格式和每题官方题分；存题分而不是回答正文，因为评分只需要题分，题库和判定器由 hash 固定，正文只会把不可信内容带进库。没有官方基线、官方运行覆盖不到题库的 90%、或官方一个题分都没拿到时，所有端点都没有产品成绩（失败关闭），绝不拿运营质量分冒充。
- **评分**：候选端点跑同一套题。一次运行绑定一个生成格式（`chat`、`messages` 或 `responses`），官方和候选必须同格式：三种格式对同一段问题的框架不同，混着比会变成比 API 而不是比模型。换官方格式等于换基线，旧成绩全部作废；embeddings、rerank 和 legacy completions 不跑基准，只有这些格式的端点没有产品成绩。对官方答过的每道题，候选答对多少算多少（多 checks 的题按比例），候选没答的题记 0；`Score = 100 × 候选题分 ÷ 官方题分`，封顶 100。封顶的理由是产品把官方直连定为 100，且候选在几道题上超过官方是抽样噪声，不是"比官方更好"的证据。官方没答的题不计入分母，候选多答的题也不加分：两边比的始终是官方答过的那一批。
- **覆盖与置信度**：一次运行每道题只生成一次。只有官方覆盖题库的 90%、候选覆盖官方答过题目的 90%、且两边配对的题不少于 20 道时才有成绩；低于任何一条都没有成绩，不是"0 分"。成绩的置信度由三部分组成：
  - 配对差的 95% 半宽。设第 i 道题官方和候选的题分是 `o_i`、`c_i`，`n` 是官方答过、进入分母的题数；候选没答的题按 0 代入区间，不跳过，`R = mean(c) / mean(o)`，则 `SE = 100 × sqrt((Var(c) + R²·Var(o) − 2R·Cov(o,c)) / (n × mean(o)²))`，半宽 = 1.96 × SE；这部分记 `max(0, 1 − 半宽/100)`。
  - 覆盖率：`配对题数 ÷ 官方答过的题数`；覆盖率刚好 90% 时置信度也乘 0.9。
  - 时间：成绩在 120 天后失效，置信度从运行时刻的满值线性衰减到 0；`ProductScoreAt` 保留最近一次运行的时刻，用来区分"从没测过"和"测过但已经旧了"，换官方基线后旧成绩不可比、时刻也归零。

  置信度是区间因子、覆盖率和时间衰减的乘积，不是成绩为真的概率；阈值 0.9 要求乘积至少 0.9，不能只检查半宽与覆盖率各自达标。答错不重试，只有限流或传输失败等未作答的题可重试。

- **运行器尚未接入**：没有自动基准请求；官方账号、月度预算、频率、触发条件与题库轮换待定。站点和账户自带端点不跑基准，因为花的是 key 所有者的钱。
- **到达路由与公开列表**：`MeasuredFor` 输出产品成绩、置信度和运行时刻，网关复制到路由端点的 `Score` / `ScoreConfidence`。预设只要显式或继承了 `min_score` / `min_score_confidence`（含 0），就先要求置信度大于 0，再比较阈值，未测、过期或置信度为 0 都不命中。公开列表的产品成绩字段和“未测量”展示尚未接入；不得拿运营质量分代替。
- **只证明什么**：成绩说明端点在同一套固定题上答得和官方直连一样好或差多少，不证明通用能力、长上下文、工具、图片或真伪；真伪继续由「真伪检测」的 `Verified` 单独回答，预设可以同时要求 `min_score` 和 `verified_only`。题库不公开也不能保证永不被猜到，所以它不能替代真伪检测，只能作为一个可重复的质量尺子。
- **持久化、跨节点采纳与版本**：成绩、官方基线和端点配置代次写在 `quality.benchmark_baselines`、`quality.benchmark_scores` 与 `quality.benchmark_configs`，基线和成绩都带题库 `version` 和 `hash`。
  - 基线按 `(model_id, version)` 唯一，成绩按 `(endpoint_id, version)` 唯一。同一版本里只有更新的运行能替换：基线比 `run_at`；成绩先比 `baseline_at`，同一基线再比 `run_at`。换基线后旧成绩已经不可比，所以更新的基线可以直接覆盖它，不会被一个时钟更晚但基线更旧的成绩挡住。
  - `benchmark_configs` 按 `endpoint_id` 记当前的 `(model_id, upstream, formats)` 和 `epoch`。配置变化在同一事务里把 `epoch` 加一，并删掉该端点的旧成绩；成绩行记下核对时的 `epoch`；写入时 SQL 同时比较配置和这个预期代次，即使配置改回旧值、字段重新相同，代次也已经前进，旧运行不能借写入时的当前代次复活。读取只丢弃越界或损坏的行，`Prepare` 和 `MeasuredFor` 要求成绩的配置和 `epoch` 与当前一致。启动后第一次 `Prepare` 如果发现库里的配置行与当前权威配置不同，会同步配置（不要求本进程曾发布过旧配置）；一旦本进程已经建立配置，旧快照仍不能把它翻回去。同一端点的 `Prepare` 用端点级锁把代次复核、配置写库和本地发布串行起来：旧快照如果在复核后等待，新的代次先发布，它会在写库前再次复核并退出；不能只在写库后检查代次。
  - 读取只取本进程题库的 `version` 和 `hash`，所以换了题库版本的节点不会读到旧版本的基线或成绩，旧节点也不会被新版本的行影响；两版在滚动升级里各读各的行。
  - `RecordOfficialBenchmark`、`RecordBenchmark` 先在事务里写库，成功后才发布内存；写失败返回 false，内存不变。成绩的 `INSERT` 只在它引用的基线仍是库里的那一行、端点当前配置仍与成绩的 `(model_id, upstream, formats)` 一致、且代次等于核对时的预期代次时成立，避免拿旧基线、旧配置或配置往返后的旧运行给新分数背书。`RecordOfficialBenchmark` 只初始化不存在的配置行，不会用迟到的旧官方运行改回配置或删掉有效成绩。全新端点的配置行在第一次记录成绩时插入；`Prepare` 只在已有成绩或已建立的配置发生变更时写配置行，所以一次只为观察的全新端点快照不会产生数据库写。
  - `Start` 在读健康行之后读一次；`Loop.Tick` 每 5 秒重读（`benchmarkEvery`），`Prepare` 把配置与端点当前配置一致、`epoch` 相同、且比当前成绩新的行放进 `State.benchmark`。因此一个节点记录的运行会在约 5 秒内出现在其他节点的下一次快照里，重启的节点在服务前就恢复，不需要重跑。
  - 成绩绑定 `(model_id, upstream, formats)`（`EndpointConfig`）和 `epoch`；换模型、上游名或格式集的端点不采纳旧行，`MeasuredFor` 继续失败关闭。官方基线刷新后，旧成绩的 `baseline_at` 与当前基线不符，分数为 0，直到端点重跑；官方端点自己的 100 也会随基线更新。

#### 质量分、吞吐与延迟

路由快照里端点的这几项，落地后各自的来源：

| 字段 | 来源 | 没有数据时 |
|---|---|---|
| `BreakerOpen`、`Health` | 健康与熔断 | 健康度 1，熔断关 |
| `Latency`（首字延迟） | 真实流量：发出到提交点的时间，只取预估输入 ≤ 4096 token 的尝试（大提示词的预填充不该让所有人看到的延迟变高），按 α = 0.2 加权平均 | 未测 |
| `Throughput`（输出速度） | 真实流量：判为成功、正常结束且输出不少于 50 token 的尝试，输出 token 数 ÷（结束 − 提交点），同样加权平均 | 未测 |
| `LatencyPercentiles`（p50/p75/p90/p99 首字延迟） | 真实流量：与 `Latency` 同一批样本，在滚动五分钟窗口内按最近 128 个样本计算最近秩分位数；每个快照重建时复制进 `routing.Endpoint`，调用路径不加锁 | 窗口内少于 5 个样本时全 0 |
| `ThroughputPercentiles`（p50/p75/p90/p99 输出速度） | 真实流量：与 `Throughput` 同一批样本，同一窗口和样本上限 | 窗口内少于 5 个样本时全 0 |
| `Quality`（质量分） | 运营质量分：健康度 × 已测性能的平均，见下文公式；每次计入的结局和试探的通过/失败都更新 | 没有计入的结局时为中性 1；没测过的性能项不计入 |
| `Confidence`（置信度） | 依据的数量与新近：计入的结局数 ÷ 10（上限 1）× 最后一个结局之后 4 小时内线性衰减到 0 | 0（未知） |
| `ToolErrorRate`（工具调用错误率） | 真实流量：正常结束、检查过客户端工具调用的回答中，有调用的参数不是合法 JSON 的比例，加上因参数接不住而失败的尝试，按回答加权平均；见上文「线上观测」 | 少于 5 个样本或 30 分钟没有新样本时为 0 |

- 延迟、吞吐与工具错误率的首个样本直接作为平均值；健康错误率从 0 起。
- **公式与未知**：质量分 = 健康度 × 性能。性能是已测项的平均：首字延迟 ≤ 1 秒记 1，否则 1 秒 ÷ 延迟；输出速度 ≥ 50 token/s 记 1，否则 速度 ÷ 50。两项都测过时取平均，只测过一个时只取它，都没测过时记 1。1 秒、50 token/s、10 个结局、4 小时是代码里的默认值（`scoreLatency`、`scoreSpeed`、`scoreSamples`、`scoreMaxAge`），尚无后台编辑入口。没有计入结局的端点质量分恒为中性 1、置信度为 0，即使不计入结局的尝试已留下足够的延迟或速度样本（它们仍留在 `Latency`、`Throughput` 里，供"最快"和"最低延迟"使用，但不改变质量分）；测出来差的端点质量分低、置信度大于 0。路由因此把"没测过"排在"测过"之后、彼此按价格加权随机，而不是给它 0 分或按端点 ID 排（见[路由的「排序的先后」](routing.md#排序的先后)）。
- **它和产品里的"质量分"不是一回事**：产品需求里的质量分是「产品成绩（固定测评题）」的 0–100，以官方直连为 100，由上一节单独给出；`Verified` 由「真伪检测」单独给出，运营质量分不冒充它们。三个信号分别过滤，合并规则见[路由的「排序的先后」](routing.md#排序的先后)和「待定问题」。

- **"测过"**的定义：样本数 ≥ 5，且最近一个样本在 30 分钟内；否则按"未测"对待，旧值不永久决定排名。质量分的置信度另有自己的 4 小时上限，两者都只用于排序，不排除端点。
- **百分位窗口**：每条指标一个固定 128 样本的环形缓冲，只取五分钟内样本；端点锁保护写入，后台复制排序，以最近秩算 p50/p75/p90/p99，窗口不足 5 样本时全部为 0。路由只读快照，不在请求中排序；高频端点最多取最近 128 个样本。
- "最快"和"质量优先"策略怎么用这些值、未测的端点怎么得到样本，见[路由的「排序的先后」](routing.md#排序的先后)。

### 调度与预算

- **当前触发条件**：健康熔断到期发恢复试探；真伪检测按新配置、周期或失败重试到期发出。改价、改倍率、上下文测试和整套测评尚无自动触发器。

- **预算、频率和重试间隔**在后台配置（`quality.probe_settings`，管理接口 `/api/admin/v1/settings/quality-probes`，保存校验并审计；节点每 30 秒重新读取，无需重启，修改周期或首次重试时重算已排定的检测）：每小时的试探数、同时试探数、熔断后第一次试探的延迟、真伪检测的周期、首次重试和结果有效期。调度资格仍是代码规则：恢复试探要求熔断打开；两种检测都要求未暂停、有可用余额、并发和预算未用完。检测产生的上游成本按尝试成本记账，并打上"检测"标记。
- **产品成绩**：预算和调度尚未接入，不占当前试探设置的运行预算。

后台设置边界如下；0 或未存值表示采用默认，记录只存有意偏离。保存与审计同事务；启动读取失败或值无效则启动失败，运行中读取失败或无效则保留旧值并记日志。缩小预算不会抹掉已消费次数，等滚动一小时窗口释放容量后再发。

| 字段 | 默认 | 非零范围 |
|---|---|---|
| 每小时检测数 | 600 | 1–100,000 |
| 并发检测数 | 4 | 1–64 |
| 首次恢复试探延迟 | 30 秒 | 1 秒–10 分钟 |
| 真伪检测周期 | 6 小时 | 1 分钟–30 天 |
| 真伪结果有效期 | 24 小时 | 1 分钟–30 天，且不短于周期 |
| 真伪首次重试 | 15 分钟 | 1 分钟–24 小时，且不长于周期 |

### 数据政策

官方供应商的数据政策已知（是否留存、是否用于训练）。中转站的多半无从得知，标为"未知"。用户可以要求只走数据政策明确的端点。

## 决策与理由

| 结论 | 理由 |
|---|---|
| 以端点为健康边界，人工开关、成本状态和熔断各自归属 | 一种自动恢复不能覆盖另一种摘除依据。 |
| 失败判定保守，要求硬失败、窗口和独立来源 | 请求特征或单把坏凭证不能轻易替所有人摘掉端点。 |
| 熔断先降权，失败复查后离线，恢复用慢启动 | 保留最后备选并让恢复有新证据，避免立即涌回全部流量。 |
| 状态与事件用条件更新和租约持久化 | 重启保留坏端点状态，多节点只让获胜者记事件和认领试探。 |
| 高频测量留节点内，低频变化后台写入 | 调用路径不增加数据库或缓存 I/O。 |
| 测量按值进快照，熔断与慢启动提供实时状态 | 排序允许一次重建延迟，摘除必须对下一次规划生效。 |
| 结构事实替换目录、不按时间过期，按配置与格式作废 | 目录是基线，时间流逝不能证明已失败的能力恢复。 |
| 运营质量、产品成绩和真伪分别给出 | 运行速度与稳定性不能证明答题水平或模型身份。 |
| 运营质量用绝对性能基准与独立置信度 | 单端点即可计算，未知不会被冒充成差分或已验证好分。 |
| 随机真伪挑战使用精确自报与已知答案 | 复用现有生成通路，但不能识别有意伪装或证明权重血统。 |
| 固定题库以版本和字节 hash 标识，官方锚定 100 | 所有节点只比较同一题库，少量题的抽样优势不被宣称为超过官方。 |
| 每题一次作答，使用配对区间而不重试错题 | 避免挑答案抬分，并用覆盖与时间表达证据强度。 |
| 产品成绩和基线先落库再发布，自动运行仍待批准 | 跨节点和重启无需为找回成绩重复花钱，运行支出需明确预算。 |
| 来源类别使用稳定 slug、软删除与回退类别 | 预设不会因重用标识而悄悄改变含义。 |
| 指纹仅取头与用量的固定运算，工具参数流式验 JSON | 避免保存用户正文、执行脚本及按参数长度增长内存。 |
| 试探设置为平台单条记录，只存偏离默认的字段 | 平台承担检测费用，统一校验与审计且不复制默认值。 |

## 待定问题

- 结构事实检测器、可编辑检测题库和定期轮换；上线、改价、倍率变化和线上异常触发的贵检测尚未实现。
- 官方基线账号、自动基准运行的月度预算、频率与触发条件；真伪的官方参考响应、tokenizer 和 logprob 等第二层证据。
- 线路健康：只对建连、DNS、TLS 失败计数，供应商全部线路失效时按无出口排除；恢复拟经出口向无副作用固定路径发 HTTP GET，任意 HTTP 响应为通，尚无执行器。
- 健康状态跨节点定期采纳、独立重置与立即试探、按端点自动摘除开关、测量阈值后台编辑；端点管理视图需并列人工、成本与熔断状态、原因和窗口、测量与样本、下次/上次试探及历史，写操作须理由与审计。
- 来源指纹的消息 ID、正文特征及 TLS/证书证据需协议或出站层提供；单端点人工类别覆盖须定义理由、审计与冲突告警。
- 工具名和 schema 校验需传递请求工具声明、决定参数保存方式与 JSON Schema 实现；当前错误率只表示参数 JSON 语法错误。
- 六类属性依据的通用合并、外部评测与人工覆盖，以及真实流量签名、token 数和协议合规检查。

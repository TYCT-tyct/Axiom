# 端点评估

一个端点到底能做什么、是不是真的、好不好、稳不稳，全部靠测量得出。对应代码模块 `quality`。端点属性的种类和获取原则见[产品需求的「端点属性」](../product.md#端点属性)，这里写怎么测、怎么合并。

## 要求

- 评估尽可能全面、自动；人只处理机器判断不了的情况。
- 端点属性靠实测，不靠自报。
- 可以借助外部评测网站的结果。

## 设计

### 依据与合并

"依据"指一个属性值是从哪里得来的。

- **六种依据**：目录基线、供应商自报、主动检测、线上观测、外部评测、人工或运营 agent 覆盖。
- **每个值都带置信度，置信度随时间衰减**，衰减快慢按依据类型不同：
  - 线上观测：以分钟到小时计，反映当下；
  - 主动检测：以天计；
  - 外部评测：以天到周计；
  - 目录基线：保持到下一次同步。
- **冲突时怎么判**：
  - 能力和真伪类：任何一个可信的失败证据都会降低置信度；但要多次独立确认，才判定为"不支持"或"假冒"，一次失败不下结论；
  - 速度和稳定类：以线上观测为准；
  - 人工覆盖必须写理由，与实测冲突时告警。
- **使用**：预设按属性和置信度筛选端点。

### 主动检测

能用"提示词 + 判定规则"表达的检测项存为后台数据，可以随时增改；复杂的才写代码。检测项分为以下几类：

| 类别 | 检测什么 | 示例方法 |
|---|---|---|
| 能力 | 工具、图片、PDF、推理、缓存、结构化输出、参数 | 发出需要该能力的请求，检查响应 |
| 上下文与输出 | 真实的上下文上限、最大输出 | 大海捞针；要求长输出，看是否被截断 |
| 真伪 | 是不是声称的那个模型 | 固定文本的 token 数与官方计数对比；Claude 推理块的签名（由 Anthropic 服务端生成，中转站无法伪造）；知识截止时间；自我认知 |
| 来源 | 上游来自哪里 | 指纹：响应头、消息 ID 格式、用量字段特征 |
| 注入与虚报 | 是否被塞了系统提示、是否虚报用量 | 输入 token 数与应有的对比；诱导复述隐藏指令 |
| 篡改 | 是否改动了模型的输出 | 让模型原样返回指定内容，例如工具调用、网址、代码片段，再逐字比对 |
| 协议与计费合规 | 响应字段、流式事件顺序、用量字段是否符合官方规范 | 与官方基线响应逐字段比对 |
| 质量 | 实际水平 | 一小套固定题，与官方基线的成绩对比 |

- **重点防篡改**：编程工具会执行模型给出的命令和代码。中转站篡改输出，就等于在用户机器上执行别人的代码，所以篡改检测是必测项。
- **官方基线**：真伪、合规、质量检测都需要官方的参考响应。基线按模型版本保存，记录采集时间；厂商更新模型后重新采集。
- **可以借鉴的检测清单**：开源的中转站检测工具已经积累了成套方法：
  - BazaarLink Probe：84 项，覆盖偷换模型、token 注水、系统提示注入、签名篡改，分类依据 arXiv 2604.08407；
  - Veridrop：与官方基线做字段、协议、加密三级比对。

  我们参考它们的方法自己实现（GitHub，2026-10）。Veridrop 采用 AGPLv3，不复制它的代码。

### 检测要像真实流量

狡猾的中转站会识别检测请求：检测时走真模型，真实流量走便宜模型。对策有三条：

- **检测请求看起来和真实请求一样**：
  - 走生产环境同样的出口和同样的 key；
  - 提示词、长度、参数都参数化并随机变化；
  - 检测题库不公开；
  - 发送时间混在真实流量里。
- **不依赖检测的校验**：对抽样的真实请求做低成本校验，例如：
  - Claude 推理块的签名是否存在、格式是否合规；
  - 上报的输入 token 数与我们的计数是否一致；
  - 工具调用是否合规；
  - 消息 ID 和用量字段是否符合规范。
- **长期不一致本身就是证据**：检测结果和线上观测长期对不上（比如检测全过、真实流量的校验却屡屡失败），就告警并降低该端点的置信度。

### 线上观测

每次尝试都顺手记录，不额外花钱：

- 首字延迟、吞吐；
- 按类型统计的错误；
- 结束原因；
- 缓存命中率；
- 上报的输入 token 与我们自己的计数是否一致；
- 上下文超长的报错（用来学习真实上限）；
- 工具调用是否是合法 JSON、工具名是否存在、参数是否符合 schema。这一项参考 OpenRouter 的 Auto Exacto，它按真实流量中的工具调用错误率给端点排序（OpenRouter《Auto Exacto》，2026-10）。

### 外部评测

外部结果作为一种依据参与合并，权重低于我们自己的实测，不单独决定结论：

| 来源 | 能提供什么 | 使用条件 |
|---|---|---|
| Artificial Analysis | 模型能力指数、各供应商的速度和延迟、各端点的准确度指数 | 免费接口每天 100 次，限内部使用并注明来源；按供应商细分的数据需要付费（Artificial Analysis《Data API》，2026-10） |
| OpenRouter 端点数据 | 官方和云厂商端点近 30 分钟的延迟、吞吐、可用率 | 只覆盖 OpenRouter 上的供应商 |
| 中转站检测网站的公开报告 | 某个中转站的历史检测结果和红黑榜 | 例如 Veridrop、BazaarLink |

- **绝不把正式 key 交给第三方检测网站**：只用可随时撤销、额度很低的测试 key；能自己检测的，就自己检测。

### 健康与熔断

- **端点**有三种状态：正常、熔断、试探恢复。连续出错就熔断，熔断中的端点不参与路由，请求直接走其他端点；隔一段时间进入试探恢复：先发检测请求，通过后放少量真实请求，都正常再回到正常状态。熔断状态写进路由快照，所有核心节点看到同样的状态。
- **凭证的健康不在这里，归[供应商](suppliers.md#凭证)**：`credentials.status` 用来筛可用凭证；冷却的实时值只在核心进程内，`cooldown_until` 列已存在但今天没有代码写入它，是否把冷却持久化待定。被上游拒绝、额度用尽、被要求等待时按适配器给的时间歇着，冷却到期后重新参与挑选，没有单独的试探状态；在途数也在核心进程内。检测和真实流量走同一个调用面，被拒的凭证同样歇着，本模块不另存一份凭证健康。

### 调度与预算

- **什么时候测**：新端点上线、发生变化（改价、改倍率、换上游）、定期抽查、线上观测发现异常。
- **贵的检测少做**：塞满上下文、整套质量测评这类检测只在上线、变化或异常时触发。
- **预算、频率、触发条件**都在后台配置。检测产生的上游成本按尝试成本记账，并打上"检测"标记。

### 数据政策

官方供应商的数据政策已知（是否留存、是否用于训练）。中转站的多半无从得知，标为"未知"。用户可以要求只走数据政策明确的端点。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 检测项尽量存为后台数据 | 新的作弊手法出现时，增加检测不需要改代码、不需要发布 |
| 把篡改检测列为必测 | 编程工具会执行模型的输出，篡改的危害远大于降智 |
| 检测伪装成真实流量，并抽样校验真实请求 | 只靠固定检测，中转站识别出检测请求后可以专门应付，检测结果就失去意义 |
| 多次独立确认才判定假冒 | 网络抖动或偶发错误不能让一个正常端点被误判下架 |
| 外部评测只作为一种依据 | 负责人提出可以借助外部评测网站；它们的覆盖面和更新频率我们无法控制，所以权重低于自己的实测 |
| 不把正式 key 交给第三方 | 第三方检测网站会拿到 key，存在泄露风险 |
| 参考开源检测工具的方法，不复制 AGPL 代码 | 方法可以学习；复制 AGPL 代码会迫使 Axiom 开源 |
| 工具调用按 schema 校验 | 工具调用出错对 agent 类用户的伤害最大；OpenRouter 用同样的信号给端点排序 |
| 端点熔断进路由快照，凭证健康留在供应商模块，用进程内的冷却时间表达 | 路由只选端点，凭证由供应商模块挑；把凭证状态放进快照，每个节点的快照都要跟着每把 key 的失败变化，而冷却到期后重新挑选本身就是试探。检测和真实流量共用凭证，失败证据自然落在同一处。否决的做法：quality 另存一份凭证熔断状态：两处状态要互相同步，快照还会带上按凭证的高基数数据 |

# 端点评估

一个端点到底能做什么、是不是真的、好不好、稳不稳，全部靠测量得出。对应代码模块 `quality`。端点属性的种类和获取原则见[产品需求的「端点属性」](../product.md#端点属性)，这里写怎么测、怎么合并。

## 要求

- 评估尽可能全面、自动；人只处理机器判断不了的情况。
- 端点属性靠实测，不靠自报。
- 可以借助外部评测网站的结果。
- 端点坏了自动摘除、有限地试探、好了自动恢复；人停用的端点永远不被自动恢复。

## 设计

### 依据与合并

"依据"指一个属性值是从哪里得来的。

- **六种依据**：目录基线、供应商自报、主动检测、线上观测、外部评测、人工或运营 agent 覆盖。
- **每个值都带置信度，置信度随时间衰减**，衰减快慢按依据类型不同：
  - 线上观测：以分钟到小时计，反映当下；
  - 主动检测：以天计；
  - 外部评测：以天到周计；
  - 目录基线：保持到下一次同步。
- **冲突时怎么判**：
  - 能力和真伪类：任何一个可信的失败证据都会降低置信度；但要多次独立确认，才判定为"不支持"或"假冒"，一次失败不下结论；
  - 速度和稳定类：以线上观测为准；
  - 人工覆盖必须写理由，与实测冲突时告警。
- **使用**：预设按属性和置信度筛选端点。

### 主动检测

能用"提示词 + 判定规则"表达的检测项存为后台数据，可以随时增改；复杂的才写代码。检测项分为以下几类：

| 类别 | 检测什么 | 示例方法 |
|---|---|---|
| 能力 | 工具、图片、PDF、推理、缓存、结构化输出、参数 | 发出需要该能力的请求，检查响应 |
| 上下文与输出 | 真实的上下文上限、最大输出 | 大海捞针；要求长输出，看是否被截断 |
| 真伪 | 是不是声称的那个模型 | 固定文本的 token 数与官方计数对比；Claude 推理块的签名（由 Anthropic 服务端生成，中转站无法伪造）；知识截止时间；自我认知 |
| 来源 | 上游来自哪里 | 指纹：响应头、消息 ID 格式、用量字段特征 |
| 注入与虚报 | 是否被塞了系统提示、是否虚报用量 | 输入 token 数与应有的对比；诱导复述隐藏指令 |
| 篡改 | 是否改动了模型的输出 | 让模型原样返回指定内容，例如工具调用、网址、代码片段，再逐字比对 |
| 协议与计费合规 | 响应字段、流式事件顺序、用量字段是否符合官方规范 | 与官方基线响应逐字段比对 |
| 质量 | 实际水平 | 一小套固定题，与官方基线的成绩对比 |

- **重点防篡改**：编程工具会执行模型给出的命令和代码。中转站篡改输出，就等于在用户机器上执行别人的代码，所以篡改检测是必测项。
- **官方基线**：真伪、合规、质量检测都需要官方的参考响应。基线按模型版本保存，记录采集时间；厂商更新模型后重新采集。
- **可以借鉴的检测清单**：开源的中转站检测工具已经积累了成套方法：
  - BazaarLink Probe：84 项，覆盖偷换模型、token 注水、系统提示注入、签名篡改，分类依据 arXiv 2604.08407；
  - Veridrop：与官方基线做字段、协议、加密三级比对。

  我们参考它们的方法自己实现（GitHub，2026-10）。Veridrop 采用 AGPLv3，不复制它的代码。

### 检测要像真实流量

狡猾的中转站会识别检测请求：检测时走真模型，真实流量走便宜模型。对策有三条：

- **检测请求看起来和真实请求一样**：
  - 走生产环境同样的出口和同样的 key；
  - 提示词、长度、参数都参数化并随机变化；
  - 检测题库不公开；
  - 发送时间混在真实流量里。
- **不依赖检测的校验**：对抽样的真实请求做低成本校验，例如：
  - Claude 推理块的签名是否存在、格式是否合规；
  - 上报的输入 token 数与我们的计数是否一致；
  - 工具调用是否合规；
  - 消息 ID 和用量字段是否符合规范。
- **长期不一致本身就是证据**：检测结果和线上观测长期对不上（比如检测全过、真实流量的校验却屡屡失败），就告警并降低该端点的置信度。

### 线上观测

每次尝试都顺手记录，不额外花钱：

- 首字延迟、吞吐；
- 按类型统计的错误；
- 结束原因；
- 缓存命中率；
- 上报的输入 token 与我们自己的计数是否一致；
- 上下文超长的报错（用来学习真实上限）；
- 工具调用是否是合法 JSON、工具名是否存在、参数是否符合 schema。这一项参考 OpenRouter 的 Auto Exacto，它按真实流量中的工具调用错误率给端点排序（OpenRouter《Auto Exacto》，2026-10）。

### 外部评测

外部结果作为一种依据参与合并，权重低于我们自己的实测，不单独决定结论：

| 来源 | 能提供什么 | 使用条件 |
|---|---|---|
| Artificial Analysis | 模型能力指数、各供应商的速度和延迟、各端点的准确度指数 | 免费接口每天 100 次，限内部使用并注明来源；按供应商细分的数据需要付费（Artificial Analysis《Data API》，2026-10） |
| OpenRouter 端点数据 | 官方和云厂商端点近 30 分钟的延迟、吞吐、可用率 | 只覆盖 OpenRouter 上的供应商 |
| 中转站检测网站的公开报告 | 某个中转站的历史检测结果和红黑榜 | 例如 Veridrop、BazaarLink |

- **绝不把正式 key 交给第三方检测网站**：只用可随时撤销、额度很低的测试 key；能自己检测的，就自己检测。

### 健康与熔断

端点连续失败就熔断（摘出路由），按退避发试探请求，试探通过就恢复。本节是 [#313](https://github.com/TYCT-tyct/Axiom/issues/313) E3-4 的设计，按下文「实现拆分」落地。**落地前的现状**：`gateway/route.go` 的 `endpointOf` 给每个端点的健康度、质量、置信度、吞吐都是 1，熔断恒为关；失败只进调用记录和路由记录（`gateway/attempt.go` 的 `failed`），没有任何东西据此摘除端点。

#### 三条摘除通道，各归各的主人

一个端点能被路由，要三样同时成立；每样只有它的主人能改，所以"自动不覆盖人工"靠数据的归属保证，不靠各处代码记得判断：

| 通道 | 存在哪 | 谁写 | 怎么回来 |
|---|---|---|---|
| 人停用 | `suppliers.endpoints.enabled` | 只有管理员；同步从不写它（[供应商的「同步与变化」](suppliers.md#同步与变化)） | 只有管理员重新启用 |
| 成本未知 | `suppliers.endpoints.cost_state` | 供应商的同步与对账（估低摘牌；[#268](https://github.com/TYCT-tyct/Axiom/issues/268) 是这条通道里的错误：结论落到了已换计划的端点上） | 同步拿到新的成本计划 |
| 熔断 | `quality.endpoint_health`（本节） | 本模块：真实流量的证据、试探结果、管理员的重置 | 试探通过；管理员重置；管理员重新启用 |

- 熔断从不写 `enabled` 或 `cost_state`：每个模块只读写自己的表（[总体架构的「模块边界规则」](../architecture.md#模块边界规则)第 1 条）。所有模块共用一个应用角色 `axiom_app`，数据库的授权分不开模块，所以由测试守住：一个测试扫描本模块的全部 SQL，不得出现 `suppliers.` 的表；另一个测试核对熔断、恢复、重置前后这两列不变。
- 人停用的端点不在 `suppliers.Service.Routable()` 里，所以既不被路由、也不被试探；熔断状态留着，但不起作用。
- **人重新启用时清掉自动状态**：管理接口在 `cmd/axiom` 里开一个事务，先调 suppliers 的 `SetEndpointEnabled`，再调本模块的重置（熔断置为关、`epoch` 加一、记事件），同成同败（[总体架构的「模块边界规则」](../architecture.md#模块边界规则)第 5 条：quality 可以引用 suppliers，反过来不行，所以由组装层同时调两边）。人停的时候端点可能正好坏着，重新启用就是"人认为它好了"，旧的失败证据不该再挡住它；它要是真坏，三次失败后会再次熔断。

#### 健康的对象

- **端点**（分组 × 模型）是熔断的对象：路由只选端点（[术语表](../glossary.md)第 6 条）。
- **出口不通不算端点的错**：请求写出前就失败（连不上、DNS 解析失败、TLS 失败，`suppliers` 的 `transportFailure(false)`，作用范围是出口）记在"供应商 × 出口"这条**线路**上，用同一套熔断规则；一家供应商的全部线路都熔断时，它的端点在路由里按"没有出口"（`NoEgress`，暂时性原因）排除，见[路由的「一个请求的路由步骤」](routing.md#一个请求的路由步骤)。线路的试探只是建连加 TLS 握手，不花钱。
- **凭证的健康不在这里，归[供应商的「凭证」](suppliers.md#凭证)**：状态、冷却和在途数都在那里。检测和真实流量走同一个调用面，被拒的凭证同样歇着，本模块不另存一份凭证健康。

#### 什么算一次失败

按一次尝试说明了端点本身的什么来判，不看请求的内容。网关在尝试结束时报给本模块（`quality.Observe`），带上结果类别；判定表只有这一份，表驱动测试逐项覆盖：

| 尝试的结局 | 对健康 | 理由 |
|---|---|---|
| 上游正常结束；已提交（交付了首段正文、推理或工具调用）之后客户端离开 | 成功 | 端点在正常回答 |
| 端点范围的 5xx（`UpstreamError`）、过载或"无可用渠道"（`Overloaded`）、认不出的响应（`Unknown`，疑似出口拦截的除外）、模型不存在（`ModelNotFound`） | 失败 | 与请求内容无关，换个请求一样失败。`ModelNotFound` 的模型名来自端点的 `upstream_name`，不来自请求：sub2api 遇到它当场让这个账号的这个模型冷却（`ratelimit_service.go:2510`） |
| 请求已写出、没有回应（`Transport`，作用范围是端点），包括等响应头超时（`errHeaderWait`） | 失败 | 上游收下了请求却不回答 |
| 2xx 之后：提交前断流、格式出错、空闲超时（`errIdle`）、200 没有正文；提交后断流、空闲超时 | 失败 | E3-4 点名的空流和超时。这些不是适配器的 `Failure`，由网关的 `broke`/`classify` 判出后带类别（`stream_broke`、`idle`、`empty`）报告 |
| 限流（`RateLimited`） | 不计 | 由 [#328](https://github.com/TYCT-tyct/Axiom/pull/328) 的暂停（`Router.Block`）和 429 降权处理；限流说明上游活着 |
| 上下文超长、内容审核、其他 400（`ContextTooLong`、`ContentRejected`、`BadRequest`） | 不计 | 换个请求就会成功。上下文超长另作"真实上限"的证据（见上文「线上观测」） |
| 凭证范围（401、403、额度用尽、`NotPermitted`）、分组范围、供应商范围（余额不足） | 不计 | 凭证歇着归 suppliers；余额不足归 #328 的供应商暂停和 #228 的余额过滤 |
| 出口范围（请求写出前就失败） | 不计入端点，计入线路 | 见上文「健康的对象」 |
| 失败时客户端已经离开（`isGone`），单次调用最长到期，网关自己的原因（内存不足、追加没批准、持有者失效、退出） | 不计 | 取消引起的传输错误、我们自己的期限和资源，都不是端点的错 |

"不计"的结局既不算失败，也不把连续失败清零。

#### 摘除：连续失败

- **同一端点在本节点连续 3 次失败、相邻两次相隔不超过 10 分钟**（中间没有成功）就熔断。10 分钟没有新的失败，计数从头算。
- 次数和间隔是后台配置（默认值在代码里）；另有按端点的"自动摘除"开关，默认开，关掉的端点只降权、从不熔断（对应 new-api 按渠道的 `AutoBan`，`service/channel.go:29`）。
- 熔断在**本节点立即生效**：路由快照里的端点持有指向本模块该端点实时状态的指针（与 routing 自己的暂停和在途数是同一种做法，快照替换不丢），`Plan` 的过滤和 `Router.Blocked` 的发出前复查都读它，不等下一次快照重建。熔断的端点按 `BreakerOpen` 排除，这是暂时性原因：一个模型的候选全部熔断时回 503（[路由的「没有可用端点时」](routing.md#没有可用端点时)）。
- 熔断不调用 `Router.Block`：暂停是上游说了"等多久"，熔断是我们判断它坏了，两者分开记、分开到期；暂停也不清零失败计数。

#### 健康度

- 健康度是成功率的指数加权平均：每个计入的结局（成功取 0、失败取 1）按 α = 0.2 更新错误率，健康度 = 1 − 错误率；没有样本时为 1。与 sub2api 的做法相同（`openai_account_scheduler.go:242` 的 `alpha = 0.2`，`:998` 的 `errorFactor = 1 − errorRate`）。
- 用途：路由"均衡"策略的权重乘以它；低于 0.5 时会话不再粘在这个端点（routing 的 `stickyMinHealth`，sub2api 的 `shouldEscapeStickyAccount` 同理，`openai_account_scheduler.go:642`）。一个失败率 50% 但没有连续失败到阈值的端点不被摘除，只少分流量。
- 熔断期间仍在跑的旧请求（熔断前发出的）的结局照样更新健康度，但不改变熔断状态；只有试探能把熔断关上。

#### 试探

- **时间**：熔断后 30 秒第一次试探；没通过就把间隔翻倍，最长 10 分钟；每次加 ±10% 的随机抖动，避免一批端点同时试探。
- **有需求时提前**：一个请求因为候选全部熔断而得不到端点时，网关通知本模块（`quality.Wanted`），把这些端点的下一次试探提前到"上一次试探后 30 秒"与现在中较晚的那个；间隔下限不变，所以仍然有界。只有一个端点的模型因此在上游恢复后约 30 秒内回来，不必等满 10 分钟。
- **上限**：每个端点同一时刻最多一个试探；每个节点同时最多 4 个、每小时最多 600 个（后台配置）。到了上限，到期的试探顺延，端点继续熔断，记指标并告警。
- **发什么**：一次真正的生成，走 suppliers 的真实调用面（挑凭证 → 准备 → 发送 → 读流，与 E3-5「用真实生成测试端点」是同一个函数，谁先落地谁提供，另一个复用），用端点原生的调用格式、流式，输出上限 16 个 token（new-api 自动测试的取值，`controller/channel-test.go:840`）。提示词从后台的试探题库随机取，不用固定的 "hi"：狡猾的中转站会识别固定的检测请求（上文「检测要像真实流量」）。
- **怎么判**：2xx 且流在试探期限内（等响应头 30 秒，之后按网关的空闲超时）到达首段内容，或者正常结束（任何结束原因，包括到了输出上限）就算通过，通过后立即取消；失败按上表判。与 new-api 的判法一致：流里至少有一个有效事件且没有错误（`controller/channel-test.go:637`）。
- **不确定的结果不算**：拿不到凭证（都在歇着）、试探遇到限流、凭证范围的失败、出口失败、预算用完，这次试探既不通过也不失败，按原间隔再排（限流按上游给的等待时间）；凭证的事由 suppliers 处理。
- **谁付钱**：试探的上游成本由平台承担，按尝试成本记账并打上"检测"标记（见下文「调度与预算」）。试探没有预留，也不经 billing 的结算，而真实请求的成本行（`attempt_costs`，带对账键）只在结算事务里写（[供应商的「没有对账日志」](../../internal/suppliers/README.md#没有对账日志)）；所以试探结束时由 suppliers 自己的事务写它的成本行（E3-5 的测试函数负责），否则供应商对这次试探的扣费在对账里对不上任何尝试，会被暂挂、等人归属。每个熔断中的端点两次试探至少相隔 30 秒，没有需求时最长相隔 10 分钟，每次 16 token；节点每小时 600 次的上限兜住总量，花费可在指标和成本记录里看到。
- 只试探熔断中、且仍在 `Routable()` 里的端点；正常的端点不做定期试探（那是下文「调度与预算」的定期抽查，不属于这个闭环），人停用的端点从不试探。

#### 恢复

- 本轮（当前 `epoch`）的试探通过：熔断关上，连续失败计数清零，`epoch` 加一；过期的试探结果（`epoch` 已变）丢弃。
- 不另设"放少量真实请求"的半开阶段：恢复后健康度还低（熔断前的失败还在加权平均里），均衡策略分给它的流量自然少，随着成功逐步回升；会话也要等健康度回到 0.5 以上才粘过来。
- 退避的级别在恢复后保留，直到它第一次成功服务一个真实请求才回到 30 秒：试探能过、真实请求却总失败的端点，会再次熔断并等得越来越久，不会来回抖动。
- 管理员的"重置"和"重新启用"也让熔断关上（见上文和下文「后台」）。

#### 持久化与多节点

- **调用路径上只用进程内的状态**（[总体架构的「模块边界规则」](../architecture.md#模块边界规则)第 3 条）：计数、健康度、熔断开关都是原子量，`Observe` 不查库、不分配。
- **状态变化写进本模块的表**，由后台写入器异步写，不在调用路径上：`quality.endpoint_health` 每个端点（或线路）一行：状态、`epoch`、熔断时刻、原因类别与熔断时的连续次数、退避级别、下一次试探时刻、上一次试探的时刻与结果、自动摘除开关、最后由谁改（系统或哪位管理员）；`quality.health_events` 只追加，每次状态变化一行，与状态行同一个事务写（第 2 条）。写失败退避重试；进程崩溃丢掉的最多是最后几次变化，最坏情况是重启后某个坏端点从"正常"开始，再失败 3 次重新熔断。
- **启动时**读出熔断中的行，照原来的退避接着试探，所以重启不会让坏端点重新接流量。
- **多个核心节点时**（H5），最少要共享这几样，都经数据库、都在后台：
  - 节点每次重建快照（5 秒）时读表，`epoch` 更大的状态覆盖本地的：别的节点熔断了，本节点也熔断；别的节点试探恢复了，本节点也恢复；
  - 试探用租约认领（`probe_owner`、`probe_lease_until`，比较后再写），一个端点同一时刻只有一个节点在试探；
  - 连续失败计数和健康度仍按节点各自统计，不共享：每个节点按自己的证据熔断，最慢的情形是坏端点在每个节点各失败 3 次。
  - 不放进缓存：调用路径上的缓存访问只有准入前那一次（[路由的「容量感知」](routing.md#容量感知)）。

#### 告警与指标

- **事件**（`quality.health_events`，经 `platform` 的告警信号报告，由 observability 汇总、去重、发送；规则、去重和投递归 [#316](https://github.com/TYCT-tyct/Axiom/issues/316)）：
  - `endpoint_removed`（警告）：端点、原因类别、连续次数、最后一次失败的请求 ID；
  - `endpoint_restored`（信息）：熔断了多久、试探了几次；
  - `endpoint_still_down`（警告）：熔断超过 1 小时；
  - `model_unavailable`（严重）：一个上架模型的全部端点都不可路由（熔断、暂停或线路不通）；
  - `path_down` / `path_restored`：供应商 × 出口的线路；
  - `probe_budget_exhausted`（警告）。
  同一个端点的同一种变化只报一次；恢复后 10 分钟内又熔断的合并成一次"反复"。
- **指标**（不带端点 ID 作标签，避免高基数；按端点的细节在后台视图）：`axiom.quality.health.transitions`（`kind` 为 endpoint 或 path，`to`，`cause`）、`axiom.quality.health.open`（各类熔断中的数量）、`axiom.quality.probes`（`result`：passed、failed、inconclusive、deferred）、`axiom.quality.probe.duration`。

#### 后台

[#317](https://github.com/TYCT-tyct/Axiom/issues/317) 的后台端点页需要（接口在 H3）：

- 每个端点一行，三条通道并排：人工开关、成本状态及原因、熔断状态；熔断的原因类别、开始时刻、连续次数、下一次试探时刻、上一次试探的结果与请求 ID；健康度、首字延迟、吞吐和样本数；
- 操作：停用、启用（同时清掉自动状态）、立即试探（通过就恢复）、重置熔断、自动摘除开关；改动都要写理由，进审计记录；
- 每个端点的状态变化历史（`quality.health_events`），以及供应商 × 出口线路的状态。

#### 质量分、吞吐与延迟

路由快照里端点的这几项，落地后各自的来源：

| 字段 | 来源 | 没有数据时 |
|---|---|---|
| `BreakerOpen`、`Health` | 本节，H1 起 | 健康度 1，熔断关 |
| `Latency`（首字延迟） | 真实流量：发出到提交点的时间，按 α = 0.2 加权平均；H1 起 | 0，表示"未测" |
| `Throughput`（输出速度） | 真实流量：正常结束且输出不少于 50 token 的尝试，输出 token 数 ÷（结束 − 提交点），同样加权平均；H1 起 | 0，表示"未测" |
| `Quality`、`Confidence` | 主动检测（#313 E3-12 及以后），本设计不提供 | 保持中性值 1，`Verified` 为假；所以"质量优先"策略在有质量分之前不能被预设选用（保存预设时拒绝） |
| `ToolErrorRate` | 真实流量的工具调用校验（上文「线上观测」），不在本设计 | 0 |

"最快"策略怎么用这两项、没测过的端点排在哪，见[路由的「排序的先后」](routing.md#排序的先后)。

#### 不变量

本模块的代码 README（`internal/quality/README.md`）随 H1 建立，不变量届时移过去并写明靠什么保证：

| 不变量 | 怎么检查 |
|---|---|
| H-I1 本模块从不写 `suppliers.endpoints` 的任何列 | 测试扫描本模块的 SQL，不得出现 `suppliers.` 的表（所有模块共用 `axiom_app`，授权分不开）；测试：熔断、恢复、重置前后 `enabled`、`cost_state` 不变 |
| H-I2 人停用的端点不被路由、不被试探，熔断状态怎么变都一样 | 测试：停用后推进时钟跨过所有试探时刻，上游收到 0 个试探请求；恢复与否都不进路线 |
| H-I3 人重新启用后，自动状态为关，且两者在同一事务里 | 测试：事务回滚时两边都不变；提交后熔断为关、`epoch` 加一 |
| H-I4 只有判定表里"失败"的结局增加计数，"不计"的既不增加也不清零 | 表驱动测试覆盖每个 `Cause` × 作用范围 × 客户端是否已离开 × 流式阶段的结局 |
| H-I5 熔断中只有本轮的试探通过能关上它 | 测试：熔断中真实请求成功不关；旧 `epoch` 的试探结果被丢弃 |
| H-I6 每个端点同时最多一个试探；节点的并发和每小时上限不被超过；间隔在 [30s, 10min] 内按倍数增长 | `testing/synctest` 推进时钟，并发提交需求，数上游收到的试探 |
| H-I7 熔断在下一次 `Plan` 和 `Blocked` 复查时就生效 | 测试：第 3 次失败之后的下一个 `Plan` 不含该端点，不重建快照 |
| H-I8 熔断状态在快照替换和进程重启后都还在 | 测试：替换快照后仍排除；重启后读表仍熔断、试探按原级别继续 |
| H-I9 每次状态变化恰好一个事件、一个告警信号 | 测试：并发的第 3、4 次失败只产生一次 `endpoint_removed` |
| H-I10 线路熔断只让该供应商的端点按 `NoEgress` 排除，从不计入端点的健康 | 测试：出口失败后两个端点的健康度和计数都不变 |

#### 测试

除上表各项外，三个端到端用例用真实的节点组装（`cmd/axiom` 的测试装置）、假上游和受控时钟，不靠墙钟和睡眠（[CONTRIBUTING 的「检查清单」](../../CONTRIBUTING.md#检查清单)「时序」）：

- **注入故障：摘除 → 试探 → 恢复**：两个端点服务同一模型，首选端点的假上游连续返回 500；第 3 次后它不再出现在路线里（路由记录的原因是 `breaker_open`），请求全部落在备选上；时钟推进 30 秒，上游收到 1 个试探，仍返回 500，熔断继续、下一次在 60 秒后；上游改为正常的流，下一次试探通过，端点回到路线里；事件依次是 `endpoint_removed`、`endpoint_restored`，指标对应增加。再加一个只有一个端点的模型：全部熔断时回 503，`Wanted` 让试探在 30 秒内发生。
- **人停用不被自动恢复**：端点熔断后管理员停用它，推进时钟跨过所有试探时刻，上游收到 0 个试探，端点不在路线里；管理员启用后熔断为关，下一个请求就路由过去。
- **首选供应商的 DNS 失败落到备选**：首选供应商的地址用解析不了的域名（`.invalid`），经真实的出口发请求；请求以备选供应商的 200 结束，路由记录里首选的失败作用范围是出口；两个端点的健康度和连续计数都不变（H-I10）。现有的 `gateway/exec_test.go`（"the only egress failing moves to the next entry"）是脚本化的出口失败，这个用例补上真实解析失败的路径。H4 再加：连续 3 次后线路熔断，下一个请求的路线里没有首选供应商（原因 `no_egress`），上游收到 0 次连接。

### 调度与预算

- **什么时候测**：新端点上线、发生变化（改价、改倍率、换上游）、定期抽查、线上观测发现异常。
- **贵的检测少做**：塞满上下文、整套质量测评这类检测只在上线、变化或异常时触发。
- **预算、频率、触发条件**都在后台配置。检测产生的上游成本按尝试成本记账，并打上"检测"标记。

### 数据政策

官方供应商的数据政策已知（是否留存、是否用于训练）。中转站的多半无从得知，标为"未知"。用户可以要求只走数据政策明确的端点。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 检测项尽量存为后台数据 | 新的作弊手法出现时，增加检测不需要改代码、不需要发布 |
| 把篡改检测列为必测 | 编程工具会执行模型的输出，篡改的危害远大于降智 |
| 检测伪装成真实流量，并抽样校验真实请求 | 只靠固定检测，中转站识别出检测请求后可以专门应付，检测结果就失去意义 |
| 多次独立确认才判定假冒 | 网络抖动或偶发错误不能让一个正常端点被误判下架 |
| 外部评测只作为一种依据 | 负责人提出可以借助外部评测网站；它们的覆盖面和更新频率我们无法控制，所以权重低于自己的实测 |
| 不把正式 key 交给第三方 | 第三方检测网站会拿到 key，存在泄露风险 |
| 参考开源检测工具的方法，不复制 AGPL 代码 | 方法可以学习；复制 AGPL 代码会迫使 Axiom 开源 |
| 工具调用按 schema 校验 | 工具调用出错对 agent 类用户的伤害最大；OpenRouter 用同样的信号给端点排序 |
| 端点熔断由路由快照持有指向本模块实时状态的指针，凭证健康留在供应商模块，用进程内的冷却时间表达 | 路由只选端点，凭证由供应商模块挑；把凭证状态放进快照，每个节点的快照都要跟着每把 key 的失败变化，而冷却到期后重新挑选本身就是试探。检测和真实流量共用凭证，失败证据自然落在同一处。熔断用指针而不是快照里的值，因为快照每 5 秒才重建一次，期间坏端点还会再接请求。否决的做法：quality 另存一份凭证熔断状态：两处状态要互相同步，快照还会带上按凭证的高基数数据 |
| 人停用、成本未知、熔断是三条通道，分属三张表的三个主人 | 自动机制只改自己的那一列，"自动不覆盖人工"由数据的归属（模块边界规则第 1 条，加扫描 SQL 的测试）保证，不靠每个调用点记得判断。new-api 把三者压在一个状态字段里（`common/constants.go:269-271` 的启用、人工停用、自动停用），只能靠 `ShouldEnableChannel` 判断"当前是自动停用才自动启用"（`service/channel.go:82`）；sub2api 也把人工的 `Schedulable` 与自动的 `TempUnschedulableUntil` 分成两个字段（`service/account.go:50,56`）。我们的人工开关和成本状态本来就在 suppliers，熔断放在 quality 自己的表里，语义与 new-api 相同：自动只恢复自动停的，人启用会清掉自动状态 |
| 摘除用"连续 3 次失败、相邻不超过 10 分钟"，健康度用加权错误率，各管一件事 | 比较过三种（2026-10-19 读两家源码）：① 加权错误率过阈值摘除：样本少时一次失败就让错误率跳 0.2，要另设最少样本数，而且没有流量时错误率停在旧值；sub2api 只把它（`openai_account_scheduler.go:242`）用于加权和粘性逃逸，从不据此摘除。② 时间窗内的次数（sub2api 的流超时 10 分钟 3 次停 5 分钟，`settings_view.go:513`；API key 健康熔断 2 分钟 10 次停 5 分钟，`:603`，两个默认都关）：流量大时一个 99.9% 可用的端点也会在窗口里攒够次数，流量小时 10 次的窗口又永远到不了。③ 连续失败：中间有一次成功就清零，所以只摘真的不能用的端点，部分失败的交给降权；小流量下 3 次就够判断。取 ③，加上 sub2api 的 10 分钟作为相邻失败的最长间隔，昨天的两次失败不和今天的一次连起来。阈值 3 同 sub2api 流超时的默认。new-api 遇到一次 401 或关键词就停用渠道（`service/channel.go:60`、`setting/operation_setting/status_code_ranges.go:17`），那些在我们这里是凭证和供应商范围的失败，已由 suppliers 的凭证歇息和 #328 的供应商暂停处理，不进熔断 |
| 限流不计入健康，过载计入 | 限流是上游说"等一下"，#328 已按 `Retry-After` 暂停并降权；把它也算失败，一阵限流就会把健康的端点熔断。过载（`Overloaded`）在我们的适配器里既是 529 也是 new-api 中转站的"无可用渠道"（`internal/suppliers/internal/newapi/quirks.go:92`），后者可能一直持续，只暂停会让它每隔几秒白耗一次尝试。sub2api 对 529 停 10 分钟（`ratelimit_service.go:1968`，默认值 `config.go:2345`），我们改为连续 3 次熔断、30 秒起试探：真过载时效果相近，恢复得更早 |
| 试探发一次真正的生成，由平台付钱，而不是放一个真实请求过去 | 两家都这样恢复：new-api 定时测试渠道，测试通过且渠道是自动停用的才启用（`controller/channel-test.go:921,963`）；sub2api 的定时测试计划成功后清掉临时不可调度（`scheduled_test_runner_service.go:134`，`ratelimit_service.go:2202`）。放真实请求过去，失败的代价由用户承担（最多等 60 秒的响应头，还占用 3 次尝试之一），而且没有流量的模型永远恢复不了。试探最多每 10 分钟一次、16 个 token，成本有上限 |
| 不设"放少量真实请求"的半开阶段 | new-api 和 sub2api 都是一次测试通过就完全恢复；我们恢复后健康度仍低，均衡策略分给它的流量本来就少，退避级别保留到第一次真实成功，已经覆盖了半开阶段要防的"试探能过、真实请求失败"。半开阶段要按端点数放行名额，多一个状态和一个计数器 |
| 退避 30 秒起、翻倍、最长 10 分钟，候选全熔断时按需提前 | 30 秒是 OpenRouter 判断"最近出过故障"的窗口（OpenRouter《Provider Routing》，2026-10-16：优先选最近 30 秒没有明显故障的供应商）；10 分钟是 new-api 自动测试的默认间隔（`setting/operation_setting/monitor_setting.go:31`）和 sub2api 过载冷却的默认值。最长间隔越长，只有一个端点的模型恢复得越慢，所以加上按需提前，下限仍是 30 秒 |
| 熔断的端点排除出路由，而不是像 OpenRouter 那样排到最后当备选 | OpenRouter 把最近出故障的供应商放在后面当回退（同上）。我们的端点多是中转站，常见的坏法是收下请求不回答，排在回退位置的坏端点每次要耗掉一次尝试、最多 60 秒的等待；而熔断是连续 3 次失败才触发，30 秒就试探，误判的代价小 |
| 熔断状态写进本模块的表，从第一个版本起持久化 | 只放进程内的话，每次发布重启都让坏端点重新接流量，直到再失败 3 次；后台视图和多节点也都要读这张表。只在状态变化时写，次数很少，而且在后台写，不在调用路径上 |
| 计数和健康度按节点统计，不共享 | 共享就要在调用路径上访问缓存或数据库；按节点统计最坏是每个节点各失败 3 次，代价有界。共享的只有熔断与否和试探的认领，都是低频的状态变化 |

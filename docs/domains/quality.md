# 端点评估

一个端点到底能做什么、是不是真的、好不好、稳不稳，全部靠测量得出。对应代码模块 `quality`。端点属性的种类和获取原则见[产品需求的「端点属性」](../product.md#端点属性)，这里写怎么测、怎么合并。

## 要求

- 评估尽可能全面、自动；人只处理机器判断不了的情况。
- 端点属性靠实测，不靠自报。
- 可以借助外部评测网站的结果。
- 端点坏了自动摘除、有限地试探、好了自动恢复；重新检测仍异常则下线并告警；人停用的端点永远不被自动恢复。

## 设计

### 依据与合并

"依据"指一个属性值是从哪里得来的。

- **六种依据**：目录基线、供应商自报、主动检测、线上观测、外部评测、人工或运营 agent 覆盖。
- **每个值都带置信度，置信度随时间衰减**，衰减快慢按依据类型不同：
  - 线上观测：以分钟到小时计，反映当下；
  - 主动检测：以天计；
  - 外部评测：以天到周计；
  - 目录基线：保持到下一次同步。
- **冲突时怎么判**：
  - 能力和真伪类：任何一个可信的失败证据都会降低置信度；但要多次独立确认，才判定为"不支持"或"假冒"，一次失败不下结论；
  - 速度和稳定类：以线上观测为准；
  - 人工覆盖必须写理由，与实测冲突时告警。
- **使用**：预设按属性和置信度筛选端点。

### 主动检测

能用"提示词 + 判定规则"表达的检测项存为后台数据，可以随时增改；复杂的才写代码。检测项分为以下几类：

| 类别 | 检测什么 | 示例方法 |
|---|---|---|
| 能力 | 工具、图片、PDF、推理、缓存、结构化输出、参数 | 发出需要该能力的请求，检查响应 |
| 上下文与输出 | 真实的上下文上限、最大输出 | 大海捞针；要求长输出，看是否被截断 |
| 真伪 | 是不是声称的那个模型 | 固定文本的 token 数与官方计数对比；Claude 推理块的签名（由 Anthropic 服务端生成，中转站无法伪造）；知识截止时间；自我认知 |
| 来源 | 上游来自哪里 | 指纹：响应头、消息 ID 格式、用量字段特征 |
| 注入与虚报 | 是否被塞了系统提示、是否虚报用量 | 输入 token 数与应有的对比；诱导复述隐藏指令 |
| 篡改 | 是否改动了模型的输出 | 让模型原样返回指定内容，例如工具调用、网址、代码片段，再逐字比对 |
| 协议与计费合规 | 响应字段、流式事件顺序、用量字段是否符合官方规范 | 与官方基线响应逐字段比对 |
| 质量 | 实际水平 | 一小套固定题，与官方基线的成绩对比 |

- **重点防篡改**：编程工具会执行模型给出的命令和代码。中转站篡改输出，就等于在用户机器上执行别人的代码，所以篡改检测是必测项。
- **官方基线**：真伪、合规、质量检测都需要官方的参考响应。基线按模型版本保存，记录采集时间；厂商更新模型后重新采集。
- **可以借鉴的检测清单**：开源的中转站检测工具已经积累了成套方法：
  - BazaarLink Probe：84 项，覆盖偷换模型、token 注水、系统提示注入、签名篡改，分类依据 arXiv 2604.08407；
  - Veridrop：与官方基线做字段、协议、加密三级比对。

  我们参考它们的方法自己实现（GitHub，2026-10）。Veridrop 采用 AGPLv3，不复制它的代码。

### 检测要像真实流量

狡猾的中转站会识别检测请求：检测时走真模型，真实流量走便宜模型。对策有三条：

- **检测请求看起来和真实请求一样**：
  - 走生产环境同样的出口和同样的 key；
  - 提示词、长度、参数都参数化并随机变化；
  - 检测题库不公开；
  - 发送时间混在真实流量里。
- **不依赖检测的校验**：对抽样的真实请求做低成本校验，例如：
  - Claude 推理块的签名是否存在、格式是否合规；
  - 上报的输入 token 数与我们的计数是否一致；
  - 工具调用是否合规；
  - 消息 ID 和用量字段是否符合规范。
- **长期不一致本身就是证据**：检测结果和线上观测长期对不上（比如检测全过、真实流量的校验却屡屡失败），就告警并降低该端点的置信度。

### 真伪检测

要回答的是"这个端点服务的，是不是它声称的那个模型"。答案是路由快照里的 `Verified`：最近一次指纹检测通过，结果还在有效期内，之后没有出现矛盾的证据。检测由健康循环定期发出，调用路径只读进程内的结果（[路由的「排序的先后」](routing.md#排序的先后)）。

- **指纹题**：一次真实生成，同一个请求里问三件有已知答案的事：

  1. 原样回显一个随机的十六进制串；
  2. 回答两个随机小整数的和；
  3. 用一个词说出创造它的公司。

  回显串对不上，说明输出被改写或没有真的生成；求和证明对面在生成，而不是回放固定文本；公司名与目录里这个模型作者的显示名比对（简称也算，`Mistral` 对 `Mistral AI`），证明它自称的身份。题面、随机串和数字每次都不同，题库不落库也不公开；检测走生产出口和生产凭证，与真实请求同一条调用面（上文「检测要像真实流量」）。只检测平台的端点：站点和账户自带的端点花的是 key 所有者的钱，和试探同一条规则。
- **判定**（`judgeVerification`）：
  - **通过**：三项都对；
  - **矛盾**：答案里出现了目录里另一个作者、且没有声称的作者；
  - **不确定**：拒答、答非所问、格式不同、超时或传输失败。不确定不改变上一次的结论，也不增加矛盾计数。
- **时刻与置信度**：通过时记下时刻，置信度在结果有效期（默认 24 小时，后台可改）内从 1 线性衰减到 0；检测周期（默认 6 小时，后台可改）后重新检查，带 ±10% 抖动。调度沿用试探的并发上限和每小时预算，先让恢复试探，再排真伪检测；预算不够时记 `axiom.quality.verification` 的 `deferred`。修改检测周期或首次重试时，已排定的下一次检测按上次检测时刻和结果重算：通过的用新周期，矛盾的用新起点重新退避，没得出确定结论的按新重试；正在执行的检测不改，完成时按新值排下一次。
- **未知与失败分开**：
  - 从未检测、或最近一次通过已超过结果有效期（默认 24 小时，后台可改）：未知，`:exacto` 不选它；
  - 一次矛盾：`Verified` 立即为假（失败关闭），但还不断言"假冒"，默认 15 分钟后重查，连续矛盾按 15 分钟、30 分钟……退避（起点和周期后台可改）；
  - 连续 `verifyFailures`（3）次矛盾：判定为假冒，仍按退避重查，直到重新通过。
- **它证明什么、不证明什么**：通过说明端点在随机挑战下自报为声称的作者、原样回了随机串、真的生成了一个随机算术答案。它挡得住没有伪装的转发、静态假接口和改写输出的中转站；挡不住注入系统提示让别的模型自称是它，也挡不住同一厂商内部的降级——这两类要看官方基线（「待定问题」）和线上观测的长期不一致。所以 `Verified` 表示"与声称的身份相符"，不表示"权重与官方完全一致"；`:exacto` 只用这个更窄的承诺。
- **证据绑定配置**：一条检测证据只说明它检测过的配置。证据记下目录模型、上游名字和所用格式，投影里任一变化就立即作废（`Verified` 为假、矛盾计数清零、假冒告警解除）并马上重查；检测途中配置变了，回来的答案丢弃，记 `stale`。路由读 `MeasuredFor`，配置不符时即使循环还没来得及清也不把 `Verified` 交出去；同一个端点 ID 换了上游名字，新上游不会继承旧的通过。
- **按节点、不落库**：结果和健康度一样只在进程内（模块边界规则第 3 条：调用路径不查库）。重启后未知、`:exacto` 失败关闭，第一次检测完成前不接 `:exacto` 流量；持久化与跨节点采纳随 H3/H5。
- **开关**：`AXIOM_MODEL_VERIFICATION` 默认 `on`；设为 `off` 时这一节不发检测，所有端点保持未验证、`:exacto` 失败关闭（503 `not_verified`）。这是为了能关掉这笔后台支出。

### 线上观测

每次尝试都顺手记录，不额外花钱：

- 首字延迟、吞吐；
- 按类型统计的错误；
- 结束原因；
- 缓存命中率；
- 上报的输入 token 与我们自己的计数是否一致；
- 上下文超长的报错（用来学习真实上限）；
- 工具调用是否是合法 JSON、工具名是否存在、参数是否符合 schema。这一项参考 OpenRouter 的 Auto Exacto，它按真实流量中的工具调用错误率给端点排序（OpenRouter《Auto Exacto》，2026-10）。

### 外部评测

外部结果作为一种依据参与合并，权重低于我们自己的实测，不单独决定结论：

| 来源 | 能提供什么 | 使用条件 |
|---|---|---|
| Artificial Analysis | 模型能力指数、各供应商的速度和延迟、各端点的准确度指数 | 免费接口每天 100 次，限内部使用并注明来源；按供应商细分的数据需要付费（Artificial Analysis《Data API》，2026-10） |
| OpenRouter 端点数据 | 官方和云厂商端点近 30 分钟的延迟、吞吐、可用率 | 只覆盖 OpenRouter 上的供应商 |
| 中转站检测网站的公开报告 | 某个中转站的历史检测结果和红黑榜 | 例如 Veridrop、BazaarLink |

- **绝不把正式 key 交给第三方检测网站**：只用可随时撤销、额度很低的测试 key；能自己检测的，就自己检测。

### 实测的能力与上限

端点的能力和上限按实测覆盖目录：

| 字段 | 实测怎么覆盖目录 | 没有实测时 |
|---|---|---|
| 能力（工具、图片、PDF、推理、提示缓存、结构化输出、服务端工具） | 测出可用的位加上（目录没声明的也加），测出不可用的位去掉；没有实测的位保留目录值 | 目录值 |
| 请求参数（采样、输出上限、停止等） | 同上，按位覆盖 | 目录值 |
| 上下文长度 | 有实测值就替换目录值，更高或更低都替换；没测过用目录值 | 目录值 |
| 最大输出 | 同上 | 目录值 |

- **只收已经确认的结论**：一次失败不下结论（「依据与合并」要求多次独立确认）。检测按自己的判定规则确认后调用 `Monitor.Measure`，支持与不支持都是已经确认的实测，不是一次请求的结局；路由不读失败计数或错误码。线上观测的结论（例如上下文超长学到的真实上限）也只有按同一规则确认后才写成事实。本版只落了这条入口和路由的替换：主动检测仍属 [#313](https://github.com/TYCT-tyct/Axiom/issues/313) E3-12，尚未实现，所以没有检测写入时所有字段都用目录值。
- **新鲜度按配置绑定，不按时间过期**：一条事实只属于测它时的目录模型、上游名字和调用格式（与真伪检测的 `claim` 同一规则），任一项变化立即作废，等新配置重新测。能力与上限是结构事实，不会随时间自己恢复；按时间回退到目录会把实测证明做不了的请求重新发过去，所以不设过期。后来的检测可以翻转它：测出支持就清掉以前的"不支持"，测出更长的上限就替换短的那个。
- **重启与节点**：事实和健康度一样只存在进程内，不落库，调用路径不查库。重启后回到目录值，直到重新测到；各节点按自己测到的值路由，跨节点采纳随 H5 与健康状态一起做。
- **发布不需要重启**：每次成功的快照重建都由 `MeasuredFor` 把事实按值取进 `routing.Endpoint` 的 `Caps`、`Parameters`、`Context`、`MaxOutput`。重建每 5 秒一次，所以正常情况下一次翻转最迟约 5 秒后进入 `Plan`；构建失败时沿用上一份快照，事实也跟着晚到。替换快照不丢事实。调用路径仍只读快照，不加锁、不查库（[性能的「调用路径上的规则」](../performance.md#调用路径上的规则)）。
- **滚动发布**：事实只在节点内存和 `MeasuredFor` 的返回值里，不新增表、迁移或对外字段；旧节点继续只用目录值，新节点只在有实测时替换。两者对同一端点给出不同路线是允许的，回退版本也不需要清理数据。
- **实测优先**：目录是基线，不是端点的上限。检测走网关同一条协议（同一个适配器和请求格式），它测到某项能力或参数可用，就说明端点能接这种请求，路由加上这一位；测到不可用就去掉；上下文和输出上限也一样，测得更高就放行，测得低就收紧。否决"只收紧"：产品要求检测后用实测值替换，只收紧会让目录的旧值永远盖住实测，测到更大的上下文也不会被使用，等于没有替换。风险由检测承担：一次误判可能把请求发给实际做不了的端点，所以检测必须多次独立确认（「依据与合并」），并用网关同一条协议测。加上的能力和参数没有目录的方言、参数清单或计费项配套时，路由可能在准备请求或计费时才发现，这类端点会被拒绝或标为缺项，不会按未知价格放行。

### 健康与熔断

端点近期大量失败、且失败来自不同的来源时熔断，先从正常路线里降权（没有别的候选时仍作为最后备选），按退避发试探请求；试探通过才恢复。第一次试探仍失败时把它标记为离线并告警（[产品需求的「自动化」](../product.md#端点属性)：重新检测，仍异常则下线并告警）。本节是 [#313](https://github.com/TYCT-tyct/Axiom/issues/313) E3-4 的设计，按下文「实现拆分」落地；H2 先以"只观察"上线，用数据核对误判率后再打开摘除。**现状**：H1、H2 已落地：实测、窗口与独立来源、实时降权与离线、告警、慢启动、带租约的试探、状态和事件持久化。`AXIOM_HEALTH_MODE` 默认 `observe`；显式设为 `enforce` 才摘除和试探。后台管理开关与重置属 H3，线路属 H4，跨节点定期采纳状态属 H5（代码见 [internal/quality/README.md](../../internal/quality/README.md)）。

#### 三条摘除通道，各归各的主人

一个端点能被路由，要三样同时成立；每样只有它的主人能改，所以"自动不覆盖人工"靠数据的归属保证，不靠各处代码记得判断：

| 通道 | 存在哪 | 谁写 | 怎么回来 |
|---|---|---|---|
| 人停用 | `suppliers.endpoints.enabled` | 只有管理员；同步从不写它（[供应商的「同步与变化」](suppliers.md#同步与变化)） | 只有管理员重新启用 |
| 成本未知 | `suppliers.endpoints.cost_state` | 供应商的同步与对账（估低摘牌只作用于仍使用该次尝试计划的端点，见[供应商成本](billing.md#供应商成本)） | 同步拿到新的成本计划 |
| 熔断 | `quality.endpoint_health`（本节） | 本模块：真实流量的证据、试探结果、管理员的重置 | 试探通过；没有试探的端点由真实请求成功恢复；管理员重置或重新启用 |

- 熔断从不写 `enabled` 或 `cost_state`：每个模块只读写自己的表（[总体架构的「模块边界规则」](../architecture.md#模块边界规则)第 1 条）。所有模块共用一个应用角色 `axiom_app`，数据库的授权分不开模块，所以由测试守住：一个测试扫描本模块的全部 SQL，不得出现 `suppliers.` 的表；另一个测试核对熔断、恢复、重置前后这两列不变。
- 人停用的端点不在 `suppliers.Service.Routable()` 里，所以既不被路由、也不被试探；熔断状态留着，但不起作用。
- **人重新启用时清掉自动状态**：管理接口在 `cmd/axiom` 里开一个事务，先调 suppliers 的 `SetEndpointEnabled`，再调本模块的重置（熔断置为关、`epoch` 加一、记事件），同成同败（第 5 条：quality 可以引用 suppliers，反过来不行，所以由组装层同时调两边）。重新启用就是"人认为它好了"，旧的失败证据不该再挡住它；它要是真坏，会按下面的规则再次熔断。

#### 健康的对象

- **端点**（分组 × 模型）是熔断的对象：路由只选端点（[术语表](../glossary.md)第 6 条）。
- **线路**（供应商 × 出口）：只记建连、DNS 解析、TLS 握手的失败（`suppliers` 的 `transportFailure(false)`，作用范围是出口），用同一套规则；一家供应商的全部线路都熔断时，它的端点按"没有出口"（`NoEgress`，暂时性原因）排除。线路的试探要到 HTTP 层：经该出口对适配器声明的一个无副作用的固定路径（如 new-api 的状态接口）发 GET，收到任何 HTTP 响应就算通；只建连加 TLS 不够，因为拦截发生在 HTTP 层。
- **疑似出口拦截**（响应是 HTML 页面，`newapi/quirks.go` 与 `sub2api/quirks.go` 归为出口范围加 `SuspectedEgressBlock`）既不计端点、也不计线路，只记日志和指标 `axiom.quality.suspected_block`：租户提示词里的代码片段就可能触发供应商的 WAF 返回 HTML，按它熔断，一个租户就能把整家供应商摘掉。
- **凭证的健康不在这里，归[供应商的「凭证」](suppliers.md#凭证)**：状态、冷却和在途数都在那里。检测和真实流量走同一个调用面，被拒的凭证同样歇着，本模块不另存一份凭证健康。

#### 什么算一次失败

按一次尝试说明了端点本身的什么来判，不看请求的内容；拿不准的一律不计，因为误计让一个租户就能替所有人摘端点。网关在尝试结束时报给本模块（`quality.Observe`，带账户、凭证、结局类别和预估输入 token 数）；判定表只有这一份，表驱动测试逐项覆盖：

| 尝试的结局 | 对健康 | 理由 |
|---|---|---|
| 上游正常结束；已提交（交付了首段正文、推理或工具调用）之后客户端离开 | 成功 | 端点在正常回答 |
| 端点范围的 5xx（`UpstreamError`）、过载或"无可用渠道"（`Overloaded`）、状态码 ≥ 500 的 `Unknown`、模型不存在（`ModelNotFound`） | 失败 | 与请求内容无关。`ModelNotFound` 的模型名来自端点的 `upstream_name`；一把没有该模型权限的 key 也会这样回答，所以它受下文"独立来源"约束 |
| 状态码 < 500 的 `Unknown`（适配器认不出的 404、408、413、415、422 等，`newapi/quirks.go:77` 归端点范围） | 不计，记指标 `unclassified` | 这些多半由请求引起（超大请求就是 413）；认出来的再补进适配器的分类 |
| 请求已写出、连接断了或没有回应（`Transport`，作用范围是端点） | 失败 | 上游收下了请求却不回答 |
| 等响应头超时（`errHeaderWait`）、提交前空闲超时（`errIdle`） | 预估输入 ≤ 32k token 时记为**辅助**失败，否则不计 | 20 万 token 的输入预填充本来就可能超过 60 秒（`gateway/config.go:78` 的 `HeaderWait`），隐藏的推理也会让提交前很久没有内容；阈值是代码默认值（后台编辑随 H3）。辅助失败进窗口、算进失败数，但单靠它们不能熔断（见「摘除」）：租户在低流量的推理模型上用长推理就能制造 60 秒没有内容 |
| 2xx 之后：连接断开、流在结束事件之前中断、事件无法解析、200 没有正文；提交后断流、空闲超时 | 失败 | E3-4 点名的空流和超时 |
| 流里的错误事件 | 类别是服务端错误（Anthropic `api_error`、`overloaded_error`，OpenAI `server_error` 及各格式的同义类别）时失败；限流、上下文超长、内容审核、请求错误和认不出的类别不计 | 它们都是 `ErrUpstream`，类别由 `protocol.FaultOf` 给出 |
| 模型输出不合规，如工具调用的参数不是 JSON（`aggregatemessages.go:392`） | 不计 | 这是模型生成的内容，不是端点坏了；工具调用的错误率另记（上文「线上观测」） |
| 限流（`RateLimited`） | 不计 | 由 [#328](https://github.com/TYCT-tyct/Axiom/pull/328) 的暂停（`Router.Block`）和 429 降权处理 |
| 上下文超长、内容审核、其他 400（`ContextTooLong`、`ContentRejected`、`BadRequest`） | 不计 | 换个请求就会成功。上下文超长另作"真实上限"的证据 |
| 凭证范围（401、403、额度用尽、`NotPermitted`）、分组范围、供应商范围（余额不足） | 不计 | 凭证歇着归 suppliers；余额不足归 #328 的供应商暂停和 #228 的余额过滤 |
| 出口范围 | 不计入端点；建连、DNS、TLS 失败计入线路，疑似拦截都不计 | 见上文「健康的对象」 |
| 失败时客户端已经离开（`isGone`），单次调用最长到期，网关自己的原因（内存不足、追加没批准、持有者失效、退出） | 不计 | 取消引起的传输错误、我们自己的期限和资源，都不是端点的错 |

"不计"的结局不进下面的窗口：既不算失败，也不算成功。

#### 摘除

- **窗口**：每个端点在本节点记最近最多 32 个计入的结局（成功或失败），每个带来源和凭证的固定大小标识、以及是不是辅助失败，存在一个固定大小的结构里，由该端点自己的锁保护，`Observe` 不分配。**来源**是账户的所有者用户：同一个人的几个账户算一个来源，由准入结果带给网关。暂时无法取得所有者的账户仍按原规则准入，结局只更新实测、不进入熔断窗口；不能把缺失标识当作独立证据。与上一个计入的结局相隔超过 10 分钟时窗口清空：昨天的失败不和今天的连起来。这是接受的取舍：每隔 10 分钟以上才有一个请求的死端点永远凑不满窗口、不会熔断，代价是每个这样的请求白耗一次尝试再回退，每小时最多约 6 次，而健康度照样下降，均衡策略少分给它。
- **熔断的条件**，同时满足：
  1. 窗口里有 n 个结局时，失败 ≥ max(5, ⌈n/2⌉)，且最近 3 个都是失败；
  2. **至少一个硬失败**：窗口里的失败中至少有一个不是辅助失败，即 5xx、过载、模型不存在、传输错误或流中断（判定表里两种超时以外的失败）；
  3. **独立来源**：这些失败至少来自 2 个来源；端点在 `Routable()` 里有 2 把以上可用凭证时，还要至少来自 2 把凭证。窗口里全部计入的结局（成功和失败）只来自 1 个来源时（自带端点、只有一个租户的站点），条件 1 提高到失败 ≥ max(10, ⌈3n/4⌉) 且最近 5 个都失败。同一租户客户端的自动重试、一把坏 key（`Acquire` 偏爱在途少的凭证，快速失败的坏 key 会被反复挑中，`suppliers/attempt.go:79-98`），都凑不出熔断。
- **为什么是这些数**（参考实现没有可抄的默认摘除规则，见「决策与理由」，这里自己证明）：失败率 p 独立时，每来一个结局就熔断的概率是 p³ × P(其余 n−3 个里失败 ≥ ⌈n/2⌉−3)。p = 10%、n = 32 时约 1.4×10⁻⁹，每秒 100 个结局跑一小时的期望熔断次数约 5×10⁻⁴；评审提议的"10 个里 5 个"在同样条件下每小时约 54 次，每秒 1 个也有约 0.5 次，所以窗口取 32。真坏的端点：新窗口 5 次失败就熔断，窗口里原有 32 个成功时要 16 次。性质测试固定这一点（见「测试」）。
- 试探的间隔与预算、真伪检测的周期是后台配置（默认值在代码里，见下文「试探」「调度与预算」）；摘除窗口的次数和比例仍是代码默认值，后台编辑随 H3 的其余管理面。另有按端点的"自动摘除"开关（H3），关掉的只降权、从不熔断，对应 new-api 按渠道的 `AutoBan`（`service/channel.go:29`）。
- **全局模式**（H2 起，后台配置）：`observe`（默认）照常计数、判定、记事件和指标，事件标为"本会熔断"，但不排除端点、不发试探；判定里的"熔断"在下一个计入的成功时结束，记"本会恢复"。`enforce` 才真正排除和试探。参考实现的自动停用默认都关（new-api `common/constants.go:134` 的 `AutomaticDisableChannelEnabled = false`，sub2api 的两个熔断默认 `Enabled: false`，`settings_view.go:513`、`:603`），我们也不在没有数据时默认摘除：观察一两周，核对"本会熔断"里有多少是误判，再由一个带数据的 PR 把默认改为 `enforce`。
- 熔断在**本节点立即生效**：路由快照里的端点持有指向本模块实时状态的指针（与 routing 自己的暂停和在途数同一种做法，快照替换不丢），`Plan` 的过滤和 `Router.Blocked` 的复查都读它，不等快照重建。
- **熔断先降权，重新检测仍失败才下线**：熔断的端点从正常路线里去掉，记 `breaker_open`；有别的候选时不接流量，一个请求的候选全部熔断时保留原有排序作为**最后备选**，不立刻回 503。它同时按退避接受试探；`Blocked` 在发出前只拒绝已经离线的端点，降权中的最后备选仍可发出。第一次到期试探仍失败后，端点标为离线：`Plan` 不再把它放进任何路线（包括最后备选），`Blocked` 也拒绝它；候选全部离线时 `Plan` 返回暂时性的没有可用端点，网关回 503 `no_endpoint`（原因 `breaker_open`，带 `Retry-After`），等试探恢复。这与 [OpenRouter 对"没有满足路由要求的供应商"的 503](https://openrouter.ai/docs/api-reference/errors)（2026-11-02）一致。代价是单端点模型在第一次试探失败前仍会接到请求（上游恢复了，真实请求先成功，下一次试探通过后回到正常路线；仍坏，最多等一个试探间隔后转 503）。
- **重新检测仍失败才下线并告警**：平台端点熔断本身只记 `removed` 事件、不告警（自带端点在熔断时发 `owned_endpoint_removed` 通知所有者，见下文「谁的端点试探」）；第一次到期试探仍失败时，把端点标为离线（`offline` 事件）并发出 `endpoint_still_down` 警告，之后的失败试探只更新退避，不重复告警。离线标记复用持久行的 `warned` 列，不另加状态；试探通过或管理员重置时清除并解除告警。信号沿用旧版本已经会解除的 `endpoint_still_down`，滚动升级时旧节点恢复也能解除这次事故；事件种类仍是 `offline`。
- 熔断不调用 `Router.Block`：暂停是上游说了"等多久"，熔断是我们判断它坏了，两者分开记、分开到期；暂停也不清空窗口。

#### 健康度

- 健康度是成功率的指数加权平均：每个计入的结局（成功取 0、失败取 1）按 α = 0.2 更新错误率，健康度 = 1 − 错误率；没有样本时为 1。与 sub2api 的做法相同（`openai_account_scheduler.go:242` 的 `alpha = 0.2`，`:998` 的 `errorFactor = 1 − errorRate`）。
- 用途：健康度是质量分的可靠性因子（见「质量分、吞吐与延迟」）；低于 0.5 时会话不再粘在这个端点（routing 的 `stickyMinHealth`，sub2api 的 `shouldEscapeStickyAccount` 同理，`openai_account_scheduler.go:642`）。"最便宜""最快"不乘健康度，所以部分失败的端点在这两个策略下不降权，只有上面的熔断管它们。
- 试探的结果也按一次结局计入健康度和质量分（通过记 0、失败记 1，不确定的不计），但不进熔断窗口：试探是我们自己的请求，不满足"不同来源"的独立性（见「试探」）。
- 熔断前发出、熔断后才结束的请求更新健康度，但不改变熔断状态。

#### 试探

- **时间**：熔断后默认 30 秒第一次试探（起点后台可改）；没通过就把间隔翻倍，最长 10 分钟（上限固定，所以起点也不能超过它）；起点最短 1 秒，因此退避有 10 级（1、2、4……512、600 秒），旧表的 5 级上限不再够用；每次加 ±25% 的随机抖动，再裁到起点至 10 分钟的范围。到期的试探按到期时刻从早到晚出队。
- **上限**：每个端点同一时刻最多一个试探；每个节点同时最多 4 个、每小时最多 600 个（默认值在代码里，后台可改）。到了上限，到期的试探顺延，端点继续降权（有别的候选时不接流量，没有时仍作最后备选），记指标并告警。试探是平台生成端点的主要恢复证据；没有按需提前的路径，也没有别的证据能替它确认。
- **暂停期间不试探**：端点或它的供应商在 #328 的暂停中（上游给了 `Retry-After`，或余额不足）时，试探推迟到暂停结束，不计结果、不占预算。quality 不能引用 routing，所以由 quality 定义只读接口（"这个端点和供应商暂停到什么时候"），`routing.Router` 实现，`cmd/axiom` 接上（模块边界规则第 5 条）。
- **`Routable()` 陈旧期间**（`ErrStale`）不发试探；恢复后，逾期的试探在 30 秒内重新抖动，再按到期先后出队，不一起涌出。
- **发什么**：一次真正的生成，用 H1.5 已实现的 `suppliers.Service.TestEndpoint`（[供应商的「用真实生成测试端点」](../../internal/suppliers/README.md#用真实生成测试端点)）走真实调用面，用端点原生的一种生成格式（chat、messages、responses 或 completions，取端点支持的第一种），流式，输出上限 16 个 token，不开推理。只有 embeddings、rerank 等直接格式的端点答不了生成题，不排试探。凭证选与上一次试探不同的一把（端点有不止一把时），一把坏 key 不会让端点一直试不过。H2 随机组合四种简短问法与 64 个整数，形成 256 种不同长度的生成题；抖动控制发送节奏。后台题库与定期轮换随 H3 管理面接入；这些小题只判断生成通路，不作为防作弊或真伪证据（上文「检测要像真实流量」）。真伪检测是另一条通路（下文「真伪检测」）：它问三行已知答案，输出上限 `verifyOutput`（48）个 token。
- **怎么判**：2xx 且流正常结束（任何结束原因，包括到了输出上限），或流里出现首段内容并随后正常结束，就算通过；失败按上表判。试探**不提前取消**，读到流结束：不传递取消的供应商（sub2api 一类）照样生成到底并收费，提前断开只会让我们记的成本少于对方扣的。
- **结果也是质量证据**：通过与失败各按一次结局更新质量分和置信度（见「质量分、吞吐与延迟」），不确定的结局不算；试探不进熔断窗口。平台生成端点的恢复只靠本轮试探通过；没有试探的端点靠一次真实请求成功。
- **不确定的结果不算**：拿不到凭证、试探遇到限流、凭证范围的失败、出口失败、预算用完，这次试探既不通过也不失败，按原间隔再排（限流按上游给的等待时间）。
- **谁付钱**：平台承担。试探没有预留，也不经 billing 的结算，而真实请求的成本行（`attempt_costs`，带对账键）只在结算事务里写（[供应商的「没有对账日志」](../../internal/suppliers/README.md#没有对账日志)）；所以 H1.5 的 `RecordTest` 在**发起试探的那个事务**里写成本行，打"检测"标记，估价取确定的上界：输入按题目的 token 数上界、输出按上限 16。成本事务提交后，对账照常把这笔扣费认到这一行（不暂挂），但从不判它：`reconcile.go` 的 `judge` 见"检测"标记就返回未判，否则扣费超过估价加取整加 1% 判估低这条规则会把一个按上界本来付得起的端点从成本通道摘掉，这是 #268 同一族的问题。生成后事务回滚导致缺失成本行的扣费仍按现有规则暂挂，失败窗口与理由见 [suppliers 的「用真实生成测试端点」](../../internal/suppliers/README.md#用真实生成测试端点)。
- **谁的端点试探**：只试探平台的、支持生成格式的端点。站点和账户自带的端点（`routing/snapshot.go:72` 的 `Owner`）用的是别人的 key、花别人的钱，不发试探；只支持 embeddings、rerank 等直接格式的平台端点也答不了生成题。这两类端点**不自动离线**：熔断后只作最后备选（有别的候选时不接），真实请求成功即恢复；平台没有不花钱又不发流量的证据能替它们做重新检测，而 H3 的管理重置入口还没落地，自动下线会让一次短暂失败再也回不来。熔断时通知所有者（账户或站点的管理员，经 #316 的用户通知），修复后真实请求会把它带回路线。
- 只试探熔断中、仍在 `Routable()` 里的端点；人停用的端点从不试探。
- **试探通过不等于真实可用**：一次 16 token 的生成说明不了带工具、长上下文、推理的请求能成功，也挡不住专门放行试探的中转站；真伪由下文「真伪检测」单独判定，恢复后的真实流量再按窗口判断。

#### 恢复

- 端点关上熔断的方式：本轮（当前 `epoch`）的试探通过；没有试探的端点由一次真实请求成功恢复；管理员重置或重新启用。关上时清空窗口、清除离线标记并解除告警，`epoch` 加一；过期的试探结果丢弃。
- **慢启动**：恢复后它在本节点的并发上限从 1 开始，每 5 秒翻倍，约 1 分钟后取消，用的是路由已有的满载判断（`MaxConcurrent`、`full()`；`full()` 也检查凭证容量，见[路由的「容量感知」](routing.md#容量感知)）；只在这个请求还有别的端点可用时生效，单端点模型不因此排队。这对所有策略都有效："最便宜""最快"下恢复的端点不会立刻接下全部流量、再被压垮。
- 恢复后健康度还低（熔断前的失败还在加权平均里），均衡策略分给它的流量也少，随着成功回升；会话要等健康度回到 0.5 以上才粘过来。
- **退避的级别**在恢复后保留，直到恢复后连续 10 个计入的结局都成功，或稳定运行 10 分钟没有再熔断，才回到 30 秒：试探能过、真实请求却总失败的端点会等得越来越久。

#### 持久化与多节点

- **调用路径上只用进程内的状态**（模块边界规则第 3 条）：窗口、健康度、熔断开关都在内存里，`Observe` 不查库、不分配。
- **状态变化写进本模块的表**，由后台写入器异步写，不在调用路径上：`quality.endpoint_health` 每个端点（或线路）一行：状态、`epoch`、熔断时刻、原因类别、窗口里的失败数、退避级别、下一次试探时刻、上一次试探的时刻与结果、试探租约（`probe_owner`、`probe_lease_until`）、试探所用凭证、是否已报告离线；人工重置与按端点开关留给 H3。写法是条件更新：`epoch` 等于本节点上次看到的值才写，写成时 `epoch` 加一，所以两个节点同时判定同一个变化，只有一个写成；`quality.health_events` 只由写成的一方在同一个事务里记录变化；十分钟内反复时合并计数、保留最新投递代际，多个节点不会重复记变化。健康变化经平台已有的持久信号接口在同一事务里写入、按源 ID 去重；观测事件不写告警。后台每秒刷新；写失败按 1–30 秒退避重试。调用路径用 1024 个值的有界通道交接变化，满时推迟新的变化、计入 `axiom.quality.health.deferred`，下个计入的结局再判；已接受的变化不丢弃。进程崩溃仍可能丢掉尚未写成的变化。
- **试探从 H2 起就用租约认领**：比较后再写，一个端点同一时刻只有一个节点在试探。
- **启动时**读出熔断中的行，照原来的退避接着试探，重启不会让坏端点重新接流量。
- **多个核心节点时**（H5）再加一样：节点每次重建快照（5 秒）时读表，`epoch` 更大的状态覆盖本地的：别的节点熔断了，本节点也熔断；别的节点恢复了，本节点也恢复。窗口和健康度仍按节点各自统计，不共享；不放进缓存（调用路径上的缓存访问只有准入前那一次，见[路由的「容量感知」](routing.md#容量感知)）。
- **保留与回收**：`health_events` 保留 90 天，后台按天删除；同一端点 10 分钟内来回的熔断与恢复合并成一行"反复"，更新计数与最新投递状态，抖动的端点不会让表无界增长。不在 `Routable()` 里超过一天的端点，从进程内的表里回收，行留在库里；端点再次出现时，先读回自己的行，再发布路由快照。

#### 告警与指标

- **事件**（`quality.health_events`，经 `platform` 的告警信号报告，由 observability 汇总、去重、发送；规则、去重和投递归 [#316](https://github.com/TYCT-tyct/Axiom/issues/316)）：`removed`（只记事件，不告警：端点已降权，等重新检测）→ `offline`（警告：重新检测仍失败，端点下线；原因类别、窗口里的失败数和来源数、最后一次失败的请求 ID 在事件行里）→ `endpoint_still_down` 信号（沿用旧版本已会解除的种类，滚动升级时旧节点恢复也能解除）；`endpoint_restored`（信息：离线了多久、怎么恢复的）；`owned_endpoint_removed`（熔断即通知站点或账户的所有者，不发给平台运维——自带端点没有试探，这是熔断时唯一的信号）；`model_unavailable`（严重：上架模型的平台端点全部离线，请求都回 503；全部降权时仍有最后备选；自带端点不参与平台告警的触发或解除）、`path_down` / `path_restored`、`probe_budget_exhausted`（警告）；`observe` 模式下是 `would_remove` / `would_restore`，只计数不告警。同一端点的同一种变化只报一次，反复的合并：一次故障的离线信号按故障时刻取源 ID，后续失败的试探和重启都不重复发送。恢复时同事务解除 `endpoint_still_down`（并兼容 `endpoint_offline`）；恢复信息作为已完成事件保留，不持续重复通知。试探预算告警按稳定节点名归并，只在开始顺延时触发，恢复调度时解除；节点启动后首次正常调度也解除上次进程遗留的预算告警。真伪的 `endpoint_fake`（严重：连续三次得到另一个作者的答案）走同一个告警接口，只发信号、不写 `quality.health_events`；之后通过或检测配置变化时解除。
- **指标**（不带端点 ID 作标签，避免高基数；按端点的细节在后台视图）：`axiom.quality.health.transitions`（`kind` 为 endpoint 或 path，`to`，`cause`，`mode`）、`axiom.quality.health.open`、`axiom.quality.probes`（`result`：passed、failed、inconclusive、deferred）、`axiom.quality.probe.duration`（只计实际发出请求的试探）、`axiom.quality.verification`（`result`：passed、contradicted、inconclusive、stale、deferred）、`axiom.quality.unclassified`、`axiom.quality.suspected_block`。

- 每个端点一行，三条通道并排：人工开关、成本状态及原因、熔断状态；熔断的原因类别、开始时刻、窗口里的失败数与来源数、下一次试探时刻、上一次试探的结果与请求 ID；健康度、质量分与置信度、首字延迟、吞吐和样本数；全局模式（`observe` / `enforce`）；

#### 质量分、吞吐与延迟

路由快照里端点的这几项，落地后各自的来源：

| 字段 | 来源 | 没有数据时 |
|---|---|---|
| `BreakerOpen`、`Health` | 本节，H1 起 | 健康度 1，熔断关 |
| `Latency`（首字延迟） | 真实流量：发出到提交点的时间，只取预估输入 ≤ 4k token 的尝试（大提示词的预填充不该让所有人看到的延迟变高），按 α = 0.2 加权平均；H1 起 | 未测 |
| `Throughput`（输出速度） | 真实流量：正常结束且输出不少于 50 token 的尝试，输出 token 数 ÷（结束 − 提交点），同样加权平均；H1 起 | 未测 |
| `LatencyPercentiles`（p50/p75/p90/p99 首字延迟） | 真实流量：与 `Latency` 同一批样本，在滚动五分钟窗口内按最近 128 个样本计算最近秩分位数；每个快照重建时复制进 `routing.Endpoint`，调用路径不加锁；2026-11-01 起 | 窗口内少于 5 个样本时全 0 |
| `ThroughputPercentiles`（p50/p75/p90/p99 输出速度） | 真实流量：与 `Throughput` 同一批样本，同一窗口和样本上限 | 窗口内少于 5 个样本时全 0 |
| `Quality`（质量分） | 运营质量分：健康度 × 已测性能的平均，见下文公式；每次计入的结局和试探的通过/失败都更新 | 没有计入的结局时为中性 1；没测过的性能项不计入 |
| `Confidence`（置信度） | 依据的数量与新近：计入的结局数 ÷ 10（上限 1）× 最后一个结局之后 4 小时内线性衰减到 0 | 0（未知） |
| `ToolErrorRate` | 真实流量的工具调用校验（上文「线上观测」），不在本设计 | 0 |

- **公式与未知**：质量分 = 健康度 × 性能。性能是已测项的平均：首字延迟 ≤ 1 秒记 1，否则 1 秒 ÷ 延迟；输出速度 ≥ 50 token/s 记 1，否则 速度 ÷ 50。两项都测过时取平均，只测过一个时只取它，都没测过时记 1。1 秒、50 token/s、10 个结局、4 小时是代码里的默认值（`scoreLatency`、`scoreSpeed`、`scoreSamples`、`scoreMaxAge`），后台编辑随 H3 的其余管理面。没有计入结局的端点质量分恒为中性 1、置信度为 0，即使不计入结局的尝试已留下足够的延迟或速度样本（它们仍留在 `Latency`、`Throughput` 里，供"最快"和"最低延迟"使用，但不改变质量分）；测出来差的端点质量分低、置信度大于 0。路由因此把"没测过"排在"测过"之后、彼此按价格加权随机，而不是给它 0 分或按端点 ID 排（见[路由的「排序的先后」](routing.md#排序的先后)）。
- **它和产品里的"质量分"不是一回事**：产品需求里的质量分是"固定测评题的成绩，以官方直连为 100"，来自主动检测（#313 E3-12），本设计不提供；`Verified` 由「真伪检测」单独给出，运营质量分不冒充它。质量分和真伪怎么合并见「待定问题」。
- **为什么用这些数和绝对基准**：1 秒与 50 token/s 是交互式使用的体感分界，低于它们的回答对用户明显更慢；10 个结局约是 α = 0.2 的两倍记忆长度，初值的影响已压到 10% 以下；4 小时是线上观测的置信度上限，再旧的证据不应参与排序。按绝对基准而不是把同一模型的端点互相归一，是因为快照按端点各自计算，不做跨端点聚合，也不依赖目录里多数模型都没有的输出速度规格；同一模型的端点比较的仍是同一把尺子。
- **"测过"**的定义：样本数 ≥ 5，且最近一个样本在 30 分钟内；否则按"未测"对待，旧值不永久决定排名。质量分的置信度另有自己的 4 小时上限，两者都只用于排序，不排除端点。
- **百分位窗口**：每个端点每条指标一个固定 128 个样本的环形缓冲，记样本值与时刻，只保留五分钟内的样本；端点自己的锁保护写入，`Observe` 仍不分配，每个端点约 4 KiB。读取在快照重建的后台完成：复制、排序后算出 p50/p75/p90/p99，调用路径只读快照里的四个值，不加锁、不分配（[性能的「调用路径上的规则」](../performance.md#调用路径上的规则)）。样本上限固定，所以高频端点只用最近 128 个样本，内存不随流量增长；这与 OpenRouter 的五分钟窗口一致（《Provider Routing》「How Percentiles Work」，2026-11-01）。窗口内少于 5 个样本时四个值全 0，路由按"未测"处理，不把 0 当成极快或极慢。
- "最快"和"质量优先"策略怎么用这些值、未测的端点怎么得到样本，见[路由的「排序的先后」](routing.md#排序的先后)。

#### 测试

除上表各项外，端到端用例用真实的节点组装（`cmd/axiom` 的测试装置）、假上游和受控时钟，不靠墙钟和睡眠（[CONTRIBUTING 的「检查清单」](../../CONTRIBUTING.md#检查清单)「测试与时序」）：

- **注入故障：摘除 → 试探 → 离线 → 恢复**（`enforce`）：两个端点服务同一模型，首选端点的假上游对来自两个账户的请求都返回 500；第 5 次后它不再出现在正常路线里（原因 `breaker_open`），请求落在备选上；时钟推进 30 秒，上游收到 1 个试探，仍返回 500，端点标为离线并发出 `endpoint_still_down`，下一次试探在 60 秒后；上游改为正常的流，试探通过，端点回到路线里，并发上限从 1 开始翻倍，`endpoint_still_down` 解除。再加一个单端点模型：熔断后仍作为最后备选接请求；第一次试探仍失败后回 503 `no_endpoint`（原因 `breaker_open`），不再发给它，直到试探通过。同一失败流在 `observe` 下只产生 `would_remove`，路线不变。
- **人停用不被自动恢复**：端点熔断后管理员停用它，推进时钟跨过所有试探时刻，上游收到 0 个试探，端点不在路线里；管理员启用后熔断为关，下一个请求就路由过去。
- **首选供应商的 DNS 失败落到备选**：首选供应商的地址用解析不了的域名（`.invalid`），经真实的出口发请求；请求以备选供应商的 200 结束，路由记录里首选的失败作用范围是出口；两个端点的窗口和健康度都不变。现有的 `gateway/exec_test.go`（"the only egress failing moves to the next entry"）是脚本化的出口失败，这个用例补上真实解析失败的路径。H4 再加：线路熔断后，下一个请求的路线里没有首选供应商（原因 `no_egress`），上游收到 0 次连接。

### 调度与预算

- **什么时候测**：新端点上线、发生变化（改价、改倍率、换上游）、定期抽查、线上观测发现异常。
- **贵的检测少做**：塞满上下文、整套质量测评这类检测只在上线、变化或异常时触发。
- **预算、频率和触发时机**都在后台配置（`quality.probe_settings`，管理接口 `/api/admin/v1/settings/quality-probes`，保存校验并审计；节点每 30 秒重新读取，无需重启，修改周期或首次重试时重算已排定的检测）：每小时的试探数、同时试探数、熔断后第一次试探的延迟、真伪检测的周期、首次重试和结果有效期。哪些条件算"到期"仍是代码规则（熔断打开、没有暂停、没有可用余额、预算未用完）。检测产生的上游成本按尝试成本记账，并打上"检测"标记。

### 数据政策

官方供应商的数据政策已知（是否留存、是否用于训练）。中转站的多半无从得知，标为"未知"。用户可以要求只走数据政策明确的端点。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 检测项尽量存为后台数据 | 新的作弊手法出现时，增加检测不需要改代码、不需要发布 |
| 把篡改检测列为必测 | 编程工具会执行模型的输出，篡改的危害远大于降智 |
| 检测伪装成真实流量，并抽样校验真实请求 | 只靠固定检测，中转站识别出检测请求后可以专门应付，检测结果就失去意义 |
| 多次独立确认才判定假冒 | 网络抖动或偶发错误不能让一个正常端点被误判下架 |
| 外部评测只作为一种依据 | 负责人提出可以借助外部评测网站；它们的覆盖面和更新频率我们无法控制，所以权重低于自己的实测 |
| 不把正式 key 交给第三方 | 第三方检测网站会拿到 key，存在泄露风险 |
| 参考开源检测工具的方法，不复制 AGPL 代码 | 方法可以学习；复制 AGPL 代码会迫使 Axiom 开源 |
| 工具调用按 schema 校验 | 工具调用出错对 agent 类用户的伤害最大；OpenRouter 用同样的信号给端点排序 |
| 端点熔断由路由快照持有指向本模块实时状态的指针，凭证健康留在供应商模块，用进程内的冷却时间表达 | 路由只选端点，凭证由供应商模块挑；把凭证状态放进快照，每个节点的快照都要跟着每把 key 的失败变化，而冷却到期后重新挑选本身就是试探。检测和真实流量共用凭证，失败证据自然落在同一处。熔断用指针而不是快照里的值，因为快照每 5 秒才重建一次，期间坏端点还会再接请求。否决的做法：quality 另存一份凭证熔断状态：两处状态要互相同步，快照还会带上按凭证的高基数数据 |
| 人停用、成本未知、熔断是三条通道，分属三张表的三个主人 | 自动机制只改自己的那一列，"自动不覆盖人工"由数据的归属（模块边界规则第 1 条，加扫描 SQL 的测试）保证，不靠每个调用点记得判断。new-api 把三者压在一个状态字段里（`common/constants.go:269-271` 的启用、人工停用、自动停用），只能靠 `ShouldEnableChannel` 判断"当前是自动停用才自动启用"（`service/channel.go:82`）；sub2api 也把人工的 `Schedulable` 与自动的 `TempUnschedulableUntil` 分成两个字段（`service/account.go:50,56`）。我们的人工开关和成本状态本来就在 suppliers，熔断放在 quality 自己的表里，语义与 new-api 相同：自动只恢复自动停的，人启用会清掉自动状态 |
| 摘除用"最近 32 个计入的结局里失败过半、最近 3 个都失败、失败来自独立的来源"，健康度用加权错误率，各管一件事 | 参考实现没有可抄的默认摘除规则：new-api 默认不自动停用（`common/constants.go:134`），开了也只按 401 和关键词（`service/channel.go:60`、`setting/operation_setting/status_code_ranges.go:17`），那些在我们这里是凭证和供应商范围，已由 suppliers 的凭证歇息和 #328 的暂停处理；sub2api 的两个窗口熔断（流超时 10 分钟 3 次，`settings_view.go:513`；API key 健康 2 分钟 10 次，`:603`）默认都关，加权错误率（`openai_account_scheduler.go:242`）只用于加权和粘性逃逸。所以阈值靠自己的计算（「摘除」）：只看"连续 3 次"，失败率 5%、每秒 100 个请求时约 84 秒就熔断一次；"10 个里 5 个"在失败率 10%、每秒 1 个时每小时仍约 0.5 次；32 个里过半在每秒 100 个时每小时约 5×10⁻⁴ 次，真坏的端点 5 到 16 次熔断。加权错误率过阈值则在样本少时一次失败跳 0.2、没有流量时停在旧值，不用来摘除。独立来源防的是一个租户（超大请求、客户端重试）或一把坏 key 替所有人摘端点 |
| 熔断先降权（有别的候选时不接，没有时作为最后备选），第一次试探仍失败才离线并回 503；试探通过恢复 | [产品需求](../product.md#端点属性)规定"线上观测到异常时降权、重新检测，仍异常则下线并告警"：降权不是立刻下线，单端点模型在试探前仍能接请求，没有试探的端点由真实成功恢复；失败试探才是下线与告警的证据。离线后不再把端点发给用户，全部离线时回 503 `no_endpoint`。否决"熔断即离线"：它把停止服务提前到重新检测之前，一次短暂抖动也要等试探；否决"永远最后备选"：坏端点会一直被送流量，"仍异常"永远得不到确认 |
| 自动摘除先以 `observe` 上线，用数据核对后再默认 `enforce` | 两家参考实现的自动停用默认都关（见上文「摘除」的出处），误摘一个端点就是一个模型的降级；先只记"本会熔断"，拿一两周的真实数据核对误判率，再决定默认值 |
| 限流不计入健康，过载计入；认不出的 4xx、流内的请求类错误、模型输出不合规、长输入的超时都不计 | 限流是上游说"等一下"，#328 已按 `Retry-After` 暂停并降权。过载（`Overloaded`）在我们的适配器里既是 529 也是 new-api 中转站的"无可用渠道"（`internal/suppliers/internal/newapi/quirks.go:92`），后者可能一直持续，只暂停会让它每隔几秒白耗一次尝试。其余几类都可能由请求或模型输出引起，拿不准就不计：误计的代价是一个租户摘掉所有人的端点，漏计的代价只是熔断晚一点 |
| 试探发一次真正的生成、读到结束、按上界估价，由平台付钱 | 恢复要有不依赖流量的证据：new-api 的自动测试（默认关，`setting/operation_setting/monitor_setting.go:30`）在测试通过且渠道是自动停用时才启用（`controller/channel-test.go:921,963`）；sub2api 的定时测试计划成功后清掉临时不可调度（`scheduled_test_runner_service.go:134`，`ratelimit_service.go:2202`）。输出上限 16 是我们自己的取值：够判断端点在生成，又让成本上界小；new-api 只在 O 系列和兜底分支用 16，带 thinking 的用 50、gemini 用 3000（`controller/channel-test.go:826-840`），我们不开推理并接受"到达上限而结束"为通过，所以不需要那些分支。读到结束和按上界估价，是为了试探的扣费在对账里不被判为估低 |
| 不设"放少量真实请求"的半开阶段，改用慢启动 | 半开阶段要按端点数放行名额，多一个状态；慢启动复用路由已有的并发上限与满载判断，对所有策略都有效，而健康度经质量分和粘性影响路线 |
| 退避 30 秒起、翻倍、最长 10 分钟，恢复后连续 10 次成功或稳定 10 分钟才重置 | 30 秒是 OpenRouter 判断"最近出过故障"的窗口（同上）；10 分钟上限是成本和恢复延迟的折中：每个熔断中的端点每小时最多约 6 次试探。起点可调到 1 秒，所以级别上限从 5 提到 10，才够从 1 秒翻倍到 10 分钟。单端点模型在熔断期间回 503，恢复只能等试探通过，所以第一次试探不能在 30 秒内反复打；试探能过、真实请求却大量失败的端点会很快再次熔断，退避从上一级接着涨，不会每分钟恢复一次 |
| 熔断状态写进本模块的表，从第一个版本起持久化，条件更新加试探租约 | 只放进程内的话，每次发布重启都让坏端点重新接流量；后台视图和多节点也都要读这张表。H2 起就可能有多个实例写同一行，所以从 H2 起用 `epoch` 条件更新和租约，事件只由写成的一方写 |
| 告警描述当前事故，确认恢复才解除 | 摘除本身只记事件：一次抖动会被下一次试探清掉，不必惊动运维。第一次试探仍失败才标记离线并发出 `endpoint_still_down`（旧版本已会解除的种类），源 ID 按熔断时刻固定，后续失败的试探和重启不会重复发送；恢复在同一个事务里解除它，避免已恢复端点继续重复通知。预算告警按稳定节点名只报状态边沿，避免每秒写信号和重启遗留 |
| H2 的开关先用启动配置，题库先用 256 种组合；试探预算、频率和周期的后台编辑已随 D11 接入，题库编辑仍属 H3 | H2 先用现有启动配置和内置组合验证完整闭环，默认保持只观察，组合题只验证生成通路，不宣称防作弊；D11 已补上试探预算、频率和周期的管理契约与审计，不改健康状态表、租约或未来题库接口 |
| 试探预算、频率和真伪检测周期是平台后台数据（`quality.probe_settings`），默认值在代码，保存时校验并审计，节点每 30 秒热读 | D11 要求检测预算、频率和触发条件由管理员在后台配置（[需求审计 #559](https://github.com/TYCT-tyct/Axiom/issues/559)）；按负责人 2026-11-02 的 D11 派工卡（[https://github.com/TYCT-tyct/Axiom/issues/559#issuecomment-6570348719](https://github.com/TYCT-tyct/Axiom/issues/559#issuecomment-6570348719)）落地：该卡明确要求后台记录、可选字段的管理接口、后台页、默认值只留代码且节点热更新；试探只针对平台端点，所以设置放在质量模块内、平台一条记录，沿用现有模块内设置记录的形态。试探花的是平台的钱，预算和并发是成本控制参数，应由有审计的流程调整，不能固化在节点配置或代码里。平台一条记录而不是每站点一套：试探只针对平台端点，节点服务多个站点，按站点切分不会改变实际支出。默认值只写在 `DefaultProbeSettings()` 一处，记录只存偏离；空记录等于默认。修改周期或首次重试时，节点按上次检测时刻和结果重算已排定的下一次检测，不让新有效期先于旧排期生效。否决重启生效：同一设置的其他部分已经热更新，改一个预算要重启全部节点不可接受。代价是每个节点每 30 秒读一次库、启动时多一次读取；保存节点与消费节点对关系的判断可能不同，消费节点保留旧值并记日志 |
| H2 用模块自有的首个迁移、有界交接、条件更新与同事务持久告警 | 比纯内存状态多两张表，但重启不会放出坏端点，失败与重试可验证；不用缓存或逐请求共享窗口，调用路径不增加 I/O。按 [负责人 2026-10-28 的委托](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)「遇到问题自己解决问题和判断最优而不是问我。」落实现有设计，独立评审仍由流水线完成 |
| 计数和健康度按节点统计，不共享 | 共享就要在调用路径上访问缓存或数据库；按节点统计最坏是每个节点各自攒够失败，代价有界。共享的只有熔断与否和试探的认领，都是低频的状态变化 |
| 不试探站点和账户自带的端点，也不试探只有直接格式的平台端点；它们熔断后只作最后备选，真实请求成功即恢复，不自动离线 | 试探花的是 key 所有者的钱；embeddings、rerank 这类直接格式答不了生成题。没有不花钱的重新检测，就不能替它们下线：H3 的重置入口还没落地，自动离线会让一次短暂失败再也回不来。真实请求成功是它们能有的重新检测；有别的候选时不接流量，只有全部熔断时才作最后备选。熔断时通知所有者 |
| 独立来源按账户的所有者去重，超时只作辅助证据 | 同一个人开两个账户就能凑出两个来源；在低流量的推理模型上，长推理不用上游出错就能制造 60 秒没有内容。要求至少一个上游真正出错（5xx、传输错误、流中断），租户就不能只靠自己的请求摘掉端点 |
| 质量分由真实流量和试探的 EWMA 合成；未知用中性 1 加置信度 0 表示 | 产品里的"固定测评题成绩"要等主动检测（#313 E3-12），而排序现在就需要一个不来自自报的质量值；已测的可靠性、首字延迟和输出速度就够覆盖"快不快、稳不稳"。未知不记 0：0 分会让没测过的端点永久排在测过的后面（"最快"也遇到同一个问题），所以用中性 1 加置信度 0，排序另按"测过/没测过"分组。均衡的权重只乘质量分、不再另乘健康度，因为质量分已含健康度，乘两次会把失败重复计算。代价：真伪已由「真伪检测」单独给出，但质量分不含能力（固定测评题）和基准分，`Verified` 也不等于 Exacto 的完整语义 |
| 真伪检测用随机指纹题，由健康循环跑，官方基线留作第二层 | 比较过两种做法。**官方基线比对**（固定题库加每个模型版本的官方参考响应，Veridrop 式字段、协议、加密三级比对）证据最强，能测出同厂商内部的降级；但要先有官方账号或公开数据集（「待定问题」），题库、采样和版本管理是一整套后台数据，短期交付不了，`Verified` 会一直空着。**随机指纹题**用目录里作者的显示名作已知答案，随机串和随机算术每次生成，健康循环的真实生成通路、预算、退避和受控时钟都能复用，今天就能测出"是不是自称的那个厂商、输出有没有被改写、是不是真的在生成"。所以先落后者；官方基线有了以后再加一层，提高置信度、收紧 `:exacto` |
| 未知、未通过、假冒三态分开；一次矛盾就失败关闭，连续三次才判定假冒 | 三态对运营的含义不同：未知只是还没测，假冒要下线并退回映射。一次矛盾可能是模型答非所问，也可能是注入的系统提示，按上文"多次独立确认才判定假冒"不能据此下结论；但路由不该带着一次未解释的矛盾继续接 `:exacto` 流量，所以 `Verified` 立即为假，结论留在"未通过"，三次连续矛盾才记假冒并告警。代价：一次误判会让 `:exacto` 暂时没有端点，直到下一次通过 |
| `:exacto` 只路由到已验证端点，并按运营质量优先；没有已验证端点时回 503 `no_endpoint`（原因 `not_verified`） | OpenRouter 的 `:exacto` 是质量优先排序，信号是真实流量的工具成功率、吞吐、延迟和基准分（《Exacto》，2026-10-30）。Axiom 还没有基准分，工具成功率也只在有工具调用的流量里有；把 `:exacto` 映射成"只在已验证的端点上按运营质量优先"是能兑现的承诺：至少不会把服务别的模型的端点按质量排给用户。显式 `provider.sort` 仍覆盖它，是官方文档的原话。没有已验证端点时用 503 而不是静默回落到未验证的端点，与 OpenRouter 对"没有满足路由要求的供应商"的 503 一致（《Errors》，2026-10-30）；检测会重试，等待能修好，所以不是 404 |
| 真伪结果按节点保存，不落库 | 调用路径不查库是硬规则；检测默认每 6 小时一次，落库要新迁移、写器和跨节点采纳，属 H3/H5。重启后未知、`:exacto` 失败关闭，代价是一个部署周期内 `:exacto` 回 503，换来的是没有证据时不放流量进去。若 `:exacto` 的可用性成为问题，再按健康表的方式持久化 |
| 试探结果计入质量分和健康度，但不进熔断窗口 | 试探是一次真实生成，理应影响"这个端点现在多好"；但它由我们自己发出，不满足摘除所需的独立来源，所以只计分和恢复，不参与熔断判定 |
| 实测的能力与上限按配置绑定、按实测替换、不按时间过期 | [产品需求](../product.md#售卖形式)要求"实测不支持的端点，不参与路由"，[自动化](../product.md#端点属性)要求"检测后用实测值替换"：目录是基线，实测是端点当前的边界，所以能力、参数、上下文和输出上限有实测就用实测，更高也放行；只收紧会让目录的旧值盖住实测，做不成"替换"。检测走网关同一条协议，测到的能力就是请求表达得出来的；误判的风险由多次独立确认和检测的判定规则承担。结构事实不会随时间恢复，按时间过期会把实测证明做不了的请求重新发过去；后来的检测可以翻转它，绑定的目录模型、上游名字和格式任一变化也会立即作废，旧上游的结论不会落到新上游。事实不落库、按节点保存，与健康度一致，调用路径不查库；发布靠每 5 秒的快照重建，不重启、不加表或对外字段 |

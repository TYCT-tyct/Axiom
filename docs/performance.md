# 性能

网关自身有多快、能扛多少、怎么保证不退化。目标数字见[总体架构的「底线指标」](architecture.md#底线指标)，调用经过哪些步骤见[总体架构的「一次调用怎么走」](architecture.md#一次调用怎么走)。页面的加载和响应指标见[前端与设计](frontend.md#前端性能指标)。

## 要求

- 达到底线指标：网关自身增加的首字延迟 p95 不超过 30ms；单个核心节点至少同时处理 5000 路流式调用。
- 每条性能规则都有对应的基准测试、压测或线上指标来检验，不靠口头约定。

## 设计

### 延迟预算

把 30ms 的总目标拆到每个环节，每次改动都有可对照的数字。下表是 p95 预算，不含节点之间和到上游的网络传输，也不含上游自身的耗时。

| 环节 | 预算 | 怎么做到 |
|---|---|---|
| 入口转给核心 | 1ms | 节点之间保持长连接，不重新握手 |
| 认站点和 key、读取请求、定规则、路由 | 2ms | 全部查内存，key 缓存未命中时才查库；读字段只扫描一遍请求体（见下文）。同格式改写复用读字段时的位置表，不再重复扫描未改写内容；大请求的纯 CPU 读取与改写使用下表分级预算（见 [gateway 模块的「性能估算」](../internal/gateway/README.md#性能估算)） |
| 限流和会话粘性 | 2ms | M1 在进程内；M2 合并成一次缓存往返 |
| 准入：核对 key 并预留第一段 | 5ms | 同一账户的并发请求合并成一个事务：单请求仍是 7 次往返（一个事务；锁、持有者、读计数、兜底价和写入的固定部分按批摊薄），分解见 [billing 的「同一账户的合并预留」](../internal/billing/README.md#同一账户的合并预留)；数据库与核心必须在同一机房（估算见 [gateway 模块的「性能估算」](../internal/gateway/README.md#性能估算)）；待实测 |
| 出口向上游发出请求 | 2ms | 复用与上游的长连接，不重新握手 |
| 转发首个字节 | 1ms | 收到就转发，不攒批 |
| 合计 | 13ms | 余下的留给排队和垃圾回收 |

读取与同格式改写的 CPU 预算按体积分级，包含 `Inspect` 和 `Prepare`，不含客户端上传、数据库、网络或跨格式转换。普通请求保留 2ms；超过 256 KiB 后按每 MiB 8ms、向上取整计算：

| 请求体 | `Inspect` + `Prepare` CPU 预算 |
|---|---|
| ≤ 256 KiB | 2ms |
| > 256 KiB、≤ 1 MiB | 8ms |
| > 1 MiB、≤ 4 MiB | 每 MiB 8ms；4 MiB 为 32ms |
| > 4 MiB、≤ 16 MiB（入口上限） | 每 MiB 8ms；16 MiB 为 128ms（线性外推，仍需压测） |

理由：共享 CI 服务器上 1 MiB 的严格摘要本身约 3–4ms，4 MiB 约 12–17ms；复用位置后两步合计约 3.9–5.1ms、14.9–18.8ms，较优化前降低约四成（各格式前后数据在 gateway 的性能估算）。8ms/MiB 为重复键、UTF-8、深度校验和一次输出拷贝留余量，保留线性上界，不以取消校验换速度。`BenchmarkRequestRead` 在 1 KiB、256 KiB、1 MiB、4 MiB 的三种格式上报告 `budget-ns/op` 与 `%-budget`，对照此表的五轮中位数，并保留每轮结果；超过 100% 要分析，绝对耗时仍按「怎么验证」只报告、不在共享机器上判失败。`BenchmarkInspect`、`BenchmarkPrepare` 分别定位成本，分配次数仍由 merge-base 对比硬性守住。大型请求的 CPU 预算可能超过 30ms，不能视作全调用 p95 目标已经达成；总体目标保持不变，仍由包含大请求比例的压测验证。

### 主要操作的耗时

| 操作 | 耗时与什么成正比 |
|---|---|
| 认 key、限流、会话粘性 | 常数 |
| 路由 | 该模型的候选端点数，通常几十个 |
| 读取请求字段 | 请求大小，扫描一遍 |
| 同格式改写 | 输出大小，复用顶层位置、分段拷贝；只解析要改的值 |
| 流式转发与格式转换 | 每段数据的大小，不随回复总长度增长 |
| 快照重建 | 端点和规则的总数，在后台进行 |
| 后台任务 | 新增的数据量 |

### 调用路径上的规则

- **请求体不整体解析，严格扫描的位置复用**：`Inspect` 按 token 完整检查一次，保留重复键、UTF-8 和深度检查，并只给有限的顶层改写成员记录位置。`Prepare` 复用位置，只解析要改的值，其余内容按段拷贝；表不随消息数或未知顶层成员数增长，也不借用 body（[protocol 的「同格式改写」](../internal/protocol/README.md#同格式改写)）。回放候选先清理转换产物、位置可能失效，沿用 tokenizer 改写。跨格式转换解码规范模型；旧版 Chat 同格式请求也在 `Inspect` 发现旧声明或旧消息时解码同一规范模型，以共用调用 ID 配对，再按原文字节改写外壳，额外工作集计入 `PrepareCost`（[protocol 的「旧版函数调用」](../internal/protocol/README.md#跨格式转换)）。普通现代请求不走这个分支，不增加分配次数。`TestAllocs` 检查 Inspect 减去 jsonx 校验的分配次数不随体积增长，Prepare 在普通和宽对象请求上自身分配次数恒定。编程工具的长历史可达数 MB，省去第二遍完整解析后仍受单次严格检查的线性 CPU 成本限制，所以采用上面的分级预算。
- **预留按字节上界，缺输入用量时有界分词暂估**：预留仍用 `InputBound` 的字节上界；仅在上游未报告任何输入侧用量的尝试结束后、`Router.End` 释放端点后计数，同一会话每个已知族最多一次。顺序扫描只解码字符串值，不数 JSON 键、外壳和不透明数据；每族最多解码/分词 256 KiB 原始字符串，余量按 4 字节 1 个 token 补齐，JSON 扫描仍随请求大小线性增长。BPE 每段最多 1 KiB，缓冲复用；未知族或失败保留字节比例，已报告用量不覆盖。首轮准入、流转发及已有输入报告的结算不运行分词器；缺输入报告时，计数仍占用会话/账户名额，并增加结算尾延迟；失败发生在回退之前时，下一次尝试的首字也会被推迟。端点先释放及字节预算只限制开销，不证明异常路径满足总体 p95 30ms 目标，仍需压测验证。2026-10-21 UTC 的 CI 服务器实测（Linux/amd64、Go 1.27.2、Xeon Gold 6262V 1.90GHz，共享负载，`GOMAXPROCS=1 GOGC=off`、20 次）：`BenchmarkInputTextEstimate` 的 1 KiB 英文为 0.539ms、58130 B、1146 次分配；256 KiB 英文为 76.1ms、14829382 B、293341 次分配，不间断文本为 441.6ms、6412822 B、2569 次分配。1 MiB 的两种文本各只再多一次分配（余量不再分词，但扫描及墙钟仍会增长）；缓存命中 122ns、0 B、0 次分配。时间是微基准均值而非 p95 或硬时限，分配门槛不豁免；`BenchmarkTextCount` 同时记录每 KiB 分词成本。两份词表在核心节点接收请求前预热：隔离进程三次中位数约 182ms、常驻堆 10.00 MiB，体积与测量口径见[计费决策表](domains/billing.md#决策与理由)。
- **输出的形状在转发时统计**：每个按解码字节计的字符串顺带统计十类特征（`textshape.Shape`），一遍、不分配，ASCII 查表、中日韩统一表意文字和中文标点先按区段判断；`BenchmarkShapeAdd` 在本机（AMD EPYC，共享负载，2026-10-29）为英文约 2.0 µs/KiB、中文约 4 µs/KiB、代码约 2.0 µs/KiB，0 次分配。它每次调用都跑（是否会报输出要到流结束才知道），换来不报输出时不必留存回复文本。Claude 两族的输入同样按形状估，不加载词表，同一会话每族一次。
- **快照预先算好**：路由候选按模型预先分组，每个候选的成本和适用的定价规则在快照重建时整理成查找表，请求时只查表计算售价，再在候选中加权挑选。快照在后台建好后整体替换，请求不等待、不加锁。
- **每个请求最多同步访问一次缓存**，在准入之前，只取限流计数和会话粘性；排队醒来不再访问；端点负载等其余共享状态在进程内（见[路由的「容量感知」](domains/routing.md#容量感知)）。
- **流式边收边转发**：每收到一段数据就处理并转发，用量随事件累加，格式转换也逐段进行，不攒完整回复。每路流的缓冲有上限，按"5000 路 × 每路上限"核算节点内存；缓冲区复用，减少垃圾回收。
- **与上游的连接预先建好**：出口为活跃的端点保持长连接；需要新建连接的请求单独计数，作为连接复用率的指标。
- **记一次指标不分配内存**：标签组合的选项按组合缓存，组合第一次出现时建一次（有界，一次性的开销），之后稳态下记一次不分配；跨度只在被采样时构造属性，默认没有导出器、没有跨度被采样，所以事务和出站请求不为属性付分配。`BenchmarkRecord`、`BenchmarkRequestTelemetry`、`BenchmarkTransactionSpan`、`BenchmarkEgressSpan` 由基准对比守住（[platform 的「遥测」](../internal/platform/README.md#遥测)）。

### 后台与数据

- 调用记录批量写入，不逐条插入。
- 数据库连接预算按服务器的 `max_connections`、预留槽位和部署节点数在启动时算出，其中留出完成类预留；后台、控制台和准入共用有界普通池，不能借用结算预留，装不下就不启动。公式、默认值和多节点总量计算由 [platform 的连接池](../internal/platform/README.md#连接池)统一定义。
- 控制台和接口里的统计查按小时、按天预先汇总的表，不扫描明细。
- 列表一律按游标翻页，不用"跳过前 N 条"，每页条数有上限。
- 大表上的每个查询都必须走索引；慢查询记日志并告警。
- 后台任务从上次处理到的位置继续，只处理新增的数据：额度分配的重放、对账、分析标签都不全量重算。

用户提醒 journal 每次余额实际变化新增一行；每分钟任务最多运行 30 秒。每批最多 1000 行，billing 一条 DELETE RETURNING、accounts 一条 INSERT SELECT 完成消费和转换；再以一条带偏好的查询读取最多 100 条待派发提醒。无提醒时往返数不随 journal 行数增长，另有开始、范围与提交的固定成本。仅两条转换语句的网络成本在 r=0.25–0.4ms 时每千行约 0.5–0.8ms；这是网络下界，不包括数据库执行、提交、连接竞争与实际邮件/Webhook 入队，也不是吞吐保证。按 50% 运行占比，若全平台每秒产生 λ 行，运行期间至少需处理 2λ 行/s；上线容量仍须按实际 journal 最旧记录与行数变化、派发积压和数据库负载测定。达到预算正常完成，下分钟续消费，不触发失败重试；Webhook 收尾和保留期清理每轮只跑一次，不随批次数重复。`TestBalanceNoticeConsumptionIsBoundedAndBatched` 与 `TestBalanceNoticeBatchResolvesEachTenantAndDefaults` 守住批量和集合判定，`TestUserNoticeRunDrainsWithoutBalanceJournal` 守住无账本事件时的派发积压。

### 规模与扩展

- 入口、核心、出口都不存数据，加机器即可横向扩展。
- 最终的瓶颈是主数据库。应对顺序：调用路径只在预留和结算时写库，转发中按段追加预留，写库次数随段数而不是事件数增长；调用记录批量写入；热点账户把同一账户的并发准入和完成按批合并提交，仍在最后一个事件之前落库（见[计费的「热点账户」](domains/billing.md#预留与结算)）；再大就按账户分库，模块接口不变。
- 每个请求的数据库往返：准入约 7（单请求；批内固定部分摊薄）+ 每段追加 9（目标已被覆盖时 6）+ 结算约 5（一次尝试的成本、写尝试、收费、计数与终态、`EndRequest`；锁、读预留、开始和提交按批摊薄，单请求仍是 9；每多一次尝试多 1），随段数增长，不随事件数增长；不可分段的请求不追加。同一账户的并发请求按批合并，这些往返按批摊薄，单请求的上限不变；批量的顺序与单语句写入边界见 [billing 模块](../internal/billing/README.md#同一账户的合并预留)。
- 热点账户：数据库余额行锁内，一个准入批次（最多 32 个）为每个请求读一次计数、写一次预留，锁、栅栏、兜底价、数据库时钟以及开始和提交每批各一次；一个完成批次（最多 16 个）为每个请求锁余额、读预留、写尝试成本、收费、计数和预留终态；锁的等待每批只发生一次，语句仍按请求。网关账户闸还包住取连接、开始和设范围，估吞吐必须算整批持闸时间，不能只算余额行锁。设往返 r、提交 c、批大小 B、每个请求自己的数据库执行 e，一个准入批次的固定开销 f ≈ 5r + c（开始、提交、连接、锁等待和每批一次的查询），占闸 T ≈ f + B·(r + e)，摊到每个请求约 f/B + r + e；完成批的固定部分只有开始、提交和一次锁等待，按请求的语句不变；B = 1 时回到 f + r + e，就是没有摊薄时的固定开销加每个请求自己的语句。取 r = 0.25–0.4ms、c ≈ 0.5ms，B = 16 时固定部分每请求约 0.11–0.16ms，另加 r、e、连接等待、Go 与数据库调度和内存计算；余额行的数据库执行仍是瓶颈。这是低负载下的容量估算，不是共享机器的保证；实测必须同时报告负载、批大小和整批持闸时间（见[计费的「热点账户」](domains/billing.md#预留与结算)）。
- 容量数字以压测结果为准，压测后写入本节。

### 怎么验证

- **基准测试**：调用路径上的关键函数（读取请求字段、格式转换、路由挑选、价格计算）都有基准测试，CI 与 `main` 对比。内存分配次数的结果稳定，增加就判失败；耗时在共享的 CI 机器上波动大，变慢只提醒。基准测试和单元测试都不按墙钟的绝对值判失败（机器被别的任务占满时会随机失败）；复杂度用同一次运行里两个规模的最快耗时之比来守，例如路由的 `TestPlanScales`（候选数乘 32，耗时之比超过 96 即失败，能抓住变成平方的退化）。上文「延迟预算」里的墙钟预算由下面的压测验证。所有基准用同一条规则，没有按名字的例外：每次运行都跑同一个固定的迭代次数（`-benchtime 20x`），关掉垃圾回收并固定在一个处理器上（`GOGC=off`、`GOMAXPROCS=1`），比较 `-count 6` 次运行里分配次数的最小值，并容许基数的千分之一（向下取整，所以不足 1000 的基准必须完全相等）。allocs/op 是一轮的总分配除以迭代次数并向下取整，所以每轮运行的一次性开销（testing 包在每轮之前做的那次回收清空缓冲池，下一轮的第一个迭代再把它建起来）除以同一个迭代次数，在 base 和 head 上相消；固定次数是因为按时长定迭代数时，迭代次数会随机器快慢走，服务器满载时 64 KiB 的 `Aggregate`、`Relay` 每轮只跑两三次，同一份代码读到的 allocs/op 比长跑多 1 到 6，而 base 和 head 相隔几分钟、负载不同，没碰基准代码的 PR 也会失败。关掉回收、固定一个处理器，是因为回收会清空缓冲池、换处理器就换一组池，池都要在下一轮的第一个迭代里重建，这笔开销按每次操作记，迭代再多也摊不掉：`Aggregate/chat/deltas=16/size=65536` 在 5 到 50 个迭代、每次六遍的八次调用里读到 583–585，关掉回收后 10、20、50 个迭代共九次调用都读到 575 或 576；`Convert/format=1/turns=4` 在八个处理器下五次调用有两次读到 430，一个处理器下五次都是 429。`Relay` 的基准早就按同样的道理把两者收在计时区间之外（`internal/protocol/relay_meter_test.go`）。关掉之后只剩每轮之前那次回收，除以固定的迭代次数后相消；容差仍然保留，因为一轮自己的分配除以迭代次数后仍可能正好让一侧多读一次，最小值滤不掉每轮都付的那部分。每个事件多分配一次的退化会多出几十到几百次，远超容差，精度要紧的小基准容差为 0。CI 服务器由多个作业共用，但基准不用锁排队：一个 `go test` 即使给了 `-p`，也会让基准包一个接一个跑（cmd/go 强制基准串行），所以门槛给每个基准包单独起一个 `go test`，base 和 head 同时测、共用同一条上限同时跑四个（`-p 4` 让构建也并行，与 `just test` 的上限相同）；每个测试二进制仍只用一个处理器、关掉回收，同时运行的作业只争处理器时间，不改变分配次数；关掉回收时最重的 protocol 包峰值约 530 MiB。基准的分配次数只取决于编进测试二进制的东西，所以每个基准包先读它的测试导入闭包（`go list -deps -test`）：base 与 head 的 merge base 到工作树之间的改动落在闭包里某个包的目录或它下面（testdata、嵌入的文件都在包的目录里）才测这一包；`go.mod`、`go.sum`、`go.work`、仓库根的 `justfile`、`.github/workflows/ci.yml`、`.github/actions/setup/` 下的文件或 `tools/benchgate/` 下的文件变了则全测，因为它们决定每个包怎么解析、编译，或基准在什么工具链、参数、环境下跑、怎么比较，没法归到某一个包。两侧都跳过的包不比较，也不算删除；跳过的包和原因打印在日志里。
- **压测**：用模拟上游，可以设定首字延迟、输出速度、长达十几分钟的流和随机断开。场景包括：
  - 单个核心节点 5000 路并发流；
  - 突发的大量新请求，以及大批客户端同时取消；
  - 数 MB 的大请求；
  - 单个账户的大量并发（热点账户），以及它的 200 路同时用到半段、追加时等锁；
  - 冷 key 的洪峰叠加热点账户的结算；
  - 数据库中断 30 秒和 150 秒；
  - 数据库主备切换。

  分别报告首字延迟、排队、结算的尾延迟（目标 p95 10ms）和峰值内存。

  每个里程碑结束前跑一次，正式上线前必须达到底线指标。

  **跑法**（代码在 `cmd/axiom/load_*_test.go`，构建标签 `load`，不进 `just check`）：`just load [比例] [场景]`，在 CI 服务器上经 `remote-check.sh <worktree> load` 跑，约 12 分钟，机器被占满，不与别的任务同时跑（CI 服务器是共享的，跑之前看一眼负载，结果里记着机器的忙碌程度）。比例小于 1 时数量和时间一起缩小，用来在小机器上试跑；场景是名称的匹配模式（如 `^1_`），只重跑匹配的场景。结果表打在最后，贴进 PR 描述，数字不写进文档。

  **做法**：
  - 每个场景起一个独立的节点进程（同一个测试二进制再运行一次），内存是节点自己的；模拟上游、客户端和数据库代理在测试进程里。
  - 客户端从 16 个回环地址发起（节点对单个地址限 500 路），50 个账户分摊（单账户限 500 路）；热点账户用同一账户的 20 个 key（单个 key 每分钟限 6000 次）。种子数据里的供应商并发上限从 4 调到 10 万、模型的上下文调到 400 万 token，让 5000 路和数 MB 的请求进得来。
  - 数据库场景里节点经一个 TCP 代理连库，切断就是关掉全部连接并拒绝新的，共享的集群不动；代理多出的两跳计入该场景的全部数字。
  - 每个场景结束后机械检查：没有 pending 的预留（钱都还回来了）、账本平衡、扣费等于做完的调用应得的数（没做完的在 0 到预留之间）、节点还活着、再接一次小请求和一次 4 MiB 请求（名额和内存都还了）、正常关闭。违反的算失败，不只是表里的一个数。

  **口径**：
  - 首字延迟开销 = 客户端收到第一个字节的时间 − 上游自己用的时间（上游记下收到请求和写出首字节的时刻），即网关加的部分（模拟上游的首字是第一个内容事件：网关要等到有内容才放出流）；
  - 结算尾延迟 = 上游写出最后一个事件到客户端收到它：成本在最后一个事件里，网关扣着它直到结算提交（[gateway 的 I3](../internal/gateway/README.md)），所以这段是结算加它前面的排队；
  - 排队 = 节点以 429/503 挡回的数量、首字开销超过 1 秒的数量、结尾带"费用待定"的数量；
  - 峰值内存 = 节点进程常驻内存的峰值减去就绪时的。

  **与上面场景的差异**：
  - 长流 100 秒而不是十几分钟（CI 机器共享，整个压测要在 20 分钟内），事件每 250ms 一个，比真实上游稀；5000 路在 40 秒内陆续到达（每秒 125 个新流），每秒 500 个以上的到达速度会被账户闸和准入挡回，那是另一个场景（突发）的内容；
  - 客户端、上游、数据库和节点在同一台机器上，数字含它们争抢处理器的部分，是上界；
  - 模型规格还没有最快输出速度，条目都不分段预留（[#229](https://github.com/TYCT-tyct/Axiom/issues/229) 的接线已在，等模型数据），没有"追加时等锁"，场景 4 用 200 路在同一刻结束，结算按账户成批在同一把锁上排队；
  - M1 没有备库，主备切换不跑。
- **线上**：每个请求都按上表的环节记录网关自身的耗时，作为指标展示并告警（见[记录与告警的「监控与告警」](domains/observability.md#监控与告警)）；持续采集 CPU、内存和锁等待的剖析数据，保存在运维节点。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 总目标拆成每个环节的预算 | 只有总目标时，任何一处变慢都难以定位；拆开后每次改动都有可对照的数字 |
| 请求体不整体解析 | 编程工具的请求可达数 MB，透传只需要其中几个字段；整体解析再拼装的开销随请求大小增长，是调用路径上最大的一项 |
| 预留保持字节上界，缺输入用量的暂估允许有界本地分词 | 按 [#203](https://github.com/TYCT-tyct/Axiom/issues/203) 改进字节规则对中文等语料的误差；首轮准入/流转发不分词，但回退首字及结算尾部会增加延迟；端点先释放、同一会话每族只做一次，256 KiB 字节预算及 1 KiB BPE 段限制尾部 CPU，余量保留字节估计；扫描依然 O(请求大小)。256 KiB 实测英文 76.1ms/293341 次分配，不间断文本 441.6ms/2569 次分配，缓存 0 次分配；词表只在启动构建一次（两份合计约 182ms、10 MiB 堆，最小测量程序的剥离二进制增加 9.02 MiB）。成本只在缺输入报告时按族发生且不随回退次数重复，换取中文等语料比字节规则更合理的暂估；并非异常路径的 30ms 保证，预留的保守上界不变 |
| 内存分配次数作硬门槛，耗时只提醒 | 共享 CI 机器上的耗时波动大，作硬门槛会频繁误报；分配次数稳定，而且在 Go 里是耗时和垃圾回收压力的主要来源 |
| 压测用模拟上游 | 真实上游费钱、不稳定、无法控制；模拟上游能复现长流、断开、慢速输出等边界情况 |
| 同一账户的资金写入按批合并，不逐请求提交 | 热点账户的瓶颈是每请求的 BEGIN、COMMIT、连接和锁等待；按批合并把它们摊薄，同时保留余额行作为唯一串行点、锁后新快照和请求 ID 幂等重试。没选逐请求提交：热点账户的尾延迟随排队线性增长（#296、#304）；没选把排队放进数据库等锁：每个等待的请求占一条连接。其他比较见[计费的决策表](domains/billing.md#决策与理由) |

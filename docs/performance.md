# 性能

网关自身有多快、能扛多少、怎么保证不退化。目标数字见[总体架构的「底线指标」](architecture.md#底线指标)，调用经过哪些步骤见[总体架构的「一次调用怎么走」](architecture.md#一次调用怎么走)。页面的加载和响应指标见[前端与设计](frontend.md#前端性能指标)。

## 要求

- 达到底线指标：网关自身增加的首字延迟 p95 不超过 30ms；单个核心节点至少同时处理 5000 路流式调用。
- 每条性能规则都有对应的基准测试、压测或线上指标来检验，不靠口头约定。

## 设计

### 延迟预算

把 30ms 的总目标拆到每个环节，每次改动都有可对照的数字。下表是 p95 预算，不含节点之间和到上游的网络传输，也不含上游自身的耗时。

| 环节 | 预算 | 怎么做到 |
|---|---|---|
| 入口转给核心 | 1ms | 节点之间保持长连接，不重新握手 |
| 认站点和 key、读取请求、定规则、路由 | 2ms | 全部查内存，key 缓存未命中时才查库；请求体只扫描一次（见下文） |
| 限流和会话粘性 | 2ms | 合并成一次缓存往返 |
| 预留第一段 | 5ms | 一条带条件的更新，数据库与核心在同一机房 |
| 出口向上游发出请求 | 2ms | 复用与上游的长连接，不重新握手 |
| 转发首个字节 | 1ms | 收到就转发，不攒批 |
| 合计 | 13ms | 余下的留给排队和垃圾回收 |

### 主要操作的耗时

| 操作 | 耗时与什么成正比 |
|---|---|
| 认 key、限流、会话粘性 | 常数 |
| 路由 | 该模型的候选端点数，通常几十个 |
| 读取请求字段 | 请求大小，只扫描一次 |
| 流式转发与格式转换 | 每段数据的大小，不随回复总长度增长 |
| 快照重建 | 端点和规则的总数，在后台进行 |
| 后台任务 | 新增的数据量 |

### 调用路径上的规则

- **请求体只扫描一次，不整体解析**：格式相同时，只取出模型、是否流式、最大输出等少数字段，原地改写模型名后转发；只有需要转换格式时才完整解析。编程工具的请求带着完整的对话历史和工具定义，上下文长时达到数百 KB 乃至数 MB，整体解析再重新拼装会成为最大的开销。
- **输入按字节数计，不运行分词器**：预留用上界，文本 token 数不超过字节数（见[计费的「预留与结算」](domains/billing.md#预留与结算)）；暂估用估计，输入 token 数按请求字节数乘以按模型从历史调用统计出的换算比例。精确计数只用于 `count_tokens` 这类需要它的接口。
- **快照预先算好**：路由候选按模型预先分组，每个候选的成本和适用的定价规则在快照重建时整理成查找表，请求时只查表计算售价，再在候选中加权挑选。快照在后台建好后整体替换，请求不等待、不加锁。
- **每个请求最多访问一次缓存**：限流计数和会话粘性在一次往返里完成。
- **流式边收边转发**：每收到一段数据就处理并转发，用量随事件累加，格式转换也逐段进行，不攒完整回复。每路流的缓冲有上限，按"5000 路 × 每路上限"核算节点内存；缓冲区复用，减少垃圾回收。
- **与上游的连接预先建好**：出口为活跃的端点保持长连接；需要新建连接的请求单独计数，作为连接复用率的指标。

### 后台与数据

- 调用记录批量写入，不逐条插入。
- 控制台和接口里的统计查按小时、按天预先汇总的表，不扫描明细。
- 列表一律按游标翻页，不用"跳过前 N 条"，每页条数有上限。
- 大表上的每个查询都必须走索引；慢查询记日志并告警。
- 后台任务从上次处理到的位置继续，只处理新增的数据：额度分配的重放、对账、分析标签都不全量重算。

### 规模与扩展

- 入口、核心、出口都不存数据，加机器即可横向扩展。
- 最终的瓶颈是主数据库。应对顺序：调用路径只在预留和结算时写库，转发中按段追加预留，写库次数随段数而不是事件数增长；调用记录批量写入；结算按账户批量入账；热点账户把几毫秒内的预留和结算合并成一次提交（由压测决定启用，见[计费的「预留与结算」](domains/billing.md#预留与结算)）；再大就按账户分库，模块接口不变。
- 容量数字以压测结果为准，压测后写入本节。

### 怎么验证

- **基准测试**：调用路径上的关键函数（读取请求字段、格式转换、路由挑选、价格计算）都有基准测试，CI 与 `main` 对比。内存分配次数的结果稳定，增加就判失败；耗时在共享的 CI 机器上波动大，变慢只提醒。
- **压测**：用模拟上游，可以设定首字延迟、输出速度、长达十几分钟的流和随机断开。场景包括：
  - 单个核心节点 5000 路并发流；
  - 突发的大量新请求，以及大批客户端同时取消；
  - 数 MB 的大请求；
  - 单个账户的大量并发（热点账户）；
  - 数据库主备切换。

  每个里程碑结束前跑一次，正式上线前必须达到底线指标。
- **线上**：每个请求都按上表的环节记录网关自身的耗时，作为指标展示并告警（见[记录与告警的「监控与告警」](domains/observability.md#监控与告警)）；持续采集 CPU、内存和锁等待的剖析数据，保存在运维节点。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 总目标拆成每个环节的预算 | 只有总目标时，任何一处变慢都难以定位；拆开后每次改动都有可对照的数字 |
| 请求体不整体解析 | 编程工具的请求可达数 MB，透传只需要其中几个字段；整体解析再拼装的开销随请求大小增长，是调用路径上最大的一项 |
| 输入按字节数计 | 分词器的耗时与请求大小成正比，还要按模型加载词表；字节数直接给出上界，暂估只需要按比例估计，差额在校正时修正 |
| 内存分配次数作硬门槛，耗时只提醒 | 共享 CI 机器上的耗时波动大，作硬门槛会频繁误报；分配次数稳定，而且在 Go 里是耗时和垃圾回收压力的主要来源 |
| 压测用模拟上游 | 真实上游费钱、不稳定、无法控制；模拟上游能复现长流、断开、慢速输出等边界情况 |

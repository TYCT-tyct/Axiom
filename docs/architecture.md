# 总体架构

系统怎么分块、怎么部署、一次调用怎么走，用什么技术，以及所有模块共同遵守的工程原则和底线指标。概念的叫法见[术语与核心概念](glossary.md)，产品要求见[产品需求](product.md)。

## 整体形态

模块化单体：一个代码库、一个程序，内部按模块严格分界，按节点角色启动。以后某个模块需要独立部署，因为边界清楚，可以直接拆出。

## 部署拓扑

每台运行 Axiom 的机器是一个节点。所有节点跑同一个程序，后台为每个节点配置它承担的节点角色：

| 节点角色与职责 | 做什么 |
|---|---|
| 入口 | 就近接住用户连接、完成 TLS 握手，再转给核心 |
| 核心 | 鉴权、路由、计费、存数据；管理监听按设计只在核心上 |
| 出口（职责，不是第四种节点角色） | 向上游发请求 |
| 运维 | 运行运营 agent、监控与告警、通知中心、部署与节点管理 |

- **单机起步，随时加节点**：只有一台机器时它兼任全部节点角色；扩展时加机器、分配节点角色，不改代码。节点、节点角色、线路都是后台数据。现状：`serve` 还没有节点角色配置，每个节点兼任全部节点角色，管理监听也每个节点都开。
- **入口先做薄层**：鉴权、路由、计费都在核心，状态只有一份。以后某个地区用户多了，可以让当地入口节点也承担核心职责，预留余额改为各区域预领额度，调用方不用改。
- **入口到核心**：用 HTTP/2，每对节点之间保持多条长连接，避免一条连接丢包拖慢所有流；实测跨境丢包严重时再改用 HTTP/3（QUIC）。入口持有证书私钥、能看到明文，所以只部署在我们自己控制的机器上。二级站点自定义域名的证书自动签发并分发到入口，细节在控制台设计中确定。
- **运维节点**：正式上线时放在另一家云服务商的机器上，与主服务器分属不同的故障域；它通过只对运维节点开放的节点管理接口（查看状态、摘除流量、重启、升级）管理其他节点。核心节点检测它的心跳，外部的在线监测服务也盯着它。
- **节点之间的安全**：节点之间的调用一律走双向 TLS，跑在 TCP 上（跨境线路常对 UDP 限速）。新节点用一次性令牌注册，由核心的内部证书机构签发证书并自动轮换。数据库和缓存只在核心所在区域的内网开放。
- **路由同时选端点和出口**：出口可以是承担出口职责的节点，也可以是外部代理。选择依据是实测的节点之间、出口到供应商之间的延迟和成功率。
- **出口的价值不在缩短距离**，而在于：
  - 满足供应商的地区限制：Anthropic 和 OpenAI 都不支持中国大陆、香港、澳门（Anthropic《Supported Regions Policy》、OpenAI《Supported countries and territories》，2026-10）；
  - 让跨境流量走我们自己控制的优化线路；
  - 与上游保持长连接，省去每次请求的握手；
  - 给号池账号和在意来源 IP 的中转站提供固定 IP。
- **核心放在哪里是部署选择，不影响代码。**第一版不在中国大陆放节点，国内用户经香港等地的入口节点和优化线路接入。

## 模块划分

模块与代码目录一一对应，除 protocol 和 platform 外也与[领域文档](README.md#文档怎么组织)一一对应：protocol 的行为要求在 [gateway](domains/gateway.md) 和它的模块 README，platform 的在它的模块 README。术语表里的业务概念各归一个模块管，见下表；platform 的值类型对应的概念见表后。

| 模块 | 负责什么 | 管哪些概念 |
|---|---|---|
| gateway | 三种调用格式的入口、API key 鉴权、限流、流式输出、中途出错的处理；节点注册、节点角色的启动和节点之间的传输 | 请求、尝试、节点、节点角色、入口、核心、出口、运维 |
| protocol | 各调用格式之间的转换，格式相同时透传 | 调用格式、能力 |
| routing | 按预设、能力、归属方筛选端点，选出口，排序、回退、会话粘性 | 预设、回退路线、会话粘性 |
| catalog | 模型与名字、规格和参考价的来源与录入、价目表结构 | 模型、模型厂商、公开名字、内部名字、版本依据、目录基线、价格来源、参考价、价目表、计费项、上下文分档、服务等级、用量 |
| suppliers | 供应商、分组、凭证、端点、代号；适配器、同步、名字映射、挑选凭证、调用上游；号池是其中一种实现 | 供应商、归属方、分组、代号、凭证、端点、适配器、声明式适配器、同步、供应商别名、成本计划 |
| quality | 检测、指纹、线上观测，把各种依据合并成端点属性；节点和出口的线路测量 | 端点属性、依据、来源、指纹、检测 |
| billing | 按定价规则算出售价（M1 是参考价 × 站点倍率或固定价，逐层加价随成本侧一起来）；预留、结算、账本、币种、对账 | 成本、售价、加价、账本、预留、在途预留、持有者、对账键、余额底线、暂估费用、资金来源、额度、额度批次、价格版本、汇率、免单 |
| payments | 收款渠道、订单、退款，结果记入账本 | 收款渠道、订单 |
| accounts | 站点、用户、账户、成员、工作区、API key、等级、登录；操作者的授权（权限、角色、范围）；平台 → 站点 → 等级 → 账户 → 工作区 → API key 的配置链；准入事务（打开事务、核对 key、交出当前设置；限额检查与预留由 gateway 在回调里调 billing 完成） | 站点、站长、管理员、用户、认证因素、会话、账户、成员、工作区、API key、管理 key、等级、操作者、权限、角色、范围、准入 |
| operations | 运营接口（含 MCP 工具）；风险分级与审批（含 AI 审批）、额度上限、审计的检索与回放；运营 agent 的接入与模型代理；部署与节点管理；权限判断调用 accounts 的授权 | 审批策略 |
| observability | 调用记录、对话内容的保存与清理、指标、告警、通知渠道 | 调用记录、通知渠道、受控导出 |

另有两块不承载业务规则：`platform` 是基础设施（数据库、加密、日志、审计日志、出站客户端、JSON、配置、遥测、HTTP 服务、前端文件、幂等键、ID 写法；缓存已设计、尚未实现，事件尚未实现）、由 `api/` 生成的接口契约（控制台接口的类型和 `StrictServerInterface` 在 `platform/consoleapi`，由 `cmd/axiom` 实现），以及跨层使用的值类型：金额（最小单位的整数）、单价（精确小数）、被下层引用的实体 ID，只有类型和运算，不放业务规则。术语表里对应的概念归 `platform`：审计日志、租户范围、请求 ID、尝试序号、币种、单价、精确金额、金额；`web` 是前端，包括官网、按站点域名换品牌的用户控制台和管理后台。

## 模块边界规则

1. **每个模块只读写自己的数据表**，其他模块通过它的公开接口访问，不直接查它的表；模块之间不建数据库外键，只按 ID 引用。
2. **跨模块的后续动作用事件**：事件与数据在同一个事务里保存，提交后才发出，不会丢失。处理事件的一方必须能承受同一事件收到多次。唯一的另一种做法是定期比对状态，只在三个条件同时成立时用：处理方只需跟上最新状态，不需要每次中间变化；被比对的状态带版本号，处理方记下用过的版本；处理方的领域文档写明比对周期和最长滞后。目前只有 billing 跟上官方价这样做（见[计费的「定价」](domains/billing.md#定价)的自动重算）。
3. **调用路径上不查数据库，只有四个例外**：准入（核对 key 并预留余额）和转发中追加预留；回答结束前的结算；API key 缓存未命中；M2 的 Responses 续接按工作区和回复 ID 读一次会话状态（见[接入与对外接口的「Responses 的会话状态」](domains/gateway.md#responses-的会话状态)），读不到就当作没有这个回复，不重试、不扫描。花费上限、预算这些值由 accounts 经准入结果传入，计数、占用和检查都在 billing，在账户余额行的锁下进行。其余所需数据都在核心内存里：
   - 路由[快照](glossary.md#术语表)：端点、属性、价格、预设、配置；
   - API key 缓存：(站点, key 的哈希) → key、账户、工作区的标识，这些创建后不会变。

   快照按固定周期重建（账户 30 秒，目录与路由 5 秒；写入数据的节点提交后立即重建）。PostgreSQL LISTEN/NOTIFY 以后作为触发源加入，见技术选型的「变更通知」。key 能否使用（各层的停用、删除、过期、IP 白名单）、预设、可用模型、花费上限、预算和等级都在准入事务里读库，定规则和路由用读出的值，不靠缓存，所以停用不需要失效缓存（见 [accounts 的「认出与准入」](../internal/accounts/README.md#认出与准入)）。
4. **模块之间只按下表引用**：表是唯一来源，从下到上排列，每行只能引用它上面的行；CI 用 `tools/checkmodules` 读取每个 Go 文件的引用（不论构建条件），新模块先在表里登记才能引用别的模块。`cmd/axiom` 负责组装，可以引用所有模块。
5. **下层用到上层时不加反向引用**，按情况选一种：
   - 后续动作用事件（规则 2）：事件的类型由发布方定义，订阅方引用发布方，所以订阅方在上层。下层要对上层的事做反应时（例如累计充值达到门槛后升级等级），不订阅上层的事件，改由上层调用下层的公开接口：必须和上层的数据一起成败的，在同一个事务里调用；其余由上层自己的事件处理器调用，仍按规则 2 在提交后执行；
   - 调用时要借上层的能力（例如供应商经出口节点发请求）：下层定义接口，上层实现，在 `cmd/axiom` 里接上；
   - 上层调用下层时，把下层需要的数据作为参数传进去（例如预留时传入 key 的花费上限）；
   - 一次写入要跨模块同成同败时，数据的所有方提供接受调用方事务（`pg.Tx`）的函数，由打开事务的一方调用。目前只有两处：billing 的预留在 accounts 打开的准入事务里；suppliers 记尝试和丢失的请求在 billing 的结算和清理事务里；
   - 运维告警：各模块经 `platform` 的告警信号报告，由 `observability` 汇总、去重和发送，不引用 `observability`。

### 模块之间的依赖

每个模块都可以引用第一行的 `platform`，表里不再重复。

| 模块 | 可以引用 | 为什么 |
|---|---|---|
| `platform` | — | 基础设施和共用值类型，不引用任何模块 |
| `catalog` | — | 模型和价目表结构是最底层的业务概念 |
| `accounts` | — | 站点、账户、授权和配置链被所有面向租户的模块使用 |
| `protocol` | `catalog` | `Request` 用目录的计费项集合和服务等级集合表达请求可能用到什么，累计的用量按目录的计费项表达 |
| `suppliers` | `catalog`、`protocol`、`accounts` | 端点是分组 × 模型，成本计划用目录的价目表结构；调用面声明自己说哪种调用格式；供应商有归属方，并在配置链里声明配置项 |
| `quality` | `suppliers`、`catalog`、`protocol` | 检测经供应商的调用面发出；目录基线是属性的默认值；按官方格式构造请求、比对响应 |
| `billing` | `catalog`、`suppliers`、`quality`、`accounts` | 参考价取目录里模型选定来源的价格，成本取供应商的成本计划，定价对象包括来源类型，加价按等级，二级站点要同时预留站长账户 |
| `routing` | `catalog`、`protocol`、`suppliers`、`quality`、`billing`、`accounts` | 路由快照由模型、端点、属性、价格、预设和配置组成；按请求的调用格式过滤 |
| `observability` | `catalog`、`protocol`、`accounts` | 调用记录的用量按计费项保存、按租户查看；对话内容按消息去重，要懂调用格式 |
| `payments` | `billing`、`accounts`、`observability` | 到账在同一个事务里生成付费额度批次；收款渠道是站点配置；拒付申诉要整理该账户的调用记录 |
| `gateway` | `catalog`、`protocol`、`accounts`、`suppliers`、`quality`、`billing`、`routing`、`observability` | 编排一次调用：认 key、解析、路由、预留、调上游、观测、结算、记录 |
| `operations` | `accounts`、`observability`、`gateway` | 授权、通知渠道、节点管理；审批经管理接口的中间层，不引用被审批的模块 |

## 一次调用怎么走

```
1. 入口节点就近接住连接，转给核心 ................... 自己的线路
2. 按登记过的域名认出站点，只凭请求头校验 API key，
   认出之前不读请求体 ................................ 内存缓存，未命中才查库
3. 读请求体，解析：用到哪些能力、上下文多长 .......... 内存
   取限流计数和会话粘性，调用路径上唯一一次 .......... M1 进程内，M2 一次缓存往返
4. 准入（一个事务）：核对 key 能否使用，读出预设、可用模型、
   等级 .............................................. PostgreSQL
5. 定规则：key 上的预设 + 各层默认值 + 请求里的临时覆盖  内存
6. 路由：选出端点和出口，排好回退顺序 ................ 内存快照
   候选都满载：回滚准入事务，在事务外排队，醒来只重做
   准入，不再取缓存 .................................. 不占数据库连接
   预留第一段费用，不够返回 402，提交准入事务 ........ PostgreSQL
7. 经出口调用上游：挑凭证、透传或转换格式，边收边转发；
   开始转发前出错就换下一个端点；按段追加预留，
   追加不到就截断 .................................... 上游、PostgreSQL
8. 回答结束前结算：成本和售价，记账本，释放多余的预留，
   费用写进最后一个事件 .............................. PostgreSQL
9. 写调用记录、保存对话内容 ........................... 异步
```

已经开始向用户输出后上游才出错的情况，无法再换端点，只能在流里报告错误（OpenRouter 的做法是 HTTP 状态码仍为 200，在流里发错误事件，见 OpenRouter 文档《Errors》，2026-10）。格式见[接入与对外接口的「错误」](domains/gateway.md#错误)；每一步的模块、事务、往返和期限见 [gateway 模块的「一次调用的步骤」](../internal/gateway/README.md#一次调用的步骤)。

## 协议转换

- **格式相同就透传**：按一份改写清单只改个别成员（模型名、路由参数、会话和用户标识、Responses 的历史与存储设置），其余字节原样转发，缓存标记、推理签名等细节不丢；清单见 [protocol 的「同格式改写」](../internal/protocol/README.md#同格式改写)。
- **格式不同经统一的中间格式转换**：每多一种格式只加一对转换器，不两两互写。
- **流式细节**：空闲超时只被真正的数据事件重置，心跳不算；从每一种事件里累计用量，流中断或用量不全时保留上游已报告的各项，只估缺的项，按暂估结算（见[计费的「用量来源与暂估」](domains/billing.md#用量来源与暂估)）。sub2api 因心跳重置计时让卡死的流挂了 16 分钟，又因流提前结束丢过输出用量（sub2api issue #7955、#7873，2026-10）。
- **验证**：录制真实上游的流式输出作为固定样本，每次改动都回放比对，结果必须一致。

## AI 运营

- 固定流程写成代码自动执行：同步、检测、端点上下线、故障切换。
- 运营 agent 运行在运维节点上，只通过运营接口操作系统；它的模型来源可配置，至少一个直连，不依赖中转站和 Axiom 自身。范围覆盖业务（供应商、价格、上下架）和基础设施（节点健康、线路）。
- 权限、审批、资金操作上限都在服务端执行，详见[运营](domains/operations.md)。

## 技术选型

后端用 Go，前端用 TypeScript，SQL 作为一等语言。每种语言只用在它最合适的地方，彼此之间用生成的契约连接：Go 与 TypeScript 之间是 OpenAPI，Go 与数据库之间是由 SQL 文件生成的类型化代码。

| 方面 | 选择 | 理由 | 不选 |
|---|---|---|---|
| 后端语言 | Go 1.27 | 网关受网络和上游限制，Go 远低于延迟目标；编译快、写法单一、代码直白，AI 写和人审都最顺；运营与支付需要的官方 SDK 齐全（Anthropic、OpenAI、Stripe、微信支付、MCP） | Rust：内存占用最低、类型最强，但编译慢、异步写法复杂、人审难，管理功能开发慢，国内支付缺官方 SDK；TypeScript：长连接性能证据最弱，npm 供应链风险大；Python：LiteLLM 正因性能把核心路径改写为 Rust（LiteLLM 博客，2026-06） |
| 调用链路与管理功能是否分用两种后端语言 | 不分，全部用 Go | 两种语言会让预设、价格、预留等核心语义在两边各写一份，迟早不一致；改一个功能要同时改两套代码 | 调用链路用 Rust、管理功能用 Go。数据面只读快照、只发事件，边界清楚，测量证明确有必要时可以单独重写调用链路 |
| HTTP | 标准库 `net/http` | 1.22 起支持按方法和路径路由；流式输出直接可控；少一层依赖 | Gin：new-api、sub2api 都用，对流式没有帮助 |

`just test` 只传 `go test` 可缓存的参数，包及其读到的文件、稳定的环境变量不变时复用测试结果。基准不在 `test` 里跑：主分支由 `just check-ci bench-once` 带竞态检测各跑一次（本地 `just check-all` 同）；PR 上除 Markdown-only 和 `web/`-only 外的改动跑 `just bench-compare` 比较分配（不带竞态），不再另跑 `bench-once`，免得同一批基准每个 PR 跑两遍。CI 的 build 跑 `just check-ci`，即 `just check` 去掉 `secrets` 和 `docs` 里 workflow.yml 已有的部分（`scripts/workflow` 的测试与 `check_docs.py`；`scripts/` 自己的测试仍跑），它们由 workflow.yml 里必需的 `secrets`、`docs` 作业在每个 PR 和主分支上跑；本地 `just check` 是推送前的门，全跑。前端构建按输入哈希（`web/`、版本戳、工具链、`VITE_`/`NODE_`/`AXIOM_` 变量和 `web_cache.py` 自身的哈希）缓存在宿主机的缓存目录；端到端通过按 `web/`、`api/`、全部 Go 代码、`go.mod`/`go.sum`、测试配置、Go 版本和同一组环境变量的哈希复用，任何 Go 变化都会重跑。缓存目录不自动淘汰，定期清理 `<cache>/web-build` 和 `<cache>/e2e`（例如 `find ~/.cache/axiom/web-build -mindepth 1 -maxdepth 1 -mtime +14 -exec rm -rf {} +`）。只改 Markdown 的 PR 不跑完整 build，只跑 `just md-checks`（`docs`、`modules`、`artifacts` 和读依赖表的 pg 测试），跳过 web、deploy-check 和基准；主分支和其余 PR 全跑。数据库测试的状态由 `pgtest` 每次新建：每个测试复制一个已迁移的模板库，集群本身也是每次运行新起的，连接串不随代码变化，因此不进入缓存键（[平台层的「测试」](../internal/platform/README.md#测试)）。

具体小库在实现时按兼容性测试选定，记在对应模块的 README（缓存客户端见 [platform/kv 的「决策与理由」](../internal/platform/kv/README.md#决策与理由)）。

## 仓库结构与契约文件

```
cmd/axiom/                    唯一的服务程序入口，按节点角色启动
internal/<模块>/              模块的公开接口
internal/<模块>/internal/     模块的实现，其他模块在编译层面就无法引用
internal/platform/            基础设施和共用值类型
api/                          控制台、管理和运营接口的 OpenAPI 定义
web/                          前端：官网、控制台、管理后台、共享组件
deploy/                       镜像与部署配置
tools/                        开发和 CI 用的 Go 工具；要引用某模块实现的开发命令放在该模块的 internal/ 下，如 protocol 的录制命令
scripts/                      CI 检查脚本
docs/                         文档
```

- 每个模块目录里放它的代码、SQL 查询、迁移脚本和 README。
- 控制台接口、管理接口和运营接口的前后端代码都由 `api/` 里的定义生成。
- 对外的模型调用接口沿用 OpenAI 和 Anthropic 的规范，我们的文档只写与它们不同之处。

## 工程原则

- **机制写在代码里，取值放在后台数据里**（见[产品需求的「质量要求」](product.md#质量要求)）。
- **钱只在 PostgreSQL**：
  - 预留在账户余额行的锁下检查并写入（余额减去在途预留不低于余额底线才预留），缓存不存任何余额；
  - 金额用 64 位整数存最小单位，运算检查溢出；
  - 所有数量类参数在入口限定上下界，结算金额不得为负，用断言守住；
  - 预留和结算带防重复编号；账本只追加。
- **配置有错就不启动**，不把错误留到运行时。
- **优雅退出**：节点先停止接收新请求，等在途的流结束（有上限时间），处理完结算后再退出。
- **参考实现的代码**：new-api 采用 AGPLv3，sub2api 采用 LGPL-3.0（GitHub，2026-10）。负责人 2026-10-20 决定 Axiom 将开源、不受这两个许可证的约束限制，所以可以复制：能原样放进 Axiom 的部分（协议与格式转换、厂商和中转站的特殊处理、签名与验签算法、错误映射、测试样本）直接复制后按 Axiom 的类型改写，并在代码里用一行注释写明来源（仓库、路径、提交）；绑在它们框架（gin、gorm/ent）、钱（Axiom 用精确分数，不用浮点数）、租户（行级安全）或数据模型上的部分，按 Axiom 的结构重写。开源时按复制来源统一整理许可证与版权声明。
- **日志从第一天内置，指标和链路追踪随第一个调用路径上的模块内置**（[Issue #54](https://github.com/TYCT-tyct/Axiom/issues/54)）；都不记录对话正文和任何密钥。指标与链路的命名、标签上限、采样和导出见 [platform 的「遥测」](../internal/platform/README.md#遥测)。
- **安全**：威胁模型、安全基线和跨模块的安全规则见[安全](security.md)。

### AI 好写好维护

- **限制文件和函数的大小**，由 lint 检查。sub2api 出现过单个文件 178KB、单个函数约 1000 行的情况（sub2api 源码，2026-10）。
- **模块边界由编译器和 CI 强制**：模块的实现放在它自己的 `internal/` 下，其他模块无法引用；模块之间允许的引用见「模块之间的依赖」。
- **用类型排除非法状态**：
  - 不同实体的 ID 用不同类型，不能混用；
  - 多选一的数据用封闭接口表示，由 gochecksumtype 和 exhaustive 检查是否处理了每一种情况；
  - 凭证按供应商类型定义成有类型的结构，不用字符串键值包。sub2api 因为字段白名单漏了几个键，导致一整类账号永远选不中（sub2api issue #7758，2026-10）。
- **不用隐式机制**：不用 ORM、依赖注入框架、反射加载配置。
- **反馈要快**：一条命令跑完格式化、lint 和单元测试。契约代码由生成得到，CI 检查生成结果是否最新。
- **CI 在哪跑**：任务的 `runs-on` 读仓库的 Actions 变量 `RUNS_ON`（project-workflow 的约定，见其工程基线；`ci.yml` 的重作业先读 `RUNS_ON_HEAVY`），不设就用 GitHub 托管的 `ubuntu-latest`；本仓库设为自托管 runner，几个 runner 共用一台机器。`ci.yml` 按检查拆成并行作业：`changes`（判断 Markdown-only、部署检查和基准是否需要跑；PR 上跑在便宜池）、`static`（`just check-ci` 里不需要跑测试的检查，加迁移版本号；列车和 `main` 再加 `docs`、`secrets`）、`go-test`（`just test`）、`web`（前端检查和端到端）、`bench`（基准；列车比较分配次数，`main` 上每个基准跑一次）、`deploy`（部署检查）；PR 的构建只跑 `static`、`go-test`、`web`，列车和 `main` 跑全部。`build` 聚合这些作业，是 `ci.yml` 里唯一进规则集的检查：任一作业失败或被取消它就失败，跳过不算。`just check`/`check-all` 的测试各用随机端口和容器名，可以并行；部署检查（`scripts/ci/deploy-check.sh`）给每个作业自己的 compose 项目名、镜像标签、数据卷和内核分配的空闲端口（项目名由 runner 名和工作区路径的短哈希组成），开始和结束时都拆掉自己的容器、数据卷和镜像，`down` 最多等 5 秒，CI 的容器没有重启策略。被 SIGKILL 的作业由同一个 runner 的下一个作业清理；如果那个 runner 不再跑，任何 runner 的下一次部署检查会清掉带本脚本标签、名字以 `axiom-ci-` 开头、容器创建超过作业超时（40 分钟）的栈——只动这些，别的容器不碰。所以同一台机器上的作业可以同时跑，不需要文件锁；`just up` 在本地仍用项目名 `axiom`、镜像 `axiom:local` 和 8080/8082 端口。只改 Markdown 的 PR 或列车只跑 `just md-checks`（读 Markdown 的便宜检查，加文件大小和二进制检查），其余作业都跳过；`docs` 检查仍跑。PR 不跑部署检查和基准，只有列车和 `main` 跑：部署检查只在改动的每个文件都明显与容器无关时跳过（`scripts/ci_skips.py` 的 `deploy-needed`：Markdown、`*_test.go`、`testdata/`、`.github/`、检查与 CI 用的脚本、`web/e2e` 和 Playwright 配置），生产 Go 代码、`go.mod`/`go.sum`、`web/` 应用源码、迁移、`deploy/`、Dockerfile、`justfile` 等都会跑它；基准只在只改 Markdown 或 ## 底线指标

正式上线时的目标。达到它需要至少两个核心节点和一个数据库热备；单机起步阶段不承诺可用性和恢复时间。

| 指标 | 目标 |
|---|---|
| 网关自身增加的首字延迟 | p95 不超过 30ms，不含网络传输和上游自身耗时 |
| 月可用性 | 不低于 99.9%，即每月停机不超过约 43 分钟 |
| 并发能力 | 单个核心节点至少同时处理 5000 路流式调用，可加机器扩展 |
| 计费准确 | 每天自动对账，账本合计与余额零偏差；同一请求不重复扣费 |
| 数据恢复 | 数据库最多丢失 5 分钟的数据，1 小时内恢复服务。做法：持续把数据库日志归档到对象存储，并保持一个流复制热备 |

## 决策与理由

| 决策 | 理由 |
|---|---|
| 模块化单体，按节点角色启动 | 微服务运维重、跨服务事务难做；不分边界的单体会越写越乱。模块化单体兼顾两者，需要时可按模块拆出 |
| 节点、节点角色、出口是后台数据，单机起步 | 负责人要求入口和核心可以分开部署。同一程序按节点角色部署，起步成本最低，扩展不改代码 |
| 入口节点先做薄层 | 状态只存一份，最简单；入口到核心的一跳走自己的线路，代价基本被省下的握手抵消 |
| 路由同时选端点和出口 | 官方 API 有地区限制，号池账号需要固定 IP，跨境线路质量不稳，都只能靠选择出口解决 |
| 调用路径只读内存，预留直接在 PostgreSQL 完成 | 满足延迟目标的前提。预留在余额行的锁下完成，同机房内耗时在毫秒级；余额只有一份真相，不会出现 new-api 那种缓存与数据库互相覆盖的漏洞 |
| 格式相同透传，不同才转换 | 透传不丢细节；统一中间格式让转换器数量随格式数线性增长 |
| 运营 agent 是独立进程，只走运营接口 | 权限、额度和审计集中在一处，agent 出错不会绕过约束 |
| 节点之间只用双向 TLS | 一层加密和身份认证足够；跑在 TCP 上，不受跨境线路对 UDP 限速的影响 |
| 第一版不在中国大陆放节点 | 负责人决定。大陆节点需要 ICP 备案，且无法直连官方 API |
| 技术选型由开发者决定 | 负责人授权开发者在调研后自行判断。各项选择的理由见「技术选型」 |
| 模块依赖表写在本文，由脚本检查，不用 depguard | 表从下到上排列、每行只能引用上面的行，所以不会有环，也没有登记的模块无法引用任何模块。depguard 的严格模式要在每条规则里列全标准库和第三方库，规则就不再只说模块之间的关系，也不会因新模块没登记而失败；所以只用它禁用个别库（见 `.golangci.yml`） |
| 订阅事件的一方引用发布方，反向需求用接口或参数解决 | 依赖方向只有一个，事件类型只有一个定义的地方 |
| 实体 ID 归所属模块；被下层引用的 ID 和金额、单价放在 `platform` | 类型放在所有使用者都能引用的最低位置。多数 ID 的所属模块本来就在使用者下面（例如 `accounts` 的账户 ID）；网关的请求、尝试、节点、出口编号却被预留、出口绑定、线路测量这些下层功能使用，金额和单价被最底层的目录使用，只能放在 `platform` |
| 路由快照由 routing 自己组装 | 快照是路由的输入，由路由负责最直接。另一种做法是在 `cmd/axiom` 里组装、routing 不引用其他模块，但组装代码会变成没有归属、却看得见所有模块的胶水 |
| 开发工具放在单独的 `tools/go.mod` | 版本和校验和由它的 go.sum 锁定，Windows 和 Linux 上完全一致，也不混进程序自己的依赖 |

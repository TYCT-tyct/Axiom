# 总体架构

系统怎么分块、怎么部署、一次调用怎么走，用什么技术，以及所有模块共同遵守的工程原则和底线指标。概念的叫法见[术语与核心概念](glossary.md)，产品要求见[产品需求](product.md)。

## 整体形态

模块化单体：一个代码库、一个程序，内部按模块严格分界，按节点角色启动。以后某个模块需要独立部署，因为边界清楚，可以直接拆出。

## 部署拓扑

每台运行 Axiom 的机器是一个节点。所有节点跑同一个程序，后台为每个节点配置它承担的节点角色：

| 节点角色 | 做什么 |
|---|---|
| 入口 | 就近接住用户连接、完成 TLS 握手，再转给核心 |
| 核心 | 鉴权、路由、计费、存数据；管理接口只由核心提供 |
| 出口 | 向上游发请求 |

- **单机起步，随时加节点**：只有一台机器时它兼任全部节点角色；扩展时加机器、分配节点角色，不改代码。节点、节点角色、线路都是后台数据。
- **入口先做薄层**：鉴权、路由、计费都在核心，状态只有一份。以后某个地区用户多了，可以让当地入口节点也承担核心职责，冻结余额改为各区域预领额度，调用方不用改。
- **入口到核心**：用 HTTP/2，每对节点之间保持多条长连接，避免一条连接丢包拖慢所有流；实测跨境丢包严重时再改用 HTTP/3（QUIC）。入口持有证书私钥、能看到明文，所以只部署在我们自己控制的机器上。二级站点自定义域名的证书自动签发并分发到入口，细节在控制台设计中确定。
- **节点之间的安全**：节点之间的调用一律走双向 TLS，跑在 TCP 上（跨境线路常对 UDP 限速）。新节点用一次性令牌注册，由核心的内部证书机构签发证书并自动轮换。数据库和缓存只在核心所在区域的内网开放。
- **路由同时选端点和出口**：出口可以是承担出口职责的节点，也可以是外部代理。选择依据是实测的节点之间、出口到供应商之间的延迟和成功率。
- **出口的价值不在缩短距离**，而在于：
  - 满足供应商的地区限制：Anthropic 和 OpenAI 都不支持中国大陆、香港、澳门（Anthropic《Supported Regions Policy》、OpenAI《Supported countries and territories》，2026-10）；
  - 让跨境流量走我们自己控制的优化线路；
  - 与上游保持长连接，省去每次请求的握手；
  - 给号池账号和在意来源 IP 的中转站提供固定 IP。
- **核心放在哪里是部署选择，不影响代码。**第一版不在中国大陆放节点，国内用户经香港等地的入口节点和优化线路接入。

## 模块划分

模块、[领域文档](README.md#文档怎么组织)、代码目录一一对应；术语表里的每个概念只归一个模块管。

| 模块 | 负责什么 | 管哪些概念 |
|---|---|---|
| gateway | 三种调用格式的入口、API key 鉴权、限流、流式输出、中途出错的处理；节点注册、节点角色的启动和节点之间的传输 | 请求、尝试、节点、节点角色、入口、核心、出口 |
| protocol | 各调用格式之间的转换，格式相同时透传 | — |
| routing | 按预设、能力、归属方筛选端点，选出口，排序、回退、会话粘性 | 预设 |
| catalog | 模型、别名、目录基线及其同步 | 模型、模型厂商、目录基线 |
| suppliers | 供应商、分组、凭证、端点、代号；适配器、同步、挑选凭证、调用上游；号池是其中一种实现 | 供应商、归属方、分组、代号、凭证、端点、适配器、同步 |
| quality | 检测、指纹、线上观测，把各种依据合并成端点属性；节点和出口的线路测量 | 端点属性、依据、来源、指纹、检测 |
| billing | 逐层加价计算成本和售价；冻结、结算、账本、币种、对账 | 成本、售价、加价、账本、冻结 |
| payments | 充值渠道、订单、退款，结果记入账本 | — |
| accounts | 站点、用户、账户、成员、工作区、API key、等级、登录；操作者的授权（权限、角色、范围）；平台 → 站点 → 账户 → 工作区 → API key 的配置链 | 站点、站长、用户、账户、成员、工作区、API key、管理 key、等级、操作者、权限、角色、范围 |
| operations | 给运营 agent 和管理员用的运营接口；资金额度上限、审批、操作审计；权限判断调用 accounts 的授权 | — |
| observability | 调用记录、对话内容的保存与清理、指标、告警 | 调用记录 |

另有两块不承载业务概念：`platform` 是基础设施（数据库、缓存、事件、加密、日志），不放业务逻辑；`web` 是前端，包括按站点域名换品牌的用户控制台和管理后台。

## 模块边界规则

1. **每个模块只读写自己的数据表**，其他模块通过它的公开接口访问，不直接查它的表；模块之间不建数据库外键，只按 ID 引用。
2. **跨模块的后续动作用事件**：事件与数据在同一个事务里保存，提交后才发出，不会丢失。处理事件的一方必须能承受同一事件收到多次。
3. **调用路径上不查数据库，只有两个例外**：冻结余额；API key 缓存未命中。其余所需数据都在核心内存里：
   - 路由快照：端点、属性、价格、预设、配置；
   - API key 缓存：key 的哈希 → 站点、账户、工作区、各层的停用状态、预设、可用模型、IP 白名单、速率限制。

   数据变化时通过变更通知重建快照、失效缓存；停用站点、账户或工作区时，其下所有 key 的缓存一并失效。花费上限和预算由冻结时的数据库检查保证，不靠缓存。

## 一次调用怎么走

```
1. 入口节点就近接住连接，转给核心 ................... 自己的线路
2. 按登记过的域名认出站点，校验 API key .............. 内存缓存，未命中才查库
3. 解析请求：用到哪些能力、上下文多长 ................ 内存
4. 定规则：key 上的预设 + 各层默认值 + 请求里的临时覆盖  内存
5. 路由：选出端点和出口，排好回退顺序 ................ 内存快照
6. 按预估费用冻结余额，不够就拒绝 .................... PostgreSQL
7. 经出口调用上游：挑凭证、透传或转换格式，边收边转发；
   出错就换下一个端点 ................................ 上游
8. 按实际用量结算：成本和逐层售价，记账本，释放多冻结的部分
9. 写调用记录、保存对话内容 ........................... 异步
```

已经开始向用户输出后上游才出错的情况，无法再换端点，只能在流里报告错误（OpenRouter 的做法是 HTTP 状态码仍为 200，在流里发错误事件，见 OpenRouter 文档《Errors》，2026-10）。具体格式在对外接口的设计中确定。

## 协议转换

- **格式相同就透传**：只改模型名、读取用量，其余原样转发，缓存标记、推理签名等细节不丢。
- **格式不同经统一的中间格式转换**：每多一种格式只加一对转换器，不两两互写。
- **流式细节**：空闲超时只被真正的数据事件重置，心跳不算；从每一种事件里累计用量，流中断时按已产生的用量结算。sub2api 因心跳重置计时让卡死的流挂了 16 分钟，又因流提前结束丢过输出用量（sub2api issue #7955、#7873，2026-10）。
- **验证**：录制真实上游的流式输出作为固定样本，每次改动都回放比对，结果必须一致。

## 规模与扩展

- 入口、核心、出口都不存数据，加机器即可横向扩展。
- 最终的瓶颈是主数据库。应对顺序：调用路径只在冻结时写库；调用记录批量写入；结算按账户批量入账；交易量特别大的账户把余额拆成多个槽位分散行锁；再大就按账户分库，模块接口不变。
- 容量数字以压测结果为准，压测后写入本文。

## AI 运营

- 固定流程写成代码自动执行：同步、检测、端点上下线、故障切换。
- 运营 agent 是独立进程，只通过运营接口操作系统，调用模型也走 Axiom 自己。它的范围覆盖业务（供应商、价格、上下架）和基础设施（节点健康、线路）。
- 运营接口自带机器可读的说明（OpenAPI），支持防重复编号和试运行，错误码稳定，便于 agent 安全地操作。sub2api 只有一个包装管理接口的命令行脚本给 AI 用，没有接口说明，也没有按 agent 区分的权限（sub2api 仓库 `skills/sub2api-admin`，2026-10）。
- 花钱的操作（加机器、给供应商充值、改售价）按[产品需求的「运营」](product.md#运营)受额度上限和审批约束。

## 技术选型

后端用 Go，前端用 TypeScript，SQL 作为一等语言。每种语言只用在它最合适的地方，彼此之间用生成的契约连接：Go 与 TypeScript 之间是 OpenAPI，Go 与数据库之间是由 SQL 文件生成的类型化代码。

| 方面 | 选择 | 理由 | 不选 |
|---|---|---|---|
| 后端语言 | Go 1.27 | 网关受网络和上游限制，Go 远低于延迟目标；编译快、写法单一、代码直白，AI 写和人审都最顺；运营与支付需要的官方 SDK 齐全（Anthropic、OpenAI、Stripe、微信支付、MCP） | Rust：内存占用最低、类型最强，但编译慢、异步写法复杂、人审难，管理功能开发慢，国内支付缺官方 SDK；TypeScript：长连接性能证据最弱，npm 供应链风险大；Python：LiteLLM 正因性能把核心路径改写为 Rust（LiteLLM 博客，2026-06） |
| 调用链路与管理功能是否分用两种后端语言 | 不分，全部用 Go | 两种语言会让预设、价格、冻结等核心语义在两边各写一份，迟早不一致；改一个功能要同时改两套代码 | 调用链路用 Rust、管理功能用 Go。数据面只读快照、只发事件，边界清楚，测量证明确有必要时可以单独重写调用链路 |
| HTTP | 标准库 `net/http` | 1.22 起支持按方法和路径路由；流式输出直接可控；少一层依赖 | Gin：new-api、sub2api 都用，对流式没有帮助 |
| JSON | 标准库 `encoding/json/v2` 和底层分词器 `encoding/json/jsontext` | v2 接口默认严格：拒绝非法 UTF-8 和重复键，避免我们解析的和上游解析的不一致；旧的 `encoding/json` 接口仍然宽松（Go 1.27 发布说明，2026-08）。透传时只按需读改个别字段，保留原始字节顺序。全部 JSON 处理走一个内部包，以后换实现只改一处 | sonic 等第三方库：没有测量证明之前不引入 |
| 数据库 | PostgreSQL，只支持这一种 | 账本要事务和行锁；按时间分区存调用记录；JSON 类型存灵活属性 | 同时支持 SQLite、MySQL：new-api 为此写了约 111 处原生 SQL 和按库分支，CI 却不测多库（new-api 源码，2026-10） |
| 数据库访问 | pgx 驱动 + sqlc（把写好的 SQL 自动生成 Go 代码），不用 ORM | SQL 写在文件里，人和 AI 都看得见实际执行的语句；类型由生成保证。管理列表这类动态筛选和排序，用一个小的参数化查询构造包集中处理，禁止拼接用户输入 | GORM：new-api 为迁就多库在 ORM 外写了大量原生 SQL；Ent：表结构真相分在模型定义和迁移两处，生成代码超过 26 万行（sub2api 源码，2026-10） |
| 数据库迁移 | goose，SQL 文件放在各自模块里，每个模块独立的版本序列，按固定顺序执行；只向前，合并后不改 | MIT 许可；模块之间没有外键，迁移互不依赖 | Atlas：默认安装受专有协议约束，检查与漂移检测收费（Atlas 官网，2026-07）。sub2api 有约 18 个迁移在执行后被改动（sub2api 源码，2026-10），所以由 CI 校验已合并迁移的内容不变 |
| 缓存与协调 | Valkey（兼容 Redis 协议） | BSD 许可，由 Linux 基金会维护（valkey.io，2026-09）。只放丢了也能重建的数据：限流计数、会话粘性、辅助锁；不存任何余额。分布式锁只做辅助，正确性靠 PostgreSQL 的行锁和防重复编号 | Redis 8：可选 AGPLv3 等三种许可，Valkey 免去许可问题；DragonflyDB：BSL 许可限制用途 |
| 后台任务 | River（基于 PostgreSQL 的任务队列） | 任务和业务数据在同一个事务里入队，事件不会丢也不会早发；MPL-2.0 许可。还没到 1.0，固定版本、升级前读变更说明 | Asynq：基于 Redis，无法与数据库事务绑定 |
| 变更通知 | PostgreSQL LISTEN/NOTIFY | 事务提交后才送达，快照重建不会读到未提交的数据。通知只带 ID；监听用直连数据库的独立连接，不经事务模式的连接池；断线重连后全量重建快照 | 定时轮询：new-api 改配置后多节点最长 60 秒才生效（new-api 源码，2026-10） |
| 对象存储 | 只依赖 S3 接口；云厂商的对象存储或自托管 SeaweedFS | 对话内容体量最大，与数据库分开 | MinIO：社区版仓库已于 2026-04 归档、停止维护（GitHub） |
| 调用记录分析 | 先用 PostgreSQL 分区表，量大后加 ClickHouse | 调用路径从不读记录表；记录经异步管道写入，以后换存储不影响调用 | 让请求路径查记录表：LiteLLM 和 sub2api 都因此变慢（LiteLLM 文档《Spend Monitoring》，2026-10；sub2api issue #7867，2026-10） |
| 可观测性 | OpenTelemetry（链路、指标）+ 标准库 slog 结构化日志 | 标准协议，后端存储可以随部署选择 | — |
| 配置 | 环境变量解析成带类型的结构，启动时校验；业务配置在数据库 | 简单、可审查；错了就不启动 | viper 等隐式加载配置的库 |
| 依赖组装 | 在程序入口手写构造函数调用 | 一眼看清依赖关系，AI 不会被生成代码绕晕 | Wire 等依赖注入框架：sub2api 的组装代码超过 2000 行（sub2api 源码，2026-10） |
| 管理接口契约 | OpenAPI 3.0.3；Go 端用 oapi-codegen，TypeScript 端用 openapi-typescript + openapi-fetch；生成器固定版本 | 先写契约再生成代码，前后端类型不会漂移；运营 agent 也直接读它。oapi-codegen 对 3.1 的支持 2026-07 才初步加入（oapi-codegen 讨论 #2478），所以先用成熟的 3.0.3 | 手写接口类型 |
| 前端 | React 19 + TypeScript 严格模式 + Vite + TanStack Router/Query + shadcn/ui + Tailwind CSS + i18next（中英文） | 生态最大，AI 写得最好；路由和数据请求都有完整类型；组件代码在仓库里，可以随意改 | Next.js：多一个 Node 服务进程，且安全更新频繁；用户控制台不需要服务端渲染。公开的模型和价格页是否需要预渲染，在控制台设计中定 |
| 前端交付 | 控制台和管理后台分成两个应用，构建产物嵌入 Go 程序。管理后台和管理接口只由核心的单独监听端口提供，只对管理域名和受限来源开放；入口和出口不挂载 | 一个文件部署，普通用户拿不到管理后台的代码。代价是改前端也要重启核心，靠优雅退出不打断在途调用 | 前后端分开部署 |
| 测试 | `go test -race`；testcontainers 跑真实 PostgreSQL 和 Valkey；协议转换用录制样本回放；解析器做模糊测试；计费用性质测试（随机生成大量输入，检查规则始终成立）验证不变量；前端 Vitest + Playwright | 测试对着真实依赖跑，不靠模拟 | — |
| 静态检查 | golangci-lint（含 gosec、staticcheck、depguard、gochecksumtype、exhaustive）、govulncheck、gitleaks；前端 Biome | 私有仓库在 GitHub 免费版上用不了 CodeQL（GitHub 文档，2026-10），以这些工具替代 | — |
| 部署 | 静态编译的单个程序 → 非 root 的最小容器镜像；每个节点用 Docker Compose | 起步最简单；节点多了再换编排工具，程序不变 | 一开始就上 Kubernetes |
| 命令入口 | just | 跨平台，Windows 开发机和 Linux CI 用同一套命令 | Makefile：Windows 上不好用 |

具体小库（如缓存客户端）在实现时按兼容性测试选定，记在对应模块的 README。

## 仓库结构与契约文件

```
cmd/axiom/                    唯一的程序入口，按节点角色启动
internal/<模块>/              模块的公开接口
internal/<模块>/internal/     模块的实现，其他模块在编译层面就无法引用
internal/platform/            基础设施
api/                          管理接口的 OpenAPI 定义
web/                          前端：控制台、管理后台、共享组件
deploy/                       镜像与部署配置
docs/                         文档
```

- 每个模块目录里放它的代码、SQL 查询、迁移脚本和 README。
- 管理接口（控制台、管理后台、运营接口）的前后端代码都由 `api/` 里的定义生成。
- 对外的模型调用接口沿用 OpenAI 和 Anthropic 的规范，我们的文档只写与它们不同之处。

## 工程原则

- **机制写在代码里，取值放在后台数据里**（见[产品需求的「质量要求」](product.md#质量要求)）。
- **钱只在 PostgreSQL**：
  - 冻结用一条带条件的更新原子完成（余额够才冻结），缓存不存任何余额；
  - 金额用 64 位整数存最小单位，运算检查溢出；
  - 所有数量类参数在入口限定上下界，结算金额不得为负，用断言守住；
  - 冻结和结算带防重复编号；账本只追加。
- **配置有错就不启动**，不把错误留到运行时。
- **优雅退出**：节点先停止接收新请求，等在途的流结束（有上限时间），处理完结算后再退出。
- **许可证**：new-api 采用 AGPLv3，sub2api 采用 LGPL-3.0（GitHub，2026-10）。适配器只参考它们的接口行为，不复制代码；复制 AGPL 代码会迫使 Axiom 开源。
- **日志、指标、链路追踪从第一天内置**，但不记录对话正文和任何密钥。

### 安全基线

new-api 的 15 条安全公告和 sub2api 的 2 条高危公告（GitHub，2026-10）几乎都属于下面几类，逐条堵住：

| 规则 | 防的是 |
|---|---|
| 所有出站请求走同一个客户端：先由我们解析目标地址并校验 IP，拒绝内网、回环、`0.0.0.0`、IPv6 映射地址和云元数据地址，再连接校验过的 IP；经外部代理时只用隧道方式连到校验过的 IP；不跟随重定向；上游路径只按白名单拼接，不拼接用户传来的路径 | SSRF：new-api 同类问题出了 4 次；sub2api 把客户端路径拼进上游地址 |
| 用户的 API key 只存带密钥的哈希；上游凭证和号池令牌用信封加密（每份数据用单独的密钥加密，这些密钥再用主密钥加密）存储，主密钥不在数据库里；任何密钥都不进日志 | new-api 的 API key 和渠道密钥明文存库；sub2api 的账号凭证看起来也是明文 |
| 访问租户数据的查询只能通过带站点和账户范围的句柄调用，在类型层面强制；对外响应使用独立的结构，不直接序列化数据库行 | 越权访问；new-api 的用户列表接口返回了管理员令牌 |
| 对话内容加密存储，对象存储不对公网开放，读取按权限控制 | 内容泄露 |
| 数量和金额在入口校验范围，运算检查溢出 | new-api 曾被在野利用的漏洞：数量溢出成负数，扣费变充值 |
| 余额不在缓存里留副本 | new-api 用旧快照整体覆盖 Redis 里的用户额度，抹掉了并发扣减，可绕过额度（GHSA-j6gc-4893-qwmp） |
| 支付回调必须验签，密钥缺失时一律拒绝，并限制请求体大小 | new-api 的 Stripe 回调验签可被绕过 |
| 生成链接和做安全判断时，不信任 Host 和转发头 | sub2api 用 Host 头拼密码重置链接 |
| 管理员必须开启两步验证；运营 agent 使用带权限范围的令牌，每次操作都记审计；修改供应商网址和凭证绑定的出口一律记审计 | sub2api 的管理接口只有一把共享密钥；改网址可以把上游 key 发到别处 |
| 从供应商页面、上游响应读到的内容，对运营 agent 一律视为不可信输入 | 提示注入 |
| 依赖尽量少；govulncheck 和 Dependabot 持续检查；前端包管理器默认禁止依赖的安装脚本，并延迟采用刚发布的版本 | 供应链攻击 |

### AI 好写好维护

- **限制文件和函数的大小**，由 lint 检查。sub2api 出现过单个文件 178KB、单个函数约 1000 行的情况（sub2api 源码，2026-10）。
- **模块边界由编译器强制**：模块的实现放在它自己的 `internal/` 下，其他模块无法引用；depguard 再限定模块之间允许的引用关系。
- **用类型排除非法状态**：
  - 不同实体的 ID 用不同类型，不能混用；
  - 多选一的数据用封闭接口表示，由 gochecksumtype 和 exhaustive 检查是否处理了每一种情况；
  - 凭证按供应商类型定义成有类型的结构，不用字符串键值包。sub2api 因为字段白名单漏了几个键，导致一整类账号永远选不中（sub2api issue #7758，2026-10）。
- **不用隐式机制**：不用 ORM、依赖注入框架、反射加载配置。
- **反馈要快**：一条命令跑完格式化、lint 和单元测试。契约代码由生成得到，CI 检查生成结果是否最新。
- **每个模块的 README 写明不变量**；测试和代码放在一起。

## 底线指标

正式上线时的目标。达到它需要至少两个核心节点和一个数据库热备；单机起步阶段不承诺可用性和恢复时间。

| 指标 | 目标 |
|---|---|
| 网关自身增加的首字延迟 | p95 不超过 30ms，不含网络传输和上游自身耗时 |
| 月可用性 | 不低于 99.9%，即每月停机不超过约 43 分钟 |
| 并发能力 | 单个核心节点至少同时处理 5000 路流式调用，可加机器扩展 |
| 计费准确 | 每天自动对账，账本合计与余额零偏差；同一请求不重复扣费 |
| 数据恢复 | 数据库最多丢失 5 分钟的数据，1 小时内恢复服务。做法：持续把数据库日志归档到对象存储，并保持一个流复制热备 |

## 决策与理由

| 决策 | 理由 |
|---|---|
| 模块化单体，按节点角色启动 | 微服务运维重、跨服务事务难做；不分边界的单体会越写越乱。模块化单体兼顾两者，需要时可按模块拆出 |
| 节点、节点角色、出口是后台数据，单机起步 | 负责人要求入口和核心可以分开部署。同一程序按节点角色部署，起步成本最低，扩展不改代码 |
| 入口节点先做薄层 | 状态只存一份，最简单；入口到核心的一跳走自己的线路，代价基本被省下的握手抵消 |
| 路由同时选端点和出口 | 官方 API 有地区限制，号池账号需要固定 IP，跨境线路质量不稳，都只能靠选择出口解决 |
| 调用路径只读内存，冻结直接在 PostgreSQL 完成 | 满足延迟目标的前提。冻结是一条带条件的更新，同机房内耗时在毫秒级；余额只有一份真相，不会出现 new-api 那种缓存与数据库互相覆盖的漏洞 |
| 格式相同透传，不同才转换 | 透传不丢细节；统一中间格式让转换器数量随格式数线性增长 |
| 运营 agent 是独立进程，只走运营接口 | 权限、额度和审计集中在一处，agent 出错不会绕过约束 |
| 节点之间只用双向 TLS | 一层加密和身份认证足够；跑在 TCP 上，不受跨境线路对 UDP 限速的影响 |
| 第一版不在中国大陆放节点 | 负责人决定。大陆节点需要 ICP 备案，且无法直连官方 API |
| 技术选型由开发者决定 | 负责人授权开发者在调研后自行判断。各项选择的理由见「技术选型」 |

## 待定问题

- 安全与合规的底线、完整的威胁模型和鉴权设计，在安全设计中确定；包括是否再用 PostgreSQL 行级安全为租户隔离兜底
- 运营 agent 的权限范围：负责人希望给它全面的权限，并能查询 bug、提交 Issue 供后续处理。修改供应商网址、凭证绑定这类高风险操作是否需要审批，与"全面权限"如何同时成立，在运营设计中确定

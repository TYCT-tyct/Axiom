# 产品需求

## 定位

Axiom 是对标 OpenRouter 的 LLM API 网关：用户用一套统一的 API 调用多家模型，Axiom 负责路由、失败回退和计费。

与 OpenRouter 的区别在供给侧：除了官方 API，中转站和 Axiom 自有的号池也是正式的供应商，由系统自动接入和管理。

## 用户与市场

| 类型 | 说明 | 开放顺序 |
|---|---|---|
| A | 个人开发者、编程工具用户（Claude Code、Codex、Cursor 等） | 首批 |
| B | 应用开发者、中小企业 | 首批 |
| C | 企业团队：多成员、预算、权限、审计 | 后续 |
| D | 二级站点运营者：在 Axiom 上开设自己的站点，有自己的用户和售价 | 后续 |

C、D 后续开放，但它们需要的数据结构（平台 → 二级站点 → 用户三层）从第一版起就要具备。

市场：国内和海外同时服务，涉及人民币与美元两种币种、国内外两类支付渠道、多地部署。

## 供给侧

三类供应商，通过同一套接口接入：

| 类型 | 说明 |
|---|---|
| 官方 API | 模型厂商的原厂接口，如 OpenAI、Anthropic、Google |
| 中转站 | 第三方转售站点，多数基于 sub2api、new-api 等系统搭建。按所用系统做适配，自动同步余额、模型列表、分组和价格，发生变化时调整路由或告警 |
| 自有号池 | Axiom 自己运营的账号，管理账号健康状态、额度和轮换 |

新增一种中转站系统时，只增加对应的适配，不改动核心。

## 计价

售价 = 实际服务该请求的供应商成本价 × (1 + 加价)。同一模型走不同供应商，售价可以不同。

## 运营

运营由 AI agent 执行：巡检各供应商的余额、模型、分组、价格和健康状态，据此调整路由、上下架模型并告警。系统为 agent 提供专用的运营接口；涉及资金的操作（如修改售价、给供应商充值）有额度上限，并保留操作记录。

## 数据留存

- 调用记录（时间、模型、用量、费用、供应商）全部保存，用于计费、对账和运营。
- 对话内容默认保存；是否保存、保留多久，可按用户和二级站点配置。

## 范围

- 第一版要求全套可用：架构按全部用户类型和供应商类型设计，功能分块实现，全部可用才算第一版完成。
- 从 AxiomCode 迁移余额不在第一版内，但要预留导入余额的能力。

## 质量要求

- 代码质量：模块清晰、精简不冗长，仓库不因堆砌而膨胀；每次改动经过独立评审。
- 可扩展：新增供应商类型、支付渠道等通过扩展模块实现，不修改核心、不打补丁。
- 可维护：代码和接口易读易懂，新成员和 AI 都能快速上手。

这些要求在架构设计中落成具体的工程原则。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 按供应商成本加价，不按质量档位定价 | 供应商无法稳定地划分质量档位。按实际供应商计费也与 OpenRouter 一致：它的每个供应商价格各异，按实际服务的供应商计费，用户可用供应商偏好和最高价格参数控制（OpenRouter 文档，2026-10） |
| 用加价而不用 OpenRouter 的充值手续费 | 加价可以按模型、客户等级、二级站点分别设定，手续费只能统一收取 |
| 多租户结构从第一版起具备 | 二级站点和企业团队虽然后续开放，事后再加租户层级只能打补丁 |
| 对话内容默认保存，可配置 | 负责人决定默认保存。OpenRouter 默认不保存（OpenRouter 文档，2026-10），因此提供按用户和二级站点的配置 |

## 待定问题

- 第一版的完整功能清单
- 底线指标：可用性、网关额外延迟、并发能力、安全与合规要求
- 成功标准
- 号池没有按次成本，其成本价如何确定
- 记账币种：人民币与美元如何结算和换算
- 加价在平台与二级站点之间如何叠加

# 账户与租户：存档

[账户与租户](../domains/accounts.md)和 [accounts 模块](../../internal/accounts/README.md)做决定时的外部对照、被否决的方案和推导。这里不是现行规则；规则以那两份文档和代码为准。

## 外部对照

| 主题 | 出处（查证日期） | 结论 |
|---|---|---|
| 工作区 | OpenRouter《Workspaces》《Create a workspace》（2026-11-07） | 每把 key 属于一个工作区，旧 key 在默认工作区；工作区有名称（1 到 100 字）、`slug` 和描述，所有者和组织管理员能建和删。默认工作区可以删，删后未归属的 key 全部失效、不指定工作区的请求改为 400，Axiom 不允许这一步。 |
| 工作区预算 | OpenRouter《Workspace Budgets》（2026-11-07） | 每个工作区最多四个预算（日、周、月、不重置各一，金额随周期变短严格递减），`/api/v1/workspaces/{id}/budgets/{interval}`，成员只能看，达到任一预算即 403，在途的调用照常完成。Axiom 先做一个；以后可兼容地加一个列表字段。 |
| 管理 key | OpenRouter《Management API Keys》、创建、更新、列表接口（2026-10-29） | 管理 key 只作管理、明文只返回一次。Axiom 的签发边界有意严于 OpenRouter 的无范围账户管理，不提供管理 key 嵌套或预算写入。 |
| 账户暂停的错误 | OpenRouter 官方错误文档（2026-10-29） | 403 用于权限拒绝，Messages 用 `permission_error`；Axiom 统一分类为 `permission_denied`，Chat/Responses 的 `error.code` 是数字 403。 |
| BYOK | OpenRouter《BYOK》（2026-11-02） | 同样是"供应商 + 凭证"的模型。 |
| 找回密码 | OpenRouter 登录页、支持页、条款 §3.1（2026-10-28） | 公开资料没有说明重置令牌、TTL、撤销会话或通知的保证，不写成 OpenRouter 的承诺。 |
| 用户提醒 | OpenRouter 公开文档与设置入口（2026-10-29） | 没有可核验的逐类型通知或公告契约，阈值和公告语义用本项目默认。 |
| GitHub PKCE | GitHub OAuth App（2025-07 起） | 支持 S256，三家 provider 因此都用 PKCE。 |

参考实现（本地只读核对，日期为核对日）：

- key 数量：new-api `controller/token.go:326`、sub2api `api_key_service.go:442` 都是先数后插，并发下会超上限；sub2api 的小时计数在缓存里、删除不返还、缓存出错就放行。
- 找回密码（2026-10-28）：new-api `controller/misc.go:254–330`、`controller/user.go`，sub2api `backend/internal/handler/auth_handler.go:590–680`、`backend/internal/service/auth_service.go:1534–1665`。两者统一文案但在请求中分支查用户；new-api 返回新生成的密码，sub2api 先消费缓存令牌再写密码。Axiom 移到持久队列防时序枚举，让用户自己选密码，消费与写密码同事务。
- 登录限流故障：sub2api 认证路由在 Redis 故障时一律 429（`routes/auth.go:34`），new-api 回 500（`middleware/rate-limit.go:119`）。Axiom 不让缓存故障变成登录故障。
- 低余额（2026-10-29）：sub2api `backend/internal/service/balance_notify_service.go` 判断 old ≥ threshold 且 new < threshold，Axiom 采用并改为定点整数；new-api 有按用户类型的偏好，但发送和限流在进程内，没有照搬。sub2api 的公告有定向、已读和草稿，Axiom 只需要发布、撤下和有效期。
- 最近使用时间（2026-11-15）：new-api `model/token.go` 的 `AccessedTime`、sub2api `backend/internal/service/api_key_service.go` 的 `TouchLastUsed`，都是尽力而为的活动提示。
- 邀请记录（2026-11-16）：new-api `controller/user.go:515–519` 不列出被邀请人邮箱；sub2api `backend/internal/service/affiliate_service.go:450–460,469–502` 返回遮掩邮箱，`backend/internal/repository/affiliate_repo.go:509–528` 用邀请关系左联用户。Axiom 取较小的披露范围。

## 被否决的方案

- **工作区预算放在哪**：A（采用）是准入查询本来就连接工作区行，顺带读出预算交给计费，在余额行锁之后与 key 的窗口用量一起读，每次调用零额外往返。B 是放进节点快照或在 Valkey 单独记数：调低预算或停用后旧值还会放行几秒，违反"能否使用以库为准"；花费计数离开余额那把锁就不能防超支。
- **key 能否使用**：缓存状态再靠失效来停用，两轮反方审查都找到反例：并发的缓存填充交出旧状态、提交确认丢失、多节点之间的通知断线；LISTEN/NOTIFY 同样有提交不确定和断线的窗口。
- **路由放在准入之前**：只能用缓存里的旧预设，收紧的预设会被绕过；缓存路由依据、准入时比较再重新路由要多三个机制，过期之前仍会误拒。
- **在事务里排队**：一个满载模型的排队请求各占一条连接，能把连接池占满，别的模型的准入和结算拿不到连接。
- **登录前的查找**：不受行级安全的查找表破坏"全部 FORCE"；调用路径用平台范围漏一个条件就跨租户；函数里设范围被 `just scope` 禁止。函数清单表要多维护一份数据，旧程序在新迁移后无法启动。
- **业务速率**：在预检前查策略、或在事务里再访问 Valkey，都多一次热路径往返；被业务 key 限额拒绝后补偿扣回账户池会引入窗口交替、缓存超时后结果未知和共享/本地两处回退的一致性问题。
- **法律文档**：原地修改正文会让接受记录指向没看过的文本；当前指针多一处状态，可能与最大版本不一致；立刻删除旧约束会让旧节点写入失败、回滚撞主键；兼容阶段按语言独立选版本会让新节点接受后旧节点又要求重签。
- **站点 logo**：对象存储为一项小配置引入新的故障域、生命周期和鉴权；一行原地覆盖会让内容寻址的长缓存失效。GIF 和 AVIF 没有解码器，logo 也不需要动画。
- **通行密钥**：自己解析 CBOR、COSE 和 attestation 容易写错；go-webauthn v0.18.2 只多 7 个间接依赖，版本已锁定并纳入 Dependabot。
- **会话**：JWT 在过期前无法收回；注册同时签发会话多一种会话来源；控制台和管理共用一套路径要把管理接口挂到公网。
- **key 数量和频率**：唯一约束约束不上（每把 key 都不同）；进程内计数多节点各数一份；按 UUIDv7 里的时间数会让慢两分钟的节点建的 key 被早两分钟排出窗口；每节点令牌桶让限额乘上节点数。
- **ID**：库里存 TypeID 索引更大；`ID[K]` 加标记类型省不了几行。

## 推导与测量

- **准入行**：准入查询把等级、所有者、业务速率、扣费顺序和所有者的协议同意作为一个 54 字节值返回：两个 UUID 各 16 字节，账户和 key 的有效速率各 4 字节，扣费顺序 2 字节（0–3 对应四个顺序），服务条款和隐私政策各一组 4 字节版本与 2 字节语言（版本 0 是没同意过，语言 1 是 zh、2 是 en），网络字节序。逐列扫描 UUID 会让准入从 64 次分配增到 66 次，固定宽度组合测得 63 次。
- **准入的代价**：`BenchmarkAdmit` 对照空事务和 `Admit`，在开发机（Windows 上的 Docker Desktop，PostgreSQL 18）测得增量约 0.5–0.9ms（各 6 轮×5000 次，中位 2.4ms 对 3.2ms），即多一次往返；命中缓存的认出约 4µs、10 次分配。全程 p95 在与核心同机房的库上验收。
- **登录次数的兜底**：Valkey 不可用时每个节点的桶突发除以节点数 N（至少 1）、间隔乘 N，所以 N 个节点合计的回填速度不超过设定、突发不超过 max(突发, N)；代价是每次故障或重启至多多一次突发。
- **运营凭证限频**：请求桶装每分钟次数的十分之一、按每分钟次数均匀补（600 是突发 60、每 100 毫秒补一个）；资金写和告警的桶装窗口次数的一半、其余在窗口里均匀回来（每分钟 30 是 15 次起、每 4 秒回一次；每小时 300 是 150 次起、每 24 秒回一次）。桶在次数调低后算不出窗口里已放行几次，所以每类另记最近放行的时刻（最多设定次数个），在同一把锁里先查窗口、再扣桶、再记放行。
- **安全失败计数**：每站点一行保存当前 UTC 分钟的计数和尚未采样的完整窗口峰值；跨分钟时把完成的次数并入峰值再清零，后台迟到也不丢峰值；积压时只保留峰值，逐条评估完整样本，后续恢复不能抹掉首次通知。

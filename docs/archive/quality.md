# 端点评估研究存档

这里保留真伪信号的比较与熔断窗口的概率推导；它们是设计背景，不是当前行为或上线承诺。

## 真伪信号的比较

- **为什么用这些信号**：
  - **Tokenizer 计数**：固定文本的输入 token 数能区分分词器家族（[lm-detector 的 tokenizer probe](https://github.com/ikaleio/lm-detector/blob/70410db4522387c7d4a6dff8c7a4b6ce0f0239f1/docs/content/docs/principles/tokenizer.en.mdx)，2026-11-03），但同一厂商的两个型号常共用分词器和聊天模板；2026-08 的留出研究在 12 对样本中只有 6 对可用，敏感度 0.50，结论是 token 计数是"共享分词栈的指纹"，不能单独证明型号血统（[Token Counts Are Not Model Lineage](https://arxiv.org/abs/2608.29930)，2026-08-30）。它还会被中转站重写 usage 绕过，适合做第二层证据。
  - **Logprob / 单 token 分布**：单 token 回答的分布能指纹模型，论文在 165 个模型、40 个格子上报告 7.3% 的等错误率，8 个格子低于 11%（[One Token Is Enough](https://arxiv.org/abs/2607.10252)，2026-07）；但需要可信参考部署的分布和 `logprobs` 支持，Messages 等格式没有 logprobs，`TestRequest` 也还没有这个字段，采集一轮参考指纹是另一套后台数据。
  - **官方基线 / 参考响应**：最强，能测出同型号线的版本和量化差异，但需要参考响应的采集与版本管理。
  - **自报型号 + 已知答案**：今天就能用现有生成通路、预算和调度；能直接堵住"同一厂商换廉价型号、模型自己报出另一个名字"这一类。代价是挡不住注入系统提示的有意伪装，第二层证据落地后再收紧 `:exacto`。

## 熔断窗口的推导

- **为什么是这些数**（仅考虑独立失败和次数门槛，未计独立来源、硬失败等附加条件）：失败率 p 独立时，每来一个结局就熔断的概率是 p³ × P(其余 n−3 个里失败 ≥ ⌈n/2⌉−3)。p = 10%、n = 32 时约 1.4×10⁻⁹，每秒 100 个结局跑一小时的期望熔断次数约 5×10⁻⁴；对比"10 个里 5 个"在同样条件下每小时约 54 次，每秒 1 个也有约 0.5 次，所以窗口取 32。真坏的端点：新窗口 5 次失败就熔断，窗口里原有 32 个成功时要 16 次。

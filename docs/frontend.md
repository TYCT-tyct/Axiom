# 前端与设计

官网、用户控制台、管理后台三类页面要做什么、按什么标准验收、外观能改到什么程度。前端的技术选型见[总体架构的「技术选型」](architecture.md#技术选型)，站点的品牌和主题配置见[账户与租户的「站点」](domains/accounts.md#站点)。

## 要求

### 基线

- 页面内容以 OpenRouter 为功能基线，再突出 Axiom 要讲清楚的部分：端点实测的属性与依据、挂在 key 上的预设、按实际服务的端点计费的明细与免单标记。管理后台没有可参照的公开页面，内容从各领域文档推出。
- 参照的网站只是学习目标，不模仿；设计和内容都是 Axiom 自己的。
- 中文优先，英文同样讲究：两种语言都完整，都像母语。

### 页面清单

优先级：「M1」在里程碑 M1 先做（排期以 [Issue #30](https://github.com/TYCT-tyct/Axiom/issues/30) 为准），「第一版」属于[产品需求的「范围」](product.md#范围)，「以后」只预留结构。

OpenRouter 的页面构成（openrouter.ai 页脚与 llms.txt，OpenRouter 文档《Workspaces》《Logs》《Activity》，2026-10-12 查证）：公开的有模型列表与详情、文档、价格等；工作区内有 API key、预设、路由、成员、预算；账户级有用量、调用日志（详情含尝试瀑布图和费用明细）、额度与账单、隐私、偏好。

### 实测

`web/e2e/vitals.spec.ts` 对着嵌入程序的构建产物测，用 web-vitals 采集；手机档是 Pixel 5 视口加 Lighthouse 的慢速 4G 和 CPU 降速 4 倍，电脑档是 10 Mbps 无降速；控制台的登录、key、调用、余额、流水和后台的用户、供应商、模型、价格、设置各取三次加载，每次目标页的前后各加载一次概览页作为参照，LCP 取三次折算值的中位数、CLS 取最大值；概览页在 PR 和列车里与基准提交的概览页成对轮流各加载九次、都不降 CPU，每次从 Chrome trace 里取主线程任务的实际 CPU 时长（见下），在 `main` 上只加载本树九次，另取三次按本档降速的加载报告 LCP 和 CLS（CLS 同样取最大值）；INP 在 CPU 降速 4 倍下，对每个对话框的打开或提交，以及调用页的翻页、筛选、打开详情和后台用户的筛选、打开账户，各取页面上最差的一次；长列表（调用日志和用户列表）各加载 1000 行（列表按游标分页，一页 50 行，所以一万行不是一个页面会有的状态），滚动 5 秒，数掉帧和长任务。数字写进每项测试的注解和输出。

这些指标里只有 LCP 和概览页的主线程 CPU 时间会让任务失败：LCP 电脑档按指标本身 1.5 秒，手机档按 CI 第一次实测最大值的 1.5 倍 6 秒（回归上限，不是 2.5 秒的目标）；概览页的 CPU 时间在 PR 和列车里按相对基准提交的比值和一个宽的绝对兜底卡，在 `main` 上只报告（见下）。其余三项只报告：CLS 同一页在两次测量之间从 0.02 跳到 0.83，滚动的掉帧率在本机调用页 0.36–0.38、用户列表 0.04–0.05，在 CI 0.68，INP 随共享 CI 机器的负载在 96–920 毫秒摆动（列车忙的时候，对话框的 INP 超过 500 毫秒），原因都还没查清，硬卡只会偶发失败。测出的值、与指标的对比和跟踪记录都在任务输出里，但不让任务失败；修一项就收紧一项的上限。测量是计时，所以单独在一个 CI 任务（`vitals`，`just web-vitals`）里一次一个测试地跑；PR 和列车里只在改动触及页面构建输入时才跑（`web/`，以及生成页面客户端所用的 `api/*.yaml`），`main` 每次推送都跑。没改这些的构建里页面的代码和资源没变，量到的差别只是宿主机负载（#503 的列车 run `41086023031` 在没有 `web/` 差异的树上量到手机 LCP 8886 毫秒，重跑 5581 毫秒）。runner 仍和别的作业同宿主机：一台 96 核主机上八个 runner 共用一个 80 核的 cgroup 配额，别的作业的负载会落在计时上，一次突发只要盖住三次加载就足以决定结果，#577 的两次列车失败就是这样。所以除概览页外，每次目标页的加载都夹在两次参照页加载之间：同一降速下把「参照页、目标页、参照页」重复三次，各自新的浏览器上下文；每次目标页的 LCP 按紧挨它前后两次参照页 LCP 的平均值折算到设定上限的基线 run，取三次折算结果的中位数。宿主机负载在取样期间按相同幅度上升时，目标页和夹着它的两次参照页一起变慢，平均参照落在目标页那次的位置上，先参照后目标带来的同向偏差被抵消；突发落在某一次加载上会让那一对偏离（目标页偏慢时折算值偏高，参照页偏慢时偏低），中位数丢掉它，另外两对不受影响。折算系数最多为 1：比基线 run 更慢的宿主会被补偿，更快的宿主不会把页面的预算压到上限以下——上限是页面的预算，不是宿主的。LCP 失败按退化处理。原始值、参照值和折算结果都写进输出。

概览页曾经也按 LCP 卡：先是原始值，后来和登录页互为参照。2026-11-05 的 main run `41983413805`（8ad75cf4 的第一次尝试）说明这个参照不够：概览页电脑档原始 LCP 2444 毫秒，登录页 1350 对基线 1090 毫秒（1.24 倍），同一提交重跑是 692 毫秒（登录页 548 对 1090），之前三次是 648–872 毫秒——概览页慢 3.5 倍，登录页只慢 1.24 倍。概览页要跑外壳的脚本、接口和一张表，登录页少得多，CPU 争抢对两者的拉伸不一样，登录页的 LCP 不是概览页工作量的比例尺。输出里的 2444 也说明这一点：折算取的是三次**折算后**结果的中位数，而注解里的「登录页 1350 对 1090」是三次**参照值**的中位数；决定中位数的那一对，它前后两次登录页的平均值在基线以内，系数封顶为 1，所以折算值等于原始值。方向没有错（参照页更慢时 `reference / base` 小于 1，把页面折算小），错的是拿登录页的 LCP 代表概览页的 CPU 争抢。

概览页现在不按 LCP 卡，也不加载参照页，而是像 Go 的 `bench-compare` 那样和基准提交比：每次加载用 Chrome trace 的 `toplevel` 类别取渲染主线程的 `ThreadControllerImpl::RunTask`，把这些任务的 `tdur`（线程实际运行的时间，不含被换下的时间）加起来；两档都不降 CPU（视口和网络照旧）。PR 和列车里 CI 给出基准提交（`BASE`：PR 的目标分支提交、列车组装时的 `main`），`web/playwright.vitals.config.ts` 用 `scripts/ci/vitals-base.sh` 在一个 git worktree 里构建它的前端（用它自己的 `scripts/web_cache.py`，这台 runner 构建过它就直接取缓存），在另一组端口上和本树的并排提供；两边都用本树的模拟接口，同一份数据，比的只是页面代码（滚动发布时旧页面接新节点本来就必须能用，见 [CONTRIBUTING.md](../CONTRIBUTING.md#检查清单)「发布与缓存」）。同一档里本树和基准的概览页紧挨着成对加载九对，奇数对先基准后本树，每对算本树除以基准的比值，门禁是九个比值的中位数，上限 1.25；本树九次的中位数另有一个绝对兜底（电脑 1020 毫秒、手机 1200 毫秒）。一对里的两次加载相隔几秒、落在同一宿主状态里，宿主忙让两边一起变贵，这一对的比值不动；页面自己变慢抬高每一对。`main` 上没有 `BASE`：同一棵树在列车里已经比过，所以只加载本树九次、报告中位数，不让宿主负载把 `main` 变红。本档降速下的 LCP 和 CLS 另取三次加载，只报告。宿主机忙只增加任务的墙钟时长（`dur`）而不增加 `tdur` 的那部分，是用 `tdur` 不用 `dur` 的原因：24 个 `yes` 进程压着时，电脑档每次加载的 `tdur` 在 0.30–0.52 秒，同一段里 `dur` 从 1.1 秒涨到 2.7 秒，`Performance.getMetrics` 的 `TaskDuration` 从 0.52 秒涨到 3.05 秒，所以没有用它。

CPU 时间不在降速下量，因为降速本身往 `tdur` 里加了一段随宿主机调度而变的空转。Chrome 的 CPU 降速（`Emulation.setCPUThrottlingRate`，Chromium 的 `thread_cpu_throttler.cc`）每 200 微秒给渲染主线程发一次信号，信号处理函数在主线程上忙等「距上次放行的墙钟时间 ×（倍率 − 1）」，墙钟时间最多按 1 毫秒算。忙等是主线程的 CPU 时间，记在当时正在跑的任务的 `tdur` 里；它按墙钟算，所以线程在运行段被换下，回来就多转最多 3 毫秒，在忙等中被换下，忙等又少算。降速下的 `tdur` 因此是页面的工作加上一段由宿主机怎样调度这个线程决定的空转，方向和幅度都不定：2026-11-05 CI 上同一页面手机档三次的最小值在 2199–3607 毫秒之间（run `42012285835` 3607 毫秒，同一 run 里概览页 LCP 只是基线的 1.2 倍），本机按任务类别拆开（另加 `devtools.timeline` 类别，按每个任务里最长的子事件归类，每种条件四到五次）：降速 4 倍的手机档平均 1836–2488 毫秒，单次 1745–3617 毫秒，布局一类在 244–442 毫秒之间摆动，32 个 `yes` 或 CPU 配额压着时反而更低；同样条件下不降速的手机档平均 457–561 毫秒、每种条件的最小值 437–494 毫秒。降速模拟更慢的硬件，同样的工作按同一倍数放大，对 CPU 时间门禁不增加信息，所以两档都在不降速下量，降速的效果留给 LCP 和 INP。

电脑档本来就不降速（倍率为 1 时 Chrome 不启动降速线程），它在 CI 上三次最小值 329–462 毫秒的差别是另一种机制：线程被频繁抢占时，同样的工作要重新填缓存（CI 主机还有超线程，兄弟线程争同一个核），CPU 时间跟着变多。本机把概览页放在权重 20 的 cgroup 里（同 CI 的 `axiom.slice`），外面 24 个高权重的进程反复忙 0.3 毫秒、睡 0.3 毫秒，电脑档的最小值从 413 毫秒涨到 522 毫秒（1.26 倍），各类任务一起涨；定时器任务每次加载只有 6–10 个，数目不随负载变，没有随墙钟变多的轮询或动画帧。这是同样工作在忙宿主上的真实代价，trace 里没有能把它扣掉的量；相对基准提交的比值抵消它，因为基准一边在同一时刻付同样的代价。也没有改成只数到某个页面里程碑为止的任务，因为涨的是全程各类任务，截断去不掉它。

CI 上不降速的手机档对固定上限也不够稳：#674 的 run `42082902709` 三次 588/698/936 毫秒（电脑档 633/472/472），列车 run `42086001099` 782/1023/768 毫秒，超过当时 690 毫秒的固定上限，同一列车里电脑档 508/500/477。忙的 CI 宿主上同样的工作要多花 1.4–1.9 倍 CPU 时间；手机档在任务开头量，正赶上列车里 e2e 等作业同时起步。试过在同一浏览器里用一个固定的参照页折算：参照页不含应用代码，用 JSON 建一张 1500 行的表并排版，约 450 毫秒 CPU，夹在每次概览页加载前后，按它的 CPU 时间折算。本机四种条件（机器自身负载、32 个 `yes`、4 核配额加 16 个 `yes`、权重 20 对 24 个短突发进程）各跑三次，概览页与参照页之比的逐次中位数手机 0.870–1.011（1.16 倍）、电脑 0.785–1.029（1.31 倍），和原始值本身的 1.14 倍、1.30 倍一样宽：压力下电脑档概览页涨了约两成，参照页一直在 440–500 毫秒。概览页是约 600 个短任务，中间有等待，每次醒来缓存是冷的；参照页是一整段连续的脚本，对抢占不敏感；纯 JavaScript 的固定循环更不敏感（#498：同一时间循环差 2%，LCP 差 58%）。所以没有采用折算。独占核做不完整：CI 宿主机上 `system.slice` 里还有别的租户（2026-11-05 约占 96 个 CPU 里的 19 个），他们的 cgroup 和容器不能改，只在 `axiom.slice` 里留出的核仍会和他们共用。不受争抢影响的量是退休指令数：线程被换下、缓存是冷的、超线程兄弟在忙，都不改变它，改变它的只有页面真正的工作和 JIT 的分层编译。2026-11-05 本机实测（CI 的 Playwright 镜像里以 root 加 `CAP_PERFMON` 和 `CAP_SYS_PTRACE` 运行，一个外部小程序用 `perf_event_open` 数渲染主线程的用户态指令，和上面同样四种条件各五次）：电脑档每次 841–862 百万条（1.025 倍），同时 `tdur` 293–563 毫秒（1.92 倍）；手机档 833–895 百万条（1.075 倍；四种条件的中位数 845–887），同时 `tdur` 376–500 毫秒（1.33 倍）。但现在还不能拿它做门禁：Playwright 的 Chromium（build 1248）已经没有 `--enable-thread-instruction-count` 开关（二进制里没有这个字符串，trace 里的任务事件不带 `tidelta`），只能在浏览器外数；CI 的 web 容器以 runner 的用户运行，非 root 进程拿不到 `--cap-add` 加的权限（只进 bounding 集，effective 为空），而宿主机 `perf_event_paranoid=4`，要先以 root 启动再用 `setpriv --ambient-caps` 降到 runner 用户；数别的进程的线程还要 `CAP_SYS_PTRACE`（渲染进程不可 dump）。`CAP_PERFMON` 允许按 CPU 观测整台机器，在和别的租户共用的宿主上是一条旁路，要不要给 CI 的容器开它是安全上的决定；CI 宿主机有没有可用的硬件计数器也还没确认。2026-11-05 决定不为运行 PR 代码、和别的租户共用宿主的容器开放 `CAP_PERFMON` 或 `CAP_SYS_PTRACE`：为一个测试门禁开这条旁路不值得。所以不按指令数卡，改按相对基准提交的比值卡（见上）。

比值的上限 1.25 来自本树和一个页面代码相同的基准在本机四种条件下的实测（机器自身负载、32 个 `yes`、4 核配额加 16 个 `yes`、权重 20 对 24 个短突发进程，各三次，其中配额一次因基准服务没起来作废，共 11 次）：手机档比值 0.916–1.098，同时本树中位数 379–492 毫秒（1.30 倍）、单次加载 344–553 毫秒（1.61 倍）；电脑档比值 0.861–1.007，同时本树中位数 320–480 毫秒（1.50 倍）、单次加载 294–589 毫秒（2.00 倍）。没有改动时比值最高 1.098，1.25 留出约 2.5 倍于此的向上波动；概览页本身约 0.4 秒，0.4 秒的变慢使比值到 2 左右。一对之内先后的影响约 1%（先加载的一边手机平均重 1.4%、电脑轻 0.5%），所以成对交替就够，不需要再夹参照。绝对兜底挡的是每个 PR 都在比值以内、累积起来却越来越慢：取干净构建的三倍（电脑 340 × 3 = 1020 毫秒、手机 400 × 3 = 1200 毫秒，基线是 2026-11-05 本机干净构建的值：电脑三次最小值 0.32–0.36 秒，手机不降速六次运行的最小值 396–467 毫秒），高于 CI 上宿主忙时出现过的 1.9 倍，只在页面本身的工作翻倍以上时才失败。原始 LCP、两边的每次 CPU 时长、比值和 CLS 都写进输出；概览页的 LCP 只报告，不卡。

门禁取每对比值的中位数，而不是两边中位数之比。原来的做法是两边五次加载各取中位数再相除：列车 run `42456875800`（2026-11-08，#702 单独在 `fbaf642` 上，概览页没有新增首屏工作）手机档量到 1.275 而失败，本树 714/723/544/615/713 毫秒、基准 559/561/476/511/678 毫秒，同一提交在自己 PR 的 run `42455183545` 是 1.011。每个中位数只取自一边的五次加载，一两次慢加载落在同一边就能单独把它推高；一对里的两次加载紧挨着，宿主的状态对两边一样，按对相除把它约掉。用 2026-11-05 到 11-08 CI 上 62 次带基准的 vitals 运行回放（两档各 310 对，绝大多数改动没碰概览页）：单对比值手机 0.62–1.65、电脑 0.71–1.52，对数标准差 0.145 和 0.129，同一运行里不成对的两次加载是 0.185 和 0.154；去掉每次运行的均值后相邻两对的比值不相关（滞后一阶相关系数手机 −0.21、电脑 −0.25，五个独立样本去均值后的期望是 −0.25），各次运行均值的离散也和独立抽样的预期一致（手机 0.054 对 0.067，电脑 0.061 对 0.057）。所以各对可以当作独立样本，从这 310 对里有放回地抽样就模拟了一棵没改的树对自己；各抽一百万次：

登录页、key、调用、余额、流水和后台各页仍以概览页的 LCP 为参照，按前后两次的平均值折算、取三次中位数；概览页变慢时它们的折算值只会更小，概览页自己的 CPU 时间门禁负责抓它，页面自己的回归仍会在它和概览页之间露出来。

没有改成让 vitals 独占 runner 或独占 CPU：八个 runner 都在同一台主机上、共用一个配额，`runner-host.sh` 没有给单个 runner 硬分区的开关，workflow 也没有让一个作业独占宿主机的办法；把它串行到其他作业之后，会让 8–14 分钟的列车再等一个 10–14 分钟的计时作业。也没有改成为 CPU 降速乘一个校准系数：#498 已经量过，固定的整数循环在基线 run 是 466 毫秒、繁忙 run 是 475 毫秒（差 2%），同一时间的 LCP 却从 4072 毫秒变成 6456 毫秒（差 58%）——循环看不到让页面变慢的那种调度延迟，而且改降速会改变模拟的设备，量到的就不再是文档写的手机档。按资源依赖图重算 LCP 的模拟节流也要把 CPU 那部分建模，仍要读宿主机上的墙钟任务时长，还要新引一个依赖，不成比例。也没有改成三对里交替先后的做法：三对中总有两对仍是先参照后目标，中位数取的正是其中一对，同向偏差不会抵消。相邻两对共用中间那次参照页加载可以少两次加载，但一次落在参照页上的突发会同时压低两对，中位数反而可能盖住页面自己的变慢；每页用自己的前后两次参照，突发仍只影响一对。成对折算保住了降速条件，只改取样。

也考虑过给概览页做一个工作量相同的参照页：同一外壳和入口、不读页面数据。跑同一份概览页代码、只是不读数据的参照页，会在概览页组件变慢时跟着一起慢，比值抓不到；只跑外壳的参照页又和登录页一样，工作量差得远。现在比的是同一个概览页在基准提交上的版本，不需要另一页，也不引入只为测试存在的页面。没有用重试、跳过或抬高上限。

模拟的接口在浏览器里直接应答，不受网络降速影响，所以手机档的 LCP 比真机少了接口那一跳。

站点 logo 的版式稳定性单独测：`web/e2e/logo-cls.spec.ts` 在控制台和后台的登录页与外壳上，分别用 1×1、1024×1024、1024×1、1×1024 的 logo、延迟 800 毫秒的 logo 和返回 404 的地址，在 1280px 与 360px 下加载；PerformanceObserver 收集 layout-shift，来源在 logo 槽位内（含随标记尺寸移动的名称）的条目必须为零，标记本身固定 20×20。这样整页 CLS 的波动不会盖住 logo 的位移，也不会把页头其他内容的移动算到 logo 上。

上表的 LCP 是各次运行的原始值。2026-10-30 在 `cb540a5` 上的基线 run（概览页手机 3.496 秒、电脑 0.948 秒，调用页 4.072 秒）是 6 秒上限的参照，也是成对折算的参照。`vitals.spec.ts` 之后每次运行把其余页面的三次加载各夹在前后两次概览页加载之间，按这两次概览页 LCP 的平均值折算，取三次的中位数；概览页自己按主线程 CPU 时间卡（见上），不折算。宿主机忙时目标页和夹着它的参照页一起变慢，比值仍在基线附近；页面自己变慢时参照页不变，折算后的 LCP 会上升。概览页曾经按最快的一次原始加载卡 6 秒，run `41886305660` 因此在宿主忙时失败；后来它和登录页互为参照，run `41983413805` 又因两者的 CPU 争抢不同而失败（见上）。按旧机制复核过的两次 #577 失败说明参照页自己也会被突发盖住：run `41347038111` 后台设置电脑档的原始值是 1488 毫秒，本来低于 1500，是概览页那次测得比基线快（856 对 948 毫秒）把折算系数抬到 1 以上，封顶后不再放大；run `41377869689` 概览页手机档的三次中位数是 6004 毫秒，而同一段里其他手机页的原始中位数是 3264–5436 毫秒，说明突发落在了概览页的三次加载上。#624 的失败是另一种：run `41695611815` 的 `console statement desktop` 折算后 1550.895 毫秒（原始 3080 毫秒，同对参照 1824 对 948 毫秒），而该页在通过的运行里是 780–787 毫秒、平时约为参照的 0.8 倍；固定先参照后目标时，负载在取样期间上升会让目标页每次都比它的参照晚一步，三对同向偏，中位数不抵消。现在目标页前后都有参照：负载按相同幅度上升时折算值回到页面自己的水平，上升更快时两次参照的平均值偏高，折算值只会更低。

差距还没有逐项查清：手机档的 LCP 在慢速 4G 下受往返次数限制（页面、脚本、样式；接口那一跳还没计入），模型页和流水页的 CLS 是内容到达后版面重排，对话框的 INP 是打开时的渲染；长列表掉帧对应的长任务还没定位。逐项修复是后续工作，修一项就收紧一项的上限。

## 设计

### 设计原则

1. **改不坏**：换任何站点、颜色、语言、数据量，页面都成立。
2. **数字有出处**：价格、速度、成功率、质量分都能看到依据和时间。
3. **状态先于功能**：余额、花费、key、报错一眼可见；出了问题直接给出原因和下一步。
4. **中文优先**：中文按中文的排版规矩来，英文同样讲究。
5. **一处惊喜，处处克制**：每个页面只有一个招牌时刻；常用操作不加动画。

### 主题与自由度

外观是主题，不是每个站点各做一套页面：

- **页面结构只有一套**。控制台和管理后台只换颜色和 logo。
- **站点 logo**：站点在后台设置页上传、更换或清除 logo（SVG 清洗后保存，或受限的 PNG/WebP；存储和清洗规则见[账户与租户](domains/accounts.md#站点)）。控制台的侧栏、登录页和 1024px 以下的顶栏显示 `getSite` 给的 `logo_url`，官网页头也读同一个公开接口；没有 logo 或图片加载失败时显示站点名称和自带的标记。图片固定 20×20、`object-contain`，加载前后不改变布局，极端长宽比也不撑开页头（`web/e2e/logo-cls.spec.ts` 核对，见「实测」）。管理后台的登录页和侧栏同样显示站点名称和 logo（公开的 `getAdminSite` 在管理域名给出地址），设置页只用后台返回的 data URL 预览当前 logo；页面标题和导航仍表明这是管理后台。
- **首页是一个插槽**：站点配置里从几套首页设计中选一套。第一版只做 Axiom 自己的首页；给二级站点用的首页模板，等开放二级站点时再做。
- **颜色自动配比**：站长选一个品牌色，或上传 logo 自动取色，系统生成浅色、深色两套完整配色；成功、失败、警告色自动避开品牌色，并且始终配图标。没有配置时用自带的浅色、深色两套（强调色默认青色 cyan）。配色由 `packages/ui/src/brand.ts` 的 `brandStyle` 生成。现在它输出七个旧令牌（`--accent`、`--accent-ink`、`--accent-soft`、`--accent-line`、`--btn`、`--btn-ink`、`--btn-line`）；重做的目标（随 #747 的后续卡交付）是只输出两个值：`--accentSolid`（填充和焦点，对相邻底色不低于 3:1）和 `--accentT`（文字，对页面、面板、卡片、悬停底色不低于 4.5:1）；其余强调色在 `tokens.css` 里用 `color-mix` 推出，只有不是 `#rrggbb` 的写法会被拒绝，其余颜色被调整而不是拒绝。**主按钮不跟品牌色**：它是中性的最深一档（sand12），品牌色只出现在强调、链接、焦点和选中。中性色按应用分：控制台和后台用 sand，官网用 slate，由根元素的属性选择。站点契约为 `brand_color`，由后台 `/sites/{site_id}/brand` 设置、控制台 `GET /site` 读取，`AppShell` 和 `AuthFrame` 通过 `useBrandStyle` 把它写到文档根元素（`<html>`），渲染在页面之外的恢复码对话框也继承同一套变量；字段缺省或旧节点不返回时用默认配色。
- **高对比主题**：用同一套机制，调高对比度参数生成。
- **用户个人**：可以选浅色、深色或跟随系统，再加一个自选主题色；站长可以关闭这项。
- **不开放**：字体、字号、间距、动效节奏。以后要开放，也只给几套精选组合。
- **官网也跟随站点**：模型与价格页、接入文档从第一版起使用站点的配色。
- **3D**：只用来表达产品本身；首屏不等 3D 加载；低端设备、省电模式、"减少动态效果"时换成静态画面；没有 3D 美术资源时，只做程序生成的 3D。

### 视觉方向

第一版的默认外观取自负责人批准的设计稿（画板：官网 Site 与手机版、控制台 AxApp 的浅色、深色、平板、手机版、AxSpec 规范；2026-11-15 起按它重做，见 [#747](https://github.com/TYCT-tyct/Axiom/issues/747)）。结论：

- **字体**：西文和数字用 Instrument Sans（官网和控制台共用一个 400–600 的可变文件），等宽用 JetBrains Mono（静态 400），官网的衬线标题用 Instrument Serif Italic（关键词）和思源宋体（中文衬线，只用于 h1、h2 和登录标题）；中文正文用 MiSans，官网、控制台和后台都用（负责人 2026-11-15）。字体文件一律自己托管，管线和预算见[字体](#字体)。
- **颜色**：深浅两套；一个强调色，青色（cyan）；中性色控制台和后台用 sand（暖灰），官网用 slate（冷灰）。颜色只写在 `tokens.css`，每个颜色用 `light-dark()` 一次写出浅、深两个值。控件边界、焦点、选中的对比度见[对比度令牌](#对比度令牌)。
- **排版**：分两套，见[排版](#排版)。
- **首页**：导航、主视觉，然后六屏——接入、模型与线路、三步开始、上生产前、常见问题、海底。主视觉和海底屏是字符画的海（ASCII 海，canvas 绘制）；首页的数字（价格、延迟、成功率）能从公开接口取的用真数据，取不到的标「示例数据」或删掉（见「内容规则」）。内容从中转站的优点和机制出发，不用概念插画。
- **登录**：留在控制台应用的 `/console/sign-in`（以及 `/register`、`/verify-email`、`/mfa`、`/consent`），不搬到官网。官网的登录按钮按下后，按钮碎成方块流向屏幕右侧（转场 `tiles` 的出发段，约 0.5 秒），然后跳转 `/console/sign-in`；登录页左边是海和导语，右边是表单卡片，从官网点过来时方块聚拢成第一步的形状、标题解码一次，直接打开时没有这一段。减少动态时直接跳转。登录流程按真实接口：邮箱 → 密码 → `signIn`，需要第二因素时进 `mfa`，第一步旁放通行密钥和站点配置的第三方登录；注册按站点是邀请码还是开放注册区分。转场以画板最终版 `tiles`（方块铺开）为准，设计交接说明里的 `swell` 已过时。
- **动效**：克制，规则见[动画](#动画)。
- **不做**：设计稿里和[产品需求](product.md#范围)冲突或没有依据的内容不做，也不做模拟数据：团队层与六种角色、成员、护栏、内容分类、可观测转发、自动充值、发票与对公转账、全局搜索（⌘K）、微信与手机号登录、日志里查看输入输出内容与重放（产品[数据留存](product.md#数据留存)禁止）、轮换 key 与到期可改、插件页、在登录页里创建第一把 key；官网只留中文和英文两种语言；设计稿里更多动物和海底终端命令的彩蛋不做。设计稿里的 Clawd（点 claude 水母带队下潜）和 deepseek 鲸都按设计稿原样保留（负责人 2026-11-15，[#747 评论](https://github.com/TYCT-tyct/Axiom/issues/747#issuecomment-6898383186)）。
- 设计系统（颜色、圆角等变量和组件）在 `web/packages/ui/src/` 的 `css/` 和 `components/` 里，以代码为唯一来源，本文只链接，不复述。

### 排版

两套规则分开：

- **产品界面**（控制台、后台、官网的模型页和文档页、登录表单）：字号只有 12/14/16/24（行高 18/22/24/32），字重只有 400 和 500。
- **官网展示字**（首页、登录页左侧、转场）：展示字号 28/32/40/48/64/72/80，h1 是 `--dsp`，手机、平板、电脑分别为 40/64/80；字重 400/500/600，600 只用在品牌字、非中文的 h1 和所有衬线标题。Instrument Sans 带 `size-adjust: 105%`，让它和回退字体等高。
- 金额、用量、延迟和其他要纵向比较的数字一律用等宽数字（`font-variant-numeric: tabular-nums`），与用哪个字体无关。
- 字体按实际用到的字重裁轴：Instrument Sans 一个 400–600 的可变文件；JetBrains Mono 只要静态 400；中文正文现在只裁 400（500 的字由覆盖爬取决定，见「决策与理由」）；衬线只要 600。

### 字体

- **管线**：用 fontTools 在开发时生成，只在开发机运行（Python，依赖用带哈希的需求文件固定），CI 不需要 Python。源字体按地址和 SHA-256 下载到仓库外的缓存，哈希对不上就失败，源文件不入库（部分字体的许可不允许单独再分发）；源是压缩包时（MiSans 官方下载 `MiSans.zip`）再取出其中写明的文件。生成的 woff2 入库，重跑结果逐字节相同。
- **中文正文 MiSans**：取官方可变字体 MiSans VF，按用到的字重实例化成静态文件。它的字重轴不是 CSS 的刻度（150–700，Regular 是 330、Medium 是 380），所以 CSS 的 400 取轴上的 330。每个应用一个字形：官网 `Axiom CJK`、控制台 `Axiom CJK Console`、后台 `Axiom CJK Admin`。每个应用发自己的一份文件，跨应用共用的分片不会被缓存复用；接口返回的文字（工作区名等）可能含任何字，`unicode-range` 会下载含它的分片，所以一页最坏会下载本字形的全部分片，与别的应用共用字形就把那个应用的字也算进这个最坏情况。各应用在自己的 `src/main.css` 把 `--family-ui` 设成自己的栈（`--family-site`、`--family-console`、`--family-admin`）：共享样式的正文和 `font-sans` 工具类都读它（Tailwind 的 `@theme inline` 把工具类直接写成 `var(--family-ui)`，覆盖 `--font-sans` 到不了工具类）；不设时是 `--family-local`，不含任何裁剪过的中文字形。
- **按页分片**：每页只带它可能用到的字：字符集取自翻译文件（中文是源文件，键有类型，可以静态算出）加覆盖爬取的结果（爬取是重做的目标，随 #747 的官网各卡交付，现在只有静态取字）——端到端测试按计算后的 `font-family` 和 `font-weight` 收集每个场景里实际渲染的字（接口数据所在节点带 `data-user-content`，不收），用来决定 500 字重和衬线落在哪个分片。控制台和后台的「页」是路由按需加载的每个模块：`web/scripts/fonts/routes.ts` 从应用入口沿 import 走，把每页和外壳的代码里出现的字面量（键本身、带点的键前缀、模板字符串的固定开头）对上翻译键，像打包器一样只沿用到的导出走进包的入口文件；官网的页在 `sources.json` 里手写。按「哪些页面用到这个字」精确切开会碎成几百个一字的文件，所以再按代价合并：两个分片合并，使同时用到两者的页面少一个文件（文件自身的表约 0.5KB，加一次请求按 1KB 计），使只用到其中之一的页面多下载另一个的字；每页还计入它的最坏情况（本字形全部分片），合并让每页的最坏情况少一份文件自身的表。只要合计更省就合并。覆盖检查不依赖 Python：翻译或页面代码里出现分片没覆盖到这一页的字，`web/scripts/fonts/coverage.test.ts` 失败并提示重跑管线。
- **预算**：每页的预算 = 这一页可能加载的字体文件去重后的大小之和，用十进制 KB，`web/scripts/budget.ts` 和 `font-budget.ts` 按 `fonts.json` 强制：每页西文 ≤60KB，中文 ≤100KB，官网、控制台和后台每一页都按这两个数（[前端性能指标](#前端性能指标)）。「可能加载」按最坏情况算：这一页所用字形的全部文件，因为接口返回的文字能触发任何分片；只算本页文案用到的分片会漏掉它（例如 27 个字的工作区名能让控制台页多下载 24 个分片）。输出里另列本页文案实际用到的部分。实测（现有文案，2026-11-15）：西文控制台和后台每页 36.4KB、官网首页 40.2KB；中文最坏情况官网首页 38.9KB（正文 35.4KB 加衬线 3.5KB）、模型页 35.4KB、控制台每页 78.9KB（6 个文件）、后台每页 97.3KB（7 个文件）；本页文案实际用到的控制台 51.2–74.9KB（1–5 个文件）、后台 42.1–92.9KB（1–6 个文件）。后台离上限只剩 2.7KB：文案再长就会超出，那时的出路是给接口数据的节点（`data-user-content`）用本机字体栈、不触发分片，预算才能回到按本页文案算。清单格式和命令见 [web/README.md 的「字体」](../web/README.md#字体)。
- **加载**：只有官网预载，只预载 `sources.json` 里标了 `preload` 的首屏中文正文分片（`web/vite.shared.ts` 写进入口页，`budget.ts` 检查入口页预载的正好是这些）；控制台和后台不预载任何字体，分片在页面显示到它的字时才下载。所有字形用 `font-display: swap`。字体到达前，中文先用 `Axiom CJK Fallback` 显示：它是访客本机的中文字体（PingFang SC、Microsoft YaHei、Noto Sans CJK SC、Source Han Sans SC），由管线按 MiSans 的度量写上 `ascent-override: 104.40%`、`descent-override: 28.20%`、`line-gap-override: 0%`、`size-adjust: 100%`（中文字宽都是 1em），换成 MiSans 时行盒不变，页面不跳。不选 `optional`：控制台是单页应用，`optional` 的分片错过约 100 毫秒的等待就整段会话不用，换页时新分片几乎总是错过，控制台就一直是系统字体；回退字体已经对齐度量，`swap` 不增加 CLS。
- **许可**：MiSans 的许可（[官方协议](https://hyperos.mi.com/font-download/MiSans%E5%AD%97%E4%BD%93%E7%9F%A5%E8%AF%86%E4%BA%A7%E6%9D%83%E8%AE%B8%E5%8F%AF%E5%8D%8F%E8%AE%AE.pdf)）要求在软件中注明使用了 MiSans（第 1 条）、在字体的副本中保留版权声明和协议（第 4 条）、不单独分发字体（第 3 条）。做法：子集保留字体自带的版权声明（name 表），入库的子集旁边放协议全文和来源 `web/packages/ui/src/css/fonts/LICENSE-MiSans.txt`；官网页脚写明「本站中文使用了 MiSans 字体」（英文同样写明），官网重做时页脚必须保留这句；子集只作为本站页面的一部分提供，不单独分发。控制台还没有「关于」或帮助区，控制台内的说明等它有了再加。
- **官网首页中文**：衬线只用在 h1、六个 h2 和登录标题（约 53 个不同的字，约 14KB）；正文取 400 一档，约六百多字装得进 100KB；真实文案超出时，按顺序处理：构建失败并列出最贵的字，衬线只留 h1，改写文案替换生僻字，最后才把首屏以下的长段落改用系统中文字体（这一步偏离设计稿，要负责人同意）。
- 换中文正文字体不止改一行：要改 `sources.json` 的源、重跑管线（回退字体的度量随之重算）、重算预算，并更新截图对比的参考字体；`fonts.css` 仍是唯一写字体族名的地方。

### 对比度令牌

按 WCAG 2.2 的 1.4.11（非文字对比度）定，不照搬设计稿的 0.5px 浅线。三个单独的令牌，实测不低于 3:1（Radix 色阶按 WCAG 相对亮度公式算）：

| 令牌 | 用在哪 | 值 |
|---|---|---|
| `--ctl-line` | 控件边界：输入框、关闭态的开关轨道、复选框、分段选择的滑块边、`Select` | 控制台和后台用 sand10，官网用 slate10；对页面、面板、悬停和选中底色 3.16–4.45:1 |
| `--focus` | 焦点环：2px 实线、外偏 2px | 等于 `--accentT`（`tokens.css` 里 `--focus: var(--accentT)`）；对页面、面板、卡片、悬停底色浅色不低于 4.79:1、深色不低于 7.59:1，满足文字的 4.5:1；对选中底色（sand4）浅色 4.45:1，只要求焦点的 3:1 |
| `--sel-ind` | 选中指示：导航当前项的实心图标和文字、分段选择当前项的文字 | 等于最深的文字色（sand12） |

- 文字令牌（`--t1`–`--t3`、`--accentT`、`--okT`、`--warnT`、`--badT`）对页面、面板、卡片、悬停底色，以及状态色 12% 的浅底不低于 4.5:1。以下是未经调整的色阶实测，不是最终令牌值：设计稿浅色的 amber11 在页面底色上只有 4.38:1，cyan11（4.18:1 在悬停底色，4.26:1 在强调浅底）、tomato11、grass11 在悬停或浅底上也不到 4.5:1。最终令牌把这几个的浅色值向第 12 阶移 15%（`tokens.css` 里的 `--accentT`、`--okT`、`--warnT`、`--badT`），深色不变；`--okT` 是为同样的理由补的。`web/scripts/tokens.test.ts` 从 `tokens.css` 读值检查这些比值（已有）。
- 控件边界用 1px；0.5px 的细线只留给卡片轮廓、表格行线这类装饰性分隔。
- 只靠底色变化表示选中不够 3:1，所以选中一律配 `--sel-ind`（设计稿「选中时变实心」的做法）。设计稿原来的焦点色 cyan8 和 sand8 线都不合格，不用。
- 品牌色混合之后：`brandStyle` 保证 `--accentT` 对页面、面板、卡片不低于 4.5:1；单元测试再保证它对悬停、选中底色不低于 3:1，`--accentSolid` 对所有底色不低于 3:1，`brand.test.ts` 的极端色网格覆盖；组件样式里 1px 及以上的边线（`border`、`outline`、`box-shadow`）引用的令牌，`web/scripts/styles.ts` 逐个算它对 sand 和 slate、深浅两套里页面、面板、悬停、选中底色的对比，低于 3:1 就失败；经本模块自定义属性引用的按它的每个值算，边线画出的颜色必须正是一个颜色令牌或 `transparent`，混色、`currentColor`、没写颜色、未定义的名字都失败；`--bw` 画的线算装饰、带模糊的阴影不是边线，都不查；在页面里逐个可聚焦控件实测（`gate.spec.ts`，含五种极端品牌色）待定。

### 动画

所有动画有一个所有者（海、首屏入场、语言与深浅切换、官网外壳、各屏、转场、登录页的方块、控制台的 CSS 动画），遵守同一套生命周期：

- **加载**：首屏内容出现之后才加载；首屏只带约 3KB 的入场，海、偏好、外壳动效在首屏之后空闲时加载，各屏的逻辑在接近视口时加载，转场在第一次按下登录按钮时加载，彩蛋在触发时加载。模块加载失败时页面照常可用，没有未处理的错误。
- **暂停**：标签页隐藏或滚出视口时暂停；所有 JS 动画走同一个帧循环，卸载后计数归零、监听器移除。
- **减少动态**：`prefers-reduced-motion: reduce` 下不播放：海只画一帧固定种子的静止画面，入场、转场直接到终态或直接跳转，语言和深浅直接切换，控制台的 CSS 动画一律 `animation: none`、不做 View Transition。这覆盖设计交接说明里「不做减少动态版本、一律播放」的规定，是负责人 2026-11-15 在 [#747](https://github.com/TYCT-tyct/Axiom/issues/747) 的要求。
- **CSP**：源码里不使用 `innerHTML`、`outerHTML`、`insertAdjacentHTML`、`cssText`、`setAttribute('style')`（`cssText` 的 setter 在 CSP3 里属于 `unsafe-eval` 一类）；单个样式属性的 CSSOM 写法可以用；SVG 资源里的 `style` 属性在构建时改成类名。
- **测试**（目标：测试文件随官网首屏与海 S1 交付，现在还不存在）：每个 JS 驱动的所有者由 `e2e/fx.spec.ts` 证明：首屏前没有请求该模块；隐藏或滚出视口后回调不再执行；减少动态下不执行回调；卸载后归零；模块 404 时页面照常。`e2e/csp-deferred.spec.ts`（同样随 S1 交付）把官网滚到底、切语言和深浅、播完转场、走完登录，再打开控制台的每种浮层，全程不得有 `securitypolicyviolation` 和控制台错误。
- **体积**：官网首屏脚本沿用前端性能指标；首屏以下的每个块 ≤50KB，延迟加载的动画与资源（如接入屏的等距图，作为单独的 `.svg` 取回）合计 ≤150KB，按真实的模块图加总。

### 内容规则

- 页面上的价格只和官方原价比；不点名比较，也不贬低其他平台。
- 不编造客户标志、评价和数字；演示用的界面和数字标明"示例数据"。
- 数据隐私只写做得到的事，例如"对话内容按账户加密存储，任何人都不能通过产品查看"；不写"不用于训练"（见[产品需求的决策](product.md#决策与理由)）。

### 前端工程

- 代码在 `web/`，是一个 pnpm 工作区；结构、命令和必须遵守的规则见 [web/README.md](../web/README.md)。
- 页面只通过 HTTP 接口取数据；要用别的前端替换它，或对接某个约定（会话、CSRF、错误、分页、幂等、金额），读[前端接口指南](frontend-api.md)。
- 官网在公网监听的 `/`，控制台在 `/console/`，管理后台只在管理监听上。
- 控制台和管理后台构建时写入同一棵代码树构建出的程序的版本号（`axiom version` 输出的整行），之后定时和切回标签页时向 `GET /api/console/v1/version`（后台是 `/api/admin/v1/version`）询问正在运行的版本，不同就提示刷新。
- 内容安全策略只在 `web/vite.shared.ts` 定义一次。构建产物嵌入 Go 程序时（`just web-embed`），这个字符串一并写进嵌入的文件，Go 服务原样发送，不另写一份；缓存、压缩和回退的规则见[平台的「前端文件」](../internal/platform/README.md#前端文件)。
- 西文和数字用自己托管的 Instrument Sans，等宽用 JetBrains Mono，中文字体和分片见[字体](#字体)；字体族名只写在 `fonts.css`。
- **样式归组件（架构 B）**：保留 React、TanStack、i18n、`DataState` 这套骨架；设计稿的 CSS 近原样提成 CSS Modules（`*.module.css`），由一个组件独占：只能放在 `packages/ui/src/components/**`（产品组件）和 `site/src/home/**`（官网各屏），且只被同目录、同名的一个 TSX 导入，规则平铺、不嵌套（检查读不到嵌套和 `@scope` 这类 at 规则里的选择器，一律拒绝）。页面只组合组件，不写样式：应用代码（`console/`、`admin/`、`site/src`，`home/` 除外，以及 `packages/app`）不导入任何 CSS，TSX 里不写 `className`，`style` 只许 `--*` 自定义属性。全局 CSS 只有 `tokens.css`、`fonts.css` 和 `base.css`（`base.css` 还没有，待定：基础组件不需要全局规则）；颜色字面量只出现在 `tokens.css`。组件清单是「做新组件之前先查」的唯一出处，页面需要清单里没有的东西时停下来补组件，不在页面里自己造。
- **检查用棘轮落地**：新规则只对新组件和已迁移的模块生效；旧用法记在一份只减不增的基线里（`web/scripts/style-baseline.json`，按文件记数量，新文件必须为 0，数量减少时必须同时更新基线），迁移完的模块进基线的 `migrated` 列表、之后必须为 0；这些规则和源码里不写 HTML 与样式文本（见「动画」的 CSP 一条）由 `web/scripts/styles.ts` 检查，它的单元测试对整棵树跑一遍，所以随 `pnpm test` 进 CI；jscpd 把 CSS 也纳入重复检查。旧的 `packages/ui/src/styles.css` 和 Tailwind 在迁移期冻结，新旧并存，`legacy.css` 把旧令牌名指到新色板，每个 PR 都能单独构建、通过。Tailwind 的去留见「待定问题」。
- **写入策略**：由业务对象决定，不由面板决定（`EditPanel` 只负责呈现）。控制台契约没有 `PATCH`，`PUT` 是整体替换（见[前端接口指南](frontend-api.md)），所以默认**显式提交整个对象**：面板持有整个对象的草稿，「保存」时一次 `PUT`，保存期间锁住表单，失败时保留草稿并显示失败提示。只有这几类可以「改一项就生效」：请求体就是一个值的接口（服务商 key 的启停、扣费顺序）；带乐观锁的接口（路由默认、工作区路由默认带 `version`，路由预设带 `revision`，冲突 409 `stale_revision` 时重新读取再提示）；通知偏好，条件是写入串成队列，每次在上一次返回的对象上改一项再发。key、工作区、预算、命名预设和路由预设的规则编辑器必须显式提交；key 的启停是唯一例外：取最新的 key，只翻转 `disabled` 再 `PUT`，串行发送，撤销就是反向再做一次。后台一律走 `ChangeDialog`，不用即时保存。「可撤销」只给有反向操作的（停用、启用）；删除仍要确认，不做延迟发送的假撤销。
- **外壳与滚动**：由文档本身滚动，不做内部滚动容器：顶栏 `position: sticky` 贴顶，侧栏 sticky、高度为视口减顶栏、内部自己滚动，手机的底部标签 sticky 贴底，这样浏览器的滚动恢复、页内查找、空格翻页、手机地址栏收起和打印都照常。只有浮层内部滚动（对话框正文、右侧面板、底部面板、平板和手机上的详情面板）。路由跳转后焦点移到主区的 h1，且页面回到顶部；跳过链接指向主区。
- **截图对比（只在开发时用）**（目标，随截图对比工具 F1c 交付，`web/e2e/design/` 现在还不存在）：它在一次性、断网、不留存储的浏览器上下文里执行设计稿自己的组件类，按画板对照产品页：1440、820、390 三个视口，深浅两套，固定时区、语言、时钟、随机种子和就绪条件，参考页用未裁剪的源字体，canvas 比较固定种子的终态；产品裁决造成的差异按区域登记（每条写依据），不用整页阈值兜底，登记之外只允许抗锯齿量级的差异。没设 `AXIOM_DESIGN_DIR` 就跳过，不进 CI；设计稿文件不入库，只当数据读。设计稿只有中文版，英文靠 `gate.spec.ts` 的不溢出和无障碍检查加人看截图。
- 官网、控制台登录页共用的动画引擎（海、方块拼形、标题解码）放在一个共享包里，只有一份；生命周期见[动画](#动画)。

站点 logo 的存储、公开地址和缓存按[负责人授权记录](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)落地，原文「遇到问题自己解决问题和判断最优而不是问我。」；数据模型和清洗规则见[账户与租户的「站点」](domains/accounts.md#站点)，这里只记前端可见的取舍。

| 决策 | 理由 |
|---|---|
| logo 由站点的公开接口按内容哈希提供，页面不直接引用上传文件或第三方地址 | 地址里的 SHA-256 让图片可以缓存一年且永不串图，换 logo 就是换地址；同源请求满足 `img-src 'self'`，不把站点品牌交给外部图床，也不需要 `blob:`。失败时回退到名称和自带标记，页面仍然完整 |

## 决策与理由

| 决策 | 理由 |
|---|---|
| 外观做成主题：一套页面结构，换颜色和 logo；首页做成可选的插槽 | 负责人提出（2026-10-12）："他类似于主题，首页我们做多个版本可以选择，控制台也差不多，可以切换主题和颜色"。一套结构只需维护一份，换站点不会改坏 |
| 颜色由一个品牌色自动生成深浅两套，不开放自由写样式 | 负责人提出颜色自动配比。自动生成能保证对比度达标、状态色不和品牌色撞色；自由写样式很容易做出看不清的页面 |
| 不开放字体、字号、间距、动效节奏 | 这几项决定排版质量，随意改最容易破版；以后要开放只给精选组合。负责人对自由度边界的答复："你自己判断，实现最优，基本同意" |
| 首页第一版只做一套 | 负责人提出首页可以有多套设计供选择、第一版只做一套；先把一套做精 |
| 视觉、内容、结构分别向 Linear、HeyRoute、OpenRouter 学，不走比喻和概念创意的方向（**视觉部分已被 2026-11-15 的设计稿取代**，见下方各行；内容以 OpenRouter 为基线仍然有效） | 负责人否定了比喻类方向（"太抽象""和 ai 也没那么贴合"），选定向这三家学习；视觉方向和首页章节负责人答复"行"。后来负责人给出了定稿的设计稿并要求照它实现（[#747](https://github.com/TYCT-tyct/Axiom/issues/747)），深色优先、冰蓝强调色、Inter 和十二章节首页不再适用 |
| 参照的网站只学不仿 | 负责人："别人的网站只是一种学习目标，不代表模仿或者其他，我们要实现自己的内容" |
| 页面内容以 OpenRouter 为基线 | 负责人："其他的去仿造 openrouter 的页面内容就行吧"。与 CONTRIBUTING 中"产品行为默认对齐 OpenRouter"一致 |
| 3D 只用来表达产品，首屏不等 3D，低端设备换静态画面 | 负责人同意可以用 3D。首屏等 3D 加载会拖慢首屏，在低端设备上会卡 |
| 中文优先，英文同样讲究 | 负责人同意开发者的推荐："按照你说的做"。国内和海外同时服务，两种语言都要完整 |
| 字体等静态资源自己托管，不依赖外部服务 | 负责人要求（2026-10-13）只用国内也能访问的资源，能自己托管的就自己托管；页面也因此少一次跨域连接 |
| 充值退款在控制台申请、后台审核，套餐退款只由管理员发起；控制台的用户通知第一版只发邮件，不做站内消息（运营的告警和审批通知见[运营的「通知」](domains/operations.md#通知)）；分组代号不单独成页；协议页面先有，内容待公司主体 | 开发者决定，负责人授权"你自己判断"，页面清单负责人回复"同意" |
| 未登录时显示站点给新账户的默认等级的价格 | 负责人在对话中授权开发者按推荐决定（2026-10-13）。访客注册后付的就是看到的价，不会注册后才发现变了；新账户进入哪个等级由账户与租户的设计写明（Issue #23） |
| 官网是单独的应用，与控制台、管理后台共享设计系统和模型价格组件 | 负责人在对话中授权开发者按推荐决定（2026-10-13）。理由和放弃的方案见[总体架构](architecture.md#技术选型)「前端交付」 |
| 页面文字的检查用 Biome 的 `noJsxLiterals` | 架构已选 Biome，这条规则移植自 eslint-plugin-react 的 `jsx-no-literals`；它不查属性里的文字，由评审补上。不选 eslint-plugin-i18next：为一条规则要再引入 ESLint 和它的解析器，依赖多出约百个包 |
| 复杂度、长度、重复和未使用代码的检查与 Go 一侧对齐 | 阈值同 `.golangci.yml`。认知复杂度用 Biome 的 `noExcessiveCognitiveComplexity`，上限 15，实测 JSX 里的条件和回调也计入。圈复杂度上限 12，同 cyclop，由 `web/scripts/limits.ts` 检查：Biome 没有这条规则，两者也不能互相代替（12 个并列的 `if` 认知复杂度 12、圈复杂度 13）；分支按 cyclop 计 `if`、循环、`case`、`&&`、`||`，再加上 JavaScript 的三元表达式、`catch` 和 `??`，嵌套函数单独计算，同 ESLint 的 `complexity`。函数 60 行、文件 500 行（不计空行和注释，测试不限函数长度）也由它检查，按语法树的词法单元数行，注释不算，字符串、模板和 JSX 里的文字照算：Biome 有这两条规则，但实测不计 JSX 里的行（Biome 2.5.15，66 行 JSX 的函数只算 3 行），组件写多长都能通过；不选 ESLint 的长度规则，理由同上一行。未使用的文件、导出和依赖用 knip，包的入口导出也查：这些包只给本仓库的应用用，没有应用引用的导出就是多余的。重复代码用 jscpd，最少 50 个词法单元，即它的默认值；Go 的 dupl 100 按语法树节点计，单位不同，不照搬。测试不查重复，同 Go；语言表的 `locales/*/index.ts` 只按同样的顺序列出命名空间，结构必须一致，也不查重复 |

| 控制台的表单把结果未知的请求写进 sessionStorage；兑换码表单只存幂等键 | 刷新或从支付渠道返回后，同一个键原样重发，服务端重放第一次的结果而不是再做一次，所以存下的请求体不能含秘密，只有退款、充值这类不含凭证的表单用它。兑换码是凭证：页面只在内存里持有，落盘的只有键；刷新后表单要求重新输入同一个码，服务端按码的哈希判断是不是同一个请求，不同的码用同一个键会被拒（`idempotency_key_reused`），重新输入不会兑换两次。升级时读到旧版的 `${scope}/axiom.console.redeem.attempt`（整个请求，码是明文）就把键迁到新键并删掉旧记录，写入时也删；旧记录不会留在浏览器里。不选把兑换码一起写进 sessionStorage：结果未知时，一个可能仍然有效的码以可读形式留在浏览器里（#530 发现 5）；也不选丢掉键换新键重试：第一次可能已兑换，第二次会报码已用过，用户看不出第一次的结果 |
| M1 后台的目录页对价格表只编辑基础价格，按次计费的项另标；分档价格（按请求大小、服务层级）保持原样、只读，其他基线信息用 JSON 输入；更换价格来源一次一个币种 | 负责人在对话中授权开发者按推荐自行决定。价格表是 12 项 × 分档 × 3 个服务层级，完整编辑器是最大的一块界面；M1 的人工维护只需基础价格，分档来自同步。改基础价格时保留已有分档，不会丢；以后要手工维护分档再加编辑器 |
| 后台订单页取“后台账户所在的站点”，订单按用户或用户账户（`user_`、`acct_`）筛选，不按邮箱；退款队列只列冻结的退款：未批准的等决定，已批准的线下退款等凭证 | 契约在 M1 没有站点列表，站点 ID 与设置页同源。支付模块读不到账户模块的邮箱，按用户或账户筛选不用跨模块查表；每行仍显示用户 ID 兜底。队列只列冻结的退款：未批准的等决定，已批准的线下退款留在这里显示等待凭证；终态在订单行下看 |
| 订单的「实付」列展示 `paid_total`、`paid_fee`，报价另标；「入账」列展示 `credited`，报价另标；缺少字段时显示状态而不是零 | 渠道实收可能与报价不同（折扣、部分支付、拒付），把 `total` 当实付会误导；`credited` 也应区分「未入账」和「未记录」：已支付或状态未知却没有 `credited` 是旧节点的缺失字段，只有待支付等已知未支付状态才显示「未入账」，不把报价冒充成付款 |

# 合并队列

`main` 只经合并队列合并：`.github/workflows/train.yml` 决定何时运行，逻辑和不变量在 `scripts/train.py`。要求分支最新时，每合并一个 PR，排队的其他 PR 的构建就作废；不要求时，两个各自通过的 PR 合在一起会弄坏 `main`（重复的迁移版本号、只在合并后失败的测试）。队列把排队的 PR 按顺序合到最新 `main` 上一起构建，通过才落地。

- **构建分层**：`ci.yml` 把构建拆成并行的 `static`、`go-test`（两个矩阵分片）、`web`、`e2e`（两个矩阵分片）、`vitals`（前端的 LCP、INP、CLS 计时，一次一个测试，不和别的测试抢 CPU）、`bench`、`deploy` 作业，`build` 聚合它们，是唯一必需的检查。PR 的构建跑 `static`、按路径选择的 `web`（构建、类型和其余前端检查；只改前端、API 或构建输入以外文件时跳过，`build` 仍通过；列车和 `main` 的非轻量构建始终跑前端）和只在改动触及页面构建输入时跑的 `vitals`；`go-test` 和两个 `e2e` 分片只在列车和 `main` 上跑：每个 PR 的测试只跑一次，就是在它的列车里，测试失败由列车二分找出元凶（理由和测量见[总体架构的「CI 在哪跑」](../architecture.md)）。`vitals` 是计时，`main` 每次落地后都跑，PR 和列车在页面构建输入（`web/` 和生成页面客户端所用的 `api/*.yaml`）没变时跳过：没改这些的树里页面代码和资源不变，量到的差别只是 runner 的负载（#503）。分片缓存键包含序号和总数；列车和 `main` 上非轻量构建的每个分片都必须成功，跳过或取消也不能通过 `build`。PR 上的检查拦格式、静态检查和前端构建这类便宜的错误；列车和落地后的 `main` 再加 `go-test`、`e2e`、`bench`、`deploy` 和 `just check` 比 `check-ci` 多的 `docs`、`secrets`，列车的基准比较从基础分支提取 `tools` 模块运行 `tools/benchgate`，门禁或其模块依赖变动时再运行当前版本，两次都通过才放行；所以测试、基准或部署的回归由列车发现，它给弄坏它的 PR 加 `train:failed` 并附失败的构建。跨 runner 分片在单个分片时保持四个 worker，两个分片同时跑时每个三个、合计六个，为浏览器、测试框架和应答模拟请求的测试进程留出 CPU 余量（构建 41922423312 的测量见[总体架构的「前端容器」](../architecture.md)）；目标是把列车的最长作业压到约 5 分钟；分片数和每分片 worker 数以列车构建的作业耗时为准，不因单次缓存命中就增加并发。
- **发车**：PR 加 `queue` 标签、一个 PR 的构建成功结束（`workflow_run`）、或每 10 分钟的定时任务运行时发车。定时任务从未触发过（#253），前两者不依赖它；没有可上车的 PR 时不做构建、不调起别的运行，只清掉上一次留下的列车分支。
- **排队**：评审通过、自己的必需检查全绿后加标签 `queue`。按加标签的时间排；同时有 `hotfix` 的排到最前。加标签时立刻拿它试合并 `main` 和排在前面的每个 PR，并查迁移版本号，有冲突就当场移出队列并评论。检查还没全绿的 PR 原地等，绿了自动进入下一班。
- **出队**：去掉 `queue` 标签。正在构建的列车整班不落地，其余的 PR 留到下一班重新构建：构建通过只证明整班车的树，后面的 PR 可能恰好修好了前面几个合在一起的问题。
- **一班车**：同一时间只有一班。从最新 `main` 依次合并排队的 PR，迁移版本号重复或低于已落地/前车的最高号、冲突、或工作流文件两边都改的 PR 被移出；然后在 `train/main/<编号>` 分支上调起 `ci.yml` 构建，全部作业（含 `changes` 和 `build`）跑在 `RUNS_ON_TRAIN`（带 `axiom-train` 标签的前四个 runner；脚本配置与扩容测量见[总体架构的「CI 在哪跑」](../architecture.md)）上并排队，不碰驱动占着的便宜池，除了 PR 也跑的 `static`、`web`，还跑只在列车和 `main` 上跑的 `go-test`、两个 `e2e` 分片、`bench`、`deploy` 和 `docs`、`secrets`（PR 上 `docs`、`secrets` 由 workflow.yml 跑），整班车只有轻量路径（复用 `scripts/workflow/changes.py` 的规则和 `.github/project-workflow.toml` 的 `[lanes]`，仓库脚本也在此配置）时，仅 `static` 跑 `just md-checks scope secrets`（含 `script-tests`、文档符号、模块依赖和产物检查），重作业全部跳过，`build` 接受这些跳过；纯 Markdown 和混合轻量改动用同一套检查，PR 的 secrets 由独立工作流运行。`bench-compare.sh` 的变动走重道，在列车中执行比较门禁。空 diff、diff 失败或 lanes 配置无效时回到全量。落地后的 main push 始终跑全部检查；`release-check.sh` 照常构建、签名和演练，但只有显式发布运行上传交付物，步骤见[发布前](release.md#选择和核对)。通过后整班落地：先确认每个 PR 仍开着、仍在排队、目标仍是 `main`、头提交仍是组装时记录的，有一个不是就一个都不落地；然后用列车的部署密钥把 `main` 快进到构建通过的那个提交（`TRAIN_LAND_URL`），一次引用更新，整班要么全在 `main` 上、要么完全不在。检查之后 PR 再怎么变（推新提交、改目标、去掉 `queue`）也只影响它自己，`main` 上落的仍是构建通过的那个提交。列车里每个 PR 是一个合并提交：第一父是前一个 PR，第二父是 PR 记录的头提交，提交说明是 PR 标题加 `(#编号)` 和去掉会话链接的描述（组装时的版本），末尾的 `Train:` 尾注记下编号、头提交和列车的基础提交；所以 `git log --first-parent main` 上每个 PR 仍是一个带标题和描述的提交，PR 的头提交进了 `main`，GitHub 把它标成 MERGED，描述里的 `Closes #N` 照常关闭 Issue。这次推送不是 `GITHUB_TOKEN` 做的，会照常触发 `main` 的 push 工作流（`ci.yml` 和 `workflow.yml`），列车不再另外调起构建。推送被拒（部署密钥缺失或失效、`main` 已变）时整班不落地：这次列车失败、删掉落地记录，PR 留在队列里，下一班从当时的 `main` 重新组装。列车没有逐个合并 PR 的路径，`main` 上只会出现整班列车或什么都没有。
- **失败**：失败全是 `.github/flaky.toml` 登记的测试时，重跑一次失败的作业。否则并行构建列车的几个前缀（切点数由 `train.yml` 的 `LANE_SIZE` 控制，默认 2；四个 runner 决定构建内作业的并发度），合并最长的通过前缀，在失败的那段里继续切，直到剩一个 PR：给它加 `train:failed`、在头提交上标 `merge-train` 失败、评论附失败的构建并移出队列；它后面的 PR 留给下一班。
- **旧基准门禁误报的恢复**：列车 HEAD 是 base 的后代，所以未改门禁的 PR 已经继承基础分支的门禁修复；另取 base 模块的作用是门禁自身变动时仍执行旧策略，两版默认都必须通过。如果旧版误报导致门禁修复无法上车，先准备只改门禁和回归测试的独立 PR，保存同一 base/head 的原始基准输出、旧版误报复现和新版拒绝真实分配回归的证据，完成独立评审及其余检查。只有负责人在该 PR 明确批准修复提交、执行管理员和临时旁路窗口后，管理员才可在无列车落地的窗口按以下人工路径处理：保存 `protect main` 规则集原配置，临时给执行管理员配置仅限 PR 合并的 bypass actor，核对批准的头提交后 squash 合并这一个修复 PR，随即恢复原配置（合并失败也恢复），确认旁路已撤销并运行 `main` 的完整 CI 后再恢复正常入队。该规则集的 bypass actor 只有列车用的部署密钥（见「权限」），对管理员用 API 合并 PR 不生效，所以这条路径仍需负责人批准后临时配置。不伪造 `build` 或 `merge-train` 成功，不放行业务改动，不把旧门禁失败改成自动忽略；没有明确批准就保持 PR 阻塞并附复现证据。
- **标签**：`queue` 在排队；`hotfix` 排到最前；`train:solo` 单独坐一班车：它前面的 PR 先成一班，它自己一班，失败时不把别的 PR 拖进二分，给首次跑 e2e 这类风险高的 PR 用；`train:conflict` 因冲突、迁移版本号重复或低于已落地/前车的最高号或工作流文件两边都改被移出；`train:failed` 因弄坏列车的构建被移出。修好后重新加 `queue`，排队时的检查通过会去掉这两个标签。
- **看失败的列车**：PR 评论里的链接是失败的构建，就是 `ci.yml` 在 `train/main/...` 分支上的一次运行，日志和 PR 的构建一样看；train 运行的摘要按时间列出每班车的成员、每次构建的结论和链接。
- **中断**：落地中途停下（runner 被杀）时，通过的列车留在 `train/main/land` 分支上，带 `train/verified` 状态；下一次运行发现 `main` 已在列车的提交上（快进已完成，`main` 的构建已由那次推送触发）就只删掉这个分支，否则重试这一次推送。推送被拒时列车失败，记录一并删掉。升级前旧版逐个合并留下的记录也在这里收尾：整班 PR 都已合入、`main` 的历史里却没有列车的提交（不是快进落地）时，先补调一次 `main` 的 `ci.yml`——旧路的 API 合并不触发 push 工作流——再删记录；只合入了前缀时，`main` 上可能有没被构建测过的工作，列车停住并保留记录，检查、revert 之后删掉 `train/main/land`，队列才恢复。这个分支在落地完成或失败、旧记录收尾之后才删除。
- **不稳定测试**：`.github/flaky.toml` 每条写一个测试（`包路径.TestName`）和一个开着的 Issue；Issue 关闭后 CI 的 build 失败，提醒删掉这条。只认 Go 测试：编译、lint、前端、端到端和部署检查的失败都不算不稳定。
- **权限**：整班落地用部署密钥（`TRAIN_DEPLOY_KEY`，一把只有该仓库写权限的部署密钥）把 `main` 快进；`protect main` 规则集的 bypass actor 是 `DeployKey`，所以只有持有该仓库一把可写部署密钥的人能推 `main`，普通用户令牌（包括管理员）仍被「只经 PR 合并」和必需检查拦住。密钥保存在 `train` 环境里，该环境的分支策略只允许 `main`：PR 分支或其他 ref 上的工作流读不到它。列车分支和落地记录的推送仍用 `GITHUB_TOKEN`；`GITHUB_TOKEN` 本身推不动 `main`，GitHub Actions 也不能作为 bypass actor（个人仓库上 API 拒绝：`Actor GitHub Actions integration must be part of the ruleset source or owner organization`）。`DeployKey` 放行仓库里所有可写部署密钥，API 不保留单个 key id（`actor_id` 存成 null），所以仓库里只保留列车这一把可写部署密钥；只读的部署密钥本来就不能推。这是 `main` 唯一的落地路径：`merge-train` 仍在必需检查里，列车不再为任何 PR 标成功，所以直接合并 PR（界面或 API）过不了必需检查。`manage.py protect` 会重写规则集并清空 bypass actors，运行它之后要按本节重新加上 `DeployKey`。重建或轮换时：生成 ed25519 密钥，用 `gh api -X POST repos/<owner>/<repo>/keys` 以写权限加入，`gh secret set TRAIN_DEPLOY_KEY --env train` 存入私钥，再把 `DeployKey` 写回规则集。
- **为什么用部署密钥作旁路**：负责人 2026-10-28 授权「遇到问题自己解决问题和判断最优而不是问我。」（转载于 [issue #309 的评论](https://github.com/TYCT-tyct/Axiom/issues/309#issuecomment-6478816797)），规则集旁路因此由实现者选定。可列的 actor 只有 `Integration`、`OrganizationAdmin`、`RepositoryRole`、`DeployKey`：个人仓库上 GitHub Actions 作为 `Integration` 被 API 拒绝；`RepositoryRole` 按角色放行，管理员（也就是所有会话用的令牌）都能绕过，等于取消「只经列车合入」；`DeployKey` 只放行仓库的部署密钥，密钥又放在只允许 `main` 的环境里，所以选它。代价是任何人给仓库加一把可写部署密钥都会得到同样的旁路，因此「权限」一节要求只保留列车这一把。
- **为什么是合并提交而不是线性的 squash 提交**：快进推上去的若是 squash 提交，PR 的头提交不在 `main` 上，GitHub 只把 PR 显示为 CLOSED，`Closes #N` 失效，关 PR、关 Issue 都得脚本补做；合并提交让 GitHub 自己认出合并。代价是 `main` 不再是线性历史：PR 分支上的中间提交经第二父进入历史，按 `--first-parent` 看才是一 PR 一提交。

迁移允许预留跳号，但不允许回填已应用高号之前的低号。`just migrations` 用 `scripts/migration_order.py` 对 main 核对，列车组装及入队预检对 main 和前车的版本再核对：发现低号即移出，要求重编号。这样 23 先落地时，后来带 22 的 PR 必须取更高号，持久库不会在新库 CI 通过后才被 goose 拒绝。

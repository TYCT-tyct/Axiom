# 合并队列

`main` 只经合并队列合并：`.github/workflows/train.yml` 决定何时运行，逻辑和不变量在 `scripts/train.py`。要求分支最新时，每合并一个 PR，排队的其他 PR 的构建就作废；不要求时，两个各自通过的 PR 合在一起会弄坏 `main`（重复的迁移版本号、只在合并后失败的测试）。队列把排队的 PR 按顺序合到最新 `main` 上一起构建，通过才合并。

- **构建分层**：`ci.yml` 把构建拆成并行的 `static`、`go-test`、`web`、`e2e`（两个矩阵分片）、`bench`、`deploy` 作业，`build` 聚合它们，是唯一必需的检查。PR 的构建只跑 `static` 和按路径选择的 `web`（构建、类型和其余前端检查；只改前端、API 或构建输入以外文件时跳过，`build` 仍通过；列车和 `main` 的非 Markdown 构建始终跑前端），`go-test` 和两个 `e2e` 分片只在列车和 `main` 上跑：每个 PR 的测试只跑一次，就是在它的列车里，测试失败由列车二分找出元凶（理由和测量见[总体架构的「CI 在哪跑」](../architecture.md)）。分片缓存键包含序号和总数；列车和 `main` 上非 Markdown 构建的每个分片都必须成功，跳过或取消也不能通过 `build`。PR 上的检查拦格式、静态检查和前端构建这类便宜的错误；列车和落地后的 `main` 再加 `go-test`、`e2e`、`bench`、`deploy` 和 `just check` 比 `check-ci` 多的 `docs`、`secrets`，列车的基准比较从基础分支提取 `tools` 模块运行 `tools/benchgate`，门禁或其模块依赖变动时再运行当前版本，两次都通过才放行；所以测试、基准或部署的回归由列车发现，它给弄坏它的 PR 加 `train:failed` 并附失败的构建。跨 runner 分片保持每个容器四个 worker 的 CPU 余量，目标是把列车的最长作业压到约 5 分钟；分片数以列车构建的作业耗时为准，不因单次缓存命中就增加并发。
- **发车**：PR 加 `queue` 标签、一个 PR 的构建成功结束（`workflow_run`）、或每 10 分钟的定时任务运行时发车。定时任务从未触发过（#253），前两者不依赖它；没有可上车的 PR 时不做构建、不调起别的运行，只清掉上一次留下的列车分支。
- **排队**：评审通过、自己的必需检查全绿后加标签 `queue`。按加标签的时间排；同时有 `hotfix` 的排到最前。加标签时立刻拿它试合并 `main` 和排在前面的每个 PR，并查迁移版本号，有冲突就当场移出队列并评论。检查还没全绿的 PR 原地等，绿了自动进入下一班。
- **出队**：去掉 `queue` 标签。正在构建的列车整班不落地，其余的 PR 留到下一班重新构建：构建通过只证明整班车的树，后面的 PR 可能恰好修好了前面几个合在一起的问题。
- **一班车**：同一时间只有一班。从最新 `main` 依次合并排队的 PR，迁移版本号重复、冲突、或工作流文件两边都改的 PR 被移出；然后在 `train/main/<编号>` 分支上调起 `ci.yml` 构建，全部作业（含 `changes` 和 `build`）跑在 `RUNS_ON_TRAIN`（带 `axiom-train` 标签的前四个 runner；脚本配置与扩容测量见[总体架构的「CI 在哪跑」](../architecture.md)）上并排队，不碰驱动占着的便宜池，除了 PR 也跑的 `static`、`web`，还跑只在列车和 `main` 上跑的 `go-test`、两个 `e2e` 分片、`bench`、`deploy` 和 `docs`、`secrets`（PR 上 `docs`、`secrets` 由 workflow.yml 跑），整班车只改 Markdown 时只跑 `just md-checks` 和 `secrets`。通过后整班落地：先确认每个 PR 仍开着、仍在排队、目标仍是 `main`、头提交仍是组装时记录的，有一个不是就一个都不合并；然后按顺序 squash 合并，只按记录的头提交合并（`--match-head-commit`），合并前在头提交上标 `merge-train` 成功，每次合并前和落地后核对 `main` 的树与列车一致。
- **失败**：失败全是 `.github/flaky.toml` 登记的测试时，重跑一次失败的作业。否则并行构建列车的几个前缀（切点数由 `train.yml` 的 `LANE_SIZE` 控制，默认 2；四个 runner 决定构建内作业的并发度），合并最长的通过前缀，在失败的那段里继续切，直到剩一个 PR：给它加 `train:failed`、在头提交上标 `merge-train` 失败、评论附失败的构建并移出队列；它后面的 PR 留给下一班。
- **标签**：`queue` 在排队；`hotfix` 排到最前；`train:conflict` 因冲突、迁移版本号重复或工作流文件两边都改被移出；`train:failed` 因弄坏列车的构建被移出。修好后重新加 `queue`，排队时的检查通过会去掉这两个标签。
- **看失败的列车**：PR 评论里的链接是失败的构建，就是 `ci.yml` 在 `train/main/...` 分支上的一次运行，日志和 PR 的构建一样看；train 运行的摘要按时间列出每班车的成员、每次构建的结论和链接。
- **中断**：落地中途停下（合并接口出错、runner 被杀）时，通过的列车留在 `train/main/land` 分支上，带 `train/verified` 状态；下一次运行接着合并已合并之外的 PR，或只补调 `main` 的构建。这个分支在全部合并、`main` 的构建调起之后才删除。
- **告警**：落地开始后有 PR 变了（检查和合并之间有几秒的窗口：改目标分支、推新提交、去标签），或 `main` 的树与列车不一致，`main` 上就是没测过的状态：本次运行立即停止，在已合并的 PR 上评论并开 Issue，列车留在 `train-alarm/main/<运行号>` 分支上。这个分支存在期间不再发车；告警时列车会在 `main` 上调起一次 `ci.yml`：它红了，就 revert 告警评论里列出的那几个已合并的提交；绿了，直接删除 `train-alarm` 分支，队列恢复。还有一个更窄的窗口：检查和合并之间如果有人把 PR 的目标改成别的分支，PR 会被合进那个新分支（`--match-head-commit` 只锁头提交，不锁目标）；之后的树检查会发现并告警，处置同样是 revert 那个提交。整班原子落地记在 Issue #269。
- **不稳定测试**：`.github/flaky.toml` 每条写一个测试（`包路径.TestName`）和一个开着的 Issue；Issue 关闭后 CI 的 build 失败，提醒删掉这条。只认 Go 测试：编译、lint、前端、端到端和部署检查的失败都不算不稳定。
- **权限**：列车用 `GITHUB_TOKEN` 合并，它做的合并不触发 `main` 的 push 工作流，所以落地后列车自己在 `main` 上调起一次 `ci.yml`。

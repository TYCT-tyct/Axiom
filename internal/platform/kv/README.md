# kv

多个核心节点共用的限流计数、登录前的尝试次数、会话粘性和邮件收件人冷却，放在 Valkey 里；这里写放什么、怎么连、键怎么写、Valkey 不可用时每种用途怎么兜底，以及部署和测试。选型的总体理由见[总体架构的「技术选型」](../../../docs/architecture.md#技术选型)。

> 本文是 [Issue #321](https://github.com/TYCT-tyct/Axiom/issues/321) E8-b 的设计，按下文「落地顺序」的 K1–K4 实现。已落地 K1–K3：访问层、限流计数、节点心跳和部署、登录前的尝试次数，以及会话粘性与后台写入；邮件收件人冷却由 [#399](https://github.com/TYCT-tyct/Axiom/issues/399) 落地。供应商凭证并发与有限 RPM 通过后台静态份额支持 N > 1（见「多节点状态核对」）。主备切换（K4）尚未落地。代码与本文不一致时，在同一个 PR 里改本文。

四样都是**丢了不影响正确性**的数据：丢失只会多放行一点、或让会话重新选一次端点，钱和权限不受影响。

## 放什么、不放什么

| 用途 | 归属 | 算法 | 丢了的后果 |
|---|---|---|---|
| 限流计数：每 key、每账户的调用和计数频率；E4-2（[#315](https://github.com/TYCT-tyct/Axiom/issues/315)）的业务额度沿用同一个脚本 | gateway | 滑动窗口近似，与现在进程内的 `RateCounter` 相同 | 至多多放行一个窗口 |
| 登录前的尝试次数：每（站点, IP）、每（站点, 邮箱）、每用户 | accounts | GCRA 令牌桶，与现在进程内的相同 | 每个桶至多多一次突发 |
| 会话粘性：会话 → 上次服务它的端点 | routing 定键和值，gateway 定读写的时机 | 键值加到期时间 | 下一次请求重新选端点，丢一次上游的提示缓存 |
| 邮件收件人冷却：每个收件人一分钟的准入 | mail 定键和值，worker 在发送前取 | 一个收件人一个键，脚本原子地比较并写入，值是可再发的时刻 | 退回各节点的进程内桶，至多每个节点每分钟一封 |

不放进 Valkey 的：

- **钱**：余额、预留、花费计数、持有者、账本只在 PostgreSQL（[gateway 的不变量 I5](../../gateway/README.md#不变量)）。sub2api 把在途预留放在 Redis、故障时放行（[计费的「决策与理由」](../../../docs/domains/billing.md)），new-api 用旧快照覆盖 Redis 里的额度被绕过（[安全](../../../docs/security.md)），我们两样都不做。
- **能被改的授权状态**：key 能否使用、控制台会话、幂等键都在 PostgreSQL，每次读库（[accounts 的「认出与准入」](../../accounts/README.md#认出与准入)）；key 缓存在进程内，只存不会变的对应关系。
- **保护本节点资源的上限**：在途数（按节点、IP、账户）、argon2id 名额、key 未命中查库的令牌桶、账户闸、连接池的分类名额，以及下文登录最前面的粗 IP 桶和粘性写入的按账户上限。它们护的是这个进程的内存、CPU、连接和它往 Valkey 里写的量，本来就该按节点算。
- **路由的硬上限**：端点负载、429 降权、凭证并发、重试预算在进程内（[路由的「容量感知」](../../../docs/domains/routing.md#容量感知)），硬上限不依赖共享的数字。
- **辅助锁**：架构允许，目前没有用途，不实现。

## 客户端与连接

- **客户端**：[valkey-go](https://github.com/valkey-io/valkey-go) v1.0.78（2026-09-15），Apache-2.0，Valkey 项目自己维护；运行时只依赖 `golang.org/x/sys`。固定版本，升级前读变更说明。depguard 只许 `internal/platform/kv` 引用它；K1 另加一条 depguard 规则，禁止 `internal/billing`、`internal/payments` 引用 `kv`（钱不进缓存；`tools/checkmodules` 按模块判断，所有模块都能引用 platform，管不到它的子包）。选它而不是 go-redis 的理由见「决策与理由」。
- **服务端**：`valkey/valkey:9.1.2-alpine`，部署和测试用同一个标签。
- **连接**：总是流水线（`AlwaysPipelining`），并发的命令共用少量连接（默认每个实例 4 条），不用按并发数配连接池（sub2api 配 1024 条，`repository/redis.go:23`、`config.go:2241`）。不开它时，没有并发的命令走同步路径，期限一到就关掉连接（v1.0.78 `pipe.go` 的 `syncDo`），低流量时每次超时都要重连。关掉客户端缓存（`DisableCache`，不发 `CLIENT TRACKING`）和自动重试（`DisableRetry`：脚本会加计数，不能重发；一次失败只计一次，直接走兜底）。建连 1s；一条连接 1s 内收不到回复就关掉重连（`ConnWriteTimeout`；默认是 `Dialer.KeepAlive` × 10，即 10s，太长）。上面四个字段名与默认值已按 v1.0.78 的 `valkey.go`（第 231、259、261、265 行和 `ConnWriteTimeout` 的默认值计算）核对，升级时重新核对。
- **期限**：每次同步访问的期限是调用方 context 与 `kv.Timeout`（20ms，[路由的「容量感知」](../../../docs/domains/routing.md#容量感知)）中较早的一个。到期立即返回，连接不断：迟到的回复由客户端的一个 goroutine 收下丢掉（`pipe.go` 的 `abort`），它至多活到 `ConnWriteTimeout`（1s）。登录也用同一个期限，Valkey 在同机房的正常往返在 1ms 以内，20ms 还没回就是它出了问题。
- **流水线满时会等，所以客户端自己限住在途的命令**：命令先放进每条连接的环（默认 2¹⁰ 格），`ring.PutMulti` 在格子满时等一个不看 context 的条件变量（v1.0.78 `ring.go`），20ms 的期限拦不住它；而熔断打开前已经通过的访问收不回来。所以 `Client.Do` 在发出命令前先拿一个「位置」（`golang.org/x/sync/semaphore`，总数 512 条命令，是一条连接的环的一半，一批落在哪条连接上都有空格；其中后台粘性写入最多占 32 条，含调用方已超时而回复尚未返回的命令）：期限到了还没拿到位置就不发、直接返回不可用。位置在回复到达（或连接因两秒左右没有回应被关闭，上限 `settleBy` 3s）时才还，不是调用方不等了就还，因为被放弃的命令仍占着环里的格子。所以环不会被填满，一次访问最长等 `kv.Timeout`。测试：用一个按测试意愿才应答的假服务端（`send_test.go`，受控的满队列、取消、释放顺序，时间由 synctest 控制），再在真实 Valkey 的 `CLIENT PAUSE … WRITE` 下同时发出 5000 个访问，断言每个都返回、到达服务端的不超过 512 条。
- **认证**：Valkey 的 ACL 用户 `axiom`，`default` 用户关闭。`AXIOM_VALKEY_URL` 只写地址和用户（`valkey://axiom@valkey:6379`），密码从受保护文件 `AXIOM_VALKEY_PASSWORD_FILE` 读，文件的权限要求同[主密钥文件](../README.md#凭证加密)，打开、类型与权限检查和读取也是同一个描述符（`privfile.Open`）：环境变量会出现在 `docker inspect` 里，而拿到密码的人能删掉全部登录桶。URL 里带了密码就不启动。同一台机器上走 compose 的内部网络，不加 TLS（与数据库的 `sslmode=disable` 相同）；跨机器（M3）用 `valkeys://`，按系统根证书校验服务端，自签 CA 的变量随那个部署加入。其他写法（`redis://` 等）不接受，一种写法。错误只报变量名，不带取值。
- **权限**：`axiom` 用户只能碰 `ax:*` 的键，命令只放行 `hello`、`auth`、`ping`、`client|setinfo`、`info`、`time`、`get`、`set`、`del`、`incr`、`pexpire`、`eval`（脚本里执行的命令也按这个用户检查；不放行 `evalsha`，见下文「接口」）。ACL 文件里只写密码的 SHA-256（`#<十六进制>`），不写明文。测试以这个用户跑完全部用法，出现 NOPERM 即失败；`FLUSHALL`、`KEYS`、`CONFIG`、`EVALSHA` 和 `ax:*` 之外的键必须被拒。

## 接口

- `kv.Open(ctx, cfg, deps) (*Client, error)`：`cfg` 是 `kv.Config`（三个变量的值，加上测试用的键名前缀），`deps` 是 `kv.Deps`（心跳用的 `*pg.DB` 和范围、`Meter`、`Logger`，以及测试用的本机时钟）；按下文「配置与启动」检查。没设 URL 时返回单核心模式的 `Client`，`Enabled()` 为假，调用方走进程内的实现；有数据库就都登记心跳。`Config.Resolve` 检查配置本身、解析 URL、读密码文件并记下结果，`serve` 在碰数据库之前就调它，`Open` 复用它的结果。
- `Client.Nodes() int`：登录兜底等分用的节点数，取配置的 N 与心跳看到的存活节点数中较大的（见「配置与启动」）。
- `Client.Now() time.Time`：本机时钟加上测得的与 Valkey 的偏差（见「时钟」）。脚本里用到的「现在」和窗口序号都取它。
- `kv.NewScript(src)` 与 `Script.Cmd(keys, args…)`：脚本写在用它的模块里（gateway 的 `count`，accounts 的 `take`、`give`），`kv` 只管执行，不含业务规则；`Cmd` 是一批命令里的一条，类型不透明，模块只能发自己的脚本。**一律 `EVAL`**，不用 `EVALSHA`：`EVALSHA` 在 Valkey 重启、切换或 `SCRIPT FLUSH` 之后得到 `NOSCRIPT`，要再发一次 `EVAL`，每个节点那一刻在途的全部请求都变成两次往返，打破「一次往返」；脚本只有几百字节，服务端按内容的 SHA 命中自己的脚本缓存，不重新编译。new-api 也是直接 `Eval`（`rate-limit.go:80`）；sub2api 的 `Script.Run` 有同样的两次往返（`rate_limiter.go:30`）。
- `Client.Do(ctx, use, cmds…) ([]Value, error)`：一批命令一次往返，统一加期限、过熔断、记指标；任何失败都返回包着原因的 `kv.ErrUnavailable`，调用方据此兜底；`Value` 按调用方的需要读成整数列表或文本，`Missing()` 表示键不存在，不让同批计数降级。
- `Get(key)`、`Delete(key)` 与 `Set(key, value, ttl)`：粘性读、删除和带正到期时长的写入；亚毫秒期限至少写成 1ms，不提供永久写入。
- `Client.Later(account, cmd)`：按账户限速后交给后台写入，队列满或内存超过阈值即丢弃（见「会话粘性」）。只接受 `Set`，命令持有不可变字符串，不引用调用方可重用的脚本参数切片；用途固定为 `sticky_write`。
- `Client.Key(space, site, parts…)` 与 `kv.Hex(id)`：拼出 `ax:<ns>:<用途>:<站点>:…` 的键，`ns` 只在这里定，ID 写成 32 位小写十六进制。
- `Client.Close(ctx)`：停后台循环、放开连接、删掉本节点的心跳行；可以调多次，`serve` 在每条退出路径上都调。

## 配置与启动

`serve` 多读四个变量：`AXIOM_VALKEY_URL`（不设就是单核心模式：三样都在进程内，与 M1 相同）、`AXIOM_VALKEY_PASSWORD_FILE` `AXIOM_CORE_NODES`（核心节点数 N，默认 1）和 `AXIOM_NODE_ID`（本节点的名字，默认主机名，至多 128 个可见字符、不含空格）。`kv.Open` 在 `AXIOM_STARTUP_TIMEOUT` 之内做下列检查：

| 情况 | 结果 |
|---|---|
| URL 读不通、写法不对、带了密码；设了 URL 却读不到密码文件；N 不是正整数；N > 1 却没设 URL | 不启动，报变量名（[gateway 的「决策与理由」](../../gateway/README.md#决策与理由)：多核心没有 Valkey 不启动） |
| 节点心跳表里另有存活节点，且它们的数目 ≥ N | 不启动：N 配小了，或者第二个节点没配 Valkey 就连上了同一个库 |
| 连得上，但认证或权限被拒（`WRONGPASS`、`NOPERM`） | 不启动：这是配置错了 |
| 连得上，`INFO memory` 里 `maxmemory` 为 0 或 `maxmemory_policy` 不是 `noeviction` | 不启动：内存没有上限，或满了会悄悄删掉登录桶 |
| 连得上，用 `TIME` 测得的时钟偏差超过 1s | 不启动：本机或 Valkey 的时钟没有同步（见「时钟」） |
| 连不上（拒绝连接、超时） | 照常启动，熔断打开（见下文），记警告；第一次连上时补做上面三项连上之后的检查，不满足记错误并计入指标（运行中不能再拒绝启动） |

就绪检查不看 Valkey：它不可用时节点仍能正确服务。

**节点心跳**：N 是静态配置的部署节点上限，凭证份额另按注册表中的存活成员分配（[总体架构的「部署拓扑」](../../../docs/architecture.md#部署拓扑)）；配错了没有别的东西会发现，所以每个核心节点，设不设 Valkey 都一样，在 PostgreSQL 里写心跳：平台 schema 的一张小表 `platform.nodes`（节点 ID：`AXIOM_NODE_ID`，重启不变；最近一次心跳的时刻），K1 加迁移，只有平台范围读写；每行还带主密钥 `key_versions`、`key_active` 和 `key_active_since`，由心跳一起写，供主密钥轮换判断每个在线节点是否已与数据库摘要核对并写出某个版本，只有版本号，没有材料；文件里失败新增留下的未登记版本不会出现在 `key_versions`。每 10 秒更新自己的一行、删掉 60 秒没更新的行；30 秒内更新过的算存活；优雅退出时删掉自己的行。份额成员按每次进程启动身份识别，同名重启使用明确的空列表表示从未准入；失联后返回或本地租期到期时保留最后成员列表，标记 `share_joining`，只关闭返回进程的自身准入。空值视图仅表示旧二进制，空列表不会占用已有节点的份额。份额的本地准入期限依据读取时心跳剩余寿命减去 5 秒，至多 25 秒，不能被持续读取一条已经变旧的心跳延长。启动时数其他存活节点和写自己的一行是同一个事务，持一把事务级 advisory lock，同时启动的几个节点一个一个进，不会各自数到零而都放进来；每一轮心跳有自己的期限（5 秒），排在这一轮对 Valkey 的检查之后，数据库卡住只会拖慢这一轮，不会让 Valkey 的检查停下。启动时按上表检查；运行中存活数持续 2 分钟大于 N（滚动发布时新旧进程会短暂重叠）记错误、计入指标 `axiom.kv.nodes_live` 并告警，登录兜底的等分数取两者中较大的。节点有固定的名字，名字归**一个进程**所有：进程启动时在一条专用的数据库连接上拿一把会话级 advisory lock（`pg.DB.Hold`，`pg_try_advisory_lock`，键由名字哈希而来），活着就一直持有。同名的第二个进程（同一台机器上默认主机名相同）拿不到锁，立刻拒绝启动并报 `AXIOM_NODE_ID`，不看旧行是否新鲜；锁属于连接。进程崩溃时系统关掉它的 socket，数据库随即放掉锁，所以崩溃后立刻重启的同一节点马上拿到名字、覆盖自己留下的行，不等行过期。整台机器挂掉（断电、内核崩溃、虚拟机重置）或网络被切断时没有谁去关 socket，数据库要靠 TCP 保活发现半开的连接，Linux 默认约两小时；所以持有名字的会话拿到锁后给自己设 `tcp_keepalives_idle = 5`、`tcp_keepalives_interval = 5`、`tcp_keepalives_count = 3` 和 `tcp_user_timeout = 20000`（`TestHoldAsksTheServerToDropADeadConnection` 在持有者的连接上 `SHOW` 这些值），数据库在约 20 到 30 秒内放掉锁。所以同名重启被拒绝的时间：进程崩溃时立即可以重启，整机故障时至多约 30 秒（经 Unix socket 连数据库时这些设置无效，也没有网络可切）。名字拿到之后，别的名字的存活行才算「别的节点」计入 N。连接在运行中丢了（数据库重启、网络断），持有者每 5 秒检查一次并发现，`Client.Lost` 关闭，`serve` 随即退出（失败即关闭）：丢了名字就可能已有别的进程以这个名字在跑，不能继续当唯一的节点。这条连接不在连接池里，所以每个节点比池的上限多一条；每个节点的连接总账（这条、River 的监听和持有者心跳的专用连接）随数据库预算按节点数扣除，见 [platform 的「连接池」](../README.md#连接池)。容器重启保留主机名，默认值够用；两个节点不能用同一个名字，第二个会被拒绝。取不到主机名又没设时，每次启动用新名字，此时名字锁挡不住同一台机器上的第二个进程，只有计数检查在。[#322](https://github.com/TYCT-tyct/Axiom/issues/322) 的主密钥分发在这张表上增加版本报告，节点身份和名字锁不变。

## 多节点状态核对

K1–K3 共享设计中放进 Valkey 的三类状态，供应商硬额度另走后台静态份额：

| 状态 | 当前归属与双节点影响 |
|---|---|
| key 的调用与 count_tokens 计数（K1） | Valkey；故障时本地全额兜底，短暂放大是设计允许的退化 |
| 登录 IP、邮箱、用户尝试次数（K2） | Valkey；故障时按配置/存活节点数的较大值等分，本地粗 IP 桶保护各节点资源 |
| 会话 → 端点（K3） | Valkey，预检一次批量 GET/DEL，后台有界 SET；故障时不粘 |
| 邮件按收件人限流 | Valkey：每个规范化地址一个键，脚本原子准入；故障时退回各节点的进程桶，至多每个节点每分钟一封（[#399](https://github.com/TYCT-tyct/Axiom/issues/399)） |
| 节点身份、存活数 | PostgreSQL 心跳与会话锁，双节点不会共用名字 |
| 钱、预留、授权、控制台会话、幂等键、同步租约、任务认领 | PostgreSQL；不依赖进程内缓存决定资金或权限 |
| 在途、账户闸、查库桶、argon2id、连接池、粘性写桶 | 每进程资源保护，按节点设限是本意 |
| 端点负载、暂停、重试预算、凭证冷却 | 进程内的路由反馈；健康熔断与试探由 quality 经 PostgreSQL 后台共享；不是全局硬额度 |
| **供应商凭证并发与账号 RPM** | 调用路径只读本地份额；每秒通过 `ShareView` 和 `ConfirmShares` 后台确认完整的成员列表，新节点等旧成员降低并排空占用后才放行。进程启动身份与确认列表存在 `platform.nodes.share_session`、`share_view`、`share_joining`；过期节点的列表和 `platform.credential_share_departures` 的离开视图继续预留 RPM 至最后可能准入的窗口结束，后台清理（迁移 `00013`）。注册表只分享额度和成员，不保存每次调用计数；详见 [suppliers 的并发与速率](../../suppliers/README.md#并发与速率) |

## 时钟

脚本用到的时间由节点传入（理由见「决策与理由」），所以节点的时钟必须与 Valkey 一致：

- `kv.Open` 和之后每 30 秒，用 `TIME` 量一次偏差（取往返的中点），`Client.Now()` = 本机时钟 + 偏差，所以窗口序号和桶的时刻都对齐到 Valkey 的时钟，各节点之间也一致。启动时偏差超过 1s 不启动；运行中超过 1s 计入指标 `axiom.kv.clock_skew_seconds` 并告警，照常修正。
- 写到期时间一律用相对时长：`SET … PX (t − 现在)`，不用 `PXAT t`。这样即使偏差还没修正，键的寿命也只取决于两个由同一节点给出的时刻之差，不会因为节点落后而写下一个已经过去的绝对时刻、让键立即消失。
- 测试：传入与服务端相差很大（如一小时）的「现在」，键的 `PTTL` 仍大于 0、等于预期的时长。

## 键

写法 `ax:<ns>:<用途>:<站点>:<主体>`。`ns` 在生产是 `v1`，即值的格式版本：值的格式一变就换 `ns`，旧键自然到期；测试每个用例用随机的 `ns`，共用一个 Valkey 也互不可见。换 `ns` 的那次滚动发布期间，新旧节点各数各的，登录次数和限流计数短暂分成两份（至多放大到两倍，到发布结束为止）。ID 一律写成 UUID 的 32 位小写十六进制。每个键都带站点（邮件桶用全零站点，见下），排障或清理一个站点时按 `SCAN MATCH ax:v1:*:<站点>:*` 找得全，代价是每个键约 33 字节。

| 用途 | 键 | 值 | 到期 |
|---|---|---|---|
| 限流计数 | `ax:v1:rate:<站点>:<维度>:<ID>:<窗口序号>`；维度为 `key`（调用）和 `count`（`count_tokens`），ID 是 key 的 ID；`account_key`、`account_count` 则使用账户 ID | 整数 | 2 × 窗口，脚本在第一次 `INCR` 时设 |
| 会话粘性 | `ax:v1:stick:<站点>:<会话键的 64 位十六进制>` | 端点 ID（32 位小写十六进制） | 预设的粘性时间（`StickyTTL`，默认一小时），`SET … PX` |
| 登录前的次数 | `ax:v1:login:<站点>:ip:<h>`、`ax:v1:login:<站点>:email:<h>`、`ax:v1:login:<站点>:user:<用户 ID>`；`h` 是 `HMAC-SHA256(登录键密钥, 用途标签 ‖ 规范化的值)` 的前 16 字节 | 桶再次装满的时刻（毫秒） | 到装满为止，`SET … PX`；装满的桶就是没有键 |
| 邮件收件人冷却 | `ax:v1:mail:00000000000000000000000000000000:<h>`；`h` 是 `HMAC-SHA256(邮件键, 小写地址)` 的前 16 字节 | 下一次可发的时刻（毫秒） | 一分钟，`SET … PX`；提前重新准入时刷新 |

- **IP 的规范化**：由 `platform/clientip` 的 `Group` 给出——先 `Unmap()`（IPv4 映射的 IPv6 地址按 IPv4 计），IPv6 去掉 zone、再取 /64 前缀——然后才进 HMAC 和进程内的 `siteIP` 桶；网关的按 IP 限流与支付回调也用同一个函数，分组粒度只有一处。一个用户分到的 IPv6 地址通常是整个 /64，按整个地址计数等于让攻击者随意换出满的桶。
- **登录键密钥**：`secret` 用 HKDF-SHA256 从主密钥文件的最高已分发版本派生（标签 `axiom kv login v1`），`serve` 启动时读一次主密钥文件，同一个快照既供 `CheckRing` 核对、又供这里派生；它与数据库选定的信封加密活动版本无关，提前分发新主密钥时登录桶可以短暂分开；专用于这些键，不随 API key 的哈希密钥轮换：后者同时最多两个版本（[accounts 的「格式与哈希」](../../accounts/README.md#格式与哈希)），滚动发布时新旧节点会取不同版本，把同一个邮箱的次数分成两份。主密钥轮换很少、由运维发起，轮换后登录次数从零重算一次；分发期间新旧节点取的版本不同，次数短暂分成两份，到分发结束为止。
- **邮件键**：与登录键同一做法，`serve` 用启动时那一次读取的主密钥快照，从文件最高已分发版本用 HKDF-SHA256 派生（标签 `axiom kv mail v1`），与数据库选定的信封加密活动版本无关；专用于收件人键，不随 API key 的哈希密钥轮换：后者同时最多两个版本，滚动发布时新旧节点会取不同版本，把同一个收件人分成两份。提前分发新主密钥时，新旧节点取的版本不同，收件人桶也会短暂分成两份，到分发结束为止。站点字段是全零：一个邮箱就是一个收件人，不因为站点不同而多一个桶，与进程内实现的作用域相同；键一分钟到期，不参与按站点的清理。
- 邮箱和 IP 只以 HMAC 出现在键里：键能被 `SCAN` 和内存转储看到，不留个人信息；会话键本身已是账户加会话的哈希，邮件的值只是时刻。
- **E4-2 的维度**：同一批里只能加在准入之前就知道 ID 的计数主体，即 key、账户、工作区（认 key 时就有）；它们的限额值（按等级、按 key 的设置）在准入事务里读出，判定本来就在 `fn` 里（[gateway 的「准入」](../../gateway/README.md#准入)），不需要在预检时知道。所以「按等级的限额」是按账户计数、限额值取自等级，不是一个按等级汇总的计数；真要一个按等级合计的计数，它的 ID 预检时还不知道，得另起往返，那时再议。

## 内存

compose 里 `maxmemory` 默认 256 MB、`maxmemory-policy noeviction`，不持久化（理由见「决策与理由」）；容器的内存上限 512 MB，留给碎片和输出缓冲，下面的估算都以 `maxmemory` 小于容器上限为前提。粗算每个键约 150–200 字节：粘性占大头，256 MB 约容纳一小时内一百万个会话；限流计数每个活跃的（维度, ID）两个键；登录的键随来源 IP 和邮箱数增长；邮件桶随一分钟内的收件人数增长。

- **满了不删已有的键**：`noeviction` 下写入得到 OOM 错误，`kv` 按「出错」处理，调用方走兜底（有界，见各用途）；已有的计数和桶都留着，到期才消失。淘汰策略会让攻击者可控的新键挤掉被猜邮箱的桶：攻击者把一个邮箱的桶用完后停手，那个桶就成了最冷的键，几秒内被挤掉，等于把限额清零。
- **粘性给计数和登录让路**：后台每 10 秒读一次 `INFO memory`，`used_memory` 超过 `maxmemory` 的 70% 时，`Later` 丢弃全部粘性写入（计入 `axiom.kv.dropped`，原因 `memory`），读照常；降回 60% 以下恢复。粘性满了只是少粘几个会话，计数和登录满了才要兜底。
- **粘性写入按账户限速**：会话键由客户端的 `session_id`、`prompt_cache_key` 决定，一个 key 能以限流允许的速度造出新会话（每分钟 6000 次，`config.go:65`），在 Valkey 里没有按账户的上限。所以每个节点对每个账户的粘性写入走一个进程内的令牌桶（突发 100、每秒 10 次），超出的不写、计入 `axiom.kv.dropped`（原因 `account`）：一个账户在一个节点上一小时至多约 3.6 万个粘性键（约 7 MB）。正常的客户端一个会话只写一两次。桶用再次装满的时刻表示，每 10 秒清理已装满的桶；表至多 65536 个账户，满时拒绝新账户的粘性写入，同样计为 `account`，不驱逐未装满的桶给它重置突发。
- **登录键的创建先过进程内的粗 IP 桶**：见下文「登录前的尝试次数」，一个来源能建的登录键数受它限制。
- **邮件桶只活一分钟**：每个不同的收件人一个键，到期即消失；一分钟内的基数由发送路径决定，不是能长期堆在库里的状态。

## 每种用途

**限流计数**

- 窗口序号 = ⌊`Client.Now()` 的毫秒 ÷ 窗口长度⌋，按纪元对齐，所以各节点的窗口边界相同；估计值 = 本窗口 + 上一窗口 ×（1 − 本窗口已过的比例），与 `RateCounter` 相同。
- 脚本 `count`：参数固定为 key、账户各一对（本窗口键, 上一窗口键），以及两窗口到期时长、节点保护额度、当前窗口已过毫秒数。先 `INCR` key 本窗口，按当前和上一窗口算相同的滑动估值；未超节点额度才 `INCR` 账户，超出只读账户计数。递增结果是 1 就 `PEXPIRE`，再 `GET` 上一窗口，返回两两一组的整数。一个请求的全部维度在一个脚本里。`INCR` 和设到期在同一个脚本里，所以不会留下没有到期时间的键，new-api 和 sub2api 补到期时间的分支（`rate-limit.go:23`、`rate_limiter.go:30`）在这里不需要。
- 不用固定窗口：new-api 和 sub2api 都是固定窗口，窗口交界处能放过两倍（new-api 的注释写明了，`rate-limit.go:19`）；我们进程内已经是滑动窗口近似，换到 Valkey 不改行为。
- 预检仍只计数不判定（[gateway 的「准入」](../../gateway/README.md#准入)）。预检的一批命令是 `count` 脚本加粘性的 `GET`（或 `DEL`），同批发出、一次往返；排队醒来不再发。
- 进程内的 `RateCounter` 分别对 key、账户每个请求照常计数（各一次 map 写入），兜底时不必从零开始。
- **不可用**（出错、到期、熔断打开）：用进程内的计数与**全额**限额比较，不乘 N。这些限额防的是滥用，不是钱：故障期间一个 key 的合计至多放大到 N 倍，换来 Valkey 抖动时不误拒。乘 N 的话，入口按地域就近转发（[总体架构的「部署拓扑」](../../../docs/architecture.md#部署拓扑)）、一个 key 的流量集中在一个核心时，Valkey 一抖这个 key 就被 429。
- **恢复**：下一批照常发往 Valkey。兜底期间的计数不合并回去，Valkey 少看到那一段，至多多放行一个窗口；限流不是钱，不值得对账。

**登录前的尝试次数**

- 算法不变（[accounts 的「注册、登录与会话」](../../accounts/README.md#注册登录与会话)）。脚本 `take(键, 突发, 间隔, 现在)`：`t = max(GET 或 现在, 现在)`；`等待 = t + 间隔 − 突发 × 间隔 − 现在`，大于 0 就返回它；否则 `t += 间隔`，`SET 键 t PX (t − 现在)`，返回 0。脚本 `give(键, 间隔, 现在)`：键不在就返回；`t −= 间隔`，`t ≤ 现在` 就 `DEL`，否则 `SET 键 t PX (t − 现在)`。与进程内 `buckets.take`、`give` 逐步对应，由性质测试核对两者对任意操作序列给出相同结果。
- 一次登录依次：先过**进程内的粗 IP 桶**（按节点，参数同站点的 IP 设置，IP 按上文规范化），过了才碰 Valkey，所以一个来源（/64）在一个节点上每分钟至多建这么多个登录键；再扣共享的 IP 桶，扣邮箱（先扣后退），成功后退回邮箱，至多三次往返；不在调用路径上。没配 Valkey 的单核心模式不另设这一层：没有共享的键要护，本节点的 IP 桶已经是这个限制。
- **退回到扣的那一边**：`failing` 记下 `take` 用的是 Valkey 还是进程内的桶，`give` 只退到同一边；Valkey 在两步之间变得不可用时，这个令牌不退（多算一次失败，偏严）。扣取超时时，已经发出的脚本仍可能在服务端扣过一次，本节点又按份额扣一次；成功后只退本节点的那一份，共享的那次不确定扣取保留，结果偏严。每次这样的尝试至多额外占用共享桶一个令牌；同一组桶参数下，累计未回填的共享占用不超过突发额度，停止此类尝试后最迟在一个完整回填窗口（突发 × 间隔）内恢复。低流量可能达不到熔断的触发条件，不能靠熔断承诺更小上界。否则扣在进程内、退到 Valkey，会给别人正在用的同一个邮箱桶白退一个令牌。性质测试的操作序列里包含两步之间切换。
- **不可用**：退回进程内的桶，参数改为突发 max(1, ⌊突发 ÷ N⌋)、间隔 × N（N 取 `Client.Nodes()`；乘法溢出时饱和到最大时长，不能回绕成放行）。N 个节点合计：回填速度不超过设定值；突发至多 N × max(1, ⌊突发 ÷ N⌋) ≤ max(突发, N)，即突发小于 N 时每个节点至少留一次。**不拒绝登录**，与 sub2api（认证路由在 Redis 故障时一律 429，`routes/auth.go:34`）和 new-api（Redis 出错回 500，`rate-limit.go:119`）不同，理由见 [accounts 的「决策与理由」](../../accounts/README.md#决策与理由)。
- **来回切换**：熔断反复开合期间，Valkey 的桶和进程内的桶各自回填、轮流被用，一个桶的速率至多是设定值加本节点的份额，不超过两倍。
- **恢复**：回到 Valkey，进程内的桶不合并。每次 Valkey 不可用或重启丢数据，一个桶至多多出一次突发；argon2id 的并发名额始终按节点限制，猜测的速度仍有上限。

**邮件收件人冷却**

- 脚本 `admit(键, 现在, 可再发时刻, 到期)`：`GET` 键，值大于现在就返回 0；否则 `SET` 键 `可再发时刻` `PX 到期`，返回 1。比较和写入在同一个脚本里，所以两个节点同时准入同一收件人时只有一个成功；比较的是节点传入的共享时钟，受控时钟的测试因此能推进时间而不等待。键的主体是小写地址的 HMAC，一个收件人一个键，与站点无关（[mail 的「限流」](../mail/README.md#限流)）。
- **不可用**：退回本进程的桶，每个节点对每个收件人每分钟至多一封；N 个节点合计至多放大到 N 倍。共享准入成功时同时记进本节点的桶，切换时不会丢掉这次冷却；共享拒绝不写本地。故障期间的准入不合并回共享键，恢复后以共享键为准。
- **发送失败也占着间隔**：准入在发送之前，失败后的重试仍被限到间隔之后；被限流的任务 snooze，不消耗尝试次数（[mail 的「队列与重试」](../mail/README.md#队列与重试)）。

**会话粘性**

- **读**：预检那一批里 `GET`。请求带「上下文已压缩」标记时换成 `DEL`，不读，等于先忘记再选。
- **写**：规则不变（[gateway 的「并发、背压与共享状态」](../../gateway/README.md#并发背压与共享状态)），`SET 键 端点 PX 粘性时间`，先过按账户的限速（见「内存」），再交给后台队列（4096 条）。一个 goroutine 每次取队列中至多 32 条，用一次 `Do` / `DoMulti` 批量发出（期限同样 20ms）。先 `TryAcquire` 一个至多 32 条的后台在途预算，再 `TryAcquire` K1 共用的 512 条位置；任一取不到就立即丢弃该批、计 `slots`，不排进前台的 FIFO 等待队列，也不越过已有的等待者。两个预算都保留到回复返回或底层超时；调用方自己到期不归还，因此后续批次不能累积占满 512 条位置。相比静态切走 32 个位置，这样前台在无后台写时仍可用全部 512 条。队列满、内存超过阈值、账户超速都丢弃并计数，不等待队列空位或网络；出队时再检查内存停写，防止已排队的写入越过停写。失败不重试，避免旧写入在恢复后覆盖别的节点的新绑定；关闭客户端时先锁住入队边界、停止接受新绑定，再停止后台循环；队列中尚未出队的绑定及关闭后投递的绑定按 `shutdown` 计数并丢弃，不等待网络写完；在途批次的取消仍由 `calls{use=sticky_write,result=skipped}` 记录。
- **不可用**：读不到就不粘，写丢掉。配了 Valkey 时不用进程内的表：别的节点看不到它，恢复后以 Valkey 为准，两份只会互相打架。sub2api 读粘性出错时同样当作没有（`service/gateway_scheduling.go:137`）。
- 单核心模式（没设 URL）照旧用 routing 进程内的表。
- 有效期从写入算起，用着不续期，与进程内表相同；K3 的写放大比较与结论见[路由的「会话粘性」](../../../docs/domains/routing.md#会话粘性)。

## 熔断

new-api 和 sub2api 都没有熔断：出错即 500 或直接放行（`rate-limit.go:119`、`rate_limiter.go:142`）。我们的期限只有 20ms，没有熔断时 Valkey 一卡，每个请求都多 20ms。

- **记什么**：前台访问和平台检查参与熔断；`StickyWrite` 的所有结果只记访问指标，不改变错误率、连续失败数或熔断状态，后台流量也不能把前台故障的连续计数清零。每次访问的结果是成功、不可用（`kv.Timeout` 自己到期、连接错误）、出错（脚本或命令被拒，是程序错误，记错误日志；OOM 也在这里，见「内存」），或跳过。只有「不可用」计入熔断。**调用方的原因不算**：调用方 context 被取消，或调用方的期限早于 `kv.Timeout` 而先到，记作跳过（`skipped`），不计入。否则攻击者快速发请求再断开，就能替我们推开熔断。成功和出错的访问都算窗口里的一次访问（下面「一半以上」「超过 20%」的分母），出错还证明服务器在，连续不可用的计数清零；打开期间才结束的在途访问不再记，不会延长打开的时间。
- **打开**，在最近 10 秒的滑动窗口上（10 个一秒的桶），满足任一条：
  - 访问至少 20 次，且一半以上不可用；
  - 访问至少 10 次，且超过 20% 是 `kv.Timeout` 到期（耗时触发：部分故障时只有一部分请求变慢，错误率条件看不到它）；
  - 连续 5 次不可用。
- 打开后 5 秒内的访问不做任何 I/O，直接返回不可用；之后半开：放一次试探出去，其余仍直接返回，试探成功即关闭，失败再打开 5 秒。后台粘性写入在熔断打开及半开期间全部跳过，不认领探测；由前台访问或平台检查探测成功后才恢复。
- **代价**：打开之前，在途的每个访问都可能等满 20ms，同一时刻约有「每秒请求数 × 20ms」个（每秒 5000 个时约 100 个）；高流量时条件在几十毫秒内满足。10 秒内不到 10 次访问的安静节点永远不会熔断，它的每次访问至多多 20ms，量小，可以接受。首字延迟里给这一步的预算是 2ms（[性能的「延迟预算」](../../../docs/performance.md#延迟预算)），所以部分故障也要靠耗时触发尽快打开。

## 指标与告警

`axiom.kv.calls`（标签 `use`：`precheck`、`sticky_write`、`login`、`mail`；`result`：`ok`、`unavailable`、`error`、`skipped`）、`axiom.kv.duration`（直方图，按 `use`）、`axiom.kv.breaker_open`（0 或 1）、`axiom.kv.dropped`（发送前因队列、内存、账户、在途位置或关闭被丢弃，标签 `reason`：`queue`、`memory`、`account`、`slots`、`shutdown`）、`axiom.kv.memory_used_bytes`（后台每 10 秒读 `INFO memory`）与 `axiom.kv.rejected_oom`（访问被服务端以 OOM 拒绝的次数，由客户端在拒绝发生时数，不读 `INFO stats`）、`axiom.kv.clock_skew_seconds`、`axiom.kv.nodes_live`。告警规则随告警出口（[#316](https://github.com/TYCT-tyct/Axiom/issues/316)）：熔断打开超过 1 分钟；有 OOM 拒绝；内存超过上限的 70%（粘性开始被丢）；`dropped` 每分钟超过 100 条持续 5 分钟；时钟偏差超过 1s；存活节点数大于 N；`precheck` 的 p95 超过 2ms。

## 部署

- **密码与 ACL**：compose 现有的 `keys` 服务一并生成密码文件（随机 32 字节），放在 `keys` 卷里，权限同主密钥文件，`axiom` 服务读 `AXIOM_VALKEY_PASSWORD_FILE`；同时把 ACL 文件（`user default off`，`axiom` 用户、`#<密码的 SHA-256>` 和上面的权限）写进只给 Valkey 读的另一个卷。密码不出现在环境变量、命令行和 `deploy/.env` 里。
- **compose 服务 `valkey`**：镜像见上；以镜像自己的 `valkey` 用户启动；与其他服务同样只读根文件系统、丢弃全部 capabilities；容器内存上限 512 MB；不映射端口，只在 compose 网络里可达。命令 `valkey-server --aclfile … --save "" --appendonly no --maxmemory 256mb --maxmemory-policy noeviction`。健康检查以 `axiom` 用户 `PING`，密码从挂载的密码文件读给 `valkey-cli`，不出现在命令行里（K1 按镜像核对 `valkey-cli` 读密码的方式）。
- **`axiom` 服务**：加 `AXIOM_VALKEY_URL` 和 `AXIOM_VALKEY_PASSWORD_FILE`；对 `valkey` 的依赖是 `service_started` 而不是 `service_healthy`，Valkey 起得慢或起不来时 Axiom 照常启动、先用兜底。
- **不持久化**：数据没有卷。重启后为空，即上文各用途「恢复」的情况，都有界。
- **主备与故障切换（M3）**：随热备方案（[#324](https://github.com/TYCT-tyct/Axiom/issues/324)）定，候选是一主一备加三个 Sentinel（URL 写 `master_set`，客户端自己跟随切换）或托管的 Valkey。复制是异步的，切换丢最后的写入，与重启同类。**不用集群模式**：一个请求的几个键不在同一个槽里（一批命令、多键脚本）；量也不需要：每次调用一批两条命令，每秒一千次调用约两千次操作，远低于单实例的能力。

## 测试

- **真实 Valkey**：`withcluster` 在一次 `just test` 里与 PostgreSQL 一起起一个 Valkey 容器（同一镜像、同一份 ACL 和配置），地址经 `KVTEST_URL`、`axiom` 用户的密码文件经 `KVTEST_PASSWORD_FILE`、只读 `admin` 用户的密码文件经 `KVTEST_ADMIN_PASSWORD_FILE` 传入，和 `PGTEST_CLUSTER_URL` 一样由 `containertest.Untracked` 读取（[共享策略](../README.md)）；三个变量缺一个时 `kvtest` 自己起容器。用例各用随机的 `ns`。读 `PTTL`、`KEYS`、`SCAN` 的用例用共享容器的只读 `admin` 用户（`Server.TTL`、`Server.Read`），不起容器；改服务端状态的用例（`CLIENT PAUSE`、重启、填满内存、改 ACL 或配置）用自己的容器。只验证不可用兜底的用例也不停容器：连接一个没有服务监听的地址（`kvtest.Down`），或关掉自己的客户端，调用方得到同一个 `ErrUnavailable`；列车负载下等 Docker 创建容器比故障本身慢得多。
- **超时**：`send_test.go` 的 `TestTimeoutReturnsAndTheBreakerRecovers` 用 `testing/synctest` 和受控假服务端验证访问恰在生产期限 `kv.Timeout`（20ms）返回不可用、熔断打开后不再发送、迟到回复不提前关闭熔断、打开期后半开探测成功并恢复正常访问，以及 `breaker_open` 从 1 回到 0；生产期限的准确耗时只在虚拟时间里断言。同文件的队列测试验证无空位时仍按期限返回、等到空位才发送，以及在途数上限。真实 Valkey 的集成验证在 `outage_test.go`：另一条连接执行 `CLIENT PAUSE <很长> WRITE` 阻塞写脚本（`INFO`、`TIME` 照常），放行时显式 `CLIENT UNPAUSE`；`TestEveryAccessReturns` 验证大量并发访问都返回、到达服务端的不超过在途上限，`TestCallerGivingUpDoesNotOpenTheBreaker` 验证调用方先取消记作跳过、不推开熔断，这两个用例不验证恢复。`TestLaterDoesNotWaitForStalledWrites` 用同一个受控服务端扣住后台 32 个在途位置，验证继续投递不推进虚拟时钟、队列最多 4096 条且溢出计数。真实服务端的正常回复使用 `kvtest` 的一分钟默认期限；熔断和时钟偏差的测试用虚拟时间或可注入时钟，不按墙钟判成败。
- **后台与前台隔离**：`later_priority_test.go` 用受控写入回复与虚拟时间，验证后台取不到位置时立即丢弃、持位与超时后仍保留最多 32 个位置，并发的两命令预检立即返回；连续后台超时不改前台熔断，半开只由前台探测。关闭测试验证非空队列、重复关闭及并发投递的 `shutdown` 计数恰好一次。
- **重启**：停止再启动容器，断言期间请求照常完成、恢复后重新连上，计数从零开始。
- **内存满**：把容器的 `maxmemory` 设得很小并写满，断言新写入得到 OOM、按出错走兜底，已有的登录桶仍在；超过 70% 后粘性写入被丢弃。
- **时钟**：见「时钟」；另测启动时偏差超过 1s 不启动。
- **多节点**：同一个 Valkey 上的两个 gateway（或两个 accounts 服务）：同一个 key 的计数合在一起、不随节点数放大（#315 的验收）；一个节点写的粘性另一个读得到；登录次数共享；两个 mail worker 对同一收件人只有一个准入成功，大小写归一，发送失败后的重试仍被限到间隔之后。心跳：两个节点、N = 1 时第二个不启动；存活数大于 N 时指标和日志出现。
- **邮件桶**：`kvtest` 的真实 Valkey 上，两个节点共享准入、并发只有一个成功、受控时钟推进不等待墙钟；Valkey 不可用时退回各节点的桶；`KEYS` 看不到明文地址，到期时间不超过一分钟。
- **脚本与进程内实现一致**：对 `count`、`take`、`give` 做性质测试，随机的操作序列和时间在 Lua 和 Go 两边给出相同结果，序列里包含在 `take` 与 `give` 之间切换存储；时间由调用方传入，测试不等待。
- **基准**：预检的一批（`BenchmarkPrecheck`，真实 Valkey）进分配门槛；K3 的粘性读另设 `BenchmarkPrecheckSticky`，带着它的同一批一起量。

| 兜底的放大有明确上界 | 限流：故障期间一个 key 合计至多放大到 N 倍，只持续到 Valkey 恢复后的一个窗口；登录：N 个节点合计回填速度不超过设定值、突发不超过 max(突发, N)，熔断来回切换时速率不超过两倍。测试：N = 2 时暂停 Valkey，单个节点的限流在全额限额处拒绝，登录桶的突发是一半 |
| 健康时多节点不放大限额 | 计数和桶都在 Valkey 里；测试见上文「多节点」 |
| 登录的退回只回到扣的那一边 | `failing` 记下 `take` 用的存储；性质测试 |
| N 配错会被发现 | 节点心跳表（每个核心节点都登记，数人和写行是一个事务）；启动检查和运行中的指标、告警；测试见上文「多节点」 |
| 配置错了不启动，Valkey 暂时不在照常启动 | 「配置与启动」的表；测试逐行覆盖，连不上用不应答的端口 |
| 密码、邮箱、IP 不出现在错误、日志、环境变量和键里 | 密码只在受保护文件里，ACL 文件只存它的哈希；错误只报变量名；邮箱和 IP 只以 HMAC 进键，登录与邮件各用一把从主密钥派生的键。测试：错误文本不含密码，`SCAN` 出的键里没有 `@` 和测试用的 IP，邮件键的值只是时刻 |
| 邮件收件人的准入在节点间只有一个 | 脚本在同一个步骤里比较并写入；N 个节点同时准入同一地址只有一个成功。测试：两节点并发准入 |

## 决策与理由

| 决策 | 理由 | 不选 |
|---|---|---|
| Valkey 客户端用 valkey-go，固定 v1.0.78，总是流水线 | 流水线模式下期限到时立即返回且不断开连接，迟到的回复由客户端丢掉（同步路径会断开，所以开 `AlwaysPipelining`）；20ms 期限在 Valkey 变慢时会大量触发，断连接只会把变慢放大成重连风暴。自动流水线让 5000 路并发共用几条连接，不用调连接池。Valkey 项目自己维护，运行时只依赖 `x/sys`；内置 Sentinel，M3 不换客户端。代价：new-api、sub2api 都用 go-redis，它们的代码不能逐行对照；流水线的环满时 `PutOne` 不看 context，要靠熔断兜住 | go-redis v9（v9.22.0 实读）：context 到期被当作坏连接关掉（`error.go` 的 `isBadConn`），context 期限要另开 `ContextTimeoutEnabled`；默认对每条新连接尝试 Redis Cloud 的维护通知（`maintnotifications` 默认 `ModeAuto`）；多 xxhash、xxh3、uber atomic 等依赖。redigo：没有自动流水线，要按并发数配连接池 |
| 不持久化，`noeviction`，内存设上限，粘性在 70% 以上停写 | 三种数据丢了都有界（各用途的「恢复」）；持久化只换来重启后少一次突发，却要卷和磁盘写。满了按出错走兜底是有界的退化；淘汰则会让攻击者造的新键挤掉被猜邮箱的桶，等于悄悄清零。粘性是唯一会被客户端撑大的数据，所以只有它让路 | RDB 或 AOF：多一个卷和写盘，快照本身也是旧的；`allkeys-lru`：攻击者可控的基数能挤掉登录桶；`volatile-ttl`：先淘汰到期最早的，正好是限流计数；计数、登录和粘性分两个实例：多一个服务，停写粘性已经够用 |
| 核心节点数 N 是静态配置 `AXIOM_CORE_NODES`，由 PostgreSQL 里的节点心跳核对 | 「多核心没有 Valkey 不启动」和登录兜底的等分都要知道 N；N 限定部署规模和登录兜底，凭证份额另用注册表的实际存活成员；心跳表让配错的 N 和没配 Valkey 的第二个节点被发现 | 只有配置：配错了没人知道，登录兜底按错误的 N 放大；在 Valkey 里登记存活的节点：Valkey 不可用时恰恰读不到；数 billing 的持有者：跨模块，持有者也不区分节点角色 |
| 时间由节点传入脚本，用 `TIME` 测得的偏差修正，到期时长用相对值 | 键名要在调用前算出（窗口序号），测试才能传入时间而不等待（[检查清单的「测试与时序」](../../../CONTRIBUTING.md#检查清单)）；修正偏差后各节点对齐到 Valkey 的时钟，相对的到期时长让偏差不会把键写成已经过期 | 脚本里读 `TIME`：窗口序号在脚本里算出的键没有事先声明，测试只能等真实时间；不测偏差、写 `PXAT`：节点落后时键提前消失，落后太多时立即消失 |
| 限流的兜底用全额限额，登录的兜底按 N 等分 | 限流防滥用，不是钱：故障期间短暂放大到 N 倍，比 Valkey 一抖就误拒流量集中在一个核心的 key 好；登录防的是猜密码，放大 N 倍就是猜测次数放大 N 倍，所以等分 | 两者都乘 N 等分：入口就近转发时一个 key 的流量本来就集中，Valkey 抖动即 429；登录也用全额：故障期间猜测次数放大 N 倍 |
| 脚本一律 `EVAL`，不用 `EVALSHA` | `NOSCRIPT` 会让重启、切换后的第一批请求全部两次往返；脚本几百字节，服务端按内容命中自己的缓存 | 先 `EVALSHA` 失败再 `EVAL`（sub2api 的 `Script.Run`）：打破「一次往返」 |
| 熔断只计 `kv.Timeout` 自己的到期和连接错误，另有耗时触发 | 调用方的取消算进来，攻击者断开连接就能推开熔断；部分故障时错误率条件看不到变慢的那部分 | 所有失败都计入：可被客户端操纵；只看错误率：部分故障时一部分请求一直多 20ms |
| 登录键用从主密钥派生的专用密钥做 HMAC，IPv6 按 /64 | 不随 API key 哈希密钥的两个版本分裂计数；/64 是一个用户通常拿到的范围，按整个地址计数等于允许无限换桶 | 用 API key 的哈希密钥：轮换和滚动发布时计数分成两份；按整个 IPv6 地址：基数攻击的入口 |
| Valkey 连不上照常启动，配置错了不启动 | 缓存故障不应该在重启时变成整个节点起不来；认证被拒、内存策略不对、时钟不同步是部署写错了，越早发现越好 | 连不上就不启动（new-api 的 `common/redis.go:45`）：Valkey 成了硬依赖，违背「只放丢了也不影响正确性的数据」 |
| 预检的计数和粘性同批发出，计数用一个脚本 | 一次往返；一个请求的多个维度在一个脚本里原子地加，E4-2 加维度不加往返 | 每样一次往返：首字路径多几次网络往返；计数和粘性合成一个脚本：粘性的键和值归 routing，要交给 gateway 的脚本去拼，同批发出也是一次往返 |

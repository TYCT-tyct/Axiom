# nodetls

节点之间调用的双向 TLS：核心用 `Server` 接受入口，入口用 `Client` 连核心。两个函数都从同一个目录读证书，返回可以直接交给 `net/http` 的 `*tls.Config`。

## 文件

| 文件 | 用途 |
|---|---|
| `node.crt` | 本节点的证书，PEM |
| `node.key` | 本节点的私钥，PEM；权限必须是 `0600`（非 Windows 上组成员和其他人不能读写）。检查的是打开后要读的那个描述符（`internal/platform/privfile`） |
| `ca.crt` | 签发节点证书的内部证书机构，PEM；可以有多张，作为信任根 |

目录由 `AXIOM_NODE_TLS_DIR` 给出；核心不设时默认与主密钥文件同一目录。错误只说变量名和文件角色，不打印路径。

## 检查

- 目录必须有，并且不能对组或其他用户可写（`0o022`）；三个文件都要能读，`node.key` 的权限不合格就拒绝启动。能写目录的人可以换掉节点出示的私钥，即使私钥文件本身是 `0600`。
- `node.key` 的类型和权限由 `privfile.Open` 从打开后的描述符检查，读的也是这个文件：在检查和读取之间把路径原子换成一个权限 `0644`、内容合法的私钥，读取不会按路径重新打开它。回归测试 `TestKeyReplacedAtOpenIsRefused` 在打开的一刻换入这个文件，要求启动被拒；换回按路径检查的写法时每次都失败。
- `node.crt` 和 `node.key` 必须配对；证书要能解析、现在有效，并且**整条链**都允许对应用途：`Server` 以 `serverAuth`、`Client` 以 `clientAuth` 走完整的 `x509.Verify`，所以中间 CA 只允许 `serverAuth` 时，它签发的 `clientAuth` 叶证书在启动就被拒，而不是等到握手。没有扩展密钥用法或显式 `anyExtendedKeyUsage` 的证书可以用作任一用途，这是 X.509 的含义。
- `ca.crt` 至少要有一张证书，否则没有信任根；`node.crt` 必须由它签发（可以带中间证书），否则节点启动后每个对端都会拒绝它，启动时就报出来。
- 最低 TLS 1.3；`Server` 要求并校验客户端证书，`Client` 用 `ca.crt` 校验服务端并核对 `AXIOM_CORE_URL` 的主机名。
- **用途**：`RequirePurpose(server, OpsPurpose)` 在链校验通过后再看对端证书的 URI 备用名，没有 `urn:axiom:node-purpose:ops` 就拒绝握手。核心的运营监听用它，所以只有运维节点的证书能连，入口的证书不行；节点监听不要求用途。`TestOperationsListenerNeedsTheOpsPurpose` 覆盖带用途、不带用途和别的用途。

## 部署

核心设 `AXIOM_NODE_ADDR` 开节点监听；入口设 `AXIOM_CORE_URL`（`https`，不带路径、查询和用户信息）和证书目录。证书目录要另外设一个组不可写的目录，不要用密钥环的卷根本身：`deploy/compose.yaml` 故意把那个卷设成 `0770`，因为程序要能原子替换主密钥文件，而这里要求目录对组不可写；不设 `AXIOM_NODE_TLS_DIR` 时默认正好是主密钥文件所在目录，核心会在这条自相矛盾的配置上拒绝启动。放在密钥卷下的子目录（如 `/keys/tls`，`0750`）或另挂一个卷都可以。证书由部署的内部证书机构签发：一次性令牌注册、签发和轮换尚未实现，到期前替换文件并重启。节点只保存自己的私钥，核心和入口不共享私钥。

## 决策与理由

| 决策 | 理由 | 不选 |
|---|---|---|
| 证书和主密钥分开成 PEM 文件，放同一个受保护目录 | 主密钥是 32 字节，证书和私钥是 PEM，生命周期也不同；同目录让权限和备份只有一处 | 把证书编码进密钥环：改密钥环的格式和轮换流程；放到任意路径：多一个要配的变量 |
| 最低 TLS 1.3，按用途校验整条链 | 节点之间没有旧客户端要兼容；用途检查能在启动时发现把客户端证书配给服务端、或中间 CA 的用途与叶证书冲突这类错误 | 允许 TLS 1.2：多一套旧密码套件要审；只看 CA 不看用途：证书互换后仍能握手；只查叶子不查链：启动通过、握手必败 |
| 私钥和目录权限在加载时检查，错误只报变量和文件角色 | 权限错是部署错误，越早失败越好；路径可能带主机名或租户信息，不进日志和错误 | 只靠部署的 `chmod`：漏一次就长期带着可读私钥运行 |
| 用途写成证书的 URI 备用名，由监听在握手后检查 | 扩展密钥用法只区分服务端和客户端，分不出入口和运维；另起一个 CA 要多维护一套信任根和轮换。URI 名由同一个内部 CA 签发，检查放在 `VerifyConnection`，链校验照旧 | 另一个 CA：信任根翻倍；按证书的 CN 或 DNS 名判断：这两个字段本来就写主机名，容易和用途混淆 |
| 私钥和主密钥用同一个打开与检查函数，检查与读取是同一个描述符 | 三个调用方各写一遍会分叉，#530 的 mTLS 一处就停在按路径检查、再按路径读；一处实现让同一类回归测试覆盖它 | 每处自己 `Stat` 路径：检查的对象和读的对象可能不同 |

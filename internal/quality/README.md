# quality

端点评估在调用路径上的代码。规则和理由见[端点评估](../../docs/domains/quality.md)的「健康与熔断」，本文写代码层面的接口、不变量和取舍。

> 已实现：[#313](https://github.com/TYCT-tyct/Axiom/issues/313) E3-4 的 H1、H2（见[实现拆分](../../docs/domains/quality.md#实现拆分)）：测量、独立来源窗口、实时熔断、离线标记与告警、慢启动、持久化和有租约的试探；[#314](https://github.com/TYCT-tyct/Axiom/issues/314) E3-16 的运营质量分（首字延迟、输出速度、错误率和试探的 EWMA，未知用置信度 0 表示）和端点真伪的指纹检测（随机指纹题、已知答案、`Verified`）和 [#560](https://github.com/TYCT-tyct/Axiom/issues/560) 的精确型号检测（型号/变体、积、倒序和字符数，`Verified` 不再只核对作者）；[#561](https://github.com/TYCT-tyct/Axiom/issues/561) 的实测结构事实（能力、参数、上下文与输出上限，`Measure` 记录、快照按实测替换）；[#563](https://github.com/TYCT-tyct/Axiom/issues/563) 的来源类别与指纹（后台增改的类别、响应头和用量条件、节点每 5 秒热读并重判）；[#564](https://github.com/TYCT-tyct/Axiom/issues/564) 的产品成绩（固定题库、官方直连为 100、配对置信区间，与运营质量分分开；成绩和官方基线落库，所有节点在启动和每 5 秒的热读里采纳）。默认只观察；H3 的管理接口和 H4 的线路健康尚未实现，写入事实的主动检测也还没有落地，`Measure` 是给它的入口；产品成绩的自动运行也还没有落地，`RecordOfficialBenchmark`、`RecordBenchmark` 是给它的入口。

## 接口

```go
func New(meter metric.Meter) *Monitor // meter 为 nil 时不报指标
func (m *Monitor) Observe(ctx context.Context, o Observation) // 每次尝试结束时一次；0 分配
func (m *Monitor) MeasuredFor(ep suppliers.Routable, now time.Time) Measures // 端点当前的数（含来源类别），并核对检测证据属于这个配置
func (m *Monitor) SetSourceClasses(classes []SourceClass) error // 编译并换入类别规则；用已保存的证据重判所有端点
func (m *Monitor) Measure(ep suppliers.Routable, format protocol.Format, facts Facts) bool // 记下该格式的实测；旧配置或未提供的格式拒绝
func (m *Monitor) RecordOfficialBenchmark(ctx context.Context, ep suppliers.Routable, run BenchmarkRun) bool // 记下官方直连的基线并落库；只收平台端点且覆盖达标的运行
func (m *Monitor) RecordBenchmark(ctx context.Context, ep suppliers.Routable, run BenchmarkRun) (BenchmarkResult, bool) // 按官方基线给端点打分并落库；旧配置、旧基线、覆盖不足拒绝
func ParseMode(value string) (Mode, error) // 默认值与合法性只在此定义
func Start(ctx context.Context, cfg Config) (*Monitor, *Loop, error)
func (m *Monitor) Prepare(ctx context.Context, endpoints []suppliers.Routable) error // 发布当前配置和快照 Generation；旧 Generation 跳过
func (m *Monitor) Live(id suppliers.EndpointID, credentials int) *State
func (s *State) Routing(now time.Time) (opened time.Time, limit int64)
func (l *Loop) Tick(ctx context.Context) error
func (l *Loop) Run(ctx context.Context)
func (l *Loop) Drain(ctx context.Context) error
```

- **谁调**：gateway 的尝试在 `close` 里调 `Observe`，每次尝试恰好一次，含流式阶段（`attempt.observe`）；`RouteDeps.Build` 每次重建快照时对每个端点调 `MeasuredFor`，填进 `routing.Endpoint` 的 `Health`、`Quality`、`Confidence`、`Throughput`、`Latency`、`Verified`，并把结构事实按格式写进 `Endpoint.Specs`；端点的 `Caps`、`Parameters`、`Context`、`MaxOutput` 是这些格式的交集与下限。两边用的是同一个 `Monitor`，由 `cmd/axiom` 建一个交给两边；写事实的只有检测（`Measure`），没有检测时快照全用目录值。
- **`Observation` 是事实，不是结论**：账户所有者（由准入的 `OwnerID` 提供；缺失时只计测量，不进摘除窗口）、所用凭证、请求 ID，适配器的 `*suppliers.Failure`（没有 2xx 时）、流读失败的 `protocol.Fault`、网关为什么取消了尝试（`Cut`：响应头超时、空闲超时、调用自己的原因）、客户端是否已走、首段内容是否在客户端还在时交付（`Delivered`）、是否正常结束、是否 200 无正文（compact 的空正文也是）、预估输入 token（`billing.InputEstimate`）、输出 token（结算用的数，上游没报时是估算）、发出、首段内容、结束的时刻；首段内容和结束（或失败）的时刻在读到时记下，不含网关自己随后的等待（追加预留、关闭、算成本）。判定只在本模块（`judge`），网关不预先下结论。
- **来源类别**：`SourceClass` 是后台数据（`quality.source_classes`），`relay` 是回退，三个种子 `official`/`cloud`/`relay` 由迁移写入、没有条件；`New` 在读表之前只装 `relay` 回退。规则只读成功响应的响应头和用量项：`Observation.Headers` 和 `UsageItems` 由网关在 2xx 后填入，但只有 `judge` 判为成功、且 `Observation.Config` 仍是 `Prepare` 当前配置的尝试才算证据；空闲超时、空正文和断流不算。`UsageItems` 只含上游报告（`billing.Segment.Reported`）且非零的项，取自响应头所属的第一跳。`Observe` 只保存当前规则引用的响应头（固定数组，超过 256 字节截断并记下截断，截断的值不判 `equals`/`suffix`，并记录哪些头查过）和用量位图，按 `position` 找第一个匹配的类别；新规则引用旧证据没查过的头时，`present` 和 `absent` 都不命中，没有证据或都不匹配时是回退。换配置时 `Prepare` 清掉证据，类别立即回到回退。`MeasuredFor` 把结果放进 `Measures.Class`（传入的配置不是 `Prepare` 当前配置时给回退），路由按值复制到 `routing.Endpoint.Class`，调用记录的尝试行写计划时冻结的 `routing.Entry.Class`。规则和类别在 `Start` 读一次、`Loop.Tick` 每 5 秒热读；内容变化时 `SetSourceClasses` 重新编译并从已保存的证据重判，不需要重启。`SetSourceClasses` 的编译错误保留旧规则，启动时读不出来则启动失败。实现见 `classes.go`、`classes_store.go`，表和种子见 `migrations/00004_source_classes.sql`。
- **`Measures`**：`Health` = 1 − 失败的加权平均（α 0.2，没有计入的结局时为 1）；`Latency`、`Throughput` 在"测过"（样本 ≥ 5 且最近一个在 30 分钟内）之前为 0，路由按 0 认作没测过。`LatencyPercentiles`、`ThroughputPercentiles` 是滚动五分钟窗口的 p50/p75/p90/p99，样本与 `Latency`、`Throughput` 同一批，窗口固定 128 个，窗口内少于 5 个样本时全 0。`Verified` 和 `VerifyConfidence` 只在一次通过的真伪检测（型号和变体、作者和全部已知答案）还在结果有效期（默认 24 小时，后台可改）内、且之后没有矛盾时为真/非零；`VerifyConfidence` 从通过时刻的 1 线性衰减到 0。`VerifiedAt` 是最近一次通过的时刻，过期或被矛盾推翻后仍保留，用来区分"从没测过"和"测过但已经不新"。`Facts` 是按调用格式分开的实测结构事实，没有测过的格式没有条目、路由用目录值。`Class` 是来源类别的稳定 slug，不是枚举。`ProductScore`、`ProductScoreConfidence`、`ProductScoreAt` 是产品成绩（0–100，官方直连 100）、它的置信度和最近一次运行的时刻，见下一节；它们与 `Quality` 的运营质量分没有关系。
- **实测的结构事实**：`Facts` 有能力的 `Supported`/`Unsupported`、参数的 `SupportedParameters`/`UnsupportedParameters` 和 `Context`、`MaxOutput` 两个上限。`Measure` 把一次检测的结论合并进端点状态：`Supported` 清掉同一批里的 `Unsupported`（反过来也一样），上限被新的非零值替换，没写的字段保持原值。路由按实测替换目录值：`Supported` 加上目录没声明但实测可用的位，`Unsupported` 去掉实测不可用的位，`Context`/`MaxOutput` 更高或更低都替换；没有实测的位和上限才用目录值（见 `gateway/route.go` 的 `endpointOf`）。检测必须走网关同一条协议，测到可用才说明请求表达得出来。事实绑定测它时的目录模型、上游名字和**调用格式**（不是端点的第一个格式），`MeasuredFor` 只返回当前配置下各格式自己的条目；`Prepare` 每次重建前发布当前配置和供应商快照的单调 `Routable.Generation`，旧 Generation 的 `Prepare` 被拒绝，因此晚到的路由构建不会把 `current` 改回旧配置或清掉新配置的事实。`Measure` 在端点锁内比较当前配置，旧配置的结果返回 `false`；旧 Generation 的 `Prepare` 不会把它改回旧配置，所以迟到测量仍被拒绝。不落库、不按时间过期，重启或换配置后回到目录值，等下一次检测。合并和读取都在端点锁内，`Observe` 不碰它。路由按实际调用的格式读 `Specs`；对外的模型页和发现接口取所有原生格式的交集与下限，不声称路由会拒绝的支持。
- **质量分与置信度**：`Quality` = `Health` × 已测性能因子的平均；首字延迟 ≤ 1 秒记 1（否则 1 秒 ÷ 延迟），输出速度 ≥ 50 token/s 记 1（否则 速度 ÷ 50），都测过取平均、只测过一个取它、都没测过记 1。没有计入的结局时 `Quality` 恒为中性 1、`Confidence` 为 0，即使不计入结局的尝试已经留下足够的延迟样本（这些样本仍留在 `Latency` 里、供"最快"和"最低延迟"使用，但不改变质量分）；计入结局数达到 10 后证据满，最后一个结局 4 小时后 `Confidence` 线性到 0。试探通过/失败同样计入（`count`），但不进熔断窗口：不满足独立来源。常量是 `scoreLatency`、`scoreSpeed`、`scoreSamples`、`scoreMaxAge`；计算只在 `State.quality`，`MeasuredFor` 不查库；结构事实的 map 只在确有事实时分配。百分位窗口是每条指标一个固定 128 个样本的环形缓冲（`sampleWindow`），`Observe` 在端点锁内写入、不分配；`MeasuredFor` 复制、排序并算四个分位数，只在快照重建的后台运行，路由只读快照里的数组。
- **产品成绩**：题库是编进二进制的 `benchmark-v2.json`，`BenchmarkSet.Version` 和文件字节的 SHA-256（`BenchmarkSet.Hash`）是它的身份；`New` 启动时就解析和校验，改一个字节就必须换文件名和版本，否则 `TestBenchmarkSet` 失败，旧成绩和官方基线也全部作废。每个问题一次生成，运行绑定端点的一个生成格式（chat、messages 或 responses），官方和候选必须同格式；embeddings、rerank 和 legacy completions 不跑基准。判定只用固定运算：`equals`（去首尾空白后精确相等）、`contains`（忽略大小写的子串）、`one_of`（忽略大小写后等于其中一个）、`json_fields`（一个 JSON 对象的指定字段值）、`json_equals`（解析后的 JSON 值相等）；不用正则、脚本或正文里的模型判断。一道题有多个 checks 时按通过的 checks 比例计一道题的分，所以 `BenchmarkResult.Points`/`Possible` 是"题"的数，不是 checks 的数。`RecordOfficialBenchmark` 收一个目录模型在官方直连（平台端点）上的运行，作为该模型所有端点的锚；`RecordBenchmark` 用同一题库的端点运行除以官方运行的分（封顶 100），并把 95% 配对标准误、端点答题覆盖率和运行年龄一起算成 `ProductScoreConfidence`。官方运行没覆盖题库的 90%、没有得分、端点覆盖不足、少于 20 对、旧配置、旧基线或租户端点都返回 false（失败关闭）。成绩和基线落库：`quality.benchmark_baselines` 按 `(model_id, version)` 一行，记官方端点、运行时刻、格式和每题官方题分；`quality.benchmark_scores` 按 `(endpoint_id, version)` 一行，记模型、上游、格式集、分数、置信度、运行时刻、基线时刻、题库 hash 和配置代次 `epoch`；`quality.benchmark_configs` 按 `endpoint_id` 一行，记当前配置和 `epoch`。基线和成绩都只读本二进制 `Version+Hash` 的行，版本在主键里，所以新题库版本的成绩不会冒充旧版本，旧节点继续读自己版本的行。`Record...` 先写库再发布内存，写失败返回 false、内存不变；`Start` 在读健康行之后读一次，`Loop.Tick` 每 5 秒热读（`refreshBenchmarks`），`Prepare` 把配置和 `epoch` 都与端点当前一致、且比当前成绩新的行放进 `State.benchmark`。换配置时同一事务把配置代次加一并删掉旧成绩；成绩行记核对时的代次，写入 SQL 同时比较配置和预期代次，所以即使配置改回旧值、字段重新相同，旧运行也不能借当前代次写入；`MeasuredFor` 也核对代次，换配置或换官方基线都会让旧成绩在 `MeasuredFor` 里变成 0（失败关闭），配置改回旧值或重启也不会复活。启动后第一次 `Prepare` 发现库里的配置与当前权威配置不同会同步它，不要求本进程曾发布过旧配置；已建立配置的节点仍拒绝旧快照翻回。同一端点的 `Prepare` 用端点级锁串行代次复核、配置写库和本地发布，旧快照等到新代次发布后会在写库前再次复核并退出。全新端点的配置行在第一次记录成绩时由 `configForScore` 插入；`Prepare` 只在已有成绩、启动时共享配置与当前配置不同，或已建立的配置变更时写配置行，不为只观察的全新端点快照写库。`RecordOfficialBenchmark` 也走只初始化不存在的配置行，迟到的旧官方运行不会改回配置或删掉有效成绩。当前没有自动发基准运行的循环（要负责人批准这笔支出），`Record...` 是给它的入口，题库、频率和成本见领域文档。实现见 `benchmark.go`、`benchmark_score.go`、`benchmark_record.go`、`benchmark_store.go`，表见 `migrations/00005_benchmarks.sql`，回放样本见 `testdata/benchmark_samples.json`。
- **真伪检测**：健康循环对每个平台的、未熔断的、到期（检测周期默认 6 小时，后台可改，先让恢复试探）的端点发一次 `TestEndpoint`：提示词要求一次 JSON 回答，含原样回显随机十六进制串、两个随机整数之和、一个四位数与三位数的积、一个随机串的倒序和字符数、正在服务的精确型号和版本、模型作者；输出上限 `verifyOutput`（256），用 `TestRequest.Capture` 取回答复文本。判定只在 `judgeVerification`：全部对上为通过；答案里出现目录里的另一个作者、且没有声称的作者，或同一条可识别型号线的变体与声称的不同（如 `gpt-4o-mini` 对 `gpt-4o`、`claude-haiku` 对 `claude-sonnet`、`8b` 对 `70b`）为矛盾；拒答、格式不同、算错、目录没有的别名、传输失败为不确定，不改变上次结论。型号先规范化（去日期、可识别的发布号、提供商前缀，保留型号线、`chat`/`instruct`/`audio` 等功能限定词和变体词；无法识别的后缀不删），相等或只差日期/发布号为相符；只有双方属于同一条可识别型号线（家族和版本等非变体部分相同）且变体不同才判矛盾，无法归到该线的别名、不同型号线或额外功能后缀（如 `gpt-4o-audio-preview`、`gpt-4.1-mini` 对 `gpt-4o`、`gpt-custom-mini` 对 `gpt-4o`、`llama-3-70b-instruct`、`llama-2-70b-chat`）只算不确定。判定只接受一个可解析的完整 JSON 对象并逐字段精确比较；纯散文、行列表和片段不参与通过判定。一次矛盾立即清掉 `Verified`（失败关闭），连续 `verifyFailures`（3）次才判定假冒并发一次 `endpoint_fake` 严重告警；通过清空矛盾计数并解除告警。重查从首次重试（默认 15 分钟，后台可改）按次翻倍到检测周期，带 ±10% 抖动；后台改周期或首次重试时，已排定的下一次检测按上次检测时刻和结果重算，执行中的检测完成时按新值排。结果按节点保存在 `State.verify`，不落库，重启后未知。证据绑定检测时的目录模型、上游名字和格式（`claim`）：投影里任一变化就清掉通过和矛盾计数、解除假冒告警并立即重查，检测途中变化则丢弃结果并记 `stale`；路由读 `MeasuredFor`，配置不符时直接不认这次通过。`Config.Identity` 由 `cmd/axiom` 从目录快照实现，返回声称的作者的显示名、目录里其余作者的显示名、目录模型的标识（`Model`，即目录 slug）和厂商原生有效名（`Name`，目录有公开原生名时）；比较对象是目录模型，不是可能被供应商别名映射的上游名字。目录不认识模型、目录模型标识或上游名字为空时这一轮不检测，15 分钟后重试。`AXIOM_MODEL_VERIFICATION=off` 关掉检测，所有端点保持未验证（`cmd/axiom` 的 `verify` 依赖为 nil）。
- **启动与时钟**：生产由 `cmd/axiom` 在监听前调用 `Start`，一次加载全部健康行、官方基线和成绩；首次出现且没有持久行的健康端点不再逐个读库。只有被内存回收过的端点再次出现时才单独读回；`Config.Now`、`Config.Rand` 可替换，默认使用系统时钟与并发安全随机源。`Loop.Run` 每秒调用 `Tick`，失败退避。`Tick` 与 `Drain` 只有一个调用者；生成 worker 只通过有界结果通道回报。退出等待已支付的生成读完、写成本，再刷新剩余变化；试探不占调用的结算预留连接。
- **实时路由**：快照持有 `Live` 的指针，`Routing` 返回熔断时刻和恢复后的临时上限，`Offline` 返回是否已在失败试探后下线（`Opened` 且 `Warned`）。`Prepare` 在后台为再次出现的端点恢复被回收的内存状态；不从这里定期加载健康状态，产品成绩和基线则从 `refreshBenchmarks` 留下的 `m.scores` 采纳。`Pauses` 由 routing 实现，经组装层接入。
- **持久化与试探**：迁移 `00001_health.sql` 建 quality 的健康表，`00002_probe_settings.sql` 建平台一条试探设置记录，`00003_probe_backoff.sql` 把退避级别上限从 5 提到 10，`00004_source_classes.sql` 建来源类别，`00005_benchmarks.sql` 建官方基线、成绩和端点配置代次；平台范围读写。设置记录留空即用代码默认值，保存时校验并审计，节点每 30 秒重读。健康表的时间用 Unix 纳秒整数，零表示未发生。窗口不落库。每次变化按旧 `epoch` 条件更新并写事件；失败重试保留同一代际，落败的一方丢弃依赖它的排队变化。试探租约两分钟，覆盖 45 秒生成与事务余量。租约认领不推进健康代际，真实请求恢复不因同时认领而作废；试探结果写入额外检查认领者、精确到期时刻与代际，超期或旧认领的结果不能恢复端点。每节点默认最多四个试探、滚动一小时最多 600 次（后台可改），暂停（含 `Funds.CanPay` 的供应商余额拒绝状态）、陈旧与自带端点不消耗预算；每次用原生格式、16 token 上限，按前次凭证轮换，成本和检测审计同事务。拿到事务连接后，剩余期限不足完整生成期限加五秒写入余量时不发生成，按不确定结果顺延，避免等待连接吃掉已付费生成的记账时间。
- **交接与事件**：`Observe` 直接在固定结构里更新测量与窗口，只有状态变化进入容量 1024 的值通道；交接满时推迟新变化并计数，已接受的变化保留重试。事件与状态原子提交，反复事件在十分钟内合并，按天清掉 90 天前事件；健康变化和平台持久信号同事务，重启不丢已提交的告警。第一次失败的试探把端点标为离线并发 `endpoint_still_down`（旧版本已会解除的种类，滚动升级可解），恢复同事务解除它；没有试探的端点（自带、只有直接格式）不自动离线，真实请求成功即恢复；恢复信息立即完成；预算告警用 `Config.Node` 的稳定节点名，只在顺延与恢复的边沿发信号，启动后的首次正常调度清理旧进程遗留。模型不可用只检查平台端点。离开可路由集合一天的内存状态回收，持久行保留；先建 ID 集合再持锁扫描，回收是线性工作，保留已回收 ID 供再次出现时读库。
- **指标**：`axiom.quality.unclassified`（端点范围、状态码 < 500 的 `Unknown`）、`axiom.quality.suspected_block`（疑似出口拦截）、`axiom.quality.verification`（`result`：passed、contradicted、inconclusive、stale、deferred），都不带端点标签。试探时长只计带真实请求 ID 的结果，未发出请求不写零时长。

## 判定的输入从哪来

- **作用范围和原因**：适配器的分类（[suppliers 的「调用面」](../suppliers/README.md#调用面)）。只有端点范围的能计；suppliers 把原因的类型都以别名公开（`suppliers.UpstreamError` 等），本模块按它们穷尽地判（`gochecksumtype`），加一个原因就要在这里决定它算不算。
- **流内错误的类别**：`protocol.FaultOf`。三种格式的出错事件按 `error.type`、`error.code`、`code`、`response.error.code` 归类，工具调用参数不是 JSON 是单独的一类；其余读失败（断流、格式错）是 `FaultBroken`。类别只给本模块判健康用，提交前换不换端点不看它（那是 #311 E2-4）。
- **超时**：网关的 `cutOf` 从尝试的 context 原因读出：`errHeaderWait` → `HeaderWait`，`errIdle` → `Idle`，其余（调用最长时间、退出、追加没批准、客户端离开）→ `Ours`。

## 决策与理由

| 决策 | 理由 |
|---|---|
| 健康度、质量分、置信度、延迟、吞吐在快照重建时按值拷进 `routing.Endpoint`，不是指针 | 端点评估的设计让快照持有指向实时状态的指针，是为了熔断在下一次 `Plan` 就生效（H2）；健康度和质量分只影响权重、粘性和质量优先排序，晚一次重建（≤ 5 秒）无害，按值拷贝不用改 routing 的类型和全部测试。H2 仅给实时熔断和慢启动加指针，测量仍按值复制 |
| 实测的能力与上限也按值拷进快照；按实测替换，按配置绑定，不按时间过期 | 能力与上限只在检测确认后改变，不是每次尝试都变，晚一次重建（≤ 5 秒）可以接受，按值拷不用让 `Plan` 读 quality 的锁。按实测替换是产品要求"检测后用实测值替换"：目录只是基线，测到能用就加、不能用就减，上限更高也放行；只收紧会让目录的旧值永远盖住实测。检测走网关同一条协议，误判的风险由检测的多次确认承担。不按时间过期是因为结构事实不会自己恢复，回退到目录会把证明做不了的请求重新发过去；换上游名、模型或格式立即作废，后来的检测可以翻转 |
| 平均值的第一个样本直接作为平均值，错误率从 0 起 | 与 sub2api 相同（`openai_account_scheduler.go` 的 `report`：首字时间以 NaN 起、第一个样本直接写入；错误率以 0 起）：没有样本时健康度是 1，第一个延迟样本不被一个任意的初值拉偏 |
| 质量分由 EWMA 合成，未知是中性 1 加置信度 0，不是 0 分 | 排序现在就需要一个来自实测而不是自报的质量值；可靠性、首字延迟、输出速度已经覆盖"快不快、稳不稳"。未知记 0 会让没测过的端点永久垫底（和"最快"同一个问题），记 1 又会越过有证据的端点，所以用中性值加一个单独衰减的置信度，由路由分组处理。绝对基准（1 秒、50 token/s）而不是按同一模型互相归一，是因为 `MeasuredFor` 只看到单个端点，跨端点聚合会依赖模型规模和目录里多数模型都没有的输出速度规格 |
| 产品成绩用嵌入的版本化题库、按文件 hash 作废旧成绩，而不是后台表 | 固定题库要能让所有端点、所有节点和官方基线跑同一套题；放代码里随版本发布，`version` 加 SHA-256 把"改了题"变成"换了题库"，不需要迁移、编辑器或热读，也不会有人改了一道题却让旧成绩看起来仍可比。后台增改和轮换以后需要时再加，届时仍以 hash 作废；现在的题库不通过任何接口暴露，`New` 在启动时校验 |
| 官方直连的运行锚定 100，候选超过官方封顶 100 | 产品原文是"以官方直连为 100"，预设的 `min_score` 是 0–100；候选在少量题上超过官方是抽样噪声，不是"比官方更好"的证据，封顶让阈值和公开字段的含义保持稳定。官方运行自己也要先过 90% 覆盖和得分非零，否则不能当锚 |
| 每题一次生成，用配对置信区间而不是重试到满意 | 基准题成本按生成计；多做几遍只降低抽样噪声，不如把同样预算放在更多题上。置信区间用同一批题上的配对差算 95% 半宽，再乘端点答题覆盖率和时间衰减；重试只用于传输/限流这类没有作答的题，不能因为答错就重试。20 对和 90% 覆盖是下限，低于它没有成绩（失败关闭） |
| 产品成绩和官方基线落库，且这一版不自动发基准运行 | 成绩要跨重启和跨节点，否则一次运行只对发出它的进程有用，重启后所有端点都掉回"没测过"。写库和读取都在调用路径之外：`Record...` 同步写一行再发布内存，失败返回 false、内存不变；`Start` 读一次，`Tick` 每 5 秒热读，`Prepare` 只采纳配置和代次相符且比当前成绩新的行。成绩和基线带题库版本和 hash，旧节点只读自己版本的行；配置代次在换配置时加一并删旧成绩，配置改回旧值或重启都不会复活作废的成绩。代价是三张表的小写入和每 5 秒一次小表全读，换来成绩跨进程可用。自动发运行仍会花钱，按负责人保留的支出决定，先把评分和记录入口做好，运行循环等批准后再接；租户端点不测，花的是 key 所有者的钱 |
| 产品成绩不复用 `Quality`，两个字段各自过滤 | `Quality` 回答"快不快、稳不稳"，来自真实流量和试探的 EWMA；产品成绩回答"答得好不好"，来自固定题。混在一起会让一个又快又稳的假端点通过"达到官方水准"；`:exacto` 的 `Verified` 也继续单独给真伪，三者不互相冒充 |
| 试探结果计入质量分和健康度，但不进熔断窗口 | 试探是一次真实生成，理应影响"这个端点现在多好"；但它由我们自己发出，不满足摘除要求的独立来源，所以只计分和恢复，不参与熔断判定 |
| 真伪检测用精确型号自报和已知答案，结果按节点保存 | 只核对作者挡不住同厂商换便宜型号（#560）；官方基线能测版本和量化，但题库、采样和版本管理要一整套后台数据，短期交付不了。精确型号自报加随机已知答案复用试探已有的生成通路、预算、退避和受控时钟，能把"模型自己报出另一个名字"的降级挡在 `Verified` 之外；tokenizer 计数和 logprob 指纹需要参考部署或格式支持，留作第二层。不落库是因为调用路径不查库：落库要新迁移、写器和跨节点采纳，属 H3/H5；重启后未知、`:exacto` 失败关闭，宁可少接也不在没证据时放流量 |
| 窗口中的来源与凭证用固定大小 UUID，不另作哈希 | 每项固定大小、不分配，避免截取 UUIDv7 时间前缀导致独立来源碰撞；标识只在本节点窗口，不写事件或指标标签 |
| 阈值（4k、32k、50 token、5 个样本、30 分钟、α、1 秒、50 token/s、10 个结局、4 小时、五分钟与 128 个样本）是代码里的常量 | 设计说它们是后台配置、默认值在代码里；后台在 H3 才有，现在只有默认值；全局模式额外由启动变量控制 |
| 吞吐只取正常结束、且判为成功的尝试 | 设计规定"正常结束"；断流的尝试的输出 token 是估算，结束时刻也不是生成结束的时刻 |
| 判定按"客户端已走 → 调用自己的原因 → 适配器的失败 → 正常结束 → 空闲 → 流内类别"的顺序 | 前两项能解释它们之后的任何失败（取消引起的断流、我们的期限），先看它们才不会把取消算成端点的错；但客户端离开前已交付首段内容（`Delivered`），或之后读到上游正常结束且有内容，是成功：端点在正常回答。只在客户端离开后才来的内容不算交付，之后断流是"客户端已走时的失败"，不计 |
